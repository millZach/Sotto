# Sotto domain context

Sotto is a desktop dictation app with manual coding threads across native providers. This file is the glossary for that domain. Use these terms in issues, tests and code; do not drift to the synonyms each entry lists as avoided.

**Sotto Owl.** Sotto's preview release track and its builds, for Windows, Apple silicon Macs and Linux on Omarchy, installed in place of Sotto with the same local data. An Owl build calls itself Sotto Owl where the running build is named (its window title, the tray's tooltip and the version lines in Help and Settings) and shows the Sotto mark alone, as a larger tile, where stable shows the mark beside the wordmark, under its night sky in the Threads sidebar, except on macOS, where neither track shows a mark beside the traffic lights. Sentences in which Sotto is the app or the speaker keep "Sotto". Watcher is the coordinating thread's name, a different thing. Avoid: "Owl app" for a separate installation, "Owl" for the coordinating thread.

**Stable release.** A release from a clean, CI-green commit on main. Owl features remain behind their switch until Zach sends them to stable; everything else goes straight to stable. The version advances past the newest published stable, normally by the next patch. The Release pull request records the shipped version afterward (ADR-0072).

**Owl feature.** A feature Zach has chosen to keep in Sotto Owl until he is confident it can go to stable, listed in `src/shared/owlFeatures.ts`. Stable shows and starts none of it while keeping its saved records whole (ADR-0072). Watcher was the first; on October 23, 2026, Zach sent all nineteen then on the list to stable, and 0.1.40 is the first stable to carry them. Those entries stay as the record. Features added to the list after that decision, recent projects on a new thread (`recent-projects`), the switch that hides the creature (`creature-toggle`), **night falls** (`night-falls`), showing a linked file in its folder (`reveal-linked-files`), the **interface language** (`interface-language`), the **slim composer** (`composer-shrink`), the Cursor provider (`cursor`), **work across machines** (`cross-machine-work`) and the DeepSeek Harness provider (`deepseek`), are held in Owl until he sends them.

**Held provider.** A thread provider an **Owl feature** keeps off a run where that feature is off, as stable 0.1.39 and earlier hold Muse and OpenCode: nothing of it is shown, started or sent, its saved threads, settings and drafts stay whole for a run that has it, and every refusal names it, as in "Muse is available in Sotto Owl. Open an Owl build to continue. Nothing was sent." Muse was the first and OpenCode the second; Cursor, the third, and DeepSeek Harness, the fourth, are held on stable now (ADR-0128, ADR-0138). A refusal that touches several names them all: "Muse and OpenCode are available in Sotto Owl. ...". Each is one entry in `src/shared/heldProviders.ts`, and one gate in main asks the held set (ADR-0079, ADR-0087). Avoid: "held thread" and "held action", which a thread's live work already means; "disabled provider", which is one the user turned off.

**Dormant thread.** A saved thread whose Owl feature is off in the running build. It is hidden and cannot receive work, while its organization, history, drafts and pending records stay whole for a build that has the feature. Clearing ordinary history leaves dormant threads alone. A disconnected ordinary thread is not dormant.

**Sending a feature to stable.** Zach's decision to make an Owl feature available on both tracks. The next stable release carrying that decision turns the feature on (ADR-0072).

## Threads

**Watcher gate.** Whether Watcher is available in the running build: on for Sotto Owl, and on for stable from 0.1.40, since Zach sent it to stable (ADR-0072). A stable build with it off, 0.1.39 and earlier, shows and starts none of Watcher, including Watcher history, while keeping its saved records in main and settings whole for a build that has it. Pane layout, focused pane and selected thread are renderer view state; such a build treats a hidden Watcher as a missing thread and does not preserve or restore that view.

**Watcher.** The one current native agent thread on a computer, using its provider's own tools and settings and Sotto's bounded thread tools (ADR-0073). The user chooses its permission mode, remembered separately from ordinary threads. It coordinates workers and reads natively. A worker it starts gets no more permission than the user's new-thread default; a send, queue or steer to a thread leaves the thread on the permission the user gave it, however wide (#1145). If its own turn changes files, Sotto marks that reply with an **own-change line**. Earlier conversations become Watcher history when its provider changes. Its guidance grants no permission and it answers no thread's request card.

**Standing watch.** A durable choice to let Watcher observe and manage a particular thread until Stop watching, or until **Settle finished threads** lets it go. It outlives an individual Watcher request and a restart. Watching a thread does not send it a prompt or answer its cards. The number of watches has no limit, and since October 19, 2026 neither has the number of threads Watcher starts (#1183).

**Settle finished threads.** A Watcher setting under Settings → Watcher, on until the user turns it off: Watcher settles a thread under a standing watch once its work is done, then stops watching it, quietly, with no notice and no news. Done means its last turn completed, nothing runs or waits on the user, there or in a thread it delegated to, nothing is queued for it or on its way from Watcher, every pull request it has or babysits is merged or closed, and Watcher has heard all of its news and its own turn has ended. A turn the user sent there counts like any other. Each finished turn is tried once; a refused settle waits for the thread's next. It settles a paired host's thread the way the user's Settle does from this computer. Avoid: "Auto-settle" for it, which is **Auto-settle merged threads**, any thread at rest whose pull request merged, watched or not.

**Watcher history.** An earlier Watcher conversation retained for reading when its provider changes, or when the user starts a new Watcher with **New Watcher** in Watcher's composer. It cannot be resumed as Watcher.

**Watched thread.** A thread Watcher watches: one under a **standing watch**, which the user gives it with **Watch** or Watcher takes with `watch_thread` when the user asks for it in a message to Watcher, or one taking part in an active Watcher request. Main marks each row of Watcher's projection `watched`, and the room, the Threads page and the iPhone take that mark as the answer. It can be a thread the user started or one Watcher started, on this computer or a paired host. It is labelled "Watched by Watcher": the owl right after its provider logo, in its row's muted text colour, in the sidebar, the Overview, Watched and its pane's header, where that owl is an image. **Watch** in its pane's header and the owl among its sidebar row's actions and at the end of its Overview row are toggles, pressed while it is watched (Zach's pick on October 13, 2026, watch B); a press acts at once, and a toast above the composer says so, with Undo. Before a new thread's first send, **Watch** sits among its composer's option chips, after its permissions; pressed, it asks main nothing until main takes that first send, which then puts the thread under a standing watch the same way. A refused send keeps it pressed; a send main never confirms drops it, and the pane header's Watch is left. Pressed while the thread is already watched, it stops the watch at once. On the desktop nothing under its composer says it is watched; the pressed Watch does (removed at Zach's request on October 24, 2026). The iPhone's reply box still says it. The user's own send fences what Watcher had prepared, and until that turn ends Watcher can only steer it; the thread stays watched and stays Watcher's until the user stops watching it. Once the user stops watching, Watcher cannot watch it again by itself: the user hands it back with **Watch** or in a newer message to Watcher. Sotto's own messages, such as a wake-up or a delegated brief, are never the user's send. The same send takes over a thread watched only through a request, which then is no longer watched. Opening it and answering its request card change nothing. There is no limit on watched threads. Distinct from the host's **watched set**, which keeps provider sessions for panes and queued user follow-ups.

**Watcher's room.** The third room, opened by the owl between Dictate and Threads on the switch. It has no sidebar (Zach's pick on October 11, 2026): the Sotto mark's tile and its night sky in the window's corner (on macOS, no app mark beside the traffic lights: no tile before Watcher starts, and its context button wears Watcher's owl instead), Watcher's own thread pane under its header, the **needs-you line** and, with Work across machines, the **machines line**, a **beside pane** when a thread is opened, and the **header switch** at the header's right end. Watcher's header has its name, **All threads** with the count of other threads, which opens the Overview over the room, and, once Watcher runs, **Conversation**, **Watched** with how many threads it watches, and **Visualize**, which shows **Watcher's picture** in the conversation's place. It has no limit to set: **Threads in flight** and More Watcher actions, which held it, went on October 19, 2026 (#1183). **Watched** shows each watched thread as a card in the conversation's place, grouped as the Overview groups them, with what Watcher last did and **Stop watching**. Its composer is labelled Watcher message and floats over the conversation as frosted glass, with the **night scene** under it, and slims as a thread's does (**slim composer**); it has **Watcher's permissions** after its model and reasoning: the modes the Threads composer offers for Watcher's model, with a line each, which main remembers apart from ordinary threads for the next Watcher (Zach's pick on October 13, 2026, control A). Its replies are signed Watcher, one in which it changed files itself carries an **own-change line**, and each carries a **receipt card** for every action it took in that turn; a **takeover line** follows the turn in which the user took a thread over. **Stop all** sits at the header's end while threads Watcher started are running. The first time, the room shows Watcher's composer ready, with a model chip offering the user's own Codex, Claude Code, Grok Build or Muse models, and the first message sent starts Watcher. The room keeps its own view: it selects nothing on the Threads page except through Open in Threads or Shift with a press, and the Threads page does not list the current Watcher. Avoid: "Agents room", "command center", "Watcher page".

**Night falls.** The move between Dictate or Threads and **Watcher's room** (Drake's pick on October 23, 2026, variant 9 of `docs/prototypes/watcher-room-transition-prototype.html`): a band of text characters sweeps across the window, the room being opened shows behind it, and the room switch's owl rides it from the sidebar foot to the header switch, or back. It has two looks (ADR-0119, decision 6): **Band**, that band, and the default; and **Stars**, a line of `*`, `+` and `·` in the theme's accent along the same front, with a faint trail of text characters behind it in the room being opened. Both reveal the room the same way and take the same time; only what sweeps across differs. Settings → Appearance turns it off and sets its look and its speed; reduced motion skips it, whichever look is set. Only on a move into or out of Watcher's room from Dictate or Threads; every other page change swaps at once. Avoid: "transition" alone, "wipe"; "Stars" for the night scene's stars, which are Watcher's room's own sky.

**Night scene.** The night drawn in text characters in the side margins of **Watcher's room**, beside the conversation's column, on Conversation and Watched; it steps away while Visualize shows, which draws a night of its own across the pane, **Watcher's picture** (Zach's picks on October 21 and 22, 2026, `prototype/watcher-owl-scene` and `prototype/watcher-owl-family`). Hills, a river, two trees, stars and a moon in the theme's text colour, with the accent in the moon's glow, the river, a few stars and the owls' eyes. The sky and the hills run on under the column at 85% and under Watcher's glass composer, and never move for the words passing over them; the scene never blinks, keeping its last frame on screen until the next is drawn (ADR-0126); each word carries a soft glow of the canvas, and no glyph in the column is stronger than the conversation's words allow at 4.5:1, which leaves the column quieter than the margins. So the scene can show stronger there, the conversation's names and times are in the secondary text colour rather than the muted one (the user's picks on October 23 and 24, 2026, variants D and D2 of `docs/prototypes/watcher-floating-composer-prototype.html`, ADR-0126; D replaced the gap kept round each line of words, which shifted as the words scrolled). The trees and the owls' perches stay in the margins; a ripple runs on under the column, and an owl crossing it shows faintly behind the words, as quiet there as the hills. Watcher's owl lives in the left tree and now and then, at random, flies to the other tree or onto a branch off the composer, and back. Each watched thread has a **thread owl**: on the right tree's long branch first, then Watcher's tree, then the ground, with "+N" in the last place when they run out; awake while the thread works, asleep while it rests, glowing in the accent while it waits on the user. A new one comes out of a whirlpool in the moon, which ripples; a settled or unwatched thread's owl flies back into it. A margin under 160 pixels shows the thread owls as a rail of eyes instead of trees. A click in the open margin sends out a ripple, and Watcher's owl looks toward it. With reduced motion nothing flies: owls appear and fade, and nothing moves but a click's brightened spot. It is a different thing from the **night sky**, the stars behind the Sotto Owl tile. Avoid: "owl scene" (Owl is the release track), "animation", "background".

**Overview.** The list of all other threads in Watcher’s room, opened over the room by All threads in Watcher's header and closed with Escape, grouped by what the user must do, with source and read times. A press on a row opens the thread in the beside pane, Shift with it in the Threads room; a waiting thread's row offers Open to answer. It is a projection, not a work queue or attention store; its groups are Needs you, Ready for review, Working, Landing, Quiet and Idle. Needs you holds the threads waiting on a question, a permission, a look at a failed turn or a prototype to review (**Prototype ready**). Avoid: "Kanban", "board".

**Needs-you line.** The one line under Watcher's header naming each thread that needs the user and why: a question, a permission, a failed turn or a prototype to review. Each name goes to that thread's **watched request card** when Watcher's conversation on screen holds it, and otherwise opens the thread in the beside pane at what it waits on. It is gone when nothing waits. Avoid: "inbox", "alerts".

**Machines line.** The line under the **needs-you line** in **Watcher's room**, always there while the Owl feature Work across machines is on (#1032; Zach's pick D "Names" on October 23, 2026): every **machine** with its **working threads**, "This computer 2 working · forge 3 working", and "1 starting" for **work placed but not started**. A problem adds words after that machine's count, in the needs-you line's warning ink: "may slow down" above ten, "busy", "short on memory", "load unknown" only when neither CPU nor memory is known, or "not connected"; names and counts never change colour, and nothing in it is a pill, chip or meter (ADR-0110). Each name opens that machine's panel: its system, **live load** and when it was read, why it reads unknown, what works there and who started it, and Change where new workers start. A narrow room, and the iPhone, keep only the machines with a problem and count the rest, or with nothing wrong say only how many machines and how much works on them. It reads Watcher's own `list_machines` only when Watcher places work or the user opens a machine's numbers, in its panel or in Settings, never on a timer (Zach, October 23, 2026); whether each machine is connected comes from the saved hosts, and working threads from the window's own list. Avoid: "machine chips", "status bar", "fleet".

**Beside pane.** A thread opened in Watcher's room: its real thread pane, to the right of Watcher's, with its own request cards, draft and reading position. There is one at a time; opening another replaces it, a **Fork from here** made in it opens there in its source's place, and closing it stops nothing. Open in Threads takes the thread to the Threads page, selected. Distinct from a thread pane on the Threads page, which is part of that page's own arrangement.

**Header switch.** Watcher's room's way off the page, since it has no sidebar: at the right end of Watcher's header, after Stop all, the switch as icons, as the sidebar foot draws it, then **More**, a menu of Usage, Settings and Help (and Memory while memory is on) and, under a rule, the update control's press, named as the control is. More wears a dot while an update is found, downloading or ready to install, and its name then says so. Linux has no update row. It replaced the **floating switch**, a bar centred at the bottom of the room (Drake's pick on October 26, 2026, D of `docs/prototypes/watcher-head-strip-prototype.html`), so the composer sits at the window's floor. Every other page keeps the sidebar foot.

**Own-change line.** The one quiet line under a Watcher reply in which Watcher changed files itself (Zach's pick on October 13, 2026, mark B): "Watcher changed 2 files itself.", then its reason, read only from exactly one whole, unfenced `Watcher change reason: <reason>` line of that reply, or "It gave no reason.", with the file names on request. The reply itself is shown without that line, everywhere it is shown or copied, since the own-change line already says it; any other text is left as written. Sotto draws it from the provider's own file-change records for that turn, never from a shared checkout's diff, so it is there whatever the reply says. Avoid: "badge", "warning".

**Watcher request.** A particular user instruction to Watcher, with main's identity, root user-message reference and budgets. Qualify it to distinguish it from an agent's pending question or permission request; retries and wake-ups keep its identity and budgets. A standing watch can authorize a fresh bounded continuation after observed news; stopped requests stay stopped. Direct user input fences an earlier automatic continuation, and until its turn ends Watcher can only steer it. Explicit Queue to Watcher joins the newest request, and refuses before the first actual Send; when it is delivered, an instruction whose request stopped or closed while it waited, or that was queued after a takeover fenced that request, starts its own request instead, so every Send of the user's reaches Watcher under an active request. The user can steer Watcher whenever it works, from the iPhone too, where Send steers while Watcher's turn runs and, when it cannot, queues the message to go next as its own turn under a request of its own (#1229). A steer into a turn that answers an active request of the user's is part of that request; one into any other turn, as one Sotto's news started, opens a request of its own, which later steers into that turn join. A message queued while Watcher reads news joins no request and goes as its own turn. An uncertain delivery keeps its slot through takeover until reconciled.

**Watcher request note.** What main tells Watcher with each user Send besides what the user typed: the Watcher request that message started and which host is this computer. It goes beside the message, through the provider's own context channel for that turn (Codex's turn context, a Claude Code prompt hook), and names no projects; Watcher calls list_projects when it needs one. Grok Build and Muse have no such channel, so their prompts carry the note as one bracketed line after the user's words, and so does a steer that opens a request of its own, since a steer has none on any provider; Muse also gets Watcher's instructions ahead of them, and keeps the message alone as what it shows. The user's bubble, Copy and the phone show the message as typed, without that line. Older messages, sent when main appended a routing footer listing every project ID to the user's text, show without it too; the provider's own history keeps what it was sent. Avoid: "tag" or "footer" for the note.

**Merge queue.** The open pull requests of the threads Watcher watches that are not drafts and whose checks passed, oldest pass first by when Sotto first saw them pass, as `read_state` gives them (#1274). Sotto works it out from GitHub's reads; nothing merges because it is queued. Avoid: GitHub's own merge queue, which Sotto does not use.

**Pending settle.** A watched thread whose work is done except for an open pull request, or for Watcher hearing its news and resting, which Settle finished threads will settle once that holds no longer. `read_state` lists each with what holds it, only while the setting is on (#1274).

**Watcher state.** What Watcher must not lose when Sotto compacts its conversation: the user's pending decisions and the standing rules the user gave, in the user's words, and the issues it filed, which Watcher keeps with `keep_state` as **kept lines**; and what Sotto works out from live data at each `read_state`, so it cannot go stale: the threads Watcher watches with what each waits on and its open pull requests, the merge queue, the pending settles and what waits on the user. Watcher reads it back with `read_state`, first thing after a compaction, with a stale flag on any open kept line that names a settled or unwatched thread or a merged or closed pull request, or that it has not added or edited for three days. Sotto compacts Watcher's conversation once it passes **Compact Watcher at** in Settings › Watcher, 400,000 tokens unless the user moved it (200,000 to 1,000,000), while Watcher rests. The kept words are saved only while Keep local history is on. Avoid: memory, which is the gated Memory feature.

**Kept line.** One line of Watcher state that Watcher keeps: a pending decision, a standing rule or an issue it filed. Each has an ID, its list's letter and a number Sotto never gives twice (`d3`, `r1`, `i12`), and Watcher adds, edits, closes or drops one at a time. A **closed** line carries a note of how it ended and stays out of its list's thirty open lines until Sotto clears it a day later. Avoid: note, for a kept line, in user-facing words; Watcher's notes are the kept lines as a whole.

**Waiting on the user.** What a watched thread cannot go on without the user: an open question or permission card, on it or on a thread it delegated to, or a prototype waiting for review. `read_state` works it out live as `waitingOnUser`, and Watcher tells the user something waits on them only from that list, never from its kept lines or earlier news. Avoid: pending, which also means a pending settle.

**Watcher news.** Sotto-observed changes in watched threads, batched through the master's existing follow-up queue after user prompts. News is separate from worker words and grants no permission. Sourced evidence names its observer, target, turn/head/checkpoint identity when known, observation time, freshness and availability. Git totals describe the working copy, not a turn. Quiet requires twenty minutes of fresh connected work without progress; a pending request or disconnection is not quiet. News wakes Watcher only for what needs it: a turn finished or failed, its work settled, a question or permission card appeared or, once Watcher had heard of it, closed (`request-closed`, which says the user answered only when Sotto saw their answer go, and carries none of it), a prototype waits for the user's review (`prototype-ready`, once for each **Prototype ready** source while its mark stands; it says only that the user has a prototype to review, and answers and approves nothing) or no longer does (`prototype-closed`), a thread went quiet, a pull request's checks failed or passed, it merged or closed, it conflicts, or a review or comment came, the user took a thread over, Sotto **restarted** threads a usage limit had stopped (`threads-restarted`, naming unwatched threads too; Owl), or one of Watcher's own sends failed, was refused or may not have gone in a way its tool's answer did not say. A question, a permission request or a failure, failing checks included, goes within seconds; other news waits for more close behind it, up to a minute. A finish whose work still runs waits for its work-settled news, a question or a failure, or twenty minutes; one that goes after twenty minutes with its thread idle opens "Held N minutes, thread idle", so Watcher reads that thread rather than wait on. A thread that a watched thread delegated to makes no news of its own; its cards come as news of the thread that delegated it. A wake-up's note also carries the start of a finished turn's reply, labelled as the worker's words and as whole when it is, read as it is sent and never queued; a whole reply is enough for Watcher to act on without reading the thread. **Work-settled** news comes once per turn that finished with background work, working sub-agents or monitoring still running, when that work reaches zero; until then that turn is not done. Unknown work, such as sub-agents a restart could not see end or a paired host that does not report the counts, is not zero. A thread's own working-copy, Git and checkpoint changes ride with the next end of its turn not yet told, its finish or, for one that finished busy, its work-settled news, and are dropped when nothing differs from what Watcher was last told; an ordinary delivered receipt is no news, and nor is one for a send refused because the user sent to that thread themselves. A pull request's facts a wake-up carried are not told again unless they change, even when that wake-up's send is unknown; failed checks are the exception, since a failure is never lost. Avoid: worker claims as verified evidence. Checkpoint facts keep their capture identity rather than guessing a native turn from the current thread.

**Delegation.** One brief an agent sends to one thread, and its **outcome**: a Watcher start or send, or an ordinary thread's (ADR-0081) `delegate` to a thread it starts, its **delegated thread**. A delegated thread is an ordinary Sotto thread linked to the thread that started it; it can delegate once more, and the threads it starts cannot (two levels). It is listed in that thread's **subagent roster**, not the sidebar, whose row for the thread at the top says when one below it needs the user; settling a thread settles them with it, and one still open below a settled thread stands in the sidebar on its own. A delegation carries no authority: the user still answers every question and permission on the thread that asks. Avoid: "task", which a monitoring task, a browser task and a provider's own agent tasks already mean; "subagent" and "subagent assignment", which are a provider's own agents; "job", a **provider job**'s.

**Delegated work.** A delegating thread's **delegations** as its transcript shows them: a row each in the **Worked for** fold of the turn that delegated (Drake's pick on October 23, 2026, variant 2 of `docs/prototypes/delegated-work-prototype.html`), or under the reply while the turn runs or has nothing else to fold. A row names the kind of work as a mark and a word (**Review**, **Muse review**, or the title of its kind of work, such as **Building** or **UI work**), the delegated thread as a link that opens it, its provider and machine, where it stands (an outcome, or **Starting**, **Needs you** and **Returned** where the row knows more), and a line on the wait, what it waits on the user for, or why it was refused. The Worked for line counts it, and what still works when the reply ends also stands under the reply, after "Still working after this reply", while the fold is closed. Under the last reply, the provider's own **background work** stands there too, as rows that name the kind of agent work (**Subagent**, **Workflow**, **Teammate**, **Remote agent**) and its label, read **Working** and open nothing; those rows are not delegated work, and they keep to delegation's Owl switch. When that reply has nothing to fold, its open delegations go under the heading with them and the settled ones stay rows above it. Read from delegation's own record and the delegated thread's pending requests, never from the words of a reply. A row whose thread the window no longer lists has no provider to read, so a Muse review there reads **Review**. It replaced the delegation cards under a reply on October 24, 2026. Avoid: "subagent" for a delegated thread's row, which is a provider's own agent.

**Outcome.** Where one delegation stands, as Sotto observed it: `working`, `background` (the turn ended with background work still running; once its thread has sat idle twenty minutes without that work being seen to end, the delegating thread is told once that it was held, with the start of its last reply), `answered`, `failed`, `stopped`, `paused` (the user's own turn in that thread holds it) or `unknown` (Sotto cannot prove what happened, as after a restart mid-turn; never guessed as answered). A thread's delegation has one more, `refused`: main turned it down under ADR-0081's rules as it was asked for, so nothing was started or sent, and it holds no slot and no budget. It ties the brief to the turn that answers it and names the reply, never carrying its words; once Sotto proves which turn a reply belongs to, reading history again cannot give it to another turn; the reply is read when asked for, or goes with the news that it answered, labelled as the thread's words either way. Retries and reads charge no budget. Avoid: "status", which is a thread's; "result" for the outcome itself.

**Worker role.** A kind of work and what it starts on: a model, an effort and a permission. There are six: **Orchestrating**, which is Watcher itself, and the five a start names, Building, UI, Code review, Research and Computer use. Settings, under Watcher, has a card for each (ADR-0091). Each role has its **defaults** in order, and the first whose model is ready is in force, so a role follows the providers that are connected; when the one it was on disconnects, it starts new work on its **next default**, the first after it that is ready. A row becomes the user's **choice** once any of its three settings changes; a provider coming or going never overwrites it, and Reset to defaults puts the defaults back. Watcher's `start_thread` names a role and `delegate` names its kind of work, and main fills in what the start leaves out, never wider than the ceiling; the user's words in a request override a role for that request, and the receipt says so. Orchestrating's model and effort are Watcher's own, the same choice its composer's chips show. A thread's own sub-agents follow the roles too: Claude Code and Codex threads get one named agent per role on their provider (`sotto_building` and the rest), held to the thread's permission, and the instructions of every Claude Code, Codex and Grok Build thread on this computer say which agent, model or delegation each kind of work goes to; Muse, Devin and paired hosts' threads are not told yet (ADR-0091 decision 9). An Owl feature, sent to stable. Avoid: "agent type", which is Codex's word for its own sub-agent roles; "profile", which is Devin's; "preset".

**Continued thread.** A new thread that carries on from another on a different provider (ADR-0089): its own Sotto thread ID and provider session, in the same project and, by default, the same folder, keeping the source's title. Its first message is the **handover** of the thread it continues ahead of the user's words, as one message, so no turn is spent on an acknowledgement; every copy shows the two apart by the length and digest the continued thread's record keeps. Each thread links to the other on its own record, "Continued from" and "Continued in", and the thread it continues stays readable and sendable. It is begun from the chips under a usage-limit stop ("Or continue now on") from "Continue in a new thread on" in the model chip, or from "Continue on another provider…" in the pane's More menu; the composer then reads "Continue on Codex" (or whichever) under a strip saying where the new thread works and what the handover carries, until the user sends or puts it away. Only this computer's threads continue for now. It never moves a thread: the source keeps its provider session (ADR-0002). Avoid: "moved thread", "migrated thread", "fork", which is a provider's own copy of a session.

**Thread card.** A main-backed reference or receipt in Watcher's transcript opening a real thread pane. It is distinct from a request card, where the user answers the owning thread, and from a visual; it answers and approves nothing.

**Receipt card.** One action Watcher took, as a **thread card** under the reply of the Watcher turn that took it (Zach's pick on October 16, 2026, cards A): Started, Sent to, Stopped or Settled, or Could not … when it did not reach the thread; the thread's name, which opens it beside Watcher; where the thread stands now; then its provider, its computer (This computer or the paired host's name) and its project. Main places each by the record's tie from the operation to its Watcher turn, never by reading anyone's words, and these cards and **watched request cards** are the only way a thread's name in Watcher's conversation becomes something to press (ADR-0073). On the iPhone the same receipts are rows in one card per reply.

**Watcher's picture.** What **Visualize**, the third tab of Watcher's room, shows across the pane's whole width (#1339): the **night scene**'s look, with a tree for each computer, a limb on it for each project, its name on a sign above, and a **thread owl** on that limb for each thread Watcher watches, with the thread's name and where it stands under it (Zach's pick on October 22, 2026, B of `prototype/watcher-visualize-owls`, which replaced A of `prototype/watcher-picture`, the constellation). A project with more threads than a limb holds grows another limb under it, and the picture scrolls when the trees run out of height. Watcher's owl sits on its own post in the middle under the moon, with **You** at its foot; when the pane is too narrow for that, the two share a line at the top. Every word has its own place, sized to it, so none sits on another. Owls perch: a working thread's owl blinks, a sleeping one's eyes are shut, and one waiting on the user glows in the accent. Settled threads fold behind **Show n settled**. The **merge turns** run along the top. Messages fly between the owls as they happen: what Watcher sends (a start, a check-in or steer, GO MERGE), a thread's reply or news, a pull request joining the merge queue or merging, and a question or permission going to **You**; each kind has its own shape. With reduced motion nothing travels: the thread's owl is ringed and a still mark stands beside it, never over a word. A press on a thread's owl or its name opens its card: where it stands, its pull request and merge turn, what it waits on the user for, what Watcher last did with it from Sotto's receipts, **Open beside Watcher** and **Open to answer**. Watcher's composer keeps one line while the picture shows, until focused. Live only: history and replay are #1340. It reads what the window already holds and asks main only for the merge turns, while it shows (ADR-0106). Avoid: "graph", "dashboard", "map", "constellation" (the picture before October 22).

**Merge turn.** Whose turn it is to merge, as Watcher runs it: a pull request is **READY TO MERGE** once it is in the merge queue that read_state works out (open, not a draft, its checks passed, oldest pass first), gets **GO MERGE** when Watcher's send gives it its turn, and is **MERGED** when GitHub says so. Watcher marks a send that gives the turn with `mergeTurn`, which main keeps in memory for **Watcher's picture** alone and never sends to a thread or a paired host (ADR-0106). READY TO MERGE and MERGED come from the pull request's own facts, never from anyone's words.

**Watched request card.** A watched thread's own question or permission card in Watcher's conversation, under the reply in which Watcher told the user about it (Zach's pick on October 19, 2026, variant B): the thread's name, provider and computer, question or permission, **Open**, the thread's last reply folded under **Show what it said**, then the same request card the thread's pane shows. The answer is the user's own, to that thread, never Watcher's. Main places it from the **wake-up ask** its wake-up carried; the card is drawn from the thread's live request, so it leaves wherever the request is answered, and gives way to the **answered line**. Avoid: "Watcher's question" (Watcher asks the user only through its own request cards).

**Wake-up ask.** One request a Watcher wake-up's news said waited on the user, kept with the wake-up as identities alone (host, thread, request and kind) in the host's record of the send (`watcherAsks`, ADR-0073). It places a **watched request card** and answers nothing.

**Answered line.** The one line that replaces a **watched request card** once its thread no longer waits: "You answered Fix login on staging: Use the staging key." when this window sent the answer, from this card, the thread's own card or its composer, in the card's own words and never the user's own text, or "Fix login on staging no longer waits on you." when Sotto does not know how it was answered. Both have **Open**. Nothing about the answer is saved.

**Takeover line.** Sotto's own quiet line in Watcher's conversation, after the turn it came in, when the user sent in a thread Watcher was driving for one of their requests: "You took over Auth refactor. Watcher stopped sending to it.", with the thread's name opening it beside Watcher and the time. A standing watch the send only paused has none, nor has a stop, a settle or a change of options. The iPhone's page carries the lines as well.

**Stop all.** The control in Watcher's room header, shown only while threads Watcher started are running, that stops every thread Watcher started for a request still active. It asks first, naming each thread with what it is doing and saying that each keeps its work and that threads the user started or took over keep running; then it says what came of each, including one still waiting on its computer to confirm, or that Sotto can't tell when the answer was lost. Put away while it stops, it keeps that answer for the button's next press. The prompts the user queued on a thread it stopped wait for the user's review, and still go first; a prompt Watcher queues there for a later request is not held by the stop. The iPhone's Watcher tab offers the same.

**Thread.** A conversation with one coding agent about one project, owned by Sotto. A thread has a Sotto thread ID, a title, a project, a model, a status (idle, running, error), messages and pending requests. In a project, a thread opens at once on its new-thread defaults; a model chosen afterward for that thread overrides its starting choice without changing the setting. Threads are a core Sotto function: memory, drafts, follow-up queues and delivery evidence refer to threads by Sotto thread ID and never by a provider's own identifier. Avoid: "T3 thread", "conversation", "chat" when referring to a project-bound thread.

**New-thread defaults.** What a thread in a project opens on, with saved native account choices supplying the model when no explicit default is set: the model, reasoning effort and permission mode chosen in Settings → Threads' "New threads start with" row. A create-thread that leaves one of them unset takes the default instead, fit to what the model it lands on actually offers: the nearest safer permission mode when the model does not offer the chosen one, and the effort at the same position among the levels the model does offer; a provider with its own permission profiles (Devin) always starts on its first, never the chosen default. An empty install keeps today's behaviour until the row is used: the model follows the reasoning-based default, and effort and permission follow the provider's own starting choice. An explicit choice made for one thread's own creation always wins over these. On the desktop they are this computer's own and apply on every host it opens a thread on (ADR-0074): the router keeps them on the local host whichever host is selected, and New thread sends the effort and permission they chose with the thread. A host whose catalog lacks the default model starts the thread on its recommended model, and a permission that lets the thread act without asking starts as "Ask for approval" on a host that does not let this computer answer. The iPhone keeps its own (ADR-0051). `src/shared/newThreadDefaults.ts`.

**Thread title.** The thread's name in every surface that names it: sidebar, pane header and paired clients. It is Sotto's own record, renamed at any time from the sidebar row or the pane header and never pushed to the provider. A thread records whether its title was set by hand (`titleSource`): a name the user typed in a rename is `user`; a name Sotto had the thread's own provider write is `generated`; the stand-in "New thread" every new thread opens with, and any name a provider supplied, are `default`, and so is a first-message title, which a `titledFromFirstMessage` flag tells apart. Anything that generates a title leaves a `user` one alone.

**Generated thread title.** The name Sotto writes for a thread that still carries a `default` one, once the first reply to its first message lands. A side call to the thread's own provider sees that first message and that first reply alone, and nothing is asked while generated titles are off or while Keep local history is off. A Devin thread, a disconnected provider and every failure leave the name the thread had, its first-message title or the stand-in; a failure is logged, never shown. It replaces a first-message title, and a thread that began with one is still named after a steer or a follow-up sent during its first turn. Regenerate title asks again for any name but a `user` one; a `user` name is never offered for rewriting.

**First-message title.** The opening words of a thread's first message, which name a new thread from the moment that message is sent until its generated thread title lands. Only a thread Sotto saw begin, empty and on a `default` name, takes one; an older or imported thread keeps the name it has. Sotto cuts it at a word to fit 60 characters and ends it with an ellipsis when cut; nothing is asked of any provider for it. It follows the same two switches as a generated title, Generated thread titles and Keep local history, and a provider's own name does not overwrite it. It stays where no generated title comes, as on a Devin thread. Avoid: "placeholder", which ADR-0026 and older notes use for the stand-in "New thread".

**Side call.** One request Sotto makes to a thread's own provider client, on the thread's account and model and in its working folder, apart from the thread's session. It writes Sotto's own short text (thread titles, branch names, commit message drafts and pull request drafts) and nothing else. It never enters the thread's transcript, history or pane, is never resumed or listed as a thread, can use no tools, and runs at the lowest effort the model offers. Devin offers none. It replaced the OpenRouter writing model (ADR-0026). Avoid: "writing model", which named that model and is gone.

**Commit message draft.** The message a side call to the thread's own provider writes for a Git action whose commit dialog left the message empty, from the diff and the names of the files the commit takes (the action stages them itself), the repository's last twenty commit subjects and its `AGENTS.md`, with an imperative subject under 72 characters and a body only where the change needs one. A message typed in the dialog is used as typed. With generated commit messages off, on a Devin thread, or when the provider does not answer, the commit takes the subject "Update project files".

**Pull request draft.** The title and body a side call to the thread's own provider writes when a Git action creates a pull request, from the branch's commit subjects, its file list, a capped diff against the base and, unless Follow pull request templates is off, the repository's pull request template: the first template file in GitHub's usual places, or the only one in a `PULL_REQUEST_TEMPLATE` folder. With generated pull request text off, on a Devin thread, or when the provider does not answer, the pull request takes the last commit subject as its title and the template, or the list of subjects, as its body. There is no form to edit it in first; the pull request's description is GitHub's to edit afterwards.

**Host ID.** The permanent identity of the Sotto host that owns a workspace. Together with a Sotto thread ID, it distinguishes a thread from threads on every other host.

**Phone-origin Watcher request.** A user instruction sent to Watcher by a phone paired with the computer running it. It identifies that phone and computer, grants no answer authority and uses the computer's own new-thread defaults for workers. Those defaults may permit edits even when the phone cannot answer. The user answers each worker's own card under Can answer on its owning computer, including when the card is shown inside Watcher. Avoid: a Watcher permission answer on the user's behalf.

**Watcher tab (phone client).** The paired desktop's Watcher page, with Conversation and Watched, a working dot and a needs-you badge. Receipts form one card per reply with a row per thread. Provider logos identify workers and the owl follows the logo for a watched worker. Watched remote workers retain their owning computer; they do not join the paired desktop's ordinary phone thread list. An old phone sees only ordinary workers, and a desktop without Watcher, such as stable 0.1.39 or earlier, shows no Watcher tab.

**Paired Watcher origin.** A Watcher request and operation attributed to the paired desktop that runs the master, while the worker's owning host keeps its ownership and receipt. It carries no permission answer or grant; uncertain remote work remains in the master's shared capacity until reconciled. Avoid: an ordinary privileged desktop command as an automation fallback.

**Sotto thread ID.** An opaque ID, unique within its host, that Sotto assigns the first time it sees or creates a thread, normally a fresh UUID. It outlives any provider session. Agent state, drafts and follow-up queue items refer to this ID; a client pairs it with the Host ID when it shows more than one host.

**Provider.** The installed native client that runs the agent for a thread: Codex, Claude Code, Grok Build, Devin, Muse, OpenCode, or Cursor and DeepSeek Harness in Sotto Owl (ADR-0079, ADR-0087, ADR-0128, ADR-0138). Providers keep their own sign-ins and may be connected together; each thread's chosen model belongs to one provider. Claude Code, Codex, Grok Build, Muse, OpenCode, Cursor and DeepSeek Harness each run a process per thread (ADR-0038), so one ending on its own affects only that thread: the provider stays connected, a reply it was writing is marked failed with a line saying it may be cut short, and the process starts again the next time the thread is opened or sent to. Codex also keeps one **provider process** that holds no thread, for the model list, the account, skills and settings reads; Grok Build, OpenCode and Cursor keep none between connects. OpenCode's processes keep their data in a folder of Sotto's own, never the user's own OpenCode folder, so its sign-ins there are Sotto's alone. Cursor's run with a Cursor folder of Sotto's own too, so a thread never changes the user's own Cursor's model or settings, but they use the user's own Cursor sign-in, which Cursor keeps outside that folder. DeepSeek Harness's run with a harness folder of Sotto's own too, and in this version run only the user's own keyless **model servers**, on no sign-in at all (ADR-0138).

**Model source.** Where a model OpenCode offers runs: OpenCode Zen for its free models, or a company the user signed in to inside Sotto's OpenCode folder, such as Anthropic, OpenAI or OpenRouter. OpenCode is the provider and the model source is what bills the turn, so the same model can sit under two model sources. The model menu opens an OpenCode thread's models on their model sources, and its chip names the source beside the model (ADR-0087). The OpenCode tile's **Model sources** block lists the ones signed in, and **Add a model source** signs in to another (#1104); a connected host's OpenCode has the same block under that host's tiles, for the host's own Sotto OpenCode folder (#1107). Avoid: "provider", which OpenCode uses for this but Sotto means the native client; "service", which is the **host service**; "model maker", which is who made a model, not what bills it.

**Model maker.** The company that made a model: Anthropic for Claude, OpenAI for GPT, Google for Gemini, xAI for Grok, Moonshot for Kimi, Z.ai for GLM, Meta for Muse, and Cursor for its own Auto and Composer. Cursor runs every model it offers on the user's Cursor plan, so its model menu groups models by maker rather than by **model source**, read from each model's name, with any model Sotto cannot place under Cursor (ADR-0128). A model's maker travels where an OpenCode model's source does, and the chip reads "Anthropic / Claude Sonnet 5.5" while the thread's provider stays Cursor. Avoid: "model source", which is what bills an OpenCode turn; "provider", which is the native client.

**Favorite model.** A model the user starred in the model menu, on Owl (ADR-0147). Favorites is the first tile on the menu's provider rail and lists every favorite model from every provider and model source, each with its provider's mark, and the menu opens there while any exist. A favorite is this window's preference, kept across restarts, not a setting and not a thread's; one whose provider or model is gone stays listed as unavailable. Avoid: "default model", which is what a new thread starts on.

**Your own model server.** A model server the user runs, such as SGLang, vLLM, Ollama, LM Studio or llama.cpp, on this computer, their network or their tailnet, added under **Your own model servers** on Settings › Providers or from **Your own server…** in OpenCode’s model sources. It is a **model source** Sotto declares rather than one OpenCode signs in to: main keeps its address and models in its own record, checks it only when the user presses Check, Add or Check again, and gives it to every OpenCode process it starts and declares it to every DeepSeek Harness process, keyless servers only there, that provider having no copy of a key OpenCode keeps. OpenCode keeps its optional key; Sotto keeps none. A provider runs it — OpenCode first, DeepSeek Harness since ADR-0138 — so the user’s “harness” is Sotto’s provider (ADR-0124). Avoid: “local model”, since the server may be on another machine; “endpoint” in the UI.

**Client update.** What Sotto knows about one installed client: the version the adapter reads from the installed client, the version that client's own install channel publishes, and the one press that installs it. The **channel** is what installed it — npm (including a client whose package npm owns but whose binary lives elsewhere), the client's own updater or maker installer (Muse), mise (on an explicit Update press, `mise cache clear <tool>`, a look at `mise ls-remote <tool> <version>`, then `mise install <tool>@<version>` for the published version, each with `MISE_MINIMUM_RELEASE_AGE=0s` for that process, and for Grok Build its package's install step after it; `mise upgrade <tool>` when no published version is known), or the Devin app — and it decides what an update runs; Claude Code, Codex and Grok Build published versions come from npm; Muse's comes from the installed stable or canary channel's public feed. Devin updates with its app. A client whose channel Sotto will not drive shows the command to run by hand instead of a button. A remote host's client updates show on its provider tiles, never on this computer's client update card; Update all lists them under their host (ADR-0077). Say "client update", not "provider update": the provider is connected or not, the client is what gets replaced (ADR-0042).

**Client update line.** The one-at-a-time order a machine runs its client updates in: a tile's Update, Update all and Settings → Providers all join it, a failure does not stop the ones after it, and a client still waiting can be taken out with Cancel update. `clientUpdateRun` counts it ("Updating 2 of 3") until it is empty. `src/main/agents/control.ts` (ADR-0042, September 29 amendment). Avoid "the queue" for it, which is a thread's follow-up queue; the command that joins it is still `queue-client-updates`, and a client in it is `queued`.

**Outdated process.** A thread's process started from a client that a client update has since replaced on disk, or, for OpenCode, before a sign-in or sign-out changed the model sources in Sotto's OpenCode folder. The update never stops a turn or disconnects the provider: an outdated process that is idle stops at once, the way the session reaper stops one, and one that is busy (a turn running, a request waiting for the user) finishes on the old client and stops the moment it is idle. A watched thread starts again on the new client straight away; any other starts it on its next action. An outdated process never sets the provider's version (ADR-0038). Avoid: "retired", which Provider retirement already means.

**Verified version.** The client version an adapter was checked against. Sotto connects to that version or newer and notes when the installed client is past it; older is refused. Not a pin: an exact pin is what kept an installed client old while newer ones were published.

**CLI lookup.** Where Sotto looks for an installed client, the same way for all thread providers on a desktop and on a host: PATH, the login shell's PATH, `~/.local/bin`, the version managers' install folders (mise's `installs/<tool>/latest`, asdf, nvm, fnm, Volta, Homebrew), then npm's global folder, with Grok Build's own `~/.grok/bin` first. A manager's shim, or a script that runs the client through the manager (`mise x`), is never taken for the client, and each provider keeps its own rule for what it starts (Codex only its native binary). A client found off PATH runs with its own folder and Node's ahead of its PATH. OpenCode's adds the places its installers use and Windows' PATH as it is now, follows a launcher to the program it starts, and connects the first OpenCode 2 it finds over an OpenCode 1 met first (`opencodeLookup.ts`, ADR-0087). `src/main/agents/cliLookup.ts`, ADR-0036. Avoid: "discovery", which is a provider's catalog of models, projects and threads.

**Provider session.** The native client's own identifier for a thread, distinct from the Sotto thread ID. In prose and user-facing text say "provider session", not "session" on its own or "remote ID".

**Idle compaction.** Sotto compacting a large Claude Code thread on its own, 54 minutes after it went quiet, while Claude still holds its prompt in cache, so the next message re-reads a short summary instead of the whole conversation at twice the price ([ADR-0127](docs/adr/0127-sotto-compacts-an-idle-claude-thread-before-its-cache-expires.md)). It is the same native compaction as Compact context, sent as Sotto's own command, once per quiet stretch, and only to an idle thread with nothing waiting, queued or drafted. Watcher's own conversation is compacted too, only while Watcher rests. One that works shows only the transcript's "Context compacted" boundary; one that fails or is unconfirmed says under the composer that Sotto tried, with **Turn off**. **Compact idle threads** on Claude Code's page in Settings › Providers turns it off. Avoid: "auto-compaction", which is the provider's own compaction when a context fills.

**Project.** A working folder the provider knows about, with an ID, a title and a path. A thread belongs to exactly one project. A project lives on one host, and its threads run there; the path is in that host's own format. Its working-copy default in Settings → Threads overrides the global default for new threads only. Local project defaults use the host-local project ID; remote project defaults retain the host-qualified client key.

**Folder browser.** Add project's dialog, and New thread's folder source: which computer the project lives on when more than one is paired (none is chosen for the user), then that computer's folders, listed by its host from its home folder (ADR-0025, September 26 amendment). Folders only, with Git and Project marks. **New folder** is a name until **Use this folder**, which adds the project and makes the folder on the host. On this computer it also offers **Browse with File Explorer** (Finder on a Mac, file manager on Linux), the system's own dialog. Avoid: "file picker", "remote file browser", which would be the Tools panel's files.

**File link.** A link in a thread's reply that names a file on this computer rather than a web page: an absolute or `~/` path, a path inside the thread's folder, or a `file://` link. In Owl, pressing it shows the file selected in its folder in File Explorer (Finder on a Mac, the file manager on Linux) and opens nothing (ADR-0120); a path inside the thread's folder must stay inside it, and a network share is never one. Stable shows it as plain text. Avoid: "open file", which would run it.

**Thread working copy.** The folder in which a thread's provider works: the shared project folder by default, or an explicitly chosen new or existing Git worktree. Threads sharing a folder share its files and checked-out branch; a separate working copy provides isolation without changing the thread's project memory scope (ADR-0014).

**Branch toolbar.** The line of small controls under a thread's composer card for a Git repository, as T3 Code has it (ADR-0027): **Run on**, **Workspace**, the pull request badge and the **branch picker**, in that order. It is one muted line of **text buttons** with their icons and a faint dot between them, below the card rather than a strip inside it (ADR-0113). Run on names the machine the thread runs on, behind a laptop or server glyph, and is always a label here, since the host is chosen when the thread is made. Workspace is where a draft will work: **Current checkout**, **New worktree**, or **Previous worktree (branch)** for a worktree another thread of the project already has; it locks to static text once the thread has a message or a session. Avoid: "git bar", "workspace picker".

**Branch picker.** The branch toolbar's control naming the folder's branch, **Select ref** for a detached HEAD, or **From origin/main** for a worktree not made yet. Its popover searches the host's refs, lists locals then remotes with `current`, `worktree`, `remote` and `default` badges, and pages them. Picking a ref checks it out in the thread's folder (a remote ref gets a tracking branch); a ref already checked out in another worktree re-points a draft at that worktree; for a worktree not made yet the pick records the base, with a **Start from origin** switch that fetches the base when origin has it and otherwise takes the local branch and says so; a name nothing matches offers **Create new ref**, except for a worktree not made yet, which starts from a branch that exists. A draft pointed at another thread's worktree shows that worktree's branch and does not move it before the first send. Right-click copies the name. A search that is a pull request URL, `#42` or a `gh pr checkout` line offers **Checkout pull request** first (see Pull request checkout). Git's refusal is shown under the row as **Failed to switch ref.** with Git's own words. A switch made here moves the thread's sent branch with it, so the branch-changed notice stays for checkouts moved elsewhere. Avoid: "branch dropdown", "checkout menu".

**Pull request badge.** The state icon and number of the branch's pull request at the right of the branch toolbar, its title in the tooltip ("PR #12 - Open: title"). A press opens the Pull request surface in Tools for that thread, pinning Tools to it when Tools was pinned to another thread.

**Pull request surface.** The Tools surface **Pull request** (its rail tile reads PR) for one of a thread's pull requests: its branch's own, else the one linked last, or one chosen from Linked pull requests. It is read from GitHub through the host's `gh` when it opens and on Refresh, never pushed with the state. Its whole reading is the merge checklist, with one large **Merge** docked under it in the method chosen beside it (Merge commit, Squash, Rebase; it starts on the Default merge method, and a pick here is saved while that is Last selected), enabled only when the checklist has nothing left; **Merge when ready** arms GitHub's auto-merge instead, where the repository allows it. An armed auto-merge, a merged and a closed pull request take Merge's place, with **Turn off** and **Reopen**. The description and Linked pull requests fold below; the ··· menu holds Ready for review or Convert to draft, Update with rebase, Merge when ready, Disable auto-merge, Babysit pull request, Copy link, Link pull request, Unlink from thread, and Close or Reopen pull request. With no pull request it offers the Git action's **Create PR** and **Link pull request**. Nothing happens from viewing; the merge, turning on auto-merge, closing and Update with rebase, which rewrites the branch on GitHub, ask first. The host acts only on a pull request the thread knows (ADR-0027). Avoid: "PR panel", "pull request form", which named the Changes form this replaced.

**Pull request sheet.** The iPhone's reading of a thread's pull request, an Owl feature sent to stable (ADR-0102): a full-height sheet the pull request chip under the thread's title opens, on a computer that offers it. It reads the pull request from GitHub through the thread's computer each time it opens, never ahead of time, and shows its state, where it stands (checks, review, conflicts and how far behind its base), then its summary, checks, reviews and changed files, with **Babysit pull request** or **Stop babysitting** docked at the bottom. It merges, closes and marks ready nothing. Avoid: "PR screen", "GitHub tab", which was the variant not chosen.

**Merge checklist.** What stands between a pull request and its base, as five lines in the order a merge meets them: Checks passing, Review approved, Up to date with the base, No conflicts, Ready for review. A line is done, or says what holds it back and carries the one press that fixes it (Open check, Open review, Update branch, Ready for review), or has none where the fix is elsewhere, such as conflicts to resolve in the branch. A line reads what GitHub reports, not a stand-in: "No checks" and "No review required" count as done, a request for changes where no review is required is said and linked without blocking, and a base GitHub could not compare, or checks GitHub would not show, are said and do not hold the merge back; the count beside the heading names it ("4 of 5 done, 1 does not block"). Avoid: "merge requirements", which is GitHub's name for its own branch rules, and "status", which the Git status already means.

**Linked pull requests.** The pull requests on a thread's record: the one its Git action created, ones linked with **Link pull request** (a GitHub URL or `#42`), and one checked out from the branch picker, each with how it came to be linked. The Pull request surface folds them below its checklist with the branch's own pull request and opens any of them; Unlink from thread, in its ··· menu, unlinks the one shown. A link is Sotto's record, not GitHub's, and is never pushed to GitHub.

**Babysit (a pull request).** Stable only: on Owl, **restart** takes its place and its reader serves Watcher (ADR-0144). A thread's standing request to be woken when one of its pull requests needs it: a check fails, every check the base branch requires has passed, someone other than the user's own GitHub account comments or reviews (a bot's notice that it could not run aside), the branch starts to conflict, or the pull request merges or closes, which also ends it. The agent starts it with Sotto's tool, or the user with **Babysit pull request** on the Pull request surface or the iPhone's pull request sheet, and either stops it. The thread's host reads GitHub for it and tells the thread in a **wake-up**; it is news, never a decision, and approves, merges and answers nothing (ADR-0061). Its sidebar row names the pull request and its status ring is an hourglass, in the sidebar and on the collapsed rail. A babysitting thread is not Working, Waiting or Monitoring: those are claims about the provider, and this one is Sotto's. Avoid: "watch", which the **watched set** means; "wait" and "waiting", a **held action**'s word; "monitor", a **monitoring task**'s; "follow", the **follow-up queue**'s; "subscribe", GitHub's own email notifications.

**Wake-up.** Sotto's message to a thread with pull request news from babysitting, including why it ended (the pull request merged or closed, ten comment-only wake-ups in a row, or GitHub kept refusing the read; never this computer being offline), or watched participant news for Watcher: what changed and where it was observed, in Sotto's words and never a commenter's, and, as the note is sent, the start of a finished turn's reply, labelled as the worker's words. A resume note is a wake-up too, and so is news of a thread's own **delegations**: which delegation and delegated thread, which turn and its **outcome**, and for an answered one the delegated thread's reply, labelled as its own words. It goes through the thread's send path like a prompt, waits behind a busy thread in its follow-up queue as Sotto's own item, and shows in the thread as sent by Sotto; it approves and answers nothing. Watcher's is the exception: its news travels beside a short message of Sotto's, through the same channel as the **Watcher request note**, and neither shows anywhere, the conversation, the queue and the phone included (ADR-0073). A delegation's news is the other: it goes to the delegating thread's agent as its next turn and shows nowhere either, waits only for that thread's own turn, never for a machine Stop, a paused queue or a set-aside prompt, and its words are the agent's to pass on in its reply (ADR-0081, October 19, 2026). The turn it starts is an **unshown turn**, one whose own message the conversation leaves out, and it sits where it happened: Watcher's first reply to it is marked **After news** in its header, with how long the work took, and opens that work; a news turn that wrote no reply shows nothing unless it failed or stopped. Watcher's wake-up holds its news alone and never changes once made: news that comes while it waits or is sent goes in the next one, and since no one is shown it to resume, it never pauses. Avoid: "wake" on its own, which does not distinguish Sotto's news; "alert", the local notification the iPhone and the desktop show; "notification"; "follow-up", which is the user's.

**Resume note.** On Owl it runs under **Restart stopped threads** and shows tagged "Restarted" (ADR-0144). The wake-up Sotto sends a thread whose turn was stopped by Sotto closing, for an update, a quit, a crash or a restart of the computer, when "Resume threads after a restart" is on: the same words for every provider, saying Sotto restarted, the turn stopped partway and any command that was running was stopped too, and asking the agent to check where things stand and carry on. It goes once the thread's provider is back and reports it idle, ahead of the user's follow-ups that waited on the stopped turn, at most three times in a row before a turn of the thread's own finishes, and shows tagged "Resumed". A note the provider refuses leaves the queue rather than hold the user's messages behind it, and the thread is left as it was. Which threads were working is kept in `restart-resume.json`, thread IDs and times only, and stops changing the moment Sotto starts closing. An Owl feature, sent to stable (ADR-0076). Avoid: "replay" or "retry", which say the user's message goes again; it never does.

**Restart (a stopped thread).** Sotto's one note to a thread that was working when something other than the user stopped it, so the agent carries on (ADR-0144, an Owl feature). A provider's usage limit schedules one for the reset the provider gave, as an instant: Claude Code's from its stop, Codex's, Grok Build's and Muse's from their own usage readings; a provider that gives none, and a spending limit, schedule nothing and leave the thread to the user. A thread on that provider with background work at the first stop counts as stopped too. A minute after the reset the note goes, the same words on every provider, through the thread's send path ahead of its queued messages, Watcher's own thread first when its provider stopped it; Watcher then hears which threads were restarted, watched or not. A thread the user has sent to since, a running one and an archived one are skipped. While one is scheduled, a band at the top of the Threads sidebar names the provider, the time and the threads, the thread's row reads "Restarts at 3:00 PM", and a strip over its composer says the same, each with Don't restart. The setting **Restart stopped threads** also governs the **resume note**. It shows tagged "Restarted", answers and approves nothing, and goes at most three times in a row. Avoid: "continue", which a **continued thread** means; "resume", the queue's and the resume note's; "wake-up" on its own, which is babysitting's and Watcher's; "retry", which says the user's message goes again.

**Pull request checkout.** T3's **Checkout pull request**, from the branch picker: a dialog that resolves the reference through `gh` as it is typed and checks the pull request out **Local**, with `gh pr checkout` in the thread's folder (the project's own checkout for a draft) and never forcing, or into a **Worktree**, which only a thread that has not started takes: the pull request's head becomes a branch (its own head branch, or `sotto/pr-<number>/<head>` for a fork) and the draft's new worktree checks that branch out on first send, or the draft points at the worktree that already has it. The pull request is linked to the thread either way.

**Local branch notice.** The dismissible line above a worktree thread's composer, in the status tone, saying that Start from origin found no `origin/<base>`, or that the project has no origin, so the worktree started from the local branch (ADR-0014, amended September 24, 2026). It names the branch, is said once per thread, and **Dismiss the local branch notice** keeps it away on this computer. Avoid: "fallback notice", "origin warning".

**Branch-changed notice.** The dismissible line above a shared-project-folder thread's composer when that checkout is on a different named branch from the thread's last send; a switch made in the branch picker moves the sent branch with it, so the notice is for a checkout moved elsewhere. Sending continues on the current branch; **Restore branch** is the user's explicit choice to switch back, with confirmation for uncommitted changes, and worktree-backed threads do not show the notice.

**Greeting.** A new thread's line above its composer until the first send, picked at random from a short list the first time the window shows the thread and kept while the window is open, with the project, the branch and where the thread runs under it. On Owl (**Recent projects**, ADR-0121) the project opens a menu of the other projects on the same host, newest work first; choosing one starts the new thread there instead, as New thread in that project would, and leaves this one empty for New thread to reuse. The greeting and the composer stand together in the middle of the pane, the composer narrower than usual (720px). The first send slides the composer down to its place and widens it, or moves it at once under reduced motion. A thread that is working, failed, settled or archived, Watcher's own conversation, and a thread with a request, older history or messages not yet drawn keep the plain line in the transcript instead (Zach's pick on October 14, 2026: variant a of `docs/prototypes/new-thread-greeting-prototype.html`). Avoid: "hero", "welcome screen", "empty state".

**Slim composer.** A floating composer stepped down to one line while the user reads back: the message box with its send, queue or stop disc beside it, and nothing else of the card, the branch toolbar or the line under it. It shows while the transcript is read more than 160 pixels above its end, the composer has no focus and holds no draft; the end, a click, Tab, a key typed in the transcript or a draft bring the composer back full. The transcript keeps the full composer's room, so nothing in it moves, and the rows under the card hide in their place, so only the card's top moves. A waiting question and a new thread's **greeting** keep the composer full. In threads and Watcher's room. An **Owl feature** (`composer-shrink`, ADR-0125; the user's pick B of `docs/prototypes/composer-shrink-prototype.html`). Avoid: "collapsed composer", "mini composer", "pill", which no control is (ADR-0110).

**Temporary thread branch.** The short starting branch of a new worktree, created on its first send and eligible for a descriptive name from that first prompt. It stops being replaceable once the user or agent changes its branch, or another thread shares the folder.

**Git status.** What the host last read of a working copy's Git state, carried on the thread's worktree record and reaching every client through the state stream: the branch, its upstream, ahead and behind against the local tracking ref, whether the tree is dirty and how much changed, the default branch and the distance from it, the branch's pull request, and when the remote was last fetched. It is read the way T3 Code reads it (ADR-0027): after finished work while a Sotto window shows (or once one shows again), on a refresh, and on a timer for the threads a window is looking at while that window is in front. Threads that finish work in one folder at about the same time share that folder's read after it. The slow half of a read, the fetch and the pull request lookup, runs outside the thread's order of work on the host, in its folder and never while the folder is being removed, and a local read in that order then takes what it brought, so a send to the thread may wait for a local read already under way but never for a fetch or a GitHub lookup, unless it is queued behind the folder's removal, which lets one still running there finish first (#766). Avoid: "git state", "sync status".

**Git action.** T3 Code's stacked action on a thread's working copy: commit, push and create the pull request from one press, or any prefix of the three, with a feature branch first when asked. The host runs it on the thread's lane, reports each stage on the thread record in T3's words, and ends it with a notice that offers the next step (Push, Create PR, View PR). Pushing from the default branch asks **Push to default ref?** first (**Abort**, **Push to** the default branch, as in **Push to main**, or **Check out feature branch & continue**); nothing is forced or rebased, nothing is merged but the merge commit the user says yes to when they **bring changes back**, and a pull is fast-forward only (ADR-0027). The control is the button at the end of the pane header, whose label follows the folder's Git status (**Commit**, **Commit & push**, **Commit, push & PR**, **Push**, **Push & create PR**, **Pull**, **Create PR**, **View PR**, **Publish repository**, and **Initialize Git** for a folder without Git), with a chevron menu holding **Commit**, **Push**, **Create PR** or **View PR**, and **Publish repository...** for a repository without a remote, each disabled with its reason rather than left out, and first, on a thread that can **bring changes back**, **Bring changes to** its parent's branch. Avoid: "sync", "quick action", "Git button".

**Bring changes back.** Bringing a thread's commits to the branch of the thread it began from: a **delegated thread**, a **continued thread**, one continued from an agent or forked at a reply, or a worker that Watcher started from a thread's branch (**start from a branch**), working in a new worktree made from the branch that thread is still on (#1030, the October 23, 2026 amendment of ADR-0027). It is offered as **Bring changes to main** (named for that branch) in a strip above the thread's composer, which says which branch it was made from and where that branch is checked out, and first in the **Git action**'s menu. A press runs Git on the host that holds the parent's folder: Git fast-forwards the branch when it can; otherwise Sotto asks **Make a merge commit on main?** and changes nothing until **Make merge commit**, while **Not now** sends nothing. The branch moves only in the folder the parent works in, the shared project folder included, so that folder's files follow; a parent no longer on it is refused, and Sotto switches no branch. A child on another **machine** sends its committed branch there first, as a **branch move** the desktop makes into an **incoming ref**, which goes once the press is over. Uncommitted work in the worktree, uncommitted changes where the branch is checked out, a **check snapshot** among the commits, and conflicts are refused, a conflict in Git's own words; Sotto resolves, rebases and forces nothing. The question and the outcome take the strip's place and are never saved. Owl only (`cross-machine-work`). Avoid: "merge back", which T3 Code uses for moving a conversation; "sync"; "merge" on its own, which is the **Pull request surface**'s.

**Checkout guard.** A reservation for one checkout shared by sends, Git actions, automatic pulls, checkpoint reverts and folder removal. A mutation excludes sends and other mutations; read reservations, including checkpoint snapshots, automatic settling, Tools/drawer shell startup and a draft choosing an existing folder, can overlap with sends. Thread creation and working-copy selection hold their destination through inspection and publication, so removal cannot gain a new thread reference while reserved. It records what holds the checkout. Identity follows the canonical checkout root, including subdirectories and aliases; linked worktrees remain independent.

**Commit dialog.** What a Git action that commits opens first, T3's **Commit changes**: the branch with a **Default branch** tag, the changed files with their line counts and an **Edit** mode that leaves files out, **Commit message (optional)** which the host writes when left empty, and **Cancel**, **Commit on new branch** and the action itself. The files come from the host on request, never with the status. Avoid: "commit form", which named the drawer inside Changes that this replaced.

**In front (a window).** The condition under which the host reads remotes on its own: the Sotto window is showing and has the focus, or had it within the last 45 seconds; on a headless host, a paired client holds an open socket. Nothing is fetched for a window that is not in front.

**Settings pages.** The pages down Settings' sidebar, eleven of them (nine on stable 0.1.39 and earlier), in four runs with a divider between runs: Dictation and Cleanup; Threads, Git & worktrees and Watcher; Providers, Hosts & phones and Cloud iPhone; Appearance, Application and Performance (ADR-0115). Each page is a run of titled groups, each group a card. A page that used to be its own, such as Transcription, Output or Phones, is now a group that keeps its section id, so a link to it still opens its page there. `settingsPages.ts` holds the pages, their runs and every setting's place.

**Find a setting.** The field at the top of Settings' sidebar. While it holds text, the sidebar lists the settings whose name or other words hold it, each with its page, in place of the pages; pressing one opens its page with focus on the setting. It offers only what the page shows now (ADR-0115).

**Settings → Git & worktrees.** The Settings section that holds every Git setting, grouped under the moment each one acts: **When a thread commits** (the Commit and pull request style), **When a pull request is made or merged** (Follow pull request templates, Default merge method, Auto-settle merged threads), **When you read Changes** (Diff layout, Hide whitespace changes, Default diff file state, Proactive panels) and **In the background** (Git fetch interval, Automatically pull, and on Owl Keep main up to date). Each description says what Sotto will do with the value shown, and changes as the value does. Since October 22, 2026 it also holds **Removing worktrees** (the worktree cleanup rules), and Generated commit messages, Generated pull request text and Let agents babysit pull requests beside the settings they belong with; Generated thread titles is under Settings → Threads. Avoid: "Git preferences".

**Git fetch interval.** The setting under Settings → Git & worktrees, In the background, that says how often, while the window is in front, the host fetches a project's origin so its threads' Git status knows ahead and behind. A refresh and a Git action also fetch first, at most once in 15 seconds. Off stops every fetch for threads, those too, so ahead and behind compare with the remote as it was last fetched; on Owl, Keep main up to date still fetches each project every 15 minutes (ADR-0142); a refresh still asks GitHub for the branch's pull request.

**Automatically pull.** The setting under Settings → Git & worktrees, In the background, off until turned on, under which the host fast-forwards a thread's folder when a read of the remote finds it on the default branch, clean, tracking an upstream and only behind, and no thread is working or waiting in that folder. It is the Git action's Pull, run at the moment the status is read; nothing is merged or rebased. Avoid: "auto-sync".

**Keep main up to date.** The Owl setting under Settings → Git & worktrees, In the background, on by default, with an override per project under Settings → Threads → Project defaults (ADR-0142). Every 15 minutes, shortly after Sotto starts, and when a pull request of the project's repository merges, the desktop fetches each of its projects' `origin` and fast-forwards the project folder's default branch to it, whether or not a window is in front. It acts only when that branch is checked out with no local changes and no commits of its own, nothing is in progress, no untracked file is in the way and no thread is working in the checkout. It never switches a branch, stashes, resets, rebases or merges. What stopped it is the project's **main line**. Unlike Automatically pull, it reaches a project folder no thread is showing. Avoid: "auto-sync", "auto-update".

**Main line.** The muted line under a project's name in the Threads sidebar that says why Keep main up to date left the default branch behind, as in "main is 1,320 behind · local changes block the update", with **Show changes** (or **Show commits**) listing what is in the way and **Open folder** beside the list. After an update that changed a lockfile it reads "Updated main · dependencies changed, run install" until dismissed. It says nothing while a thread is working in the checkout or the remote cannot be reached. Avoid: "behind badge", "sync warning".

**Default merge method.** The setting under Settings → Git & worktrees that says which method a pull request's merge should start on: Last selected (the method used last, which Sotto remembers only while this is the choice), Merge, Squash and merge, or Rebase and merge. It is the method the pull request checklist's merge starts on; under Last selected, a method picked beside that Merge becomes the one used last.

**Commit and pull request style.** The setting under Settings → Git & worktrees, When a thread commits, that shapes the commit messages and pull request text a thread's own provider writes: Repository conventions (the recent subjects and `AGENTS.md` the request already carries), Conventional Commits, or Custom instructions in the user's words, sent with each of those requests. Either of the last two takes precedence over the repository's own style, whose context is still sent. An example under it shows a commit subject and pull request title in the chosen style; under Custom instructions it shows the subject the instructions start from and says the model applies them, because Settings asks no model and does not guess. Follow pull request templates, under When a pull request is made or merged, says whether the thread's own model is given the repository's pull request template to follow when a Git action drafts a pull request. Avoid: "writing style", "commit format", "prompt".

**Proactive panels.** The setting under Settings → Git & worktrees, When you read Changes, off until turned on, under which Changes opens on its own when a turn leaves its folder with at least 3 more changed files or 50 more changed lines (T3 Code's measure, taken from the working copy's counts before and after the turn rather than the turn's own diff, and only while the Threads page is open), only on a closed Tools panel not pinned to another thread, and without moving keyboard focus. A large turn in a pane not in focus waits until its thread is focused. It is the one exception to "nothing announces itself unasked", and it exists only because the user asks for it (ADR-0027).

**Reclaim (a worktree).** Removing a worktree Sotto created while keeping its branch and its thread; the next send puts the folder back on that branch. For a thread, it happens on the user's word (**Remove worktree** in the Working copy panel, or the question Settle asks) or under a cleanup rule the user turned on, never for a folder with uncommitted work without their answer (ADR-0041). The thread's question lists ignored items other than dependencies and requires a separate acknowledgement to discard them; a changed list requires a new question. Nested repositories and worktrees are listed with a count of uncommitted changes; repositories also show commits not on any remote and go only after the separate acknowledgement. Each host reclaims only its own worktrees. Sotto deletes the folder's files itself while Git holds the worktree locked for the removal, and a reclaim cut off partway leaves a **half-removed** folder that the next Refresh, send or sweep finishes. A half-removed folder without Sotto's lock, as Git's own cut-off removal left it, is repaired from Git's index instead, with nothing more deleted (ADR-0041, #1297). Avoid: "delete the worktree", "clean up the thread".

**Thread pane.** A view of one thread within the Threads page, with its own reading position and input. Closing a pane leaves the thread and its running work intact.

**Unreadable-request notice.** A line in the owning thread's pane saying that a native request could not be shown and was refused. It is neither a pending request nor the user's answer, and grants no approval.

**Thread activity.** Provider-reported work alongside a thread's messages, including commands, file changes, visible summaries, tool results and subagent states. Activity is observational history, not a user message or permission to act.

**Computer Use.** Codex's own tool for seeing and operating the apps on the computer, named as Codex names it. In a Codex thread it works only in Full access and while the Codex desktop app is open; its calls show in the thread activity as Computer Use, and a recognised failure shows guidance. A native pipe failure means the connection to the app helper is unavailable, even if the app is open; it does not prove that no earlier action happened. Sotto relays it and changes nothing about how Codex runs it. Avoid: using it for Sotto's own browser, which is the Tools panel's.

**Native skill.** A reusable instruction set exposed by a provider for a thread's working copy. A chosen skill shows as a pill in the thread's draft, led by a wand. It is sent as its native token and removed whole. Selecting it adds a provider-recognized reference to that draft; it neither submits the draft nor grants authority.

**File mention.** A file of a thread's working copy named in a draft by typing `@` and picking it, like a native skill's `$`: both are mentions, a sigil and a name written into the draft's own text. The mention is the reference — deleting its token removes the file from the send — and it reaches every provider as the same `@path` relative to the working copy. Files outside the working copy, git-administrative entries and paths containing a space are never offered.

**Tools panel.** The shared working surface beside the thread panes. Its working-copy tools follow the focused thread unless pinned to a particular thread's working copy. Agents always follows the focused thread, even while another working copy is pinned. Its seven surfaces (Browser, iPhone, Terminal, Files, Changes, Pull request, whose tile reads PR, and Agents) sit on a rail at its outer edge, each surface under one line of chrome naming what is open, and the working copy it reads is its footer, which ends "on forge" for a thread on a paired host. For such a thread Files, Changes and Agents are read from its host, and Terminal, Browser and iPhone say they are on the host machine. A dot on a surface in the rail means something is live there. Avoid: "tab" for a surface, which is a page or a shell inside one.

**Changes.** The Tools surface that shows a thread's working folder as T3 Code's diff panel: the files of one **diff scope** as blocks with their status and line counts, each collapsible, with Copy path and a name that opens the file in Files, and a file tree beside them. Its comparisons read and never write: there is no staging, discarding or reverting of lines or files in it, and committing is the **Git action**'s (ADR-0027). The one thing on it that writes is Sotto's own **Checkpoints** drawer, whose toggle sits on its line of chrome: it reverts a whole turn's files and conversation, after a confirmation. It starts in the layout, whitespace and file state that Diff layout, Hide whitespace changes and Default diff file state name. A choice made in it holds until one of those settings changes or Sotto restarts. `mod+d` toggles it, or `mod+shift+d` when the dictation hotkey holds `mod+d`. Inside it, "diff" names a comparison, never the surface, as T3's labels use it (Refresh diff, Stacked diff view). For a thread on a paired host it is read from that host and offers Working tree and Branch changes only, with no Checkpoints, since turn checkpoints are kept only for this computer's threads (ADR-0025, October 5 amendment). Avoid: "Diff" or "diff panel" for the surface.

**Checkpoint retention.** Turn checkpoints follow Keep local history. Turning it off or forgetting a thread deletes its saved checkpoints at once, along with file backups that no other checkpoint needs. Turning history off, forgetting a thread and the age and size limits keep unfinished revert records and their file backups until recovery finishes. Completed checkpoints expire after 30 days; checkpoint storage is capped at 500 MB, removing the oldest checkpoints and recovery backups first. Turning history back on starts fresh checkpoints.

**Checkpoint verdict.** What Sotto remembers about a working folder whose turn checkpoint could not be taken: why, in the words the checkpoint shows. While nothing that decided it moves (the folder's Git `HEAD`, reflog, index size, top-level listing and ignore files, and the files or directories the reason names, such as the large files that put it over the limit), each later send records an unavailable checkpoint with the same reason without measuring the folder again. A folder Git does not know or trust has none, and Git is asked again on every send. It lives in memory, so a restart forgets it, as does turning Keep local history off. Avoid: "cache", which names no reason.

**Checkpoint journal.** `checkpoints.journal`, beside `checkpoints.json`: where a send adds its checkpoint record instead of rewriting the whole file. Each line carries the generation of the file it was written against, and a line from another generation is ignored. Sotto folds the journal into the file whenever it rewrites the file: at start, in the hourly sweep, when a turn whose checkpoint was taken completes, after a revert or a forgotten thread, and once the journal outgrows the file. A damaged line is set aside as a damaged file is. Avoid: "log": it holds only the records sends added since the file was last written. Older notes call `checkpoints.json` itself a journal; that is the checkpoint file, and a record of an unfinished revert is a recovery record.

**Diff scope.** What Changes compares. **Working tree** is the working copy against HEAD, untracked files included; **Branch changes** is the branch against its base as `base...HEAD`, the changes since the two parted, with the base **Automatic** (the branch's recorded merge base, the remote's default branch, then `main` or `master`, the remote copy preferred) unless one is picked; **Latest turn** and **Turn N** are one turn's edits from Sotto's own checkpoints, numbered in the order the thread's checkpoints were taken in that working copy, and a turn whose checkpoint is unavailable says so rather than showing nothing. Avoid: "staged" and "unstaged", which are not scopes any more.

**Review comment.** The user's words about lines picked in **Changes**, waiting on that thread's composer as a chip named for the lines (`voice.ts L12 to L15`, or `(before)` when every line was removed) and marked under them with Delete comment. The next prompt carries each one as text after the user's message: its name, its words and its lines as a fenced diff, so every provider reads the same message. It keeps the lines as they read when written, lasts until it is sent or deleted, and is held in the window rather than saved with the **draft**. It is evidence for the agent to read, like any prompt text; it answers nothing and grants nothing. Avoid: "annotation", "inline comment", and "mention" for it: a **file mention** is a token written in the draft, a review comment is not.

**Reply quote.** Words the user selected in one of the agent's replies and pressed **Add to prompt** on, waiting on that thread's composer as a chip showing their first six words in curly quotes, with **Remove quote**. The next prompt carries each one as text ahead of the user's message, as `From your earlier reply:` followed by the words, each line a Markdown `> ` blockquote, so every provider reads the same message; **review comments** follow the message. It keeps the reply's message ID, lasts until it is sent or removed, is held in the window rather than saved with the **draft**, and never rides on an answer. Like a review comment it is evidence for the agent to read; it answers nothing and grants nothing. An Owl feature (ADR-0129). Avoid: "attachment" (a screenshot), "lifted question", "citation" and "excerpt" for it.

**Runnable command.** Code in one of the agent's replies that Sotto offers to run: a fenced block in a shell's language, or an inline span that reads as a program and its arguments or a path, as `src/shared/runnableCommand.ts` decides. Pointing at it or tabbing to it shows **Run in terminal**; a press opens the pane's **Terminal drawer** on a new shell, in the project folder, that main starts with exactly the text the reply shows, a block line by line. The press is the user's grant; nothing a reply writes runs by itself. Afterwards it says **Run again**, never whether the command worked, since a terminal reports only its shell's exit. Not offered on a paired host's thread. An Owl feature (ADR-0139). Avoid: "snippet" and "code block" for one that runs, "execute", "auto-run".

**Next prompt.** What the user will most likely type next in a thread, suggested after a turn on this computer, Watcher's included, ends with an answer: the thread's own provider is asked on the side for it, as for a title (ADR-0026), from the last three exchanges; a thread that ended its turn while no window showed it is asked when a client next shows it. It shows in the empty composer as a **ghost**, in placeholder ink with a Tab keycap, and Tab takes it; when what is typed begins it, the rest stays ghosted. Escape puts it away for that turn. The ghost is never part of the **draft**. It is gone once anything is sent, the thread starts again or a question is up, and it is held in main's memory, never saved. An Owl feature (ADR-0132), with **Suggest a next prompt after each turn** in Settings → Threads. Avoid: "autocomplete", "completion" and "suggestion chip".

**Next list.** The list Up in an empty prompt or the composer's **Next** button opens over the transcript, built like the skills list: the reply's headline, then answers to a question the reply asked in prose (Enter sends one at once as the user's own message), the **next prompt** (Tab), and four suggestions, numbered 1 to 4, to continue, verify, challenge or wrap up, each written into the prompt for the user to send. It answers nothing and grants nothing: a provider's structured question stays with its question card. Avoid: "chips" (the **option chips** and review comments' chips), "picker" for it in the interface, and "quick replies".

**Browser task.** One thread's work with a page in Sotto's browser, including its current action, user decisions, checks and evidence. A browser task may be working, paused, completed or failed; its reported result states what was checked and what remains unchecked.

**Browser player.** The floating window over a browser task's page, for the focused thread and never another's, pinned or not (#331). It opens on its own when that thread's agent opens a page, starting at 340x250 above the composer; drag its title bar (or, focused, the arrow keys) anywhere below the drag strip, and resize it from its corner down to 280x200. There is one placement for the session, the same for every thread. **Move into Tools** sends its page to Tools > Browser without pinning; **Shrink** turns it into a small button at its own corner that restores it; **Hide** leaves the agent working with Tools > Browser as the way back. It steps aside, drawing nothing, while Tools > Browser already shows that same thread's same page. **Show the browser when an agent opens a page** in Settings turns off only its opening on its own; the work and Tools > Browser are unchanged either way. Avoid: "preview", the corner view it replaced, which showed a thumbnail rather than the live page.

**Shared browser page.** A browser page its owning thread can observe: one the user shared, or, while the thread has a browser grant, any page of that thread the user has not made private. Under the grant it stays shared as it moves to another site; without one, sharing covers only the site it was given for. Sharing observation does not approve navigation, clicks or typing, and **Stop sharing** ends that access and makes the page private until the user shares it again.

**Browser grant.** What lets one thread open pages, navigate, click and type in Sotto's browser without asking. It covers those four actions and nothing else; on the test iPhone a tap is a click and a key press is typing, so it covers those too (ADR-0045). Every project thread has one by default, on **Let agents use the browser without asking** in Settings; while that is on, a thread's grant has the source `settings`. Off, a request in Tools offers **Allow this thread to use the browser** beside Allow once, which grants that thread the browser with the source `user`. While it lives, every page in the thread's browser is shared with the thread, whoever opened it, and stays shared as it moves to another site, unless the user made that page private with **Stop sharing** (ADR-0029, October 5 amendment); the grant reaches no other thread. It is shaped like a policy record but held only in memory. **Stop** on the grant line in Tools > Browser or Tools > iPhone ends the thread's grant, whichever its source, and the thread asks again until granted once more or Sotto restarts; turning the setting off ends every `settings` grant at once, while a `user` grant stays until stopped. It ends at Stop, when the thread is gone, and when Sotto closes. Only the setting or the user's own answer in Tools makes one; a memory, repetition or a provider's confirmation never does (ADR-0029). Avoid: "trust", "auto-approve", "allowance", which is a Devin profile's word.

**Test iPhone.** A thread's page in Sotto's browser drawn as an iPhone 15 Pro: 393 by 852 CSS pixels, iOS Safari's user agent, a touch screen and a storage of its own. An agent opens a web or Expo-web build on it with `iphone_open` and drives it with taps, swipes, typing and key presses; the user can use it too. One per thread; opening another address replaces what it shows. It is not iOS and runs no native code, so native modules, the camera and iOS rendering are not tested on it. It is a browser page, so the browser grant covers it and Tools > iPhone holds its address, sharing, steps and requests (ADR-0045). Avoid: "simulator", "emulator", which it is not; "iPhone client", which is Sotto's own app for a real iPhone.

**Cloud iPhone.** A run.cloud iOS simulator one thread uses to test a native build: the agent names a simulator build in the thread's folder, and the thread asks the user, with the build, the price and the month's minutes, before anything is uploaded. **Start cloud iPhone** covers that one session; inside it, taps, swipes and typing do not ask. It ends when the agent finishes, at **End session**, after the idle minutes, at the monthly cap, when its thread is gone, or when Sotto quits, and Sotto deletes the upload. Its key and its monthly cap live in Settings > Cloud iPhone. It is a simulator, not a device (ADR-0047). Avoid: "device farm", "emulator", "test iPhone", which is the browser page.

**3D model.** A file Meshy made for one thread from the words its agent wrote or a photo in the thread's folder, saved with its still picture in `models/` in that folder (proposed, an Owl feature, ADR-0141). The thread asks first, with the words or the photo and the credits it costs, and **Make the model** covers that one 3D model; with **Ask before each 3D model** off in Settings, threads make them without asking up to the month's credit limit. Sotto keeps a record of each one, which follows Keep local history; the files are the user's and Sotto never deletes them. A thread shows one as a quiet line that opens a turnable view; the **3D models** page and its Tools surface list them. Avoid: bare "model", which is the AI model a thread runs on; "asset", "mesh".

**Phone player.** The floating test iPhone over the focused thread, framed as Virtual iPhone's widget was: a label to drag it by (with its size, **Show in Tools** and **Hide**), the phone with the live page in its screen, and what the agent is doing below, with Pause and any waiting request. It opens on its own when that thread's agent starts a task on its phone, under **Show the browser when an agent opens a page**, and Tools > iPhone's **Show phone** brings it back. One place and size for the session, three sizes, never larger than the window allows. It can be open beside the Browser player; each steps aside only where the other overlaps it. While the thread's cloud iPhone runs, the phone player shows it instead, with its minutes and **End session**. Avoid: "widget", which is Sotto's floating dictation widget.

**Browser feedback.** A screenshot and optional selected-element or region context added to a thread's draft by the user. It is unsent draft content until the user sends it.

**Settled.** A reversible workspace grouping for a thread or project whose work the user has put aside. It preserves history and running work; restoring a project preserves the individual threads the user had already settled. Creating a new thread in a settled project returns the folder to the active sidebar with only the new thread; older threads stay in Settled. Settling a thread settles its unsettled **delegated threads** with it, and restoring it restores those settled with it (ADR-0081). Watcher restores one with `unsettle_thread` when the user asks, such as a thread settled while its background work still ran. New work restores a settled thread first: a prompt sent or queued to it, by the user, Watcher, a delegating thread or a phone, so no thread works while settled (October 23, 2026); in a settled project that thread returns alone, as a new thread does. Sotto's own news is not new work. Under **Auto-settle merged threads** (off until turned on) the host settles a thread at rest, its turn, background work, sub-agents and monitoring all ended, once GitHub reports a pull request merged at the current commit of the branch it last sent on, checked on the worktree cleanup's hourly sweep, once per thread and branch while Sotto runs; it removes no folder unless a cleanup rule says so.

**Clear (threads).** Deleting settled threads from Sotto for good (ADR-0140; Owl): **Delete thread…** in a settled thread's pane menu for one, **Clear now…** in Settings → Threads for this computer's settled threads quiet longer than a chosen age, and **Clear settled threads after** for the same on its own, after 30 days unless the user chooses 90, 180 or Never. A thread's age counts from the later of its settle and its last activity. Clearing takes the thread's record, its history and activity, its provider alias, its drafts and its own clean worktree folder; it keeps branches, Usage's numbers and the provider's own session files, and keeps back any thread that is not at rest or has uncommitted work, an open pull request, a delegated thread still working, a babysit or a watch, or a worktree holding ignored files (which **Delete thread…** lists to tick). There is no undo; Settle is the step that can be taken back. A cleared thread's ID is kept so no provider report brings it back. Avoid: "archive", which is a provider's own state that Sotto no longer writes; "forget", the store's word for taking one thread's words out; "clear history", which is the Dictate room's.

**Working threads.** The threads on this computer with a turn running (`isThreadTurnRunning`), whoever started them: the user's, Watcher's workers and delegated threads. Watcher's own thread and threads on other computers are not counted. Sotto starts any number. Past ten it warns, and holds nothing back: the **working threads line** under the Threads sidebar's search field, "11 threads are working. This computer may slow down or use its battery faster.", gone at ten or fewer, never dismissed or announced; and the same sentence as `warning` in the result of a Watcher or delegation start that took the count past ten, for the agent to tell the user (#1183, Zach's picks A and D, October 19, 2026). With Work across machines on (#1032), working threads are also counted on each **machine** (`workingThreadsByMachine`), and a Watcher start on another machine that takes that machine past ten carries "11 threads are working on forge. Forge may slow down." in its result; nothing is refused at any count on any machine. Avoid: "Threads in flight", the starts limit this replaced, and "in-flight limit".

**Terminal drawer.** A thread pane's own terminal, under its composer across the bottom third of the pane, opened with the pane's Terminal drawer button or Ctrl+J (Cmd+J on a Mac) in the pane the key lands in. Its terminal leaves Ctrl+J to the page; terminal search and text-size chords act in the focused terminal unless dictation uses that chord. Escape closes link choices first, then an open search, and otherwise belongs to the shell. Its shells start in the thread's project folder, even when the thread has its own worktree, and in the working copy only when the project folder is gone or cannot be opened; its bar names the branch only for a thread that shares the project folder. They are separate from the Tools panel's terminal: a shell started in one never shows in the other. Opening a drawer with no shell starts one; closing its last shell hides it. Hiding it leaves its shells running. Each thread remembers whether its drawer is open and how tall it is, and every pane of a split has its own. A thread on a paired host has no drawer; its terminal is on the host (ADR-0049). Avoid: "bottom panel", "terminal tab", or "Terminal" alone, which is the Tools panel's.

Both terminals, the Tools panel's and the Terminal drawer's, choose the same shell: `pwsh.exe` on Windows PATH, else Windows PowerShell; `SHELL` elsewhere, else zsh on macOS or sh on Linux. Their shells share 32 slots across every thread, ended shells included; restored running records have no output and say so.

**Thread binding.** The durable relationship between a Sotto thread, its provider session and its project. Historical bindings survive a provider's retirement and never grant a replacement provider authority over that thread.

**Provider retirement.** An upgrade that stops using an old thread provider while retaining recovery evidence and the user's draft. Old assignments, answers and uncertain actions are not transferred or replayed through a native client.

**Thread interface.** The verbs the coordinator uses for any provider, with no provider identifiers in their signatures:

| Verb | Meaning | In code (`AgentHost`) |
|---|---|---|
| create | open a new thread in a project with a model | `execute({ type: 'create-thread' })` |
| resume | observe an existing thread's detail so its history and later events arrive for it | `observeThreads` (optional for adapters that always deliver detail) then `snapshot` |
| prompt | send a user message to a thread | `execute({ type: 'send' })` |
| cancel | interrupt the agent's current turn | `execute({ type: 'interrupt' })` |
| status | read every project, model and thread the provider knows | `snapshot` |
| events | subscribe to status changes pushed by the provider | `subscribe` |

Answering a question or permission request and creating a project are also part of the thread interface. The native provider adapters preserve Sotto thread identity across these actions.

**Provider adapter.** An implementation of `AgentHost` that speaks one provider's protocol and identifiers. Every adapter must pass the shared adapter contract in `tests/integration/adapterContract.ts`. Avoid: "driver", "backend".

**Provider profile.** What Sotto knows about one provider that does not change from thread to thread, held in one record per provider: whether it writes short text, takes Sotto's tool servers and runs Watcher, which skill sigils its composer takes, whether it compacts and whether it says how full a thread's context is. What once tested a provider's name for these asks its profile instead, so a new provider is one record, and the type checker names it as missing until it has one. A connected client's capabilities say what it can do now; where a profile answer and a capability name the same thing, the adapter contract holds them equal. `src/shared/providerProfile.ts` (ADR-0095). Distinct from the launch profile Watcher gives a thread and Devin's permission profiles (ADR-0022), which are about what one thread may do. Avoid: "provider config", "provider settings".

**Codex provider session alias.** The adapter-owned record in `codex-threads.json` that maps the provider session ID Sotto chose at creation to the thread ID the Codex App Server assigned, plus the working directory, title, model and the digests of dispatched messages. The thread registry holds only the Sotto-chosen provider session ID; the Codex thread ID never leaves the adapter (ADR-0005).

**Codex session log.** Codex's own persisted transcript of a provider session (`rollout-*.jsonl` under `$CODEX_HOME/sessions`). Sotto reads only its user-authored entries to tell its own dispatched messages from text typed directly in Codex: an exact client identity and matching digest suppress Sotto's own entries, including `item.client_id` on completed items. Legacy entries without a client identity use the pending digest and consecutive-entry check. Other authored entries are a takeover. Sotto never copies or logs the log's content.

**Newest-turn check.** What the read before a send does on Codex in place of reading the whole transcript, once per send: in the coordinator's read, or in the adapter's own before `turn/start` when no read was made for the send or the thread moved since (#765). It asks Codex for its newest turn alone and reads the whole transcript only when that turn is not the finished one Sotto already holds, with the same messages. It decides whether a whole read is needed, never whether the send may go: the stale-reply check after it is the same (ADR-0005, #324). Avoid: "freshness cache", "quick read".

**Transcript cursor.** How far a thread's provider transcript had been read when Sotto last stopped, stored by the adapter beside the thread's alias: the byte after the last complete line, the identity of the file it was read from, and what the reader had already matched there. Reconnecting seeks to it instead of reading the file again, and it is only trusted beside the messages and bounded activity it accounts for in the same history epoch. `WorkspaceHost` supplies that evidence through the per-thread history source, or through `restoreThreadHistory` on the legacy path (ADR-0015, ADR-0016). For activity the store's word that it holds the records is enough: Claude reads them when a line first changes the thread, not at connect. Claude has one; a thread whose history is not handed back is read from its first byte. Avoid: "bookmark", "watermark".

**Read before a send.** The coordinator's read of a thread immediately before it dispatches a send, with `{ beforeSend: true }` and the send's message ID. The send is written against what it shows. It stands for the adapter's own read at the start of that send, and of no other, while the thread has not moved since. It writes and publishes nothing when it found nothing. The recheck still follows it (ADR-0005, #765). Avoid: "pre-send refresh", "send cache", "the one read".

**Recheck.** An adapter's read of what is new in a thread just before the prompt goes out, once the send has saved what it is about to send, so input typed into the session while the send was being prepared is seen. Nothing the send waits on after it can let input in unseen: Grok's one later wait finds the thread's process already running, or cancels the send when the session was unloaded. A reply to an old last message is refused there. Claude reads the transcript and Grok the history; Codex polls its session log, in process. It is never skipped (#765). Avoid: "second read".

**Takeover.** The user taking direct control of a thread. Native input, such as through `codex resume`, is observed without a Sotto command ID; the stale-reply check prevents an older prepared reply from being sent afterward. On a Watcher participant, direct Sotto sends, queued instructions and stop, settle, compaction or configuration controls also fence Watcher before dispatch. Opening, reading and editing an unsent draft do not take over a thread. Answering its existing request card keeps participation. A standing watch survives takeover and keeps the thread Watcher's: the user's instruction fences what Watcher had prepared, and Watcher can only steer until the user's turn and pending user work have ended. A message Sotto sent itself, such as a wake-up or a delegated brief, is never a takeover. A send that takes over a thread Watcher drove for a request alone leaves a **takeover line** in Watcher's conversation; that request no longer reaches the thread, but one the user sends Watcher afterwards does, steering only while the user's own turn runs.

**Stale-reply check.** The adapter's refusal of a send that names a different user message as the thread's newest than the one it recorded, so a reply written before a takeover is not sent after it. The coordinator names the thread's `lastUserMessageId`, which the adapter publishes from what it recorded rather than from the window of messages it holds: a window put away while the thread's session ended and taken back up later holds none of the older messages. Each adapter words its refusal its own way, says the thread changed, and sends nothing.

## History and the host

**Usage.** The page for subscription limits and all the work each connected computer's Claude Code and Codex clients did, in Sotto and outside it, and the work Grok Build, Devin, Muse and OpenCode did in Sotto's threads, with Overview, Subscriptions and Models. Its headline index opens one focused measure at a time (ADR-0083). An Owl feature, sent to stable.

**Usage history.** Counts, dates, model names and app names retained on the computer that ran the work, independently of transcript history: what Sotto observed, and what Usage read from the clients' own session records on that computer, keeping numbers only. Clear usage removes its figures separately; records from before a clear never return and new work counts afterward.

**Outside Sotto.** Work a provider client did on a computer without Sotto sending it: Claude Code itself, the Codex app, the Codex CLI, `codex exec`, Codex in VS Code, T3 Code or the Codex plugin in Claude Code, named as the client's own records name the app. Usage's **Everywhere / In Sotto / Outside Sotto** menu and its **Where you work** view tell it apart from work in Sotto. Avoid: "elsewhere", which first-run setup uses for its group of other computers and the iPhone; "external".

**Subagent work.** The tokens a subagent spent for its session, in Sotto or outside it. Usage counts it in tokens, with a bar of its own for Sotto's subagents, and never as a prompt.

**Accepted prompt.** One user message sent through Sotto whose exact native echo confirms acceptance, counted under its **served model**. Watcher messages and wake-ups have separate counts (on Owl, with **restart** on, Watcher's news counts as Watcher's and the page names no wake-ups); an uncertain send waits for that evidence. Sotto messages from before Usage began are read from the thread store, and prompts outside Sotto are the client's own user turns, each `codex exec` run included.

**Served model.** The model that answered a prompt, under one spelling: the first token report after the prompt in its thread or session, else the model selected when it was sent. A prompt on `opus` and the tokens Claude reports for `claude-opus-5-5` are one model.

**Subscription limits.** The current account allowance reported by a provider's native client, including work outside Sotto, read on demand as metadata (Claude Code through its own `get_usage`, Muse through its own `usage/read`, which a running Muse thread answers once it has made a model call, Grok Build through its own `_x.ai/billing`, which a running Grok Build thread's process answers when there is one). Each computer has its own readings and ages; percentages are never added across computers, and Subscriptions shows the freshest one with the others beside it. OpenCode reports none, so it has no place on Subscriptions.

**Observed tokens.** Numeric native request usage, under the model the provider reported: what Sotto saw on its threads, and what the clients' own records hold for Sotto and outside it. Input contains cache read/write subsets; total is input plus output. A request Sotto already counted gains its date from the client's record rather than counting twice.

**Event store.** The SQLite database `threads.sqlite` in the user data folder, opened by `node:sqlite` behind `ThreadStore`, and the source of truth for what was said in every thread. Providers are read to append to it and never asked to rebuild it; their transcripts are read on demand for rewind, takeover detection and a capped import (ADR-0016). It is a second database beside the memory store, which keeps memories and policy records and is not touched by history. Avoid: "message cache", "transcript backup".

**Log checkpoint.** SQLite folding the **event store**'s write-ahead log into `threads.sqlite` and flushing both to the disk. The **store worker** runs them between its writes, half a second after the last one finished, so nothing on main runs one (ADR-0016, October 23 and 26 amendments). As the only writer it waits for no save: once the log holds 16 MB its RESTART waits a moment for main's reads to move off the log, and the next write starts the log over. A removal the user asks for runs its own there, after the removal commits. Where the worker cannot run, SQLite runs one inside the save that grows the log past 4 MB, as it always did. Avoid: "checkpoint" alone, which is a turn's **checkpoint**.

**Posted write.** One write to the **event store**, as main hands it over: posted, then confirmed by the store once it has committed or failed. Every write goes this way (`threadStoreWriter.ts`, ADR-0016, October 26 amendment), and writes commit in the order they were posted. Until a write is confirmed, main holds it. A read that cannot wait lays the held events over what the store returns, the overlay, so the publish never waits for the disk; a read that needs the store itself waits for the confirmation. Each thread has at most one **batch in flight**, a posted batch of its events not yet confirmed, and its next batch is posted only once that one is: a batch that fails is retried, and nothing of the thread commits ahead of it. An answer posted on its own, and a history-publishing host's write, hold the thread's next write the same way. The **store worker** confirms each write once it has committed it; where it cannot run, the store confirms on main as it writes. Avoid: "pending write", which says nothing about who holds it.

**Store worker.** The worker thread that makes every write to the **event store** and runs its **log checkpoints**, confirming each **posted write** back to main, whose own connection only reads (`threadStoreWorker.ts`, `storeWorker.ts`, ADR-0016, October 26 amendment, #1457). Its commit shows to main's reads before its confirmation arrives, so the overlay leaves out what main's connection already holds. Removals commit there waiting for the disk, and their scrub runs there. Closing waits for it to commit everything posted. With Keep local history off it takes the file's words out and stops, and main keeps this run in memory. Where its built file is missing, as under the test runner, main writes as before and logs nothing. A worker that goes logs `thread-store-worker-lost`, and main writes again and finishes what it had not answered. Closing waits a minute at most; what is unanswered then is reported as not saved.

**Handover.** A fixed-rule summary of one thread's history that a new thread can start from, built by main from the **event store** with no model call, so it is the same for every provider (`handover.ts`, #1026). It keeps the thread's first user message, the latest request and its answer, then the newest history back to a character budget, shown oldest first. A message longer than a quarter of the budget is left out whole and named by who said it, when and how long it was; nothing is cut mid-way. It never carries attachments, images, visuals, tool calls or their results, and says which it left out. It opens by saying the history is context, not a new request, and names the source thread and provider. With Keep local history off it holds only what Sotto kept in memory since it started, and says so. A thread that began from another can start from one too, ahead of its first message (**Continue as a thread**); a **thin handover** is the version made from an agent's roster record. ADR-0073's "bounded visible handover" when Watcher changes provider is one: after the change, or after **New Watcher** starts a new Watcher on the same choices, the room offers the last Watcher's handover over the new one's composer, and only a send the user makes while that offer stands carries it, ahead of their words in the same message; the conversation then shows it as Sotto's, apart from their words. A **continued thread**'s first message carries one the same way (ADR-0089). It is not the atomic swap of Watcher's current reference that a comment in `shared/watcher.ts` calls a handover. Avoid: "summary" for this alone, "handoff", "transcript replay".

**Thin handover.** A handover of one subagent's assignment alone: the task it was given and the result it reported, from the roster's own record, each carried whole or left out whole and named (`agentHandover.ts`, #1028). It says it is thin, because everything the agent read, ran and decided is left out. A Codex agent's task reached Codex encrypted, so its thin handover carries its title in the task's place. It goes ahead of the new thread's first message and is shown as Sotto's, labelled **Handover, thin**.

**Message identity alias.** Corroborated native evidence that two saved message IDs describe the same authored message. Its `message-aliased` thread event keeps the canonical message in the projection only after comparing both saved messages. It is separate from a Codex provider session alias, which maps a thread to a provider session. Equal text alone is not an identity alias.

**Interactive visual.** A **visual** that is an agent's own HTML page, with its own script: a chart, a simulation, a clickable explainer. It runs in a sealed page: a `<webview>` guest on an in-memory session that cancels every request but its own one load, denies every permission and sends anything else to a proxy that answers nothing. It cannot see Sotto or load anything. The three known gaps are closed in #819: address prefetching is off for the app, WebRTC is removed from the page and its frames, and copy and cut commands the page starts write nothing; the reader can still copy a selection (ADR-0060). Main serves it from its store, once per address; the window never sends the page. Sotto gives it the theme's colours as `--sotto-*` variables and sends it the **walkthrough**'s step, with the names that step is about, and theme changes as window messages, so the page can show the step being read. Avoid: "artifact", "app", "widget", "iframe".

**Prototype ready.** A thread whose prototype waits for the user to review it (ADR-0108): a reply that ended a turn named a **working page**, or a question waiting in it carries one. The host's coordinator records it and publishes it on the thread as `prototypeReady`, with those pages and their tokens and the source it came from, the reply or the question; a question with a working page comes first. It stays until the user opens one of its pages, from the desktop or through the page route from a phone, or replies in the thread after it; a wake-up Sotto sent is not a reply, and answering the question is replying to it. The thread running again does not end a reply's mark, nor does a newer reply that names no working page; a newer one that does takes its place. The reply that holds the mark is saved, so a restart keeps it, and a source opened is remembered, and saved, so a restart does not bring its mark back. Showing the thread does not clear it, and Watcher's own threads and settled threads never earn it. The desktop's sidebar row reads **Prototype ready**, the thread pane shows **Prototype ready for review** above the composer with an **Open the prototype** row for each page, and Watcher's needs-you line and the Overview count it as needing the user. Distinct from **Finished unread**, which showing the thread clears. Avoid: "preview", "artifact", "review request".

**Prototype question.** A provider's question whose words, or the agent's reply before it, say prototype or mock-up (ADR-0108). The host's coordinator holds it while Sotto looks for its pages: no client, Watcher or alert sees it, and nothing queued goes to the thread meanwhile. With a **working page** it shows with its pages. Without one Sotto **sends it back**: it answers the question once, as Sotto, with a fixed note that says the user has not seen it and asks for a page that opens, and keeps it hidden until the provider puts it away. The thread's next question within a minute shows, marked **link missing** when it still has no working page, and is never sent back. When none comes, Sotto's own copy of the question shows, a **Sotto request** marked link missing, and the user's answer to it goes to the thread as the user's own message, quoting the question; a new question from the thread, or archiving or settling it, puts the copy away. A question that takes only listed choices cannot carry the note, so it shows at once, marked link missing. A hold lives in memory on the host that runs the thread, so a restart shows whatever the provider still has. Sending a question back answers nothing on the user's behalf and is never done for a permission. Avoid: "rejected question", "auto-answer".

**Link missing.** The mark on a **prototype question** that still names no working page after Sotto sent its thread back for one, or that could not be sent back (`linkMissing`). The host adds it; no provider does. Avoid: "broken link".

**Question page.** A prototype page an agent made that Sotto found for one of its questions, in the question's words or the agent's newest reply when the question arrived (ADR-0085): an HTML file inside the thread's folder, named by path, `file://` link or file name, or a page the agent serves on that computer's loopback. The host gives it a random token and serves it at `/page/<token>/` on its own listener, the one phone access carries, while the question waits and for an hour after; the question carries it in `pages`, and no provider supplies one. Sotto also finds the pages a thread's newest reply names, the same way, for **Prototype ready**. Every client shows it as an **Open the prototype** row before the question's **Open the link** rows. On the desktop it opens in the browser **Web links in threads** chooses: in Sotto's browser a file opens through phone access's listener, or in the system browser while phone access is off. On the iPhone it opens in Safari over the question sheet. A row opens and answers nothing. Distinct from a **visual**, which the agent draws in the thread with a tool, and from a web link in a message, which opens at its own address. Avoid: "preview", which a staged image's bytes already mean; "artifact".

**Visual.** A diagram or an **interactive visual** an agent drew in its project thread with the `visualize` tool, shown as a card where it drew it: a title and kind, the drawing or the page, and an explanation of an intro and numbered steps. A visual with steps opens as a walkthrough: one step at a time under the drawing, with Back and Next, the parts of the drawing the step names lit and the rest dimmed; **Read all** shows the intro and every step instead, with the whole drawing lit. A visual's step is one part of its explanation. Sotto keeps it with the thread in its own table, not as a **thread event**, anchored to the newest message when the call arrived; it follows Keep local history and a confirmed rewind as the thread's words do. A reader that cannot draw it, the iPhone among them, gets its words and a line saying the visual is on the computer. Drawing one changes nothing outside the thread, so it asks nothing (ADR-0056). Distinct from a Mermaid diagram written inside a reply, which is part of that reply, and from a **Step (iPhone client)**, which is one thing the agent did. Avoid: "chart", "artifact", "image".

**Walkthrough.** How a **visual** with steps is read: one step at a time under the drawing, "Step 2 of 4" with a dot for each step, Back and Next, the step's words, and the parts of the drawing the step names lit with the rest dimmed. A visual's step is one part of its explanation, written by the agent with the names of the parts it is about; it is not a **Step (iPhone client)**, which is one thing an agent did. **Read all** swaps the walkthrough for the intro and every step, with nothing dimmed, and reads **Step through** until it is pressed again. The same walkthrough steps an **interactive visual**: each step the reader moves to is sent to its page, with the names that step lists, so the page can show it. Avoid: "slideshow", "tour", "stepper" in the UI.

**Working page.** A **question page** that opens when Sotto looks (ADR-0108): an HTML file found in the thread's folder, or a loopback address that answers one GET within a moment with a status below 400, checked from the computer that runs the thread. A loopback page that does not answer is still offered on a question, but it is not a working page and earns no **Prototype ready**. Avoid: "live page".

**Thread event.** One append-only row in the event store's `events` table: a sequence number, the Sotto thread ID, a kind, a time and a JSON payload. The kinds are `message-added`, `message-text-appended` (a streaming message grew by a suffix), `message-replaced` (a whole message changed in a way an append cannot say), `message-aliased` (a native identity repair that removes only a corroborated duplicate from the projection), `messages-reset` (a confirmed rewind, carrying the new history epoch) and `answer-given` (a permission or question answer, with its attribution). Nothing is edited or deleted to change what happened; a correction is another event. Avoid: "log line", "record" for one of these.

**Sequence number.** The event store's own counter, one per thread event across all threads, and the thing a client resumes from: "everything after N" is the whole catch-up protocol. The desktop reads no events from a remote host, so it asks for none and resumes from nothing (ADR-0025). Distinct from a thread detail's `revision`, which is what one window holds for one thread, and from a message's position in the projection. Avoid: "offset", "version".

**Activity summary.** An activity record cut down to what a **step** on a phone's thread page shows: its kind, status and title, the command it ran, its exit code, when it started and how long it took, and the paths of the files it changed. Its output, text, error, diffs, plan steps and agents stay on the host. A socket client that accepts the `activity-summaries` host feature is sent every record this way, in whole details and in detail deltas alike; it is still an activity record, so a delta of summaries applies as any other does (ADR-0025, October 3 amendment). Not a reasoning summary, which is a record of its own, and not a thread's summary on its sidebar row. Avoid: "slim activity", "lite record".

**Cut body.** An activity record's command output, text or change diff that its host sent a desktop cut, its whole still on the host: at most its last 2,048 bytes of output, or its first 2,048 of text or a diff, ending at a line break, with the record's `cut` naming the whole size. Tool input that is JSON stays JSON, with its long strings shortened. Only a desktop that accepts the `activity-bodies` host feature is sent one, and every other field of the record goes whole. When the row opens, the desktop reads the record whole from the host and keeps it for the session; until then the row shows the part it was sent, says the rest is coming from the host, and holds Copy back (ADR-0025, October 18 amendment). Not **truncated**, which says details were not kept anywhere, and not an **activity summary**, which leaves the bodies out altogether. Avoid: "held body", since a **held thread**, a **held action** and a **held provider** already use the word; "lazy body", "stub".

**Detail delta.** What changed in one thread's history since a revision a client holds: text a streaming message grew by, a whole message, or an activity record as it now stands or its removal (`AgentThreadDetailDelta`). Main sends one in place of the whole detail while a thread changes, to the window over IPC and to a socket client that accepts `detail-delta`. A client applies it only to the revision it was measured from and otherwise reads the whole detail once. Avoid: "patch", "diff" for what is sent.

**Publish window.** How long one layer of main gathers a streaming burst into one send: 16 ms in an adapter's snapshot publisher, the workspace host and the coordinator's broadcast, and 50 ms for the shell and for each thread's detail at the IPC boundary and on the host socket. The first change of a burst goes out at once and starts the window; what arrives inside it goes out once, at its end, as the latest state, and that send starts the next. With both Watcher and streaming-publish-cost enabled at startup, desktop Watcher room notifications also use a 50 ms leading/trailing window. A Watcher change only marks the room changed; the room is built when an update goes, at once for the first change and at the trailing deadline for the rest, from what is true then, even after the source becomes quiet. Each update carries only what changed since the last one the window was sent, and none goes when nothing changed but the time the room was read (#1450). This is a separate desktop room publisher, with a timer independent of shell, detail and coordinator publishers. Direct room operations flush prior pending notifications when they settle and retain their own result or error. Watcher observations and phone/socket event timing stay unchanged. Distinct from the main window and from a history window. Avoid: "debounce", "the window" on its own.

**Push pacing.** How a host's listener keeps a socket client that reads slowly from being buried: while output to that client is still backed up, the host writes it no further shell, Watcher projection or thread update. Once the output drains it sends the newest shell and projection, built then, and for each observed thread one update folding everything that changed while the client was behind, removals included, or the thread whole when the changes do not fold. Answers never wait. Distinct from a publish window, which every client shares; pacing is each client's own. Avoid: "throttling", "dropping" (no push is lost).

**Opening change.** A change that brings a message's first words or a new activity record, as against more words for a message already sent or a record that changed. No layer holds one behind a publish window: it goes at once and starts a fresh window, so a reply's first words do not wait behind the echo of the prompt that asked for it (#771). An adapter's publisher, the workspace and the detail coalescers let only one opening change cut a given window short, and none cut the window after a send that carried one held back, so a read that records hundreds of messages costs two publishes rather than hundreds, and a read that goes on costs one a window. The workspace counts only threads a window may be looking at; the coordinator cuts only for a thread a window holds. A reply that has sent only whitespace has said nothing yet. Avoid: "first chunk" for a new record.

**Thread changes.** What one layer of main hands the next in place of a whole snapshot: the threads that changed, as whole records frozen all the way down, the Sotto thread IDs of those that went, a **placement** for each thread that came somewhere other than last or moved (the thread it now goes before), and the rest of the snapshot (providers, catalog, projects, connection) only when it changed (`threadChanges.ts`, ADR-0016's proposed October 24 amendment, #925). Each carries a sequence number. The first is **whole**, listing every thread in order, and so is one after a subscriber missed one and asked its publisher for a **resync**, or one in which most of the threads moved. Each subscriber keeps its own **thread map** of the records, applies what it is given, ignores one older than what it holds, and builds a whole snapshot only for a read or a command. They are internal to main and never cross IPC or the socket; until a layer marks its own, a shim works them out by reading each thread against the record it published last. Every provider adapter marks its own: each path that changes a thread **marks** it changed, and the adapter's publication carries only the marked threads (`adapterThreadChanges.ts`). Avoid: "diff", "delta", "patch", which name other things here.

**Catalog revision.** A number main gives each host's model catalog, advanced only when the catalog's content changes (ADR-0028). The broadcast sends a catalog once per revision per window and then only its revision; a command receipt always sends only its revision. A window reads the whole state once through `AGENT_GET` when it holds neither that revision nor, for a command receipt, a newer one. The headless host and the desktop's phone listener each keep catalog revisions of their own for the paired clients that accept `model-catalog-revision`: each shell names the revision, and carries the catalog only the first time a connection is sent it. Distinct from a thread detail's `revision` and from a sequence number. Avoid: "catalog version".

**Changed thread records.** What a main-window broadcast carries in place of every thread: the thread records new or changed since the last broadcast that window was sent, which it names as its base, with the IDs of threads that went and, when it moved, the order (`AgentThreadsBroadcast`, ADR-0028's October 22 amendment). The page rebuilds the whole ordered list before any reader sees it. A window that holds another base reads the whole state through `AGENT_GET`, and the next broadcast lists every record. Command receipts and `AGENT_GET` carry every thread. Distinct from a catalog revision and a thread detail's `revision`. Avoid: "thread diff", "delta" (a detail delta is one thread's history).

**Command receipt.** What main answers a window's command with: the shell after the command, its outcome and the evidence its caller acts on (the draft revision saved, the effective settings), with each model catalog named by its catalog revision rather than listed (`AgentCommandReceipt`, ADR-0028). The page puts the catalogs back before any caller reads it. Distinct from the delivery receipts in `deliveredDrafts` and `followupReceipts`, which each record that one draft revision was accepted. Avoid: "command response" for what crosses.

**Answer receipt.** The owning host's evidence that it accepted one client's exact submission for a question in a thread, with that question's original form. It settles only that saved answer; a question disappearing or a command finishing alone is not an answer receipt. Avoid: "command receipt" for answer acceptance.

**Projection.** A table derived from the event log for reading, currently `messages`: one row per message of a thread, keyed by position, which is what a thread pane draws. A projection is rebuilt from the log when it is missing or when the schema version moves, and is never written to by hand. Avoid: "view", "cache".

**History window.** How much of a thread's history a pane holds: the newest ten turns when it opens, then twenty more each time the user presses **Show earlier messages**. A turn here is a user message and the assistant messages that follow it. The detail says whether anything older exists (`earlierAvailable`), so opening a long thread costs the same as opening a short one. The detail windows activity the same way: the work of a turn above the window stays out of it with that turn's messages and takes its place between them when they load, so it never trails the newest answer. The turn still running is always in it. Only the detail does this; the store keeps every record and the sidebar counts them all, while a thread no window is looking at keeps them in the store alone (**stored activity**).

**Turn fold.** The one line a finished turn puts its work under, between the user's message and the turn's last written reply. It says how the turn ended, how long it took and how many steps it holds ("Worked for 40s · 6 steps", "Failed after 12s · 2 steps"), with the files it changed beside it. Pressing it opens the messages and activity in between, and Escape on it or inside what it opened folds it again, as it folds every open activity line, one level at a time. A **visual** never folds and is never the last written reply: it stays in view where it was drawn, before or after that reply. Until pressed it starts as the user last left any turn's steps (**steps opening**). A turn still running keeps its steps under the **working line** instead, and a turn whose start is above the history window keeps every row on screen because it has no finished span to fold. A failed step folds with the rest; the turn's own error stays in view. So the rows a pane draws count what it is showing, never how much history it holds. What the folded replies asked stays in view under the line as **lifted questions**.

**Working line.** The one line at the end of a running turn: the working words ("Combing the desert", "Ludicrous speed") with a slow band of light crossing them that lights the letters in the theme's accent at its most vivid, and the turn's steps folded under it. It has no clock (ADR-0134). A press opens the steps, the newest six in view, and Escape folds them again; until pressed they start as the user last left any turn's steps (**steps opening**). It has no sign of a failed step, and it is named for the fact rather than the words: "Working, 12 steps so far". Under reduced motion the light holds still and a still dot stands beside the words; while the provider is not connected it reads Last seen working. Once the turn ends its work goes under the **turn fold** (ADR-0134). The iPhone's working **step run** shows the same words with its own, softer light. Avoid: "spinner", "shimmer", "status line".

**Steps opening.** Whether a turn's steps start open or folded: the **working line**, the **turn fold** and the groups inside it, and the work folded into a Watcher reply's header. One answer for the whole app, set by the last press on any of those lines (Escape folds only the one it is in) and kept after a restart; every line the user has not pressed while it is on screen follows it, and one they pressed keeps its own state. A group inside a fold follows it without setting it, so folding a group never folds the turn around it. Not a setting: there is no Settings row for it (ADR-0134, October 26 amendment). Avoid: "expanded state", "thinking dropdown".

**Lifted question.** A sentence ending in a question mark in a reply the **turn fold** hid, quoted under the fold with who asked it, when, and **Show where it asked**, which opens the fold at that reply (ADR-0080). Sotto picks it by punctuation alone, outside code, headings, tables and quotes, so it can quote an aside and miss a question asked without a question mark. It is for reading: it is not a request, the sidebar does not change for it, and nothing answers it. A question the provider asked with its own question tool is a request card, and folds with the work once answered. Avoid: "pending question", "detected question".

**Message scrubber.** The column of ticks in a long conversation's left margin, one for each message the user sent, in a thread and in Watcher's Conversation tab (ADR-0109; an Owl feature, sent to stable). It shows once three or more messages were sent and the conversation is two screens tall, faint until the pointer or the keyboard reaches it; the ticks near the pointer rise on a normal curve. A tick's card shows the message and the start of the reply, or the question it led to, and a press puts that message at the top of the transcript, drawing an earlier page first when it has to. It reaches every message sent in the thread: those the **history window** holds, and above them the ones only the thread's store holds, which a press loads the window back to first. In Watcher the **night scene** runs on under its lane, the ticks floating over it with no box, while the scene's owls keep out of it. Avoid: "minimap", "timeline", "jump bar".

**Thinking.** What a model works out before and between the parts of its reply, as its provider streams it: Claude Code's thinking blocks, and Grok Build's and Devin's thought chunks. It is a reasoning activity record titled Thinking, drawn by the same row as a Codex reasoning summary and placed the same way. It shows from the block's first byte rather than once the block is finished, and grows as the words come. A block the provider keeps to itself (Claude's redacted thinking, or a block with no words) still shows the row, without text. Thinking cut off by its turn failing or being stopped settles as interrupted. Thinking is reply content: it stays in the thread's own record and never reaches a log. A finished turn's fold counts it apart from reasoning summaries ("thought 3 times"). On the phone it is a **step** whose line reads Thinking; the same word in what VoiceOver hears of a working run's line, when no step is running, means only that the agent is between steps. Avoid: "reasoning" for it alone, which also names the coordinator's reasoning account; "thoughts" in the UI.

**Creature.** The small pixel character above a thread composer that shows what the provider says is still going on. It has four poses, each owned by its own entry: it walks with a magnifying glass for a **monitoring task**, stands by the readout and sends small agents out for **background work**, holds an hourglass for a **held action**, and rests holding a sign in a quiet colour while the thread **babysits** a pull request. Settings → Appearance → Creature chooses which character wears the poses, Sotto's own or **Claude bot**; the choice is saved on this computer and never changes when, or whether, a pose shows (ADR-0116). In Sotto Owl the same place has a switch, Show the creature (`creature-toggle`, an **Owl feature**); off, no pose and no readout stand above any composer, and the sidebar still says what each thread is doing. Beside it stands the **readout**: the words naming the task, with Monitoring, Working, Waiting or Babysitting under them, set on the room with no fill or outline, so they never cover what they stand over. Avoid: "mascot", "avatar", "pet"; "ornament", which is what the code calls the whole strip.

**Claude bot.** The second **creature**: a small boxy pixel bot with an antenna, two arms, four legs and a chest emblem that turns like a spinner. It wears the provider's colour for Claude through the theme, muted while babysitting, and wears every pose under the same rules as Sotto's own creature. It is only how the creature looks; it claims nothing and grants nothing. Avoid: "Claude mascot".

**Monitoring task.** A live, provider-confirmed watch on a background process or task. A running command or unattended process is not enough evidence. The little creature above the thread composer (see **Creature**) appears while that watch is active and leaves when it ends or needs your answer. Monitoring is observation, never permission to act, and is not restored from history. It outranks **background work** and a **held action** for the composer's one creature, because it is the strongest claim of the three: the provider says it is looking at something. A thread whose turn is over while one runs says Monitoring in its sidebar row, and its status ring is an hourglass, as a babysitting thread's is.

**Background work.** Agent work, or a command sent to the background, started from this thread that the provider has confirmed is still running, whether or not a turn is: a workflow, a subagent, a teammate, a remote agent, or a shell command. The creature (see **Creature**) stands at the end of the track by the readout and sends small agents out along it, and the reader is told **Working**, or *Working · 3 agents* when there are several. A command waits rather than works: once the turn has ended it holds the hourglass and the reader is told **Waiting**, named by its description; beside agents it is only counted, *Working · 2 agents · 1 command*. The evidence is the provider's own task frames, a start and the bookend that ends it, never elapsed time or what the transcript says; today only Claude Code reports them. A subagent the turn is still blocking on is the turn's own action, not background work, until it is moved to the background. Work started by another agent is that agent's business and does not count. Background work survives the end of the turn, and so does the thread's sidebar row: it stays **Working** with its ring while agents run, or reads **Waiting** for a command alone, and when the work ends it reads **Working** through the turn Claude Code starts on its own to report back, saying **Done** once that report is in. A message from another session, or a continuation after a usage limit, is a turn Claude Code starts on its own too, and reads the same. It keeps its provider session from being reaped, and ends with its bookend, an interrupt, an error, a disconnect or a restart. Like a monitoring task it is observation only, grants nothing and is never restored from history. A monitoring task outranks it; it outranks a held action. While the creature may show, on Owl, each agent (not a command) also has a row under the thread's last finished reply, after "Still working after this reply", beside any delegated work still running, until its bookend; the row opens nothing. Not to be confused with **working preferences**, your answers about how you like to work.

**Held action.** One action of the live turn — a command, a tool call or a subagent — has held the thread for twenty seconds or more. The same creature (see **Creature**) stands above the composer holding an hourglass, naming the action and how long it has run; the reader is told **Waiting**, which is the plain word for it. A command the turn sent to the background wears the same pose once the turn has ended (see **Background work**). Not to be confused with a thread **waiting on you**, which is `ThreadRow.waitingFor` and reads *Needs your approval* or *Needs your answer* in the sidebar: that is the one case a held action excludes, because its request card already says so. A held action claims only elapsed time — unlike a monitoring task it is no evidence that the provider is watching anything, it grants nothing, and it reads the `activities` every adapter writes rather than any one provider’s events, so it needs only that the adapter record when a running action started, which Claude Code, Codex, Grok Build and Devin all do. A confirmed monitoring task and confirmed **background work** both outrank it, in that order, because the composer reserves room for one creature and each of them is a stronger claim than a clock.

**Watched set.** The threads the host keeps in memory and keeps a provider session for: the threads on screen, plus ones with queued user follow-ups. A thread whose queue holds only a **wake-up** still waiting is not queued for this; babysitting is not background work (ADR-0061). A wake-up being sent is: its thread joins the set from the moment the queue takes it until the provider confirms it, so a wake-up to a thread no one is looking at is confirmed like any other send. It is what `observeThreads` names. A thread outside it carries its summary alone, so startup and publish cost follow the open panes rather than the whole archive. Avoid: "active threads", "open threads".

**Finished unread.** A thread that finished its work while no client showed it, and that no client has shown since. The host's coordinator records it, keeps it across a restart and publishes it on the thread as `finishedUnread` (ADR-0046). The thread earns it when its turn, and any background work that turn started, ends while no client observes it; a disconnect, a failed turn or a thread on screen earns nothing, and working again drops it. Showing the thread on any client clears it on all of them: a pane on the desktop while its window has the focus, or the thread open on a paired iPhone. A thread that finishes in a pane while the window is behind another app, minimised or in the tray earns it, and the window gaining the focus clears it. The desktop's sidebar reads it as **Just finished**; the iPhone marks the row in Recent with a dot and a bold title and counts it on the Threads tab. Avoid: "unseen", "new", "unread" on its own (messages have no read state).

**Failure seen.** A thread whose last turn failed and which asks nothing, and which a client has shown since it failed, or which **Dismiss all** named. The host's coordinator records it with the failure it was seen in, keeps it across a restart and publishes it on the thread as `failureSeen` (ADR-0092). Showing works as for **Finished unread**. The thread loses it when it runs or rests again, so its next failure says **Needs attention** again. The desktop's sidebar reads a seen failure as **Done**, and the open pane still says why the turn failed. A thread waiting on a permission or a question is never seen this way. Avoid: "dismissed", "acknowledged", "cleared error" (the thread is still failed).

**Dismiss all.** The button beside the sidebar's **N need attention** line, under the search. One press marks every failed thread that has not been seen as **Failure seen**, on whichever host runs it. It counts and dismisses failed turns only, never a request waiting on the user (ADR-0092). Avoid: "Clear all", "Mark all read".

**Session reaper.** The host's sweep, every five minutes, that stops a provider session idle for thirty minutes. It never stops a session with a running turn, one with a pending request, one with a confirmed live monitoring task or background work, or one in the watched set, and stopping one costs only a resume because the resume cursor stays on the host. An in-flight history read defers its session's stop without renewing idle age or holding another session open. Empty polls do not count as activity; newly read provider events do.

**Early start.** The first keystroke in a thread's composer starts the thread's provider session on its host, so the send that follows does not wait for it (ADR-0057). It starts only what the thread's next action would, sends nothing to a model, marks nothing busy and says nothing when it cannot start; the send reports its own error. A window asks once per thread and again only after it has seen that session open, from the thread's `providerSessionOpen`. A new thread whose first send has not happened gets the client that send would use. Claude Code gets a **spare**: its CLI started on the session ID the send will create the thread under and answered `initialize` and nothing more, which the send adopts when it creates the thread with the same folder and settings. A spare runs in the thread's folder, so a thread whose worktree the first send makes gets none. Codex and Grok Build get the thread's process with no session, and Devin gets nothing. Whatever its provider, a thread whose new worktree starts from origin also has its base fetched, unless the Git fetch interval is Off, and the send uses that fetch while it runs or for two minutes after it finished. No provider session, worktree, branch or record exists before the send. Avoid: "wake", which could be confused with a babysitting wake-up; "warm-up", "prewarm".

**Stored activity.** A thread's activity records while they are in the thread store and not in memory. A saved thread starts this way, and one that no window is looking at and nothing is running in goes back to it after a save. Its count and history marker stay in hand for the sidebar and the transcript cursor. Its records are read back when a window looks at the thread, when its provider changes one, or when an adapter asks for them, and a stored thread's list is never saved over, so nothing in it is lost (ADR-0016, #918). Not a **held thread**, which is about an adapter's messages. Avoid: "unloaded", "evicted", "cold".

**Held thread.** A thread whose messages its adapter keeps in memory: it is in the watched set, its provider session is still open, or nothing has yet said what is watched (`ThreadMessageLog.holding`). The session reaper decides how long an idle one stays held, so during a working session most threads are. A held thread's messages still reach the workspace only as thread events, never in the activity snapshots it reads, a thread refresh, or the snapshot a confirmed thread settings change hands back (ADR-0016). Not to be confused with a **held action**, one action of a live turn that has run for twenty seconds or more. Avoid: "loaded thread", "open thread".

**Host.** The process that owns the providers, the worktrees and the event store. It is Electron main on this computer (the local host) or `src/host/index.ts` running under plain Node on any machine reached over SSH (a remote host); the desktop can hold several at once (ADR-0025). The word is also the suffix of the interfaces inside it (`AgentHost`, `WorkspaceHost`); in the host-and-client sense it means the whole owning side, whichever machine it runs on. A host Sotto started over SSH outlives the desktop and stops only on Stop host or Forget. On Linux it can also **start at boot**, and a host its boot unit started counts as started by Sotto (ADR-0054). A desktop reaches a remote host by a **tailnet connection** first and its **SSH connection** when that does not answer (ADR-0053). Avoid: "server", "backend".

**Host service.** The interface the host offers a client and nothing more: the event stream after a sequence number, the shell, one thread's detail, and commands. `HostService` in `src/main/agents/hostService.ts`, with `LocalHostService` over `AgentControl` as the only implementation today; the window's commands go through it, so a second transport is a new client rather than a rewrite. Distinct from `AgentHost`, which is the interface a provider adapter implements on the other side of the coordinator. Avoid: "API", "server interface".

**Host facts.** What kind of **machine** a host runs on, read at one observation time: its operating system family, name and version as the system gives them (Windows 11 by build, macOS by its marketing version, a Linux distribution's os-release name such as Omarchy), architecture, total and free memory, and logical CPU count. The operating system is read once when the host starts; memory is read again when facts are asked for and the last reading is a few seconds old, never on a timer. A headless host sends them, with how many of its threads are running a turn, through the optional `host-facts` feature to a desktop only, and the desktop reads its own the same way. A fact the machine cannot give, or an older host that sends none, reads unknown, never guessed. Numbers and the system's own name only, on the connection Sotto already keeps; never a user name, path or address, and nothing in a log. Watcher's `list_machines` shows them for This computer and every connected machine. `src/main/agents/hostFacts.ts` (#1031). Not the host ID, which says which machine, not what kind. In copy the thing a host runs on is a **machine**; the host is the process, and This computer is the local one. Avoid: "specs", "system info", "server".

**Branch move.** Carrying a committed branch from one of the desktop's **machines** to another, as a Git bundle over the host socket the desktop already keeps, so no SSH session is opened and nothing goes through GitHub (ADR-0082, amended by ADR-0105 decision 8). The sending working copy must be clean: uncommitted work refuses the move with a request to commit first, and the commit Sotto checked is the one that moves. The bundle carries only what the receiving repository lacks, at most 256 MiB, and lands in an **incoming ref**; a transfer cut off lands nothing. The desktop is the only caller today, and a move ends in a receipt: the incoming ref, or a refusal that says nothing moved. Owl only (`cross-machine-work`). `src/main/agents/branchMoves.ts`, `src/main/agents/branchBundles.ts`, `src/host/branchMoves.ts`. Not a thread move, which continues a thread on another machine as a new thread, and not a push: no remote is involved. Avoid: "sync", "transfer" on its own, "push to forge".

**Incoming ref.** Where a **branch move** lands in the receiving repository: `refs/sotto/incoming/<move>/<branch>`, one per move, created once and never moved or forced. A checked-out branch, and any branch the user made, is never written by a move; the receiving worker starts in a new worktree made from the incoming ref (ADR-0082 decisions 2 to 4), and the ref is removed when that worktree is. A ref that brings a child's commits back to the thread it began from (**bring changes back**) is removed once that press is over. Avoid: "remote branch", "tracking branch".

**Start from a branch.** A worker Watcher or a delegating thread starts from a thread's branch (#1033): `fromThread` on Watcher's `start_thread`, `from_my_branch` on `delegate`. Sotto puts that branch in an **incoming ref** on the machine the worker starts on, by a **branch move** to another machine or a copy on the same one, then starts the worker in a new worktree on a branch of the moved name, or the next free `<name>-<n>` when that name is taken there, as it is when the worker starts beside the thread that holds it. Uncommitted work refuses it, as it refuses a move, unless the start is a **check**. Its receipt's `startedFrom` says "Started on forge from feat/x." Owl only (`cross-machine-work`). Avoid: "fork", which is a thread's conversation, and "clone".

**Check.** A start that says it is there to run tests, by `testRun` on `start_thread` or `test_run` on `delegate` (the model-facing names keep the older words). Sotto never guesses one from the commands a thread runs (Zach, October 22). A **start from a branch** that is a check carries the thread's uncommitted work as a **check snapshot** instead of refusing it. A machine runs one check at a time, and the rest wait in its **check queue**; reusing one test worktree per project is still #1312's. Its reply is the contract: the thread is asked to begin it with the verdict, the counts and the failing lines, inside the 32 KiB Sotto passes on, and Sotto reads no pass or fail from it. Not a pull request's checks, the CI runs GitHub reports on a pull request (Gates, Package result, Desktop result), which Sotto only reads: a check is a worker Sotto starts on one of your machines, and its verdict is that thread's own words. Avoid: "test run", "CI run".

**Check queue.** A machine's **checks**, one at a time (#1312, Zach, October 21 and 23): the one running and the ones waiting behind it, in the order they were asked for, whoever asked. A check takes its place as it is asked for, before its snapshot is taken, so a slower snapshot never lets a later check overtake it. A waiting check's outcome stays `working`, with no outcome word of its own; nothing of it is started, so it counts as no working thread, and the call's result says how many are ahead ("Waiting for This computer's check to finish. 1 ahead."). Stop on it, or on the thread that asked for it, takes it out of the queue. A check holds its place while it works, while its brief's delivery is unconfirmed, and while background work its turn left running has not been seen to end, up to twenty idle minutes (`CHECK_HOLDS_THROUGH_BACKGROUND`, Zach, October 27). Only starts queue: a later brief to a check's thread does not. The queue lives in the memory of the Sotto running on that machine, so a restart empties it and starts none of what waited, and closing Sotto lets go of the branches waiting checks would have started from. So far it holds the checks a thread delegates on This computer (`CheckQueue` in `src/main/agents/checkQueue.ts`); Watcher's checks join it in a later part. Owl only (`cross-machine-work`). Avoid: "test queue", "CI queue".

**Check snapshot.** A thread's uncommitted work, carried for a **check** as one commit object: Sotto copies the thread's Git index to a temporary file, runs `git add -A` against the copy so `.gitignore` is respected, writes its tree and commits it with the branch's commit as parent. No branch, no stash, and the thread's working tree and index are untouched. `git add -A` takes only a submodule's commit, so a submodule with changes of its own refuses the check rather than leave them behind. It is taken when the check is asked for, even when the check then waits its turn, and the receipt says when, as the computer writes a time in the interface language, and names the untracked files it carried: "Started on forge from feat/x with your uncommitted changes as they were at 2:02 PM (3 untracked files)." Its author and committer are "Sotto <sotto@localhost>", and a branch that holds one is never brought back as a commit (**bring changes back**). `snapshotOf` in `src/main/agents/branchBundles.ts`. Not a provider's snapshot, a host snapshot or a checkpoint's, which are reads of state. Avoid: "stash", "snapshot" on its own.

**Where new workers start.** The setting (`newWorkerMachine`, under Settings, Watcher, part of the Owl feature Work across machines, #1032) that says which **machine** a new worker goes to when the start names none: **This computer**, the default, so nothing moves until the user chooses; a connected machine, by its saved host ID; or **Let Watcher choose**. A start's own words decide over it for that start: a start may name a machine, or a **system** (`os`: Windows, macOS or Linux, matched against **host facts**), and a system never falls back to another. A project named on This computer goes to the machine new workers start on, to that machine's copy of it; a project named on another machine starts there, as Watcher has always placed work. A machine that is not connected, or no longer saved, starts the worker on This computer instead, and the receipt says why. `src/main/agents/workerPlacement.ts`. Avoid: "default host", "target", "placement policy".

**Placement.** Where a start went, as its receipt records it: the **machine** by host ID and name, whether that is away from where new workers start and, if so, that machine's name, and Sotto's sentence saying why when it chose itself. Watcher says why in its reply when a worker is away from the default. Kept in memory with the receipt, as a worker role's note is. Not the browser player's placement, which is where its window sits. Avoid: "scheduling".

**Project origin.** The GitHub repository a project's `origin` remote names, by host, owner and name, read from the URL alone so HTTPS and SSH spellings match (`sameRepository`). How Sotto finds the same project on another **machine**: a machine with no project of that origin has no copy, and a start there is refused in plain words ("Forge has no copy of Sotto. Add the project on forge first."); Sotto never clones. A headless host reports its projects' origins to a desktop through the optional `project-origins` feature, only where its Owl answer turns Work across machines on; an older host cannot be matched, and a start must name one of its own projects. Never a path or a remote URL. `src/main/agents/projectOrigins.ts`. Avoid: "remote", which is the Git remote itself, and "repo match".

**Live load.** How busy a **machine** is now, read with its **host facts** over one window ending at one observation time: the share of CPU time not spent idle, the one-minute load average where the system has one (not Windows), the memory a new process could have at the window's start and end (unknown on macOS, where the free memory Sotto can read understates), and Linux's own memory pressure where the kernel gives it. A host reads it only when facts are asked for, over the window since its last reading or from two samples a couple of seconds apart, and keeps the last reading; nothing reads on a timer. Any number the machine cannot give, and an older host's whole load, reads unknown, never guessed, and a reading over a minute old is unknown for placement, not idle. Short on memory and busy are what it says against `MACHINE_LOAD_THRESHOLDS` in `src/shared/hostFacts.ts` (#1311). Short on memory is under the smaller of 2 GiB and a tenth of the total, so a machine whose total is unknown is never called short: under 2 GiB it reads unknown. Part of the Owl feature Work across machines: a machine whose Owl answer has it off reads none, and its facts are what they were. Avoid: "usage", which is the **Usage** page's; "health".

**Work placed but not started.** A **machine**'s threads that have been sent work and have not begun it: not running a turn, with a send queued or being submitted, a follow-up queued until it starts or is withdrawn, or a Watcher start admitted there whose first prompt has not gone, counted from admission, before its thread exists. Its host counts them with its **live load**, so two starts seconds apart do not both count the same free memory, and only while Work across machines is on, as the load is. A start a desktop's Watcher has admitted for another machine counts there from admission too: until that machine holds it the desktop adds it, and once the machine counts it, by the same Sotto thread ID, the desktop does not. A start whose request to that machine timed out still counts until the machine's own receipt for it is read, since the machine may yet start it; one whose connection closed does not. Not running threads, which have begun (#1311).

**Desktop defaults.** The user's new-thread default and worker roles as the desktop holds them, which the desktop sends a headless host that runs **delegation** for its own threads (#1310, part of the Owl feature Work across machines), when it connects and whenever either changes. The host keeps each desktop's, with its client ID. The last ones sent apply, among the desktops still paired there with an answers grant; one forgotten, revoked or without a grant stops counting, and the next most recent apply instead. A thread delegated there starts no wider than them, and no wider than Ask for approval when none count. A host never told holds every delegated start to Ask for approval; its own stored new-thread default never applies. Settings, never a key or a grant. `src/shared/desktopDefaults.ts`. Avoid: "host settings", which are the host's own, and "sync", since nothing comes back.

**Client identity.** Who is speaking to the host service, carried on every command. The desktop window uses `desktop-window` over IPC; a paired remote client uses its pairing ID over a socket. Answers carry that attribution, while policy records decide whether the client may grant. Avoid: "session", "caller".

**Client.** The side that draws threads and sends commands, speaking only the event stream and the thread interface and holding no provider identity of its own. The app's window is one over IPC; the desktop reaching a remote host is another, speaking the same two things over a socket (`SocketHostService`, ADR-0025). The iPhone client (`apps/ios`, in development) speaks the same socket protocol from its own Swift code, not through `SocketHostService`, to a headless host or to a desktop with phone access on. Avoid: "frontend", "UI" when the split is what is meant.

**Attribution.** Who gave an answer, carried on every `answer-given` event: `{ clientId, user, transport }`, where transport is `ipc` for the desktop window on this machine or `socket` for a paired remote client. It is evidence of who answered and never authority in itself; policy records decide whether an answer counts as a grant (ADR-0004), and the local desktop window always may answer. Avoid: "identity", "actor".

**Pairing.** How a client beyond loopback is admitted: a short-lived single-use code is redeemed once for a token, and signed sessions over that token carry every later request. `PairedClients` in `src/main/agents/pairing.ts` holds the records — a client ID, a normalised device name and the token kept only as a hash — and a per-install secret signs the sessions. Over SSH the desktop asks the host for a code and redeems it itself, the tunnel being the user's authenticated session; a client with no SSH session types a code shown on the host instead, in Settings > Hosts & phones on a desktop, in a headless host's Phones dialog on the desktop that reaches it, or printed by the host's own command. The iPhone client does this over private Tailscale HTTPS, once for each **computer** it adds: the user types the machine's name on the tailnet, the phone finds its full `*.ts.net` address through MagicDNS and checks a Sotto host answers there, on port 8443 (where the desktop serves it), then 10000 (where it serves when another app holds 8443) and then 443, and the code is spent only on that host (ADR-0025). Being paired is admission and not authority: a `remote-answer` policy record scoped `client:<clientId>` is what lets a client's answers count as grants (ADR-0004). Setup over the user's authenticated SSH session creates that record for the desktop once; any recorded revocation or expiry prevents setup from granting it again. Clients paired by code need an explicit grant. The host's listener binds loopback only, and the README's "Privacy and cost" section names the SSH path and phone access. A desktop pairs only over SSH, never on the **tailnet listener**; the token it gets over SSH also opens its **tailnet connection**, because the host keeps one pairing store for both listeners, and the grant written over SSH is honoured there too (ADR-0053).

**Phone access.** The desktop letting the owner's paired phones reach its local threads, over the owner's tailnet (ADR-0033). While the `phoneAccess` setting is on and the local host runs, main opens the host protocol listener on loopback over the desktop's host service and has Tailscale Serve carry HTTPS port 8443 on the tailnet to it, or 10000 when another app already holds 8443; never Funnel, and never port 443. Sotto changes only a Serve setting that is its own, removes it when phone access turns off and when Sotto quits, and puts it back at the next start, on the port it last used while that port is free. If removal fails, phone access stays in a cleanup failure state, stops the host protocol, reserves its loopback port, and retries while Sotto is open. Settings > Hosts & phones is where it is turned on, where each setup step says whether it worked, where pairing codes are shown (one at a time, and nowhere else on the desktop's own phone access), and where each paired phone has **Can answer**, the owner's switch that writes or revokes that phone's `remote-answer` policy record, and Remove. Pairing also allows a phone to change the computer’s saved reasoning provider and model without Can answer; nothing sends coordinator content any more, so this only changes the model a new thread starts on when no new-thread default names one. It also allows the computer's projects directory and new-thread defaults, except a permission default that lets threads act without asking, which needs Can answer (ADR-0074). Keys and endpoints stay host-local. Each computer shares only its own threads. A headless host runs the same phone access over its own host service and pairing store, on its **tailnet listener** (ADR-0050). Its `phoneAccess` setting is the host's own, and the desktop turns it on, shows its checks, pairs its phones and gives each Can answer and Remove in the host's **Phones** dialog in Settings > Hosts & phones, through the host's administrative routes, over its **SSH connection** or, when it is on its tailnet connection, an **admin connection** (ADR-0053). Turning a host's phone access off no longer cuts off a desktop's tailnet connection there. The clients that paired through phone access are its phones; a desktop paired with the same host is never one. `src/main/phones/`, `src/host/phones.ts`, `src/main/hosts/hostPhones.ts`. Avoid: "remote access", "mobile server", "tunnel" for this, and "phone host": the phone is a client.

**Launch script.** The fixed Node script the desktop pipes to one `ssh` command per operation on a remote host's machine: find the host or start one detached, ask it for a pairing code, revoke a client, stop a host Sotto started, or take one step of a **host update**. It prints one JSON result and exits. The only ssh that stays open is the port forward of an **SSH connection**, and an **admin connection** for as long as it is in use; a **tailnet connection** needs neither (ADR-0053). A launch's result also carries the host's administrative token and the host's **tailnet address**. The desktop keeps the token in memory for that ssh, whichever of the two it is, to administer the host's phone access through it (ADR-0050). The result also names the Node the script ran under, which a **Forget notice** puts in its command. The launch script also installs, reports and removes **start at boot** (ADR-0054). A short shell in front of it finds a Node the host archive accepts, through the login shell and the usual version managers, and says so when there is none. A host it starts records that in its own listener descriptor, which is how a host counts as started by Sotto (ADR-0025). A host that updates itself runs the same script's update steps on its own machine, as a child of the host rather than over `ssh` (ADR-0088). `src/main/hosts/launchScript.ts`. Avoid: "daemon".

**Tailnet connection.** The desktop's connection to a remote host through the host's **tailnet address**, authenticated by the pairing the desktop made over SSH. It is tried first when the owner prefers it, which Add host chooses for a new host (a host saved before it keeps SSH until the owner chooses otherwise), and needs no ssh at all; when it does not answer, the desktop uses the **SSH connection** and tries the tailnet again every 5 minutes. A move between the two keeps the host's threads on the page. The owner chooses in Edit connection, under How Sotto connects, and the host's row begins with `Tailnet` or `SSH forge` to say which one it is on. It adds no grant: the `remote-answer` grant is still written only over SSH, and is honoured on the tailnet connection too (ADR-0053). Sotto leans on Tailscale: it is required for phones and recommended for hosts, plain SSH stays the way into a host that always works, and Sotto runs no relay of its own (ADR-0088). Avoid: "route", which ADR-0025 and the guide use for the SSH address; "direct"; "tunnel".

**Tailnet address.** Where a desktop reaches a host's **tailnet listener**: `https://<MagicDNS name>:<Serve port>`, as the host reports it in its launch result and its hello. It is learned, never typed, and the desktop accepts only an `https:` address on a `*.ts.net` name. Kept per saved host in `remote-host-tailnet.json`, beside `remote-hosts.json` rather than in it, so an older Sotto still reads its saved hosts (ADR-0053).

**Tailnet listener.** A headless host's second loopback listener, which Tailscale Serve carries to the owner's tailnet. It has no administrative routes. It was the phone listener, and now carries a paired desktop's **tailnet connection** as well as phones: Serve runs while the host's `phoneAccess` or `tailnetConnections` setting is on. A client counts as a desktop there only once the launch script has recorded it as one over SSH, in `desktop-clients.json`; every other client is a phone. A desktop never pairs on it, and while phone access is off it refuses pairing and refuses a session to every client that is not a desktop (ADR-0050, ADR-0053). Distinct from the listener with the administrative routes, which is never served. Avoid: "phone listener" for a headless host's.

**SSH connection.** A desktop's connection to a remote host through `ssh`: a sign-in that runs the **launch script**, then a `-N -L` port forward that carries the socket, with the host's administrative token kept in memory for as long as it is open. Every host had only this before the **tailnet connection**, and it is still what Add host, pairing and the `remote-answer` grant use, what a host falls back to when the tailnet does not answer or the owner chose SSH only, and what the row names as `SSH forge`. While a host is on it, an administrative press uses it and opens nothing new (ADR-0025, ADR-0053). Avoid: "tunnel", and "route" in anything a user reads; for any other `ssh` sign-in, say "SSH session".

**Admin connection.** An SSH connection to a remote host opened for administrative presses while the host's socket is on no SSH connection (on its **tailnet connection**, or, for Forget, on no connection at all), with no socket on it, and closed 60 seconds after its last use: the Phones dialog while it is open, Stop host, Forget's revoke of this desktop (before its stop), its stop and its removal of a boot unit, Update, and Start at boot. ADR-0088 takes Update off the list for a host that updates itself when the desktop asks over its tailnet connection; such an update opens one only to copy an archive the host could not download, or for a step the host refused or never received, as after its grant was taken away or when the tailnet does not answer. Pairing again after the host refused a token, and the test connect that saving Edit connection makes, are not admin connections: each is the host's own **SSH connection**, which then moves the socket back to the tailnet. It runs the **launch script** and carries the host's administrative token, kept in memory for that connection only. A press holds it for as long as the press runs, including any request it sends through the forward, and a read nobody asked for, such as the Phones read when a host connects, goes only over one already open. Its launch finds the running host and starts none, so a press on a host that is not running fails at the connect. Because it begins with a connect, a **Tailscale approval** shows in the surface that asked for it, and SSH's question says it is for a change the user asked for; stopping the sign-in there, or with Keep host in Forget's dialog, sends nothing and changes nothing (ADR-0053). In code, what a press goes over, the SSH connection or the admin connection, is a `PressConnection`. `src/main/hosts/adminConnection.ts`, `src/main/hosts/adminConnections.ts`. Avoid: "admin session", since a session is a provider's or the signed one a host mints; "control channel".

**Forget notice.** What Settings > Hosts & phones shows after Forget removed a remote host from this computer but could not finish on the host, with **Copy command** for each line it gives and **Dismiss**. When it did not revoke this computer's pairing there, it says why (SSH could not reach the host, its host was not running, or it refused the revoke), that the host still trusts this computer until it is removed there, and the one `--revoke-client` line to run on the host (ADR-0053). When it could not take the host's **start at boot** unit away, it says the host still starts with its machine and gives the one line that removes this installation's unit (ADR-0054). It says either or both. Sotto never runs those lines. Each forgotten host has its own notice, kept in memory until dismissed. In code, `HostsState.forgotten`. Avoid: "not-revoked notice", its name before it covered the unit; "warning", "error", since Forget did what it said.

**Installation folder.** Where a remote host's release is unpacked on its machine, which a saved host names (`~/.local/share/sotto-host` by default). It holds either one flat install, with `host/index.js` in the folder itself, or **host versions** side by side under `versions/<X.Y.Z>/` with a `current` file naming the one to start; the launch script starts what `current` names and a flat install otherwise (ADR-0040). Distinct from the host's data folder (`~/.sotto`), which holds its workspace and pairings and which no update touches. Avoid: "install path" in anything a user reads.

**Host update.** This computer putting its own Sotto version on a remote host that runs an older one, when the user presses Update beside the window controls on the Threads page, at the top right on a Mac and on Linux (ADR-0040), or Update all, which takes the pill's place (ADR-0077). A host **needs an update** when the version it says it runs is earlier than this computer's or, with Update all on, earlier than the Sotto this computer is downloading once that version's host archive is published for the host's own system, so the host is updated before Sotto restarts (ADR-0077); a newer host is left alone. Four steps: download (by the host, or by this computer and copied over SSH when the host cannot reach GitHub), check against the release's checksum, install beside the running version, restart. Each step is the **launch script**'s, run over the host's SSH connection or an admin connection, except on a host's **tailnet connection** whose hello lists `host-update`: there the host runs download, install and restart on itself when this computer asks over its socket, with no SSH and no **Tailscale approval** (ADR-0088). The host offers that only to a desktop the launch script recorded, with its `remote-answer` grant, refuses any version that is not newer than its own, and says how its restart ended once this computer has connected again; after a restart sent that way this computer tries the tailnet alone for the restart's whole budget. A step the socket refused or never sent goes over SSH, and so does a download whose answer timed out, after closing its socket to end it, or copying an archive the host could not download; a restart that went over the socket is never sent again over SSH (`src/main/hosts/hostSelfUpdateRoute.ts`). A busy host asks first and can wait until none of its threads is working, and an update waits to start, and an installed one waits to restart, while the host's client update line is running, so its restart cuts no client update off (ADR-0077). A failure leaves the old version running, or starts it again, and says so. **Not now** hides it until Sotto next starts. A host Sotto did not start is not restarted; its panel offers the commands instead. `src/main/hosts/hostUpdate.ts`. Distinct from the update control, which updates Sotto on this computer, and from a client update (ADR-0042), which updates a provider's client. Avoid: "upgrade", "auto-update", "sync".

**Host version.** One Sotto release unpacked in a host's installation folder, in `versions/<X.Y.Z>/`. A host update keeps the version running and the one before it, and deletes older ones once the new version runs. Distinct from the host protocol's version, which is `v: 1` whatever Sotto version speaks it.

**Device.** A machine Add host lists as one Sotto could connect to, before it is a host. The list is read on this computer when the dialog opens: the other devices on the tailnet from `tailscale status --json` (name, operating system, whether it is online, when it was last seen, and whether Tailscale SSH is on), then the aliases in the SSH configuration and the names in known hosts. A configuration alias whose `HostName` (the alias itself when it has none) is one of a tailnet device's names or addresses is the same device, listed once with both tags, and Sotto connects through the alias so the user's user and key settings apply; a tailnet device with no alias is reached by its MagicDNS name. Devices Sotto can add are under **Can connect**; offline devices, phones, those already saved as hosts, SSH entries that go to this computer (one of its addresses or its full tailnet name, never a bare name, loopback, or an address reached through a jump host) and SSH entries for a Git service (the host SSH connects to, not the alias) are greyed under **Can't use now** with the reason. **Another SSH host…**, always last, swaps the list for typing a host. A device becomes a host only once it is added and paired. `src/main/hosts/tailscale.ts` reads and merges, `src/renderer/src/features/settings/DevicePicker.tsx` lists. Distinct from the iPhone client's **computer**, which is a host the phone is already paired with. Avoid: "peer" and "node" (Tailscale's words), "suggestion" (the SSH setup's entries are now devices).

**Askpass helper.** The small program OpenSSH runs through `SSH_ASKPASS` when it needs a password, a key passphrase or a yes to a new host key. It carries the question to the desktop over a loopback-only socket, the desktop shows it in the Add host dialog, or for a saved host over whichever page is open, and the helper hands the answer back to ssh. An answer is reused for the rest of that connection, so the user answers once per connect. A notice OpenSSH runs it for without asking anything, such as a security key's touch request, is not shown, and a question ssh stops waiting for is taken away. `src/main/hosts/sshAskpass.ts`. Avoid: "SSH prompt handler", "password dialog".

**Host setup checklist.** What Add host becomes once pressed: a line saying what is being added, with Change, and the steps a connect goes through, in order: Reached, Approved in Tailscale (only for a Tailscale approval), Signed in, Host installed, Host started, Paired. The launcher reports which step it is on (`HostStatus.step`); the desktop adds Paired, and after it, for Add host's own add, Reach forge over your tailnet, which main reports on the saved host (`HostStatus.addTailnet`) and which ends either on the **tailnet connection** or saying why the host stayed on its **SSH connection**, with Try the tailnet again; the host is saved before that step runs, so its dialog offers Close rather than Cancel while it does; the connected card offers **start at boot** (ADR-0053, ADR-0054). A failure shows on the step it belongs to, with main's sentence and, where there is one, the exact command that fixes it, which Sotto never runs. Until the host archive carries its own Node (#207), a missing or unsuitable Node counts against Host installed. While a **host setup** runs, the same checklist follows its thread's checks and add: a step that stopped the last check shows why without asking the user to act, and one that passed after an earlier check stopped there reads "by the agent". Distinct from the Phones page's setup rows and from the merge checklist.

**Tailscale approval.** Tailscale SSH in a tailnet policy's `check` mode holding a new `ssh` sign-in until the user approves it in a browser; its banner on ssh's stderr names the approval page. While it holds one, the connect waits up to five minutes on the Tailscale step, and Open approval page opens that page, only a `https://login.tailscale.com/` one, from main, on the user's press. The page's address reaches the window and the browser and never a log. An approval that never comes is `tailscale-unapproved`, which only the user can fix, so a saved host stops retrying on it after a press, or when it prefers SSH. Sotto's own retry of a host it tried on the tailnet first goes on instead, since the tailnet asks for no approval (ADR-0053, October 13 amendment). Nor does an Update on a host that updates itself over its tailnet connection (ADR-0088).

**Host setup.** Add host's **Have my agent set this up**: one device, one **host setup thread**, and the check or add that thread ran last, which the dialog's host setup checklist follows (ADR-0035). It is `starting` until the thread has its brief, `running` while it works, and ends `connected`, `stopped` or `failed`; an ended setup stays on the Hosts page until put away. One runs at a time, and not beside a **provider job**: one agent job at a time. It lives in memory: quitting ends it the way Stop setup does. `src/main/hosts/hostSetup.ts`. Distinct from the **host setup checklist**, which is the list of steps both Add it and a host setup show. Avoid: "installer", "wizard", "onboarding".

**Host setup thread.** The normal thread a host setup runs in, named "Set up forge", in the **Host setup** project at Sotto's own `host-setup` folder, sharing that folder rather than taking a worktree. Its first message is the fixed brief, which names the device, its SSH address and folders, a failed step's reason code and the install steps, and never a key. It starts in the permission mode that asks before everything, which is the provider's strictest and still lets the provider's own read-only commands run without asking. Only it gets the **host setup tools**, and only while its setup runs; afterwards it is an ordinary thread that stays until archived. It starts only on the user's press and asks the user to answer its requests. Avoid: "installer thread", "setup agent".

**Host setup tools.** `sotto_host_setup`, the loopback MCP server a host setup thread or a **provider job**'s thread gets beside `sotto_browser`, on the same transport (`ThreadToolServer`). A host setup thread gets three tools and no others: `host_status`, `host_check` (Add host's own connect as far as the host answering, pairing and saving nothing) and `host_add` (Add host's add, after the user answers "Add forge as a host?" in the thread). A provider job's thread gets two: `provider_status` and `provider_check` (the host's `refresh` for that provider, which is Check again). Each thread lists and may call only its own job's tools, and none takes a target; the device, or the host and provider, is fixed when the job starts. `src/main/hosts/hostSetupTools.ts`. Avoid: "setup API".

**Provider job.** An agent installing, updating or fixing one provider on one connected host, started from that provider's tile with **Have my agent install it** (update it, fix it) (ADR-0035, amended for #461). `install` is for a provider the host did not find, `update` for one older than its **floor**, `fix` for one installed where the host cannot find or start it. It runs as a host setup does: a normal thread on this computer named "Install Devin on forge" in the Host setup project, asking before everything, with a fixed brief that names the host, the provider, what the host reported, where the host looks and the maker's install method, and never a key. It is `starting`, then `running`, and ends `found` once the host finds the provider and can start it, `stopped` on Stop, or `failed`; while it runs the tile reads "Agent is installing it" with Show thread and Stop. It never signs in: at found, the tile offers Sign in. One agent job runs at a time, a host setup or a provider job. `src/main/hosts/hostProviderJob.ts`. Avoid: "installer", "repair wizard", "provider setup".

**Floor (a provider's).** The oldest client a provider's adapter connects, below which a host's tile says **Too old to use** and offers Have my agent update it: Grok Build 1.0.5 and Devin 3000.11.92, the versions their adapters were checked against (ADR-0042), and for Claude Code the set of flags Sotto runs it with, which has no version number. Each is written next to its adapter with its reason. Codex has none. Carried to the tile as `requiredVersion` where it is a version. Avoid: "minimum supported version" in anything a user reads; the tile says "Sotto needs 1.0.5 or later".

**Sotto request.** A request Sotto itself puts in a thread, answered on its request card like a provider's, and never sent to the provider: the coordinator merges it into the thread's requests and hands the answer back to Sotto (`SottoThreadRequests`). Its ID starts with `sotto:`. Only a client that may grant answers one (ADR-0004). There are two: the host setup thread's "Add forge as a host?" (ADR-0035), and the copy of a **prototype question** Sotto sent back (ADR-0108), whose answer goes to the thread as the user's own message. Avoid: "synthetic request", "fake request".

**Switched on, switched off (a saved host).** Whether this computer keeps a saved remote host connected. On, Sotto connects now and every time it starts, in the background, and a dropped connection reconnects on the backoff until a failure only the user can fix stops it. Off, this computer does not connect: the row and its pairing stay, and a host Sotto started keeps running, since switching off stops nothing on the host; Stop host does that, and switches the host off so the next launch does not start it again. For a host that **starts at boot**, Stop host stops its unit until the machine restarts, and switching it on starts the unit again rather than a detached host (ADR-0054). A host is saved only once Add host has connected and paired, and a host saved before the switch existed reads as on (ADR-0025). Avoid: "enabled" in anything a user reads, "disconnected" for off, since a host that is on can be disconnected for a moment.

**Turned off (a host's provider).** A provider the user disconnected through a host, by name or with Disconnect, or left out when changing the enabled set, and has not connected again. A host connects every provider that is installed and signed in on its machine when it starts, except a turned-off one, which stays off across restarts. The desktop keeps the same record for this computer's providers, and its **Connect providers**, on the Threads page or in first-run setup, likewise turns on every installed provider but a turned-off one (setup's row says "Turned off" too). Recorded as `disconnectedProviders` in the host's coordinator settings, because the enabled set alone cannot tell a provider nobody asked for from one the user turned off (ADR-0036). Distinct from a provider in error, which is not installed or not signed in and is tried again at the next start or on Check again. A provider tile says "Turned off" and offers Connect. Avoid: "switched off", which is a saved host's.

**Provider tile.** One of a connected host's providers under its row in Settings → Hosts & phones, opened with **Show providers**: the provider's mark and name, a state line with a dot, a detail line and its action, which acts on that host alone. Connected (with what it is signed in with and its version) offers Disconnect; turned off offers Connect; not signed in offers Sign in, or, for Devin, the command to run on the host; not installed, too old or can't be started offers Have my agent install it (update it, fix it), which starts a **provider job**, beside Check again, which is the host's `refresh` for that provider and tries a provider in error again. While a provider job works on it, the tile says so, with Show thread and Stop. A connected client that is behind says what is available, with Update beside Disconnect, and the chip beside Show providers opens Update all for the host (ADR-0042, September 29 amendment). `src/renderer/src/features/settings/HostProviders.tsx` (ADR-0037). Distinct from Settings → Providers, which is this computer's. Avoid: "provider card", "switched off" on a tile.

**Provider problem.** Why a provider is not connected, as a code its adapter names where it finds it: `not-installed`, `too-old`, `signed-out` or `cannot-start`. It rides on the provider's status beside the sentence in `error`, and a provider tile decides on the code, never on the sentence; an error without one reads as can't be started (ADR-0037). Avoid: "status" for this, which is the whole connection state.

**Host sign-in.** A provider's own sign-in run on a host for the paired client that asked, and finished by the user in that client's browser: a device code shown in the dialog for Codex and Grok Build, which their clients finish by themselves, or a code pasted back for Claude Code, which Sotto hands to the client and keeps nothing of. The page's address and the codes live in the host's memory for that client only, never in a log or on disk, and go when it ends or after 15 minutes. Sotto opens only the provider's own sign-in page, from main, on the user's press. `src/host/providerSignIn.ts`, the `provider-sign-in` host feature (ADR-0037). A host's OpenCode signs in to **model sources** instead, from the Add a model source dialog under that host's tiles, through the `opencode-sign-in` host feature; only its sign-ins that end at the model source (a key, a device code, a pasted code) work from another computer (#1107). Avoid: "remote login", "auth flow".

**Host for new work.** The host a new thread or a new project goes to when nothing else names one: the router's selected host. New thread and Add project set it when they add a folder as a project on the host chosen there; opening a thread or project also moves it to that thread's host. A thread's own host never changes once the thread exists. Avoid: "active host", "current host".

**Host lock.** `host-listener.lock` in a host's data folder, which keeps a second host from opening the same stores. It holds the lease of the host that owns the folder: its process, a nonce and the machine's boot identity. The next start reclaims a lock whose process has ended, or that was written before the machine last restarted, and does it atomically: starting hosts take turns to clear a stale lock through `host-listener.lock.reclaim`, so however many start together, only one owns the folder. A lock whose process still runs, even one another account owns, is refused and the refusal names that process, and the host exits with code 75, which a **start at boot** unit does not retry; every other refusal, a moment's contention while a stale lock is cleared included, exits with 1. `src/host/lock.ts` (ADR-0025, ADR-0054). Avoid: "pidfile", "lease" for the file itself.

**Start at boot.** A remote host's systemd user unit, `sotto-host.service`, which Sotto installs with the owner's consent, over the host's **SSH connection** or an **admin connection**, and which starts the host when its machine starts. Linux with a systemd user manager only; on macOS, Windows and Linux without one the launch script says it is unsupported and nothing is offered. It needs the account's linger setting, so Sotto turns linger on first with `loginctl enable-linger`, and if that is refused it changes nothing on the host and shows `sudo loginctl enable-linger <user>` for the owner to run, never sudo itself. Installing and removing it restart a host Sotto started once, after the busy-host question (**Wait until they finish**, **Stop N threads now** or **Cancel**), and removing it never starts a host that is switched off. Sotto never enables it while linger is off; a launch that finds linger turned off under an enabled unit disables the unit, starts a detached host and reports start at boot as off. Forget removes it. A host its unit started records `startedBy: "boot"` and counts as started by Sotto. Offered on Add host's connected card and from the row's More menu, **Start at boot…** and **Stop starting at boot…** (ADR-0054). Avoid: "service", which is the **host service**; "daemon"; "supervisor".

**Remote command.** A command a paired client may send over the socket. The list in `src/host/remoteCommands.ts` is closed: a new command or field is refused remotely until it is added on purpose. Commands that change what a thread may do unasked (a runtime mode other than asking first, a provider mode whose allowance is more than nothing) or discard uncommitted work need the same `remote-answer` policy record an answer does; a setting that grants nothing is free, so a paired device can always put a thread back to asking (ADR-0025). Avoid: "remote API".

**Host protocol.** What a client and a host exchange over HTTP and the socket, listed message by message in `docs/host-protocol.md`. Its version is `v: 1` on every message and is separate from the Sotto version; version 1 is frozen and grows only by optional fields, host features and push forms a client asks for (ADR-0025). Avoid: "API", "wire format" as a name for it.

**Host feature.** A named part of the host protocol beyond version 1's base, such as `detail-delta`, which a host lists in `features` in its health, its listener file and its hello reply. A client uses one only when the host lists it and asks for a push form by naming it in hello's `accepts`. A host with no feature list predates the freeze, and the desktop asks the user to install this computer's version of the host, stop it and connect again. A provider that joined Sotto after a client was built has a host feature of its own, `provider-opencode` for OpenCode: a host sends that provider's rows, models, projects and threads only to a client whose hello accepts it, since an older client refuses a whole shell naming a provider it does not know, and hides that provider's threads from every other client (#1107). Distinct from hello's `capabilities`, which is what this client may do on this host, and from a provider's capabilities in the shell. Avoid: "capability" for this.

## Retired conversations

**Personal chat (retired).** A former project-free conversation, distinct from a project-bound thread, which Sotto no longer opens, resumes or connects. Its retained Sotto records follow Keep local history and are not thread drafts (ADR-0010).

## Coordination

**Coordinator.** The host's agent control, which routes manual commands to a thread's provider and keeps drafts, follow-up queues, outbox entries and delivery evidence. It also sends explicit wake-ups from babysitting and Watcher; it no longer interprets natural-language commands or supervises threads (ADR-0068). Avoid: "reasoning agent", "thread provider".

**Pending setting.** An option chip's choice the thread's provider has not confirmed yet in the state the window draws. The chip shows it from the press, but the setting in force is still the provider's last confirmed one, and for permissions that is what decides its next tool call. So a pending permission is marked on its chip, a dashed edge in the activity colour and a small dot that holds still under reduced motion, and a caption beside the chips says what is still in force in the provider's name and the mode's own terms: "Claude Code still asks for approval until it confirms." A pending model or effort carries no mark while its answer is on the way; one the provider gave no result for is marked as a pending permission is, and described by the line that says what may still be in force. It ends when the window draws the provider's answer, not when the reply lands (#306), or when the provider refuses, which puts the chip back and says so under the composer's row with Try again. A change the provider never gave a result for stays pending, marked the same way, until the thread shows the choice or main lets it go. One that sets a permission mode holds the thread: main takes no other action on it until it knows, so the chips are fixed and the line under the row says what happened and what comes next, with nothing to press. One that sets only a model, an effort or **fast mode** holds nothing back (#1192): the thread still sends and takes another choice, which replaces it, and a turn meanwhile can run on the setting before it, which the chip shows. Avoid: "saving", "optimistic".

**Threads page.** The main-window page that lists threads across Sotto's providers, including retained threads whose provider is disconnected. A thread's messages and pending decisions stay with its original provider. Avoid: "inbox", "dashboard".

**Allowance.** What a Devin thread's owned profile lets Devin do without asking: nothing, edits, or everything. Sotto writes it and reads it back, so it is what decides whether a permission request reaches the user. It carries out the permission mode the user chose; it is not an ADR-0004 policy record and is never a grant of authority. A provider's own conversation mode is set alongside the allowance and never stands in for one: a mode named for not asking says what the provider will not ask itself about, not what Sotto will stop asking (ADR-0022). Avoid: "grant", which is ADR-0004's word; "permission level"; "mode" for the allowance.

**Needs you.** What waits on the user, gathered where they look first. On the iPhone, a thread's question or permission waiting on the user, shown first on Threads under the heading **Needs you** and counted on that tab, including requests in settled threads; it is no longer a separate page. Each card is tagged **Question** or **Permission**, and one with one-tap choices can be answered on the card (ADR-0051). On the desktop (ADR-0135, Owl first), a card of the same name under the Threads sidebar's search: one entry per thread that needs the user across every project and host — a permission, a question, or a failed turn nobody has seen — blocking requests first and then the longest wait, three standing and the rest counted. A short approval, a one-choice question and a failure can be settled there, through the same answer store and dismissal as in the thread's pane; everything else opens its thread. Settled threads' requests stand in it tagged **Settled**; **Finished unread** and **Prototype ready** never do. At none there is no card, and while the feature is off the sidebar keeps its dots and its **Dismiss all** line. On the collapsed rail (ADR-0146, Owl first) the same queue is a tray: an amber panel with the count at its head and a tile per waiting thread, absent at none; it opens threads and answers nothing. These are the thread's own pending requests. Watcher's own cards belong to the Watcher tab and its badge. A worker's own card may also appear inside Watcher; answering there still answers the worker as the user, under its existing Can answer policy. Avoid: "inbox", "notifications".

**Computer (iPhone client).** A machine the iPhone client is paired with: a desktop running Sotto or a host without a screen, one pairing each. The app shows every computer's threads together and names each thread's computer, which shares its own threads. A computer is named by the `name` in its health, which the desktop and a headless host's **tailnet listener** send, else by its machine name on the tailnet, and can be renamed on the iPhone alone. A new thread chooses its computer first, then a project already there or an existing folder to register, then that computer’s ready model and options. The thread remains manual and uses the shared project folder, or a new worktree when chosen. Folder browsing reads that computer’s directory names, not file contents; filtering narrows one directory. The word is the phone's user-facing name for a **host** reached as a whole machine; inside the code the same thing is a host ID. While the app is active, a dropped connection is tried again for about a minute, with waits from one to thirty seconds; after that, like a computer that doesn't answer its first attempt, it reads **Can’t reach it** and waits for the user's Try again or Reconnect. A new session refreshes state and reconciles unconfirmed actions without replaying them. Backgrounding stops retries, and returning connects every computer that hasn't given up (ADR-0033). The iPhone calls the desktop a host without a screen is reached from **your main computer**, since that is where its phone access is turned on (ADR-0050). Avoid: "host" or "server" in anything the iPhone shows.

**Draft.** An unsent prompt or answer, including its attachments, owned by a thread and optionally a question request. Each thread retains its own drafts across navigation and restart. The desktop retains its latest remote draft edit separately from socket delivery, so a busy or disconnected host cannot replace it with an older draft. That local recovery copy follows Keep local history: on disk while enabled, only in memory otherwise. Recovery preserves the original question binding and saves only against the host revision the edit was based on; a conflict keeps both copies. An uncertain Send remains held, never recovered as a new unsent draft. Each local copy belongs to the saved host registration, so Forget followed by Add cannot restore it. Sending ends a draft: the press starts a fresh empty revision, and what was sent is a sent message from then on. Accepting one submitted revision never clears a newer revision.

**Leftover draft.** The coordinator's own draft when the thread it was written for is no longer listed. A send from a thread's composer holds the prompt there until the provider takes it, so a send that never finished, on a thread that later went away, leaves it with nowhere to show. With no pane open, the Threads page shows it with any images: **New thread with this draft** opens a thread with its words and images in the composer, after anything already written there and never twice, and the leftover copy is cleared only once that composer is saved; **Discard draft** asks first. Skill and file references chosen for the old thread do not move, since they name its provider and working copy; their mentions stay in the words. A draft that answered a question in the old thread is called an answer on the page, and becomes an ordinary prompt in the new one. While Sotto is disconnected the page asks to reconnect instead. A draft whose thread is still listed is offered with **Open thread**. Distinct from a recovered draft after a provider retirement, which has its own notice. Avoid: "orphan draft", "lost draft"; nothing about it is lost.

**Screenshot bound.** The longest edge, 2576 pixels, that any model Sotto sends screenshots to reads: Claude 4.7 and later downscale to it, and Codex to 2048. The composer scales a screenshot past it down to it, in the same format, before it joins the draft, and so does browser feedback. Its chip says **Resized from** the size before **to** the sent size under the name. The attachment keeps its original and sent sizes, never its old pixels. Nothing is scaled up, a GIF, an animated PNG or WebP, or an image past 16384 x 16384 pixels in area is never scaled, and a copy that would not be smaller in bytes is not used (ADR-0030). Avoid: "thumbnail", "compression".

**Staged image.** An image attached to a draft, whose bytes the host that runs the thread has kept once in its attachment store, and which everything else names by its handle: an ID, the file name, the type, the size and the SHA-256 digest of the content (ADR-0031). Drafts, queued follow-ups, commands, the outbox, the shell and every broadcast carry the handle; the bytes are read only to draw a chip the window has no thumbnail for, to show a sent message's preview, and by the adapter as it hands the image to the provider. The store keeps one file per content under `attachments/` in the host's data folder, with an index of digest, type, size and staging time, and keeps it while a draft, a queued follow-up, a send whose result is unknown or a preview names it, then an hour more. With history off, a newly staged image is kept in memory only. The iPhone client stages the photos it attaches to a reply, or to a message to Watcher, the same way, made ready on the phone first and staged again before it sends one its computer may have let go (ADR-0031, October 3 amendment). Avoid: "attachment" alone for the bytes, "upload".

**Attached file.** A file attached to a draft that is not one of the four image types a **staged image** is (ADR-0131): a PDF, a log, an archive, anything. It is staged and carried by handle exactly as a staged image is, kept as `attachments/<digest>.bin` with its type in the index, and its bytes are never inspected while staging, scaled or drawn: the composer shows it as a pill under the image tiles, and a sent message as a tile with its type and size. A file is at most 25 MB, and a draft's attachments at most 8 and 50 MB in all. A remote host takes one in parts (`file-staging`). When it is sent, the adapter copies it into the thread's working folder under `.sotto/attachments/`, where it stays until the user removes it, and names it to the agent in a note apart from the user's words, which the thread never shows; a PDF also goes as part of the prompt to Claude, and to OpenCode when the model reads PDFs, unless its pages cannot be counted, number more than 100, or would take the message past 20 MB. Every model takes files, and a thread with no working folder takes none. An Owl feature, `attach-any-file`. Avoid: "document", which a PDF block sent to Claude already means; "upload".

**Sent message.** What the user sent from this window, drawn in the transcript where it will be read from the press onwards, with the state of its delivery beside it: queued, sending, unconfirmed or not sent. A message bound for the **follow-up queue** is not a sent message yet: the queue above the composer alone shows it, and it joins the transcript once the provider's history carries it. The iPhone client draws a reply, answer or stop the same way: sending while its computer has not answered or says it is still carrying it out, and unconfirmed, with Check again, only when it cannot say. It becomes an ordinary message when the provider's own history carries it. A refused one comes back to an empty composer, or is offered back when something newer is written there; an unconfirmed one stays in its message, because Sotto will not send it twice. Avoid: "optimistic message", "ghost message".

**Set aside (a sent message).** An unconfirmed direct prompt the user has chosen to move past with **Continue with a new message** on its owning desktop. Its delivery remains unknown, its identity is kept to prevent a duplicate send, and the newer draft stays ready; setting it aside sends nothing and grants nothing. Confirmation of a fresh explicit prompt in the same thread releases normal automatic updates without changing the original delivery. A set-aside message never holds Watcher's sends: Watcher can send to that thread again at once. Avoid: "failed", "delivered" or "cancelled" for this choice.

**Delivery receipt.** Main's record that one draft of a thread was accepted, by thread ID and draft ID: sent to its provider (`deliveredDrafts`) or taken into its follow-up queue (`followupReceipts`). The composer and transcript read it to stop showing that draft as unsent, and main reads it to refuse sending the same draft twice. A **wake-up** has no draft and takes none, waiting in the queue or sent. Distinct from a command receipt, which is main's answer to one command. Avoid: "receipt" alone.

**Answer draft.** Saved choices and text for a particular provider question in its original conversation, recoverable even if the provider closes or changes that question. Retaining or copying an answer does not recreate the question, confirm delivery, or grant authority to send it.

**Follow-up queue.** The ordered messages the user has prepared for a thread after its current provider turn, editable or removable until dispatch. Above the composer it sits in a tray of its own surface, with no edge, tucked under the composer card, under a line that says when it sends, each message on one line with **Steer now** and its other actions beside it (ADR-0113). A **wake-up** that has to wait joins it after them as Sotto's own item, which can be removed but not edited. It is distinct from the outbox of already-dispatched commands.

**Steering.** The user's explicit submission of new input to a provider's current running turn through a supported native mechanism. It does not imply permission to stop a command or start a replacement conversation. A Claude steer that lands while Claude thinks or writes goes as Claude Code's own send now, which drops that step and ends the turn so the steer runs as the next. That turn is **steered**, not stopped, and its header says so (ADR-0075). Watcher's sends steer by default: one that names no delivery, or names steer, steers a running turn, whether or not Sotto has confirmed it, goes now to a thread whose turn is over, and queues only where the provider cannot steer. Its result says which, and a steer that went now or queued says so (ADR-0130).

**Option chips.** The three controls in the composer footer that say what a thread is set to: the model, with its provider's mark, the reasoning effort and the permissions. Where the thread's model offers it, the **fast mode** bolt sits between the model and the effort. In a composer each is a **text button** (ADR-0113), and where the composer is narrow permissions shows its shield in place of its words; in Settings each is a filled chip (ADR-0110). Each opens its own picker above the composer, or below it where the room above is too short, as it can be with a new thread's **greeting** in the middle of the pane, so the typed text and the send disc stay where they were. The model's menu is two columns: a rail of provider marks down the left, one tile each and no names, so a provider costs the same room whatever it is called and its name is the tile's accessible name and tooltip; and on the right that provider's models under a search line, with the reminder that any provider is still a choice on a thread before its first message. Once the thread has sent, the rail keeps the other providers, each headed "Continue in a new thread on" with that provider's name, since picking one begins a **continued thread** rather than changing this one. A model is listed under the fullest name the provider gives it, version and all, and the one the provider recommends stays at the top of its list. A thread or a Settings default on a long-context variant the provider no longer lists, such as Claude Code's `opus[1m]` beside `opus`, is on that base model: it shows under the base model's name alone, with its efforts and image support, and keeps its own ID for the provider, so pressing the base model's entry again leaves it where it is. The effort chip opens the effort card: the level word and one line saying what the level costs, Default when the model reports one, and a track with a stop per level. Dragging previews and settles on a stop; release chooses, and the wheel, arrows, Home, End and the digits step. Every chip shows a choice from the press itself — for effort the word, the chip, the composer's outline and the arrival — while the save runs behind it, and no chip waits on a save or goes dead for one; a choice made while a save is in flight waits, and only the last is sent. The provider is still authoritative: the value it answers with is what remains, so a change it refuses takes the press back and says so under the chips, with Try again. A permission choice is a **pending setting** until the provider confirms it. At the model's highest level the word, the chip and the composer take the effort color, and reaching it plays the arrival once (ADR-0019). Claude prompts can add a visible `ultrathink` instruction for that prompt; this does not change the saved effort or permissions. The effort levels and permission list come from the provider: Claude Code reports its effort levels at initialize, so a level it does not report cannot be offered. A provider whose permission modes are its own rather than Sotto's four lists those instead, each with the one sentence saying what Sotto will still ask about under it. New thread opens on its defaults with no such form, and Settings → Threads' "New threads start with" row holds the same chips for those defaults. Avoid: "pill" or "Thread options" for the row.

**Fast mode.** A thread's choice to have its provider answer faster at a higher price: Claude Code's fast mode, up to 2.5x faster output at twice the price per token, or Codex's Fast service tier, which uses more of the plan. It belongs to one thread (ADR-0143). A new thread starts with it off, it stays as the user left it, and there is no default for new threads. The thread keeps the choice, not what runs: on a model without fast mode it runs at normal speed and keeps the choice, and back on a model that has it, fast mode runs again, unless Claude Code refuses it then, which turns the choice off. Whether a model has it is the provider's word, Claude Code's catalog or Codex's model list. In a composer it is a one-press bolt after the model chip, a muted outline while off and filled in the accent while on, drawn only for a Claude Code or Codex model that offers it; its tooltip says the cost once. It answers no permission, so a change waiting on the provider holds nothing back, as a model change does. Avoid: "turbo", "priority mode", "speed mode".

**Turn.** One recorded coordinator action from start to finish: a manual command or a wake-up sent by Sotto. A send's record can wait for its first output (see Send stage) and its finish wait; draft edits are not turns.

**Turn record.** One diagnostic record of a turn's source, thread and project identities, timings, outcome and fixed failure code, without prompt, answer or error text. New records have source `command` or `wake-up`; historical `utterance` and `supervision` records remain readable. Records are scrubbed at startup and kept within count and size bounds, regardless of Keep local history. Avoid: "trace", "log entry".

**Send stage.** One step of a send between Send and the reply's first output, as its turn record times it in whole milliseconds: admission (the coordinator's own work before its host: the draft and outbox writes, the wait for the thread's lane), the read before the send, the workspace's preparation (folder check, branch record, checkpoint, and starting the provider session on a first send), the adapter's own work before it writes the prompt, the provider's acknowledgement, and the first output (the reply's first text, thinking or tool activity reaching the coordinator). Only a turn whose prompt the coordinator handed to its host carries them; a send refused before then, after its read or by its checks, carries none, and one the workspace or the adapter refuses after that carries the steps it took. A step the send did not take, or that nobody timed, is null: Devin marks neither the prompt written nor its acknowledgement, so its first output counts from the workspace and is timed only when it beats the command's return; a queued follow-up's admission starts when the queue takes it. A send whose provider acknowledged it is held in memory and written once the first output arrives, the reply ends without one, the thread is sent to again, Sotto stops, or two minutes pass, whichever is first; a crash or forced quit before then loses that record. The command does not wait for it, and its finish time and total are still when the command finished. Avoid: "phase", "span".

**Finish wait.** How long a provider took from its turn's last output to saying the turn finished, kept with how long it took from starting the turn to its first output, as the adapter that times its turns adds them to the send's turn record (`turnFinishWaitMs`, `turnFirstOutputMs`). Only Muse's adapter does (#1420). The record waits for them after the first output, at most thirty minutes, and no longer once the thread shows the turn ended, the thread is sent to again or Sotto stops. Numbers only, from when Sotto's client saw each thing arrive. Avoid: "tail", and "latency" on its own.

**Thread lane.** The order the coordinator runs one thread's own commands in. A command that names a thread and acts only on that thread — a prompt, a steer, an answer, thread options, compaction, settling and restoring, working-copy actions — runs in that thread's lane, so it waits only for earlier work on the same thread. Commands with no thread, and those that move the composer draft or a whole project, keep the single global lane, which is what the published `globalLaneBusy` mark stands for; the threads whose own lanes are running are published beside it as `busyThreadIds`. Every surface that shows one thread reads that thread's mark, so work on one thread never dims or locks another's pane; the provider and configuration surfaces read the global one. The window keeps the same split: it sends a thread's lane commands, and Stop, to main at once, and holds only global-lane commands behind the reply to the one before, so it never makes one thread wait on another before main has heard of it. Both read one list, `THREAD_SCOPED_COMMAND_TYPES` in `src/shared/threadLanes.ts`; beside it, `LANELESS_THREAD_COMMAND_TYPES` names Stop and the other thread commands main answers before it chooses any lane, which the window sends at once as well. The workspace host keeps an order of its own for each thread's folder: a send, a Git action, Git's inspection of the folder and a local **Git status** read run there one at a time, and only a status read's fetch and pull request lookup run outside it (#766). Avoid: "queue" for a lane, "busy" on its own for either mark.

**Outbox.** Durable intent for a dispatched command whose acknowledgement may be lost. Sotto reconciles outbox items against the next status rather than resending. A send is reconciled by the provider's echo of its message; when the echo has not reached the coordinator by the time the provider accepts, the coordinator asks the workspace for what it holds, where the echo usually waits to be published, and reads the thread whole only when it is not there (#765). A thread settings change is reconciled by the snapshot its adapter hands back when the provider confirms it; its entry leaves the disk with the next write. A prompt's outbox entry is written in the one write of `agents.json` before its provider hears it. A prompt that goes at once is first saved by that write. One that has to wait behind other work on its thread is saved as soon as main takes it (ADR-0058).

**Origin.** An adapter's durable record that Sotto sent one prompt to a thread: the Sotto message and command IDs, a digest of what was sent and when, never the text. It is on disk before the prompt is written to the provider, so the provider's echo is matched to Sotto's message, and a prompt the provider took is never left looking unsent (ADR-0005). Codex, Grok and Devin keep origins in their thread stores (`codex-threads.json` and the like); Claude Code appends each new one as a line of its **origin journal**, `claude-origins.jsonl`, until it next writes `claude-threads.json` whole. Each whole write moves the journal's generation on, and a line from an older generation than the store's is never folded back, so an origin the store dropped stays dropped. Avoid: "receipt" for an origin, which is the record of sending, not of acceptance.

## Dictation

**Voice coordinator (retired).** The removed wake listening, reply voices, Agents room, orb and per-thread Manage controls. Dictation remains independent; [ADR-0068](docs/adr/0068-remove-voice-control-and-thread-management.md) records the removal and upgrade boundary.

**Transcription.** Turning dictated audio into text. Since ADR-0071 it happens on this computer: each segment is encoded as a 16 kHz mono PCM16 WAV, sent from the renderer to main, decoded back to samples and handed to the **speech model**. Audio never leaves the computer and there is no hosted route; a segment that could not be transcribed is reported with its reason. Avoid: "upload", "transcription server", "remote ASR".

**Speech model.** The model that transcribes dictation on this computer, the one the user chose (`speechModel`, ADR-0094). Nothing downloads until the user picks one; an install that already had Parakeet v3 keeps it chosen. Sotto's own downloads, on every platform and in this order, are Moondream's Parakeet Ultra (v3 post-trained, which Sotto converted to its format itself), NVIDIA's Parakeet TDT 0.6B v3 and NVIDIA's Parakeet TDT 0.6B v2, each 8-bit and run through sherpa-onnx (ADR-0071): picking one downloads its four files once, about 670 MB from Sotto's releases on GitHub, into its own folder, checks each against a pinned size and SHA-256 and resumes a stopped download. On an Apple silicon Mac the user can instead pick a Core ML Parakeet model already on this computer, in FluidAudio's folder (`~/Library/Application Support/FluidAudio/Models`), put there by another app such as Willow Voice: Parakeet Ultra (Core ML), Parakeet v3 (Core ML) or Parakeet v2 (Core ML). A Mac is not offered Sotto's download of a model FluidAudio already keeps there, unless Sotto's copy is already downloaded or is the choice. Sotto only reads that folder and runs the model through its bundled helper, `sotto-coreml-asr`. The chosen model stays loaded while Sotto runs. Its status is missing (no model chosen yet), downloading (with bytes so far), loading, ready, or failed (network, checksum, disk, engine, or gone: its files are no longer on this computer). Until it is ready, dictation says so and records nothing. Setup's speech model step offers the models already on this computer first, then Sotto's downloads, and suggests the first of them, so Parakeet Ultra where nothing is here yet; a suggestion chooses nothing; Settings → Dictation's **Speech model** picker switches between them and shows the status with Try again. Parakeet v3 and Ultra understand 25 European languages and detect which one is spoken; v2 is English only. Avoid: "preset", "local model" in user-facing text, "ASR", "imported model" (Sotto never copies another app's model).

**Transcription failure.** Why a segment came back without text, and what the user is told: the speech model was not ready (Model not ready), it could not transcribe the segment or took past the deadline (Couldn't transcribe), or the audio was not a WAV the recorder makes. The recording becomes a kept recording, so each sentence says it is kept until the user tries again or discards it. Starting a dictation before the speech model is ready is not a transcription failure: nothing is recorded, and the sentence points at the speech model in Settings → Dictation. Main appends each failure except a user's cancel to `transcription-diagnostics.jsonl` beside `polish-diagnostics.jsonl`: when it started, the reason, the segment's length and the time taken. Never words or audio. Avoid: "error log", "crash report".

**Kept recording.** A dictation whose transcription failed, kept in memory so it can be sent again. A long dictation is transcribed in parts, a segment at each pause and the tail at stop; the parts that came back keep their text and let go of their audio, and only the others are kept. The widget pill reads **Click to try again** and the Dictate room offers **Try again**, which sends only the parts without text and then finishes the dictation as usual. A Try again that fails too keeps it again, and the pill says so (**Failed again · retry**); one cancelled while it runs returns to the kept recording. The widget's ×, **Discard recording** or `Escape` in Sotto's window, or starting a new dictation lets it go, and closing Sotto loses it. It is never written to disk (ADR-0055). Not a **held thread** or a **held action**, which are about threads. Avoid: "saved recording", "draft", "queued audio".

**Dictation record.** The numbers Sotto keeps for each finished dictation, on this computer only, in `dictation-records.jsonl` beside `history.json`: when it finished, how long the user talked, how many words came out, and its **delivered app**. No text and no audio. It is kept whether **Keep local history** is on or off, retention never trims it, and it shares its id with the dictation's transcript, so deleting the transcript deletes it and Clear history deletes every one. The first start without records fills them from the transcripts already saved (ADR-0100). Not **Usage history**, which counts thread work, and not a **turn record**. Avoid: "analytics", "telemetry", "dictation log".

**Delivered app.** The name of the app that had focus when Sotto pasted or copied a dictation, as the system names it: the foreground process's file description on Windows, the front application's name on macOS, the active window's class on Linux. Only the name, never a window title or anything read from the app, and read without a new permission. A dictation whose app could not be read has none. Main reads it; the window never supplies one (ADR-0100). Avoid: "target app", "active window", "window title".

**OpenRouter key.** The one API key the user supplies, stored encrypted in the operating system credential store under the `formatting` slot and never returned to the renderer. Since ADR-0071 it pays only for the optional cleanup pass; it sits under the AI formatting switch in Settings → Cleanup, with Verify key. In settings code it is still the `llmApiKey` field.

**Personal dictionary.** The user's list of names and terms, one per line (`llmDictionary`), up to 4,000 characters. Its draft saves when the field loses focus or Settings is left. It is quoted in the cleanup prompt, so AI cleanup spells those words as written; the speech model does not take it (ADR-0071), so with cleanup off names come out as they sound. Avoid: "vocabulary hints" in user-facing text.

**Cleanup pass.** The optional LLM pass over the finished transcript (punctuation, fillers, self-corrections, lists), run through OpenRouter chat completions and skipped for very short transcripts. Sotto picks the model, not the user: one model cleans up, and a faster backup takes over when it fails or runs long (ADR-0069). On Owl the user may choose the **cleanup model** from OpenRouter's list and a **cleanup mode** (Default, Nitro for the fastest host, Floor for the cheapest); the backup stays (ADR-0122). Also on Owl, the cleanup model may be a model on **your own model server** added without a key, which main asks directly with the setting **Measure** found fastest, and Mercury 2 still takes over (ADR-0136). Audio never goes through it. Avoid: "polish" in user-facing text (the code still says `polish`).

**Measure (a server for cleanup).** Sotto cleaning up a built-in sample transcript on the user's own model server with each thinking setting in turn (left to the model, thinking off, least effort), twice each, and keeping the fastest that cleaned up the whole sample, per server and model, in `own-server-cleanup.json` (ADR-0136). It runs only when the user chooses one of the server's models as the cleanup model or presses **Measure again**, never in the background, and never sends the user's own words. A cleanup then gives the server three times the measured time before Mercury 2 takes over. Avoid: "benchmark" and "tune" in user-facing text, since the result is one setting, not a score.

**Segment.** One slice of a dictation, cut at a pause or at most every 15 seconds, transcribed as its own request so the final text is ready almost as soon as the user stops and the speech model rarely takes one long recording. When a segment cannot be sent, the rest of the recording goes as one request, up to Sotto's five-minute limit (ADR-0071, ADR-0094). The tail left at stop is not sent when it is shorter than six seconds and never rises above the level that counts as a pause, since the speech model makes a filler word of silence; a recording that is only such a tail reads as no speech. Avoid: "chunk".

**Compositor binding.** A key the desktop’s compositor, rather than Sotto, listens for and that runs Sotto’s dictation command. On Linux, Hyprland runs `sotto dictation start|stop|toggle|cancel`. Sotto writes its own into its snippet, `~/.config/hypr/sotto-bindings.lua`, once the **Omarchy setup** has set up its keys, and rewrites them when a shortcut changes in Settings › Dictation: a **press shortcut** binds `toggle`, a **hold shortcut** binds `start` on key-down and `stop` on key-up (ADR-0097). The defaults are F9 held to talk and Super+Ctrl+X pressed to toggle, the keys Omarchy’s own dictation had, and they replace Voxtype’s bindings. Windows and macOS use Sotto’s own **press shortcuts** and **hold shortcuts** instead. On Linux, Escape cancels inside Sotto’s window; a compositor binding may also run `cancel` from another app.

**Hold shortcut.** A dictation shortcut that talks while its keys are down: dictation starts when they go down and finishes when any of them goes up. Pressing another key while a hold of modifiers alone is down cancels it. Its row is behind the **Owl feature** `dictation-hold-shortcuts`, sent to stable (ADR-0097). New installs hold Fn on macOS and Ctrl+Win on Windows; Linux holds F9, as it always has, and stable 0.1.39 and earlier keep that **compositor binding** without showing its row; on Linux a hold shortcut is one F key on its own. Up to four, in Settings › Dictation's "Hold to dictate" row. On Windows and macOS it needs the **key listener**; on Linux it is a compositor binding. Avoid: "push-to-talk" in user-facing text.

**Key listener.** The small native helper main runs to see held keys and Fn, which Electron's global shortcut cannot: a listen-only event tap in a bundled Swift binary on macOS, a C# low-level keyboard hook compiled by PowerShell on Windows (ADR-0097). It reports only modifier keys and the keys of the configured shortcuts, other keys pressed under a modifier as an anonymous other key, and every key only while Settings records new keys. It keeps, logs and sends nothing. It runs only while a hold shortcut, an Fn or modifier-only shortcut or a recording needs it, and never on Linux. On macOS it needs Input Monitoring, not Accessibility.

**Press shortcut.** A dictation shortcut pressed once to start dictation and again to finish it. The main press shortcut is the dictation hotkey (`hotkey`), registered through Electron's global shortcut; it always has a key besides Fn and modifiers, so it works without the **key listener**, and the press row is never empty. Up to three more may be added, which may use Fn or modifiers alone. Recorded in Settings › Dictation's "Press to start and stop" row by pressing the keys. On Linux each is a **compositor binding** Sotto writes, Super+Ctrl+X by default, with a key besides modifiers.

**Thread shortcut.** A keyboard shortcut for working in threads — New thread, Settle, Changes and the rest — read from the window's keys while Sotto holds them, never registered with the system (ADR-0133). The user's choices live on Settings › Keyboard (`threadShortcuts`), recorded by pressing the keys as dictation's are; a row left alone follows its default, and the chords this glossary names for **Changes**, the **Terminal drawer** and the rest are those defaults. Every thread shortcut stands down for the dictation hotkey, in terminals and while a dialog is open, and each presses the same button it stands for. Avoid: "hotkey" for one of these, which is dictation's; "keybinding".

**Shell pill.** The dictation widget drawn by Omarchy’s `sotto.dictation` shell plugin: a bar indicator between dictations and a pill while dictating, with Stop, Cancel, Try again and Discard. On Linux it replaces the Electron widget while its installed folder exists and Sotto has started the dictation socket and published a live state file. Main publishes status, fixed copy, whether a failed recording is kept and the saved edge in a private runtime file; never the transcript or audio. The pill starts centred under the bar, snaps to a centred screen edge on release and remembers that edge through `sotto dictation place`. It appears on the focused display when dictation starts and stays there until it ends (#850). While it stands in, Settings' **Show floating widget when idle** says so and cannot be changed.

Pressing Stop, releasing F9 or pressing the dictation shortcut again while the microphone is connecting cancels the session as soon as the microphone is ready. No audio is kept or transcribed.

## Memory

**Memory.** One remembered fact about the user, a project or the world, with the metadata the spec requires: type, scope, content, source class (explicit, observed, inferred, imported, agent-confirmed), confidence, evidence count, importance, temporal fields (created, last confirmed, last used, valid from, valid to), provenance, tags, state (active, superseded, disputed, temporary, archived) and authority (preference, policy, permission). Avoid: "fact", "note", "record".

**Memory store.** The SQLite database `memory.sqlite` in the user data folder, the single source of truth for accepted memories. It is opened by Node's built-in `node:sqlite` in the packaged Electron runtime, without another production dependency, and it carries a full-text index for lexical retrieval. Search honours a memory's validity window and includes temporary memories that are current. See ADR-0003.

**Provenance.** Where a memory came from: a Sotto thread and reference, or a dated questionnaire answer or inspector correction. Questionnaire and inspector provenance do not invent a thread; provenance never carries a provider session ID.

**Working preferences.** The user's explicit answers about communication, autonomy, verification, Git and review, agent choices, workflow and privacy, kept behind the memory gate. They are remembered context, never permission grants or changes to history settings.

**Retrieved preferences.** Current explicit memories selected for a question by thread, project and global scope. They belong to the gated memory feature; manual thread turns do not retrieve them automatically. Retrieved preferences provide context, never authority.

**Memory inspector.** The Memory page where the user sees remembered content, its provenance and history, and can correct, supersede or delete it. Corrections retain earlier versions; deleting a memory removes its full chain of versions.

**Memory (hidden).** The Memory page, its link and working-preferences questionnaire are hidden for the beta behind the memory gate, off by default (ADR-0013). The store and its permissions remain; turning the gate on restores the page and questionnaire. Manual thread turns do not retrieve memories automatically.

**Memory store probe.** The check that proves the shipped build can use the store: the packaged executable is launched in an isolated profile and its debugger invokes the bundled probe, which opens the real memory store in a temporary user-data folder, migrates, inserts, answers a full-text query and returns its evidence. The unused environment probe launch mode has been removed. The packaged-resource verifier fails the build without it. A direct Node-only probe (`scripts/probe-memory-store.mjs`) exists for the Mac runtime check.

## Authority

**Policy record.** One row in the `policies` table of the memory store that carries authority: an action (`spend`, `publish`, `destroy`, `relax-verification`), a resource (`*` or a specific path, repository or provider), a scope (`global` or a project id), an effect (`allow` or `always-confirm`), a source (`user` or `questionnaire`), a note, and granted, expiry and revocation times. Policy records carry standing authority; the user's explicit answer can authorize one action without creating a policy record; a memory whose authority field says `permission` is evidence, never a grant. An `always-confirm` record beats any `allow`; expired or revoked records never allow. See ADR-0004. Avoid: "permission memory", "rule".

**Risky action.** A permission approval classified from the request text as spending, publishing, destroying or relaxing verification. Dispatch checks every matching policy class before the provider sees the user's answer; the user's explicit Allow confirms one action without changing policy. Avoid: "dangerous command", "privileged op".

**Risk boundary.** An action the user says Sotto must always confirm, captured by the questionnaire and stored as `always-confirm` policy records with source `questionnaire`, never as inferred memory.

**Approval surface.** The place a provider client sends the requests only a person can answer. Sotto claims it at launch, per thread, in every runtime mode, and a client that does not grant it answers those requests itself: Claude Code denies them and withholds its question tool, so a thread keeps working while nothing reaches the user. Because that looks exactly like a model choosing not to ask, an adapter that finds the surface missing, or that receives a request for the user it cannot read, says so on the provider instead of staying quiet. See ADR-0043. Avoid: "permission channel", "prompt host".

## Memory evaluation

**SottoMemEval.** The product-specific memory benchmark in `scripts/memeval/`: labelled memory cases run against a pluggable backend, scored per category (recall, abstention, temporal adaptation, temporary exception, project leak, authority leak), printed as a table and saved with the backend name and case-set version. Run it with `npm run memeval`.

**Case.** One labelled scenario in a case set: a short history of provider events, a question asked as of a date and a project, and the expected outcome (an answer pattern, an abstention, or a forbidden leak pattern). Cases carry a `draft` or `reviewed` status until the founder has checked them. Avoid: "sample", "example".

**Case set.** A versioned file of cases (`scripts/memeval/cases/v1.json`). Results always name the case-set version they were scored against.

**Backend.** The memory system under test in SottoMemEval: it observes history events and answers questions, and never sees ground-truth labels. The `none` backend remembers nothing and always abstains; it is the required baseline. This is the one place "backend" is the right word; a provider adapter is never a backend.

## Main window

**Crossing.** The main window's shell since redesign round 3: one room under a thin strip, set in Figtree. It is dark by default and can be light; see Appearance and Theme. The floating widget keeps its own look.

**Appearance.** The main window's mode setting: System, Light or Dark. Dark is the default for new and upgraded installs (ADR-0009), except a fresh Omarchy install with a valid rendered palette starts on System (ADR-0070). System follows the operating system's scheme live; on Linux a chosen Omarchy theme follows Omarchy's rendered mode. The `theme` setting is the floating widget's mode, not a Theme. Avoid: "theme" for the mode.

**Interface language.** The language Sotto's own words are written in: every page, the floating widget, the tray, the application menu and Sotto's dialogs (ADR-0123). One setting holds it, `interfaceLanguage`: **Same as this computer** (`system`, the default), which follows the computer's language when it is one of the thirty Sotto has and English otherwise, or one language chosen in Settings → Appearance → Language, which wins over the computer. It is not the language a thread, a reply, a file or the terminal is written in, which show as written, nor dictation's language, which the speech model hears (ADR-0071); what Sotto writes for a model stays English. A message with no translation shows in English. Arabic and Urdu keep the English layout: only text runs right to left. The words live in one catalog per area of the tree, `src/locales/<area>/<language>.po`, with English as the source and `docs/translation-glossary.md` as what a translation follows. An **Owl feature** (`interface-language`): on stable the row does not exist, Sotto is English and a saved choice is kept. Avoid: "locale" in what a user reads, "localization" for the setting, and "language" alone where dictation's could be meant.

**Theme.** A named palette of colour roles (background, text, accent, sidebar, terminal and so on) in the T3 Code file format: one of the six built-ins, all Sotto's own (Sotto, Hush, Linen, Nocturne, Tropic, Citrine), or a custom theme the user created, duplicated or imported (ADR-0011, ADR-0024). Linux also offers the Omarchy theme (ADR-0070). A theme has a light variant, a dark variant or both. The iPhone client offers the six built-ins, generated from these definitions and chosen on the phone alone (ADR-0051). The selected palettes also colour the Sotto mark and the floating widget, except that on the default theme the mark is the app icon itself. The widget still resolves its own mode from the system, including the rendered Omarchy mode on Linux. Avoid: "accent" for the palette; the accent chooser is gone.

**Light half, dark half.** The two theme selections, `lightTheme` and `darkTheme`: the theme that paints the window when it resolves to Light, and the one for Dark. They are chosen independently, in the Light and Dark columns of Settings → Appearance, and both start on Sotto, except a fresh Omarchy install with a valid rendered palette starts on Omarchy (ADR-0070). The column for the mode the window is in says it is painting the window now.

**Omarchy theme.** The Linux theme choice that follows Omarchy’s current room, text and accent live, in Sotto’s shaped surfaces (ADR-0070). It appears in both Appearance columns, names the current desktop theme, and waits on Sotto in a half the current theme does not carry. It is read-only; Create theme can copy it. Main reads the rendered `sotto.json` and paints both windows through the existing theme path. Avoid: “custom theme” for this choice.

**Readability check.** The load-time guard for the Omarchy theme. It mixes a text role toward the theme’s text by the smallest whole percent that reaches 4.5:1 on its surfaces; focus reaches 3:1. Sotto’s own red and amber stand in when Omarchy’s status colours lose their meaning or need more than a 35% mix. An impossible palette is refused and Sotto stays readable.

**Ink.** Sotto's own dark half: an almost-black room for the thread beside a lighter graphite sidebar, with the app icon's teal as the accent. Not a separate theme; it is the dark variant of the Sotto theme.

**Sotto mark.** The owl: a black owl's head on a rounded teal tile, its eyes and beak cut through to the tile (ADR-0064). `build/icon.svg` is its one master, and every icon Sotto ships is rendered from it; inside the app `SottoMark` draws the same owl in the theme's colours, and while Sotto runs on macOS the Dock icon wears them too, from the saved theme in the half the main window shows. The macOS menu bar, and the Omarchy shell's bar and dictation pill, show the owl simplified for 16 pixels, without its tile; on a Mac the menu bar shows the **menu bar owl** instead; stable 0.1.39 and earlier keep the one-tint template. The wordmark beside it is "Sotto". Avoid: "logo" for the in-app mark, "glyph" for the whole mark (the glyph is the owl, the tile is the tile).

**Menu bar owl.** The macOS menu bar icon: a crescent moon with the owl's lit eyes in its dark side and a star that twinkles every 5 to 10 seconds; the eyes glance around and blink (ADR-0114, ADR-0137). Its frames are drawn ahead of time at 1x (`npm run tray:owl`), kept in the repository and shown pixel-doubled; the app only swaps them, and it sits still with reduced motion. An Owl feature (`menu-bar-owl`), sent to stable; stable 0.1.39 and earlier keep the one-tint template. Avoid: "tray icon animation", "mascot".

**Owl body.** The menu bar owl's moon colour: Slate (the default), Ink or Light, chosen on Settings → Appearance on a Mac.

**Owl eyes.** The menu bar owl's eye colour: Sotto teal (the default), Ice blue or Amber, chosen beside Owl body.

**App icon brand.** How the Sotto mark looks on the default theme: the icon's own teal tile (`#47b8a9`) and black glyph in both halves, whatever the half's accent. Both windows mark the root `data-brand="app-icon"` when the default theme paints it; on any other theme the mark takes that theme's accent (ADR-0024).

**Contrast.** The appearance slider (50-200%) that strengthens or softens text and borders against the theme's own background. It is the only appearance slider: the window and every surface in it are solid, and nothing lets the desktop or the room show through (ADR-0084). In the code, "glass" still names the surfaces that float over the room (dialogs, menus, toasts, side sheets and the composer), painted in the theme's overlay and field colours. Avoid: "Glass opacity", "Frosted window" and "See-through", the retired settings.

**Card.** A container the main window paints as a fill one step off the room, with no outline (ADR-0110): the theme's raised surface by night, the room with a little of the text mixed in by day. Rows on a card are divided by a line in the room's colour, and the fields, samples and segmented tracks on it take the room's colour too; a selected card or item wears the accent mixed into the card. Each group of Settings rows, each provider and its detail, Usage's index and its chart, the composer and each worker role are cards. A **thread card**, a **receipt card** and a request card are named things of their own, whatever they are drawn as. Avoid: "box" for a card.

**Text button.** A control that is its words, or its value and a small chevron, with no edge and no fill at rest: the hover wash shows while it is pointed at or open, and the focus ring from the keyboard, and it keeps a full-size hit area (ADR-0113). The composer's option chips, Steer now, New Watcher, the branch toolbar and a queued message's Steer now are text buttons. Distinct from a ghost icon button, which is an icon alone. Avoid: "link" for a text button, since it opens nothing outside the window.

**Effort color.** The colourway a thread's effort control turns at a model's highest level: one of Ember, Cyberpunk, Rainbow, Aurora, Plasma or Theme accent, chosen on Settings → Appearance and painted on the window root as `data-effort-color` (ADR-0019). It colours the card's fill and tinted word, the effort chip, and the composer's arrival; the composer wears no outline (ADR-0110). Ember and Theme accent come from theme roles; the other four are fixed palettes no theme carries, the one place the main window's colour does not come from the theme. Avoid: "effort theme"; a theme is a palette of roles, and this is one choice across all of them.

**Highest level.** The last effort level in Sotto's order, whatever it is called (Max on Claude Code, Ultra on GPT-6 Astra). Sotto lists a model's levels least to most thorough; Codex and Claude Code report them that way, and Grok's own list, which runs highest first, is turned round (ADR-0044). A model that reports one level has no highest level. The effort chip wears the effort color while a thread sits there, and the arrival is what plays on reaching it from below: a tide of the colourway through the card and the composer, the letters of the level taking the colour in turn while the word lifts and settles as one, the card's border tinting and fading. The composer itself wears no outline (ADR-0110). Reduced motion shows the settled state. Avoid: "max" or "gold" for the state; the name belongs to the level, and the colour is the user's.

**Theme editor.** The floating panel that creates or edits a custom theme and paints it live over the saved look until Save or Cancel. Pick app color (the inspector) chooses a colour role by pointing at the page; a role's label spotlights everywhere it is used.

**Strip.** The top bar of the main window on the pages that still wear one, Memory (behind its beta gate), first-run setup and the starting screen: the Sotto mark on the left (on macOS, no mark beside the traffic lights), the switch in the centre, the window controls on the right. It is the window's drag region. Every other page has the sidebar top row instead, except Watcher's room, which has no sidebar and whose header is the drag region. The Threads page owns the whole window, with the sidebar's top row and the pane header as its drag regions and the window controls once at the top right. Dictate, Usage and Help seat the Threads sidebar beside the room, with a thin drag strip above the room carrying the window controls. Settings gives its own left column the sidebar top row and the sidebar foot, at the width the Threads sidebar has, and carries the window controls at the top right the way Threads does.

On Linux the title areas stay, with no minimise, maximise or close buttons and no space reserved for them. On Omarchy, Super+W asks Sotto to close; it hides to the tray and keeps running. Windows keeps its buttons, and macOS keeps its native traffic lights.

**Sidebar width.** The remembered space the user gives the Threads sidebar, shared with the same sidebar beside Dictate, Usage and Help. Until the user drags its edge it is 30% of the window, from 260 to 280 pixels, and follows the window; a width the user dragged stays theirs, and double-clicking the edge forgets it (ADR-0110). Collapsing it leaves a narrow rail for threads and page links, a tile per open thread with its status ring; expanding it restores the chosen width. On Owl (ADR-0146) the rail also carries Watcher's tile under Expand, the **Needs you** tray, then the moving threads, then the resting ones smaller, each tile showing two letters of its title. Settings takes the same width for its own column, whichever of these it is, so going there and back moves nothing in the sidebar's frame; a collapsed sidebar leaves it the width the sidebar expands to, since a rail cannot hold the sections.

**Sidebar top row.** The first row of the Threads sidebar, and of the Settings column: the Sotto mark with the wordmark "Sotto" beside it, then, in the Threads sidebar only, Add project and New thread. The Threads sidebar ends it with Collapse sidebar. It is a drag region. On macOS it is inset for the traffic lights and shows no mark beside them, in either track; the collapsed rail likewise carries no mark at its top there. A Sotto Owl build shows the mark alone at 24 pixels in place of both, here and in the strip, named "Sotto Owl" for assistive technology. In the Threads sidebar an Owl build also paints its night sky behind the row and the search field.

**Night sky.** Sotto Owl's decoration behind the Threads sidebar's top row and search field: a faint band in the theme's own night hue, or Sotto's blue where a theme has none, with the accent glowing behind the tile (no tile and no glow on macOS) and eleven tiny stars, four of which slowly dim and come back on their own slow cycles by night, three by day. With reduced motion, from the system or from Sotto's setting, nothing moves. By day the stars take the accent and the band is a faint wash of it, never darker than the sidebar. It lies under every control and catches no press; the search field takes the night too. Stable has none, and the collapsed rail and the Settings column have none. Avoid: "banner", "header image", "Owl theme" (a theme is something else).

**First-run setup.** What a new install opens on until it is finished: nine steps (ten on Linux) in four groups (Start, Dictation, Agents, Elsewhere) on a card under the strip, from the welcome through Omarchy setup on Linux, the look, the microphone, choosing a speech model and the shortcut to the coding agents, a first project, other computers and the iPhone beta (ADR-0063). Each step uses the surface that owns it, and every step after the welcome can be skipped: its button reads Continue once the step's task is done and Skip for now until then. Finishing sets `onboardingComplete` and opens Threads with the **Threads tour**; Reset settings opens it again. `src/renderer/src/features/onboarding/`. Avoid: "wizard", and "host setup", which is a different thing.

**Omarchy setup.** Sotto’s keys, owl in the bar and theme on Linux, offered together in first-run setup and Settings → Dictation. A piece set up by hand counts as done and stays the user’s; Remove acts on pieces Sotto set up. Showing its step or Settings block, or returning focus to Sotto, rechecks outside changes without clearing the rows or inspecting files during an operation. Avoid: "installer", which installs the package, and "host setup", which runs an agent on another computer.

**Threads tour.** Four notes on the real Threads page right after first-run setup finishes: the sidebar, New thread, the thread area and Settings, each lit in turn with the rest of the window dimmed. It runs once, in that session, and Escape or Skip tour ends it. `ThreadsTour.tsx`. Avoid: "onboarding tour", "walkthrough".

**Starting screen.** What the window shows at launch, once first-run setup is finished, until every provider on this computer and every saved host Sotto is connecting has settled (ADR-0086): under the strip, only the Sotto mark, one line saying what Sotto is doing now ("Connecting Codex"), and a dot and name for each provider and host. Settled means connected, or an answer that it will not connect now: an error such as not installed or signed out, turned off, or a host waiting on the user's answer. After ten seconds it names what has not answered and offers **Open Sotto without** it, or, if main has not given its first state, says Sotto has not loaded your threads and offers **Open Sotto now**. The button takes focus, unless an SSH question is open over the screen, when it waits for the question to close. What it names keeps connecting in the background. When everything has settled the app replaces it with a short fade, in one step with reduced motion. It is for launch only: once the app has opened, a reload or a reopened window goes straight to it, and a launch with nothing to connect never shows it. A reload while it still shows brings it back on the same ten seconds. `features/starting/`. Avoid: "splash screen", "loading screen".

**Sidebar foot.** The bottom of the Threads sidebar, and of the Settings column: one row of icons, the switch first, then a short upright hairline, the page links (Usage, Settings, Help, and Memory while memory is switched on) and the update control at the far end (Drake's pick on October 25, 2026, 6 of `docs/prototypes/sidebar-footer-prototype.html`). The switch's tiles there are icons only, the open room's too, each naming itself on hover; the open room and the open page are lit with a quiet tint, not the accent. It is one part drawn in both, inset from the column's edges, so it sits in the same boxes on every page that has one. There is no History link: transcripts live in the Dictate room's **Journal** (ADR-0101). Every page without a strip has one, except Watcher's room, whose header switch carries the same three things, so the way to any page is the same from any page.

**Switch.** The control that flips the room between Dictate and Threads, with Watcher's room between them, shown as the owl and named Watcher. Each room is its own tile with no tray behind them: a microphone for Dictate, the owl for Watcher, speech bubbles for Threads. The open room's tile takes the accent and widens to show its name; a closed room names itself on hover (Drake's pick on October 24, 2026, G in `docs/prototypes/room-switch-dock-prototype.html`). The sidebar foot draws every tile as an icon, the open one lit with a quiet tint instead, and every tile names itself on hover. It is a tablist; arrow keys move between the rooms, and only the lit tab is in the Tab order. Dictate is lit on the Dictate room, Watcher in Watcher's room, Threads for the Threads and Memory pages, and none on Usage, Settings and Help. It sits in the sidebar foot beside the page links, in Watcher's header switch, and in the strip on the pages that still wear one. Every place offers the same rooms from one definition, and a press hands focus to the lit tab of the page it opens. The room keeps its place in the shell tree across the layouts, so switching pages never remounts what is inside it. With dictation turned off in Settings › Dictation, Dictate leaves the switch: it reads owl | Threads, and when only Threads would remain no switch is drawn (ADR-0107). Avoid: "tabs" in prose; "Agents" for the second state.

**Room.** The single content area beside the sidebar, or under the strip where a page still wears one. The switch chooses the Dictate room, Watcher's room or the Threads page, and Threads is the page the application opens on; the page links open the others (Usage, Settings, Help, and Memory while memory is switched on) in the same area. Those links are icons in the sidebar foot, or in Watcher's floating switch; only a page under a strip lists them in a footer.

**Dictate room.** The Dictate side of the switch, and the one place transcripts live (ADR-0101): the **dictate bar**, then the **Journal**, with the **stats column** beside it. The bar is the small seven-bar wave, one sentence for the current state ("Ready when you are.", "Listening." with its timer, "Pasted into Outlook." once the dictation's record names its **delivered app**), Start dictation or Stop, and the shortcut. Errors, a **kept recording** and the text to recover keep their sentences and buttons in the bar and under it. Ctrl+K (Cmd+K on a Mac) opens the room on the Journal's search from any page. The user can turn dictation off (**Dictate with Sotto**, `dictationEnabled`); the room is then hidden, while its transcripts and records are kept (ADR-0107). Avoid: "History" for the room or its feed; there is no History page.

**Journal.** The Dictate room's feed: every saved transcript, grouped by day under that day's words and pace, a week at a time with **Show the 7 days before**, narrowed by search and by app chips (All, then the five apps that took the most words in the last 30 days). A row opens in place on its full text, facts, Copy and Delete; Escape closes it. **Clear history** is in the More menu beside the search. With **Keep local history** off a line says so, and older transcripts stay listed. Not the **checkpoint journal** or the **origin journal**, which are files.

**Stats column.** The column beside the Journal, counted from **dictation records** alone, so it keeps counting with history off: today against your **usual** (the pace over the last 90 days), speed over the last 30 days, the streak (and the longest in the last year) over a 13-week calendar, where the words went over the last 30 days, and this month's time saved against **Typing speed** (Settings, Dictation; 40 words a minute by default) and busiest hour. A record without a delivered app is left out of where and the chips. Below 900 pixels of room it becomes a row of today's and this month's figures above the feed, and the charts step aside. Avoid: "analytics", "insights", "dashboard", which is Usage's.

**Footer status.** The one-line status text supplied by whichever page is open (for example where the speech model stands in the Dictate room). Beside the sidebar it sits in a thin foot under the room; on Settings it sits in the room's bottom-right corner; under a strip it sits on the right of the footer links. The Threads page has no footer status; a thread says what it is doing in its own row and pane.

**Update control.** The small square button at the end of the sidebar foot, or at the far right of the footer under a strip, the one place the updater shows itself in the window; in Watcher's room it is the last row of the header switch's More. Idle it offers a check; when a release is found it wears a download glyph, a progress ring while the installer downloads, and a restart glyph once the installer is on disk. Its accessible name says exactly what a press does. A press that downloads or fails gets a toast; a press that installs asks first, because the restart interrupts dictation and agent work. Automatic checks run fifteen seconds after launch and every four minutes, only on the installed Windows app and on Sotto Owl on a Mac (ADR-0093), and only while the setting allows and no download is in progress or ready to install, and never install anything on quit. Linux has no in-app updater (ADR-0062), so its window shows no update control. "Check for Updates…" in the tray menu on Windows, and in the application menu of Sotto Owl on a Mac, presses the control from outside the window.

**Update all.** The card in the window's bottom-right corner that lists everything out of date as the steps one press runs, in order: Sotto's download, this computer's clients, each connected host's clients and then that host's own update, and last the restart. It pops up when something new appears and folds into a button. One press starts Sotto's download, puts every client Sotto can install into its machine's client update line, and updates each host once the clients asked of it have finished; a host with working threads waits for them. Then, once Sotto's download is ready, it asks to restart, saying whether the threads that stops carry on after (the resume note). What Sotto cannot do, a client it does not drive or a host it did not start, is listed with what to run. A press that ends with everything updated and nothing waiting puts the card away by itself a few seconds later, never while the pointer or focus is on it; one with a failure stays until dismissed. It drives the update control, the client update lines and the host updates through their own commands, and takes the place of the client update card and the host update button (ADR-0077). An Owl feature, sent to stable. Avoid: "upgrade", "sync", "auto-update".

**Frozen.** Sotto's main process, blocked for more than half of the last minute (#1233, ADR-0098). Main measures it itself: a timer that asks to run every 100 ms counts how late it ran, and a **freeze** is one stretch of 100 ms or more it could not answer. An Owl feature (`main-freeze`), sent to stable. Avoid: "hung", "not responding", which Windows says of a window.

**Main freeze notice.** The **Main is slow** button in the window's top row, left of the window controls, while main is frozen, while an activity recording runs (**Recording, 42 s**) or while a saved one waits (**Recording saved**). It opens a popover with the minute's numbers and chart, **Record a minute** and **Not now**, which hides it until main recovers and freezes again. **Tell me when main freezes** in Settings > Performance turns it off.

**Activity recording.** One minute of main's and the window's CPU profiles, saved on this computer by **Record a minute** under Sotto's data folder in `performance-recordings`, as `main.cpuprofile`, `window.cpuprofile` and `summary.json` (ADR-0098). It holds function names, places in Sotto's own scripts and timings; never anything the user dictated or typed. Only the newest five are kept. **Attach to a thread** opens a new thread whose unsent draft names it. The notice shortens it to "Recording", beside the button and nowhere else. Not a **kept recording**, which is dictation audio and never written to disk. Avoid: "trace", "dump", "diagnostics".

**Hang recording.** What Sotto saves by itself when main or the main window stops answering for a few seconds (ADR-0098, October 26 amendment): a folder named `sotto-hang-` and the time it stopped, in `performance-recordings`, holding `hang.json`. For main, its stack a few times while it stayed stopped, taken from another thread; for the window, each Sotto process's CPU and memory and main's minute. Then how long the hang lasted, once it ended. Places in Sotto's code, timings and numbers only. The newest five are kept, apart from activity recordings. Not an **activity recording**, which a person starts. Avoid: "crash dump", "watchdog report".

**Mark.** A fact a part of a surface tells the surface, worn as a `data-` attribute on the surface's element for its stylesheet to select on: the Threads page wears `data-tools="docked"` while the tools panel stands beside the panes, a pane wears `data-greeting` while its greeting shows. A mark stands in for `:has()` on the page, a workspace body or a pane. Chromium keys `:has()` invalidation by the pseudo-class, not the rule: every node inserted or text changed under an element whose style was resolved against a `:has()` subject restyles that subject with the merged right-hand sides of every `:has()` rule in the document, so a text size change in the terminal, two hundred glyph measurements, froze the window for seconds (#1441). `useMark` tells and `Marked` wears, in `src/renderer/src/components/marks.tsx`. Avoid: a `:has()` whose subject stands above the terminal.

## Subagents

**Subagent.** A child agent reported by a thread's provider. It belongs to its parent thread and has an observational identity; it is not a Sotto thread or a target for commands. **Continue as a thread** makes a new thread from it and leaves the subagent as it was.

**Continue as a thread.** The press on a finished subagent's row in the roster that makes a new Sotto thread from that agent in the same project, in the parent's own folder or a new worktree from its branch (#1028, ADR-0090). A Codex agent becomes a **fork** of its own conversation, its task carried encrypted and never read by Sotto; a Claude Code agent, or a Codex agent Codex no longer has, starts the new thread from a **thin handover**. The new thread is titled for the agent, records where it began by the parent's Sotto thread ID (its **started-from** record), and opens with Sotto's note saying so. A working agent, or one Sotto last saw working, is refused until it is seen to finish. Avoid: "promote", which suggests the agent itself becomes the thread; "resume", which would change the parent's agent.

**Fork (of a thread).** A new Sotto thread that is a provider's own copy of another conversation: one of a thread's Codex agents (Codex's durable `thread/fork`), or a thread up to one of its replies (**Fork from here**: Codex's `thread/fork` at the reply's turn, or the Claude Code session fork its rewind also uses). It is bound to the copy when it is made, as creation binds a thread to its provider session (ADR-0002). A Codex fork keeps its source's own turn IDs and reads its history from its source's rollout, so it cannot be opened once that rollout is gone; Sotto says so and keeps what it shows. A fork never rewinds files. Not a rewind, which goes back inside one thread.

**Fork from here.** The press under the newest reply of a finished turn that makes a new thread with the conversation up to that reply, titled "Fork of" the thread's title (#1028, ADR-0090). Its card opens in the transcript under the reply, and everything below is marked "Not carried". Codex and Claude Code make a **fork**; Grok Build, Devin and Muse have no fork of their own, so their new thread starts from a handover of the conversation up to the reply, which goes with its first message. A Claude Code fork starts in its thread's own folder. A working thread is refused until its turn ends. Avoid: "branch", which is Git's; "rewind", which changes the thread itself.

**Started-from record.** What a thread that began from another keeps on its own record (`startedFrom`): the source thread by its Sotto thread ID, whether it came from an agent or a reply, whether it is a **fork** or starts from a handover, and, for a handover, its counts and, once it has gone, which characters of the first message it was. Never a provider's identifier and never the handover's words.

**Subagent roster.** The thread's retained list of reported subagents, shown in Tools under Agents. It includes finished agents and follows Tools' selected or pinned thread. It also lists the thread's **delegated threads**, and theirs, mixed with its subagents by start time, newest first. Unlike a subagent, a delegated thread is a Sotto thread: its row opens it in the pane, and Tools stays pinned on the roster it was opened from. The row shows the brief and the outcome, never the delegated thread's reply. With Work across machines on, a roster whose thread, or one of its delegated threads, runs on another machine groups its delegated threads under a heading per machine with a count (#1310). While that machine is not connected each row keeps the outcome Sotto last read there, greyed and said as such ("Working when last read"), never Unknown for what was known, until the machine connects again and is read afresh.

**Workflow page.** One Claude Code workflow's run and its agents, opened in place of the subagent roster by pressing the workflow's row. The roster shows a workflow as one row with a strip and a count of its agents; the page lists each agent as a row of its own. **All agents**, or Escape, returns to the roster. Like the roster it only observes: nothing on it acts on an agent.

**Subagent transcript.** The file Claude Code writes for a subagent it runs as its own session, beside the parent thread's transcript. Sotto reads only the model named on its first reply, for a roster row the stream left without one; the task and replies in it are never kept. Not the thread's own transcript, which Sotto reads for messages and activity.

**Subagent assignment.** One task given to a subagent, with the result it reported. A reused subagent keeps its identity and earlier tasks; a subagent assignment is an observation and grants Sotto no authority.

**Last seen working.** A subagent whose last known work has not been confirmed after a disconnect or restart. It is evidence of earlier activity, not a claim that the agent is running now.

**Alert.** A local notification Sotto shows when a thread needs the user or finishes, never for the thread on screen. It carries the thread's title and one plain line saying what happened and on which computer, and answers nothing. Settings lists alerts under the system's own heading, **Notifications**. On the iPhone, an alert can also say a thread stopped with an error; each kind has its own switch, off until the user turns one on, and alerts arrive only while Sotto is open; nothing goes through a push service (ADR-0051). Watcher uses these same switches for its requests and errors, never for its own finished turns. On the desktop, on a Mac only, there are two switches, **When a thread needs you** and **When a thread has finished everything**, both on by default, and no error alert yet (ADR-0117). A finish alerts only when the thread is **wrapped up**. A delegated thread and Watcher's own thread never alert as finished, and nor does a **watched thread**, because Watcher keeps it going and brings the user its questions and permissions, so its finish is not the last word; its questions and permissions still alert, and a delegated thread's question alerts under its top-level thread's title. Pressing a desktop alert opens the thread. Avoid: "push", "notification" for the Needs you section. Desktop copy uses macOS's own word, notification, for what macOS shows.

**Wrapped up.** A thread whose finish is the whole job's (ADR-0117): it is **Finished unread**, and nothing is babysat, no delegated thread is working or waiting on the user, no monitoring task or background work runs (a sub-agent that is working, or **last seen working** after a restart, holds it back as background work does), no request waits and nothing is on its way to send (a paused or failed message does not hold it back), still so after a 3 second settle delay, 15 seconds for a thread that delegated work. A failed or stopped turn is never wrapped up. The desktop's Finished alert fires once for each finish that is wrapped up. Avoid: "finished" on its own, which **Finished unread** means; "done", "complete".

**Step (iPhone client).** One thing the agent did, as the phone's thread page shows it between messages: a file read or changed, a command and how long it took, its reasoning. It is an activity record (an **activity summary** on the wire), placed by when it started among messages placed by when they were sent. The steps between two messages are a run, and each run is folded into one line. While the thread works through the last run, its line shows the working words with a light crossing them, like the desktop's **working line**, and VoiceOver hears the step running now, or Thinking between steps, and how many steps so far; once a run has ended, its line says how many steps it had and how long they took ("14 steps · 1m 32s"). A press opens the run's steps in place and another folds them. Steps replaced the phone's separate Activity tab (ADR-0051). Not a visual's step, which is one part of a **walkthrough**. Steps between two messages make a **step run**, which the thread page folds into one line; it is the phone's counterpart of the desktop's **Turn fold**, but it folds only the steps, never the messages. Avoid: "event", "log line".

**Wash (iPhone client).** The soft colour at the top of a phone page, mixed from the chosen theme's accent, that scrolls away with the page. It warms while a thread needs the user and leans to the danger colour on a failed thread's page (ADR-0051). Avoid: "gradient", "header background".
