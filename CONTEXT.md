# Sotto domain context

Sotto is a desktop dictation app that is becoming a voice development coordinator: the user talks to Sotto, and Sotto manages the coding agents. This file is the glossary for that domain. Use these terms in issues, tests and code; do not drift to the synonyms each entry lists as avoided.

## Threads

**Thread.** A conversation with one coding agent about one project, owned by Sotto. A thread has a Sotto thread ID, a title, a project, a model, a status (idle, running, error), messages and pending requests. In a project, a thread opens at once on its new-thread defaults; a model chosen afterward for that thread overrides its starting choice without changing the setting. Threads are a core Sotto function: memory, goals, assignments and the attention queue refer to threads by Sotto thread ID and never by a provider's own identifier. Avoid: "T3 thread", "conversation", "chat" when referring to a project-bound thread.

**New-thread defaults.** What a thread in a project opens on, apart from personal chats' and the coordinator's own reasoning model and effort: the model, reasoning effort and permission mode chosen in Settings → Agents' "New threads start with" row. A create-thread that leaves one of them unset takes the default instead, fit to what the model it lands on actually offers: the nearest safer permission mode when the model does not offer the chosen one, and the effort at the same position among the levels the model does offer; a provider with its own permission profiles (Devin) always starts on its first, never the chosen default. An empty install keeps today's behaviour until the row is used: the model follows the reasoning-based default, and effort and permission follow the provider's own starting choice. An explicit choice made for one thread's own creation always wins over these. `src/shared/newThreadDefaults.ts`.

**Thread title.** The thread's name in every surface that names it: sidebar, pane header, attention queue, widget and spoken summaries. It is Sotto's own record, renamed at any time from the sidebar row or the pane header and never pushed to the provider. A thread records whether its title was set by hand (`titleSource`): a name the user typed in a rename is `user`; a name Sotto had the thread's own provider write is `generated`; the stand-in "New thread" every new thread opens with, and any name a provider supplied, are `default`, and so is a first-message title, which a `titledFromFirstMessage` flag tells apart. Anything that generates a title leaves a `user` one alone.

**Generated thread title.** The name Sotto writes for a thread that still carries a `default` one, once the first reply to its first message lands. A side call to the thread's own provider sees that first message and that first reply alone, and nothing is asked while generated titles are off or while Keep local history is off. A Devin thread, a disconnected provider and every failure leave the name the thread had, its first-message title or the stand-in; a failure is logged, never shown. It replaces a first-message title, and a thread that began with one is still named after a steer or a follow-up sent during its first turn. Regenerate title asks again for any name but a `user` one; a `user` name is never offered for rewriting.

**First-message title.** The opening words of a thread's first message, which name a new thread from the moment that message is sent until its generated thread title lands. Only a thread Sotto saw begin, empty and on a `default` name, takes one; an older or imported thread keeps the name it has. Sotto cuts it at a word to fit 60 characters and ends it with an ellipsis when cut; nothing is asked of any provider for it. It follows the same two switches as a generated title, Generated thread titles and Keep local history, and a provider's own name does not overwrite it. It stays where no generated title comes, as on a Devin thread. Avoid: "placeholder", which ADR-0026 and older notes use for the stand-in "New thread".

**Side call.** One request Sotto makes to a thread's own provider client, on the thread's account and model and in its working folder, apart from the thread's session. It writes Sotto's own short text (thread titles, branch names, commit message drafts and pull request drafts) and nothing else. It never enters the thread's transcript, history or pane, is never resumed or listed as a thread, can use no tools, and runs at the lowest effort the model offers. Devin offers none. It replaced the OpenRouter writing model (ADR-0026). Avoid: "writing model", which named that model and is gone.

**Commit message draft.** The message a side call to the thread's own provider writes for a Git action whose commit dialog left the message empty, from the diff and the names of the files the commit takes (the action stages them itself), the repository's last twenty commit subjects and its `AGENTS.md`, with an imperative subject under 72 characters and a body only where the change needs one. A message typed in the dialog is used as typed. With generated commit messages off, on a Devin thread, or when the provider does not answer, the commit takes the subject "Update project files".

**Pull request draft.** The title and body a side call to the thread's own provider writes when a Git action creates a pull request, from the branch's commit subjects, its file list, a capped diff against the base and, unless Follow pull request templates is off, the repository's pull request template: the first template file in GitHub's usual places, or the only one in a `PULL_REQUEST_TEMPLATE` folder. With generated pull request text off, on a Devin thread, or when the provider does not answer, the pull request takes the last commit subject as its title and the template, or the list of subjects, as its body. There is no form to edit it in first; the pull request's description is GitHub's to edit afterwards.

**Host ID.** The permanent identity of the Sotto host that owns a workspace. Together with a Sotto thread ID, it distinguishes a thread from threads on every other host.

**Sotto thread ID.** An opaque ID, unique within its host, that Sotto assigns the first time it sees or creates a thread, normally a fresh UUID. It outlives any provider session. Agent state, queue items and assignments refer to this ID; a client pairs it with the Host ID when it shows more than one host.

**Provider.** The installed native client that runs the agent for a thread: Codex, Claude Code, Grok Build or Devin. Providers keep their own sign-ins and may be connected together; each thread's chosen model belongs to one provider. Claude Code, Codex and Grok Build each run a process per thread or chat (ADR-0038), so one ending on its own affects only that thread or chat: the provider stays connected, a reply it was writing is marked failed with a line saying it may be cut short, and the process starts again the next time the thread or chat is opened or sent to. Codex also keeps one **provider process** that holds no thread, for the model list, the account, skills and settings reads; Grok Build keeps none between connects.

**Client update.** What Sotto knows about one installed client: the version the adapter reads from the installed client, the version that client's own install channel publishes, and the one press that installs it. The **channel** is what installed it — npm (including a client whose package npm owns but whose binary lives elsewhere), the client's own updater, mise (`mise upgrade <tool>`, and for Grok Build its package's install step after it), or the Devin app — and it decides what an update runs; the published version is read from the npm registry. A client whose channel Sotto will not drive shows the command to run by hand instead of a button. A remote host's client updates show on its provider tiles, never on this computer's corner card. Say "client update", not "provider update": the provider is connected or not, the client is what gets replaced (ADR-0042).

**Client update line.** The one-at-a-time order a machine runs its client updates in: a tile's Update, Update all and Settings → Providers all join it, a failure does not stop the ones after it, and a client still waiting can be taken out with Cancel update. `clientUpdateRun` counts it ("Updating 2 of 3") until it is empty. `src/main/agents/control.ts` (ADR-0042, September 29 amendment). Avoid "the queue" for it, which is the coordinator's queue of threads; the command that joins it is still `queue-client-updates`, and a client in it is `queued`.

**Outdated process.** A thread's or chat's process started from a client that a client update has since replaced on disk. The update never stops a turn or disconnects the provider: an outdated process that is idle stops at once, the way the session reaper stops one, and one that is busy (a turn running, a request waiting for the user) finishes on the old client and stops the moment it is idle. A watched thread starts again on the new client straight away; any other starts it on its next action. An outdated process never sets the provider's version (ADR-0038). Avoid: "retired", which Provider retirement already means.

**Verified version.** The client version an adapter was checked against. Sotto connects to that version or newer and notes when the installed client is past it; older is refused. Not a pin: an exact pin is what kept an installed client old while newer ones were published.

**CLI lookup.** Where Sotto looks for an installed client, the same way for all four providers on a desktop and on a host: PATH, the login shell's PATH, `~/.local/bin`, the version managers' install folders (mise's `installs/<tool>/latest`, asdf, nvm, fnm, Volta, Homebrew), then npm's global folder, with Grok Build's own `~/.grok/bin` first. A manager's shim, or a script that runs the client through the manager (`mise x`), is never taken for the client, and each provider keeps its own rule for what it starts (Codex only its native binary). A client found off PATH runs with its own folder and Node's ahead of its PATH. `src/main/agents/cliLookup.ts`, ADR-0036. Avoid: "discovery", which is a provider's catalog of models, projects and threads.

**Provider session.** The native client's own identifier for a thread, distinct from the Sotto thread ID. In prose and user-facing text say "provider session", not "session" on its own or "remote ID".

**Project.** A working folder the provider knows about, with an ID, a title and a path. A thread belongs to exactly one project. A project lives on one host, and its threads run there; the path is in that host's own format. Its working-copy default in Settings → Application overrides the global default for new threads only. Local project defaults use the host-local project ID; remote project defaults retain the host-qualified client key.

**Folder browser.** Add project's dialog, and New thread's folder source: which computer the project lives on when more than one is paired (none is chosen for the user), then that computer's folders, listed by its host from its home folder (ADR-0025, September 26 amendment). Folders only, with Git and Project marks. **New folder** is a name until **Use this folder**, which adds the project and makes the folder on the host. On this computer it also offers **Browse with File Explorer** (Finder on a Mac), the system's own dialog. Avoid: "file picker", "remote file browser", which would be the Tools panel's files.

**Thread working copy.** The folder in which a thread's provider works: the shared project folder by default, or an explicitly chosen new or existing Git worktree. Threads sharing a folder share its files and checked-out branch; a separate working copy provides isolation without changing the thread's project memory scope (ADR-0014).

**Branch toolbar.** The row of pills under a thread's composer card for a Git repository, as T3 Code has it (ADR-0027): **Run on** and **Workspace** at the left, the pull request badge and the **branch picker** at the right. Each is its own bordered pill below the card, not a strip inside it. Run on names the machine the thread runs on, behind a laptop or server glyph, and is always a label here, since the host is chosen when the thread is made. Workspace is where a draft will work: **Current checkout**, **New worktree**, or **Previous worktree (branch)** for a worktree another thread of the project already has; it locks to static text once the thread has a message or a session. Avoid: "git bar", "workspace picker".

**Branch picker.** The branch toolbar's pill naming the folder's branch, **Select ref** for a detached HEAD, or **From origin/main** for a worktree not made yet. Its popover searches the host's refs, lists locals then remotes with `current`, `worktree`, `remote` and `default` badges, and pages them. Picking a ref checks it out in the thread's folder (a remote ref gets a tracking branch); a ref already checked out in another worktree re-points a draft at that worktree; for a worktree not made yet the pick records the base, with a **Start from origin** switch that fetches the base when origin has it and otherwise takes the local branch and says so; a name nothing matches offers **Create new ref**, except for a worktree not made yet, which starts from a branch that exists. A draft pointed at another thread's worktree shows that worktree's branch and does not move it before the first send. Right-click copies the name. A search that is a pull request URL, `#42` or a `gh pr checkout` line offers **Checkout pull request** first (see Pull request checkout). Git's refusal is shown under the row as **Failed to switch ref.** with Git's own words. A switch made here moves the thread's sent branch with it, so the branch-changed notice stays for checkouts moved elsewhere. Avoid: "branch dropdown", "checkout menu".

**Pull request badge.** The state icon and number of the branch's pull request at the right of the branch toolbar, its title in the tooltip ("PR #12 - Open: title"). A press opens the Pull request surface in Tools for that thread, pinning Tools to it when Tools was pinned to another thread.

**Pull request surface.** The Tools surface **Pull request** (its rail tile reads PR) for one of a thread's pull requests: its branch's own, else the one linked last, or one chosen from Linked pull requests. It is read from GitHub through the host's `gh` when it opens and on Refresh, never pushed with the state. Its whole reading is the merge checklist, with one large **Merge** docked under it in the method chosen beside it (Merge commit, Squash, Rebase; it starts on the Default merge method, and a pick here is saved while that is Last selected), enabled only when the checklist has nothing left; **Merge when ready** arms GitHub's auto-merge instead, where the repository allows it. An armed auto-merge, a merged and a closed pull request take Merge's place, with **Turn off** and **Reopen**. The description and Linked pull requests fold below; the ··· menu holds Ready for review or Convert to draft, Update with rebase, Merge when ready, Disable auto-merge, Copy link, Link pull request, Unlink from thread, and Close or Reopen pull request. With no pull request it offers the Git action's **Create PR** and **Link pull request**. Nothing happens from viewing; the merge, turning on auto-merge, closing and Update with rebase, which rewrites the branch on GitHub, ask first. The host acts only on a pull request the thread knows (ADR-0027). Avoid: "PR panel", "pull request form", which named the Changes form this replaced.

**Merge checklist.** What stands between a pull request and its base, as five lines in the order a merge meets them: Checks passing, Review approved, Up to date with the base, No conflicts, Ready for review. A line is done, or says what holds it back and carries the one press that fixes it (Open check, Open review, Update branch, Ready for review), or has none where the fix is elsewhere, such as conflicts to resolve in the branch. A line reads what GitHub reports, not a stand-in: "No checks" and "No review required" count as done, a request for changes where no review is required is said and linked without blocking, and a base GitHub could not compare is said and does not hold the merge back; the count beside the heading names it ("4 of 5 done, 1 does not block"). Avoid: "merge requirements", which is GitHub's name for its own branch rules, and "status", which the Git status already means.

**Linked pull requests.** The pull requests on a thread's record: the one its Git action created, ones linked with **Link pull request** (a GitHub URL or `#42`), and one checked out from the branch picker, each with how it came to be linked. The Pull request surface folds them below its checklist with the branch's own pull request and opens any of them; Unlink from thread, in its ··· menu, unlinks the one shown. A link is Sotto's record, not GitHub's, and is never pushed to GitHub.

**Pull request checkout.** T3's **Checkout pull request**, from the branch picker: a dialog that resolves the reference through `gh` as it is typed and checks the pull request out **Local**, with `gh pr checkout` in the thread's folder (the project's own checkout for a draft) and never forcing, or into a **Worktree**, which only a thread that has not started takes: the pull request's head becomes a branch (its own head branch, or `sotto/pr-<number>/<head>` for a fork) and the draft's new worktree checks that branch out on first send, or the draft points at the worktree that already has it. The pull request is linked to the thread either way.

**Local branch notice.** The dismissible line above a worktree thread's composer, in the status tone, saying that Start from origin found no `origin/<base>`, or that the project has no origin, so the worktree started from the local branch (ADR-0014, amended September 24, 2026). It names the branch, is said once per thread, and **Dismiss the local branch notice** keeps it away on this computer. Avoid: "fallback notice", "origin warning".

**Branch-changed notice.** The dismissible line above a shared-project-folder thread's composer when that checkout is on a different named branch from the thread's last send; a switch made in the branch picker moves the sent branch with it, so the notice is for a checkout moved elsewhere. Sending continues on the current branch; **Restore branch** is the user's explicit choice to switch back, with confirmation for uncommitted changes, and worktree-backed threads do not show the notice.

**Temporary thread branch.** The short starting branch of a new worktree, created on its first send and eligible for a descriptive name from that first prompt. It stops being replaceable once the user or agent changes its branch, or another thread shares the folder.

**Git status.** What the host last read of a working copy's Git state, carried on the thread's worktree record and reaching every client through the state stream: the branch, its upstream, ahead and behind against the local tracking ref, whether the tree is dirty and how much changed, the default branch and the distance from it, the branch's pull request, and when the remote was last fetched. It is read the way T3 Code reads it (ADR-0027): after finished work, on a refresh, and on a timer for the threads a window is looking at while that window is in front. Avoid: "git state", "sync status".

**Git action.** T3 Code's stacked action on a thread's working copy: commit, push and create the pull request from one press, or any prefix of the three, with a feature branch first when asked. The host runs it on the thread's lane, reports each stage on the thread record in T3's words, and ends it with a notice that offers the next step (Push, Create PR, View PR). Pushing from the default branch asks **Push to default ref?** first (**Abort**, **Push to** the default branch, as in **Push to main**, or **Check out feature branch & continue**); nothing is forced, merged or rebased, and a pull is fast-forward only (ADR-0027). The control is the button at the end of the pane header, whose label follows the folder's Git status (**Commit**, **Commit & push**, **Commit, push & PR**, **Push**, **Push & create PR**, **Pull**, **Create PR**, **View PR**, **Publish repository**, and **Initialize Git** for a folder without Git), with a chevron menu holding **Commit**, **Push**, **Create PR** or **View PR**, and **Publish repository...** for a repository without a remote, each disabled with its reason rather than left out. Avoid: "sync", "quick action", "Git button".

**Checkout guard.** A reservation for one checkout shared by sends, Git actions, automatic pulls, checkpoint reverts and folder removal. A mutation excludes sends and other mutations; read reservations, including checkpoint snapshots and automatic settling, can overlap with sends. It records what holds the checkout. Identity follows the canonical checkout root, including subdirectories and aliases; linked worktrees remain independent.

**Commit dialog.** What a Git action that commits opens first, T3's **Commit changes**: the branch with a **Default branch** tag, the changed files with their line counts and an **Edit** mode that leaves files out, **Commit message (optional)** which the host writes when left empty, and **Cancel**, **Commit on new branch** and the action itself. The files come from the host on request, never with the status. Avoid: "commit form", which named the drawer inside Changes that this replaced.

**In front (a window).** The condition under which the host reads remotes on its own: the Sotto window is showing and has the focus, or had it within the last 45 seconds; on a headless host, a paired client holds an open socket. Nothing is fetched for a window that is not in front.

**Settings → Git.** The Settings section that holds every Git setting, grouped under the moment each one acts: **When a thread commits** (the Commit and pull request style), **When a pull request is made or merged** (Follow pull request templates, Default merge method, Auto-settle merged threads), **When you read Changes** (Diff layout, Hide whitespace changes, Default diff file state, Proactive panels) and **In the background** (Git fetch interval, Automatically pull). Each description says what Sotto will do with the value shown, and changes as the value does. The worktree cleanup rules stay under Application, and the Generated switches under Cleanup. Avoid: "Git preferences".

**Git fetch interval.** The setting under Settings → Git, In the background, that says how often, while the window is in front, the host fetches a project's origin so its threads' Git status knows ahead and behind. A refresh and a Git action also fetch first, at most once in 15 seconds. Off stops every fetch, those too, so ahead and behind compare with the remote as it was last fetched; a refresh still asks GitHub for the branch's pull request.

**Automatically pull.** The setting under Settings → Git, In the background, off until turned on, under which the host fast-forwards a thread's folder when a read of the remote finds it on the default branch, clean, tracking an upstream and only behind, and no thread is working or waiting in that folder. It is the Git action's Pull, run at the moment the status is read; nothing is merged or rebased. Avoid: "auto-sync".

**Default merge method.** The setting under Settings → Git that says which method a pull request's merge should start on: Last selected (the method used last, which Sotto remembers only while this is the choice), Merge, Squash and merge, or Rebase and merge. It is the method the pull request checklist's merge starts on; under Last selected, a method picked beside that Merge becomes the one used last.

**Commit and pull request style.** The setting under Settings → Git, When a thread commits, that shapes the commit messages and pull request text a thread's own provider writes: Repository conventions (the recent subjects and `AGENTS.md` the request already carries), Conventional Commits, or Custom instructions in the user's words, sent with each of those requests. Either of the last two takes precedence over the repository's own style, whose context is still sent. An example under it shows a commit subject and pull request title in the chosen style; under Custom instructions it shows the subject the instructions start from and says the model applies them, because Settings asks no model and does not guess. Follow pull request templates, under When a pull request is made or merged, says whether the thread's own model is given the repository's pull request template to follow when a Git action drafts a pull request. Avoid: "writing style", "commit format", "prompt".

**Proactive panels.** The setting under Settings → Git, When you read Changes, off until turned on, under which Changes opens on its own when a turn leaves its folder with at least 3 more changed files or 50 more changed lines (T3 Code's measure, taken from the working copy's counts before and after the turn rather than the turn's own diff, and only while the Threads page is open), only on a closed Tools panel not pinned to another thread, and without moving keyboard focus. A large turn in a pane not in focus waits until its thread is focused. It is the one exception to "nothing announces itself unasked", and it exists only because the user asks for it (ADR-0027).

**Reclaim (a worktree).** Removing a thread's own worktree folder while keeping its branch and the thread; the next send puts the folder back on that branch. It happens on the user's word (**Remove worktree** in the Working copy panel, or the question Settle asks) or under a cleanup rule the user turned on, never for a folder with uncommitted work without their answer (ADR-0041). The question lists ignored items other than dependencies and requires a separate acknowledgement to discard them; a changed list requires a new question. Nested repositories and worktrees are listed with a count of uncommitted changes; repositories also show commits not on any remote and go only after the separate acknowledgement. Each host reclaims only its own worktrees, under the rules in its own settings. Avoid: "delete the worktree", "clean up the thread".

**Thread pane.** A view of one thread within the Threads page, with its own reading position and input. Closing a pane leaves the thread and its running work intact.

**Unreadable-request notice.** A line in the owning thread's pane saying that a native request could not be shown and was refused. It is neither a pending request nor the user's answer, and grants no approval.

**Thread activity.** Provider-reported work alongside a thread's messages, including commands, file changes, visible summaries, tool results and subagent states. Activity is observational history, not a user message, an assignment or permission to act.

**Computer Use.** Codex's own tool for seeing and operating the apps on the computer, named as Codex names it. In a Codex thread it works only in Full access and while the Codex desktop app is open; its calls show in the thread activity as Computer Use, and a recognised failure shows guidance. A native pipe failure means the connection to the app helper is unavailable, even if the app is open; it does not prove that no earlier action happened. Sotto relays it and changes nothing about how Codex runs it. Avoid: using it for Sotto's own browser, which is the Tools panel's.

**Native skill.** A reusable instruction set exposed by a provider for a thread's working copy. Selecting a skill adds reviewed text and a provider-recognized reference to that draft; it neither submits the draft nor grants authority.

**File mention.** A file of a thread's working copy named in a draft by typing `@` and picking it, like a native skill's `$`: both are mentions, a sigil and a name written into the draft's own text. The mention is the reference — deleting its token removes the file from the send — and it reaches every provider as the same `@path` relative to the working copy. Files outside the working copy, git-administrative entries and paths containing a space are never offered.

**Tools panel.** The shared working surface beside the thread panes. Its working-copy tools follow the focused thread unless pinned to a particular thread's working copy. Agents always follows the focused thread, even while another working copy is pinned. Its seven surfaces (Browser, iPhone, Terminal, Files, Changes, Pull request, whose tile reads PR, and Agents) sit on a rail at its outer edge, each surface under one line of chrome naming what is open, and the working copy it reads is its footer. A dot on a surface in the rail means something is live there. Avoid: "tab" for a surface, which is a page or a shell inside one.

**Changes.** The Tools surface that shows a thread's working folder as T3 Code's diff panel: the files of one **diff scope** as blocks with their status and line counts, each collapsible, with Copy path and a name that opens the file in Files, and a file tree beside them. Its comparisons read and never write: there is no staging, discarding or reverting of lines or files in it, and committing is the **Git action**'s (ADR-0027). The one thing on it that writes is Sotto's own **Checkpoints** drawer, whose toggle sits on its line of chrome: it reverts a whole turn's files and conversation, after a confirmation. It starts in the layout, whitespace and file state that Diff layout, Hide whitespace changes and Default diff file state name. A choice made in it holds until one of those settings changes or Sotto restarts. `mod+d` toggles it, or `mod+shift+d` when the dictation hotkey holds `mod+d`. Inside it, "diff" names a comparison, never the surface, as T3's labels use it (Refresh diff, Stacked diff view). A thread on a paired host has no Changes here; the surface says to use it on the host. Avoid: "Diff" or "diff panel" for the surface.

**Checkpoint retention.** Turn checkpoints follow Keep local history. Turning it off or forgetting a thread deletes its saved checkpoints at once, along with file backups that no other checkpoint needs. Turning history off, forgetting a thread and the age and size limits keep unfinished revert records and their file backups until recovery finishes. Completed checkpoints expire after 30 days; checkpoint storage is capped at 500 MB, removing the oldest checkpoints and recovery backups first. Turning history back on starts fresh checkpoints.

**Diff scope.** What Changes compares. **Working tree** is the working copy against HEAD, untracked files included; **Branch changes** is the branch against its base as `base...HEAD`, the changes since the two parted, with the base **Automatic** (the branch's recorded merge base, the remote's default branch, then `main` or `master`, the remote copy preferred) unless one is picked; **Latest turn** and **Turn N** are one turn's edits from Sotto's own checkpoints, numbered in the order the thread's checkpoints were taken in that working copy, and a turn whose checkpoint is unavailable says so rather than showing nothing. Avoid: "staged" and "unstaged", which are not scopes any more.

**Review comment.** The user's words about lines picked in **Changes**, waiting on that thread's composer as a chip named for the lines (`voice.ts L12 to L15`, or `(before)` when every line was removed) and marked under them with Delete comment. The next prompt carries each one as text after the user's message: its name, its words and its lines as a fenced diff, so every provider reads the same message. It keeps the lines as they read when written, lasts until it is sent or deleted, and is held in the window rather than saved with the **draft**. It is evidence for the agent to read, like any prompt text; it answers nothing and grants nothing. Avoid: "annotation", "inline comment", and "mention" for it: a **file mention** is a token written in the draft, a review comment is not.

**Browser task.** One thread's work with a page in Sotto's browser, including its current action, user decisions, checks and evidence. A browser task may be working, paused, completed or failed; its reported result states what was checked and what remains unchecked.

**Browser player.** The floating window over a browser task's page, for the focused thread and never another's, pinned or not (#331). It opens on its own when that thread's agent opens a page, starting at 340x250 above the composer; drag its title bar (or, focused, the arrow keys) anywhere below the drag strip, and resize it from its corner down to 280x200. There is one placement for the session, the same for every thread. **Move into Tools** sends its page to Tools > Browser without pinning; **Shrink** turns it into a pill at its own corner that restores it; **Hide** leaves the agent working with Tools > Browser as the way back. It steps aside, drawing nothing, while Tools > Browser already shows that same thread's same page. **Show the browser when an agent opens a page** in Settings turns off only its opening on its own; the work and Tools > Browser are unchanged either way. Avoid: "preview", the corner view it replaced, which showed a thumbnail rather than the live page.

**Shared browser page.** A browser page the user has made observable to its owning thread. Sharing observation does not approve navigation, clicks or typing, and revoking it ends that access.

**Browser grant.** What lets one thread open pages, navigate, click and type in Sotto's browser without asking. It covers those four actions and nothing else; on the test iPhone a tap is a click and a key press is typing, so it covers those too (ADR-0045). Every project thread has one by default, on **Let agents use the browser without asking** in Settings; while that is on, a thread's grant has the source `settings`. Off, a request in Tools offers **Allow this thread to use the browser** beside Allow once, which grants that thread the browser with the source `user`. A page the grant opens is shared the way Open and share shares it, and nothing more: a page the user opened stays private until shared, and the grant reaches no other thread. It is shaped like a policy record but held only in memory. **Stop** on the grant line in Tools > Browser or Tools > iPhone ends the thread's grant, whichever its source, and the thread asks again until granted once more or Sotto restarts; turning the setting off ends every `settings` grant at once, while a `user` grant stays until stopped. It ends at Stop, when the thread is gone, and when Sotto closes. Only the setting or the user's own answer in Tools makes one; supervision, a memory, repetition or a provider's confirmation never does (ADR-0029). Avoid: "trust", "auto-approve", "allowance", which is a Devin profile's word.

**Test iPhone.** A thread's page in Sotto's browser drawn as an iPhone 15 Pro: 393 by 852 CSS pixels, iOS Safari's user agent, a touch screen and a storage of its own. An agent opens a web or Expo-web build on it with `iphone_open` and drives it with taps, swipes, typing and key presses; the user can use it too. One per thread; opening another address replaces what it shows. It is not iOS and runs no native code, so native modules, the camera and iOS rendering are not tested on it. It is a browser page, so the browser grant covers it and Tools > iPhone holds its address, sharing, steps and requests (ADR-0045). Avoid: "simulator", "emulator", which it is not; "iPhone client", which is Sotto's own app for a real iPhone.

**Cloud iPhone.** A run.cloud iOS simulator one thread uses to test a native build: the agent names a simulator build in the thread's folder, and the thread asks the user, with the build, the price and the month's minutes, before anything is uploaded. **Start cloud iPhone** covers that one session; inside it, taps, swipes and typing do not ask. It ends when the agent finishes, at **End session**, after the idle minutes, at the monthly cap, when its thread is gone, or when Sotto quits, and Sotto deletes the upload. Its key and its monthly cap live in Settings > Cloud iPhone. It is a simulator, not a device (ADR-0047). Avoid: "device farm", "emulator", "test iPhone", which is the browser page.

**Phone player.** The floating test iPhone over the focused thread, framed as Virtual iPhone's widget was: a label to drag it by (with its size, **Show in Tools** and **Hide**), the phone with the live page in its screen, and what the agent is doing below, with Pause and any waiting request. It opens on its own when that thread's agent starts a task on its phone, under **Show the browser when an agent opens a page**, and Tools > iPhone's **Show phone** brings it back. One place and size for the session, three sizes, never larger than the window allows. It can be open beside the Browser player; each steps aside only where the other overlaps it. While the thread's cloud iPhone runs, the phone player shows it instead, with its minutes and **End session**. Avoid: "widget", which is Sotto's floating dictation widget.

**Browser feedback.** A screenshot and optional selected-element or region context added to a thread's draft by the user. It is unsent draft content until the user sends it.


**Settled.** A reversible workspace grouping for a thread or project whose work the user has put aside. It preserves history and running work; restoring a project preserves the individual threads the user had already settled. Creating a new thread in a settled project returns the folder to the active sidebar with only the new thread; older threads stay in Settled. Under **Auto-settle merged threads** (off until turned on) the host settles a thread at rest once GitHub reports a pull request merged at the current commit of the branch it last sent on, checked on the worktree cleanup's hourly sweep, once per thread and branch while Sotto runs; it removes no folder unless a cleanup rule says so.

**Terminal mode.** The Threads sidebar showing terminals instead of threads, switched with the Threads | Terminal control in the sidebar's top row. Terminals open in the same pane grid as thread panes, so turning the control to Terminal from another page leads to the Threads page. A project's folder head in Terminal mode offers Settle project, the same as in the thread list; a settled project leaves the list once its terminals close. Avoid: "terminal tab", "terminal page".

**Terminal.** In Terminal mode, a shell or a provider CLI that Sotto starts in a project folder or in its own worktree, named by the user when it opens. It belongs to a project, never to a thread, and keeps running while its pane is hidden. Distinct from the Tools panel's terminal and from a pane's Terminal drawer, which both belong to a thread's working copy. Its first line, printed by Sotto, names the folder and the command.

**Terminal drawer.** A thread pane's own terminal, under its composer across the bottom third of the pane, opened with the pane's Terminal drawer button or Ctrl+J (Cmd+J on a Mac) in the pane the key lands in. Its terminal leaves Ctrl+J to the page; Escape and every other key belong to the shell. Its shells start in the thread's working copy and are separate from the Tools panel's terminal: a shell started in one never shows in the other. Opening a drawer with no shell starts one; closing its last shell hides it. Hiding it leaves its shells running. Each thread remembers whether its drawer is open and how tall it is, and every pane of a split has its own. Under a Frosted window the drawer is see-through too, a little more solid than the room. A thread on a paired host has no drawer; its terminal is on the host (ADR-0049). Avoid: "bottom panel", "terminal tab", or "Terminal" alone, which is Terminal mode's.

**Closed.** Terminal mode's counterpart to Settled: the shelf of terminals explicitly closed this session, which can be reopened with the same command until Sotto quits. Every row stays; its old output is released on Close. Stop and a process exiting leave its output readable. The 64-terminal limit counts terminals outside Closed.

**Thread binding.** The durable relationship between a Sotto thread, its provider session and its project. Historical bindings survive a provider's retirement and never grant a replacement provider authority over that thread.

**Provider retirement.** An upgrade that stops using an old thread provider while retaining recovery evidence and the user's draft. Old assignments, answers and uncertain actions are not transferred or replayed through a native client.

**Thread interface.** The verbs the coordinator uses for any provider, with no provider identifiers in their signatures:

| Verb | Meaning | In code (`AgentHost`) |
|---|---|---|
| create | open a new thread in a project with a model | `execute({ type: 'create-thread' })` |
| resume | observe an existing thread's detail so its history and later events arrive for it | `observeThreads` (optional for adapters that always deliver detail) then `snapshot` |
| prompt | send a user message to a thread | `execute({ type: 'send' })` |
| cancel | interrupt the agent's current turn | `execute({ type: 'interrupt' })` |
| status | read every project, model and thread the provider knows | `snapshot` |
| events | subscribe to status changes pushed by the provider | `subscribe` |

Answering a question or permission request and creating a project are also part of the thread interface. The native provider adapters preserve Sotto thread identity across these actions.

**Provider adapter.** An implementation of `AgentHost` that speaks one provider's protocol and identifiers. Every adapter must pass the shared adapter contract in `tests/integration/adapterContract.ts`. Avoid: "driver", "backend".

**Codex provider session alias.** The adapter-owned record in `codex-threads.json` that maps the provider session ID Sotto chose at creation to the thread ID the Codex App Server assigned, plus the working directory, title, model and the digests of dispatched messages. The thread registry holds only the Sotto-chosen provider session ID; the Codex thread ID never leaves the adapter (ADR-0005).

**Codex session log.** Codex's own persisted transcript of a provider session (`rollout-*.jsonl` under `$CODEX_HOME/sessions`). Sotto reads only its user-authored entries to tell its own dispatched messages from text typed directly in Codex: an exact client identity and matching digest suppress Sotto's own entries, including `item.client_id` on completed items. Legacy entries without a client identity use the pending digest and consecutive-entry check. Other authored entries are a takeover. Sotto never copies or logs the log's content.

**Newest-turn check.** What a read immediately before a Codex send does in place of reading the whole transcript, whether the coordinator makes it or the adapter does before `turn/start`: it asks Codex for its newest turn alone and reads the whole transcript only when that turn is not the finished one Sotto already holds, with the same messages. It decides whether a whole read is needed, never whether the send may go: the stale-reply check after it is the same (ADR-0005, #324). Avoid: "freshness cache", "quick read".

**Transcript cursor.** How far a thread's provider transcript had been read when Sotto last stopped, stored by the adapter beside the thread's alias: the byte after the last complete line, the identity of the file it was read from, and what the reader had already matched there. Reconnecting seeks to it instead of reading the file again, and it is only trusted beside the messages and bounded activity it accounts for in the same history epoch. `WorkspaceHost` supplies that evidence through the per-thread history source, or through `restoreThreadHistory` on the legacy path (ADR-0015, ADR-0016). Claude has one; a thread whose history is not handed back is read from its first byte. Avoid: "bookmark", "watermark".

**Takeover.** The user sends a message to an assigned thread directly through the provider (for example `codex resume` in the Codex CLI). The adapter reports that message as a user message with no command ID, so the coordinator switches the assignment to manual mode and keeps watching. Opening or reading a thread is not a takeover.

**Stale-reply check.** The adapter's refusal of a send that names a different user message as the thread's newest than the one it recorded, so a reply written before a takeover is not sent after it. The coordinator names the thread's `lastUserMessageId`, which the adapter publishes from what it recorded rather than from the window of messages it holds: a window put away while the thread's session ended and taken back up later holds none of the older messages. Each adapter words its refusal its own way, says the thread changed, and sends nothing.

## History and the host

**Event store.** The SQLite database `threads.sqlite` in the user data folder, opened by `node:sqlite` behind `ThreadStore`, and the source of truth for what was said in every thread. Providers are read to append to it and never asked to rebuild it; their transcripts are read on demand for rewind, takeover detection and a capped import (ADR-0016). It is a second database beside the memory store, which keeps memories and policy records and is not touched by history. Avoid: "message cache", "transcript backup".

**Message identity alias.** Corroborated native evidence that two saved message IDs describe the same authored message. Its `message-aliased` thread event keeps the canonical message in the projection only after comparing both saved messages. It is separate from a Codex provider session alias, which maps a thread to a provider session. Equal text alone is not an identity alias.

**Thread event.** One append-only row in the event store's `events` table: a sequence number, the Sotto thread ID, a kind, a time and a JSON payload. The kinds are `message-added`, `message-text-appended` (a streaming message grew by a suffix), `message-replaced` (a whole message changed in a way an append cannot say), `message-aliased` (a native identity repair that removes only a corroborated duplicate from the projection), `messages-reset` (a confirmed rewind, carrying the new history epoch) and `answer-given` (a permission or question answer, with its attribution). Nothing is edited or deleted to change what happened; a correction is another event. Avoid: "log line", "record" for one of these.

**Sequence number.** The event store's own counter, one per thread event across all threads, and the thing a client resumes from: "everything after N" is the whole catch-up protocol. The desktop reads no events from a remote host, so it asks for none and resumes from nothing (ADR-0025). Distinct from a thread detail's `revision`, which is what one window holds for one thread, and from a message's position in the projection. Avoid: "offset", "version".

**Activity summary.** An activity record cut down to what a **step** on a phone's thread page shows: its kind, status and title, the command it ran, its exit code, when it started and how long it took, and the paths of the files it changed. Its output, text, error, diffs, plan steps and agents stay on the host. A socket client that accepts the `activity-summaries` host feature is sent every record this way, in whole details and in detail deltas alike; it is still an activity record, so a delta of summaries applies as any other does (ADR-0025, October 3 amendment). Not a reasoning summary, which is a record of its own, and not a thread's summary on its sidebar row. Avoid: "slim activity", "lite record".

**Detail delta.** What changed in one thread's history since a revision a client holds: text a streaming message grew by, a whole message, or an activity record as it now stands or its removal (`AgentThreadDetailDelta`). Main sends one in place of the whole detail while a thread changes, to the window over IPC and to a socket client that accepts `detail-delta`. A client applies it only to the revision it was measured from and otherwise reads the whole detail once. Avoid: "patch", "diff" for what is sent.

**Catalog revision.** A number main gives each host's model catalog, advanced only when the catalog's content changes (ADR-0028). The broadcast sends a catalog once per revision per window and then only its revision; a command receipt always sends only its revision. A window reads the whole state once through `AGENT_GET` when it holds neither that revision nor, for a command receipt, a newer one. The headless host and the desktop's phone listener each keep catalog revisions of their own for the paired clients that accept `model-catalog-revision`: each shell names the revision, and carries the catalog only the first time a connection is sent it. Distinct from a thread detail's `revision` and from a sequence number. Avoid: "catalog version".

**Command receipt.** What main answers a window's command with: the shell after the command, its outcome and the evidence its caller acts on (the draft revision saved, the effective settings), with each model catalog named by its catalog revision rather than listed (`AgentCommandReceipt`, ADR-0028). The page puts the catalogs back before any caller reads it. Distinct from the delivery receipts in `deliveredDrafts` and `followupReceipts`, which each record that one draft revision was accepted. Avoid: "command response" for what crosses.

**Projection.** A table derived from the event log for reading, currently `messages`: one row per message of a thread, keyed by position, which is what a thread pane draws. A projection is rebuilt from the log when it is missing or when the schema version moves, and is never written to by hand. Avoid: "view", "cache".

**History window.** How much of a thread's history a pane holds: the newest ten turns when it opens, then twenty more each time the user presses **Show earlier messages**. A turn here is a user message and the assistant messages that follow it. The detail says whether anything older exists (`earlierAvailable`), so opening a long thread costs the same as opening a short one. The detail windows activity the same way: the work of a turn above the window stays out of it with that turn's messages and takes its place between them when they load, so it never trails the newest answer. The turn still running is always in it. Only the detail does this; the store, the sidebar and the adapters keep every record.

**Turn fold.** The one line a finished turn puts its work under, between the user's message and the turn's last written reply. It says how the turn ended and how long it took ("Worked for 40s", "Failed after 12s"), with the files it changed beside it. Pressing it opens the messages and activity in between. A turn still running, and a turn whose start is above the history window, keep every row on screen because neither has a finished span to fold. So the rows a pane draws count what it is showing, never how much history it holds.

**Monitoring task.** A live, provider-confirmed watch on a background process or task. A running command or unattended process is not enough evidence. The little creature above the thread composer appears while that watch is active and leaves when it ends or needs your answer. Monitoring is observation, never permission to act, and is not restored from history. It outranks **background work** and a **held action** for the composer's one creature, because it is the strongest claim of the three: the provider says it is looking at something.

**Background work.** Agent work, or a command sent to the background, started from this thread that the provider has confirmed is still running, whether or not a turn is: a workflow, a subagent, a teammate, a remote agent, or a shell command. The creature stands at the end of the track by the readout and sends small agents out along it, and the reader is told **Working**, or *Working · 3 agents* when there are several. A command waits rather than works: once the turn has ended it holds the hourglass and the reader is told **Waiting**, named by its description; beside agents it is only counted, *Working · 2 agents · 1 command*. The evidence is the provider's own task frames, a start and the bookend that ends it, never elapsed time or what the transcript says; today only Claude Code reports them. A subagent the turn is still blocking on is the turn's own action, not background work, until it is moved to the background. Work started by another agent is that agent's business and does not count. Background work survives the end of the turn, and so does the thread's sidebar row: it stays **Working** with its ring while agents run, or reads **Waiting** for a command alone, and when the work ends it reads **Working** through the turn Claude Code starts on its own to report back, saying **Done** once that report is in. A message from another session, or a continuation after a usage limit, is a turn Claude Code starts on its own too, and reads the same. It keeps its provider session from being reaped, and ends with its bookend, an interrupt, an error, a disconnect or a restart. Like a monitoring task it is observation only, grants nothing and is never restored from history. A monitoring task outranks it; it outranks a held action. Not to be confused with **working preferences**, your answers about how you like to work.

**Held action.** One action of the live turn — a command, a tool call or a subagent — has held the thread for twenty seconds or more. The same creature stands above the composer holding an hourglass, naming the action and how long it has run; the reader is told **Waiting**, which is the plain word for it. A command the turn sent to the background wears the same pose once the turn has ended (see **Background work**). Not to be confused with a thread **waiting on you**, which is `ThreadRow.waitingFor` and reads *Needs your approval* or *Needs your answer* in the sidebar: that is the one case a held action excludes, because its request card already says so. A held action claims only elapsed time — unlike a monitoring task it is no evidence that the provider is watching anything, it grants nothing, and it reads the `activities` every adapter writes rather than any one provider’s events, so it needs only that the adapter record when a running action started, which Claude Code, Codex, Grok Build and Devin all do. A confirmed monitoring task and confirmed **background work** both outrank it, in that order, because the composer reserves room for one creature and each of them is a stronger claim than a clock.

**Watched set.** The threads the host keeps in memory and keeps a provider session for: the threads on screen, plus assigned or queued ones. It is what `observeThreads` names. A thread outside it carries its summary alone, so startup and publish cost follow the open panes rather than the whole archive. Avoid: "active threads", "open threads".

**Finished unread.** A thread that finished its work while no client showed it, and that no client has shown since. The host's coordinator records it, keeps it across a restart and publishes it on the thread as `finishedUnread` (ADR-0046). The thread earns it when its turn, and any background work that turn started, ends while no client observes it; a disconnect, a failed turn or a thread on screen earns nothing, and working again drops it. Showing the thread on any client clears it on all of them: a pane on the desktop while its window has the focus, or the thread open on a paired iPhone. A thread that finishes in a pane while the window is behind another app, minimised or in the tray earns it, and the window gaining the focus clears it. The desktop's sidebar reads it as **Just finished**; the iPhone marks the row in Recent with a dot and a bold title and counts it on the Threads tab. Avoid: "unseen", "new", "unread" on its own (messages have no read state).

**Session reaper.** The host's sweep, every five minutes, that stops a provider session idle for thirty minutes. It never stops a session with a running turn, one with a pending request, one with a confirmed live monitoring task or background work, or one in the watched set, and stopping one costs only a resume because the resume cursor stays on the host. An in-flight history read defers its session's stop without renewing idle age or holding another session open. Empty polls do not count as activity; newly read provider events do.

**Held thread.** A thread whose messages its adapter keeps in memory: it is in the watched set, its provider session is still open, or nothing has yet said what is watched (`ThreadMessageLog.holding`). The session reaper decides how long an idle one stays held, so during a working session most threads are. A held thread's messages still reach the workspace only as thread events, never in the activity snapshots it reads, a thread refresh, or the snapshot a confirmed thread settings change hands back (ADR-0016). Not to be confused with a **held action**, one action of a live turn that has run for twenty seconds or more. Avoid: "loaded thread", "open thread".

**Host.** The process that owns the providers, the worktrees and the event store. It is Electron main on this computer (the local host) or `src/host/index.ts` running under plain Node on any machine reached over SSH (a remote host); the desktop can hold several at once (ADR-0025). The word is also the suffix of the interfaces inside it (`AgentHost`, `WorkspaceHost`); in the host-and-client sense it means the whole owning side, whichever machine it runs on. A host Sotto started over SSH outlives the desktop and stops only on Stop host or Forget. Avoid: "server", "backend".

**Host service.** The interface the host offers a client and nothing more: the event stream after a sequence number, the shell, one thread's detail, and commands. `HostService` in `src/main/agents/hostService.ts`, with `LocalHostService` over `AgentControl` as the only implementation today; the window's commands go through it, so a second transport is a new client rather than a rewrite. Distinct from `AgentHost`, which is the interface a provider adapter implements on the other side of the coordinator. Avoid: "API", "server interface".

**Client identity.** Who is speaking to the host service, carried on every command: `{ clientId, user, transport }`. The desktop window is `desktop-window` over `ipc`; Sotto's own supervision is `sotto-supervision`, so a record shows an answer that came from Sotto rather than the user; a paired remote client is its pairing ID over `socket`. It becomes the attribution on an `answer-given` event, and `Authority.mayGrant` is where it is asked whether that client's answer may count as a grant. The user name is recorded locally and never logged or sent. Avoid: "session", "caller".

**Client.** The side that draws threads and sends commands, speaking only the event stream and the thread interface and holding no provider identity of its own. The app's window is one over IPC; the desktop reaching a remote host is another, speaking the same two things over a socket (`SocketHostService`, ADR-0025). The iPhone client (`apps/ios`, in development) speaks the same socket protocol from its own Swift code, not through `SocketHostService`, to a headless host or to a desktop with phone access on. Avoid: "frontend", "UI" when the split is what is meant.

**Attribution.** Who gave an answer, carried on every `answer-given` event: `{ clientId, user, transport }`, where transport is `ipc` for the desktop window on this machine or `socket` for a paired remote client. It is evidence of who answered and never authority in itself; policy records decide whether an answer counts as a grant (ADR-0004), and the local desktop window always may answer. Avoid: "identity", "actor".

**Pairing.** How a client beyond loopback is admitted: a short-lived single-use code is redeemed once for a token, and signed sessions over that token carry every later request. `PairedClients` in `src/main/agents/pairing.ts` holds the records — a client ID, a normalised device name and the token kept only as a hash — and a per-install secret signs the sessions. Over SSH the desktop asks the host for a code and redeems it itself, the tunnel being the user's authenticated session; a client with no SSH session types a code shown on the host instead, in Settings > Phones on a desktop, in a headless host's Phones dialog on the desktop that reaches it, or printed by the host's own command. The iPhone client does this over private Tailscale HTTPS, once for each **computer** it adds: the user types the machine's name on the tailnet, the phone finds its full `*.ts.net` address through MagicDNS and checks a Sotto host answers there, on port 8443 (where the desktop serves it) and then 443, and the code is spent only on that host (ADR-0025). Being paired is admission and not authority: a `remote-answer` policy record scoped `client:<clientId>` is what lets a client's answers count as grants (ADR-0004). Setup over the user's authenticated SSH connection creates that record for the desktop once; any recorded revocation or expiry prevents setup from granting it again. Clients paired by code need an explicit grant. The host's listener binds loopback only, and the README's "Privacy and cost" section names the SSH path and phone access.

**Phone access.** The desktop letting the owner's paired phones reach the threads its own local host runs, over the owner's tailnet (ADR-0033). While the `phoneAccess` setting is on and the local host runs, main opens the host protocol listener on loopback over the desktop's host service and has Tailscale Serve carry HTTPS port 8443 on the tailnet to it; never Funnel, and never port 443. Sotto changes only a Serve setting that is its own, removes it when phone access turns off and when Sotto quits, and puts it back at the next start. If removal fails, phone access stays in a cleanup failure state, stops the host protocol, reserves its loopback port, and retries while Sotto is open. Settings > Phones is where it is turned on, where each setup step says whether it worked, where pairing codes are shown (one at a time, and nowhere else on the desktop's own phone access), and where each paired phone has **Can answer**, the owner's switch that writes or revokes that phone's `remote-answer` policy record, and Remove. Pairing also allows a phone to choose the coordinator’s reasoning provider and model using the computer’s saved credentials, without Can answer; this may change which configured reasoning host receives coordinator content. Keys and endpoints stay host-local. Each computer shares only its own threads. A headless host runs the same phone access over its own host service and pairing store (ADR-0050). Its `phoneAccess` setting is the host's own, and the desktop turns it on, shows its checks, pairs its phones and gives each Can answer and Remove in the host's **Phones** dialog in Settings > Hosts, through the host's administrative routes on the SSH connection's forwarded port. The clients that paired through phone access are its phones; a desktop paired with the same host is never one. `src/main/phones/`, `src/host/phones.ts`, `src/main/hosts/hostPhones.ts`. Avoid: "remote access", "mobile server", "tunnel" for this, and "phone host": the phone is a client.

**Launch script.** The fixed Node script the desktop pipes to one `ssh` command per operation on a remote host's machine: find the host or start one detached, ask it for a pairing code, revoke a client, stop a host Sotto started, or take one step of a **host update**. It prints one JSON result and exits; the SSH port forward is the only ssh that stays open. A launch's result also carries the host's administrative token, which the desktop keeps in memory for that connection to administer the host's phone access through the forward (ADR-0050). A short shell in front of it finds a Node the host archive accepts, through the login shell and the usual version managers, and says so when there is none. A host it starts records that in its own listener descriptor, which is how a host counts as started by Sotto (ADR-0025). `src/main/hosts/launchScript.ts`. Avoid: "supervisor", which is Sotto following an assigned thread (supervision); "daemon".

**Installation folder.** Where a remote host's release is unpacked on its machine, which a saved host names (`~/.local/share/sotto-host` by default). It holds either one flat install, with `host/index.js` in the folder itself, or **host versions** side by side under `versions/<X.Y.Z>/` with a `current` file naming the one to start; the launch script starts what `current` names and a flat install otherwise (ADR-0040). Distinct from the host's data folder (`~/.sotto`), which holds its workspace and pairings and which no update touches. Avoid: "install path" in anything a user reads.

**Host update.** This computer putting its own Sotto version on a remote host that runs an older one, when the user presses Update in the pill beside the window controls on the Threads page, at the top right on a Mac (ADR-0040). A host **needs an update** when the version it says it runs is earlier than this computer's; a newer host is left alone. Four steps: download (by the host, or by this computer and copied over SSH when the host cannot reach GitHub), check against the release's checksum, install beside the running version, restart. A busy host asks first and can wait until none of its threads is working. A failure leaves the old version running, or starts it again, and says so. **Not now** hides it until Sotto next starts. A host Sotto did not start is not restarted; its panel offers the commands instead. `src/main/hosts/hostUpdate.ts`. Distinct from the update control, which updates Sotto on this computer, and from a client update (ADR-0042), which updates a provider's client. Avoid: "upgrade", "auto-update", "sync".

**Host version.** One Sotto release unpacked in a host's installation folder, in `versions/<X.Y.Z>/`. A host update keeps the version running and the one before it, and deletes older ones once the new version runs. Distinct from the host protocol's version, which is `v: 1` whatever Sotto version speaks it.

**Device.** A machine Add host lists as one Sotto could connect to, before it is a host. The list is read on this computer when the dialog opens: the other devices on the tailnet from `tailscale status --json` (name, operating system, whether it is online, when it was last seen, and whether Tailscale SSH is on), then the aliases in the SSH configuration and the names in known hosts. A configuration alias whose `HostName` (the alias itself when it has none) is one of a tailnet device's names or addresses is the same device, listed once with both tags, and Sotto connects through the alias so the user's user and key settings apply; a tailnet device with no alias is reached by its MagicDNS name. Devices Sotto can add are under **Can connect**; offline devices, phones and those already saved as hosts are greyed under **Can't use now** with the reason. **Another SSH host…**, always last, swaps the list for typing a host. A device becomes a host only once it is added and paired. `src/main/hosts/tailscale.ts` reads and merges, `src/renderer/src/features/settings/DevicePicker.tsx` lists. Distinct from the iPhone client's **computer**, which is a host the phone is already paired with. Avoid: "peer" and "node" (Tailscale's words), "suggestion" (the SSH setup's entries are now devices).

**Askpass helper.** The small program OpenSSH runs through `SSH_ASKPASS` when it needs a password, a key passphrase or a yes to a new host key. It carries the question to the desktop over a loopback-only socket, the desktop shows it in the Add host dialog, or for a saved host over whichever page is open, and the helper hands the answer back to ssh. An answer is reused for the rest of that connection, so the user answers once per connect. A notice OpenSSH runs it for without asking anything, such as a security key's touch request, is not shown, and a question ssh stops waiting for is taken away. `src/main/hosts/sshAskpass.ts`. Avoid: "SSH prompt handler", "password dialog".

**Host setup checklist.** What Add host becomes once pressed: a line saying what is being added, with Change, and the steps a connect goes through, in order: Reached, Approved in Tailscale (only for a Tailscale approval), Signed in, Host installed, Host started, Paired. The launcher reports which step it is on (`HostStatus.step`); the desktop adds Paired. A failure shows on the step it belongs to, with main's sentence and, where there is one, the exact command that fixes it, which Sotto never runs. Until the host archive carries its own Node (#207), a missing or unsuitable Node counts against Host installed. While a **host setup** runs, the same checklist follows its thread's checks and add: a step that stopped the last check shows why without asking the user to act, and one that passed after an earlier check stopped there reads "by the agent". Distinct from the Phones page's setup rows and from the merge checklist.

**Tailscale approval.** Tailscale SSH in a tailnet policy's `check` mode holding a new SSH connection until the user approves it in a browser; its banner on ssh's stderr names the approval page. While it holds one, the connect waits up to five minutes on the Tailscale step, and Open approval page opens that page, only a `https://login.tailscale.com/` one, from main, on the user's press. The page's address reaches the window and the browser and never a log. An approval that never comes is `tailscale-unapproved`, which only the user can fix, so a saved host stops retrying on it.

**Host setup.** Add host's **Have my agent set this up**: one device, one **host setup thread**, and the check or add that thread ran last, which the dialog's host setup checklist follows (ADR-0035). It is `starting` until the thread has its brief, `running` while it works, and ends `connected`, `stopped` or `failed`; an ended setup stays on the Hosts page until put away. One runs at a time, and not beside a **provider job**: one agent job at a time. It lives in memory: quitting ends it the way Stop setup does. `src/main/hosts/hostSetup.ts`. Distinct from the **host setup checklist**, which is the list of steps both Add it and a host setup show. Avoid: "installer", "wizard", "onboarding".

**Host setup thread.** The normal thread a host setup runs in, named "Set up forge", in the **Host setup** project at Sotto's own `host-setup` folder, sharing that folder rather than taking a worktree. Its first message is the fixed brief, which names the device, its SSH address and folders, a failed step's reason code and the install steps, and never a key. It starts in the permission mode that asks before everything, which is the provider's strictest and still lets the provider's own read-only commands run without asking. Only it gets the **host setup tools**, and only while its setup runs; afterwards it is an ordinary thread that stays until archived. It is started by the user's press, not by the coordinator: it is not managed and sits outside the voice gate (ADR-0012). Avoid: "installer thread", "setup agent".

**Host setup tools.** `sotto_host_setup`, the loopback MCP server a host setup thread or a **provider job**'s thread gets beside `sotto_browser`, on the same transport (`ThreadToolServer`). A host setup thread gets three tools and no others: `host_status`, `host_check` (Add host's own connect as far as the host answering, pairing and saving nothing) and `host_add` (Add host's add, after the user answers "Add forge as a host?" in the thread). A provider job's thread gets two: `provider_status` and `provider_check` (the host's `refresh` for that provider, which is Check again). Each thread lists and may call only its own job's tools, and none takes a target; the device, or the host and provider, is fixed when the job starts. `src/main/hosts/hostSetupTools.ts`. Avoid: "setup API".

**Provider job.** An agent installing, updating or fixing one provider on one connected host, started from that provider's tile with **Have my agent install it** (update it, fix it) (ADR-0035, amended for #461). `install` is for a provider the host did not find, `update` for one older than its **floor**, `fix` for one installed where the host cannot find or start it. It runs as a host setup does: a normal thread on this computer named "Install Devin on forge" in the Host setup project, asking before everything, with a fixed brief that names the host, the provider, what the host reported, where the host looks and the maker's install method, and never a key. It is `starting`, then `running`, and ends `found` once the host finds the provider and can start it, `stopped` on Stop, or `failed`; while it runs the tile reads "Agent is installing it" with Show thread and Stop. It never signs in: at found, the tile offers Sign in. One agent job runs at a time, a host setup or a provider job. `src/main/hosts/hostProviderJob.ts`. Avoid: "installer", "repair wizard", "provider setup".

**Floor (a provider's).** The oldest client a provider's adapter connects, below which a host's tile says **Too old to use** and offers Have my agent update it: Grok Build 1.0.5 and Devin 3000.10.31, the versions their adapters were checked against (ADR-0042), and for Claude Code the set of flags Sotto runs it with, which has no version number. Each is written next to its adapter with its reason. Codex has none. Carried to the tile as `requiredVersion` where it is a version. Avoid: "minimum supported version" in anything a user reads; the tile says "Sotto needs 1.0.5 or later".

**Sotto request.** A request Sotto itself puts in a thread, answered on its request card like a provider's, and never sent to the provider: the coordinator merges it into the thread's requests and hands the answer back to Sotto (`SottoThreadRequests`). Its ID starts with `sotto:`. Only a client that may grant answers one (ADR-0004). The only one is the host setup thread's "Add forge as a host?" (ADR-0035). Avoid: "synthetic request", "fake request".

**Switched on, switched off (a saved host).** Whether this computer keeps a saved remote host connected. On, Sotto connects now and every time it starts, in the background, and a dropped connection reconnects on the backoff until a failure only the user can fix stops it. Off, this computer does not connect: the row and its pairing stay, and a host Sotto started keeps running, since switching off stops nothing on the host; Stop host does that, and switches the host off so the next launch does not start it again. A host is saved only once Add host has connected and paired, and a host saved before the switch existed reads as on (ADR-0025). Avoid: "enabled" in anything a user reads, "disconnected" for off, since a host that is on can be disconnected for a moment.

**Turned off (a host's provider).** A provider the user disconnected through a host, by name or with Disconnect, or left out when changing the enabled set, and has not connected again. A host connects every provider that is installed and signed in on its machine when it starts, except a turned-off one, which stays off across restarts. Recorded as `disconnectedProviders` in the host's coordinator settings, because the enabled set alone cannot tell a provider nobody asked for from one the user turned off (ADR-0036). Distinct from a provider in error, which is not installed or not signed in and is tried again at the next start or on Check again. A provider tile says "Turned off" and offers Connect. Avoid: "switched off", which is a saved host's.

**Provider tile.** One of a connected host's providers under its row in Settings → Hosts, opened with **Show providers**: the provider's mark and name, a state line with a dot, a detail line and its action, which acts on that host alone. Connected (with what it is signed in with and its version) offers Disconnect; turned off offers Connect; not signed in offers Sign in, or, for Devin, the command to run on the host; not installed, too old or can't be started offers Have my agent install it (update it, fix it), which starts a **provider job**, beside Check again, which is the host's `refresh` for that provider and tries a provider in error again. While a provider job works on it, the tile says so, with Show thread and Stop. A connected client that is behind says what is available, with Update beside Disconnect, and the chip beside Show providers opens Update all for the host (ADR-0042, September 29 amendment). `src/renderer/src/features/settings/HostProviders.tsx` (ADR-0037). Distinct from Settings → Providers, which is this computer's. Avoid: "provider card", "switched off" on a tile.

**Provider problem.** Why a provider is not connected, as a code its adapter names where it finds it: `not-installed`, `too-old`, `signed-out` or `cannot-start`. It rides on the provider's status beside the sentence in `error`, and a provider tile decides on the code, never on the sentence; an error without one reads as can't be started (ADR-0037). Avoid: "status" for this, which is the whole connection state.

**Host sign-in.** A provider's own sign-in run on a host for the paired client that asked, and finished by the user in that client's browser: a device code shown in the dialog for Codex and Grok Build, which their clients finish by themselves, or a code pasted back for Claude Code, which Sotto hands to the client and keeps nothing of. The page's address and the codes live in the host's memory for that client only, never in a log or on disk, and go when it ends or after 15 minutes. Sotto opens only the provider's own sign-in page, from main, on the user's press. `src/host/providerSignIn.ts`, the `provider-sign-in` host feature (ADR-0037). Avoid: "remote login", "auth flow".

**Host for new work.** The host a new thread or a new project goes to when nothing else names one: the router's selected host. New thread and Add project set it when they add a folder as a project on the host chosen there; opening a thread or project also moves it to that thread's host. A thread's own host never changes once the thread exists. Avoid: "active host", "current host".

**Host lock.** `host-listener.lock` in a host's data folder, which keeps a second host from opening the same stores. It holds the lease of the host that owns the folder: its process, a nonce and the machine's boot identity. The next start reclaims a lock whose process has ended, or that was written before the machine last restarted, and does it atomically: starting hosts take turns to clear a stale lock through `host-listener.lock.reclaim`, so however many start together, only one owns the folder. A lock whose process still runs, even one another account owns, is refused and the refusal names that process. `src/host/lock.ts` (ADR-0025). Avoid: "pidfile", "lease" for the file itself.

**Remote command.** A command a paired client may send over the socket. The list in `src/host/remoteCommands.ts` is closed: a new command or field is refused remotely until it is added on purpose. Commands that change what a thread may do unasked (a runtime mode other than asking first, a provider mode whose allowance is more than nothing) or discard uncommitted work need the same `remote-answer` policy record an answer does; a setting that grants nothing is free, so a paired device can always put a thread back to asking (ADR-0025). Avoid: "remote API".

**Host protocol.** What a client and a host exchange over HTTP and the socket, listed message by message in `docs/host-protocol.md`. Its version is `v: 1` on every message and is separate from the Sotto version; version 1 is frozen and grows only by optional fields, host features and push forms a client asks for (ADR-0025). Avoid: "API", "wire format" as a name for it.

**Host feature.** A named part of the host protocol beyond version 1's base, such as `detail-delta`, which a host lists in `features` in its health, its listener file and its hello reply. A client uses one only when the host lists it and asks for a push form by naming it in hello's `accepts`. A host with no feature list predates the freeze, and the desktop asks the user to install this computer's version of the host, stop it and connect again. Distinct from hello's `capabilities`, which is what this client may do on this host, and from a provider's capabilities in the shell. Avoid: "capability" for this.

## Personal conversations

**Personal chat.** A saved, project-free conversation with Sotto's configured coordinator, distinct from a project-bound thread. A started personal chat stays with its original provider; changing coordinator defaults affects new chats only. Every provider with a saved chat, plus the coordinator's own provider, connects at launch without the user pressing Connect; a drop the user did not ask for reconnects by itself after five seconds, then after longer waits, and after five failed tries the error waits for Connect. Pressing Disconnect holds every provider off until Connect or a restart. A Claude Code chat refreshes changed retrieved preferences by starting its client again. While background work runs, messages continue on the existing client with its previous context; the first send after that work ends starts the client again with the latest context. Deleting a memory in the running client's context forces that restart on the next send and stops background work. Avoid: "project thread", "global project".

**Personal chat ID.** The durable Sotto-owned identity of one personal chat, independent of its provider session and of every project thread. Selecting or resuming it grants no management, delegation or project-creation authority.

## Coordination

**Coordinator.** The default reasoning agent Sotto uses for deep reasoning and managing assigned threads. Its account, model and reasoning effort are independent of the providers and models running those threads. Avoid: "thread provider" when referring to Sotto's reasoning agent.

**Pending setting.** An option chip's choice the thread's provider has not confirmed yet in the state the window draws. The chip shows it from the press, but the setting in force is still the provider's last confirmed one, and for permissions that is what decides its next tool call. So a pending permission is marked on its chip, a dashed edge in the activity colour and a small dot that holds still under reduced motion, and a caption beside the chips says what is still in force in the provider's name and the mode's own terms: "Claude Code still asks for approval until it confirms." A pending model or effort carries no mark. It ends when the window draws the provider's answer, not when the reply lands (#306), or when the provider refuses, which puts the chip back and says so under the composer's row with Try again. A change the provider never gave a result for stays pending, marked the same way: main keeps it for the thread's next start and takes no other action on the thread until it knows, so the chips are fixed and the line under the row says what happened and what comes next, with nothing to press, until the thread shows the choice or main lets it go. A prompt sent meanwhile runs on the pending setting: main's thread lane runs the change first. Avoid: "saving", "optimistic".

**Assignment.** Sotto's authority to reply automatically on a thread. Modes are `managed` (Sotto may send follow-ups within its limits) and `manual` (the user replied in the provider directly, so Sotto only watches). Selecting or reading a thread never creates an assignment. Avoid: "subscription", "watch".

**Assignment facts.** What the coordinator records on an assignment so the app can say how it started and why it stopped: `startedAt`, `origin` (`voice`, `typed` or `unknown`), `stopReason` (`none`, `limit`, `repeat` or `error`) and `stoppedAt`. A takeover clears the stop facts; a save failure only stamps `error` when nothing else stopped the assignment first.

**Threads page.** The management-window view that lists threads across Sotto's providers, including retained threads whose provider is disconnected. A thread's messages and pending decisions stay with its original provider. Avoid: "inbox", "dashboard".

**Allowance.** What a Devin thread's owned profile lets Devin do without asking: nothing, edits, or everything. Sotto writes it and reads it back, so it is what decides whether a permission request reaches the user. It carries out the permission mode the user chose; it is not an ADR-0004 policy record and is never a grant of authority. A provider's own conversation mode is set alongside the allowance and never stands in for one: a mode named for not asking says what the provider will not ask itself about, not what Sotto will stop asking (ADR-0022). Avoid: "grant", which is ADR-0004's word; "permission level"; "mode" for the allowance.

**Needs you (iPhone client).** A thread's question or permission waiting on the user, shown first on Threads under the heading **Needs you** and counted on that tab, including requests in settled threads; it is no longer a separate page. Each card is tagged **Question** or **Permission**, and one with one-tap choices can be answered on the card (ADR-0051). These are the thread's own pending requests, with or without an assignment, rather than the attention queue. Avoid: "inbox", "notifications".


**Computer (iPhone client).** A machine the iPhone client is paired with: a desktop running Sotto or a host without a screen, one pairing each. The app shows every computer's threads together and names each thread's computer, which shares only its own threads. A computer is named by the `name` in its health, which the desktop and a headless host's phone listener send, else by its machine name on the tailnet, and can be renamed on the iPhone alone. A new thread chooses its computer first, then a project already there or an existing folder to register, then that computer’s ready model and options. The thread remains manual and uses the shared project folder, or a new worktree when chosen. Folder browsing reads that computer’s directory names, not file contents; filtering narrows one directory. The word is the phone's user-facing name for a **host** reached as a whole machine; inside the code the same thing is a host ID. While the app is active, a dropped connection reconnects with waits increasing from one to thirty seconds; a new session refreshes state and reconciles unconfirmed actions without replaying them. Backgrounding stops retries, and returning connects again. The iPhone calls the desktop a host without a screen is reached from **your main computer**, since that is where its phone access is turned on (ADR-0050). Avoid: "host" or "server" in anything the iPhone shows.

**Attention queue.** The coordinator's ordered list of the threads with an assignment that need the user: a thread is `ready` for a prompt, has a `question`, has a `permission` request, or is `blocked`. It orders what the coordinator presents and says; it is not where a thread's waiting is recorded. A thread with no assignment never enters it, and neither does a question supervision is still deciding; the sidebar row and composer still say the thread waits on you from its own pending requests. Permissions are never answered automatically and are never inferred. Avoid: "inbox", "notifications".

**Draft.** An unsent prompt or answer, including its attachments, owned by a thread or personal chat and optionally a question request. Each conversation retains its own drafts across navigation and restart. Sending ends a draft: the press starts a fresh empty revision, and what was sent is a sent message from then on. Accepting one submitted revision never clears a newer revision.

**Screenshot bound.** The longest edge, 2576 pixels, that any model Sotto sends screenshots to reads: Claude 4.7 and later downscale to it, and Codex to 2048. The composer scales a screenshot past it down to it, in the same format, before it joins the draft, and so does browser feedback. Its chip says **Resized from** the size before **to** the sent size under the name. The attachment keeps its original and sent sizes, never its old pixels. Nothing is scaled up, a GIF, an animated PNG or WebP, or an image past 16384 x 16384 pixels in area is never scaled, and a copy that would not be smaller in bytes is not used (ADR-0030). Avoid: "thumbnail", "compression".

**Staged image.** An image attached to a draft, whose bytes the host that runs the thread has kept once in its attachment store, and which everything else names by its handle: an ID, the file name, the type, the size and the SHA-256 digest of the content (ADR-0031). Drafts, queued follow-ups, commands, the outbox, the shell and every broadcast carry the handle; the bytes are read only to draw a chip the window has no thumbnail for, to show a sent message's preview, and by the adapter as it hands the image to the provider. The store keeps one file per content under `attachments/` in the host's data folder, with an index of digest, type, size and staging time, and keeps it while a draft, a queued follow-up, a send whose result is unknown or a preview names it, then an hour more. With history off, a newly staged image is kept in memory only. The iPhone client stages the photos it attaches to a reply the same way, made ready on the phone first and staged again before it sends one its computer may have let go (ADR-0031, October 3 amendment). Avoid: "attachment" alone for the bytes, "upload".

**Sent message.** What the user sent from this window, drawn in the transcript where it will be read from the press onwards, with the state of its delivery beside it: queued, sending, unconfirmed or not sent. The iPhone client draws a reply, answer or stop the same way: sending while its computer has not answered or says it is still carrying it out, and unconfirmed, with Check again, only when it cannot say. It becomes an ordinary message when the provider's own history carries it. A refused one comes back to an empty composer, or is offered back when something newer is written there; an unconfirmed one stays in its message, because Sotto will not send it twice. Avoid: "optimistic message", "ghost message".

**Delivery receipt.** Main's record that one draft of a thread was accepted, by thread ID and draft ID: sent to its provider (`deliveredDrafts`) or taken into its follow-up queue (`followupReceipts`). The composer and transcript read it to stop showing that draft as unsent, and main reads it to refuse sending the same draft twice. Distinct from a command receipt, which is main's answer to one command. Avoid: "receipt" alone.

**Answer draft.** Saved choices and text for a particular provider question in its original conversation, recoverable even if the provider closes or changes that question. Retaining or copying an answer does not recreate the question, confirm delivery, or grant authority to send it.

**Follow-up queue.** The ordered messages the user has prepared for a thread after its current provider turn, editable or removable until dispatch. It is distinct from the attention queue and the outbox of already-dispatched commands.

**Steering.** The user's explicit submission of new input to a provider's current running turn through a supported native mechanism. It does not imply permission to cancel the turn or start a replacement conversation.

**Option chips.** The three controls in the composer footer that say what a thread is set to: the model, with its provider's mark, the reasoning effort and the permissions. Each is one chip that opens its own picker above the composer, so the typed text and the send disc stay where they were. The model's menu is two columns: a rail of provider marks down the left, one tile each and no names, so a provider costs the same room whatever it is called and its name is the tile's accessible name and tooltip; and on the right that provider's models under a search line, with the reminder that any provider is still a choice on a thread before its first message. Once the thread has sent, the list holds its own provider's models alone and there is no rail. A model is listed under the fullest name the provider gives it, version and all, and the one the provider recommends stays at the top of its list. A thread or a Settings default on a long-context variant the provider no longer lists, such as Claude Code's `opus[1m]` beside `opus`, is on that base model: it shows under the base model's name alone, with its efforts and image support, and keeps its own ID for the provider, so pressing the base model's entry again leaves it where it is. The effort chip opens the effort card: the level word and one line saying what the level costs, Default when the model reports one, and a pill track with a stop per level. Dragging previews and settles on a stop; release chooses, and the wheel, arrows, Home, End and the digits step. Every chip shows a choice from the press itself — for effort the word, the chip, the composer's outline and the arrival — while the save runs behind it, and no chip waits on a save or goes dead for one; a choice made while a save is in flight waits, and only the last is sent. The provider is still authoritative: the value it answers with is what remains, so a change it refuses takes the press back and says so under the chips, with Try again. A permission choice is a **pending setting** until the provider confirms it. At the model's highest level the word, the chip and the composer take the effort color, and reaching it plays the arrival once (ADR-0019). Claude prompts can add a visible `ultrathink` instruction for that prompt; this does not change the saved effort or permissions. The effort levels and permission list come from the provider: Claude Code reports its effort levels at initialize, so a level it does not report cannot be offered. A provider whose permission modes are its own rather than Sotto's four lists those instead, each with the one sentence saying what Sotto will still ask about under it. New terminal shows the same three controls laid out in full; New thread opens on its defaults with no such form, and Settings → Agents' "New threads start with" row holds the same chips for those defaults. Avoid: "pill" or "Thread options" for the row.

**Turn.** One coordinator action from start to finish: a spoken utterance, a typed command, or an automatic follow-up sent by supervision. Every turn is recorded.

**Turn record.** One JSON line in `turns.jsonl` in the user data folder, written by the turn recorder when a turn finishes: source (`utterance`, `command` or `supervision`), the Sotto thread ID and project the turn acted on, the provider session resolved from the thread registry, timings (intent, retrieval, delegation, total; speech-to-intent and speech-to-first-feedback once the voice pipeline supplies an end-of-speech time), retrieved memory IDs, a context-token estimate, the outcome (`completed`, `clarified`, `failed`) and a fixed failure code (`action-failed`, `reasoning-failed`, `provider-failed`, `storage-failed`, or `unknown` for older failures) without prompt, answer or error text, regardless of Keep local history. Existing records are scrubbed once when the recorder starts; malformed records are discarded. Compaction retains at most 1000 newest records and drops the oldest until below half the 2 MiB cap. Draft edits are not turns. Avoid: "trace", "log entry".

**Thread lane.** The order the coordinator runs one thread's own commands in. A command that names a thread and acts only on that thread — a prompt, a steer, an answer, thread options, compaction, settling and restoring, working-copy actions — runs in that thread's lane, so it waits only for earlier work on the same thread. Commands with no thread, and those that move assignment authority, the composer draft or a whole project, keep the single global lane, which is what the published `globalLaneBusy` mark stands for; the threads whose own lanes are running are published beside it as `busyThreadIds`. Every surface that shows one thread reads that thread's mark, so work on one thread never dims or locks another's pane; the provider and configuration surfaces read the global one. The window keeps the same split: it sends a thread's lane commands, and Stop, to main at once, and holds only global-lane commands behind the reply to the one before, so it never makes one thread wait on another before main has heard of it. Both read one list, `THREAD_SCOPED_COMMAND_TYPES` in `src/shared/threadLanes.ts`; beside it, `LANELESS_THREAD_COMMAND_TYPES` names Stop and the other thread commands main answers before it chooses any lane, which the window sends at once as well. Avoid: "queue" for a lane, "busy" on its own for either mark.

**Outbox.** Durable intent for a dispatched command whose acknowledgement may be lost. Sotto reconciles outbox items against the next status rather than resending. A thread settings change is reconciled by the snapshot its adapter hands back when the provider confirms it; its entry leaves the disk with the next write.

## Speech

**Wake phrase.** "Hey Sotto". Bare "Sotto" is not a wake phrase.

**Voice coordinator (hidden).** Everything that speaks, listens for the wake phrase or hands a thread to Sotto: the wake session, the Agents room, spoken hints, the widget's microphone and speech controls, the voice settings, a personal chat's Talk controls, and Manage, Pause managing, Resume managing and Stop managing. All of it is hidden for the beta behind `voiceCoordinatorEnabled` in settings, which defaults to false; the renderer asks `useVoiceCoordinatorEnabled()` and the floating widget is told through the snapshot's `voiceCoordinator` field. Nothing is deleted, and dictation never depended on it (ADR-0012).

**Utterance.** One transcribed spoken command handled by the coordinator.

**Transcription.** Turning dictated audio into text. Since ADR-0006 there is exactly one route: each segment is encoded as a 16 kHz mono PCM16 WAV and sent from the main process to Microsoft MAI-Transcribe-2 through OpenRouter's transcription endpoint with the user's OpenRouter key. Nothing is transcribed on this computer and there is no fallback route; a failed request is reported with its reason. Avoid: "local model", "preset", "transcription server", "remote ASR".

**Transcription failure.** Why a transcription request came back without text, and what the user is told. Each reason has its own widget title and sentence: no key (API key needed), a rejected key (API key rejected), no connection or a deadline (Connection unavailable), no credit on the key (Out of credit, HTTP 402), rate limited (Too many requests, 429), any other HTTP error, 5xx after its one retry (OpenRouter error), and an unreadable answer (Couldn't transcribe). Every sentence says the recording was not kept, because dictation audio never is. Main appends each failure except a user's cancel to `transcription-diagnostics.jsonl` beside `polish-diagnostics.jsonl`: when the request started, reason, the last attempt's HTTP status, attempts, clip length and time taken, and never words, audio or the key. Avoid: "error log", "crash report".

**OpenRouter key.** The one API key the user supplies, stored encrypted in the operating system credential store under the `formatting` slot and never returned to the renderer. It pays for transcription, the cleanup pass and any OpenRouter-hosted reasoning. In settings code it is still the `llmApiKey` field.

**Personal dictionary.** The user's list of names and terms, one per line (`llmDictionary`), up to 4,000 characters. Its draft saves when the field loses focus or Settings is left. It is sent with every transcription request as an Azure phrase list so MAI spells those words as written, and it is also quoted in the cleanup prompt. Avoid: "vocabulary hints" in user-facing text.

**Cleanup pass.** The optional LLM pass over the finished transcript (punctuation, fillers, self-corrections, lists), run through OpenRouter chat completions at the chosen quality tier and skipped for very short transcripts. Audio never goes through it. Avoid: "polish" in user-facing text (the code still says `polish`).

**Segment.** One slice of a dictation, cut at a pause while streaming transcription is on, transcribed as its own request so the final text is ready almost as soon as the user stops. Avoid: "chunk".

Pressing Stop or the dictation shortcut again while the microphone is connecting cancels the session as soon as the microphone is ready. No audio is kept or transcribed.

## Memory

**Memory.** One remembered fact about the user, a project or the world, with the metadata the spec requires: type, scope, content, source class (explicit, observed, inferred, imported, agent-confirmed), confidence, evidence count, importance, temporal fields (created, last confirmed, last used, valid from, valid to), provenance, tags, state (active, superseded, disputed, temporary, archived) and authority (preference, policy, permission). Avoid: "fact", "note", "record".

**Memory store.** The SQLite database `memory.sqlite` in the user data folder, the single source of truth for accepted memories. It is opened by Node's built-in `node:sqlite` in the packaged Electron runtime, without another production dependency, and it carries a full-text index for lexical retrieval. Search honours a memory's validity window and includes temporary memories that are current. See ADR-0003.

**Provenance.** Where a memory came from: a Sotto thread and reference, or a dated questionnaire answer or inspector correction. Questionnaire and inspector provenance do not invent a thread; provenance never carries a provider session ID.

**Working preferences.** The user's explicit answers about communication, autonomy, verification, git and review, agent choices, workflow and privacy. They guide coordinator replies without granting permissions or changing history settings.

**Retrieved preferences.** Current explicit memories relevant to the coordinator's question, drawn from the current thread, its project and global scope in that order. Irrelevant memories are omitted; retrieved preferences provide context, never authority.

**Memory inspector.** The Memory page where the user sees remembered content, its provenance and history, and can correct, supersede or delete it. Corrections retain earlier versions; deleting a memory removes its full chain of versions.

**Memory (hidden).** The Memory page and its link, the questionnaire that greets the Agents room, and the preferences a turn would retrieve from the store are all hidden for the beta behind `memoryEnabled` in settings, which defaults to false; the renderer asks `useMemoryEnabled()` and the main process reads the setting once at start and hands neither the agent control nor the personal chats a preferences source. The store still opens and its IPC stays registered, and nothing is deleted (ADR-0013).

**Memory store probe.** The check that proves the shipped build can use the store: the packaged executable is launched in an isolated profile and its debugger invokes the bundled probe, which opens the real memory store in a temporary user-data folder, migrates, inserts, answers a full-text query and returns its evidence. The unused environment probe launch mode has been removed. The packaged-resource verifier fails the build without it. A direct Node-only probe (`scripts/probe-memory-store.mjs`) exists for the Mac runtime check.

## Authority

**Policy record.** One row in the `policies` table of the memory store that carries authority: an action (`spend`, `publish`, `destroy`, `relax-verification`), a resource (`*` or a specific path, repository or provider), a scope (`global` or a project id), an effect (`allow` or `always-confirm`), a source (`user` or `questionnaire`), a note, and granted, expiry and revocation times. Policy records are the only thing that can authorize a risky action; a memory whose authority field says `permission` is evidence, never a grant. An `always-confirm` record beats any `allow`; expired or revoked records never allow. See ADR-0004. Avoid: "permission memory", "rule".

**Risky action.** A permission approval that the coordinator classifies from the request text as spending, publishing, destroying or relaxing verification. A request can carry several classes. Dispatch of a risky action consults policy before the provider sees the answer: supervision never answers a permission request, and the user's explicit Allow is the confirmation an `always-confirm` boundary requires. Avoid: "dangerous command", "privileged op".

**Risk boundary.** An action the user says Sotto must always confirm, captured by the questionnaire and stored as `always-confirm` policy records with source `questionnaire`, never as inferred memory.

**Approval surface.** The place a provider client sends the requests only a person can answer. Sotto claims it at launch, per thread, in every runtime mode, and a client that does not grant it answers those requests itself: Claude Code denies them and withholds its question tool, so a thread keeps working while nothing reaches the user. Because that looks exactly like a model choosing not to ask, an adapter that finds the surface missing, or that receives a request for the user it cannot read, says so on the provider instead of staying quiet. See ADR-0043. Avoid: "permission channel", "prompt host".

## Memory evaluation

**SottoMemEval.** The product-specific memory benchmark in `scripts/memeval/`: labelled memory cases run against a pluggable backend, scored per category (recall, abstention, temporal adaptation, temporary exception, project leak, authority leak), printed as a table and saved with the backend name and case-set version. Run it with `npm run memeval`.

**Case.** One labelled scenario in a case set: a short history of provider events, a question asked as of a date and a project, and the expected outcome (an answer pattern, an abstention, or a forbidden leak pattern). Cases carry a `draft` or `reviewed` status until the founder has checked them. Avoid: "sample", "example".

**Case set.** A versioned file of cases (`scripts/memeval/cases/v1.json`). Results always name the case-set version they were scored against.

**Backend.** The memory system under test in SottoMemEval: it observes history events and answers questions, and never sees ground-truth labels. The `none` backend remembers nothing and always abstains; it is the required baseline. This is the one place "backend" is the right word; a provider adapter is never a backend.

## Main window

**Crossing.** The main window's shell since redesign round 3: one room under a thin strip, set in Figtree. It is dark by default and can be light; see Appearance and Theme. The floating widget keeps its own look.

**Appearance.** The main window's mode setting: System, Light or Dark. Dark is the default for new and upgraded installs (ADR-0009). System follows the operating system's scheme live. The `theme` setting is the floating widget's mode, not a Theme. Avoid: "theme" for the mode.

**Theme.** A named palette of colour roles (background, text, accent, sidebar, terminal and so on) in the T3 Code file format: one of the six built-ins, all Sotto's own (Sotto, Hush, Linen, Nocturne, Tropic, Citrine), or a custom theme the user created, duplicated or imported (ADR-0011, ADR-0024). A theme has a light variant, a dark variant or both. The iPhone client offers the six built-ins, generated from these definitions and chosen on the phone alone (ADR-0051). The selected palettes also colour the Sotto mark, the voice sphere and the floating widget, except that on the default theme the mark is the app icon itself. The widget still resolves its own mode from the system. Avoid: "accent" for the palette; the accent chooser is gone.

**Light half, dark half.** The two theme selections, `lightTheme` and `darkTheme`: the theme that paints the window when it resolves to Light, and the one for Dark. They are chosen independently, in the Light and Dark columns of Settings → Appearance, and both start on Sotto. The column for the mode the window is in says it is painting the window now.

**Ink.** Sotto's own dark half: an almost-black room for the thread beside a lighter graphite sidebar, with the app icon's teal as the accent. Not a separate theme; it is the dark variant of the Sotto theme.

**App icon brand.** How the Sotto mark looks on the default theme: the icon's own teal tile (`#47b8a9`) and black glyph in both halves, whatever the half's accent. Both windows mark the root `data-brand="app-icon"` when the default theme paints it; on any other theme the mark takes that theme's accent (ADR-0024).

**Contrast and Glass.** The two appearance sliders. Contrast (50-200%) strengthens or softens text and borders against the theme's own background. Glass (40-100%) sets how solid dialogs, menus and floating panels are over the blurred room.

**Frosted window.** The appearance switch that lets the desktop show through the main window, blurred by the system's own material: acrylic on Windows 11 22H2 and later, vibrancy on macOS (ADR-0048). It works with any theme. See-through (10-80%) sets how much of the desktop shows through the room; the sidebar stays a little more solid, a pane's Terminal drawer more solid again, and messages, the composer, dialogs and menus keep their own surfaces. Windows draws it solid while another window is in front. It is off by default, the widget is never frosted, and a system set to reduce transparency keeps the window solid. Avoid: "transparent theme" (it is not a theme), "Glass" for this (Glass is the floating surfaces over the room).

**Effort color.** The colourway a thread's effort control turns at a model's highest level: one of Ember, Cyberpunk, Rainbow, Aurora, Plasma or Theme accent, chosen on Settings → Appearance and painted on the window root as `data-effort-color` (ADR-0019). It colours the card's fill and tinted word, the effort chip, and the composer's outline and arrival. Ember and Theme accent come from theme roles; the other four are fixed palettes no theme carries, the one place the main window's colour does not come from the theme. Avoid: "effort theme"; a theme is a palette of roles, and this is one choice across all of them.

**Highest level.** The last effort level in Sotto's order, whatever it is called (Max on Claude Code, Ultra on GPT-6 Astra). Sotto lists a model's levels least to most thorough; Codex and Claude Code report them that way, and Grok's own list, which runs highest first, is turned round (ADR-0044). A model that reports one level has no highest level. The composer wears the effort color's outline while a thread sits there, and the arrival is what plays on reaching it from below: a tide of the colourway through the card and the composer, the letters of the level taking the colour in turn while the word lifts and settles as one, both borders tinting and fading. Reduced motion shows the settled state. Avoid: "max" or "gold" for the state; the name belongs to the level, and the colour is the user's.

**Theme editor.** The floating panel that creates or edits a custom theme and paints it live over the saved look until Save or Cancel. Pick app color (the inspector) chooses a colour role by pointing at the page; a role's label spotlights everywhere it is used.

**Strip.** The top bar of the main window on the pages that still wear one, Agents and Memory (both behind their beta gates) and onboarding: the Sotto mark on the left, the switch in the centre, the window controls on the right. It is the window's drag region. Every other page has the sidebar top row instead. The Threads page owns the whole window, with the sidebar's top row and the pane header as its drag regions and the window controls once at the top right. Dictate, History and Help seat the Threads sidebar beside the room, with a thin drag strip above the room carrying the window controls. Settings and Chats give their own left column the sidebar top row and the sidebar foot, and carry the window controls at the top right the way Threads does.

**Sidebar width.** The remembered space the user gives the Threads sidebar, shared with Terminal mode and with the same sidebar beside Dictate, History and Help. Collapsing it leaves a narrow rail for threads and page links; expanding it restores the chosen width, while Settings keeps its own column. The Chats list has a width and a collapse of its own, remembered apart from this one; collapsed, it is a rail with one provider mark per chat.

**Sidebar top row.** The first row of the Threads sidebar, and of the Settings and Chats columns: the Sotto mark with the wordmark "Sotto" beside it, then, in the Threads sidebar only, the Threads | Terminal control, Add project and New thread. The Threads sidebar and the Chats column end it with Collapse sidebar. It is a drag region. On macOS it is inset and drops the wordmark, to leave the traffic lights their place.

**Sidebar foot.** The bottom of the Threads sidebar, and of the Settings and Chats columns: the switch, the page links as icons (Chats, History, Settings, Help, and Memory while memory is switched on) and the update control. Every page without a strip has one, so the way to any page is the same from any page.

**Switch.** The two-state control that flips the room between Dictate and Threads. It is a tablist; arrow keys move between the two. Dictate is lit on the Dictate room, Threads for the threads, chats and memory pages, and neither on History, Settings and Help. It sits in the sidebar foot beside the page links, and in the strip on the pages that still wear one. Both places offer the same rooms: while the voice coordinator setting is on, Agents joins as a third state in each. The room keeps its place in the shell tree across the layouts, so switching pages never remounts what is inside it. Avoid: "tabs" in prose; "Agents" for the second state.

**Room.** The single content area beside the sidebar, or under the strip where a page still wears one. The switch chooses the Dictate room or the Threads page, and Threads is the page the application opens on; the page links open the others (Chats, History, Settings, Help, and Memory while memory is switched on) in the same area. Those links are icons in the sidebar foot; only a page under a strip lists them in a footer.

**Dictate room.** The Dictate side of the switch: the large seven-bar wave, one sentence for the current state, one button with the shortcut, then the last transcript at reading size with Copy.

**Footer status.** The one-line status text supplied by whichever page is open (for example the model and paste mode in the Dictate room, or whether History still holds older transcripts once it is off). Beside the sidebar it sits in a thin foot under the room; on Settings and Chats it sits in the room's bottom-right corner; under a strip it sits on the right of the footer links. The Threads page has no footer status; a thread says what it is doing in its own row and pane.

**Update control.** The small round button at the end of the sidebar foot, or at the far right of the footer under a strip, the one place the updater shows itself in the window. Idle it offers a check; when a release is found it wears a download glyph, a progress ring while the installer downloads, and a restart glyph once the installer is on disk. Its accessible name says exactly what a press does. A press that downloads or fails gets a toast; a press that installs asks first, because the restart interrupts dictation and agent work. Automatic checks run fifteen seconds after launch and every four minutes, only on the installed Windows app and only while the setting allows and no download is in progress or ready to install, and never install anything on quit. "Check for Updates…" in the tray menu (and the macOS application menu) presses the control from outside the window.

## Subagents

**Subagent.** A child agent reported by a thread's provider. It belongs to its parent thread and has an observational identity; it is not a Sotto thread or a target for commands.

**Subagent roster.** The thread's retained list of reported subagents, shown in Tools under Agents. It includes finished agents and follows Tools' selected or pinned thread.

**Workflow page.** One Claude Code workflow's run and its agents, opened in place of the subagent roster by pressing the workflow's row. The roster shows a workflow as one row with a strip and a count of its agents; the page lists each agent as a row of its own. **All agents**, or Escape, returns to the roster. Like the roster it only observes: nothing on it acts on an agent.

**Subagent transcript.** The file Claude Code writes for a subagent it runs as its own session, beside the parent thread's transcript. Sotto reads only the model named on its first reply, for a roster row the stream left without one; the task and replies in it are never kept. Not the thread's own transcript, which Sotto reads for messages and activity.

**Subagent assignment.** One task given to a subagent, with the result it reported. A reused subagent keeps its identity and earlier tasks; unlike a coordinator assignment, a subagent assignment grants Sotto no authority.

**Last seen working.** A subagent whose last known work has not been confirmed after a disconnect or restart. It is evidence of earlier activity, not a claim that the agent is running now.

**Alert (iPhone client).** A local notification the iPhone shows when a thread needs the user, finishes, or stops with an error, each turned on in Settings, which uses iOS's own heading Notifications for them. Alerts are off until the user turns one on, arrive only while Sotto is open, never for the thread on screen, and carry the thread's title and a plain line saying what happened and on which computer; nothing goes through a push service (ADR-0051). Avoid: "push", "notification" for the Needs you section.

**Step (iPhone client).** One thing the agent did, as the phone's thread page shows it between messages: a file read or changed, a command and how long it took, its reasoning. It is an activity record (an **activity summary** on the wire), placed by when it started among messages placed by when they were sent, and the one running now ticks at the end. It replaced the phone's separate Activity tab (ADR-0051). Avoid: "event", "log line".

**Wash (iPhone client).** The soft colour at the top of a phone page, mixed from the chosen theme's accent, that scrolls away with the page. It warms while a thread needs the user and leans to the danger colour on a failed thread's page (ADR-0051). Avoid: "gradient", "header background".
