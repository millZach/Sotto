# Settings > Hosts says how each host is connected

October 6, 2026. Plan `docs/plans/host-tailnet-connection.md`, pull request 5, on `feat/host-connection-ui`, after the tailnet connection (pull request 4, #783) merged into `main`. The spec ran again on the branch once `main` was merged in, and its captures matched those below but for the time of day. The decision is [ADR-0053](../adr/0053-a-desktop-reaches-a-host-over-its-tailnet-first.md), "What the owner sees", and its October 6 amendment, "Settings > Hosts as built". The look is the prototype's pick, variant C with A's controls (`docs/prototypes/host-tailnet-prototype.html`).

## What was run

`tests/e2e/host-tailnet.spec.ts` in the built app on Windows, with reduced motion on. The scripted ssh (`tests/fixtures/fakeSsh.mjs`, `run` mode) runs the real launch script on this computer against a real headless host built from `tests/fixtures/e2eSshHost.ts`, under a throwaway home. The host's Tailscale is the end-to-end stand-in, running, and a loopback proxy (`tests/fixtures/serveStandIn.ts`) stands in for Tailscale Serve in front of the host's tailnet listener, at the address `SOTTO_E2E_TAILNET_MAP` gives `forge.tail5728ca.ts.net`. The second journey starts with the stand-in refusing Serve to an account that is not Tailscale's operator (`serve: "denied"` in its `e2e-tailscale.json`), as Linux does.

1. Add forge with **Add it**, from the keyboard: the device list's last entry, the SSH host field, and Enter. The checklist ends with the tailnet step, which turns on forge's tailnet connections and meets the refused Serve. forge is added and connected over SSH. The title reads "forge is connected over SSH", the last step reads **Could not reach forge over your tailnet** with the operator's sentence and `sudo tailscale set --operator=$USER` with **Copy**, and the card below says forge is added and connected over SSH. The card's start at boot line (ADR-0054, already in `main`) says this host has no systemd user manager, since the end-to-end host runs on Windows. Focus is on **Done**, beside **Use SSH only** and **Try again**.
2. The stand-in lets Serve through, as it would once the command was run on forge. **Try again** chooses the tailnet again: the host sets up its Serve again, the socket moves to the tailnet, the title becomes "forge is connected", the step reads **Reached forge over your tailnet** with `https://forge.tail5728ca.ts.net:8443` under it, and the card says forge is added and connected over your tailnet. Focus is back on **Done**, and Enter closes the dialog. The row reads "Tailnet · Connected".
3. **More**, then **Edit connection**, from the keyboard. **How Sotto connects** has **Over your tailnet, SSH when it can't** checked and focused, and its description is the address, when this computer last reached forge there, and that it turns on Tailscale Serve on forge, on your tailnet only. The SSH fields sit under **SSH (for setup, updates and phones)**. ArrowDown checks **SSH only**; **Save connection** turns forge's tailnet connections off and moves it to SSH, and the row reads "SSH forge · Connected", with no reason under it. Choosing the tailnet again and saving moves it back: "Tailnet · Connected".
4. Sotto quits and starts again, and every SSH sign-in is held for Tailscale's approval (`run+tailscale`). forge's **Phones…** reads the host over an admin connection: the dialog says it is waiting for your approval in Tailscale, with **Open approval page** and **Why Tailscale asks**, and lists **Let phones reach forge** ("Not read yet. The switch shows once Sotto reaches forge over SSH."), **Tailscale on forge**, **Tailscale Serve on port 8443** and **Paired phones** as waiting. There is no switch. Escape closes it.

Each of the four states was captured at 1600×1000, 1280×800 and 820×560, dark and light. At every size nothing scrolls sideways, and the press each state is about (**Done**, **Save connection** and the tailnet choice, **Open approval page**) sits wholly inside the window once scrolled to. The first journey in the same spec ran too, and its captures of the row on the tailnet show "Tailnet" in the text's colour. This was a Playwright run, not a hand test.

## What the tests cover that the app run does not

- The Hosts page (`tests/unit/renderer/hostsSettings.test.tsx`): the tailnet step under way after Paired, with every step before it done and no **Change**; done, with the address and the card; kept on SSH with each reason's sentence, **Try again** sending `set-connection` for the tailnet and following what main then reports, a Try again the host refuses saying why on the step, and **Use SSH only** sending `set-connection` for SSH and closing; Edit connection's radios moving with the arrows, the tailnet choice's description, a save that changes only the choice sending `set-connection` and nothing else, a save that changes the route sending `set-connection` and then `save`, and no choice for a host never paired; Rename saying how Sotto connects does not change; the row's connection in its own span; the Tailscale row's line when Tailscale is not installed.
- The Phones dialog (`tests/unit/renderer/hostPhonesDialog.test.tsx`): the approval's sentence and buttons, and the not-yet-read checks with no switch, which give way to the switch once the host is read.
- Main (`tests/integration/desktopHostsTailnet.test.ts`, against a real headless host behind the Serve stand-in): the tailnet step is reported from the moment the host is saved and ends done; a host with no Tailscale running ends it saying so; a Serve refused for the operator ends it saying so, and choosing the tailnet again has the host set up its Serve again and moves the socket; the 5-minute check does the same over the SSH connection the host is on, with no new sign-in; and a reconnect over the tailnet tells the window when this computer last reached the host there.

Not run: real TLS, MagicDNS and Tailscale Serve, a real Tailscale approval, and a Linux host whose account is not Tailscale's operator. The check on forge is pull request 8.
