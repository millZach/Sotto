# Sotto Owl release track, October 9, 2026

Scope: Windows x64, local packaging only. No installation over Zach's Sotto, publishing, push, release creation or upload. Renderer branding came later, in [the October 10 section](#branding-october-10-2026). The accessor is `useReleaseTrack()` in `src/renderer/src/state/useReleaseTrack.ts`; main includes `releaseTrack` in existing update information even on unsupported platforms.

## Update selection

`tests/unit/main/owlUpdates.test.ts` runs the installed electron-updater 6.8.9 `NsisUpdater`, provider factory, GitHub Atom selector, manifest parser and semantic-version availability gate. Only HTTP responses and the app adapter are scripted. Cases cover stable ignoring Owl, Owl skipping newer stable and superseded stable tags, numeric daily build ordering, next-patch Owl updates, same/older builds, no Owl tags, mismatched manifests and the GitHub provider's `latest.yml` fallback within an Owl tag. Invalid metadata cannot become a downloadable offer. Stable retains `allowPrerelease = false`; Owl sets channel `owl`, enables prereleases and resets `allowDowngrade = false` after the upstream channel setter. Automatic download and installation on quit remain off.

Shared helper, main status and renderer accessor tests cover version-derived track reporting. No renderer view, stylesheet or control was changed, so no visual prototype or design baseline was needed.

## Returning to stable

GitHub main and local `origin/main` both resolved to `09ea3f4231dd6ee81ac545f0f15363283eeabe47` during verification. A detached checkout under the repository's `.worktrees/` received its own `npm ci` (no junction or dependency sharing) and was removed afterwards.

`node tools/verify-owl-profile.mjs <stable-checkout>` built separate probes against each checkout's actual modules. The Owl probe created real threads through `WorkspaceHost`, seeded synthetic current/history roles and a schema-valid command-center fixture, then reopened and saved through the branch's `AgentControl.start()` / `privacyChanged()`, workspace fixture, `ThreadRegistry`, `ThreadStore`, `SettingsRepository` and `AgentCredentials`. The stable probe used the clean checkout's same load/save paths over that profile. Providers were test fixtures; no native session, paid turn or real key was used.

Observed output is retained in `artifacts/sotto-owl-release/stable-profile.json` and can be regenerated with the retained tool. All ten thread identities/titles survived, including current and retired Watcher conversations. Four messages (ordinary, current, retired and worker) survived in `threads.sqlite`. The ordinary selected thread, draft, French language, `Control+Alt+O` shortcut and XOR-encrypted synthetic formatting key survived. There were no corrupt backups or ordinary-data resets.

Stable stripped every `kind` and dropped the complete `commandCenter` record on save: identity, active request/participant, uncertain operation/receipt references, reservation and read position. It dropped the Watcher capacity setting (seeded at 6), and also dropped `llmQuality` (seeded high), which main intentionally retired in its own ADR-0069. Reopening on this Owl branch would default the missing record empty, missing kinds to project, capacity to 4 and cleanup quality to low. Watcher conversations can consequently be treated as ordinary threads by stable; this is a material limitation, not a lossless rollback.

Main needs an inert preservation path for the command-center record and setting, safe retention/handling of special thread kinds, and an Owl-to-stable-to-Owl regression before that rollback can preserve Watcher. No main code was changed. The fixture proves these specific records and stores, not every possible production profile, OS credential decryption or native provider recovery. Unrecognized profile files were not deleted by the test; provider launch-profile side files were not part of this fixture.

## Branding, October 10, 2026

Zach chose the look from his screenshot and the approved mock-up's "Sotto Owl header" view: an Owl build shows Sotto's owl alone as a teal rounded tile where stable shows the small mark beside "Sotto". `releaseTrackName()` in `src/shared/releaseTrack.ts` gives the words, "Sotto Owl" or "Sotto". The renderer reads the track with `useReleaseTrack()`. Main reads it from `app.getVersion()`, as the updater does.

What an Owl build changes; stable keeps each one exactly as before:

| Surface | Stable | Owl |
| --- | --- | --- |
| Sidebar top row: Threads, Dictate, History, Help and the Settings column (`SidebarTop`) | 18 px mark and "Sotto" | The same `SottoMark` alone at 24 px, `role="img"`, named "Sotto Owl" |
| Strip over first-run setup and Memory | 20 px mark and "Sotto" | The tile alone at 24 px, named "Sotto Owl" |
| Main window title and document title | Sotto | Sotto Owl |
| Tray tooltip | Sotto | Sotto Owl |
| Help, About | Sotto 0.1.34, Windows. … | Sotto Owl 0.1.35-owl.20261010.1, Windows. … |
| Settings → Application → Updates | Sotto 0.1.34 | Sotto Owl 0.1.35-owl.20261010.1 |

The tile's colours come from the theme the way the mark's always have: the app icon's teal and black on the Sotto theme, and another theme's accent and its readable foreground anywhere else. The new rules set sizes only. Main now passes the build's name to `WindowManager` as the window's title. The page's `<title>` says Sotto until the renderer learns the track, so the main window prevents `page-title-updated` and keeps main's title from the start. The renderer then sets the document title to match. Main's own window lookups by title (the foreground check for background Git reads, and the e2e paste and snapshot) use the same name. The tray now takes its tooltip directly (`createTrayResource({ tooltip })`) instead of a configure callback. On Owl, Help keeps the version on one line (`.help-about__version`), because at the 820 px minimum the first run broke an Owl version at its hyphen. Stable keeps the line's original markup: a version has no hyphen there to break at, and the design gate showed that the extra span moved the text after it by a subpixel at 125% scaling.

Left as Sotto on purpose: the installer identity, `productName`, `appId` and data folder (ADR-0071). Also left: the window controls' names ("Minimize Sotto", "Close Sotto to tray"), the collapsed rail's mark (it never had a wordmark), the macOS application menu (there is no Owl Mac build), and every sentence in which Sotto is the app or the speaker ("Sotto looks for new releases…", "No account with Sotto"). The Watcher switch segment, badges and room are not part of this change.

The design gate was red before this change, from the release-track commit itself. That commit made main read its version from `app.getVersion()` so a package can carry an Owl version. An e2e or design run starts Electron on the bare `out/main/index.js`, with no app manifest, so Electron reported its own version (43.1.0), and the Help captures read "Sotto 43.1.0" against baselines reading "Sotto 0.1.34". `runningVersion()` in `src/main/runningVersion.ts` now takes `app.getVersion()` unless it is Electron's own version, and the bundled source version in that case. A packaged Sotto or Owl build reads its manifest as before. Main reads it once, for the update status and for the build's name. `tests/unit/main/runningVersion.test.ts` covers the three cases.

### How it was run

`tests/e2e/sotto-owl-branding.spec.ts` ran against the output of `npm run build`, each launch with its own owned e2e profile and the `design-threads` fixture, never Zach's data. The Owl launches start Electron on a temporary folder whose `package.json` declares version `0.1.35-owl.20261010.1`, with `main` pointing at the same built entry. Packaging uses the same mechanism: `extraMetadata` writes the version into the app's manifest, and `app.getVersion()` reads it back. Main reported `currentVersion: 0.1.35-owl.20261010.1` and `releaseTrack: owl`. The stable launches reported `0.1.34` and `stable`. The run published with `SOTTO_E2E_EVIDENCE=publish`; all six tests passed.

Checked, with the measured values in [branding.json](../../artifacts/sotto-owl-branding/branding.json):

- **Titles.** `BrowserWindow.getTitle()` and `document.title` read "Sotto Owl" on Owl and "Sotto" on stable: on Threads, after Help and Settings, and over first-run setup.
- **Tile.** It measures 24 × 24 on Threads and in the Settings column at 1280x800 and 820x560, in dark and light, and in the first-run strip. It is centred vertically in its row within 1 px and sits clear of the first toolbar control. Threads, Terminal, Add project, New thread, Collapse sidebar and Search threads keep the stable build's position and size to the pixel at both sizes in both modes. Nothing in the row overflows or clips at the minimum.
- **Contrast.** The glyph (`#000000`) on the tile (`#47b8a9`) is 8.70:1 in both modes, against the 3:1 asked for. The version lines' text, composited over the surfaces they sit on, measures 9.48:1 (dark) and 6.72:1 (light) in Help, and 19.55:1 and 15.74:1 in Settings.
- **Keyboard.** The tile is a picture, not a control. Its `tabIndex` is -1 and it has no focusable descendant, so the row's Tab order is the stable one. It sits in the row's drag region as the mark does.
- **Reduced motion.** With reduced motion on, the tile has no animations; it never had any.

I opened every capture at its own resolution, and the 1280x800 close-ups again at four times their size. A pixel comparison of each Owl capture against its stable pair finds changes only in the brand, the version text, and pieces that move with time: the streaming caret, the activity dot and the working rings on Threads, and a hover still fading from a Settings row the pointer had crossed. The tile matches the mock-up's 24 px tile and Zach's screenshot: the black owl on the teal tile, eyes and beak cut through. The first published run showed the Settings column scrolled under its top row on both tracks. That was the press on Application at 820x560 carried over to the larger size, behaviour that predates this change. The spec now scrolls the column back to the top before each Settings capture.

Not observed directly: the tooltip on a real tray icon. An e2e run creates no tray. A packaged Owl's icon would land in the Windows 11 overflow flyout, which UI Automation cannot read without opening it on Zach's taskbar, so no packaged build was made or launched for this change. `tests/unit/main/trayIcon.test.ts` covers the tray being named from the version, and main hands the tray and the window the same name. A UI Automation probe during the Owl run found the window grouped under the pinned Sotto taskbar button, which still reads "Sotto": the app ID is Sotto's on purpose (ADR-0071), so the group label comes from the shortcut, not the window title.
