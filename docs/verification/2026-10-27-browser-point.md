# Point at something verification

October 27, 2026, on `feat/browser-point`, from `feat/browser-pane` at e568aae14. This is ADR-0154's Point at something, behind the `quiet-browser` Owl feature. `tests/e2e/browser-point.spec.ts` launched the built app on the Owl track (`onReleaseTrack('owl')`) over the fake Claude Code provider and a local page with a Sign in and a Save trail button, and ran with `SOTTO_E2E_EVIDENCE=publish`. The user opened the page from the pane's address field. Captures are the window's own pixels (`desktopCapturer` by window title), so the native page main draws, and Chromium's overlay on it, are in them. The window's content was 1280x800 or 820x560. Every capture below was looked at. The measured boxes and the draft's text are in `artifacts/browser-point/verification.json`.

Playwright's mouse reaches Sotto's own window, never the native page main draws over it. The spec moves and clicks on the page with `webContents.sendInputEvent`, which is real input through Chromium: the inspect overlay reads it as it reads the user's mouse, and the hover name, the pick and the picture below all came through main's own overlay path, not a scripted event.

All ten captures were taken again on October 27 with every review fix in (63617a538), and looked at.

## What the captures show

1. **Pointing** (`hover-1280x800-dark.png`, `hover-1280x800-light.png`): Point at something is pressed, between the address and Screenshot to message. The line over the page reads "button · Sign in · Click something, or Tab to it and press Enter · Esc to stop"; at 1280 wide its words take two lines. Chromium's own label stands beside the hovered button: "button#sign-in", its size, and its accessibility name (Sign in), role (button) and that it is keyboard-focusable. The button is tinted in the theme's accent: Chromium fills an element's boxes and draws no outline (ADR-0154 amendment).
2. **The comment** (`comment-1280x800-dark.png`, `comment-1280x800-light.png`): a click on Sign in took a picture of the page and put it in the page's place, with a 2px accent outline round Sign in, a "button · Sign in" chip under it and the comment beside it: "What should the agent know about this?", Cancel with its Esc key, and Add to message. The field had focus. The outline's centre was within 12 pixels of the button's centre on the page.
3. **The comment at the minimum** (`comment-820x560-dark.png`, `comment-820x560-light.png`): the window shrank with the comment open. The picture scaled down to fit the page's place, and the outline, chip and comment followed it; the comment stays inside the page's place.
4. **Added** (`added-1280x800-dark.png`, `added-1280x800-light.png`, `added-820x560-dark.png`, `added-820x560-light.png`): a second round, from the keyboard (Enter on Point, Tab twice to Save trail, Enter), pointed at Save trail with the comment "This should say Save, to match the header." Add to message put one item in the composer: the picture, "button · Save trail", and the comment under it. The composer's text stayed empty; the address, selector, box and words travel with the item and are written into the message only when it is sent. Point ended and focus went back to its button. Nothing was sent, and the page's own Save trail handler never ran.

Between the rounds, Escape in the comment closed it and went back to pointing on the live page with focus on Point at something, and Escape again ended pointing.

The unit tests cover the rest: in `tests/unit/main/browserTools.test.ts`, the overlay going on in the accent with Chromium's label for a shown page without sharing or a grant and off again, a page nobody shows doing nothing, a request without the accent refused, the Owl answer off refusing it, an Off that overtakes an On or arrives during setup leaving the overlay off, the hover name as data, the pick's description, box and picture, Enter picking the focused element, a hide during a pick sending no picture, one pick per turn, and navigating, hiding the page, minimizing or hiding the window and Escape in the page each ending it; in `tests/unit/main/attachedFiles.test.ts`, the feedback block written for the provider at send and read back off; in `tests/unit/renderer/tools/browserPane.test.tsx`, the button's place and state, the line, the comment and Add to message, the comment placed again when it changes size, an unreadable accent, Escape twice, main ending it, and stable keeping Comment on page; in `tests/unit/renderer/tools/browserReview.test.tsx`, the one draft item and the text left alone; in `tests/unit/renderer/screenshotInput.test.tsx`, the chip showing the name and comment and removing all of it.

Each test for a review fix was run with its fix undone and failed, and passes with it in, the last four (feedback reaching the provider, read-back taking off only Sotto's own blocks, a start made stale by a hidden window, and the short-window captions) on October 27 after local runs resumed. The spec passed four runs in a row and the captures' run. Its check that the page has the keyboard after Point is turned on applies while Sotto's window is in front; Windows reports a page focused only then, and with another app in front the keys still reach the page directly.
