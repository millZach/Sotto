# Watcher on the iPhone: the Watcher tab

Ticket 8b of the Watcher plan, branch `feat/watcher-iphone`, built on ticket 8a's `feat/watcher-phone` (the wire contract at `3cb736fdd`, then its host and SottoCore models merged at `da592927c`). Windows 11 on LAPTOP-RUSSH2J5, October 11, 2026. The design is Zach's picks from the phone prototype of the same day (1B, 2B, 3B, 4B, 5A, 6B, 7A), recorded in ADR-0073's October 11 amendment.

**Native iPhone app: NOT VERIFIED.** No Swift was compiled, run or tested on this machine: there is no Xcode or Swift toolchain here, and the brief allowed installing none. The Native iOS job has since compiled it and passed its model tests, and four of the six Watcher journeys failed there (see [The first CI run](#the-first-ci-run-october-12)); the fixes for them are again source only. The [second run](#the-second-ci-run-october-12) passed all six on both phones and failed one older journey on the Pro Max. The [third](#the-third-ci-run-october-12) failed one Watcher journey on the SE because of the journey's own wait, not the app. The [review round](#the-review-round-october-13) changed the app again, source only, and the [fourth run](#the-fourth-ci-run-october-13) failed only its new journey, whose pull was too short to refresh. Until that job is green on both phones and its `watcher-*` screenshots have been opened and inspected, the journeys are not proven.

## What was checked here

- **Provider logos and the owl as vectors.** The desktop's provider marks (`src/renderer/src/agents/ProviderMark.tsx`) and Watcher's owl (`WatcherOwl.tsx` on `feat/watcher-room`) were rewritten as SVG paths using only absolute moves, lines and cubic curves, with arcs turned into curves, so Xcode's SVG reader has nothing unusual to parse. Each rewritten file and the desktop's own path were drawn at 256 pixels in Chromium and compared pixel by pixel: Claude Code, Devin, Grok Build, the owl and both tab owls match exactly; Codex differs in 9 antialiased edge pixels out of 24,484 drawn. [The comparison sheet](../../artifacts/watcher-iphone/provider-marks-comparison.png) shows each desktop mark beside its rewrite, and the tab owl with its working dot. This shows the shapes are the desktop's; it does not show how the asset catalog draws them on a phone.
- **The prototype.** The approved walkthrough's captures were opened and read for the layout this build follows: `01-threads-dot`, `02-conversation`, `03-watched`, `06-watched-thread-3B`, `07-needs-you-4B`, `13-watcher-permission` and `17-no-can-answer-watcher` (`captures-2/` beside the prototype). The app keeps the system tab bar, so the dot is drawn into the tab's owl rather than beside it in the accent colour, and takes the tab bar's tint.
- **The contract.** The model was written against `phone-contract.md` and `src/shared/watcherPhone.ts`, then switched to 8a's SottoCore models (`WatcherPhoneState`, `WatcherWire` and the result enums) once they landed. Its uses of the wire were read against 8a's host code (`src/main/agents/watcherPhone.ts`, `src/host/socketServer.ts`): the page comes with each shell to a phone that accepted `watcher-phone`; Watcher's own threads never appear in a phone's thread list; `watcher-phone-answer` answers only threads on the computer that runs Watcher, under its Can answer; a card's `mayAnswer` is display only.
- **Review by reading.** Every changed Swift file was read for compile errors by a second reviewer, since nothing here can compile it: SottoCore member and nested type names, conformances SwiftUI needs, enum patterns, file-scoped `private` use, the AppModel test target's sources, the Xcode project's entries and the asset names. It found no compile failure. It found one journey assertion that passed before what it claimed had happened (a receipt row that already existed), which now waits for the second row. Reading is not compiling.

No root gate covers this work: it changes only `apps/ios/`, documents and the iOS job's timeout. The npm suite does not read Swift.

## The first CI run (October 12)

Run 38201680489 (job 114656655740, draft #946, which carries `apps/ios` from this branch onto `main`) compiled the app and its tests and passed all 354 SottoCore and app-model tests, `WatcherModelTests` included. On the iPhone SE, 21 journeys passed, among them `testAWorkersCardIsAnsweredInWatchersPage` and `testAOneTapQuestionIsAnsweredOnItsCard`, and four Watcher journeys failed. `verify-ui.sh` stops after the first phone that fails, so the iPhone 16 Pro Max (accessibility text, reduced motion) has not run any of them yet. The screenshots and the hierarchies the job kept gave each failure's cause:

- **`testStopAllAsksFirst`: the app.** iOS 26 drew Stop all's confirmation dialog as a popover from the middle of Watcher's page and left its Cancel button out, so the journey had nothing to press. The design asks in a centred dialog with Stop and Cancel, so it is now an alert, its message in the design's words with each thread and where it runs. The journey finds the alert by its question and presses its own buttons.
- **`testAReceiptRowOpensItsThread` and `testAPhoneWithoutCanAnswerSaysSoInWatchersPage`: the journeys.** Watcher's page opens at the end of its conversation under a glass header. The receipt row sat at -39 to 64 points and the card's Review question behind Conversation | Watched; XCTest called each hittable, so the shared reveal helper didn't scroll, and the press landed on the header: the row opened nothing, and Review opened Watched rather than the card's sheet. A Watcher helper now scrolls each target whole between the header and the reply box before it is pressed, in every Watcher conversation journey.
- **`testTheWatcherTabOpensAndTakesAMessage`: both.** The journey put the keyboard away with a swipe on the first scroll view, which stays above the keyboard; the conversation lets the keyboard go only when a drag carries on down into it. Its screenshot also showed that with the keyboard up on the SE, neither the message sent nor Watcher's answer was on screen: the page scrolled to its end, under the card still waiting. As the design does, sending now puts the keyboard away, and new words are scrolled to just above the box with waiting cards below them. The journey checks both, then puts the keyboard away with a drag down into it.

The passing journeys' screenshots, dark and light, match the design except the header: on the SE the line under Watcher's name was set a size larger than the prototype's, which pushed the state pill onto a row of its own. It is now caption size, with the prototype's 40-point tile, and the state stays beside the name short of the accessibility sizes. The provider logos and owls draw as the desktop's, in the line's colour, and the tab's value read "Working" in the hierarchy.

## The third CI run (October 12)

Run 38295149569 (job 114964923470, draft #946 at `0d76597a7`, carrying this branch's `apps/ios` as of `9cb6d8c46`) passed the one-tap journey on the iPhone SE. One journey that had passed there in the second run failed, so the Pro Max did not run.

- **`testTheWatcherTabOpensAndTakesAMessage`: the journey.** It reported Watcher's answer at a zero frame, outside the band between the header and the box. The app had it right. The failure's screenshot and hierarchy show the answer at 310 to 351 points, inside a band of 146 to 519. The recording shows it there, still, from the answer's arrival to the end of the journey. The wait was the problem. It gave the answer ten seconds and, on every read, also found the header, the tab bar, the box, the held line and any message. Each of those queries took one to two seconds on CI's SE, so the wait got a single read of about nine seconds. In the second run that read finished with a second to spare. In this run it ran past the deadline: its last queries failed at once, and the answer's frame came back empty. Nothing scrolled the answer away, and nothing unloaded it. The band is now read once before the wait and again after it. The wait reads only the answer, needs two matching reads in a row, and has sixty seconds, as the thread page's own end check does. What the journey proves has not changed.

## The review round (October 13)

A two-axis review of this branch alone (`5353df2a8..2423311f4`) found ten things. Each was checked against the code, and all ten were real. Every fix is source only, as before. Each has a SottoAppModel test that fails without it, or, for the scroll fix, a Focus journey.

- **Edits defeated send deduplication.** The box kept only its last words and draft ID, so other words sent after a lost acknowledgement dropped the first words' ID. It now keeps every unconfirmed draft ID with its exact words (`WatcherDrafts`, up to 32 for each computer) until a reply or a page says Watcher took them. Test: `testUnconfirmedWordsKeepTheirDraftIDThroughOtherWords`.
- **Stop all couldn't recover its outcome.** It now keeps its request ID until the outcome is known. After a lost acknowledgement it reads the receipt under that ID (`receipt.watcherStop`), then Watcher's page. A receipt it can't read yet is read once the computer is reached again. Test: `testALostStopAllAcknowledgementReadsItsReceipt`.
- **A vanished remote request still offered answers.** A card for a thread on another paired computer is now answered only while that computer, reached now, holds the same request. It answers with that computer's copy, and otherwise says why (`watcherCardRoute`). Test: `testACardForAThreadOnAnotherComputerIsAnsweredOnlyWhileThatComputerHoldsIt`.
- **A lost acknowledgement could leave taken words in the box.** The page read after it arrived while the send was still on its way, so nothing settled it. The box now settles against the page it holds when the send ends. Test: `testThePageReadAfterALostAcknowledgementSettlesTheWords`.
- **Watcher's conversation published on the whole model.** The page now lives in `WatcherStore`, which only the Watcher tab and the request sheet watch. The model keeps a summary (`WatcherSummary`) and the shell kept on the model leaves the page out (ADR-0051). Test: `testWatchersGrowingConversationPublishesOnlyOnItsStore`.
- **New words pulled a reader away.** The conversation now follows Watcher's new words only for a reader who sees the newest words or the page's end, never while the user moves the page, and catches up when they let go there. On iOS 18 and later the bottom anchor only sets where the page opens and how a short conversation sits. Journey: `testWatchersNewWordsLeaveAReaderOfEarlierMessagesWhereTheyAre`, screenshot `watcher-reading-earlier-dark`.
- **Refused words could be lost.** Words that can't go back in the box, because the user wrote newer ones while the send was on its way, now wait under the conversation with **Put it back in the box**. The message says where they are. Test: `testWordsThatDidntReachWatcherAreOfferedBackWhenNewerWordsAreInTheBox`.
- **A failed read said nothing.** The page, Watched and the box now say what happened: the computer's own words when it refused, otherwise "Watcher on Laptop couldn't be read. Nothing was lost. Pull down to read it again." The next page clears it. Test: `testAPageThatCantBeReadSaysWhatHappened`.
- **The overview.** The root README's iPhone section now describes the Watcher tab. The guide and `apps/ios/README.md` cover this round's behaviour.
- **Duplicated controls.** The Threads card and Watcher's card now share `OneTapQuestion` and `CardPermissionButtons`, each with its own routing.

A second reviewer then read the Swift diff against the real declarations, since nothing here compiles it. It found no compile error and one defect: reconnecting waited on the Stop all receipt read, which follows a pending receipt for up to ten minutes. That read now runs after the connection attempt. Its other points are fixed too:

- The page decides whether to follow when the user lets go, the box moves or the header changes, never as content grows. It looks again after the scroll has run.
- The journey's scroll view is scoped to the conversation.
- The draft-limit test goes past the limit.
- Words set aside after a connection changed mid-send say so.

## Sotto Bug Bot on #1005 (October 13)

With the fourth run's fix, CI was green on #1005, every journey included. Sotto Bug Bot then found four things. Each was checked against the code, and all four were real. Each has a SottoAppModel test that fails without its fix. Source only again:

- **A Watcher alert from a second computer opened the first one's Watcher.** The tab always showed the first computer that runs Watcher. An alert dropped its computer, and alerts stayed quiet for every computer while the tab was open. The model now keeps which computer's Watcher the tab shows. An alert chooses its own computer, and alerts stay quiet only for the Watcher on screen. With Watcher on more than one computer, the line naming the computer under Watcher's name opens a menu of them. Test: `testAWatcherAlertFromAnotherComputerShowsThatComputersWatcher`.
- **A queued read was lost after a failed or stale read.** The read loop returned before checking for a read asked for meanwhile. It now falls through to that read. Test: `testAReadAskedForDuringAFailedReadStillRuns`.
- **The same words reused a draft ID the desktop may already have delivered.** The desktop lists a draft from the moment it reads its send until Watcher took it or it failed, and won't take again one whose result it doesn't know. So the box now lets go of a draft ID once a page asked for after its send ended no longer shows it on its way. That page is the read after a lost acknowledgement, a later pull to refresh, or a later connection's hello. A page pushed with a shell is no proof, since the desktop may have made it before it read the send. Neither is a page that says nothing of drafts. Words resent while the draft may still be on its way keep its ID. Test: `testTheSameWordsGoAsANewMessageOnceAPageSaysTheFirstIsNoLongerOnItsWay`.
- **Two reads of one Stop all receipt could poll together.** Only one now runs over each connection to a computer. A read over a newer connection still runs while an older one waits, since the older one stops at its next read. Tests: `testOneStopAllReceiptIsReadAtATime`, `testAReconnectReadsStopAllsReceiptWhileTheOldConnectionsReadWaits`.

A second reviewer read this round's Swift against the real declarations. It found two problems in the first versions of the draft and receipt fixes: pushed pages retired draft IDs, and a reconnect could skip the receipt read. It also found a side effect inside `removeAll` and the menu's accessible name. All four are fixed, as described above. On a second read it found a defect in the fix. The read after a lost acknowledgement had re-enabled Send. It also found that a page asked for before the same words went again could let go of their ID. The box now waits through that read, and each draft counts how many times its words have gone with its ID, so an older page can't speak for a later send.

## What neither proves

A live Owl desktop running Watcher with a real iPhone: the shell's page arriving over the network, a send's draft settling from `draftDeliveries`, an answer's receipt, Stop all against real threads, alerts on a device, VoiceOver and Dynamic Type by hand, and the keyboard's microphone key dictating into Ask Watcher. Answering a card for a thread on another paired computer (a host such as forge) goes to that computer as an ordinary answer; no journey has a second online computer to show it.

## Decisions made here

- With several computers running Watcher, the tab shows the first in the order they were added, until a Watcher alert or the menu on the line naming the computer chooses another (October 13, after Sotto Bug Bot on #1005).
- A worker's brief from Watcher is not labelled From Watcher in the worker's own thread, as the prototype showed: the wire marks no message as Watcher's.
- Watcher's own requests are not on Threads; the Watcher tab's badge counts them, with any card for a thread this iPhone doesn't list.
- The Watcher box keeps no saved marker for a send. One draft ID per exact text makes sending again safe, and the page's `draftDeliveries` clears words Watcher took.
