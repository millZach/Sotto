# Host protocol, version 1

This is every message a client and a host exchange: the desktop reaching a remote host through `SocketHostService`, and the iPhone client (`apps/ios`) from its own Swift code. The schemas are in `src/shared/hostProtocol.ts`; the listener is `src/host/socketServer.ts`. Why the host works this way is ADR-0025.

October 8, 2026 amendment ([ADR-0068](adr/0068-remove-voice-control-and-thread-management.md)): voice control and thread management are retired. Protocol v1 retains `assignments:[]`, `queue:[]`, `pendingRequest:''`, `speech:{id:0,text:''}`, `voice:{status:'off',error:null,action:'none',revision:0}` and `credentials.grokSpeech:false`. Configuration retains inert `orbColor:'teal'`, `followupLimit:5`, `speak:false`, `speechProvider:'grok'`, `speechVoice:'F1'`, `grokSpeechVoice:'altair'`, `wakeModelDirectory:''` and `wakeRuntimeDirectory:''`, alongside its existing membership placeholder. They are compatibility fields and grant nothing.

Readers inspect an old host's assignments before discarding those retired fields. A host with live assignments requires Update from the Threads page before ordinary commands continue; history and drafts stay readable, and selection, observation, draft saves and Stop remain available. A host without assignments can continue ordinary v1 work. The desktop sends `managed:false` when creating a thread on v1, including when its caller omitted the field, because old hosts defaulted to managed creation. New hosts accept false or omission as manual creation and refuse true. They also refuse assign, unassign, pause, resume, attention navigation, conversation pause/resume, spoken input and voice configuration. Manual answers, permission policy, receipts, follow-up queues and explicit babysitting are unchanged. No legacy unassign exchange is used.

Version 1 is frozen from the pull request that added detail deltas and the version check (#238, #239). A later host may add to it, and only in these ways:

- an optional field on a response or push, which a client may ignore;
- a new **host feature**, named in the `features` list of health, the listener file and the hello reply;
- a new push form, sent only to a client that asked for it by feature name in hello's `accepts`.

October 9 exception ([ADR-0068](adr/0068-remove-voice-control-and-thread-management.md)): `connect` may carry optional `notice:false`, solely to leave success feedback unset. The schema rejects every other value and every extra command field; pairing and answer policies are unchanged. Published desktop clients strip this presentation metadata from remote connect packets, so strict older hosts receive exactly their existing v1 command. The desktop suppresses only Sotto's known connection-success text locally, retaining unrelated notices and errors. Existing phone packets are unchanged. This exception grants no command, provider action or permission.

Nothing v1 carries is renamed, removed or given a new meaning. A change that needs one is version 2, with its own support window. `v` stays `1` on every message until then.

October 9, 2026 contract ([ADR-0073](adr/0073-watcher-coordinates-threads-with-its-providers-own-tools.md)): a thread may carry optional `kind: 'project' | 'watcher' | 'watcher-history'`. Absence means `project`; older clients may ignore it. It is Sotto-owned organization, not a capability or grant. Zach's October 11 choice keeps Watcher available to later phone projections; ticket 8 supplies its phone surface. These host features add no phone filtering or aggregate desktop roster to the phone.

## Watcher on a paired host

October 11, 2026: headless hosts offer `watcher-control` and `watcher-reads` on either release track. Their health and descriptor list both; hello lists them only for a paired desktop recorded in `desktop-clients.json` over SSH, including on the administrative listener. A general paired socket client or phone cannot supply machine origin. This client classification grants no remote-answer policy. Stable desktops accept and send neither feature. The desktop requires both for automated mutation, including start; ordinary commands are never a fallback. Existing summaries remain readable on older hosts.

The closed schemas are `src/shared/watcherHost.ts`. Every envelope still has `v:1` and the existing socket request identity and session. Watcher's local tool bearer stays in the master's process and never travels on this connection.

| Operation | Fields | Result |
| --- | --- | --- |
| `watcher-control` | `request:{master,request,ceiling,operation,call}` | The matching frozen Watcher tool result or refusal. `call` is exactly `start_thread`, `send_to_thread`, `stop_thread` or `settle_thread`, with its existing tool input. |
| `watcher-read` | `request:{master,stoppedRequests?,call?}` | With `call`, the existing bounded `list_threads`, `list_projects`, `list_working_copies`, `read_thread` or `read_operation` result. Without it, the scoped text-free host projection and registration for accepted pushes. |
| Push `watcher-state` | `projection` | Only after accepting `watcher-reads` in hello and reading that master's projection. It carries host/master identity, observation time, a fingerprint revision, bounded ownership/receipts and sourced evidence. |

`master` is the desktop's durable Watcher identity. `request` retains its main-minted UUID, Watcher target, original user-message reference and creation time. `operation` retains the master's exact operation/retry/digest/target/generation and receipt/message references, initially queued. The authenticated client, master creation identity, root reference and submitted ceiling are immutable for that request. Submitted identities cannot reuse another operation's message, draft, card or receipt, or start over an existing thread. A changed retry returns a refusal. The host does not accept an origin field on an ordinary command, a tool answer or a permission change.

The desktop persists the operation and records its reservation before transmission. The host imports that reservation's identity, admits it through the local Watcher enforcement service, persists text-free ownership and receipts, and rechecks its live paired connection, ownership, pending requests, expected native identities and, for a start, permission ceilings after preparation and immediately before the provider writer. A start is held to the desktop's new-thread permission default, not the host's own, and to Ask for approval unless the host's policy lets that desktop answer there (ADR-0073, October 19, 2026); incomparable provider profiles refuse. A send, queue or steer gives the thread no permission and is held to no ceiling (ADR-0073, October 21, 2026, #1145). The host cannot issue a desktop request or mint global capacity. A host's returned limits are replaced by the master's global limits before its tool result is returned.

For `start_thread`, the model is explicit and an omitted effort comes from this computer's new-thread defaults, fitted to the chosen owning-host model's offered levels (ADR-0074). The desktop resolves effort and permission before hashing the transmitted operation. Its optional text-free `inputDigest` binds the original tool call for retries; changing defaults later cannot change that operation or create another send. Older saved operations without it retain their original digest check.

A dropped reply leaves the master's operation uncertain, and its reservation kept, until exact host evidence settles it. Reconnect reads receipts and ownership and reapplies saved stopped-request fences; it sends no new provider operation automatically. A host restart marks dispatching work uncertain, restores its original identities and has no restored connection guard for queued dispatch. A retry returns its original receipt even after its request closes; no retry creates another send. An operation omitted by the bounded projection is read exactly. Before answering `OPERATION_NOT_RECORDED` for an unrecorded ID, the owning host persists a text-free absence fence and serializes it with admission. That ID cannot arrive later as a new send, including after restart. `UNKNOWN_OPERATION` can mean a different client scope and is never proof of non-admission. Only the fenced negative result refunds the master's operation; a read failure or projection omission leaves it uncertain. The host retains at most one thousand absence fences and refuses another negative proof when that bound is full, keeping the slot held. A stopped Watcher service refuses control and reads with `NOT_CURRENT_WATCHER`. Direct native, desktop or phone instructions on the worker increment host ownership generation before subsequent machine dispatch. Reading, observing and answering the existing card do not take over.

A scoped `watcher-read` may carry up to one thousand saved `stoppedRequests`, each only its immutable request identity and original ceiling. The host validates the authenticated owner and master, persists the stopped fence before refreshing live guards, cancels only that request's machine queue, and refuses late admission. Repeated feedback makes no state write once the fence and queue are settled. Native and phone user queues remain intact. Confirmed Stop all carries an internal `confirmedStop` marker on its stop operation; only an owned Watcher-started, participating worker can be stopped after the request closes. The marker is absent from tool arguments, changes no request back to active, and gives no send, approval or permission authority.

`read_thread` uses the owning host's history epoch and zero-based message positions, with `-1` before position zero. It caps fifty messages and 64 KiB, returns a restart position for a reset epoch and distinguishes missing history from an empty page. A detail revision, projection fingerprint and event sequence are separate identities. No project-file broker or native mount is added. Projection revisions are fingerprints of text-free control/evidence, not event cursors. Projections cap requests, operations and evidence at one thousand each; exact operation reads remain available separately.

The owning host retains checkpoint and GitHub facts without running a master wake-up loop. The scoped projection may carry up to one thousand `progress` entries, each only a target and opaque fingerprint from the shared progress classifier. Plan-step changes update that fingerprint even when the ordinary shell summary is unchanged. The desktop reconciles ownership before importing facts and progress into its existing wake-up observer. Typed `watcher-state` notifications are separate from ordinary streaming shell publications. The desktop caches their scoped projections and coalesces background reconciliation per host for 250 ms. Progress-only or unchanged pushes require no RPC or record write; hosts without work for this master are skipped. Explicit control/Stop/reconnect paths still refresh the owning scope, and failed hosts retry independently with backoff from one to thirty seconds. News follows the user's queue and cannot resume a stopped worker.

Paired GitHub state, checks, review and auto-merge remain separate sourced facts, with their own head and observation time. A checks-only read or unchanged projection cannot erase or refresh the other facts. Waiting news stays held while sources are unknown after restart or omitted by a bounded projection. An observed change to an already-known owning-host fact supersedes the older occurrence, using the host ID and Sotto thread ID together. A connected owning-host roster that removes a PR also removes its local and paired GitHub facts, including approval and auto-merge, before the next Landing classification. An empty or bounded evidence projection, or a disconnected roster, does not confirm an unlink.

## Watcher on a paired phone (October 11, 2026)

Protocol stays v1. `watcher-phone` is offered only by a desktop running Watcher, on its phone listener: an Owl desktop, or a stable one from 0.1.40, when Watcher was sent to stable (ADR-0072). A client reads the offer, never the track. A headless host offers no phone Watcher, even when it serves `watcher-control` to a desktop. A client opts in with `hello.accepts: ["watcher-phone"]`; only then can optional `shell.watcher` carry the page projection. Existing shell pushes carry updates; there is no new push form. `watcher-phone-stop-all` additionally admits the user-only preview and confirmation. The old phone's thread list, details and events omit current and historical Watcher conversations; ordinary workers remain usable. Opted-in ordinary worker rows may carry `watchedByWatcher: boolean`. Nothing changes saved records.

Wire schemas live in `src/shared/watcherPhone.ts`. Every request has the normal v1 id/session envelope. `watcher-phone-read` has no payload and returns `{status:"ok",state}` or WatcherRefusal. State has the serving hostId, nullable current target/provider/model/effort/status/connection, bounded conversation messages/revision/earlierAvailable, receiptGroups, watchedThreads with owning targets/provider, needsYou with the owning request cards and mayAnswer, inFlight/limit, working, recoveryNotice and observedAt. Optional draftDeliveries carries only draftId/status evidence for this current Watcher, so lost acknowledgements can be reconciled after restart without replay. It includes neither master/worker tool arguments nor control-record digests, tokens or prompt copies. An unavailable provider is null, never a guessed logo. A receipt group names requestId and replyMessageId (null when its reply is unavailable), with one row per thread showing its latest recorded operation in that reply. Receipts carry operationId, owning target/title/provider, action, optional delivery, deliveryState, times and optional refusalCode; acceptance establishes delivery only.

Conversation messages are what the user typed. Watcher's request note reaches its provider beside the user's words, not in them, and the desktop's own snapshot removes only the exact line Sotto once put after a Watcher user message for that message's own request: the routing footer that listed every project ID on older sends, or Grok Build's request line. Native messages remain unchanged, and assistant words are not parsed or redacted. Receipt grouping stays within the observed user-message window; an action without a retained reply does not attach to the next user's reply.

`watcher-phone-send` takes `request: {origin:{kind:"phone",hostId,clientId},target:{hostId,threadId},draftId:UUID,text}`. The host matches the origin against the authenticated pairing and its own host, and the target against its current Watcher. It admits an actual user instruction, retaining optional text-free request.phoneOrigin, through the existing command lane and writer. Success is `{status:"ok",draftId,state}`; refusals never become worker answers. New workers use the computer's new-thread defaults, including for a phone without Can answer; those defaults may allow edits without asking. Stable, headless, non-opted-in clients, forged origins, retired masters, pending user cards and disconnected providers refuse. Pairing grants no permission authority.

`watcher-phone-answer` takes `request: {target,command:{type:"answer",threadId,requestId,answer,approved?,questionAnswers?,permissionChoice?}}`. The two thread IDs must agree. The serving desktop admits only its local cards; a remote worker card is answered through the phone's existing pairing to its owning host and that host's ordinary answer command. The desktop never relays its own answer authority for the phone. It answers the exact local owning card by the user's existing command path, under freshly checked Can answer, and never through a Watcher tool. Opening or answering is not takeover. Direct ordinary phone Send to a watched worker is takeover before dispatch. Success returns `{status:"ok",state}`; transport receipt recovery uses the same request id. A changed card refuses stale_request; denied authority refuses forbidden. Provider failures remain unavailable, without protocol-body logging.

`watcher-phone-prepare-stop-all` has no payload and returns `{status:"ok",confirmationId,targets:[{hostId,threadId,title,provider}],expiresAt}` or WatcherRefusal. `watcher-phone-stop-all` takes confirmationId, and returns `{status:"ok",state,results:[{target,status,message}]}` or WatcherRefusal. Preview identities are short-lived and bound to the authenticated client; cancellation sends nothing. Unknown, expired, another client's or changed previews refuse before stopping. Each target's ownership and connection are checked again. Current Watcher, user-started, protected and taken-over threads stay outside its scope. Individual stop results can be partial or uncertain.

October 12 review correction: Stop all records a pending and completed command receipt under the authenticated phone's original request ID. Optional receipt.watcherStop is either {status:"ok",results:[{target,status,message}]} (including partial, refused and uncertain target results) or the original WatcherRefusal. It carries no page snapshot. Read that receipt and watcher-phone-read after a lost acknowledgement; never retry automatically. An explicit retry with the same ID and confirmation returns that retained outcome with fresh state and performs no second stop; changing the confirmation under the same ID refuses invalid_request. Another pairing sees unknown. These in-memory transport receipts share the existing bounded five-minute settled replay window and do not survive a listener restart; unknown still requires a fresh read and user review of a new preview. No feature name, request shape or stop reply changes. SottoCore Receipt.watcherStop decodes WatcherStopReceipt; old clients ignore this optional field.

October 13 Stop all client-isolation correction: the main-owned confirmation store retains at most sixteen previews per client. The desktop room is its own client; each paired phone uses its authenticated client ID, including after reconnect. Opening another preview always retains the newest and prunes only that client's oldest; no phone can block or evict the desktop room's or another phone's previews. Confirmation checks the client before consuming its preview, as well as expiry, scope, ownership and the live connection guards. Pruned IDs keep the existing TARGET_CHANGED code because v1 has no dedicated preview-replacement refusal. Unavailable-preview wording names expiry or replacement by a newer preview, rather than claiming the threads changed; actual scope changes still name the changed threads. Total retained previews are bounded by the number of clients, and expiration or consumption releases space. This replaces the shared-capacity refusal design. No refusal code, feature name or wire shape changes.

October 13 answer replay correction: an authenticated, opted-in phone can explicitly retry the same watcher-phone-answer request ID, owning target and exact command to read the recorded outcome with fresh state. Receipt lookup and digest comparison happen before checking the current card or Can answer; replay performs no second answer and needs no new answer grant. A changed target or command under the same ID refuses invalid_request. A new request still checks its owning target, current card and Can answer at admission and the writer. No refusal code, feature name or wire shape changes, and unconfirmed mutations are never retried automatically.

October 23, 2026, photos for Watcher from the phone ([ADR-0073](adr/0073-watcher-coordinates-threads-with-its-providers-own-tools.md)): optional `watcher-phone-photos` is offered with `watcher-phone` on a Watcher desktop's phone listener whose host stages images and answers previews; a phone needs no accept for it. `watcher-phone-send` may then carry `images`, one to eight handles `stage-attachment` answered, within a thread reply's limits, and its `text` may be empty when it does; a send with neither words nor photos is refused `invalid_request`, and so is one with `images` from a listener that does not offer the feature. The photos go with the words however they go: now, as a steer into Watcher's running turn, or queued to go next, under the same draft ID. Each of the page's messages carries its photos as `attachments`, each with the `preview` marker when Sotto keeps a copy, and never the bytes. `watcher-phone-preview` takes `{target, messageId, attachmentId}` and answers `{dataUrl}` or null, as `preview` does for a thread, for the current Watcher's thread only, one at a time per client on the preview guard; a phone's own `preview` of Watcher's thread stays `forbidden`. An older phone ignores both fields.

October 21, 2026, steering Watcher from the phone (#1229, [ADR-0073](adr/0073-watcher-coordinates-threads-with-its-providers-own-tools.md)): optional `watcher-phone-steer` is offered with `watcher-phone` on a Watcher desktop's phone listener; hello.accepts must contain both. A phone that negotiated it may add `delivery: "steer"` to `watcher-phone-send`. While Watcher's turn runs, the desktop then steers the words into that turn when Watcher's provider takes a steer, under the desktop's steer rules: they join the request the turn answers, or open one of their own with the phone origin. Otherwise, or when the steer surely did not go, it queues them as one of the user's follow-ups in Watcher's queue, under the same draft ID, to go next as their own turn; such a follow-up takes a request of its own, with the phone origin, when it is delivered. It keeps the phone's origin, text-free and never sent to a client, and goes only while that phone is still paired and phones are admitted, asked again at dispatch and at the writer; a revoked phone's follow-up fails unsent, as its own send would. While no phone listener runs to say so, it waits. A steer that may have gone is never queued too: the send refuses `DELIVERY_UNCERTAIN`. With Watcher idle the field changes nothing. A send that carries the field from a phone that did not negotiate the feature refuses `invalid_request`. Success is `{status:"ok",draftId,state}` as before, whether the words steered or wait. Every phone operation reports its own outcome, never an error the desktop was already showing, and never a file system's own words. A send without the field while Watcher works refuses `THREAD_BUSY` with words saying so; it was `PROVIDER_UNAVAILABLE` with generic words before.

October 23, 2026, the machines line on the phone (#1032, part of the Owl feature Work across machines): optional `watcher-phone-machines` is offered with `watcher-phone` on the Owl desktop's phone listener only while Work across machines is on, read once at start. A phone whose hello accepts it is sent `machines` on every Watcher page, in its shell and in each phone operation's answer: `{ readAt, rows }`, where `readAt` is when the desktop last read its machines (null before any read) and each row is one machine, This computer first, then each paired machine: `hostId`, `name`, `thisComputer`, `connected` (the saved host's connection now), `working` (threads working there, counted from that machine's own list), `starting` (its work placed but not started), `isDefault` (new workers start there), `cpuState` and `memoryState` (null while the machine has not been read), `system`, `logicalCpuCount`, `totalMemoryBytes`, `cpuBusyPercent`, `windowMs`, `availableMemoryBytes` and `loadObservedAt`, each nullable, `unknownWhy` (the desktop panel's sentence when the load, or half of it, reads unknown) and `threads`, the first six working there as `{ title, who }`. The phone says the line's words itself. `watcher-phone-read` may then carry `machines: true`, which reads every machine afresh before answering; the iPhone sends it when the user opens a machine's panel and once for each set of Watcher's start receipts it has not read for, never on a timer. From a phone that did not negotiate the feature it refuses `invalid_request`. An older phone ignores the field, and a desktop with Work across machines off neither offers the feature nor sends the field.

For such a phone the page adds optional `current.steers`, whether Watcher's provider takes a steer, and `followups`: the user's own follow-ups waiting in Watcher's queue, from the phone or the desktop, first in line first and at most fifty, each `{itemId, draftId, text, status}` with status `queued`, `dispatching`, `uncertain`, `failed` or `paused`. Wake-ups, Watcher's news, Watcher's own sends and delegated briefs are never listed. A phone that did not negotiate the feature gets neither field. A draft listed there is waiting, not lost: a phone reconciling a lost acknowledgement treats it as taken.

## Versions and features

Every host advertises two things beside `v`:

- `sottoVersion`: the Sotto release the host runs, such as `0.1.16`. It says which build answered; it is not a compatibility rule by itself.
- `features`: the host features it offers. The shared host features are: `client-liveness` for client-owned keep-alive pings, `message-aliases` for native message identity repairs, `detail-delta`, `git-refs` for the branch picker's request, `git-changed-files` for the commit dialog's, `git-pull-request` for the Pull request surface's, `attachment-staging` for the `stage-attachment` and `attachment-content` requests (ADR-0031), `host-folders` for the folder browser's request (ADR-0025, September 26 amendment), `provider-sign-in` for the four sign-in requests (ADR-0037), `client-updates` for the `queue-client-updates` and `cancel-client-updates` commands (ADR-0042, September 29 amendment), `activity-summaries` for activity records cut down to what a summary row shows (ADR-0025, October 3 amendment), and `model-catalog-revision` for shells that name the model catalog by its revision instead of resending it ([below](#model-catalog-revisions), ADR-0028, October 3 amendment), and three for a thread's Tools (ADR-0025, October 5 amendment): `thread-files` for the `thread-files` and `thread-file-preview` requests, `thread-changes` for `thread-changes` and `thread-changes-review`, and `subagents` for `subagent-page` and `subagent-assignments`. It also offers `answer-receipts` for exact question-answer acceptance and `answer-check` for an explicit fresh provider recovery read, and `atomic-send` for a composer draft carried with its Send command and targeted composer saves, and `draft-revisions` for stable composer/Send revisions, conditional recovery saves and private save outcomes (ADR-0025, October 6 amendment), and `background-refresh` for a `refresh-thread-worktree` the window made on its own (ADR-0027, October 7 amendment), and `pull-request-babysit` for the `babysit-pull-request` and `stop-babysitting` commands (ADR-0061), and `pull-request-view` for the iPhone's pull request sheet (ADR-0102), listed only where the host's own Owl answer turns `iphone-pull-request-view` on, on either listener. A headless host lists these features; the desktop's phone listener lists all but `provider-sign-in` and `client-updates`, and `pull-request-babysit` only while this computer reads GitHub for its threads. A host that offers `client-updates` also lists `client-update-outcomes` (October 21, 2026, ADR-0077): its `check-client-updates` keeps what an update already run said about a client while it still describes the client, the same version installed and the same release, so a desktop asks it to check afresh whatever its readings hold. Like `client-updates`, only a desktop is offered it. A host that does not list it may set those findings aside when it checks.

`terminals` is retired ([ADR-0111](adr/0111-terminal-mode-is-removed.md), October 22, 2026). The desktop's phone listener offered it for Terminal mode's rows (ADR-0066); no host offers it now. A client whose hello still accepts it, an iPhone from before then, receives `shell.terminals` as an empty list, which settles any terminal answer it was still waiting on; any other client receives no such field.

A client reads `/v1/health` before it opens a session, and uses a feature only when the host lists it. It never finds out by sending a request and reading the refusal. Feature names it does not know are ignored.

Features can also differ by client. A headless host's **tailnet listener** carries paired desktops as well as phones (ADR-0053), and its health lists every feature the listener offers. Its hello lists the ones this client may use: a desktop gets every feature health lists, and a phone all but `provider-sign-in`, `client-updates`, `watcher-control` and `watcher-reads`. The host refuses a phone's sign-in requests with `invalid_request` and its `queue-client-updates` and `cancel-client-updates` commands with `forbidden`. So on that listener a client uses a feature only when its hello lists it. A client is a desktop there only when the launch script recorded it as one over SSH ([below](#the-launch-script)); every other client is a phone. The listener with administrative routes still treats every client as a desktop for its older features; Watcher's two features require the SSH record on both listeners, and an unrecorded origin is refused with `forbidden`. So does `host-update` ([below](#a-host-that-updates-itself-october-16-2026)), which also needs the client's `remote-answer` policy: a hello lists it only for a recorded desktop that may answer, on either listener.

A host whose health carries no `features` predates the freeze, and one with another `v` speaks another protocol. The desktop sends such a host nothing more and says which side to bring up to date. For a host whose `sottoVersion` is older, or that advertises none: "This host is running a different version of Sotto. Nothing on the host was lost. Put the Sotto 0.1.16 host in its installation folder, press Stop host, then connect again.", naming the desktop's own version, because Connect starts whatever is installed. For a host Sotto did not start, "press Stop host" becomes "stop the host on that machine". For a host whose `sottoVersion` is newer: "This host is running a newer version of Sotto than this computer. Nothing on the host was lost. Update Sotto on this computer, then connect again." The Hosts page keeps Stop host beside the first sentence for a host Sotto started.

Between two v1 builds of different Sotto versions, the thread and command shapes inside the envelope can still differ. When a host of another version refuses a request as unreadable, or sends something the client cannot read, the desktop says the same sentence instead of "This request is not supported" or closing the socket.

October 17, 2026 contract (#1107, [ADR-0087](adr/0087-opencode-is-a-thread-provider.md)): every listener lists `provider-opencode`. A desktop or phone from before OpenCode reads provider IDs against a list without `opencode` and refuses a whole shell that names one, so the host sends OpenCode's provider row, models, projects, threads, thread drafts, client updates and settings only to a client whose hello accepts `provider-opencode`. To any other client it sends nothing of OpenCode from any field: no skill catalog, delivery, follow-up, draft receipt, busy or unconfirmed-settings entry of an OpenCode thread, no link a thread keeps to one it continues, is continued in, was delegated by or began from, no active OpenCode project, and no OpenCode model a client host's agent setting names. Watcher's answers are filtered the same way: a Watcher read, its projection, a phone's Watcher state in the shell and every `watcher-phone-*` answer leave out each row, worker, project, card, receipt and watch that names an OpenCode thread, project or model, by its provider or by its target alone. Stop all is the one exception: its confirmation lists every thread it will stop, one of a provider the client does not know by its title with no provider, and its result keeps a row for each of them by its target, so the client hears which it could not stop. To that client an OpenCode thread is hidden as a phone's Watcher threads are: its events are left out of pages, and `detail`, `events` for it, `observe` and every command that names it are refused with `forbidden` or leave it out, and so are a Watcher read or direction and a phone's Watcher watch, send or answer that names an OpenCode thread, project or model, before the host acts on it. A handover from an OpenCode thread in another thread's message, in a detail, a delta or an event, loses its record of where it came from. The desktop accepts it, and so do the iPhone and Android clients from #1107 on. `opencode-sign-in` is desktop-only, listed by a headless host whose OpenCode runs (an Owl one, or a stable one from 0.1.40), and answers the `opencode-sign-in` request above.

## HTTP

All on the host's loopback listener, reached through the SSH forward or private Tailscale HTTPS. The desktop's own listener, with phone access on, is reached at `https://<machine>.<tailnet>.ts.net:8443`, or `:10000` when another app holds 8443 on that computer, through Tailscale Serve (ADR-0033). A headless host opens a second loopback listener, the tailnet listener, on a port it remembers, which Tailscale Serve on its machine carries the same way while the host's `phoneAccess` or `tailnetConnections` setting is on; that one has no administrative routes (ADR-0050, ADR-0053). The listener with the administrative routes is never served. Every response is JSON with `Cache-Control: no-store`, except a question's page. A request carrying an `Origin` other than a loopback page, or one the host was started to allow, is refused, except a question's page.

While the host's phone access is off and its tailnet listener is up for desktops, that listener answers `/v1/pair` with 403 `forbidden`, since a desktop never pairs there, and answers `/v1/session` and the socket upgrade with 403 for every client that is not a desktop. A phone already connected is closed within a second of phone access turning off, and a phone's `hello` in that second is refused with `forbidden`; a desktop stays. The 403 says the pairing is kept, where 401 says to pair again, and its message names the host and the switch that lets phones back in, so a phone shows it and keeps trying.

## The socket

`GET /v1/socket` upgrades to a WebSocket (RFC 6455, version 13) with `Authorization: Bearer <session>`. Every message is one UTF-8 JSON text frame of at most 16 MiB. The host allows 32 clients, 100 requests a second and 32 unanswered requests per client, and closes a client that goes over. An authenticated upgrade at capacity receives 503; its pairing stays valid. An upgrade 401 from an older host does not imply revoked pairing; `/v1/session` checks that.

A client opting into `client-liveness` in hello's `accepts` initiates pings every 25 seconds. For that client, the host counts incoming bytes, including partial frames and pings, and outgoing frames as progress. It closes only after 75 seconds without progress and with no output buffered. With the 25-second timer, a dead opted-in peer closes within 100 seconds of the last progress once output has drained.

Every other client keeps host pings every 25 seconds. Host pings and Node desktop-client pings require two consecutive silent rounds before closing. Any received bytes reset silence, even before a frame is complete. A round with frames written since the previous ping, or output still buffered, cannot count as silent: a tunnel may drain Node's buffer before the peer receives those frames. The heartbeat's own ping is excluded from write progress. A completely silent connection closes at 75 seconds from heartbeat startup; after traffic or a final drained application write, closure occurs within 75 seconds. Continuing traffic or buffered writes defer this bound. This is an additive v1 capability; older clients need no change.

The phone allows ten seconds per liveness round and requires two consecutive silent rounds before closing. A pong, received message or growth in URLSession's received-byte counter resets silence; an outstanding request within its deadline prevents a silent round. Detail and observe requests have 120-second deadlines, so pending large reads do not depend on the byte counter. URLSession does not guarantee partial-frame counter updates; a slow unsolicited push without such updates remains a physical-device verification limitation. With no request or progress, the phone closes at about 60 seconds after opening. An unanswered detail expires at 120 seconds and the next two silent checks close by about 160 seconds.

### Compression (October 18, 2026)

A desktop's messages may be compressed with `permessage-deflate` (RFC 7692). The desktop's host client offers `Sec-WebSocket-Extensions: permessage-deflate; client_no_context_takeover; server_no_context_takeover` in its upgrade. The host answers `permessage-deflate; server_no_context_takeover; client_no_context_takeover` only when the client offered the extension and is a desktop: on the listener the host machine and SSH reach, every client is one, and on a tailnet listener only a client the launch script recorded as a desktop is, the record being read again first when a client that offers is not in it. Phones are not answered with it, on any listener, even when their WebSocket stack offers it, as Android's OkHttp does, and the desktop's own phone listener never answers with it. A client the host did not answer with the extension is never sent a compressed frame, and a frame with RSV1 from a client that did not negotiate closes the connection like any other bad frame. A host from before October 18 ignores the offer, and the desktop then reads its messages as they come. An answer the desktop never offered, such as one without `server_no_context_takeover`, fails that upgrade as RFC 7692 requires, and the desktop opens the socket again offering nothing, so a host or a proxy that gets the extension wrong still connects, uncompressed.

Neither side keeps a compression context between messages, so each compressed message stands alone. A text message under 1 KiB goes uncompressed, as the extension allows for any message, and so does one that would not shrink; control frames never are compressed. A compressed message sets RSV1 on its first frame only. The 16 MiB limit applies twice: to the frames as sent, and to the message once inflated, so a message that inflates past 16 MiB closes the connection. The 32 MiB of unread output a client may hold is still counted by each message's uncompressed size, and every `too_large` refusal still means the message's uncompressed JSON would not fit.

The host compresses at zlib level 6, and a desktop compresses what it sends the same way, a staged image among it. A message up to 64 KiB is compressed at once; a larger one is compressed on Node's thread pool so the host keeps serving other clients, and the messages sent after it wait for it, so a connection's messages arrive in the order they were sent. A message still being compressed counts as output the client has not read, so a shell push waits for it as it waits for any backed-up output. Inflating stays on the loop where the message arrives: it is several times faster than deflating.

A request from this session that the host cannot read, such as one from a client of a newer Sotto version, is answered with `invalid_request` by its `id`; a message that is not JSON, or has no readable `v`, `id` and `session`, closes the socket.

A question draft sent through `send` keeps an uncertain answer outcome in its command reply and receipt. Its editor stays active with the saved answer; the shared desktop shell stays clear of that uncertainty. Replaying the same command cannot send the answer again.

When the host advertises `atomic-send`, a `send` command may include a strict `draft: { threadId, text, attachments? }`. Main stages and sends that draft within one command admission, so a concurrent Check cannot release an uncertain answer between separate Compose and Send calls. The thread must match this authenticated client's selection, nested handles are verified, and a native question requires current answer authority even when no question draft was saved yet. Unsupported hosts receive no atomic packet or two-command fallback; the desktop reports that the draft is kept on this computer and has not been saved on the host, and asks for an update. The same feature permits optional `compose.threadId`, which must match the authenticated selection and keeps an autosave on its original thread when Send advances the queue. A targeted Compose preserves an existing nonempty null prompt binding; it requires answer authority only when bound to a question. Omitted images and other draft fields inherit from earlier edits at execution only for that same thread and request binding; explicit empty images remove them. Compose settles from its command acknowledgement without fetching thread history. Payload-free `send` and ownerless `compose` retain their existing v1 behavior.

Targeted Compose settles its binding when it executes: earlier saved or empty edits on that thread take precedence over a question that appeared while it was queued. An empty binding to a closed question expires; a saved answer keeps its original binding. If an earlier accepted Send removed the bound draft and question, a queued Compose falls back to a null prompt rather than its closed captured question or a different question that arrived meanwhile. The socket still validates pairing, shape and selected thread, while the coordinator checks current answer authority against the resolved binding before saving. Send and legacy Compose keep their existing socket policy checks. Send retains its admitted binding and question form; an absent form at admission cannot become valid merely because the same request ID appears later. A different binding established by earlier queued edits causes Send to save the packet on that established binding, when authorized, and refuse dispatch.

The desktop permits at most two targeted Compose requests on the wire and coalesces a waiting batch for one thread to its latest text and last explicitly supplied images. Omitted images inherit; an explicit empty list removes them. The latest full edit is retained independently of that batch, keyed by authenticated host and Sotto thread, with its revision and original request binding. A later command flushes a batch when capacity permits without waiting for save acknowledgements. Saturation or disconnect returns a failure for unsent work while retaining its content. Explicit command identities are never combined. Receipt, Check and ordinary read requests retain room in the connection's shared request limit.

Recovery uses an exact-bound `save-thread-draft`, subject to current answer authority, and never replays Send or Answer. A recovered question carries its original optional `questionsDigest` alongside `requestId`; the host requires the same current question and form before saving it. Prompt recovery omits the digest and keeps its null request binding. An atomic Send may additionally carry `draft.binding: { requestId, questionsDigest }`: both null for a prompt, or an ID and SHA-256 question digest for an answer. Main validates that expectation against its own binding and form before admitting the command, then retains its immutable execution checks. Client-side observation alone cannot authorize a later question. Missing images and failed storage retain the local edit without claiming a complete host save. The desktop's local recovery file follows Keep local history, and only exact acceptance or deliberate clearing retires the matching revision.

With `draft-revisions`, targeted Compose accepts optional `draftId: UUID`, atomic Send accepts `draft.draftId: UUID`, and recovery save accepts `expectedDraftId: UUID | null`. The host preserves these submitted revision IDs. Recovery requires the current host revision to match its expected base before mutation; retrying the exact same revision and full contents is idempotent. Known revision reuse with changed contents or another owner is refused. An ordinary Compose acknowledgement can establish the host's resolved question binding only after matching complete saved contents and durability; a recovery acknowledgement cannot rebind its original question. Targeted Compose and socket draft-save successes, warnings and refusals are command-local. Legacy ownerless Compose retains its existing behavior.

The desktop marks a retained revision before placing Send on the wire, flushing that mark first when local history is enabled. Lost replies leave it held, never restored automatically as an unsent draft. Newer edits retain the earlier attempt's uncertainty until exact proof settles it. Host packet identity uses the existing bounded delivery/outbox records and digests; replay cannot change an admitted packet's contents. No delivery command is replayed by recovery.

The optional `obsoleteDrafts` shell field names up to 128 exact `{ threadId, draftId }` revisions that the host superseded or explicitly cleared. Confirmed sends and matching positively accepted question drafts use `deliveredDrafts`. Exact proof retires the matching local revision. A saved copy also stops overriding an authoritative reconnect or live snapshot after its host revision or owner is gone, even after old proof expires. Older command acknowledgements and reads begun before newer observations cannot retire the new copy. Unsaved local edits and uncertain Sends remain protected.

### Pushes

A push has `event` in place of `id`. The host coalesces them the way the desktop's IPC does: the shell, and each thread's detail, go out at most once every 50 ms. A shell push carries the state as it is when it is sent; deltas waiting for one thread are folded into one where they can be and otherwise sent in order. A thread's delta that brings a message or an activity record its pushes have not carried yet is not held for the window: it goes at once, after anything waiting ahead of it, so a reply's first words are not held behind the echo of the prompt. Only one such delta cuts a window short; another in the window it starts, or in the window after a push that carried one held back, waits for the window's end. Later changes to that message or record wait for the window again.

Pushes are also paced to what the client reads. While output to a client is still backed up in the host's side of its socket, the host sends it no further shell; once that output drains, the host sends the newest shell, built then, with an event page from the client's own place in the event stream. A slow link therefore gets shells as fast as it reads them, with never more than about one waiting in the host's buffer, and a shell it is not sent loses no event. A `watcher-state` push waits with the shell, and the projection sent once the output drains is the newest.

A thread's `detail` and `detail-delta` pushes wait the same way (October 21, 2026, #1089). While a client's output is backed up, the host holds one update for each observed thread, folding every later one into it: consecutive deltas become one delta from the revision the client holds to the newest, removals included, and a whole detail followed by deltas becomes the newer whole. Deltas that do not follow each other, or a fold that names more entries than a thread holds activity records, give way to the thread's whole detail as it is when it goes. A thread the client starts observing while behind is sent its first whole with the changes made while it waited. Once the output drains the held updates go a thread at a time, and wait again whenever the output backs up. Each still follows the revision it applies to, so a client applies them exactly as it would deltas sent as they happened, and one already covered by a whole detail sent since, as `observe` sends, is not sent. A client that reads slowly is therefore sent one delta for what changed while it was behind rather than every delta in turn, and a busy thread's growing records no longer fill its socket until the host closes it. Answers are never held back, and a `detail` read answers with the thread as it is. A read answered while a delta is held for that thread can leave the client holding a revision partway through it, so the client is then sent the thread whole as it is rather than a delta that does not start from what it holds. Nothing changes on the wire, so every client, older ones included, takes these pushes as it did. The host still closes a client whose unread output would pass 32 MiB, twice the frame limit.

A shell push whose `state` is byte for byte the state of the last shell push written to that client, and whose event page would carry no events and no `hasMore`, is not sent (October 18, 2026): the client already shows it. Its place in the event stream does not move until a push tells it where it is. A hello, a `shell` read or a command answers with a shell of its own, so after any of them the next push is sent whatever it repeats, and a new connection starts with nothing remembered. The time a phone's Watcher page was read, `watcher.observedAt`, is left out of the comparison (October 23, 2026): it is new on every read, so with it no shell to a phone running Watcher ever repeated, and every publish sent that phone its whole shell and Watcher's conversation again. A push that goes carries the page's time as it was read then. An answer to a `watcher-phone-` request carries a page of its own, so after one the next push is sent whatever it repeats, as after a shell read. A phone's shell leaves `lastUser`, `lastAssistant` and `activityCount` out of each thread row's `summary` (October 26, 2026): a working thread changes them with every word and step, no phone reads them, and with them every publish sent a phone its whole shell while any thread worked. A desktop's rows keep them.

The desktop keeps the drawing itself in a `visual` field that no socket client is sent, in a `detail`, a `detail-delta` or a read, so a client shows the text as it would any reply.

Every shell returned by hello, a read or a command, and every shell push, may include `clientCapabilities: { mayAnswer }`. This is the receiving client's current host policy, read when that shell is sent. Changing Can answer publishes a new shell even if no thread changed. Older hosts omit the field; those clients retain the authority from hello until reconnecting. The field reports authority and never grants it.

A receipt lookup without acceptance watches that exact client, command and answer target for later native acceptance. Each connection retains at most 512 watches and removes a watch after sending its proof. Unrelated thread updates do not cause receipt polling. The desktop matches a pushed proof against a target it already queried; an older negative reply cannot erase that proof. This settles a delayed native callback even after the question disappeared and the command stopped being busy. A reconnect looks up held answers again without replaying them.

A thread in the shell may carry `finishedUnread: true`: it finished while no client observed it, and no client has observed it since (ADR-0046). The host sets and clears it and saves it across a restart. Observing the thread, with `observe` or the `observe-threads` command, is what clears it, for every client, and the next shell says so. Older hosts never send it, and a client that does not know it ignores it.

A thread in the shell may also carry `providerSessionOpen: true`: its provider session is open on the host now, so its next send will not start it (ADR-0057). The host's adapter sets and clears it as the session starts and stops; it is never saved, and a disconnected provider's threads never carry it. A desktop asks for no early start for a thread that carries it. Older hosts never send it, and a desktop then asks once per thread for as long as its window runs. A client that does not know it, such as the iPhone client, ignores it.

### Model catalog revisions

A client that includes `model-catalog-revision` in hello's `accepts` is sent every shell with `host.modelsRevision`: a positive number naming the host's model catalog as this connection is sent it, which moves on only when that content changes. A client that does not know a provider is sent the catalog without its models (`provider-opencode`), and its revision counts that list's changes alone. That holds for the shell in hello, a `shell` read, a command's answer and every shell push alike. Such a shell carries `host.models` only when no frame on this connection has carried that revision whole yet, and otherwise leaves `models` out. A revision counts as sent only once a frame carrying it was written, not when a `too_large` error went in its place. Hello always carries the catalog whole, and a new connection starts with nothing sent.

The client keeps the last catalog this connection carried whole, with its revision, and puts it back into every shell that names that revision before anything reads the shell. It keeps it in the order frames arrive, so a reply read after a later push is still matched with the catalog that was current when the reply arrived. A shell that names a revision the client does not hold should not happen. The iPhone then drops the connection and connects again, and that connection's hello carries the catalog, rather than show the computer with no models.

A revision means something only on its own connection to its own listener; a client never compares one across connections. Only `host.models` is named this way. The desktop's own host client accepts it too (ADR-0028, October 16 amendment) and puts the catalog back the same way, a shell naming a revision it does not hold closing the connection so the desktop connects again. A client that does not accept the feature, such as every iPhone build before it and earlier desktops, is sent `models` whole in every shell and no `modelsRevision`, exactly as before.

### Detail deltas

A delta is `{ threadId, baseRevision, revision, messageDeltas, activityDeltas }`, the same form the desktop's window gets over IPC (`AgentThreadDetailDelta` in `src/shared/agents.ts`, arithmetic in `src/shared/agentThreadDetail.ts`). A message delta is a whole message `{ message }`, or `{ id, appendText }` for text a streaming message grew by. An activity delta is a record as it now stands `{ record }`, or `{ id, removed: true }`.

A client applies a delta only when `baseRevision` is the revision it holds: appended text goes on the end of that message, a whole message replaces the one with its ID or goes last, a record replaces the one with its ID in place or goes last, and a removal drops it. It then holds `revision`. A delta whose `revision` is not newer than what it holds is already covered and is dropped. Any other delta means a push was missed: the client asks for the whole thread with `detail`, once however many deltas miss, and applies deltas again from the revision that returns.

When a thread is too large to send, its `error` push names it. A client does not ask for that thread again because a delta did not follow; observing it again, or its whole detail arriving, starts it over.

### Activity summaries

A client that lists `activity-summaries` in hello's `accepts` is sent every activity record as its activity summary: in each `detail` push, each `detail-delta` push and the answer to each `detail` request. A summary keeps `id`, `turnId`, `sequence`, `kind`, `status` and `title`, and, where the record has them, `command`, `exitCode`, `durationMs`, `startedAt` and each change's `path` and `kind`. Everything else stays on the host: a command's `output` and `cwd`, a record's `text` and `error`, each change's `diff`, a plan's `steps`, a workflow's `agents`, a compaction's `context`, and the record's other times and anchors. A summary is still a valid activity record, and a delta of summaries has the same revisions, so a client applies it exactly as it would a delta of whole records. Messages are unchanged.

The host makes a thread's summaries once for each update and sends the same ones to every client that accepts them. A client that does not accept the feature, including the desktop's own host client, is sent every record whole. The iPhone accepts it, since its activity list reads nothing else; on a long thread this cuts a detail by about nine tenths (`docs/perf/2026-10-03-activity-summaries.md`).

### Cut bodies

A desktop that lists `activity-bodies` in hello's `accepts`, and not `activity-summaries`, is sent every activity record with each long **body** cut: in each `detail` push, each `detail-delta` push and the answer to each `detail` request. The bodies are a record's `output`, its `text`, and each change's `diff`. One over 2,048 UTF-8 bytes is cut to at most 2,048 bytes, at a line break so no line shows half, and never inside a UTF-16 surrogate pair. `output` keeps its end, where a command's result is; `text` and diffs keep their start. A window with no line break in it keeps nothing, and the desktop says the body is on its way instead.

`text` that parses as a JSON object or array, as a tool's input does, stays valid JSON. It is written compactly, and each string value in it longer than its share is shortened, at a line break where one is in reach, so a file path or pattern stays whole for the row's preview. Only if that still leaves it over 2,048 bytes is the raw text cut as above. JSON that fits once compacted, with no string shortened, is not marked cut. A reasoning, plan, status or turn record's text is never read as JSON.

A record with a cut body carries `cut: { output?, text?, diffs?: [{ index, bytes }] }`: each cut body's whole size in UTF-8 bytes, a diff's by the index of its change. Every other field goes whole, so a row keeps its place, nesting, steps, agents, times, error, folder and the rest. A record with no body over the limit is sent as it is, with no `cut`. `cut` is an optional field of the activity record, which a client from before October 18 strips, and which no client that does not accept the feature is ever sent.

The record's signature, which decides whether a delta carries it ([Detail deltas](#detail-deltas)), counts the sizes `cut` names, so a running command's delta carries its new cut although the end it keeps can stay the same length. The host cuts each record once and shares it between every desktop and every detail it goes in, and cutting the 3.6 MB benchmark thread takes about 7 ms (`docs/perf/2026-10-18-remote-thread-open-bytes.md`).

The desktop reads a record whole with `activity-body` when its row opens, never ahead, and keeps it for the session outside the thread's detail, so a later delta replacing the record does not lose it. A record whose signature changed shows its new cut, and its row asks again if it is open. The iPhone and Android clients keep `activity-summaries`.

| `unauthenticated` | The session or token is not valid any more. Connect again or pair again. |
| `invalid_request` | The host cannot read or does not support the request. |

### Message identity repairs

A client that includes `message-aliases` in hello's `accepts` may receive `message-aliased` events in hello, event pages and shell pushes. Each carries `at`, `messageId` and `canonicalId`; only the duplicate projection row is removed, after comparing the saved content. Original events remain. Without this opt-in the host omits these events and advances `latestSeq` over them, even when a page becomes empty. Such clients read the corrected history from thread detail; the original version 1 event union is unchanged for them.

The active iPhone reconnects with exponential delays starting at about one second, a 0.8–1.2 random multiplier and a thirty-second cap. Only a successful liveness round resets the delay. Reconnecting reads fresh state and reconciles receipts without resending commands; backgrounding cancels retries. Compose, send and draft controls use the receiving peer’s selected Sotto thread ID. They preserve drafts for other threads, and question answers still require the remote-answer policy.

## The launch script

The desktop runs the launch script over SSH (`src/main/hosts/launchScript.ts`), one operation per `ssh`. It is not part of the socket protocol, but what it reports is how a desktop finds a host and what it may do with it.

A launch answers `{ type: "ready", v: 1, status: "ready", hostId, pid, port, owned, node, adminToken?, tailnetAddress?, startedBy?, bootStart }`: `node` the Node the script ran under, `tailnetAddress` and `startedBy` as the host's descriptor records them, and only an `https:` address on a `*.ts.net` name with a port. Serve comes up a few seconds after a host starts, so a launch that started the host often has no address yet; hello carries it once there is one.

A host the launch script started records `startedBy: "launch-script"` in its `host-listener.json`, and a host its start at boot unit started records `startedBy: "boot"` (ADR-0054). Either counts as started by Sotto, as does any host this installation's unit runs, so Stop host, Forget's stop and Update apply to it. A host refused because another live host holds its data folder exits with code 75, which the unit does not retry; every other refusal exits with 1.

Every result that starts or finds a host, a launch's and an update's restart's, carries `bootStart`, start at boot as the host's machine has it: `{ supported, reason?, installed, enabled, active, linger, nodeDrift, fix? }`. `reason` is `macos` or `no-user-manager` when it is not supported, and `fix` is `sudo loginctl enable-linger <user>` when it is supported and the account does not linger; an unsupported host never carries one. `boot-status` answers the same fields with `type: "boot-status"`. `boot-install` answers `{ type: "boot-installed", installed, stopped, pid?, bootStart }`, with `installed: false` and the `fix` when linger could not be turned on, and `boot-remove`, given `restart`, answers `{ type: "boot-removed", stopped, pid?, bootStart }`. `stopped` says whether the host the desktop reached was stopped, so the desktop knows to connect again. A failure is `{ type: "error", reason }`, the reasons being the launch script's own codes:

- `boot-unit-taken`: another installation's unit holds the name, and nothing was changed.
- `boot-install-failed`: the user manager would not reload or enable the unit, which was taken away again, or a folder's name holds a control character a unit cannot carry; the host is untouched.
- `boot-stop-failed`: the host Sotto started would not stop, so the unit was taken away again; the host keeps running.
- `boot-start-failed`, with `restarted` and `cause`: the unit did not bring the host back after the install stopped it, so the unit was taken away again and the host was started the way a launch starts it. `restarted` says whether that worked, and `cause` is the first start's own code, such as `boot-start-refused`.
- `boot-remove-failed`: the unit's files could not be removed.
- `update-busy`: an update or another change to start at boot holds the installation folder.
- `archive-missing`, `descriptor-invalid`, `port-taken`, `host-busy`, `host-timeout`, `host-start-failed`, `boot-start-refused` and `boot-unit-failed`: a start the operation asked for failed as a launch's would. The last two mean the unit would not start the host or would not keep it running.
- `boot-failed`: anything else.

`desktop-answers`, which the desktop runs on every SSH connect once the host's hello has confirmed its paired client ID, writes the desktop's default `remote-answer` grant when it has no policy history and records the client in `desktop-clients.json` in the host's data folder. That file, a JSON array of client IDs that only this step adds to, is how the tailnet listener tells a desktop from a phone. The host takes a client out when it is revoked, and reads a file it cannot parse as naming nobody. The step writes the file whole and renames it into place, and leaves alone a file it could not read this time. For a desktop that may already answer, only the record is at stake, so the desktop carries on when the step fails and records itself at its next SSH connect; for one that cannot answer yet, a failed step still fails the connect.

## A host that updates itself (October 16, 2026)

[ADR-0088](adr/0088-sotto-leans-on-tailscale.md). A headless host that Sotto started (`startedBy` is `launch-script` or `boot`), running from a release's own layout (`<installation folder>/host/index.js` or `<installation folder>/versions/<version>/host/index.js`), offers the optional `host-update` feature and runs the launch script's update operations on itself when a desktop asks over its socket. It offers it on both listeners, and health lists it there. Hello lists it only for a client the launch script recorded in `desktop-clients.json` whose `remote-answer` policy lets it answer; `--deny-answers` on the host takes it away at the next request. A phone, a desktop the host does not know as one and a desktop without the grant get `forbidden`, and a host that does not list the feature, or a request before hello, gets `invalid_request`. Every addition is optional, so `v` stays 1.

The request is `{ op: "host-update", action, version?, file?, sha256? }`, with `action` one of:

- `fetch` with `version`: the host downloads its own archive for that release from the published releases page and checks it against its `.sha256` sidecar. Answers `{ type: "update-fetched", file, sha256 }`, which `install` takes back. The asking client's `cancel`, or its socket closing, ends the download, and the answer is then `{ type: "update-cancelled", cancelled: true }`.
- `install` with `version`, `file` and `sha256`: the host checks the archive again and unpacks it beside the running version. `file` must be the name `fetch` gave for the host's own system. Answers `{ type: "update-installed", version }`. It finishes even when the asking client's socket closes partway.
- `restart` with `version`: the version must already be installed. The host starts the launch script's restart in a process that outlives it and answers `{ type: "update-restarting", version }` once the restart has passed its checks, within about ten seconds; the restart then stops this host and starts the new version, or starts this one again when the new one does not start. The client's connection drops with the host, as it does over SSH. While a restart already answered for is still running, another `restart` answers `update-busy` and changes nothing, so the first one's status stays for `outcome`.
- `cancel`: ends this client's own download. Answers `{ type: "update-cancelled", cancelled }`, false when it had none running.
- `outcome`: how the last restart over the socket went, for a client that has connected again. Answers `{ type: "update-outcome", running, restart }`, where `running` is the version this host runs and `restart` is `{ state: "none" }`, `{ state: "restarting", version, attempt? }` while the restart has not finished, or `{ state: "finished", version, attempt?, result }`, with optional `attempt` naming the status file's restart attempt, so repeated identical results can be told apart, and `result` either `{ type: "ready", hostId, pid }` for the host it started or `{ type: "error", reason, restarted?, cause? }`. A restart whose process has gone before it finished, or whose `restarting` is older than any restart takes (about two and a half minutes), was interrupted, as by a kill or the machine restarting: it reads as finished with `update-lost`, and `running` says what the host runs now.

Any action can answer `{ type: "error", reason, ... }` with the launch script's own reasons, the ones the desktop already turns into sentences for an update over SSH (`update-busy`, `checksum-mismatch`, `update-start-failed` with `restarted` and `cause`, and the rest). `update-invalid` also covers a version that is not a release number or not newer than the one the host runs, by the rule the desktop uses to decide a host needs an update; the host refuses an older or equal version at every step, so a client cannot move it back to the version `versions/` still keeps. `restart-not-sent` means the restart did not pass its checks in time, and nothing was touched. The client never sends a URL, a path, a Node or any setting: the host builds them all from its own command line and location, and downloads only from the releases page Sotto publishes.

One update runs at a time. A second action while one runs answers `update-busy`. Every step of the launch script holds the installation folder's update lock while it runs, the download as well as the install and the restart, over SSH or on the host itself, so an update over SSH and one over the socket refuse each other with `update-busy`; a lock held by a process that has gone is taken over by one update at a time, the one that places `.update-lock.takeover` beside it, which looks again and removes only a lock still stale, so updates taking over the same stale lock never both own it and a live lock is never removed.

`host-update-step` pushes `{ step }` to the asking client while its action runs: `download` and `check` during `fetch`, `install` during `install` and `restart` before the restart starts.

Each restart over the socket is one attempt, which the host names with a random token (`attempt`, 8 to 64 lowercase hex digits). The restart writes `host-update-status.json` in the host's data folder: `{ v: 1, attempt, version, state: "restarting" }` once its checks pass, then `{ v: 1, attempt, version, state: "finished", result }`. Before either, it claims the attempt by making `host-update-status.json.<attempt>.claim`, which only one process can make. A host that stops waiting makes it first and writes `restart-not-sent` as the attempt's result, and a restart that reaches its checks after that stops without touching anything; since every attempt has its own claim, a later attempt cannot revive an earlier one. A restart that claimed its attempt but could not write its status does not go ahead either, and the host answers `restart-not-sent`. The host answers only from a status with its own attempt. Once the host has handed its `update-restarting` answer to the client's socket, it writes an empty `host-update-status.json.<attempt>.answered`, and the restart waits up to five seconds for that before it stops the host, so the answer is not cut off with the connection. The host clears the status file when a new restart begins, takes away claim and answer files older than ten minutes, and reads at most 4 KiB of the status file.

For a host its start at boot unit runs, the restart runs in a transient user unit of its own, `sotto-host-update-<id>`, through `systemd-run --user --collect`, since stopping `sotto-host` kills everything in that unit's cgroup ([ADR-0054](adr/0054-a-host-can-start-at-boot-on-linux.md)). Otherwise it runs detached in its own session.

The desktop accepts `host-update` in its hello whenever health lists it, and reads `host-update-step` for the step it asked for ([ADR-0088](adr/0088-sotto-leans-on-tailscale.md), the October 16 amendment, as built). It uses the route only on the host's tailnet connection, and asks `outcome` once it has connected again after `update-restarting`, or after a restart whose answer never came. Over the host's SSH connection it keeps running the launch script there.

The launch script's `update-restart` takes an optional `resultFile`, a file directly in the data folder, with `attempt` and `answerWaitMs`, for this; without a valid `attempt` it writes no file, and the desktop never sends any of them over SSH. The script also reads its configuration as its last argument, so it runs the same from stdin, with `-e` or as a file.

## Branch moves (October 23, 2026)

[ADR-0082](adr/0082-work-moves-between-a-desktops-machines-over-its-own-ssh-link.md), as amended by [ADR-0105](adr/0105-hosts-reach-each-other-over-host-links-the-desktop-sets-up.md) decision 8. A **branch move** carries a committed branch between the desktop and a host as a Git bundle, in chunks, over the socket the desktop already keeps to that host, so no move opens an SSH session and nothing goes through GitHub. The desktop is the only caller today; host links will call the same request later. The request is `{ op: "branch-move", request }`, with `request.action` one of:

- `tips` with `projectId`: the receiving project's newest branch tips, `{ type: "tips", tips }`, at most 256 commit IDs from `refs/heads`, `refs/remotes` and the `refs/sotto/incoming` refs earlier moves left. The sender bundles against the ones it also has, so the bundle carries only what the receiver lacks.
- `receive-begin` with `moveId` (a UUID), `projectId`, `branch`, `commit`, `size` and `sha256`: the host is about to take a bundle of `commit` for `branch` into that project. Answers `{ type: "receiving" }`; or the move's receipt when that move already landed with that commit, so a retry after a lost answer writes nothing; or a refusal.
- `receive-chunk` with `moveId`, `offset` and `data`: the next bytes of the bundle, base64, at most 1 MiB of bytes, in order from offset 0. Answers `{ type: "received", bytes }`. A chunk out of order or past `size` discards the transfer.
- `receive-finish` with `moveId`: the host checks the bundle's size and SHA-256 against what `receive-begin` named, runs `git bundle verify` in the project, and checks that the bundle's one ref is `refs/sotto/outgoing/<moveId>` naming `commit`. It imports the objects without writing a ref, checks that `commit` names a commit (a bundle whose one ref names a blob or a tree is refused as `not-whole` and nothing is recorded), records the move with its commit, creates `refs/sotto/incoming/<moveId>/<branch>` only if it does not exist, and reads it back. Answers `{ type: "moved", moveId, branch, commit, ref }`, or a refusal.
- `receive-ref` with `moveId`, `projectId`, `branch` and `commit`: in place of the three steps above when the project's `tips` already hold `commit`, so nothing it has travels again. The host checks that `commit` is reachable from one of the project's refs, records the move and creates its incoming ref as `receive-finish` does. Answers the same; a project that turns out not to have the commit refuses with `not-whole`, and the sender's retry sends a bundle.
- `send-begin` with `moveId`, `threadId`, `bases` and an optional `snapshot`: the host checks the thread's working copy, stages a bundle of its branch's commit against the `bases` it has, and answers `{ type: "sending", branch, commit, size, sha256 }`; or `{ type: "present", branch, commit }` when the `bases` already hold that commit, so nothing is staged and the desktop only creates its incoming ref; or a refusal. Anything `git status --porcelain --ignore-submodules=none` lists refuses the move (so a repository's `submodule.<name>.ignore` cannot hide a changed submodule), and so does a working copy on no branch; with `snapshot`, uncommitted work goes as a check snapshot instead (below).
- `send-chunk` with `moveId` and `offset`: `{ type: "chunk", data }`, up to 1 MiB of the staged bundle from `offset`, base64.
- `end` with `moveId`: `null`. Discards whatever the move staged on the host, either way. Once it answers, nothing of the move lands: a `receive-finish` still importing, or a `receive-ref` still checking, creates no ref, and one already creating its ref has finished before `end` answers. A closed connection does the same for each move it held.
- `copy` with `moveId`, `threadId`, `projectId` and an optional `snapshot`: lands the thread's branch in that project's incoming ref on the same host, for a worker the desktop starts there from it (#1033). Nothing but the answer crosses the socket: when the project's refs already reach the commit, as a thread's worktree and its project's checkout share one object store, only the ref is written, as `receive-ref` writes it; otherwise, as for a check snapshot no ref names yet, the host bundles it across itself. Answers the move's receipt, `{ type: "moved", ... }`, or a refusal. Like `receive-ref`, once `end` answers or the connection closes, a copy still reading the thread, bundling or importing creates no ref. A desktop whose `copy` request fails or times out sends `end`, which fences the copy so no ref of it is created once `end` answers, then `forget`, which removes a ref a copy landed before that.
- `forget` with `moveId` and `projectId`: `null`. Removes the incoming refs that move landed in the project, for a start the desktop knows never made its thread there: a stop or a refusal after the branch arrived, or the host refusing the start outright. A move still under way on the host keeps its ref. A start whose outcome is uncertain is never forgotten, since its thread may own the ref.

`send-begin` and `copy` take `snapshot: true` for a **check** (#1033, #1312): the thread's uncommitted work goes too, as a **check snapshot**, instead of refusing the move. The host copies the working copy's index to a temporary file in its staging folder, runs `git add -A` against the copy (so `.gitignore` is respected), writes its tree and makes a commit with the branch's commit as parent, named for Sotto and never signed. No branch, no stash; the working tree and the real index are untouched, and the temporary index is removed. A clean working copy sends its branch's commit as a plain move does. A submodule with changes of its own, tracked or untracked, refuses the check as `uncommitted` with a sentence saying so, because `git add -A` in the parent takes only the submodule's commit. The answer then carries `snapshot: { untracked, untrackedCount }`, the untracked files it took (the first 200, by their paths in the working copy) and how many there were; `sending` carries it for the desktop to put on the receipt, and so does `present`, when the receiver already has the snapshot's commit; `moved` from `copy` carries it too. A host without these refuses `copy`, and an unknown `snapshot` key, with `invalid_request`; both came with the same `branch-moves` feature, before any host listed it.

A refusal is an answer, `{ type: "refused", reason, message }`, with `reason` one of `uncommitted`, `not-on-branch`, `not-a-repository`, `unknown-project`, `unknown-thread`, `too-large`, `move-differs`, `not-whole`, `cut-off`, `busy`, `unsupported` or `failed`, and `message` a sentence that says nothing moved or changed and what to do next. Git's own output never crosses the socket or reaches a log. A host that cannot run the step at all answers `unavailable`.

Each transfer belongs to the connection that began it: another connection cannot begin it again (`busy`) or take its steps (`cut-off`), and when that connection closes the host discards what it staged, so a transfer cut off lands nothing. A host takes a move's place before it does anything else, so begins that arrive together count against the limit as they are taken. Staged bundles wait in `branch-moves/` in the host's data folder, one file for each attempt, so an attempt a dropped connection left running removes only its own file and never a retry's; they are cleared at start; the move records are `branch-moves.json` beside it. One move carries at most 256 MiB; a bundle over it is refused as `too-large` on either side. A host stages at most four moves at once and refuses a fifth as `busy`. Nothing is ever forced: no ref under `refs/heads` is written, an incoming ref is created once and never moved, the ref itself is written rather than anything a symbolic ref in its place points at (such a ref refuses the move), the sender's outgoing ref is written and removed the same way and a symbolic ref in its place refuses the move as `failed` with its own sentence (something other than Sotto changed the project's `refs/sotto` folder), and a move ID that comes back with another commit, or whose ref already names another, is refused as `move-differs`.

### Starting a worker from a moved branch (#1033)

The desktop moves the branch first, then starts the worker. A Watcher start sent to a host in `watcher-control` names the move in its `start_thread` input as `fromMove`, a UUID, and nothing of the thread it came from. The host's own Watcher creates the thread with `create-thread`'s `startFromMove`, and the workspace finds the one ref under `refs/sotto/incoming/<move>/` in the project's repository. The worker's new worktree is made from it on a branch of the moved name, or the next free `<name>-<n>` when a branch of that name is already there, and the worktree record keeps the incoming ref (`incomingRef`), which is removed when the worktree is (ADR-0082 decision 3). A `create-thread` with `startFromMove` from anyone but Watcher or delegation is refused, and so is one asking for a shared checkout, an existing worktree or a base branch beside it. The input may also carry `madeFrom: { thread, host?, by? }`, Sotto's like `fromMove`: the thread whose branch it was, by its own Sotto thread ID, `host`, the desktop's host ID for that thread's machine, only when that is not the worker's, and with `host`, `by`, the host ID of the starting desktop's own computer. Only that desktop brings the worker's commits back across machines: another desktop offers nothing for it and refuses the press, and a record with `host` and no `by` is brought back by none (October 24, 2026). Being optional does not make `by` safe for every host: `madeFrom` is checked strictly, so a host that knows only `{ thread, host? }` refuses the whole start. That is safe only because `fromMove` and `madeFrom` go solely to a host that lists `branch-moves`, which no released build does: every host that lists it and lacks `by` is an unreleased build of this branch line, and is updated with it. Once `branch-moves` ships, a change to `madeFrom` needs a feature of its own. `v` stays 1. `create-thread` passes it with `startFromMove`, and the worktree record keeps it so the worker's commits can be brought back there (#1030). Watcher naming either is refused.

## Delegation relay (October 27, 2026)

A thread on a headless host delegates to a thread on This computer through the desktop (#1316, Owl `cross-machine-work`, [ADR-0105](adr/0105-hosts-reach-each-other-over-host-links-the-desktop-sets-up.md) decisions 1 and 6). A host that runs delegation for its own threads lists `delegation-relay`, on both listeners, to a client the launch script recorded as a desktop, never to a phone. A desktop accepts it in hello only where its own Owl answer turns on Work across machines and its Watcher runs, since a relayed start is placed as the desktop's own delegations are. A stable desktop never accepts it, and a stable host never lists it and refuses both requests below as `invalid_request`.

The host pushes `{ v: 1, event: "delegation-relay-ask", askId, ask }` to the desktop connected last whose hello accepted the feature and that is still paired there with an answers grant, read at every ask (Zach, October 27, 2026). It tells the relay about a desktop only once that hello's answer has gone, so an ask never reaches a desktop before it knows the feature; a desktop holds asks that come before its relay listens (at most 64) and hands them over when it does. `ask` is one of:

- `{ type: "start", relayId, threadId, levels, rootUserMessageId, callerMessageId?, runtimeMode, projectId, machine?, os?, input, waitMs }`: start a delegated thread for one of the host's threads. `relayId` is the host's own name for the ask, saved before it is pushed. `levels` is how many threads delegated above the asking one, `runtimeMode` its own permission, and `projectId` its project on the host. `input` is the `delegate` call's arguments without `machine`, `os`, `from_my_branch` and `test_run`.
- `{ type: "read", threadId, delegation? | relayId? }`: read one relayed delegation exactly, by the desktop's delegation ID, or by `relayId` when the answer to its start was lost.
- `{ type: "cancel", threadId, delegation }`: cancel it, as `cancel_delegation` does on the desktop.
- `{ type: "machines" }`: the machines the desktop lists, which the host shows beside its own.

When it starts relaying, the desktop sends `delegation-relay-name` `{ name }`, the name it saved for the host in Settings › Hosts & phones; the host keeps it and says it in its away refusal, and says its own machine name only until a desktop has sent one. The desktop answers asks with the request `delegation-relay-answer` `{ askId, result }`: the `delegate`, `read_delegation` or `cancel_delegation` result the desktop's own delegation gives, or its machine list. The host answers `{ taken }`, false for an ask it no longer waits for. A start's result carries `placement`, where it started. The asking thread is named by the connection's host, so a host can address only its own threads (`host:<hostId>:<threadId>` on the desktop). The desktop places the start with the machine and system asked and finds the project there by its GitHub origin, as Watcher does. It admits it as one of its own delegations: no wider than the narrower of `runtimeMode` and the desktop's own new-thread default, its own worker roles, and the four briefs per turn counted against `rootUserMessageId`. Its depth is what the desktop can prove from its own read of the host's threads (`delegatedBy`), never less than `levels`; a chain it cannot follow to the top counts as the deepest a delegating thread may be. A start placed back on the asking host, or on a third machine, is refused in plain words; for now a relayed start goes to This computer only. A `retry_key` the call gave is kept; without one, `relayId` is the retry key, so a second ask with the same key starts nothing new. The desktop saves the ask with that retry key before the start runs, so a read by `relayId` finds what it made through delegation's own record even if the answer is lost or the desktop restarts while the start waits.

When a relayed delegation's outcome changes, the desktop sends `delegation-relay-news` `{ threadId, news, replies? }`: the host's thread ID, delegation news as a wake-up carries it, and each answered delegation's reply, cut as `read_delegation` cuts it (ADR-0105 decision 6). News that names a start whose answer has not arrived waits for it. The host delivers the news as the thread's hidden wake-up, with each reply labelled as the delegated thread's words and kept in memory only until it is worded, and answers `{ told: true }` once it is queued. News the host holds no record of, or cannot deliver, is refused `unavailable`, so the desktop offers it again, a few times.

The host keeps `delegation-relay.json`: each relayed delegation's IDs, the delegated thread, the machine, the outcome and what the thread was told, and the name a desktop sent, never a brief or a reply. Neither side drops an open delegation to stay small: past 500 delegations on the host, and 1,000 callers or 2,000 asks on the desktop, only settled ones go, oldest first. The desktop keeps `delegation-relay-callers.json`: each asking thread's key, project and permission as last asked, and each `relayId` with the delegation it made. While no desktop that relays is connected, a start elsewhere is refused with "This computer isn't connected to forge, so nothing was started there. Start it on forge instead, or try again when this computer is back." and nothing is queued; its refused delegation records `away`, which the desktop's roster words the same way. A start the desktop refused for its machine, another machine or one without the project, records `relayed`, and its row reads "Asked for the Mac. forge can start threads on forge or on This computer for now." (Zach, October 27, 2026). An ask whose answer is lost (the socket closed, or the wait plus 20 seconds passed) is never asked again (ADR-0058): its delegation reads `unknown`. When a desktop that relays connects again, the host reads every open relayed delegation, and every one whose answer was lost, exactly; what the desktop's record says then stands, and an ask the desktop never recorded stays `unknown`. A thread whose outcome moved is told once. Nothing is logged but `delegation-relay-answer-lost` and `delegation-relay-reconciled` on the host and `delegation-relay-answer-failed` and `delegation-relay-news-failed` on the desktop.

## A host's own check queue (October 27, 2026)

Contract (#1312, Owl `cross-machine-work`, [ADR-0082, October 27 amendment](adr/0082-work-moves-between-a-desktops-machines-over-its-own-ssh-link.md)): a headless host whose Owl answer turns on Work across machines, and which runs Watcher for a desktop, lists `watcher-check-queue`. Like the other `watcher-` features its hello lists it only for a client the launch script recorded as a desktop. It adds no request: a Watcher start sent in `watcher-control` may carry `check: true` in its `start_thread` input, Sotto's like `fromMove`, set by the desktop for a start with `testRun` and never named by Watcher. The host then runs one **check** at a time, in the order asked, in one queue it shares with the checks its own threads delegate (#1310). A start that waits answers at once: `status: "ok"`, a receipt whose `deliveryState` is `queued`, and `check: { ahead, note }`, how many checks are ahead of it, the running one included. The host makes its thread and sends its first prompt when its turn comes, and the desktop reads that as it reads any receipt, by reconciling. A stopped request fails a waiting start as stopped and takes it out of the queue; a restart of the host empties the queue, and a start still queued there reads unknown. A host whose Owl answer is off refuses a start carrying the flag as `HOST_FEATURE_UNAVAILABLE`, and an older host's strict start refuses the unknown key. A desktop sends the flag only to a host that lists the feature, and a stable desktop never sends it. `v` stays 1.
