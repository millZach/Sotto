# How T3 Code drives OpenCode, and how Sotto could

Studied on 2026-10-16, when Zach asked whether Sotto could add OpenCode the way T3 Code has. T3 Code was read at [`e58a4857`](https://github.com/pingdotgg/t3code/tree/e58a4857130a93cc58b45dd6ebee14cf08df04ec), its `main` that day, and Sotto at `00f32d33d`. Nothing of T3 was run. OpenCode 1.19.3 was run on forge: `opencode serve` was started for a minute and its OpenAPI document read from `/doc`, and `opencode models --verbose` was read. Links below use `T3/` for `https://github.com/pingdotgg/t3code/blob/e58a4857130a93cc58b45dd6ebee14cf08df04ec/` and `P/` for `T3/packages/provider-opencode/src/`.

## Finding

T3 drives OpenCode over OpenCode's own HTTP server, not its ACP mode. It starts `opencode serve` on a free local port with a fresh password, sends each request with the thread's folder, reads the server's event stream, and answers OpenCode's permission and question requests through the server's reply routes. Everything Sotto needs for a thread provider is in that server: sessions, prompts, abort, history, models with effort levels, permission requests with one-time replies, questions, image parts, slash commands, skills, and remote MCP servers. So Sotto can add OpenCode as its sixth thread provider in the shape it already uses, one client process per thread (ADR-0038), without a new runtime dependency: Node's `fetch` reads the server and its event stream.

OpenCode now ships two lines. The 1.x line (`opencode-ai` on npm, 1.19.3 released today) is what mise, pacman, scoop, Homebrew and the OpenCode desktop app install, and what forge and this laptop's desktop app run. The 2.x line (`@opencode/cli` on npm, 2.0.0 on September 11, 2.0.31 today) is what OpenCode's README now gives for npm. Their servers differ, and T3 keeps a separate adapter for each, chosen by `opencode --version`.

## How T3 does it

**Two adapters.** `P/server/adapter.ts` (3,734 lines) speaks the 1.x server through `@opencode-ai/sdk`. Its factory is called `makeOpenCodeAdapterV2`, where V2 names T3's adapter interface, not OpenCode 2. `P/server/v2/adapter.ts` (3,948 lines) speaks the 2.x server through `@opencode/client`. [`P/server/driver.ts:93-129`](https://github.com/pingdotgg/t3code/blob/e58a4857130a93cc58b45dd6ebee14cf08df04ec/packages/provider-opencode/src/server/driver.ts#L93-L129) picks one by major version. The whole provider is 21 source files and 12,514 lines, with 18 test files. There is no ACP path. OpenCode is off by default in T3.

**Starting the server.** [`P/server/OpenCodeRuntime.ts:680`](https://github.com/pingdotgg/t3code/blob/e58a4857130a93cc58b45dd6ebee14cf08df04ec/packages/provider-opencode/src/server/OpenCodeRuntime.ts#L680) runs `opencode serve --hostname=127.0.0.1 --port=<free port>` with `OPENCODE_SERVER_PASSWORD` set and `OPENCODE_CONFIG_CONTENT` defaulting to `{}`. It waits up to 30 seconds for the stdout line `opencode server listening on http://…` ([`:297-303`](https://github.com/pingdotgg/t3code/blob/e58a4857130a93cc58b45dd6ebee14cf08df04ec/packages/provider-opencode/src/server/OpenCodeRuntime.ts#L297-L303)); OpenCode's server docs do not mention that line, but 1.19.3 on forge printed exactly it. Requests use HTTP Basic with the user `opencode`. The server takes no folder; each request carries `directory`.

**How many servers.** For 1.x, one server per T3 session, started in the thread's folder ([`P/server/adapter.ts:120-122`](https://github.com/pingdotgg/t3code/blob/e58a4857130a93cc58b45dd6ebee14cf08df04ec/packages/provider-opencode/src/server/adapter.ts#L120-L122): "one directory-bound client/server per session"), plus a shared, reference-counted server with a 30-second idle close for model lists, skills, commands and side writing. For 2.x, one shared server for every thread, since a 2.x server serves every folder. On Windows T3 kills only the direct child and keeps no record to reap a leftover server after a crash, which its open issue #18788 reports.

**A turn.** 1.x: `session.create` with a permission rule set, `session.promptAsync` with `model` (`provider/model`), `agent`, `variant` and parts, events from `/event`, `session.abort` to stop. A turn ends on `session.idle` or `session.status` idle. Text, reasoning and tool calls arrive as message parts; `todo.updated` becomes a plan; token counts come from each step. A `/name` that matches the server's command list is sent with `session.command`. Rollback is `session.fork` at the boundary message. Resume after a restart is `session.get` and `session.messages` on the saved session ID. 2.x adds steering a running turn (`delivery: "steer"`), switching model or agent on a live session, and a staged revert.

**Permissions.** T3 never writes OpenCode's config file. It sends a rule set with `session.create` ([`P/server/adapter.ts:606-696`](https://github.com/pingdotgg/t3code/blob/e58a4857130a93cc58b45dd6ebee14cf08df04ec/packages/provider-opencode/src/server/adapter.ts#L606-L696)): full access is the single rule allow `*`. Otherwise everything is denied, then asked, then a short always-safe list is allowed, `.env` reads ask, and Auto-accept edits allows `edit`. A `permission.asked` event becomes T3's approval card, and the answer goes back with `permission.reply`. 1.x maps T3's "for this session" and "always" choices to OpenCode's own `always`. The 2.x adapter stopped doing that because, in its own words, "OpenCode's own 'always' saves a grant for the whole project"; it keeps such grants on the thread instead. Questions (`question.asked`, forms in 2.x) become T3's question cards.

**Models.** `provider.list` gives each signed-in service's models. A model's ID is `service/model`, and its `variants` are its effort levels. On forge these are `low`, `medium`, `high`, `xhigh` and `max`, the same names Sotto's effort control uses, and `capabilities.input.image` says whether it takes images. With no credentials, forge lists the 12 free OpenCode Zen models only.

**Install and sign-in.** T3 runs the user's `opencode` (a path setting, default `opencode`), refuses anything older than 1.14.19, and reads signed-in services from `provider.list`. With none it says OpenCode "did not report any connected upstream providers." Updates use `opencode upgrade` or the package manager that installed it, and never move an install between the 1.x and 2.x packages.

**Sotto-like extras.** T3 adds its own MCP server to each OpenCode session with `mcp.add` (`type: "remote"`, a URL and an `Authorization` header), which is how OpenCode reaches T3's tools. T3 reads usage from OpenCode's SQLite files, and asks `opencode.ai/zen/go/v1/usage` with the user's OpenCode Go key for plan limits.

**Open problems in T3.** Leftover servers on Windows (#18788), OpenCode's shared database lock when two servers start together (#9065, #17806), 2.x pasted images sent only as a path (#16144), 2.x MCP tools lost after idle (#16768, #16141, #19276), and OpenCode not offered on SSH remote hosts (#17182). The search was capped at 30 issues and 30 pull requests, all open.

## What OpenCode 1.19.3 offers, checked on forge

`opencode serve` listened on the port given, warned that no password was set, and served a 480 KB OpenAPI document with 162 routes. Two generations sit side by side in it: the 1.x routes T3's 1.x adapter uses (`/session`, `/session/{id}/prompt_async`, `/session/{id}/abort`, `/permission/{id}/reply`, `/question/{id}/reply`, `/event`, `/provider`, `/mcp`) and a newer `/api/…` set (`/api/session/{id}/prompt`, `/api/session/{id}/interrupt`, `/api/event`, `/api/model`) whose events are named `session.next.*`. T3's 2.x adapter handles `session.text.*` and `session.execution.*`, so the `/api/…` set in 1.19.3 is not the same as the 2.x server, and nothing here relies on it.

## How it maps onto Sotto

Written against the 1.x server before Zach chose OpenCode 2; the shape holds for 2.x, whose routes and event names are in the 2.0.31 section below.

| Sotto needs | OpenCode 1.x gives | Notes |
|---|---|---|
| One process per thread (ADR-0038) | `opencode serve` per thread on a free port, fresh password | As T3's 1.x adapter. Provider-level reads (version, models, sign-in) on a short-lived server, as Grok Build does. |
| A client Sotto can find and update (ADR-0036, ADR-0042, ADR-0077) | `opencode --version`; installs from npm (`opencode-ai`), mise, scoop, Homebrew, pacman, the install script | `registry.npmjs.org` is already a named host. The install script's `opencode.ai` joins the README's list of makers a host may download from. |
| The user answers every permission (ADR-0004) | A rule set per session; `permission.asked`; `permission.reply` with `once` or `reject` | Send only `once` and `reject`. OpenCode's `always` would be a standing project-wide grant outside Sotto's policy records. |
| Runtime modes | Ask for approval, Auto-accept edits and Full access as rule sets | No native Automatic. The rule set goes with `session.create`, and `session.update` takes a new one on a live session; T3's 1.x adapter does not use that, so it is unproven. |
| Questions | `question.asked`, `question.reply` | The existing question card. |
| Models and effort | `provider.list`; `variants` are low to max; image capability per model | Model labels must carry OpenCode's own name: an Anthropic model inside OpenCode must not read as a Claude Code thread (the label-inference risk in `providerIdOfLabel`). |
| Streaming, tools, plans, usage per turn | Message parts, `todo.updated`, per-step tokens | Into Sotto's existing activity. |
| Stop, resume after restart (ADR-0076) | `session.abort`; `session.get` and `session.messages` | A running turn ends as interrupted when its server closes. |
| Side writing (ADR-0026) | A throwaway session whose rule set denies `*` | OpenCode's rule set disables every tool, the check that kept Muse out of side writing. |
| Sotto's tools: browser, visuals, thread tools | `mcp.add` with `type: "remote"` and a bearer header | Sotto's thread tool server is already local HTTP MCP with one bearer token per thread (`src/main/agents/threadToolServer.ts`). |
| Watcher (ADR-0073) | | Refused at first, as Devin and Muse are. |
| Hosts and phones | Same adapter on the headless host | Phones need only the provider's name and new-thread entry. |

Three settings Sotto would pass in `OPENCODE_CONFIG_CONTENT` for its own servers: `share: "disabled"`, so a thread is never published to an OpenCode share link; `autoupdate: false`, so a thread's server makes no update check of its own (OpenCode never installs an update by itself; Sotto's update coordinator does that); and no other change to the user's own OpenCode configuration.

## What a sixth provider costs in Sotto

Muse is the yardstick: its first commit touched 69 files (+2,480/-105), and the whole pull request was about +7,900 lines including tests and evidence. Several provider lists are capped at five (`src/shared/agents.ts:478,561,568,640,648,897,899`) and fail to parse with a sixth. `providerWritesShortText` and `providerTakesSottoTools` default to true for a new provider. About a dozen lists name providers by hand without the type checker noticing a missing one (the installed order, the host provider order, usage, terminal and Watcher lists, the provider colours, the phone apps). An Owl gate repeats Muse's hand-written checks in about 23 files, since there is no generic per-provider gate yet.

## OpenCode 2.0.31, checked on this laptop

Zach chose OpenCode 2, so `@opencode/cli@2.0.31` was installed into a scratch folder on the Windows laptop and run against a throwaway data folder, with only OpenCode Zen's free models and a local fake model server; nothing of Zach's own OpenCode was touched. What it showed:

- **Launch.** `opencode serve --hostname=127.0.0.1 --port=0` prints `server listening on http://127.0.0.1:<port>`. The password comes from `OPENCODE_PASSWORD`; with none set, the server makes one up and prints it on the next line, so its output must never be logged. `GET /api/info` answers `{version, pid, urls, ...}`. `OPENCODE_CONFIG_CONTENT` is honoured; the 2.x settings are `share` and `update` (not `autoupdate`), and `OPENCODE_DISABLE_AUTOUPDATE=1` turns the update check off. The OpenAPI document is at `/openapi.json` (118 paths), behind the password.
- **Several servers, one data folder.** One server serves several folders, each request naming its folder. Several servers share one data folder once its database exists; three started together on a fresh folder raced its creation and one exited. A server sees the others' sessions but not their live work, and nothing stops two servers running one session at once.
- **A turn.** `POST /api/session` with a model `{id, providerID, variant}`, a folder and a permission rule set; `POST /api/session/{id}/prompt` with text, files and `delivery` (`steer` or `queue`); events on `GET /api/event`: `session.text.*`, `session.reasoning.*`, `session.tool.*`, `session.step.*`, ending with `session.execution.succeeded|failed|interrupted`. A steered or queued prompt joins the running execution, so one execution can carry several prompts. `POST /api/session/{id}/interrupt` stops it.
- **Permissions.** `permission.asked` carries the action, the resources and, for an edit, the diff. A reply is `once`, `reject` or `always`. A reject reaches the model as a failed tool call and the turn goes on. `always` saves a grant for the whole project that later sessions obey even when their own rules ask; only a session rule that denies beats it.
- **Questions** arrive as `form.created` with typed fields and are answered with `POST /api/session/{id}/form/{formID}/reply`. The form waited minutes for its answer.
- **Resume.** A new server reads a session and its typed history back. A session whose server died mid-tool has no outcome and a tool that reads `running` until the next prompt repairs it.
- **Deny-all.** A session whose rule set denies `*` gives the model no tools at all, built-in reads and web fetch included. OpenCode Zen's free models refuse any session whose tools differ from OpenCode's own ("OpenCode's free tier can only be used from within OpenCode"), so side writing works on a signed-in model source only.
- **Images** go inline as `data:` URIs on the prompt's files. **MCP**: a remote server with a bearer header can be added and removed at runtime, per folder and per process.
- **Install channels** that give 2.x: npm `@opencode/cli`, `opencode.ai/v2/install`, Homebrew core `opencode`, the tap's `opencode-v2`, scoop's `versions/opencode2`, Arch's `extra/opencode`. `opencode upgrade` picks the method its install came from.
- **Windows.** Stopping only the server left a running tool's processes behind; stopping its process tree left nothing. No console window flashed when it was started the way Electron starts a child.
