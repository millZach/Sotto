# Issue 23: native Grok thread adapter verification

Implemented `GrokAcpHost(userDataDirectory, options?)`, exported from `src/main/agents/grok.ts`. This is an `AgentHost` provider adapter for wrapping with `SottoThreadHost('grok', adapter, registry)`. The wrapper remains the owner of Sotto thread IDs. `grok-threads.json` stores the adapter alias, native Grok UUID, project metadata, model confirmation, and dispatched-message SHA-256 digests/command identities. `grok-projects.json` stores project directories. Neither file stores transcript text or credentials.

## Native protocol evidence

Checked installed `grok --version`: **1.0.5 (5115b46bc9)**. Connect requires **ACP protocol 1** and `initialize._meta.agentVersion === '1.0.5'`; it also requires load support and native cached-token authentication. A mismatch fails before authentication or creating a session. Models come from `initialize._meta.modelState`; custom guessed model catalogs are not used.

Primary sources inspected on 2026-09-11:

- [Official Grok Build overview](https://docs.x.ai/build/overview) and [CLI reference](https://docs.x.ai/build/cli/reference): native stdio ACP, native CLI resume, and headless operation.
- [Official source snapshot](https://github.com/xai-org/grok-build/tree/37949780c144e37df692e3d669051a21fec24f20), with repository `SOURCE_REV` c4ea71cfdbcdb21e32e41bc25a0043d7d4836714. This snapshot supplements the installed-version live checks; it is not claimed to be the installed binary's exact source revision.
- [`session_updates.rs`](https://github.com/xai-org/grok-build/blob/37949780c144e37df692e3d669051a21fec24f20/crates/codegen/xai-grok-shell/src/extensions/session_updates.rs): `_x.ai/session/updates` reads durable session updates, supports `offset`/`limit`, and filters rewound branches. Results contain storage envelopes rather than only update payloads.

Blocking interactions are shared with other attached clients.

Two real protocol details were caught by running the synthetic native flow and corrected in both implementation and tests:

1. Native stored `timestamp` is epoch seconds, with finer timestamps in `params._meta.agentTimestampMs`. Assuming a string timestamp broke history reads.
2. **Grok reuses `params._meta.eventId` values after another CLI process resumes the same native session.** Event ID alone wrongly attributed an external prompt to a prior Sotto command. Message keys now hash event ID, native timestamp and the full update; origin matching additionally requires the authored-text digest. A fixture explicitly reproduces repeated native event IDs.

## Delivery, recovery and permissions

Launch is the native executable with `--permission-mode default agent --leader stdio`; shared native leader operation is explicit rather than dependent on the user's `use_leader` setting. Native durable session storage remains enabled. The native environment keeps existing Grok home/auth paths and blocks API-key authentication. It excludes inherited API keys and does not copy the text-only reasoning client's tool-denial profile, temporary home, or disabled tool features. Sotto does not read tokens or implement an API-billing fallback.

`session/new`, `session/load`, `session/set_model`, `session/prompt`, `session/cancel`, `session/update`, `_x.ai/session/updates`, `_x.ai/session_notification`, and `_x.ai/ask_user_question` use native wire names and shapes. ACP prompt acknowledgement is the authored-message echo: the `session/prompt` response arrives at turn completion, not initial acceptance. A missing echo returns uncertainty without resending. Durable history reconciles delivery and carries the coordinator's message ID. Late creation responses still save the native alias; unconfirmed creation/model settings block prompts, and reconnect reads their actual settings without repeating creation or selection blindly.

Live authored input and assistant chunks stay visible while persistence catches up. The history query and stale-message guard run before a send and again after saving its origin, immediately before dispatch. A takeover during that save removes the undispatched origin and rejects the stale reply. A different externally authored message has no Sotto command ID, so existing coordinator takeover behavior applies. Concurrent prompts on one thread are rejected. Read-only request timeouts remove their waiters; uncertain creation/selection callbacks remain for late responses. Total outstanding requests, frame size, queued frame bytes and stderr bytes are bounded. Stderr and protocol bodies are never logged by the adapter. A shutdown barrier waits for child exit, frame handling and metadata writes.

With explicit leader mode, the live restart-during-run probe verified that a model turn continues after its ACP proxy disconnects. A new adapter attaches to the same native session, observes completion and retains its original user message. [The native leader launcher](https://github.com/xai-org/grok-build/blob/37949780c144e37df692e3d669051a21fec24f20/crates/codegen/xai-grok-shell/src/leader/mod.rs) passes `--no-exit-on-disconnect`. The fake preserves running native work across proxy replacement and never reroutes the old proxy's prompt response to a new client's RPC ID. Native leader `server.rs` and its reconnect tests also preserve/replay shared pending interactions for attaching clients; these source-backed semantics were inspected without invoking live tools or permissions.

On Windows the leader can inherit the proxy's output handles. Destroying the proxy's output streams after its process exits prevents those inherited handles from keeping Node's close event and the adapter shutdown barrier open indefinitely. A fake child reproduces that inherited-handle case.

Permissions expose the tool title and bounded raw input, and select only an offered `allow_once` on explicit `approved: true`. All other answers use `reject_once` or ACP cancellation. Sotto never chooses `allow_always`. Interrupt/disconnect cancel outstanding questions/permissions. An answer is removed before writing so it cannot be answered or declined twice. Unknown tool/client requests receive unsupported-method errors. Images remain deliberately unavailable. Per-thread permission modes are described below; Sotto's own answers never select `allow_always` in any mode.

### Per-thread permission modes (verified 2026-09-14, Grok 1.0.5)

The shared leader still launches with `--permission-mode default`; the mode is applied per native session through `session/new` / `session/load` `_meta`, which Grok's installed docs (`user-guide/15-agent-mode.md`, "Session `_meta` options"; `22-permissions-and-safety.md`) define as `yoloMode` (always-approve) and `autoMode` (auto, superseded by always-approve). Advertised modes and mapping:

| Sotto mode | `_meta` sent on create, resume and reload |
| --- | --- |
| `approval-required` (also any thread without a stored mode) | `{ yoloMode: false, autoMode: false }` |
| `auto` | `{ yoloMode: false, autoMode: true }` |
| `full-access` | `{ yoloMode: true, autoMode: false }` |

`auto-accept-edits` is not advertised. `acceptEdits` appears only as a process-wide `--permission-mode` / settings `defaultMode` value, which cannot vary per thread on the shared leader. There is no per-session `_meta` flag for it, and Grok's hook docs say the effective session mode is only ever `default`, `auto`, `plan` or `bypassPermissions`. `session/set_mode` is not a verified switch either: against the real binary it returned `{}` for `default`, `acceptEdits`, `auto`, `bypassPermissions`, `always-approve` and `nonsense` alike, with no `current_mode_update` notification.

Live probe method: a throwaway ACP client against the installed `grok.exe` in a temporary working directory with a temporary `GROK_HOME` (native `GROK_AUTH_PATH`), holding one global `SessionStart` hook that recorded its stdin. The only prompts were the local `/session-info` host command (`hostTurn: true`, zero model tokens); no model turn or tool ran. Observed `permissionMode` in the hook payload and `yolo` in `_x.ai/sessions/changed`:

- `session/new` with the three `_meta` values above produced `default`, `auto` and `bypassPermissions`.
- `session/load` of a session that is **resident** in the leader does not fire `SessionStart` and does not downgrade it: loading an always-approve session with `yoloMode: false` left `yolo: true`. Loading a resident ask session with `yoloMode: true` did turn `yolo` on.
- `_x.ai/session/close` returns `{ result: { success: true, outcome: 'closed' } }` (or `'notResident'`). A following `session/load` fires `SessionStart` with `source: 'load'` and applies its `_meta` exactly: always-approve became `default`, auto became `default`, ask became `auto`. A load without `_meta` produced `default`, so the mode must be resent on every resume.

Sotto therefore stores `runtimeMode` in the Grok alias and sends its policy on every `session/new` and `session/load`. `configure-thread` can change only the permission mode of an existing thread (model/reasoning changes are still rejected). It refreshes history, refuses while the thread runs or has pending requests, persists `pendingRuntimeMode` and blocks sends, then closes and reloads the native session with the new `_meta`. The mode is committed only after the load is confirmed. An interrupted change is finished on reconnect with the same close-then-load sequence before the thread can send again. Closing a native session could disturb another client attached to it at that moment, such as the Grok CLI; that interaction was not probed. The effect of `autoMode` on real tool calls was not exercised, and neither was a close/reload during a leader-hosted running turn (Sotto refuses mode changes while a turn is known to be running).

## Validation

- Shared adapter behavioral contract: **9 passed, no skips**, against a real child process using the native ACP fake. The parent-owned shared contract accepts native method names and a permission-result decoder; recorded traffic is not renamed to Codex methods.
- Provider-specific tests: **16 passed** after independent-review fixes, covering version rejection before authentication, environment filtering, live history lag, live takeover during lag, reused native event IDs, command deduplication, concurrent prompt rejection, uncertain creation, rejected model selection, takeover during origin persistence, reconnect on the same instance, Sotto registry identity across restart, malformed-frame disconnect, and inherited output handles. Live running, success and error states survive stale durable-history polls until the corresponding event is persisted; subsequent durable events can then advance status.
- Opt-in live test: **1 passed** with `SOTTO_GROK_LIVE=1 npx vitest run tests/integration/grokAdapterLive.test.ts`. It creates a new isolated temporary project and native session, sends a text-only synthetic prompt, verifies the reply, resumes the same native UUID through the real Grok CLI with another synthetic prompt, observes CLI takeover without command attribution, rejects a stale automatic reply, and verifies identical messages/identity after replacing the adapter and reconnecting. The real native takeover check failed before the event-ID fix and passed after it.
- Node TypeScript check and focused ESLint passed. The parent runs the combined repository checks after integrating provider wiring.

The live probe only used newly created synthetic sessions and temporary working directories; no existing user conversation, credential file, or real project command was read or executed. Native session persistence leaves those synthetic provider sessions in Grok's own history; Sotto's temporary local probe folders are removed. Native permission/question interaction shapes are source-verified and covered by strict fake-response checks; the live test did not ask Grok to execute tools or generate a real permission request.

## Limits

- Foreign session discovery is not implemented: only aliases Sotto created are loaded. A crash before receiving `session/new` can leave an unknown native session and a deliberately unresolved alias; it is never recreated automatically.
- Full history is read in bounded pages at each poll. Very large sessions may need incremental indexing later. Native rewinds are filtered by Grok; origin metadata survives, so a removed prior dispatch is not automatically retried.
- A byte-identical external prompt arriving while an identical Sotto dispatch is still unconfirmed is indistinguishable by text digest until stronger native identity is available. Previously confirmed prompts are protected by composite event identity, including against event-ID reuse after native CLI resume.
- Model/reasoning settings are available at creation; changing an existing thread's model or reasoning level, images, persistent permission grants, plan-exit extensions, and richer tool presentation are not advertised. No native CLI TUI visual review is claimed; the tested takeover path is the native headless resume command.
