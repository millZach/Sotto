## Implementation and acceptance

- [x] Source: standalone apps/ios package, Xcode project/shared scheme, SwiftUI app targeting iOS 17, Foundation HTTP/WebSocket and Security Keychain. No third-party runtime or changes to desktop dependencies.
- [x] Source: pair by entering the private HTTPS host and code read on the host. Reject non-HTTPS/non-ts.net routes, URL credentials/query/path; preserve default TLS validation; prohibit credential-bearing redirects. Token only in unlocked/device-only Keychain; no provider keys or transcript logs.
- [x] Source: host-scoped thread list/detail, text replies, interrupt, native question choices and explicit permissions. Pairing never grants authority. Unknown request kinds/choices fail closed. No terminal, new-thread, worktree, audio or file controls.
- [x] Source: foreground obtains a new session, full shell and selected detail. Stable submitted command ID; no automatic replay after uncertain delivery. Persist only pending identifiers, not transcript text; drafts remain in memory across backgrounding, clear on termination/Forget. Host retains work independently.
- [ ] Meaningful Swift codec, endpoint, question validation and uncertain-command tests. Run on a Swift-capable machine; Windows currently has neither swift nor xcodebuild.
- [x] Source: many computers. A list of paired computers, each its own Keychain item under its host ID with its own connection and state; the single saved pairing moves over as the first computer. Needs you and Threads merge every computer's threads with a strip to narrow to one; thread identity is the host ID with the thread ID everywhere. Computers tab with Add computer, status, details, Rename and Remove. Endpoints on 443 and 8443 only, tried 8443 first; health's optional `name` names the computer.
- [ ] Simulator build/test, signed device build, installation and real iPhone journey. No claimed completion from HTML or static validation. No TestFlight upload without a reviewable signed build.

## Framework comparison

SwiftUI fits this iOS-only scope with native lifecycle/accessibility, Foundation networking and Keychain without a third-party runtime. React Native/Expo matches T3 and would share TypeScript wire models, but brings a JS/native dependency and build boundary; desktop DOM/preload still cannot be reused. Choose SwiftUI here, and test Codable fixtures against the shared host protocol to manage duplicated wire types. Android is outside scope. Local Xcode/macOS is needed for native verification; cloud builds are not selected.

## Design checks

Concept, as chosen on September 26: **Needs you first** (variant B of `docs/prototypes/iphone-client-prototype.html`). Three tabs, Needs you, Threads and Host. Home lists every waiting question and permission on the host's threads, each answerable on its card, then the threads that are working. The owner chose B over A (thread-first list, then a quiet full-width thread, the direction this plan first set) and C (swipeable thread pages with one floating reply dock). This reverses the earlier line that attention-first "would compete with the owner's chosen quiet phone flow and is not reopened": the owner reopened it and picked it. Within B the owner chose: permissions answer on their card (Allow once, Deny) without opening the thread; threads read as chat bubbles; the Threads tab groups by project with All, Working and Done; a thread has Messages and Activity; a waiting request opens as a sheet from its thread and the reply box offers it again after Not now; the Host tab carries connection, answer permission, client ID and Forget.

Delivery, as chosen the same day: the owner has no Mac, so a GitHub Actions job on a macOS runner archives, signs (cloud-managed, with an App Store Connect API key) and uploads to TestFlight when an `ios-testflight-*` tag is pushed (ADR-0032). Rewriting in Expo to use Expo Go was offered and declined.

Pairing, as chosen the same day: the owner wants hosts without a screen to pair, so the phone finds the host **through Tailscale**. Step 1 asks for the machine's name on the tailnet (`forge`); the system resolver, answered by MagicDNS while Tailscale is connected, gives the full `*.ts.net` name, and `/v1/health` confirms a Sotto host there. Step 2 takes the eight-character code the host prints; the pairing is refused if another host answers. Signing in to Tailscale to list machines, and admitting the owner's own Tailscale account without a code, were offered and deferred: the first adds a host (Tailscale's API) and the second changes admission (ADR-0025), so both wait for their own ADR.

Many computers, as chosen on September 26, 2026: the owner wants T3 Code's model, where every computer running the Sotto desktop app, and any host without a screen, can be paired and the phone shows them all together. From `docs/prototypes/phone-access-prototype.html` the owner picked **C, "Guided setup"**, for both halves; the desktop half (Settings › Phones: one switch, a checklist, Pair a phone, a Can answer switch per phone) is built on `feat/phone-access`. On the phone: one merged list on Needs you and Threads with a strip of pills (All, then one per computer) that narrows both, the computer named in each card's and row's second line, and a Computers tab with Add computer first, then each computer's status and details (name on tailnet, answers from this iPhone, client ID, Rename, Remove). Each computer shares only its own threads, and its name comes from the desktop (the optional `name` in its health), falling back to its tailnet machine name. The desktop serves its host through Tailscale Serve on port 8443 so 443 stays free for other apps, so the phone tries 8443 before 443 and accepts no other port.

Worked out while building it, and not in the prototype: the strip shows only when more than one computer is paired, since with one there is nothing to narrow. Threads is one list, most recent first, rather than grouped by project; the project moves into each row's second line as variant C shows it. A computer's details open on a page of their own from its row, so the tab stays short with several computers. Requests on a computer that can't be reached are left off Needs you, since they can't be answered, and the line for that computer says they show once it is back; its threads stay on Threads, muted. Remove forgets a computer on the phone even when it can't be reached, and says so, where Forget used to keep an unreachable host for a retry: the token it leaves on the computer is a hash nobody holds, and the phone says to remove it there too. Adding a computer that is already paired is refused at step 1, before a code is spent.

## Evidence

The initial transition overflow was fixed by containing the app viewport. Reduced motion computed animation-name:none.
