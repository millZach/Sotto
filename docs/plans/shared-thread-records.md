# Each layer passes on only the threads that changed (#925)

The plan behind ADR-0016's amendment of October 24, 2026, accepted October 25. Step 1 landed in #1502, step 2 in #1515, step 3 in #1525, step 4 in #1530, step 5's coordinator, router and usage in #1532, and its Watcher and delegation from `perf/thread-changes-watcher`.

## Zach's picks, October 24, 2026

- **Option 2: publish only what changed.** Each publication carries the threads that changed and the threads that went. Every layer and subscriber keeps its own map and applies them. Option 1, keeping a record's identity through every layer, was the draft's recommendation as the narrower change; Zach chose the one whose cost follows the change whatever the threads number.
- **#925 before #1457.** The store worker #1457 needs is then fed these changes as they are.

## The problem

On every streamed chunk, five steps between an adapter and the window build a new record for every thread. They are the adapter's view and copy, the Sotto identity wrapper, the provider switch, the workspace's accept and the host stamp. Because every record arrives new, the workspace's publication then walks every thread to prove it unchanged. In the October 23 recording (0.1.38-owl.20261023.3, about 529 threads) that was about 12 s of a 44.7 s busy minute, 27% of main, and it grows with the threads rather than with what changed. The ADR amendment has the breakdown and the four options.

## The shape

- **Thread changes.** A new internal type, `AgentHostChanges`, carries:
  - a sequence number;
  - `upserts`, whole frozen thread records;
  - `removals`, Sotto thread IDs;
  - the non-thread parts (providers, catalog, projects, connection, error) only when they changed;
  - `whole: true` on a first publication, or one after a gap.
- **The subscription.** `subscribeActivityChanges(listener)` replaces `subscribeActivitySnapshots` for activity subscribers. A subscriber that sees a sequence gap calls its publisher's `resync()` and gets a whole one.
- **A map per layer.** `ThreadMap` is a shared helper holding records by ID in display order. It applies changes and builds a whole snapshot on demand for `snapshot`, `workspaceSnapshot` and ordinary `subscribe`. Each layer and subscriber owns one.
- **Frozen records.** Every record is frozen and only ever replaced, from the adapter to the window.

## How it would be built

One pull request per step. Each step keeps the old snapshot subscription working beside the new one until the last subscriber has moved, so every step can ship alone.

1. **Gates and the type.**
   - `AgentHostChanges`, `ThreadMap` and the sequence and resync rules, with unit tests: apply, remove, gap, resync, and display order after upserts.
   - `ownerScaleWorkBudget.perf.test.ts` gains "thread records touched per streamed update". The target is the threads that changed (1 or 3), and the count must not grow with the threads or the history.
   - A verifying mode rebuilds each layer's map from a whole snapshot after every change in the owner-scale fixture and compares the two. A missed removal or a stale record fails the gate.
2. **Adapters.**
   - A boundary shim turns any adapter's snapshot publication into changes by comparing each thread's record with the last one published. That is one check per thread, for that adapter's threads only.
   - Then each adapter (Claude, Codex, Grok, Devin, Muse, OpenCode) marks a thread changed on every path that changes it. Its publication sends only marked threads, and the shim goes for that adapter.
   - `tests/integration/adapterContract.ts` gains a check that every state change publishes the thread, and that a removed thread is published as removed.
   - **Landed.** All seven adapters (Claude, Codex, Grok, Devin, Muse, OpenCode and Cursor) offer `subscribeActivityChanges` beside their activity snapshots, and all seven mark their own changes (`adapterThreadChanges.ts`), so none uses the shim. An adapter falls back to it only for a first publication, the first after a connection or another change to every thread, and one bringing more than one new thread. `publishChanges` now leaves out a record equal to the one published, unless the same change removes or places that thread, and a rest equal to the published rest, so a publication carries only what changed. The contract also checks a thread watched from before it is created, and with `SOTTO_VERIFY_THREAD_CHANGES=1` checks both forms after every publication in every case. Nothing above the adapters reads the changes yet, so the owner-scale `threadRecordsTouched` count does not fall until step 3.
3. **The wrapper and the provider switch.** `threads.ts` binds IDs and `providerSwitch.ts` names providers for upserts only, mapping removals to Sotto IDs, and each keeps its map.
   - **Landed.** The identity wrapper offers `subscribeActivityChanges` whenever its adapter does. It keeps a mirror of each form the adapter publishes, hands each upsert on under its Sotto thread ID and maps removals and placements to Sotto IDs. An adapter record it handed on before comes out as the same record. Nothing goes out before the durable bindings load, and the first publication after they do is whole.
   - The provider switch takes each provider's activity as thread changes, from the wrapper, or through the shim from a host that publishes none (the fakes and the held stand-ins). Each provider's threads are a thread map that a change applies to at a cost that follows the change. A read, or a provider that disconnects naming no threads, leaves the map apart from what the subscription published, and the next publication replaces it whole, as every publication used to. The switch names each thread once per provider record and publishes changes of its own. A new thread of one provider is placed before the next provider's first thread. A change to a provider's connection or catalog carries the rest, and threads it drops are removals.
   - The switch's activity snapshot, which the workspace still reads, is built from those maps: each thread is the record the switch named, so the snapshot costs a reference per thread rather than a new record, and says what it said before. Its records are now frozen.
   - At the owner's scale on Owl, thread records touched fall from 1,310 to 889 per streamed update, and from 5,800 to 4,299 per send. The adapter and the wrapper touch about one record an update. The switch still walks its threads once to build the workspace's snapshot, until step 4. The adapter's copy of its whole view went with its last snapshot subscriber. `ownerScaleWorkBudget.perf.test.ts` has the figures, and verifying mode checks the wrapper's and the switch's changes, and the switch's threads against the wrapper's whole snapshot, through every scenario.
   - For step 4: the workspace subscribes to the switch's changes with the same `historyFromEvents` as now, so the switch subscribes to its providers as it does. The switch's records are owned and frozen, so `accept` merges over them without copying them. A provider's read still replaces the switch's map until the next publication, and a read in the message form changes each watched thread there and back. The switch's activity snapshot can go once the workspace and the tests no longer read it.
4. **The workspace.**
   - `accept` applies upserts and removals to its state, merging each upserted thread with what it lays over the provider's: messages, activities, worktree, Git action, pull requests and the rest.
   - Its publication passes on what changed, including threads whose own state changed: an event, a saved activity, a settle.
   - Its saves and event batch look only at changed threads.
   - **Landed.** The workspace subscribes to the provider switch's thread changes with the same `historyFromEvents` as before, so the switch subscribes to its providers as it did, and keeps the switch's threads in a thread map (`incoming`). A host that publishes only snapshots has its changes worked out by the shim, so every workspace test runs this path.
   - An ordinary change is taken in at a cost that follows it (`acceptThreads`). Each thread it upserted or removed, and each thread the workspace changed since the last accept (`remerge`), is merged again over the switch's frozen record, or loses its live state when the switch no longer publishes it, exactly as taking in the whole snapshot treats it, and goes back in its place, or last when it is new. Every other thread is left as it is, which is what merging it again gave. `trackSubagents`, the creation look-up and the summaries run only for those threads; a thread that stayed disconnected and untouched takes the last accept's date for its agents when it is next taken in, as every accept used to date it. A thread's creation is found by an index, since started creations stay as long as their threads; a walk of them for every merged thread made a change to N created threads cost N² (found in review, and now counted at the owner's scale as `creationReads`). A thread whose subagent roster or history write failed is merged again at the next accept whatever it names, as the old accept retried every thread.
   - These are taken in whole, as every publication was (`accept`): a whole publication, one carrying the rest of the snapshot, one bringing more than one thread new to the workspace, the first after the workspace changed the rest itself (a disconnect), and the first after a read. A read (a connection, a snapshot, a thread read, a creation's or settings' result) can leave the state saying what the switch has not published, so the publication after it puts everything back as the switch says it, as the old accept did. A read before a send that changed nothing leaves every mark as it was.
   - The workspace keeps its own order, as it always did: the switch's placements move nothing, a thread new to the workspace goes last, and a thread the workspace removes comes back at the next accept while its provider still publishes it. The provider dropping a thread removes nothing; the thread loses its live state.
   - Every path that changes a thread's record, or what its merge or its publication reads (its stored activity, its subagent summary, its creation, an invalid event's notice), marks the thread by its ID after the change (`touch`), so a change made after an await is marked too. A path that changes many threads, or the providers and catalog, marks them all. This replaces the October 22 amendment's promise that a change made inside a record in place is seen by the next publication without one: a write nobody marked is not published, and verifying mode finds it.
   - The activity publication keeps its frozen records in a thread map (`published`), in the state's order, and reads again only the marked threads, in one call, each against its last record. The snapshot is built from the map, a reference per thread, and says exactly what it said before; with `SOTTO_VERIFY_THREAD_CHANGES=1` the map is checked after every change against a publication worked out from every thread. After a whole accept the publication is worked out from every thread, as it was, and the map takes only the records that changed. The workspace's own thread changes (`subscribeActivityChanges`, one form for every subscriber) are read off the same map when their publisher builds them: the threads whose record changed, the threads that went, a thread new to the publication placed, and whole for a first publication or after one worked out from every thread.
   - Saves sync only the threads marked since the last save that succeeded, unless the save keeps subagent task words, is the first without them after one that did, or follows a whole accept; a list that is not certified stays marked, since it may change in place. A release looks only at threads marked since the last release, and at every thread when a window first says what it shows. Before any window has said so, a stream on one of 200 threads saved 2,200 thread lists over a hundred chunks, each with its own read of the thread's message reset; it now saves the 9 or 10 the stream changed. The event batch already wrote only the threads with events waiting; its look-ups and the accept's are by an index now rather than a walk of the list.
   - At the owner's scale on Owl, thread records touched fall from 889 to 10.77 per streamed update on one thread, from 4,299 to 2,103 per send and from 1,012 to 4 per answer-draft save. Three streaming threads read 80.62, because the connection the fixture makes between the streams is a read and the publication after it is taken in whole; the same read before every send is most of what is left there. Copies per streamed update fall from 2.69 to 1.85, and in the streaming copy budget from 3 to 2.07 on Owl and 3.07 to 2.13 on stable, the switch no longer building its activity snapshot. The workspace's change records are counted (`workspaceChangeRecords`): about one per streamed update on one thread, 54 per send, which follows the threads with stored activity a read brings back.
   - `workspaceThreadChanges.test.ts` holds the workspace to the host-level contract, and holds a workspace taking in changes to one taking everything in whole, byte for byte, across a seeded run of mixed operations, through the switch and through the shim.
   - For step 5: the coordinator can read the workspace's thread changes, whose records are the very records its activity snapshots carry. The activity snapshot is still built for each publish, a reference per thread, until nothing reads it. A read still costs the publication after it a whole accept and a walk of every thread, and brings back every thread whose activity is in the store; both are as before. Test code that writes into the workspace's records must mark the thread, as the workspace's own code does.
5. **The subscribers.**
   - The coordinator applies changes to its host state. Its shell and its finish, failure and unread tracking work per changed thread, which also covers the per-thread `acceptSnapshot` work #1334 left.
   - Usage reads upserts.
   - Watcher and delegation observe changed threads.
   - The router stamps hosts on upserts and joins every host's changes for the coordinator.
   - The host socket and the phone path apply the changes they are given.
   - When no subscriber is left on it, the old activity snapshot subscription goes.
   - **Landed: the coordinator, the router and usage.** The coordinator subscribes to the workspace's thread changes and keeps them in a thread map (`incoming`). A change is taken in at a cost that follows it (`acceptChanges`): only the threads it names, and those whose shown record must be worked out again (`reshow`: Watcher's conversations when Watcher's requests move, a thread whose prototype question the user answered, a question whose search found none and is due to look again), are shown, tracked and listed again, in display order, as the whole path reads every thread: what several threads do in one change, such as finishing past Just finished's limit, follows the order they are read in. Each step of showing a snapshot (Watcher's filters, held providers, Watcher's own messages, start handovers, Sotto's own requests, question pages, the prototype-ready mark and prototype questions) reads only those threads and lets go of what it kept for the threads that went (`gone`), which is what reading every thread again would have done. The finish and failure trackers read them alone (`trackChanged`). A thread whose kept prototype reply or cleared source is let go to make room for another's (`onEvicted`) can lose or regain its mark though nothing in it changed. A change is shown in three phases, as the whole path shows every thread one step at a time (found in review: showing each thread through every step on its own looked up the settled projects once per thread, a change of N threads in N projects costing N squared, and let one thread's prune take a page another was about to bring back). First, once over every thread the change names, every step that reads a thread alone, up to the question pages, which look at each thread's pages with the prototype records as they stood, then sweep what is still asked and prune what is past its time, once, as the whole path does. Then the prototype-ready marks, the one step whose records are shared. Last, once, prototype questions over the threads marked, and letting go of what was kept for threads that went, whatever the change names, so a change that only removes threads lets go of theirs. One look-up of the settled projects serves every step. The marks are made one thread at a time from a queue ordered by display position: one let go ahead of the place reached joins the queue and is read at its place, among the threads the change named, as the whole path reads it after the eviction in the same pass; its pages are read, not looked at again, since nothing named it and the whole path's look at them found them as they were; one let go behind it is read with the next change, as the whole path reads it with the next snapshot. Only threads ahead join, and the place only moves on, so a chain of marks letting each other go is read to its end, each thread at most once (found in review: a batch then a replay read them out of order, and a cut-off ended long chains early). The first-output watches are all read, by a look-up of each one's thread; there are a few at most. A change and its check in verifying mode share one reading of the clock, so a prototype question's deadline passing between them is no drift. The check's whole pass puts the prototype records back and names nothing, and leaves out only threads named to be shown again before it began, so it cannot excuse what it found itself. The host list is patched in a copy when threads are replaced in place, and listed again from the map in the workspace's order when one is added, removed, moved or no longer shown. The coordinator finds a thread by an index of its list rather than a walk of it, on the update path and for the router's and Watcher's look-ups.
   - Taken in whole, as every publication was: a whole publication, one carrying the rest of the snapshot, and the first after anything else set the host snapshot: a command's read, a disconnect, or the coordinator taking its own snapshot again when a question's pages, a prototype question or Sotto's own requests move. While threads may begin from others, so is one that brings or removes a thread or changes one's provider, which a thread that began from it shows.

## What it means for #1457

The workspace knows exactly which threads changed on each publish, so the #1457 store worker can be posted those upserts, removals and events as they are. A stored thread's list can be read and parsed on the worker and handed back as an upsert. #1457's design is drafted once steps 1 to 4 have landed.

## Risks

- **Drift between maps.** A missed removal leaves a ghost thread, and a missed upsert leaves a stale one. The guards are the verifying mode, the sequence numbers with resync, and the adapter contract checks.
- **The width of the change.** Every activity subscriber moves. The staged order keeps the old subscription alive until the last one has moved, so any step can be reverted alone.
- **Display order.** `ThreadMap` keeps each publisher's order, and the tests check order after upserts that move a thread.
- **Writes into frozen records.** ES modules run in strict mode, so a write into a frozen record throws. Tests find these, and each is replaced with a new record, as #1326 and #1334 did.
