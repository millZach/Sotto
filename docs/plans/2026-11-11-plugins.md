# Plugins

Zach asked on November 11, 2026 for "plugins for the app that give agents a known place where things are connected": his mail accounts, Vercel, GitHub, Meshy, X, ElevenLabs, Higgsfield, and Grok Bot driving Sotto, with its own tab in Settings. This plan builds what he decided that day, in slices small enough to review and merge one at a time.

The decisions are [ADR-0205](../adr/0205-plugins-connect-outside-services-once-and-threads-use-them-through-sottos-tools.md) (plugins) and [ADR-0206](../adr/0206-an-assistant-drives-sotto-over-the-tailnet-and-never-answers.md) (Grok Bot). The words are in `CONTEXT.md` under Plugins. The page is his pick A of `docs/prototypes/plugins-settings-prototype.html`, with each service's own icon. Both are Owl features: `plugins` and `assistants`. The map issue is #2503.

## What already existed

- Nothing was building this: no pull request, issue or branch.
- `docs/research/2026-10-28-assistants-drive-sotto.md` (#1685) covered how Grok Bot and Hermes could drive Sotto. Zach dropped it on October 28 and reopened it here; ADR-0206 builds its Design A.
- ADR-0141 decided how a thread makes 3D models with Meshy (#1568). It was never built. Slice 11 builds it as a plugin.
- The cloud iPhone's run.cloud key (ADR-0047) is the built pattern for a paid key, a tool, an ask before each use and a monthly cap.

## Rules for every slice

- **One pull request per slice**, closing its issue, behind the Owl switch from the first line. Stable shows and starts none of it.
- **A slice that adds a plugin adds its hosts to `README.md`** under "Privacy and cost", in that section's form, and confirms the host names and terms in ADR-0205's table against the vendor's pages on the day. A fact that turned out wrong amends the table with the date.
- **No secret is ever printed, logged or committed.** Tests use made-up values against a local fake of each service, as the Meshy plan does. Nothing in CI reaches a real service. A live check is gated by a `SOTTO_*_LIVE` variable, run by hand, and needs Zach to enter the secret in the app himself; no agent is given one.
- **No account name, address or other detail of Zach's goes to an outside service** unless he says so on a card. Verification notes and screenshots use made-up accounts.
- **Mail is read only as far as a test he approved needs.** The mail slices are proved against a local fake IMAP and SMTP server. A live check reads a message he names, in a mailbox he chose.
- **Each plugin sits behind one adapter in `src/main/plugins/<name>/`** that imports nothing from Electron, so the host runs the same code, and uses Node's `fetch` or sockets. No vendor SDK, no new runtime dependency (ADR-0018).
- **Targeted tests on the laptop, the suite on GitHub.** Each slice lists the tests that cover it.
- **A question that is Zach's goes to him on a card before the slice that needs it.** The open ones are listed under their slice.

## Is "the tab, plus GitHub and one other service" small enough to land first?

No. Checked against the code on November 11, that is four separate pieces of work, each with its own tests and its own way to go wrong:

| Piece | What it touches |
|---|---|
| A Settings page | `settingsPages.ts`, `SettingsView.tsx`, a new page component and stylesheet (onto the `owned` list of `themeTokens.test.ts`), the Owl list, the Find index, `settingsReachable.test.tsx`, the interface catalogues, design captures |
| GitHub's row | A new read of who `gh` is signed in as (today's helper in `src/main/agents/git/github.ts` returns host names only), an IPC channel and a preload bridge |
| Agent tools | A new tool server on the `ScopedThreadTools` seam, its gate, Devin's list of Sotto servers, the use record and its store |
| One other service | The account store, a credential slot per account, add, replace and remove over IPC with nothing readable by the window, a check against the service, a new host in the README, and reads held to that host |

So it is three slices: the page with GitHub's row and no tools (slice 1), the tools with GitHub reads and no secret (slice 2), and Vercel as the first account with a secret (slice 3). Slice 1 proves the page and the gate; slice 2 proves an agent can reach a plugin; slice 3 proves a secret can be kept and used without an agent holding it. Each is reviewable on its own and none leaves a half-working control on the page.

## Slices

A plugin's row appears on the page in the slice that makes it work. The page never lists a plugin that does nothing yet.

### 1. The Plugins page, with GitHub's row (#2486)

- The Owl entry `plugins`. A **Plugins** page after Providers, shown only on Owl, reachable from Find a setting and from the keyboard.
- The plugin list in `src/shared/plugins.ts`: an ID, a name, a group and an icon for each. Only GitHub's row shows.
- GitHub's row opens in place: who `gh` is signed in as on this computer, or that it is not signed in and how to sign in. Nothing stored.
- The page's one sentence on how agents use a plugin.
- Docs: `CONTEXT.md`'s Settings pages entry, `docs/guide.md`, a verification note with screenshots at 1600x1000, 1280x800 and 820x560, dark and light.
- Icons are each service's own mark in one colour from the theme, the way provider marks are drawn. Zach sees it in this slice's screenshots and can ask for their own colours instead.
- Tests: `settingsReachable.test.tsx`, a page test for both sign-in states, `themeTokens.test.ts`, `scaleTokens.test.ts`, `interfaceCatalogs.test.ts`, the gh reader's unit test.

### 2. Plugin tools, with GitHub reads (#2487)

- The tool server `sotto_plugins` on the `ScopedThreadTools` seam, admitted per thread, with `plugin_accounts` and `plugin_read`. Watcher gets these two reading tools and never a change's tool.
- `plugin_read` for GitHub: `gh api` with `GET` only, nothing else reachable through it.
- The plugin use record, in its own store, and **Recent use** on GitHub's row.
- Devin's list of Sotto servers gains the name, so Devin does not ask natively.
- Tests: the tool server's unit tests (admission, `GET` only, a refused method), the record's store test, the adapter contract unchanged, `copySites` and `zodSchemaSites` clean.

### 3. Vercel accounts (#2488)

- The account store and one credential slot per account. Add, name, replace and remove from the page; the window learns only "saved" and when.
- Adding checks the token against Vercel and says plainly when it is refused.
- `plugin_read` for Vercel over `fetch`, held to `api.vercel.com`, with the refuse list for reads that return other secrets.
- `README.md` names `api.vercel.com`.
- Tests against a local fake of Vercel's API: add, refuse, replace, remove, a read, a refused read, a host that is not Vercel's. `settingsHistoryIpc.test.ts` for any new setting.
- **Hand step for Zach:** paste a real token into the built app once and read one deployment from a thread.

### 4. A change asks first (#2489)

- The pending change: a named tool's call waits in Sotto on a card that names the thread, the account and what will happen; it counts in Needs you, lapses, and only the user's choice answers it.
- The first named changes. Zach chose, on November 12: comment, open an issue, and close or reopen an issue (GitHub); redeploy as a preview, promote to production, cancel a build and roll back (Vercel).
- Landed in two pull requests. The first carries the pending change and one change per plugin: `github_comment` and `vercel_cancel_deployment`. The second carries the rest.
- **Redeploy as a preview waits for a live check.** Vercel's pages say that without a target "the branch decides production or preview", so a redeploy Sotto calls a preview could deploy to production. It ships only after a check against a real project shows it cannot, or its card says production.
- Tests: a change never reaches the service before the answer; Deny, lapse and a settled thread all refuse; Watcher and wake-up turns cannot answer; the card's words (ADR-0185).

### 5. Which threads may use an account (#2490)

- The account's on switch, and narrowing an account to chosen projects.
- `plugin_accounts` and every tool honour both, re-checked at the call, not only when the tools were handed out.

### 6. Ask before each preview deploy (#2491)

- The first **Ask before each** switch, on by default, on a Vercel account. Off, a preview deploy runs without a card and still shows in the thread and the record.
- `AGENTS.md` and the guide say what the switch grants.

### 7. Account copies on paired hosts (#2492)

- One limit and one switch wherever the account is: computers holding a copy report their spending to each other while connected, a host cut off keeps to what was left when it last heard, and a switch turned off on the desktop applies on a host.
- The amendment to ADR-0025 in code: the desktop sends an account's secret and settings to its own paired hosts over the connection it holds, and the host keeps it in its encrypted credential file.
- The **Other computers** group, the copy default, a switch per account and host, the waiting state, removal that reaches every copy.
- The host serves `sotto_plugins` to its own threads from its copies. GitHub's row shows each host's own `gh` sign-in.
- A host protocol feature, so an older host is told apart and never sent a secret it cannot keep.
- Tests: `hostServiceContract.ts`, only the desktop that holds the host's desktop grant may send one, a phone and a local app are refused, a host never sends one back, removal while the host is away.
- **Hand step for Zach:** add an account on the laptop and use it from a thread on forge with the laptop closed.

### 8. Gmail: read (#2493)

- The mail adapter over IMAP with an app password. `plugin_read` takes a search, or a message to open, for a mail account.
- The mail grant: a thread's first read waits on a card naming the account and the thread's provider.
- `README.md` names Gmail's mail hosts.
- Tests against a local fake IMAP server.
- **For Zach, on a card, before any live check:** which mailbox and which message a live check may read.

### 9. Mail: send (#2494)

- Sending over SMTP as a named change that always asks, showing the recipients, the subject and the text.

### 10. Proton Mail (#2495)

## Order and what can run side by side

Slices 1 to 4 are in order. After 4, slices 5 and 6 are small and independent; 7 needs 3; 8 needs 4; 9 and 10 need 8; 11 to 14 need 4 and are independent of each other; 15 needs nothing after 2 and can start early; 16 needs 15.

## Not part of this

- Keys for your own model servers stay where ADR-0124 put them, in Sotto's OpenCode and Hermes folders. They are a provider's keys, not plugin accounts, and this plan does not move them.
- A plugin a user writes or installs. The list is Sotto's.
