# Needs you in the Threads sidebar

Zach picked №11, the combination of variants 3 and 7, from `docs/prototypes/thread-attention-prototype.html` on October 24, 2026, over the ten variants before it. His calls the same day: blocking requests first, then oldest; no Undo; settled threads' requests surface, tagged **Settled**; **Just finished** and **Prototype ready** stay separate and softer (his earlier no-answer took the recommended default); and it is an Owl feature first. The decision is [ADR-0135](../adr/0135-the-threads-sidebar-opens-on-needs-you.md) (number provisional until merge). Desktop only: the iPhone already opens on Needs you, and the phones, Watcher and alerts do not change. One branch, one pull request: `feat/needs-you-queue`.

## Goal

Under Search threads, a **Needs you** card lists one entry per thread that needs the user, across every project and host, and answers or dismisses the simple cases where the user stands. Done means: no one has to expand folders or decode "● 4" to learn who is blocked, on what, and since when — and a short approval, a one-tap question and a failed turn can each be settled from the sidebar with exactly the delivery guarantees the thread pane gives them today.

## Acceptance checks

- [ ] With `needs-you-queue` off, the sidebar is today's whole: folder and Settled dots, the "N need attention" line and Dismiss all, every existing test unchanged. With it on, the card takes the line's place, the dots are not drawn, and folder toggles still name how many of their threads wait on you.
- [ ] Membership is derived, never stored: rows whose state is `needs` — own permission, own question, own unseen failure; a delegated wait stands on its listed thread with "Waiting in …" and opens only; settled permissions and questions stand tagged Settled; settled and seen failures never stand; **Finished unread** and **Prototype ready** never stand and never count. Searching never changes the card. At zero there is no card.
- [ ] Order is permissions, then questions, then failures; oldest wait first inside each kind; ties by thread ID. Three entries stand; the rest read "+ N more waiting" with their kinds counted, behind **Show all** (Escape folds it back and returns focus). Settling the top entry pulls the next up without the card jumping.
- [ ] The host stamps each request (`since`) and each named failure (`failureSince`) and publishes both add-only on protocol v1. Entries say the wait only from a stamp; an older host's entries order by last activity inside their kind and show no wait words. A restart restamps, understating rather than inventing.
- [ ] An inline answer is offered only for the entry thread's own request, while its pane card could answer: not busy, connected, nothing sending, sent, held or uncertain, and no draft in progress. Permissions only when the whole summary fits (no plan, no details block, at most three choices, none described; command and folder within the plan's starting bounds — command 160 characters, folder 80 — held as named constants beside the derivation). Questions only when single, structured, single-choice, at most four options, no free text, nothing unavailable, no pages and no missing link; an optional one also offers Skip. Everything else — legacy choices, plain-text questions, plans, described or extra choices, delegated waits — offers **Open to answer** and nothing else.
- [ ] Answering from the card is answering from the pane: the same `RequestAnswerStore` entry, owner, `answer` command, Check again read and state words; one send closes both surfaces; an unconfirmed delivery holds on both. There is no Undo and no second path. What main took is still noted for Watcher where Watcher is on.
- [ ] A failure's **Dismiss** sends `dismiss-failures` for that thread with the `failureId` its row showed; with two or more failures standing, **Dismiss N failed** sends them together under the existing cap. An older or unreachable host answers in today's words and focus stays on the press; an accepted press moves focus to the next entry's first control, else the search field.
- [ ] The look is ADR-0110's, not the prototype's: a filled card, rows divided as card rows are, the app's own buttons, a filled count badge and Settled tag, need said by the ring and its words, colour only from `--tt-*` tokens, 4.5:1 text, nothing clipped at a 260px sidebar or an 820×560 window, dark, light and reduced motion. No pill, no amber outline, no live region, no timer of its own.
- [ ] The whole card works from the keyboard in eye order after the search field. Every control names its press and its thread. New words go through the Lingui macros; provider labels stand as sent.
- [ ] No new setting, host, dependency or permission. Derivation is linear in the rows already described and adds no per-second work.

## Steps

1. **Stamps (shared + host).** Add the two optional add-only fields in `src/shared/agents.ts`; stamp requests where the coordinator first publishes them in `src/main/agents/control.ts` (kept beside the request while it stands, never from an adapter), and publish the named-at moment `FailuresSeen` already records (`src/main/agents/failuresSeen.ts`). Older readers drop the fields. Gate: `tests/unit/main/failuresSeen.test.ts`, `failuresSeenControl.test.ts`, plus a control-level stamp test.
2. **Derivation (renderer facts).** In `src/renderer/src/agents/threadFacts.ts`, derive the queue from the rows `organizeWorkspace` already produces: membership, order, the three shown and the overflow counts, and each entry's action — answerable with its choices, dismissible, or open-only — with the fit bounds as named constants. Pure and shared like the rows, so an untouched entry does not re-render. Gate: `tests/unit/renderer/agents/threadFacts.test.tsx` and `threadFactsMetadata.test.ts` cases for every acceptance line above that is a fact.
3. **One submit path.** Lift the pane's submit and check wiring (`ThreadRequests` in `ThreadPane.tsx`) into a hook both surfaces call, over `threadRequestOwner`/`threadRequestBlocked` and the shared store; the pane keeps its behaviour, and the two "answered here and nowhere else" comments now name the store as the one place. Gate: existing request-card and pane tests stay green untouched in what they assert.
4. **The card (sidebar).** A `NeedsYouQueue` in `ThreadSidebar.tsx` rendered through the existing `afterSearch` slot while `useOwlFeature('needs-you-queue')` answers yes — the entry added to `src/shared/owlFeatures.ts`, `sentToStable: false`, owned by ADR-0135 — and the Dismiss all line and collapsed dots only while it answers no. Styles join `threadSidebar.css` in tokens; dismissal reuses the line's focus rules. Gate: a new `tests/unit/renderer/needsYouQueue.test.tsx` (phases, hold, blocked, refusals, focus succession, off-means-today) with `needsAttentionSeen.test.tsx` and `threadsView.test.tsx` still passing.
5. **Words.** CONTEXT.md's **Needs you** stops being iPhone-only and says what the desktop card is, keeping "inbox" avoided; `docs/guide.md`'s sidebar words and any screenshot of the sidebar head follow. Run `npm run i18n:extract` for the new strings.
6. **Captures and evidence.** Regenerate only the sidebar design captures the card changes (`npm run design:capture`, then `npm run design:verify`, saying so in the PR), exercise the real app at 1600×1000, 1280×800 and 820×560 in dark, light and reduced motion, and record it in `docs/verification/needs-you-queue.md` with its artifacts folder named in `.gitignore` and `eslint.config.mjs`.

## Validation

- `npm run typecheck`, `npm run lint`, `npm run notices:verify`.
- `npx vitest run tests/unit/renderer/agents/threadFacts.test.tsx tests/unit/renderer/threadFactsMetadata.test.ts tests/unit/renderer/needsAttentionSeen.test.tsx tests/unit/renderer/needsYouQueue.test.tsx tests/unit/renderer/agents/threadsView.test.tsx tests/unit/main/failuresSeen.test.ts tests/unit/main/failuresSeenControl.test.ts tests/unit/renderer/themeTokens.test.ts`, then the full `npm test`.
- `npm run build` and Playwright on `tests/e2e/needs-attention-seen.spec.ts` plus a new queue journey: approve from the sidebar while the pane is closed, watch the pane's card close too; dismiss one failure and all failures; refuse once from an older host and keep focus.
- Highest risk, checked first among equals: one store entry, two surfaces — answer a request in the queue while its pane card stands open, and again from the card while the queue stands, including the unconfirmed hold. If either can double-send, the feature does not ship.

## Not doing

No Undo or delayed send. No per-request entries (one per thread). No finished or prototype strip — rows keep saying Just finished and Prototype ready. No rail queue, no new shortcut, no phone, Watcher, Overview or alert changes, and no removal of the Dismiss all line or the dots while the feature is off.

Prototype source: `docs/prototypes/thread-attention-prototype.html`, kept with the build as the other prototypes here are kept. Verification: `docs/verification/needs-you-queue.md`.
