# Main lagging with a few hundred threads - October 20, 2026

## The gate

Issue #1232. Main's lag kept coming back (#917, #925, #1038, #1062, #1065-#1068, and the October 20 profile of Owl
0.1.38-owl.20261020.1, main 96% busy with 105 stalls of 100 ms or more in a minute). Each time the cause had the same
shape: work per update that grew with what the user had accumulated. The checks that block a merge,
`streamingCopyBudget.perf.test.ts` and `copySites.test.ts`, missed October 20's two causes, #1230 and #1231, because
their pipeline had no remote host, no answer retirements and an empty Watcher record, did nothing the user does, and
did not count `clonePlainData` of Watcher's record or the router's shell builds. Timing checks are opt-in, so nothing
else in CI could see it.

### What it counts

`tests/perf/ownerScaleWorkBudget.perf.test.ts` builds main from its real pieces, wired as `src/main/index.ts` wires them
(`tests/fixtures/ownerScalePipeline.ts`): the provider switch, the workspace, the coordinator, the local host service,
the desktop router with this computer and a connected remote host, the window's state publisher with the
answer-recovery pass it asks for on every publish, the answer-draft store started from a file of retirements, the
Watcher room and the host-update busy check. It builds it twice over:

- **Owl**, with every Owl feature on and no provider held: Watcher open with a full record and standing watches.
- **Stable**, with the Owl features off and Muse and OpenCode held: their adapters are stand-ins, Watcher does not run
  and its record is kept whole, and every publish filters the held providers' models, projects and threads out (#1068).

The world is generated from counts only (`tests/fixtures/ownerScale.ts`). Scale 1 is the owner's:

| | Scale 1 |
| --- | ---: |
| Threads on this computer | 250 |
| Threads on the remote host, each with an answered question | 40 |
| Answer retirements, of them on the remote host | 256, 40 |
| Watcher owners in request-drafts.json | 4 |
| Watcher operations, requests, standing watches | 150, 160, 5 |

The first row is the threads; every other row is the history. Each track is built three times: with the owner's
threads and a quarter of their history, with all of both, and with a quarter of their threads and all of their history.

In each, it streams 30 chunks on one thread and on three, counted per coordinator update, and does once each what the
user does: saves an answer draft, types in a composer (the debounced draft save main receives), opens a thread
(selection, detail and observation) and sends. Each is counted until a second after it, on the test's clock, so what it
set off is counted with it. Watcher's wake-up pass runs on every update here, as it does when an update moves something
it reacts to. For each scenario it counts:

- copies of a host's whole state (`structuredClone`, `clonePlainData`, `cloneHostSnapshot` or `cloneActivitySnapshot` of
  a shell or snapshot that carries every thread of a host), and the threads they carried and the objects they made;
- router shell builds (`DesktopHostRouter.build`) and coordinator shell builds (`AgentControl.shellOf`);
- thread visits: every read of a thread out of a snapshot's or a shell's thread list, through a counting Proxy on the
  lists the adapter, the coordinator and the remote host hand out (`tests/fixtures/threadVisits.ts`);
- copies of Watcher's whole record, the objects those copies made, and whole-record comparisons (`isDeepStrictEqual`);
- the answer-draft store's look-ups of an answer's thread;
- `JSON.stringify` calls, which stand for work done per item;
- reads of a provider out of a public model or project ID (`parsePublicProviderEntityId`), which is how stable filters
  the providers it holds, and schema failures, each of which builds an error (#1068).

### The same counts on every run

The first version paced the stream with real 5 ms sleeps and closed each measurement after a real 700 ms, while
publication and the answer-recovery pass (every 500 ms) ran on timers, so the machine's speed decided which deferred
work fell into a measurement. It took the median of five. Now every timer main sets runs on Vitest's fake clock, which
moves only in 5 ms steps the test takes, and after each step the test waits until no file read or write is in flight.
Two things finished on the machine's time and moved work between steps until they were taken off it: the workspace
asks Git about each project folder, and a Git stand-in now answers at once, as Git does for a folder that is not a
repository; and `node:timers/promises` waits run on the same fake clock. Five runs on the scratch branch printed the
same counts, byte for byte, and three runs on `main` did too, so each action is counted once.

### Two lines, two rules

A count may not grow the wrong way along either line:

- **Along the history**, with the owner's threads held, every count stays flat: a tenth more and two more at most. This
  is how every regression above grew.
- **Along the threads**, with the owner's history held, thread visits, `JSON.stringify` calls and the threads and objects
  whole copies carry may grow in proportion, since a broadcast carries every thread, but no faster; every other count
  stays flat.

It also fails when a count passes its budget at the owner's scale. A failure names the track, the scenario, the count,
the line it grew along and both ends. With `SOTTO_WORK_SITES=1` it also names the places in `src/` whose serializations
and thread visits grew most.

The first version allowed `JSON.stringify` to grow fivefold for fourfold history (125 to 445-480 an update). That was the
threads, not the history: its quarter scale also had a quarter of the threads, and `sessionKey`
(`src/main/agents/threads.ts`) stringifies a key for every thread on every update. With the threads held, an update's
`JSON.stringify` calls are 441 and 445 at a quarter of the history and at all of it.

### Raising a budget

Read the failure: it names what grew and along which line. Do work bounded by what changed, and read state without
copying it. The budgets only tighten. A change that lowers a count lowers its budget in the same pull request; a change
that needs a higher one says why in the pull request, and asks Zach first, as the copy budget does. A fix for #1248
removes its `KNOWN_HISTORY_GROWTH` entry. To see every count, and where the serializations and visits are made:

```powershell
$env:SOTTO_PERF_BENCH = '1'; $env:SOTTO_WORK_SITES = '1'; npx vitest run tests/perf/ownerScaleWorkBudget.perf.test.ts --maxWorkers=1 --disable-console-intercept
```

`tests/e2e/main-freeze.spec.ts` every night on a Windows runner with `SOTTO_PERF_ASSERT=1`: the built app on Owl with

## Keystrokes

where on main it read 20 to 30 ms. Nothing in Sotto caused that. The spec's timer runs from a key's keydown to the next
animation frame, and the window was off screen. Chromium draws a window that is minimized, covered or behind a locked
screen about once a second, so each key waited a uniform 0 to 1,000 ms for its frame: p50 about 500 ms, p95 about

The Watcher fix moved some work to the window. Typing in the spec pauses 375 ms between keys, so the composer saves
after every key (it saves a pause of 250 ms), and main answers each save with the whole state. The window committed that
reply urgently, as it does the reply to an action the user is watching, so each save became a synchronous render of the
whole sidebar at 272 threads, about 60 ms, which the next key could wait behind. While main froze, a broadcast usually
arrived during the save's round trip and the window skipped the reply, so the render rarely happened. With main free,
every reply landed: the window's long tasks while typing went from 2 to about 30 in fifteen seconds. A draft save's
reply now commits as a transition, as a broadcast does (`AgentContext.tsx`; `draftSaveReplyPriority.test.tsx` counts
it). With that, long tasks went back to 0 or 1 a case, keystroke p95 to 24 to 27 ms, and the window drew 48 to 50 frames
a second while threads streamed, where it had drawn 26 to 37.

Main sends the window about 120 state broadcasts in a fifteen-second case of typing with nothing streaming, whichever
build (7.5 a second once main keeps up), and 17.5 a second while threads stream, each about 480 KB as JSON at 272
threads. The fixes did not change how many; what changed was the urgent render each save's reply added.

The spec now marks a case whose window drew fewer than 5 frames a second invalid, and with `SOTTO_PERF_ASSERT=1` fails
it. It reports per case the frames a second, the state broadcasts a second, the window's long tasks and its handling
time per key (keydown to input) beside the keystroke latency. `SOTTO_FREEZE_PROFILE=<folder>` writes a CPU profile of
the window per case. `docs/verification/2026-10-20-draft-save-reply-priority.md` records the runs behind the tables
above, with their output in `artifacts/draft-save-reply-priority/`.

## Answer-draft saves

Issue #1230. The owner's profile of Owl 0.1.38-owl.20261020.1 put half of main's time in one minute under `RequestDraftService.commit`, reached from `save`. Each save of a question answer looked up the thread of every retired answer in the ledger, and for a thread on a remote host the router built every host's state afresh to find it (`DesktopHostRouter.shell()`: `visibleState`, `clientAgentState` and a copy of each remote host's shell). The owner's store held 256 retirements, 40 of them remote, so every save built the whole state about 40 times, and the count grew with every question answered.

What changed:

- The router answers for one remote thread from that host's view, read in place (`windowThread`). Only the thread's requests are copied for the caller, as they already were for this computer's own threads. A thread with no provider of its own takes the selected host's catalog and default from that host's view, as `shell()` would give them, without building anything.
- The receipt pass (`issueRequestDraftChecks`) reads each held answer's thread the same way rather than building every host's state.
- `preservesDormantThread` reads the host's view instead of copying its shell.
- Once the ledger has been classified, `commit` looks up a retired answer's owner only when looking it up could change what is saved: its thread is Watcher or held to Owl now, or the owner is still unclassified. `requestDraftWatcherOwnerIds` names those threads, on this computer and each remote host, by reading each thread's kind in place, and the store finds them in an index of the ledger. Owners with a draft are looked up on every commit as before, and a legacy file with no Watcher list is classified in full once.
- The ledger index is rebuilt from the saved ledger when it changes, so it holds nothing the ledger no longer names. `retirement()` reads it rather than scanning the ledger.
- A commit that keeps the ledger as it was checks only the rest of the record, rather than parsing and comparing every retirement again.

Counted by `tests/unit/main/requestDraftSaveCost.test.ts`, a real `DesktopHostRouter` with one remote host behind `requestDraftOwnerState`, saving an answer on a remote thread. Owner keys count every `requestDraftOwnerKey` the store and router work out.

| Ledger | Whole-state builds per save | Remote shell copies per save | Owner lookups per save | Owner keys per save |
| --- | --- | --- | --- | --- |
| origin/main, 64 retirements (10 remote) | 12 | 12 | 66 | |
| origin/main, 256 retirements (40 remote) | 42 | 42 | 258 | |
| Round 1, 64 retirements (10 remote) | 0 | 0 | 2 | 197 |
| Round 1, 256 retirements (40 remote) | 0 | 0 | 2 | 773 |
| Now, 64 retirements (10 remote) | 0 | 0 | 2 | 4 |

The first save after start makes the same two lookups and indexes the ledger once (131 and 515 owner keys). A recovery pass over a held answer on a remote thread that names no provider built the whole state 6 times in round 1 and builds it none now.

## Watcher's pass

The owner's Owl build (0.1.38-owl.20261020.1) had about 250 threads, five standing watches and a Watcher record of 160
requests and 149 operations. In a one-minute CPU profile of main, Watcher took about 27% of it (#1231, which replaces
#1064):

- `WatcherService.observe`, which runs for every snapshot main accepts, about 12%. For each thread it walked every
  request's participants and every operation, then walked every operation again against the thread list and the send
  records. It offered the record to `AgentControl.mutateWatcher` on every pass, which copied it and compared the copy
  with the original even when nothing had changed.
- `WatcherService.state()`, which builds the room on every publish, about 10%. For each target the record names it
  searched the watches and every participation of every request, building two target keys (`JSON.stringify`) at each
  step. `key` alone was 7.6% of main's own time.
- The wake-up news Watcher reads on every publish worked out its workers again for every recent event.

All of it grew with the record times the thread count, and no test built a record that size.

### What changed

- The observe pass reads the record once. What the record says about each of this host's threads (participations still
  taking part, operations, standing watch) is indexed once per record. The record is replaced on every change and never
  edited, so the index holds until the record changes. Each operation's delivery and failed follow-up are read once per
  pass, and threads are found by ID.
- The pass gathers what it changes and makes one change at its end. Before it does, it asks the record itself whether
  anything would change: an operation's delivery or outcome, a reservation, a request to close. When nothing would, it
  makes no copy and no comparison. The question and the change work out an operation's delivery with the same
  calculation, so they cannot disagree, and a queued send whose failure is already recorded asks for no change.
- A takeover the pass finds (the user's own message arriving in a thread) is made at once on a copy of the record, which
  the rest of the pass reads and its one change keeps, so a pass with two takeovers copies the record once and changes
  it once, where it changed it three times. The queued sends a takeover fences leave the queue after that change.
- A record loaded with more prompt turns than are kept is trimmed by the first pass after it loads, as before.
- The room state walks the record once per publish, by target keys built once per record, and finds each target's
  thread by ID.
- Wake-up news works out Watcher's workers once per pass and finds them by target, request and standing watch. The
  pass that looks at every thread keeps each thread's key from the last pass.
- `AgentControl.observeWatcher` gathers the messages Sotto sent only when the pass asks.

Behaviour is unchanged: every existing Watcher test passes, apart from one count of paired-host reads that is now lower.

### Not changed

- The wake-up pass still visits every thread, and `WatcherService.snapshot()` still spreads every thread into the merged
  snapshot it reads. Both are once per pass, not per thread or per record entry.
- A takeover still builds target keys across the record, about 4,000 for two at the owner's scale. It runs only when
  the user acts in a thread Watcher has.
