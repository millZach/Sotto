# Main lagging with a few hundred threads - October 20, 2026

## The gate

Issue #1232. Main's lag kept coming back (#917, #925, #1038, #1062, #1065-#1068, and the October 20 profile of Owl
0.1.38-owl.20261020.1, main 96% busy with 105 stalls of 100 ms or more in a minute). Each time the cause had the same
shape: work per update that grew with what the user had accumulated. The checks that block a merge,
`streamingCopyBudget.perf.test.ts` and `copySites.test.ts`, missed October 20's two causes, #1230 and #1231, because
their pipeline had no remote host, no answer retirements and an empty Watcher record, did nothing the user does, and
did not count `clonePlainData` of Watcher's record or the router's shell builds. Timing checks are opt-in, so nothing
else in CI could see it.

### What it counts

`tests/perf/ownerScaleWorkBudget.perf.test.ts` builds main from its real pieces, wired as `src/main/index.ts` wires them
on Owl (`tests/fixtures/ownerScalePipeline.ts`): the provider switch, the workspace, the coordinator, Watcher open with a
full record, the local host service, the desktop router with this computer and a connected remote host, the window's
state publisher with the answer-recovery pass it asks for on every publish, the answer-draft store started from a file
of retirements, the Watcher room and the host-update busy check. The history is generated from counts only
(`tests/fixtures/ownerScale.ts`); scale 1 is the owner's:

| | Scale 1 |
| --- | ---: |
| Threads on this computer | 250 |
| Threads on the remote host | 40 |
| Answer retirements, of them on the remote host | 256, 40 |
| Watcher owners in request-drafts.json | 4 |
| Watcher operations, requests, standing watches | 150, 160, 5 |

It streams 30 chunks on one thread and on three, counted per coordinator update, and does what the user does, each five
times and counted once what it set off has settled, keeping the median: saves an answer draft, types in a composer (the
debounced draft save main receives), opens a thread (selection, detail and observation) and sends. Watcher's wake-up
pass runs on every update here, as it does when an update moves something it reacts to; left to its 250 ms timer, how
many updates it ran in would depend on the machine. For each scenario it counts:

- copies of a host's whole state: `structuredClone`, `clonePlainData`, `cloneHostSnapshot` or `cloneActivitySnapshot`
  of a shell or snapshot that carries every thread of a host;
- router shell builds (`DesktopHostRouter.build`) and coordinator shell builds (`AgentControl.shellOf`);
- copies of Watcher's whole record, the objects those copies made, and whole-record comparisons (`isDeepStrictEqual`);
- the answer-draft store's look-ups of an answer's thread;
- `JSON.stringify` calls, which stand for work done per item: Watcher's target keys are built with it.

It runs everything at a quarter of the owner's history and at all of it. A count fails when it grows by more than a
quarter and one between the two. Two may grow as the history does (five times for four times the history) but not as
its square: `JSON.stringify` calls, and the objects a user's action copies out of Watcher's record, since a command may
copy the record while how many copies it makes is held flat. An update copies none of it. A count also fails when it
passes its budget at the owner's scale. It counts calls and never times anything, so it runs in the default suite, and
Gates (Windows) requires it. A failure names the scenario, the counts that grew and both scales' numbers.

green: `perf/answer-draft-save-cost` the save, `perf/watcher-pass-cost` the stream, typing, opening and sending.

### With both fixes

Merged together on a scratch branch (`perf/answer-draft-save-cost` at 86759be29, `perf/watcher-pass-cost` at
75a3f62f0), every scenario passes. At the owner's scale, in two runs that agreed:

| Scenario | Whole-state copies | Router builds | Coordinator shells | Watcher record copies (objects) | Look-ups | `JSON.stringify` |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| One thread streaming, per update | 1 | 1 | 1 | 0 (0) | 0 | 445-480 |
| Three threads streaming, per update | 1 | 1 | 1 | 0 (0) | 0 | 449 |
| Saving an answer draft, per save | 0 | 0 | 0 | 0 (0) | 3 | 33 |
| Typing in a composer, per save | 5 | 4 | 7 | 2 (2,898) | 2 | 44 |
| Opening a thread, per open | 10 | 5 | 8 | 2 (2,898) | 1 | 46 |
| Sending, per send | 22 | 10 | 16 | 7 (10,143) | 2 | 3,855 |

At a quarter of the history an update made 125 `JSON.stringify` calls, about a third as many: that work now follows the
history rather than its square. The budgets are these numbers with about a fifth more room, and an update may copy
Watcher's record at most once in four. What still grows is the size of the record copies a typed draft, an opened
thread and a send make; those are commands, not updates, and how many they make is held flat.

The nightly spec, run on this machine at the owner's scale with `SOTTO_PERF_LIMITS=1`:

| Case | Main: longest stall, stalls of 100 ms or more | Both fixes: longest stall, stalls | Both fixes: keystrokes p50, p95 |
| --- | --- | --- | --- |
| Nothing streaming | 289 ms, 113 | 32 ms, 0 | 534 ms, 969 ms |
| One thread streaming | 342 ms, 136 | 55 ms, 0 | 481 ms, 915 ms |
| Three threads streaming | 322 ms, 129 | 392 ms, 2 | 567 ms, 989 ms |

On main every case failed its limits; with both fixes every case passed them. The keystroke column is new and not yet explained: with main no
longer stalling, a key took half a second to a second to reach the screen, even with nothing streaming, where on main it
took 20 to 30 ms. The renderer, not main, is the next place to look; the spec reports it and sets no limit on it.

### Raising a budget

Read the failure: it names what grew. Do work bounded by what changed, and read state without copying it. The budgets
only tighten. A change that lowers a count lowers its budget in the same pull request; a change that needs a higher one
says why in the pull request, and asks Zach first, as the copy budget does. To see every count:

```powershell
$env:SOTTO_PERF_BENCH = '1'; npx vitest run tests/perf/ownerScaleWorkBudget.perf.test.ts --maxWorkers=1 --disable-console-intercept
```

### The nightly timing run

Counting misses work that is cheap to count and slow to do. `.github/workflows/main-freeze.yml` runs
`tests/e2e/main-freeze.spec.ts` every night on a Windows runner with `SOTTO_PERF_LIMITS=1`: the built app on Owl with
the owner's history (threads with provider sessions, Watcher's record at the owner's size, the retirements and a paired
headless host with 40 threads), and fails when main's longest stall or its count of stalls of 100 ms or more passes the
spec's limits while none, one or three threads stream. It never gates a pull request (`docs/ci.md`).
