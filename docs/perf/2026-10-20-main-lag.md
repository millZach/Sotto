# Main lagging with a few hundred threads - October 20, 2026

## Answer-draft saves

Issue #1230. The owner's profile of Owl 0.1.38-owl.20261020.1 put half of main's time in one minute under `RequestDraftService.commit`, reached from `save`. Each save of a question answer looked up the thread of every retired answer in the ledger, and for a thread on a remote host the router built every host's state afresh to find it (`DesktopHostRouter.shell()`: `visibleState`, `clientAgentState` and a copy of each remote host's shell). The owner's store held 256 retirements, 40 of them remote, so every save built the whole state about 40 times, and the count grew with every question answered.

What changed:

- The router answers for one remote thread from that host's view, read in place (`windowThread`). Only the thread's requests are copied for the caller, as they already were for this computer's own threads. A thread with no provider of its own still builds the whole state to take the selected host's default, as before.
- The receipt pass (`issueRequestDraftChecks`) reads each held answer's thread the same way rather than building every host's state.
- `preservesDormantThread` reads the host's view instead of copying its shell.
- `commit` looks each owner up once, skips a retirement owner already kept as Watcher, and remembers retirement owners it has seen listed as ordinary threads, so it does not look them up again. A thread's kind and provider are fixed when it starts, and the run's held providers and Watcher switch are read once at start, so looking one up again could not change what is saved. Owners with a draft, unclassified owners and retirements whose thread is not listed (a host still offline, a removed thread) are looked up on every commit as before, now without building anything.
- A commit that leaves the retirement ledger as it was no longer compares every retirement to find changed owners.

Counted by `tests/unit/main/requestDraftSaveCost.test.ts`, a real `DesktopHostRouter` with one remote host behind `requestDraftOwnerState`, saving an answer on a remote thread:

| Ledger | Whole-state builds per save | Remote shell copies per save | Owner lookups per save |
| --- | --- | --- | --- |
| Before, 64 retirements (10 remote) | 12 | 12 | 66 |
| Before, 256 retirements (40 remote) | 42 | 42 | 258 |
| After, 64 retirements (10 remote) | 0 | 0 | 2 |
| After, 256 retirements (40 remote) | 0 | 0 | 2 |

After the change, the first save after start still looks up every owner once (66 and 258) to classify it, without building or copying any state. The two lookups on each later save are the thread being typed in: once for the save and once to classify its own draft.
