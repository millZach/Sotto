# Six small performance fixes - September 22, 2026

Six fixes from the September audit, one commit each. None changes what the user sees except the diagram, which now appears without a flash of its source. Each has a unit test that pins the new behaviour by count, not by stopwatch. The timings below are standalone Node measurements on the development machine (Windows 11, Intel Core Ultra 9 275HX, Node v24.14.1), taken while other test suites were running on it, so read them as sizes rather than budgets.

| Fix | What was counted or timed | Before | After |
| --- | --- | ---: | ---: |
| Widget agent connection | Widget commits for 100 streamed shells, voice coordinator off | 100 | 0 |
| | Agent subscriptions and state fetches, voice coordinator off | 1 and 1 | 0 and 0 |
| Cached diagram remount | First synchronous render of a diagram drawn earlier | source and "Drawing…" | drawn |
| | Commits for that remount | 2 | 1 |
| Follow-up queue reads | Queue copies for 50 host snapshots, one 3 MB image queued behind a running turn | 100 | 0 |
| | One copy of that queue | 2.17 ms | none |
| Files binding | Whole agent-state copies for a workspace check and a listing on each of two threads | 16 | 0 |
| Runtime hash | Serial SHA-256 of the four runtime files (36 MB), warm cache, median of 7 | 39.7 ms | the same work, started before the stores load so that it overlaps them |
| Reply audio decode | Base64 to bytes, 1 MB, median of 9 | 52-55 ms | 1.4-1.5 ms |
| | Natural voice base64 encode before playback, 1 MB | 30 ms | none |

## Notes

- **Widget.** Counted with a React Profiler around `WidgetEntry` in `tests/unit/renderer/widgetApp.test.tsx`. With the coordinator on, the same 100 shells still give 100 commits, so the feature is unchanged when it is enabled.
- **Diagrams.** `tests/unit/renderer/messageDiagrams.test.tsx`. The renderer is still asked on every mount; it answers with the same cached result, which is not a second commit. Failed and slow drawings are never mounted as drawn.
- **Follow-ups.** `tests/unit/main/followups.test.ts` spies on `FollowupStore.get` and `peek`. The shell copy that `AgentControl.shell()` makes for IPC on every broadcast still includes the queue; that copy is out of scope here.
- **Files binding.** `tests/unit/main/filesBinding.test.ts` spies on `AgentControl.get`. Through the old wiring, one listing was six whole-state copies and one workspace check two. The size of each copy depends on how much history is loaded; the audit measured 6 to 13 ms each with every history loaded.
- **Runtime hash.** The audit measured 113 ms for the same loop; this machine measured 39.7 ms. Startup still awaits the answer before any window, so the gain is only the part of the hash that overlaps the credential, settings and store loads, and the hash callbacks themselves run on the main thread. Launch-to-window medians over packaged launches were not measured for this change.
- **Reply audio.** A 20 s Grok or Kokoro reply is about 1 MB of WAV, so about 50 ms comes off the time before it starts playing; a 20 s natural-voice reply is about 1.8 MB, so about 150 ms. Typical coordinator replies are a few seconds and gain 5 to 15 ms. `npm run perf:voice` was not re-run.

## Re-run

The counts are in the tests named above: `npm test -- tests/unit/renderer/widgetApp.test.tsx tests/unit/renderer/messageDiagrams.test.tsx tests/unit/main/followups.test.ts tests/unit/main/filesBinding.test.ts tests/unit/main/modelProtocol.test.ts tests/unit/renderer/naturalSpeech.test.ts`.

The timings came from short Node scripts:

- Runtime hash: stream each of the four files in `resources/runtime` through `createHash('sha256')`, as `hashFile` in `src/main/models/modelProtocol.ts` does, one after another.
- Queue copy: `structuredClone` of `{ items: [one follow-up with a 3 MB PNG data URL], receipts: [] }`.
- Reply audio: 1 MB of bytes to base64 with `Buffer`, then `Uint8Array.from(atob(b64), c => c.charCodeAt(0))` against the indexed loop in `decodeBase64Audio`, and the old chunked `String.fromCharCode` plus `btoa` encode.
