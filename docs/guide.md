## Threads

### Starting a thread

When typing with a Japanese or Chinese input method, Enter finishes the current word first. Press Enter again to choose a project or branch, confirm a thread rename, or name a new folder.

New work starts in Unsettled. Pressing **New thread** can reuse an empty thread only if it is still unsettled, its known model, effort and permission choices match the current defaults in Settings, and no setting change is pending. If the saved effort or permission default cannot be resolved from the model catalog, a new thread opens instead. Settled threads and empty threads with older choices stay as they were.

A thread in a project opens at once, named "New thread" and ready for your first message: the pen beside a project row, the empty Threads page's own button, and choosing a project from the sidebar's top **New thread** button (or **Ctrl+Shift+N**, **Cmd+Shift+N** on a Mac) all open one this way. Only the top button and the shortcut with no thread focused ask which project first; the pen and the empty page's button already know it. The shortcut opens a thread in the focused pane's project, or asks which project when none is focused; it does nothing while a dialog is open or a terminal has focus. If the project already has an unused thread that meets those reuse conditions, it takes you back to that one instead of opening another. A creation the provider refuses says why where the sidebar shows other such errors, and nothing else is lost. When you send a new thread its first message, the thread takes the message's opening words as its name at once, and the name its provider writes replaces them shortly after the first turn ends. Both need Generated thread titles and Keep local history on (see Thread titles, branch names and Git).

Until you send it, a new thread greets you with a short line above its composer, picked at random, with the project, the branch and where the thread runs under it. The line and the composer sit together in the middle of the pane, so the composer is where you are already looking. The first send moves the composer down to its usual place at the bottom.

A new thread starts on **New threads start with** in **Settings → Agents**: a model, a reasoning effort and a permission mode, the same chips the composer itself shows. Change any of them for one thread from its own composer once it is open; the setting only chooses what a thread starts on. A model or provider that does not offer the chosen effort or permission starts on the nearest one it does — the closest safer permission mode, and the effort at the same position among the levels offered — and Settings says so under the row when that applies to the model chosen there. A provider with its own permission profiles, such as Devin, always starts on its first profile. These defaults belong to this computer and apply to a new thread on every connected host too. A host that does not have the chosen model starts the thread on its own recommended model. A host that does not let this computer answer permission requests starts the thread on **Ask for approval** instead of a permission that skips asking, and Settings names that host under the row.

If a new thread cannot be created, the error says when its prompt and screenshots are kept and names the project to open **New thread** in. The next new thread you open in that project gets its prompt and staged screenshots back. This includes a prompt you pressed Send on while creation was pending, along with anything typed afterward. Leaving Threads for Settings keeps this recovery in the window, and reusing an empty thread combines it with any draft already there. When their combined text or screenshots exceed a prompt's limits, each part stays as a **Not sent** message. Use **Restore prompt** to bring a part into the composer; the other parts remain available. Nothing is sent again automatically. Prompt text stays until you close the window; screenshots not owned by a saved draft are kept for an hour, so reopen the thread before then to keep them.

With no thread open, the Threads page shows a prompt Sotto is still keeping for you. When its thread is still listed, it says **Your draft for** the thread **is saved.** and **Open thread** takes you to it. When that thread is no longer listed, because a send to it never finished before it went away, the page says **A draft from an earlier thread is saved.**, or **An answer from an earlier thread is saved.** when it answered a question there, and names any images under the draft. **New thread with this draft** opens a new thread in the current project, or asks which project, with the draft's words and images in its composer; the old copy is cleared only once the new composer has saved it. Skills and files you chose for the old thread are not carried over, but their mentions stay in the text, so you can pick them again. **Discard draft** asks first, and **Keep draft** or Escape leaves it as it was. The page asks you to reconnect only while Sotto is disconnected; the draft waits until then.

### Providers and models

Setup and **Settings → Providers** show their own connection status and leave no success notice in Threads. **Connect providers** and Reconnect pressed in Threads report success there. Connection failures still say what happened.

Threads run in the installed Codex, Claude Code, Grok Build and Devin clients, and, in Sotto Owl, Muse and OpenCode. Connect clients independently in **Settings → Providers** and choose a model for each thread. That page is always this computer's clients, whichever host is selected for new work; a host's own are on its tiles in **Settings > Hosts**, and their messages name the host. Sotto finds each client the same way wherever it runs: on PATH, then on your login shell's PATH (not on Windows), then in `~/.local/bin`, then where mise, asdf, nvm, fnm, Volta and Homebrew install it, then in npm's global folder, so a client a version manager installed is found even when Sotto was started from the Dock. Grok Build's own `~/.grok/bin` comes first, and Codex is only ever started as its native binary, never through a wrapper script. OpenCode looks in more places still; its paragraph below says where. A manager's shim, or a script that runs the client through `mise x`, `mise exec` or `asdf exec`, is passed over for the install it would have run. A client found off PATH runs with its own folder and Node's added to the front of its PATH, so an npm-installed client can start. The model chip opens a two-column menu: the connected providers as a rail of marks down the left, and that provider's models on the right under a search line. Turn the mouse wheel over the rail to step through the providers. OpenCode's models come from several model sources, so its tile opens on those first: each with its model count, OpenCode Zen marked **Free with OpenCode Zen**, and the source of the thread's model in the accent colour. Choose one to see its models, newest first, with **Model sources** to go back. Typing in the search line skips that step and searches every source at once, under each source's name, and a source's name finds all its models. Escape steps back one level at a time: it clears the search, then returns to the model sources, then closes the menu. An OpenCode thread's chip names the source before the model, such as **Anthropic / Claude Sonnet 5**, with the OpenCode mark; in a narrow composer a long source name shortens first, so the model's name stays whole. The permissions chip beside it lists what a thread may do without asking; on Devin it lists Devin's own modes, each saying what Sotto will still ask you about under it. A choice on any chip shows at once, and the chips stay usable while the provider takes it. Until the provider confirms a permission change, the chip has a dashed outline and a small dot, and a line beside the chips says what is still in force, such as "Claude Code still asks for approval until it confirms.": that is the mode the provider's next tool call runs under. A prompt you send meanwhile runs on the new setting, because Sotto makes the change before it sends the prompt. If the provider will not take a change, the chip goes back to the value in force and a line under the composer says what happened, in the provider's own words where it says more, with **Try again**. If the provider never says whether it took a change, for example because its answer was lost, the chip keeps your choice with the same outline and dot, the chips wait, and the line says what happened and that the thread starts on your choice the next time it is used; the mark goes once the thread shows it. While a prompt you sent is still on its way to the provider, the chips wait for it. A model is listed under the fullest name its provider gives it, version and all, and the one the provider recommends stays at the top. A thread on a long-context model, such as Claude Code's `opus[1m]`, shows under its base model's name, for example **Opus 5.5**, and keeps its long context; choosing that entry again changes nothing. **Settings → Agents**, below Hosts, configures new-thread defaults and the default projects directory. The floating widget retains click-to-dictate and dragging. In a thread composer, open the effort chip to slide between the model’s supported reasoning levels; each level says what it costs. Release to choose, or use the wheel, the arrow keys, Home, End or the digits, and **Default** returns to the model’s own level. A new thread starts on that level unless you choose another; for Grok it is the level Grok marks as its default, not the one set in Grok’s own settings. The level you choose shows at once and the card stays usable while it is saved, so you can keep moving; the provider has the last word, and a change it will not take goes back to the level you were on and says so under the chips. At the model’s highest level the word, the chip and the composer’s outline take the **Effort color** chosen in **Settings → Appearance** (Ember, Cyberpunk, Rainbow, Aurora, Plasma or Theme accent), and reaching it plays a short wash of that color; reduced motion shows the finished state. Claude’s **Add Ultrathink to prompt** puts a visible instruction in the current draft without changing effort or permissions. Ultracode workflow orchestration is not currently exposed in Sotto.

In a thread's composer, type `/` at the start of a line or `$` to choose a native skill. A chosen skill shows as a pill led by a wand. Pointing at it says what it does. Backspace after the pill removes it whole; Delete before it does too. It is sent as the provider's native token. A token you type without choosing a skill stays plain text, even if you have already chosen that skill. Text typed or pasted against a pill gets a space where needed to keep its token whole. The queued message editor shows chosen skills the same way.

A new thread's model follows **New threads start with** in Settings → Agents until you choose it there, and until then follows the native agent and model selected for reasoning, including its reported default model when no model is selected. An unavailable selection waits until it connects, or choose another model from the composer's own model chip once the thread is open. With no native agent selected (Not configured or an API account), Sotto starts with an available native thread provider.

Claude Code model, effort and permission changes reach the thread's running session and wait for Claude Code to confirm them, so the session keeps going. When no session is running, when Claude Code refuses a change, or when the thread enters or leaves full access, Sotto starts the session again with the new settings instead. Choosing a model without a level uses that model's own default level. If Claude Code does not answer, Sotto stops that session and says the change is unconfirmed; the next start carries it, and nothing is sent twice. Stopping the session ends any background agents or commands it was running, so the message names them and the thread shows an error; ask Claude to start them again if you still need them.

Codex model, effort and permission changes use its native settings update and wait for confirmation. An interrupted change does not disconnect the provider. If Codex cannot confirm a permission change, the affected thread asks you to choose its settings again before sending. A model or effort change it cannot confirm holds nothing back: the thread still sends and takes another change, and its chip shows the change as unconfirmed until Codex reports it. Other threads remain available; reconnecting does not replay the settings change.

After you type directly in the Claude CLI, the next message from Sotto restarts its client to load the updated native history, even while background work runs. Any work stopped by the restart is named in the notice.

In Owl, **Settings → Providers → Muse** shows Muse's own mark, connection, installed and published versions, and model list. Install Muse and run `muse login` in a terminal before connecting; **Copy Muse login command** copies that command. Each computer keeps its own Muse sign-in, so a host's Muse is signed in on that host. Sotto says Muse is not signed in only when Muse answers with its empty built-in catalog; a Muse that is set up but lists no models says so instead. **Update** uses the installer that owns the existing copy. For Meta's own installation it updates the same folder without changing PATH or signing you in. Working threads keep their current client until they finish. An unidentified installation has **Open Muse installation guide** instead. Sotto checks Muse's own release channel when client update checks are on. Muse threads support questions and approvals, and get Sotto's browser, visuals and pull request babysitting as Claude Code, Codex and Grok Build threads do, when the installed Muse can take tools for one session (1.4.7 and newer can). On an older Muse, a thread offers none of them. A call to one of those tools is let through without a Muse prompt, and the tools still ask you wherever they always do. Muse gives up on a tool call after 5 minutes, so a browser request still waiting for your answer after 4 returns to the agent and stays open for you. Muse can host Watcher when it can take tools for one session; see Watcher's room below. Muse threads cannot set up a host, use skills, or write automatic titles and Git drafts in this version. **Shell sandbox** on the same page controls Muse's own shell sandbox on this computer: leave it on unless Muse's sandbox cannot be set up here (its one-time Windows setup does not run on some machines, and every shell command then fails). Off, Muse's shell commands and file tools run as you, with no sandbox: they can reach files outside the project and the network. A thread on **Ask for approval** still asks; Automatic and Full access do not. The switch applies when Muse next connects, and the page offers **Reconnect** while Muse still runs with the old setting; reconnecting stops a Muse reply that is under way. Each computer keeps its own switch. Only a computer's own Settings turn its sandbox off; a paired phone or desktop can turn it back on, but not off.

In Owl, **Settings → Providers → OpenCode** connects OpenCode 2. Install it from `opencode.ai/v2/install`, npm's `@opencode/cli`, Homebrew, scoop's `opencode2` or Arch's `opencode`; any of them works. Sotto looks in `~/.opencode/bin` first, where the install script puts it, then where it looks for the other clients, then where bun, pnpm, yarn, scoop, WinGet, Chocolatey and nix put commands, and in `/usr/bin` and `/usr/local/bin`. On Windows it also reads your PATH as Windows has it now, so a copy you installed after Sotto started is found when you connect again. It finds `opencode` and `opencode2`, follows a package manager's launcher to the program it starts, and when an install skipped `@opencode/cli`'s own install script, as pnpm and bun do unless told otherwise, it uses the program npm's package downloaded for this computer instead of the stand-in left in its place. OpenCode 1, which `opencode.ai/install`, npm's `opencode-ai`, WinGet, Chocolatey and nixpkgs give, and OpenCode 2 older than 2.0.31 are passed over for an OpenCode 2 found later. When there is none, connecting refuses with the version the first one reported and where OpenCode 2 comes from, and first-run setup offers OpenCode 2's install guide. Sotto runs OpenCode in a folder of its own, not the one your own OpenCode uses, so OpenCode starts there with no sign-ins: until you sign in to a model source in it, it offers only OpenCode Zen's free models. Each thread starts its own OpenCode server, which Sotto stops, with everything it started, once the thread has sat unwatched and idle for a while or when you disconnect; if Sotto itself stops without stopping them, it ends what they left running the next time OpenCode connects. Its models are listed under their model source, such as OpenCode Zen or Anthropic, always as OpenCode models; a model's variants are its effort levels, and a model that takes images can be sent them. Permissions are **Ask for approval**, which asks before commands, edits, work outside the project folder, web fetches, web searches and subagents, **Auto-accept edits**, which allows edits and asks before the rest, and **Full access**; OpenCode has no mode like Auto. You answer each permission with Allow once or Reject, and a rejection reaches the model as a failed tool call, so the turn goes on. OpenCode's questions arrive as question cards; one Sotto cannot draw, such as a field that shows only for another field's answer, is declined, and the model is told so. Replies stream with reasoning and tool activity, a running turn can be steered or stopped, and a thread resumes after Sotto restarts; a turn whose OpenCode server stopped reads as stopped, not as still running. OpenCode threads get Sotto's browser, visuals and the other tools Sotto gives a thread, which they use without OpenCode asking first; what each tool may do is still Sotto's to ask you about, as on every provider. If a thread's OpenCode server will not take them, the thread works without them, as a Muse thread without them does. OpenCode writes a thread's title, its new worktree's branch name and its Git drafts on the thread's own model, in one generation that offers the model no tools and adds nothing to OpenCode's list of sessions. OpenCode Zen's free models refuse that, so a thread on one keeps the opening words of its first message as its name, its temporary branch and the stand-in commit subject. OpenCode threads cannot host Watcher or use skills.

**Model sources** on the OpenCode tile lists OpenCode Zen, whose free models need no sign-in, and each model source Sotto's OpenCode is signed in to, with how it signed in (an API key, or an account such as ChatGPT), how many of its models are in the model menu, and **Sign out**. **Add a model source** opens a list of every model source OpenCode knows, the common ones first (Anthropic, OpenAI, OpenRouter, GitHub Copilot, Google and xAI), then the rest A to Z; type to search it, and use the arrow keys to move through it. A source already signed in is marked and cannot be picked. Pick one to sign in: when it has more than one way, choose one. An API key goes in a password field; Sotto hands it to its own OpenCode once and keeps no copy. OpenCode does not try a key when you paste it, so a wrong key shows on the first turn that uses one of its models: that turn says the model source refused the sign-in, and you sign out and paste the key again. A browser sign-in opens the model source's page in your browser and waits there, showing a code to enter on that page, a field for the code the page shows you, or a line that the page finishes by itself, with when it expires, **Open the page again** and **Cancel**. If your browser does not open the page, the dialog says so and shows its address, with **Copy address**, to open yourself. Sotto keeps checking a waiting sign-in, a pasted code included until OpenCode has taken it, so a page that expires while you wait says so. Closing the dialog, or leaving Settings, cancels a browser sign-in, even one still starting, and opens no page for it; one its page finished just before is kept. A key or a sign-in already on this computer that is still being saved when you close the dialog is not stopped: if OpenCode kept it, it shows under Model sources. Some ask a question first, such as GitHub.com or GitHub Enterprise and its address. The account you sign in with pays for its models. Sign-ins live in Sotto's OpenCode folder; Sotto never reads or copies the sign-ins of the OpenCode you run yourself, and signing out here leaves yours as it is. Each thread moves to the new sign-ins when it next goes idle; if Sotto cannot read OpenCode's model list again afterwards, the tile says the model menu may be out of date. If Sotto cannot tell whether OpenCode saved a key, it reads OpenCode's sign-ins again and says what it found.

OpenCode is checked for updates like the other clients. An npm install of `@opencode/cli` updates through npm, even one under Homebrew's Node, a copy OpenCode 2's install script put in `~/.opencode/bin` updates itself with `opencode upgrade`, and a copy Homebrew, scoop or pacman owns shows that manager's command under **Installation steps**. A copy bun, pnpm, yarn, Volta or asdf installed is that tool's to update, so its Installation steps say to use it; Sotto never runs npm over it, which would only install a second copy. Threads keep working while it installs and move to the new client as each goes idle, and **Update all** includes it. When OpenCode is not installed, or is too old to use, **Installation steps** on its tile says so and opens OpenCode 2's install guide.

### Memory (off for the beta)

Memory remains a separate gated feature. When enabled, open **Memory** and choose **Set working preferences** to start its questionnaire. The store, saved preferences and permission policies keep their existing behavior.

Voice control, the Agents room and thread management controls have been removed. Dictation remains available. **Settings → Agents** keeps new-thread defaults and the default projects directory; saved reasoning accounts still resolve the inherited native model, while dormant reasoning controls are hidden.

### Questions and permissions

If delivery of your answer to Claude Code is uncertain, press **Check again** to check its state, read the thread's activity, or press **Stop** to interrupt the work. Checking sends no answer. While the original write is pending, another answer cannot be sent. If that write finishes, Sotto keeps your original choice and marks it answered. If the write fails outright or the client is gone, **Check again** can reopen a request that is still pending so you can choose and send another answer. Sotto never retries it on its own. An unconfirmed answer from a phone is reported to that phone only; it raises no desktop notice. Sending a question draft keeps its unconfirmed result in the editor.

In split threads, **Ctrl+Shift+M** zooms the focused pane or returns to all panes. If dictation uses that shortcut, use the pane's **Zoom** or **Show all panes** button instead.

Model questions with choices appear above the thread's message bar. Pick an answer or type in **Write my own answer**, then press **Send answer**. The model's suggested option is marked **(recommended)** when it supplies one; nothing is selected for you. Enter adds a line to a custom answer. Escape collapses the question, and reopening it keeps your answer. Prepared choices also survive restarting Sotto. Long forms scroll inside the panel, while your message draft stays separate. In a very short split pane, collapse the question to return to reading the thread. Pending permissions and saved-answer recovery remain reachable by scrolling the pane. Questions without supplied choices keep their text-answer path. The question covers the end of the agent's message, so each web link in that message gets an **Open the link** row between the question and its choices, named by where it goes. A link written into the question itself stays a link in its words. Either opens in your system browser and never picks a choice, even while the choices can't be used. When the question or that message names a prototype page the agent made, an HTML file in the thread's folder (by its path, a `file://` link or its name alone) or a page it serves on `localhost`, the page gets an **Open the prototype** row first, named by its file or address, and a `localhost` address it opens has no **Open the link** row of its own. A file opens in your browser as the file, a `localhost` page at its address, and a page on another computer at that computer's tailnet address. If the file has been moved or deleted since, or the question was answered over an hour ago, the row says so.

Sotto asks Codex, Claude Code and Grok Build to put a question that needs your answer through their own question tool, so it arrives here as a question. Codex's clarification tool is enabled during normal work, and a Codex question can appear while Codex continues independent work. Grok Build takes the request only when a thread is created, so a Grok thread from before this version is not asked. Devin and Muse cannot be asked. Only **Send answer** submits your choice.

A model can still write a question into an ordinary reply and keep working. When the turn finishes, every reply but the last folds under the turn's **Worked for** line, so each sentence in those replies that ends in a question mark is quoted under the line, with who asked it and when. **Show where it asked** opens the line at the reply that asked it. Sotto finds these by their punctuation alone, so it can quote a question that was only an aside, and it does not mark the thread as waiting for you.

When a thread runs on another computer, its saved answer clears after that host confirms receiving the exact submission. Losing the connection or seeing the question disappear does not count as confirmation. An unconfirmed answer stays saved and is never sent again automatically. Checking delivery looks up the original submission, including after a restart while the host still retains its receipt. Update both the desktop and the host for this confirmation support. Older saved answers without a submission identity remain available to copy or discard.

A provider can ask the same question again after its process restarts. Sotto keeps **Check again** available even when the earlier answer was accepted. Check reads the provider's current request; it never sends an answer. If that read permits another answer, the new form starts blank when the earlier text has already been removed. Choose and send the new answer yourself. Remote checking requires the host's `answer-check` support; an older host asks for an update rather than treating cached detail as a fresh check.

If an answer is queued or still being sent, wait for it to finish before checking again. Check keeps saved answers when the question changes, the provider disconnects or permission to answer is removed, and explains what happened. If a queued Send would use a different thread than the one you sent from, Sotto keeps the draft and asks you to review it before sending again.

The composer's **Send** carries its text and images as one action for the selected thread. Checking an earlier answer cannot make that waiting action send the answer again. An ordinary prompt keeps its original binding when a question arrives; sending it does not answer that question. Emptying an old prompt does not make later answers stay bound to that prompt. Text edits keep the images already attached to that draft, including when earlier edits are still saving. After an answer is accepted and its question closes, edits queued behind that Send remain as a prompt; they do not become an answer to another question. If the remote host needs an update to save or send the draft, its text stays only in the current window and is not saved on the host. Update the host before closing the window. Repeated edits show the same update notice once while it remains visible.

When a supported host is busy or disconnected, this computer keeps the latest remote draft, including image removals. Switching threads or reconnecting cannot replace it with an older host copy. Reconnecting saves only the original draft; it never sends an answer. A changed question or unavailable image keeps the draft for review instead of changing what Send would mean. With **Keep local history** on, the local copy also survives quitting. With it off, keep Sotto open until the host has saved your edits. Storage failures say what could not be saved; keep your text and images until they are resolved.

If another device saved newer text on the host, reconnecting leaves that text intact and keeps your laptop edit visible with a notice. Review the host draft before saving again. When Send has an unknown result, its copy stays held for review; restarting cannot make it a new unsent prompt. Exact confirmation clears only the submitted revision, keeping anything typed afterward. Both computers need the updated draft support; an older host shows update guidance and keeps your local copy.

Unreadable local recovery storage does not block connecting to a host. With history on, the original file stays untouched and new edits remain in memory; repair storage before sending a draft that needs a durable recovery record. **Forget** first completes revocation and host removal, then attempts draft cleanup. Canceling Forget or a failed host stop keeps the draft. Failed optional cleanup shows a notice but does not restore the forgotten host or make its old drafts return when you add it again.

Saved answers use version 2 of `request-drafts.json`. Current Sotto reads earlier version 1 files and upgrades them on the next successful save. Older builds cannot read version 2. If an older build reports unreadable answer storage after a downgrade, return to the updated build; keep the file intact so saved answers remain recoverable.

When Codex asks you to open a link, for example to sign in to an app, the question shows the link with **Continue** and **Decline**. Open the link yourself, then press **Continue**.

### Codex's Computer Use

Codex can see and operate the apps on your computer with its Computer Use, as it does in the Codex app. In Sotto it works when two things are true:

- The thread's permissions are **Full access**. Codex's sandbox stops Computer Use in every other mode. Full access means exactly that: Codex can then run anything and change anything, on the whole computer.
- The Codex desktop app is open. Computer Use talks to a helper the Codex app runs.

Ask for it by name ("use Computer Use to…") or with Codex's `$computer-use` skill. Its calls show in the thread's activity as **Computer Use**. A recognised sandbox failure explains how to use Full access. If the connection to the app helper is unavailable, open Codex if it is closed. Keep it open and try again. The app can be open while an older connection no longer works, such as after Codex restarts. If this continues, restart Sotto when your other threads are idle. A connection failure does not tell Sotto whether an earlier action in the same call changed anything.

When the Codex app changes its connection, Sotto refreshes the thread's tools before the next prompt; a refresh failure leaves that prompt unsent so you can try again.

### Terminal mode

In Terminal mode, **Close** releases the terminal's output and keeps its row on **Closed** until Sotto quits. **Reopen** starts the same command with fresh output. **Stop**, a command finishing, or hiding its pane keeps the output readable. Up to 64 terminals can be open at once; Closed rows do not count toward that limit.

An agent starts in **Starting**, then shows **Working**, **Idle**, **Needs you** or **Exited**. Working stays working through silence. Needs you means a current approval or question: answer it in the native terminal, or on a paired iPhone when its blocking hook supports a one-time answer. Its row moves to **Needs you** above all projects, with the project named on the right, and a thin edge marks that pane's header. **Working** comes next, followed by the remaining terminals under their projects and then Closed. Each state has its own shape as well as its name. Keyboard focus stays on the same row action when its state moves it to another group. A collapsed project opens if needed to keep that focused row reachable.

A successful turn completed while its terminal is out of sight says **Just finished**, with the same dot and bold title as threads. Viewing its pane or a foreground terminal detail on a paired iPhone clears the mark. Every visible split pane counts, including one without focus. Zoomed-out panes and panes in a minimised, hidden or tray window do not count; a sidebar row alone does not count. Finishing on screen goes straight to Idle, and leaving afterwards creates no mark. New work, a request or exit clears an old mark. Marks last for this run only. Cancelling or failing a turn earns nothing.

Claude Code's run-only hooks and Codex's completion notification report state locally. Bundled screen rules cover Claude Code 2.1.295, Codex 0.162.0 and 0.162.1, and Grok Build 1.0.50. Codex's empty input prompt is recognised with either its shortcuts hint or its default model and folder status line. Unknown versions fall back to output activity, and the pane's status line says Sotto can't tell when that version needs you. Such a fallback never invents Needs you or Just finished. Plain shells retain Running for recent output and Idle otherwise. Sotto changes no user or project CLI settings, saves no terminal output and sends no approval on your behalf. The Tools terminal and Terminal drawer keep their existing behaviour.

When Claude Code, Codex or Grok Build exits, its agent state becomes **Exited**, its exit code is printed and the terminal stays at an interactive shell in the same folder. Shell input and output do not restart the agent's state; search, links, text sizing and paste still work there. **Restart** runs the provider again with fresh state. **Stop** ends the shell too.

All three terminal surfaces use the same shell: PowerShell 7 when `pwsh.exe` is on PATH, otherwise Windows PowerShell; your `SHELL` on macOS and Linux, with zsh and sh as their respective fallbacks. On macOS, Command+C copies a selection; Ctrl+C interrupts.

Closing a terminal in a new worktree tries to reclaim its folder, keeping its branch and commits. Uncommitted work, ignored files other than installed dependencies, outside links, locked or replaced folders and nested work that needs your answer keep the folder. A folder another thread or open terminal still uses stays too. Reopen restores a reclaimed folder on its retained branch before starting the command. Closing while the worktree is being prepared waits for that preparation before trying to reclaim it.

In Terminal mode, the Terminal drawer and the Tools terminal, **Ctrl+F** (**Cmd+F** on a Mac) opens a search bar at the top right of the focused terminal. Type to highlight matches in its output; Enter and Shift+Enter move forward and back, and Escape or Close search returns focus to the shell. An empty field clears the highlights. A hidden terminal keeps its query and selected match for when it comes back. Resizing or repainting keeps that match when its text still exists. At 1,000 matches, the count shows **1000+**; next and previous still search beyond that count.

Search sits above the output so it cannot cover a match. A short drawer grows while search is open and returns to its saved height on close. Pane navigation, pane zoom and Ctrl+K, which opens the Dictate room's search, keep working from the search controls.

**Ctrl+click** (**Cmd+click** on a Mac) opens an HTTP or HTTPS URL, including a named OSC 8 link, in your browser. From the keyboard, open search, Tab to **Open terminal link** and press Enter. Choose a link with Tab and Enter; its destination appears below its name. Escape closes the list and returns to its button. A click without the modifier keeps the link in the terminal. Other link schemes do not open.

**Ctrl+Plus** (or **Ctrl+=**), **Ctrl+-** and **Ctrl+0** make terminal text larger, smaller and reset it to 13 pixels. On a Mac, use **Cmd+=**, **Cmd+-** and **Cmd+0**. The size, from 8 to 32 pixels, is shared by all terminals and remembered when Sotto restarts. Search and zoom leave a chord to dictation when it is your global dictation shortcut; other keys still go to the shell. Emoji and wide characters, such as Chinese or Japanese text, take two columns, so the text after them lines up.

Pasting an image in any of these terminals saves a PNG under `.sotto/clipboard` in its working folder and types its path as a quoted, literal argument. Later keys and image pastes wait until it finishes. That folder excludes the images from Git. PNGs are limited to 10 MiB; larger images ask for a smaller one. If conversion or saving fails, Sotto says whether later queued input was discarded and asks you to check the command before trying again. Text pastes as text.

### Sending, steering and screenshots

**Unconfirmed** means Sotto cannot tell whether the provider received your prompt. **Check again** looks for confirmation without resending it. For a prompt sent at once, **Continue with a new message**, on the desktop that owns the thread, sets it aside and keeps your next draft. That press sends nothing. The old prompt stays marked **Set aside · Unconfirmed** until the provider confirms it. Sotto keeps its identity so a retry cannot send that revision again, including after a restart. New messages and answers you explicitly send can go. Once the provider confirms a new message in that thread, automatic updates resume under their usual rules; the old prompt is never resent. An unconfirmed or rejected new send keeps automatic updates held. Questions, permissions, queued follow-ups and messages still being sent keep their own recovery rules.

If a permission arrives while you type, the composer keeps focus and your draft. It becomes read-only until you allow or deny the request above. Tab still reaches the other controls.

If a question answer fails, its text comes back to the composer unless you have written a newer draft. The error stays with that thread when you switch away and return, until you edit or retry the answer or close the window.

A message you write while a thread is working waits in the queue above the composer, where you can edit, move or remove it. It joins the conversation once it is sent, never before. While a thread is running, **Steer now** beside a queued message sends that message into the current turn when the provider supports steering, as Codex and Claude Code do; **Steer now** beside the composer does the same for the draft, and Enter still queues. The rest of the queue and any newer composer draft stay in place. An unconfirmed message cannot be steered again; use **Check again** to reconcile its delivery. If Claude is thinking or writing, a steer cuts that step short and Claude answers the steer at once, as its next turn. What it was writing is dropped, and the turn it cut reads **Steered** where a turn you stop reads **Stopped**. If Claude is running a command or another tool, the steer waits for it and joins the same turn, and Stop still ends the command. A steer Claude has not read when you stop the turn still runs, because Claude Code already holds it ([ADR-0065](adr/0065-claude-threads-steer-and-the-iphone-queues-steers-and-compacts.md), [ADR-0075](adr/0075-a-claude-steer-cuts-the-step-claude-is-thinking-or-writing.md)).

When a Claude Code or Codex thread's context holds 100,000 tokens or more and has not changed for over an hour, a line under the composer says so, with **Compact** and **Keep full history**. In Sotto Owl, a Muse thread shows it too once Muse has said how full its context is. Compact asks the provider to fold the thread's context; Keep full history hides the line until the context changes again or Sotto restarts. Grok Build, Devin and, in Sotto Owl, OpenCode cannot compact, so their threads never show it ([ADR-0095](adr/0095-one-provider-profile-holds-each-providers-answers.md)).

Paste a screenshot into a thread's prompt, drag it in, or choose **Attach screenshots**. Codex models that accept images and Claude Code models support screenshots; text-only models keep the control unavailable. Send an image on its own or alongside text, with up to eight images, 10 MB per image and 20 MB total. Grok Build currently cannot receive screenshots through its native client.

A screenshot longer than 2576 pixels on either side is scaled down to that as it is added, in the same format. Its chip says both sizes under the name, such as *Resized from 3840 x 2160 to 2576 x 1449*. That is the most any model Sotto sends screenshots to reads, so the model reads the same size and detail. The smaller copy is in sRGB colour, and a JPEG or WebP is saved again at high quality. A screenshot the smaller copy would not make smaller in bytes, an animated PNG or WebP, any GIF, and an image too large to open safely (past 16384 x 16384 pixels in area) go as you attached them. A browser feedback screenshot is scaled the same way when you add it to a draft. The size limits apply to the files as you attach them. If one of several screenshots cannot be added, the ones before it are, and the composer names it and says it and the ones after it were not attached. In a thread's composer, if you move to another thread while a screenshot is still being added, it goes into the draft you added it to, and that thread's **Send** waits until it has. One that no longer fits that draft, or that draft now answering a question, or the thread's model no longer reading screenshots, leaves it out, and that thread's composer says so until you next change the draft or send it. The coordinator's composer does not do this yet: a screenshot still being added when its thread changes is dropped.

A screenshot is kept once, as a file on the computer that runs the thread (the host, for a thread on a remote host), from the moment you attach it until nothing needs it: not an unsent draft, not a queued message, and not a sent message's preview, which lasts seven days. An hour after that it is removed. With **Keep local history** off, a newly attached screenshot stays in memory instead, so an unsent draft or queued message comes back from a restart without it; a queued message that lost one waits, paused, and says so.

A screenshot in a sent message opens large when you press it. It fills the thread's pane, with the sidebar and other panes still in view, and fits the pane without being enlarged. Zoom with the scroll wheel, the + and − keys or the buttons above it, drag a zoomed image or use the arrow keys to move it, and press 0 to fit it again. When the message holds more than one screenshot, a strip under the image shows them all: press one, or use the Left and Right arrow keys, to move between them; the Up and Down keys and dragging still move a zoomed image. **Copy image** (or Ctrl+C, Command+C on a Mac) puts the image on the clipboard, ready to paste into another app. Escape or **Close image** closes it. Right-click a screenshot in the transcript, or press Shift+F10 with it focused, for **Open image** and **Copy image** without opening it.

If a kept screenshot disappears or is damaged, sending stops and asks you to remove it and attach it again. Attaching the same image restores its copy before you send.

You can create a thread from the Threads page while another thread has a saved draft. The draft stays with its original thread.

Stop can cancel running work even when the provider has not confirmed the last prompt. That prompt stays unconfirmed until the provider reports receiving it; stopping does not resend it or discard its saved identity. A failure to save the queue pause does not block Stop. Your queued messages stay saved; check them before sending another message. A refused Stop does not cancel native work. Other storage failures can still prevent cancellation; Sotto reports the failure.

### History and copying

Long replies are saved in full. If one history event cannot be saved, the thread says part of its history could not be kept; other valid messages still save. Copy any missing text before closing Sotto. Storage failures keep their events for retry.

A thread's messages and retained activity are Sotto's own record, kept in `threads.sqlite` in the app's data folder rather than rebuilt from the provider each time Sotto starts. A thread pane opens on its newest ten turns; press **Show earlier messages** above the oldest one to read further back. A provider session starts when you open or send to a thread, not at connect, and one left idle for thirty minutes is stopped until the next time it is needed. Typing in a thread's composer starts its session too, so the reply to the message you are writing does not wait for it. For a new thread, typing starts the client its first message will use and creates no thread, provider session or worktree: those still begin when you send. When the thread gets a new worktree that starts from origin, typing also fetches the base branch, unless the Git fetch interval is Off. Starting a Claude Code client runs your own Claude Code hooks and MCP servers in the project folder, as opening a thread does, even if you never send the message. A new thread getting its own worktree gets no Claude Code client before you send, since the worktree does not exist yet, and a new Devin thread gets nothing. A client started this way for a message you never send stops after the same thirty minutes. A message sent from the queue or by the coordinator to a thread you were not typing in still starts a stopped session when it is sent. With **Keep local history** off, no message text or activity output is written to disk; turning it off removes the text already written, and what was not kept cannot be recovered. A thread no pane has open shows none of that removed activity from then on, as it shows none of the removed messages. Sotto saves history without waiting for the disk each time. Quitting or a crash of Sotto loses nothing it has saved; a reply's newest words wait up to a quarter of a second before they are saved. A power cut or a crash of the computer can lose what was saved since Sotto last put it on the disk: usually the last few seconds of thread activity, usage and agent records while threads run, and longer when little is being written. What you take out (turning Keep local history off, forgetting a thread, a rewind, clearing usage) waits for the disk, so a power cut cannot bring it back. See [ADR-0016](adr/0016-sotto-owned-history-on-an-event-store.md).

Diagnostic turn records keep event names, IDs, outcomes, fixed failure codes and timings only. They never keep prompt, answer or error text. On upgrade, Sotto removes text from existing turn records before starting the coordinator. If that rewrite cannot finish, Sotto deletes the diagnostic file; if deletion also fails, it asks you to close apps using the file and restart.

Hovering a message or a finished reply shows a copy control in its bottom-left corner. One press copies it as Markdown, so code blocks, lists and tables paste intact somewhere else. Right-click the control, or press Shift+F10 with it focused, to copy as plain text instead. A reply still being written has no copy control, and each code block keeps a copy button of its own.

While a turn runs, what the agent does shows between your message and its reply, a row for each command, edit, tool call or agent. Claude Code's, Grok Build's and Devin's thinking shows the same way, as a **Thinking** row. The row appears as soon as the model starts to think, not once it has finished. Open it to read the thinking as it grows. When the provider keeps its thinking to itself, as Claude Code often does, the row shows without words. Codex shows its reasoning summaries in the same kind of row, titled **Reasoning summary**. Codex reasons through many steps without writing a summary, and those steps show no row. A Claude Code or Grok Build thread read back from the provider's own history shows the same rows, because both keep their thinking. Sotto reads none of a Devin thread's work back from Devin, so its rows come from Sotto's own record of the thread. Thinking is part of the reply: it stays with the thread and is never written to a log.

### Visuals

An agent in a project thread can draw a visual to show how something works: a flow, an architecture, a state machine, a sequence of calls. It does that on its own when a picture helps, and when you ask for one. The visual appears in the thread where the agent drew it, after what it wrote before and before what it writes next, as a card with its title and kind, the diagram, and its explanation: an intro and numbered steps. A visual with steps opens as a walkthrough. Under the diagram, **Step 1 of 4** and a dot for each step sit beside **Back** and **Next**, with the step's words below. The parts of the diagram the step is about are lit and the rest is dimmed: the boxes, arrows and groups of a flowchart, the states of a state diagram, the classes and entities of a class or entity relationship diagram, and the participants and arrows of a sequence diagram. A step that names nothing the diagram has leaves it all lit. **Next** becomes **Start over** on the last step, a dot goes straight to its step, and with the focus anywhere in the walkthrough the Left and Right arrow keys step back and forward. The dots are one Tab stop, on the step you are on, and while the focus is on them it moves with the step. **Read all**, in the card's header, shows the intro and every step as a numbered list instead, with nothing dimmed; it then reads **Step through**, which goes back to the step you were on. The card stays on its step while Sotto is open, when the turn finishes and when you come back to the thread. With reduced motion on, the diagram changes from one step to the next at once instead of fading. A visual with one step shows its words under the diagram, with that part lit, and no Back or Next. A visual without steps shows the diagram and its intro. **Show source** swaps the diagram for its Mermaid source, **Copy source** copies the source, and **Expand** opens the diagram, lit for the step you are on, to zoom and pan; Escape closes it. A diagram that cannot be drawn shows its source and the reason, and the steps stay readable. Visuals stay out of a finished turn's **Worked for** line, so they are in view with the reply.

A visual can also be an interactive page the agent wrote: a chart you can hover, a simulation, an explainer you click through. It sits in the same card, with **Show source** showing the page's HTML. If it has steps, the same walkthrough runs under it, and each step you move to is passed to the page, so it can show the part that step is about; **Read all** tells it every step is showing. The page runs locked down: it cannot load anything from the network or from your computer, cannot see Sotto, and cannot open windows, download files or ask for permissions. The three known gaps are closed (#819): address (DNS) prefetching is off for the app, WebRTC is removed from the page and its frames, and copy and cut commands the page starts write nothing. You can still copy selected text yourself. It takes your theme's colours and follows light and dark. Sotto sizes it to the page, up to 640 pixels tall; a taller page scrolls inside. Press Escape inside the page to go back to the card. A page runs only while its card is near the view, at most three at once, and starts again from the top when it comes back. A card past the three says so, with **Run this page** to run it in place of the page you passed first. A page that fails to load or stops says so, with **Try again**. **Expand** shows it over the window. See [ADR-0060](adr/0060-an-interactive-visual-runs-in-a-sealed-page.md).

Claude Code, Codex, Grok Build, Devin and, in Sotto Owl, Muse can draw visuals; a thread on another host cannot. A visual changes nothing outside its thread, so drawing one asks you nothing. To stop agents drawing them, turn off **Let agents draw visuals in threads** in Settings under Application. Agents then explain in text, and visuals already in threads stay.

A visual is kept with its thread: it is back after a restart, goes when **Keep local history** is turned off or a checkpoint rewinds the turn it was drawn in, and stays when a later turn is rewound. A turn can draw up to 6 visuals and a thread can hold 100. The iPhone app and paired devices show a visual's explanation, with a line saying the visual is in Sotto on your computer. Visuals are drawn on this computer and contact no one. See [ADR-0056](adr/0056-an-agent-can-draw-a-visual-in-its-thread.md).

### Babysitting a pull request

An agent that would otherwise wait on a pull request, polling `gh` or sleeping, can ask Sotto to **babysit** it instead and end its turn. Claude Code, Codex, Grok Build, Devin and Muse threads on this computer have the tool for it: the thread's branch's own pull request, or one the agent names by its link or number, which Sotto links to the thread first if the thread does not know it. Starting asks you nothing and changes nothing on GitHub.

While a thread babysits, the computer that runs it asks GitHub about the pull request every two minutes, also while the window is not in front, and sends the thread a **wake-up** when it needs the agent: a check fails, or fails again after a rerun; the required checks pass; someone other than your own GitHub account comments or reviews; the branch starts to conflict; or the pull request merges or closes. The required checks are every check the base branch's rules require, including one that has not started yet, so the pass comes once they have all passed, and again if a rerun turns a failed one green. A review bot's notice that it could not run, because it hit a usage limit, ran out of credits, its trial ended or the change is too large for it, wakes nobody. A wake-up is one message in Sotto's words, the same for every provider. It names the pull request and each change with its link, and never carries what anyone wrote, so the agent reads comments and reviews itself. It goes through the thread like a prompt: at once when the thread is ready, otherwise after your queued follow-ups, as Sotto's own item in the queue, which later news joins until it goes. You can remove it there, but not edit it, and it never answers a question or permission waiting on you; it waits behind it. The sidebar row says Sotto sent it.

You can babysit the pull request the **Pull request** surface shows: **Babysit pull request** is in its **···** menu, after the merge items, for an open pull request the thread knows, when nothing babysits it yet. While the thread babysits it, a line under the merge checklist, above Merge, says **Babysitting since 2:02 pm**, who started it, you or the thread's agent, and that Sotto sends the thread a wake-up when the pull request needs it, with **Stop**. When babysitting ended on its own, the line says so and why: the pull request merged or closed, ten wake-ups in a row brought only comments, GitHub could not be read, or the setting ended what an agent started. **Dismiss** puts that line away once you have read it; it stays away in this window until babysitting that pull request ends again. Babysit pull request is offered for a thread on this computer, and for a thread on a paired host whose Sotto babysits; a host on an earlier Sotto offers nothing.

While a thread babysits and is at rest, its sidebar row says **Babysitting #74** where it would say Done; Working, Just finished and a request waiting on you outrank it. Above the composer the creature rests in a quiet colour, holding a sign with the pull request's mark, over the pull request's number and title and since when. A watch, background work and a held action all take its place, and it steps aside while a turn runs. A wake-up shows on your side of the thread labelled **Sotto** and **Wake-up**, with every word the provider received, links included; waiting in the follow-up queue it is named the same way, with only Remove. On a paired iPhone a wake-up is an ordinary message. In Sotto Owl the iPhone's pull request sheet has **Babysit pull request** and **Stop babysitting** too. **Let agents babysit pull requests**, in Settings under Application beside the other switches that let agents act on their own, governs the agent's tool only; your own Babysit pull request works either way.

Babysitting ends when the pull request merges or closes, after ten wake-ups in a row bring only comments, or after GitHub refuses the read eight passes in a row, because the sign-in was refused, it no longer shows the pull request, it stopped answering, or its answer made no sense; each of these sends a last wake-up saying so and why. This computer being offline or asleep ends nothing: babysitting picks up again once GitHub can be reached. A stop, by the agent or by you, settling, archiving or forgetting the thread, unlinking the pull request, and turning off **Let agents babysit pull requests** end it without sending anything, and take back what a wake-up still waiting says of that pull request. The setting ends only what agents started, and while it is off, agents are offered no tool and their calls are refused. GitHub limiting your sign-in only pauses babysitting. A thread is not Working while it babysits. See [ADR-0061](adr/0061-a-thread-can-babysit-its-pull-request.md).

### Working indicators

When Claude Code reports an active monitoring task, a small pixel creature walks above the composer with a magnifying glass and the task name. It appears immediately for a confirmed watch, including a brief one, and leaves when the watch ends, the thread disconnects, or your answer is needed. Ordinary commands and unattended background processes do not trigger it. Reduced motion holds a still inspection pose. Codex, Grok Build and Devin stay hidden until their native events can confirm the same lifecycle.

When Claude Code reports that a workflow, subagent, teammate or remote agent started from a thread is still running, the same creature stands by the readout and sends small agents out along the track, one for each task, up to six. The readout names the first task and says **Working**, or *Working · 3 agents* when there are several; hover it to see them all. It stays after the turn ends, for as long as Claude Code says the work is running, and leaves when the work finishes, you stop the thread, it fails or disconnects, or your answer is needed. A subagent the turn is still waiting on shows the hourglass instead. While it shows, you can still change the thread's model, effort or permissions, because Claude Code takes the change without restarting and the agents carry on. Rewinding waits for them to finish, and so does a settings change Claude Code will only make by restarting, such as entering or leaving full access, because a restart would end them. A confirmed monitoring task takes the space first. Reduced motion stands the small agents still in a line.

When one command, tool call or subagent has held a thread for twenty seconds or more, the same creature stands there instead with an hourglass, showing what is running and how long it has run. It reads the thread's own activity rather than any one provider's events, so it is not tied to Claude the way the monitoring creature is; it appears on Claude Code, Codex, Grok Build and Devin threads alike. It says only that time is passing: nothing is being watched on your behalf, and nothing is approved. A confirmed monitoring task or running background work takes the space instead, and a pending question or permission clears it, as before. Reduced motion holds a half-run glass.

When a Claude Code turn ends but a command it sent to the background is still running, the hourglass stays: it names the command by the one-line description Claude gave it, says **Waiting** and counts from when the command started, or *Waiting · 2 commands* when there are several. It leaves when Claude Code says the command has finished. While it shows, Sotto keeps the session running and holds rewinds, and any settings change that needs a restart, as it does for background agents, because either would stop the command. If agents are running too, the working creature takes the space and counts the commands beside them: *Working · 2 agents · 1 command*.

### Sidebar

**Add project**, the folder button at the top of the sidebar, opens a project on any computer Sotto can reach. When a remote host is paired it first asks where the project should live, with nothing chosen for you; with only this computer it goes straight to its folders. The folders are that computer's own, starting in its home folder: open one to go in, use the path above the list or **Backspace** to go back up, and search to narrow the list. Folders holding a Git repository are marked **Git**, and one that is already a project is marked **Project** and opens instead of being added again. **New folder** names a folder that is made only when you press **Use this folder**, so closing the dialog leaves nothing behind. On this computer, **Browse with File Explorer** (**Browse with Finder** on a Mac) opens the system's own folder dialog instead. The project's threads and agents run on the computer you chose, and every Sotto connected to it shows them. Once the project is added, or opened because the folder already was one, a new thread opens in it; from the Terminal sidebar, **New terminal** opens for it instead.

The Threads sidebar keeps each thread’s provider, status and last activity beneath its project. Each row shows its provider as the provider's mark, in the provider's colour; hovering the mark names the provider and the model, and a wide sidebar shows the model's name beside it. A thread whose turn has ended while agents it started are still running in the background stays **Working**, and a command it left running on its own reads **Waiting**; when it ends, Claude Code reports back on its own and the row reads **Working** until that report is in, then says **Done**. A turn Claude Code starts for a message from another session, or to carry on after a usage limit, reads **Working** the same way. A thread that finished while you were not looking at it says **Just finished** until you open it here or on your iPhone. A pane shows its thread only while the Sotto window has the focus, so a thread that finishes in a pane while you are in another app, or with Sotto minimised or in the tray, is marked too, and coming back to the window clears it. The computer that runs the thread keeps the mark, so a restart keeps it, and opening the thread on the phone clears it here. A thread whose last turn failed says **Needs attention** until you open it, here or on your iPhone; then it says **Done**, and its pane still says why the turn failed: on the failed turn's line in the transcript when the provider gave a reason, otherwise in a note above the composer. While any failed thread has not been opened, a line under the search says how many, such as **2 need attention**, with **Dismiss all** beside it, which marks them all as seen without opening each. It never counts or dismisses a thread waiting for your approval or your answer. A failed thread that runs again and fails again says Needs attention again. Settling a thread, its project or the thread that delegated it reads its finish and sees its failure, on every device: it loses Just finished and Needs attention, and restoring it does not bring them back. Every project folder starts closed when Sotto starts, in Settled too; a closed folder still shows its working and waiting marks, a folder you open stays open until you quit, and searching opens every folder with a match. Drag its right edge to resize it; a wider sidebar reveals the branch, model and working copy. Collapse sidebar makes more room for the conversation, and Expand sidebar restores the width you chose. With the divider focused, arrow keys resize it, Home and End choose the limits, and a double-click resets it. Creating a new thread in a settled project returns the folder to the active sidebar with only the new thread; older threads stay in Settled.

Sotto starts as many threads as you, Watcher or your threads ask for. While more than ten threads are working on this computer, a line under the Threads sidebar's search field says so: **11 threads are working.** This computer may slow down or use its battery faster. The count is live, and the line goes once ten or fewer are working. It counts every thread here with a turn running, whoever started it, but not Watcher's own thread, terminals or threads on other computers. It holds nothing back, has nothing to dismiss and is not announced; the collapsed sidebar does not show it.

Standalone Chats, including Talk and Generate prompt, has been removed. With **Keep local history** on, existing `personal-chat/` files and personal records in `request-drafts.json` are preserved without reopening conversations, reconnecting providers or showing old drafts. Turning history off clears Sotto's retained personal transcripts and submitted answers; startup applies the same cleanup when history is already off. Provider-owned history is untouched; nothing is migrated into Threads.

Claude Code, Codex and Grok Build run one process per thread; if one stops, only that thread is affected. A reply it was writing says it may be cut short, and the client starts again there when you send a message.

### Terminal drawer

Tools and drawer shells share a limit of 32 across every thread, including ended shells. Close a terminal to free a slot. After Sotto quits, a shell that was running returns as **Ended when Sotto closed** with no saved output. Reopen starts a fresh shell in its working folder. Output is never written to disk.

If removal or another Git operation holds the folder, a new shell waits for your retry. The error names that operation and says the terminal did not start. Try again when it finishes. In a short drawer, scroll inside it to read the full message. A draft cannot choose a folder while it is being removed; its previous working-copy choice stays.

Each thread pane has a **Terminal drawer** button in its header, beside Tools. It opens a terminal across the bottom third of the pane, under the composer, starting in the project folder. A thread with its own worktree starts there too, so `git` shows the project folder's branch rather than the thread's; change into the worktree to work on the thread's branch. The drawer names the branch only for a thread that shares the project folder. Ctrl+J (Cmd+J on a Mac) opens and hides the drawer of the pane you are in, even from inside the terminal; opening it this way puts you in the terminal, and hiding it puts you back in the composer. Drag the line above the drawer to make it taller or shorter, or focus it and use the arrow keys; double-click it to go back to a third. **+** starts another shell, and each shell has a tab. Hiding the drawer leaves its shells running. Closing a shell's tab ends it, and closing the last one hides the drawer. Hiding the drawer from inside it, with **Hide terminal drawer** or by closing its last shell, puts you back in the composer. These shells are separate from the Terminal in Tools: one never shows the other's. Every pane of a split has its own drawer, and each thread remembers whether its drawer is open and how tall it is. If your dictation shortcut is Ctrl+J, the drawer leaves the shortcut to dictation and you open it with the button. In the Terminal in Tools and in Terminal mode, Ctrl+J still goes to the shell. Escape closes link choices first, then an open search, and otherwise goes to the shell; it never hides the drawer. A thread on a paired host has no drawer: its terminal is on the host machine.

## Tools

Right-click a branch name to copy it. **Copy link** in Pull request and **Copy address** in Settings → Phones copy to your clipboard. Settings → Hosts also copies client update commands, provider sign-in codes and setup fix commands. In a terminal, Ctrl+C copies selected text (Command+C on a Mac). Blank selections copy nothing. If copying fails, the selection stays so you can try again.

Files shows names outside its supported path format as unavailable, including names with Windows-reserved characters. Those entries stay visible but cannot be previewed, copied or revealed.

A small dot above-left of the Tools icon means agents are working in the selected thread, or that a browser request in the current or pinned working copy is waiting for your answer. In Owl the dot also counts the threads the selected thread delegated, and takes the attention colour while one of them waits for your answer. Opening Tools keeps the surface you last used. Inside Tools the surfaces (Browser, Terminal, Files, Changes, PR and Agents) sit on a rail at the panel's outer edge; a dot on one means something is live there: a browser task working or waiting, changed files, or agents working. Away from Changes, its dot follows the check Sotto makes of the working copy after each turn, so a change you make yourself in the terminal shows in Changes at once but lights the dot only after the thread's next turn. **Changes** reads like T3 Code's diff panel: pick **Working tree** (everything uncommitted against the last commit, new files included), **Branch changes** (what the branch adds since it left its base; the base is **Automatic** unless you pick another branch, local or remote), **Latest turn** or any **Turn** (one turn's edits, from the snapshots Sotto keeps of each turn; a turn whose snapshot could not be kept says so). Each changed file is a block with its counts that you can collapse; its name opens it in Files, and **Copy path** copies it. The bar above the files expands or collapses them all, switches between stacked and split views, wraps lines, hides whitespace changes and shows a file tree. Ctrl+D (Command+D on a Mac) opens and closes Changes, or Ctrl+Shift+D when your dictation shortcut is Ctrl+D; a terminal keeps its own Ctrl+D. Changes only reads: commit from the Git action, where the commit dialog lets you leave files out. The one exception is **Checkpoints** on its line, which can revert a whole turn's files and conversation after you confirm. To say something about particular lines, click a line (Shift+click takes more) and press **Comment**, or press a line number to comment on that line alone. Write in the box that opens under the lines (**Add a comment…**; Escape cancels) and press **Comment**. The comment waits on the thread's composer as a chip named for its lines, such as `voice.ts L12 to L15` (old numbers marked "(before)" when every line was removed), and under its lines with **Delete comment** (a comment on lines the comparison on screen does not show is listed after the files). Your next prompt carries each comment with its lines, written out after your message, and the chips clear when it is sent; a refused prompt comes back with them written in. From the keyboard, Tab reaches a file's lines and then the Comment button, the arrow keys move, Shift with an arrow or Space picks, Enter opens the comment and Ctrl+Enter (Command+Enter on a Mac) adds it. Comments are kept until you send them or close the window, and are not saved on their own; once sent they are part of your prompt. **Pin**, **Expand tools panel** and **Close tools panel** sit at the rail's foot. Agents has no Pin control because its roster always belongs to the selected thread, except in Owl, where it lists delegated threads you can open and follows the pin like the other surfaces. The working copy Tools reads is the panel's footer: the project, the branch when it is known, and the kind of folder. After a disconnect or restart, **Last seen working** means current activity has not been confirmed; the clock and dot wait for fresh provider evidence. Finished agents remain in local history independently of the transcript's activity limit. **Keep local history** controls whether this roster and its task text are saved. Turning it off erases saved tasks and results while unfinished agents keep their status and generic task labels. If you turn it back on, erased assignments stay text-free, including later results; fresh assignments are saved again.

Turn checkpoints follow Keep local history. Turning it off or forgetting a thread deletes its saved checkpoints at once, along with file backups that no other checkpoint needs. Turning history off, forgetting a thread and the age and size limits keep unfinished revert records and their file backups until recovery finishes. Completed checkpoints expire after 30 days; checkpoint storage is capped at 500 MB, removing the oldest checkpoints and recovery backups first. Turning history back on starts fresh checkpoints.

Each send adds its checkpoint to a journal, `checkpoints.journal`, beside `checkpoints.json`. Sotto folds the journal into `checkpoints.json` whenever it rewrites that file: at start, in the hourly sweep, when a turn whose checkpoint was taken completes, after a revert or a forgotten thread, and once the journal outgrows the file. The checkpoint limits are 10,000 files, 64 MiB in all and 8 MiB a file. A working copy over them is measured once. Later sends record the same reason without measuring it again. That lasts until its Git state, its ignore files or the files behind the reason change, or Sotto restarts. A folder Git cannot list, because it is not a repository or Git does not trust it, is asked about again on every send. Between two snapshots Sotto reads only the files whose size or times changed, and any file edited in the three seconds before the last one. The checkpoint file records which storage format it uses. If it or the journal is damaged, Sotto keeps readable records and backs up the original beside `checkpoints.json` as `checkpoints.json.corrupt-<id>`. The Checkpoints drawer names the backup file without its folder and says Sotto kept the readable checkpoints. Readable interrupted reverts still require recovery before more work; unreadable records cannot be restored. Backups share the storage limit, expire after 30 days and are erased when Keep local history is turned off or a thread they mention is forgotten.


Open **Tools → Agents** in a thread to see its reported subagents. Agents always follows the selected thread, even when the other tools are pinned to another working copy; in Owl it follows the pin too, so the threads a thread delegated stay a press away (see [Delegation between threads](#delegation-between-threads)). Each row shows the task, the model it ran on, status and elapsed time when known. Open a row for its task and result, including earlier assignments when an agent is reused. Children appear under their reported parent. Codex's newer agent tools send an agent's task to Codex encrypted, so such an agent is named by the short name Codex gave it, such as *review_tests*, and its task is not shown. A message to such an agent after it finished does not make it working again; it works again only when Codex starts it on new work. A Claude Code workflow is one row, named for the workflow, with a strip of one segment per agent (working, finished or failed) and a count such as *4 of 6 finished · 1 failed*. The count at the top of the roster counts a workflow's agents, not the workflow. Press the row to open the **workflow page**: the workflow's task and latest update or result, the models its agents ran on, then each agent as a row of its own with its label, model, status and time. An agent's task and result are the previews Claude Code sends, which end in "…" when it has cut them short. In an Owl build, a finished agent's row also offers **Continue as a thread** ([Continue an agent as its own thread](#continue-an-agent-as-its-own-thread)). **All agents**, or Escape, goes back. The workflow stays working until Claude Code says the run has ended; a run that ends with a failed agent reads **Finished**, and the count says what failed. **Load earlier agents** reads older entries without loading the whole history at once.

In a terminal on Windows, Ctrl+C copies a selection and otherwise interrupts, and Ctrl+V pastes. On a Mac, Ctrl+C always interrupts and Ctrl+V goes to the shell, as in Terminal; Command+C and Command+V copy and paste. Option types characters as it does in Terminal, so layouts that put @, | or [ on Option keep them. Terminal keystrokes and pasted text are sent in order for each terminal. If a write fails, Sotto stops sending the queued remainder and shows a notice. Check the command already on screen before typing again; Sotto does not retry it automatically. Closing, stopping or restarting a terminal discards input still waiting to be sent to that shell.

### Browser

Codex, Claude Code, Grok Build and, in Sotto Owl, Muse can use the browser to inspect and check a page. When the focused thread's agent opens one, a floating **browser player** shows its live page above the composer; drag its title bar to move it, resize it from its corner, or send it into **Tools > Browser** with **Move into Tools**. **Shrink** turns it into a small pill that restores it, and **Hide** leaves the agent working while Tools > Browser stays the way back. Every thread starts with **Let agents use the browser without asking** on in Settings, so opening, navigating, clicking and typing all run without a wait, including on a site where Sotto's browser is signed in; turn the setting off, or press **Stop** on the grant line, and that thread's requests wait for your one-time answer again. A waiting request offers **Allow this thread to use the browser** beside Allow once, which grants that thread the browser until you stop it or Sotto closes. The player shows only the focused thread's own task, never another thread's, and **Show the browser when an agent opens a page** in Settings turns off only its opening on its own, without stopping the work; a waiting request still puts a dot on the Tools icon of the pane showing its thread. While the setting is on, the agent can also see every page in its thread's browser, including pages you open there, and a page stays shared as it moves to another site, such as a sign-in page. **Stop sharing** in the page's tab line makes one page private, and a line under its address says so until you press **Share with agent**. With the setting off or stopped, a page you open from then on must be shared before an agent can observe it, and sharing covers only the site you shared; a page already shared stays shared on the site it is on until it leaves that site or you press **Stop sharing**.

The browser also has a **test iPhone**, for checking a web or Expo-web build as it looks on a phone. Start your app's web server (for Expo, `npx expo start --web`) and ask the agent to test it on the iPhone. It opens the address on the thread's phone, and the phone floats over the thread, framed as an iPhone 15 Pro, while the agent taps, swipes and types. Drag the phone by its label; the button beside the name changes its size, **Show in Tools** opens **Tools > iPhone**, and **Hide** (or Escape) puts it away while the agent keeps working. You can tap and type in it yourself. **Tools > iPhone** loads an address on the phone, reloads or closes it, shares it with the agent, and lists what the agent did there, with any request waiting for your answer. The phone is a page in Sotto's browser at 393 by 852 with iOS Safari's user agent and a touch screen, so the browser's permission setting covers it: a tap counts as a click and a key press as typing. It is not iOS. Native modules, the camera, push and iOS rendering are not tested on it, and it keeps its own storage, apart from your other pages.

For a native app, the thread can use a **cloud iPhone**, an iOS simulator on run.cloud. Add your run.cloud key in **Settings > Cloud iPhone**, where you also set the monthly cap (750 minutes unless you change it), how many idle minutes end a session (minutes with no tap, typing or agent action), and see this month's minutes and recent sessions. Ask the agent to build the app for the simulator and test it on a cloud iPhone: for Xcode, a build made with `-sdk iphonesimulator` and zipped; for Expo, an EAS build with `ios.simulator: true`. A card in the thread names the build, the price and the month's minutes, and waits for **Start cloud iPhone** or **Deny**. Nothing is uploaded until you start it. The phone then floats over the thread showing the simulator, with the session's minutes and **End session**, and **Tools > iPhone** shows the session and its steps. Taps and typing inside a session do not ask. A session ends when the agent finishes, when you end it, after the idle minutes, or at the cap, and Sotto deletes the upload from run.cloud. It is a simulator: push notifications and some hardware are not tested.

Select an element or region, add a comment, and attach it to the thread's editable draft. Finished tasks retain observed steps, screenshots and unchecked cases for the app session. Image attachments depend on the provider's capabilities. A Devin thread has the Sotto browser connection from Devin CLI 3000.11.92. See [browser tasks](agent-control.md#browser-tasks) for details.

## Git, branches and worktrees

The merged-pull-request cleanup rule and Auto-settle merged threads require the merged pull request to match the branch's current commit. A reused branch name or another branch in a fork does not count by name alone.

A Git action, branch restore or checkpoint revert refuses sends from other threads in the same checkout until it finishes. For a Git action, the notice says: **A Git action is running in this folder. Your message was not sent. Your text is kept. Send it again when the action finishes.** Your text is kept: it returns to the composer if you have not typed newer text, otherwise the refused prompt stays available to restore or retry. A refused follow-up stays in the queue as failed; use **Resume queue** after the action finishes.

Git actions are refused while a thread in the folder is working or has pending work. The notice names the thread and its reason: answer a waiting request, retry failed history or archive the thread, or resume or remove failed follow-ups. Loading history and setting up a working copy ask you to try again in a moment. During Automatically pull it says: **Sotto is pulling this folder. Try again in a moment.** Separate worktrees remain independent.

Saving a post-turn checkpoint briefly holds the folder for reading. A Git press during that read says: **Sotto is saving a checkpoint in this folder. Try again in a moment.**

A refused Git press leaves the previous Git result and its **View PR** link available. The refusal appears as the thread's error; progress replaces the previous result only after the new action is admitted.

Clearing **Search refs** restores the full branch list. Enter waits for the current search to finish; changing the search cancels that choice. Press Enter again to choose from the new results.

New threads use the **Project folder** by default, including its uncommitted edits. Threads in that folder share files and branch. A new thread opens straight into its project's working copy; the working copy itself is chosen under the composer once the thread is open. There, for a Git repository, the **branch toolbar** shows **Run on** (the machine the thread runs on), **Workspace** (**Current checkout**, **New worktree** for independent parallel work, or **Previous worktree** to reuse a worktree another thread of the project has), the branch's pull request, and the **branch picker**. Workspace locks after the first message. The workspace menu keeps Current checkout and New worktree at the top, then shows the five worktrees used most recently by this project’s threads. Search worktrees searches all available worktrees in the project by branch or folder, including older ones. The picker searches the repository's branches and switches the folder to the one you pick, creates a tracking branch for a remote one, offers **Create new ref** for a name that does not exist, and for a new worktree records the branch it starts from with a **Start from origin** switch that fetches that branch before the first send. The fetch starts when you type the first message. The send uses it if it fetched the branch in the last two minutes, and asks again if it is older, failed or found no such branch on origin. With the Git fetch interval Off, only the send fetches. When origin does not have that branch, or the project has no origin, the worktree starts from the local branch instead and a notice above the composer says so; only a fetch that fails for another reason, the connection or your credentials, stops setup. Its label reads **Select ref** for a detached HEAD. Picking a branch that another thread's worktree has checked out points a draft at that worktree instead of checking it out twice, and right-click copies a branch name. Git's refusal to switch is shown under the row in Git's words. Uncommitted project edits stay in the project folder. Settings under Application sets the global default; expand **Project defaults** there to override it for a project. Previously saved project choices are restored when Sotto updates. Existing threads keep their folders and unfinished work. The **Git action** at the end of the pane header says what the folder needs next and does it from one press: **Commit**, **Commit & push** or **Commit, push & PR** for a folder with changes, **Push** or **Push & create PR**, **Pull** when the branch is behind, **Sync ref** when it is both ahead and behind, **Create PR** or **View PR**, **Publish repository** for a repository without a remote, and **Initialize Git** for a folder without one; its chevron menu holds Commit, Push, Create PR or View PR, and Publish repository for a repository without a remote. A commit opens **Commit changes** first, where you can leave files out, type a message or leave it for the thread's provider to write, and commit on a new branch; a push or pull request from the default branch asks first. Staged changes in selected files stay as you staged them; files with no staged changes are staged in full. Leaving a rename in includes both names. Files left out keep their staging, and a failed commit restores the staging you started with. Conflicted files must be resolved before committing here; a refused commit leaves the index and working files alone. The action's progress and result show above the composer. The pull request badge on the branch toolbar opens **Pull request** in Tools (its rail tile reads PR): the branch's pull request, or one linked to the thread, as a merge checklist. Five lines say what stands between it and its base: **Checks passing**, **Review approved**, **Up to date** with the base, **No conflicts** and **Ready for review**. Each is done or carries the one press that fixes it: **Open check** for a failing check and **Open review** for a request for changes (both open GitHub; re-running a check is done there), **Update branch** when the branch is behind, **Ready for review** for a draft. A repository that asks for no review, or a branch with no checks, says so on that line, and the line counts as done. A line GitHub would not let Sotto read says so instead: checks it refused, or a base it could not compare. Such a line is not done, and the count beside the heading says it does not block, because GitHub itself decides when you press Merge; a failing or running check it did return still holds the merge back. So does a request for changes, unless the repository asks for no review, in which case it is shown with Open review and does not block. **Merge** is enabled once no line holds it back, in the method beside it (Merge commit, Squash or Rebase), which starts on the **Default merge method** in Settings → Git; until then **Merge when ready** turns on GitHub's auto-merge where the repository allows it. The description and **Linked pull requests** fold below. The **···** menu has Ready for review or Convert to draft, Update with rebase, Merge when ready, Disable auto-merge, Babysit pull request (see [Babysitting a pull request](#babysitting-a-pull-request)), Copy link, Link pull request, Unlink from thread, and Close or Reopen pull request; **Open on GitHub** and **Refresh** sit beside it. Merging, turning on auto-merge, closing and Update with rebase ask first; Update with rebase rewrites the branch on GitHub, so a local copy of it no longer matches until you pull or check it out again. With no pull request yet, the surface offers **Create PR**, the Git action's own, and **Link pull request**, which adds one by URL or `#42`. Typing a pull request URL or `#42` into the branch picker offers **Checkout pull request**: **Local** checks it out in the thread's folder, and **Worktree** gives a thread that has not started a worktree of its own on the pull request's branch. It is GitHub only, through `gh` and your own sign-in, and a thread on a paired host reads and acts on its pull request on that host.

The branch label follows the actual checkout. A shared project folder that changes branches can show a dismissible notice while you draft; sending continues on the current branch. **Restore branch** switches back by your choice, asking first about uncommitted changes. A branch you pick in the branch picker is your own switch, so it shows no notice; the notice is for a checkout moved some other way, by the agent, a terminal or another thread. Worktree-backed threads follow their branch without that notice.

A worktree is a full checkout, and an agent that installs dependencies in it can leave a gigabyte or more behind. You can give the folder back: **Remove worktree** in the thread's working-copy control removes the folder and keeps its branch, and settling a worktree-backed thread asks whether to remove its worktree too. Sending to the thread again puts the folder back on that branch. A folder with uncommitted changes is removed only after you confirm that they are lost. The question lists every ignored item other than installed dependencies. Tick **Delete these N ignored items with the folder** to discard them. If the list changes, nothing is removed; close the question and choose Remove worktree again. Nested repositories and worktrees are listed with a count of uncommitted changes; repositories, including clean or deinitialized submodules, also show commits not on any remote. Automatic rules leave those submodules alone; manual removal deletes their listed history only after the tick. The tick explicitly includes their uncommitted work. Ignored folders have one summary row each; files appearing or disappearing inside a listed folder require a new question. Rewriting an existing cache file is allowed; byte sizes are not compared. Settings under Application also offers rules that remove a clean worktree on their own: after it has been idle for a chosen number of days, when its thread is settled, when its commits are all in the repository's default branch, or when its pull request is merged. Every rule is off unless you turn it on; none of them touches uncommitted work or a folder holding anything but installed dependencies in its ignored files. Removing a folder with a large `node_modules` can take a minute or more on Windows, and it runs until it is done. If it is cut off, because Sotto quit or another program kept a file in the folder open, the working-copy control says Sotto did not finish removing the folder. Choose Refresh to finish removing it, or send to the thread, which finishes it and puts the folder back on its branch. A folder an older version of Sotto left half removed says it was only partly removed instead: Refresh puts its missing files back from Git, and you reinstall its dependencies if it had any. The branch keeps its commits either way.

The rest of the Git choices are in Settings → Git, each in T3 Code's terms and grouped under the moment it acts, and each description says what Sotto will do with the value shown. **Automatically pull** (off) pulls a thread's folder when it is on the default branch, has no changes and is only behind its remote, each time Sotto checks the remote; the pull is fast-forward only, a folder a thread is working or waiting in is left for the next check, and the pull shows only as the branch no longer being behind. **Diff layout** (Stacked or Split), **Hide whitespace changes** (on) and **Default diff file state** (Expanded or Collapsed, Collapsed to start) are where Changes starts. A choice made in Changes holds until one of these settings changes or Sotto restarts. **Default merge method** (**Last selected**, **Merge**, **Squash and merge** or **Rebase and merge**) is the method the merge in the pull request checklist starts on; under Last selected, a method picked beside that Merge is the one it starts on next time. **Auto-settle merged threads** (off) settles a thread at rest once the pull request of the branch it last sent on is merged, checked once an hour; a thread you restore stays restored while Sotto runs, and settling removes no folder unless a worktree rule says so. **Proactive panels** (off) opens Changes on its own when a turn leaves its folder with at least 3 more changed files or 50 more changed lines, when the Tools panel is closed, without moving the cursor from where you were typing; a large turn in a pane you are not in waits until you go to its thread. It counts the folder's changes before and after the turn, so edits you make by hand during the turn count too, and it counts only while the Threads page is open. **Commit and pull request style** chooses how generated commit messages and pull request text are written: **Repository conventions** (the repository's recent commits and its `AGENTS.md`), **Conventional Commits**, or **Custom instructions** in your own words. Conventional Commits and Custom instructions take precedence over the repository's own style, though its recent commits and `AGENTS.md` are still sent. An example under it shows a commit subject and pull request title in the chosen style; with Custom instructions it shows the subject your instructions start from, because Settings asks no model what it would write. **Follow pull request templates** (on) has the thread's own model follow the repository's pull request template when a Git action drafts a pull request: the first template file in GitHub's usual places, or the only one in a `PULL_REQUEST_TEMPLATE` folder. The **Git fetch interval** is there too, under In the background.

What the Git action and generated names send is in [Privacy in detail](#thread-titles-branch-names-and-git).

## Remote hosts

*Development feature.*

Remote navigation belongs to each client. Compose, send and draft controls act on the thread that client picked; they do not change another thread’s draft. Answers still require Can answer.

In **Settings > Hosts**, press **Add host** to add any machine you reach over SSH. The **Device** list opens with the dialog and shows the machines Sotto can see from this computer, read when the dialog opens and sent nowhere: the other devices on your tailnet, from this computer's Tailscale, and the aliases in your SSH configuration (following `Include`) and the hosts in your known hosts. A machine in both shows once with both tags, such as "forge · Linux · Tailscale SSH · SSH configuration"; it is the same machine when the alias's `HostName` is one of the device's tailnet names or addresses, and Sotto connects through the alias so your user and key settings apply. A tailnet device without an alias is reached by its tailnet name, such as `pihole.tail5728ca.ts.net`. **Can connect** lists online computers and your SSH entries; **Can't use now** lists offline devices ("Offline, last seen 8 days ago"), phones ("A phone cannot run the host"), machines already added, SSH entries that go to this computer ("This computer runs its own local host"; its host is **Run the local host** above) and SSH entries for a Git service such as `github.com` ("A Git service, not a computer"), greyed with the reason. An entry goes to this computer when it names one of this computer's addresses or its full tailnet name. A bare name never counts, since two machines can share a default name such as `pop-os`, and neither does loopback, which is how a VM such as Colima is reached. An entry reached through `ProxyJump` or a `ProxyCommand` is not this computer by its address, because the jump decides where the connection goes. A Git service is the host SSH connects to, so an alias named `github.com` that goes to an ordinary computer stays selectable. A device with Tailscale but without Tailscale SSH reads "SSH server not checked", because it may still run its own SSH server. From the keyboard, the arrow keys, Home and End move through the list, typing a name jumps to it, Enter picks, and Escape closes the list before it closes the dialog. The last entry, **Another SSH host…**, swaps the list for an **SSH host** field where you type a host name, an alias or `user@server`, with Username and Port; **Choose from your devices** goes back. Below the list, or the SSH host field, the dialog offers two ways to add the machine: **Have my agent set this up**, for a machine without the host yet, where an agent installs it in a thread you watch (see [Having an agent set up a host](#having-an-agent-set-up-a-host)), and **Add it**, for a machine that already has the host, which is what the rest of this paragraph describes. Username and Port are optional and override your SSH configuration; the host installation and data folders are under **Folders on the host** and start at `~/.local/share/sotto-host` and `~/.sotto`. Pressing **Add host** connects from inside the dialog: it starts or discovers the installed host, forwards its loopback listener and pairs this computer itself over that connection, with no code typed. The list or form then gives way to a line saying what is being added, with **Change** to go back to it, and a checklist of the steps: **Reached forge**, **Approved in Tailscale** (only when Tailscale asks, see [Hosts over Tailscale SSH](#hosts-over-tailscale-ssh)), **Signed in**, **Host installed**, **Host started**, **Paired** and, for **Add it**, **Reach forge over your tailnet** (see below). The title says where it stands: "Connecting to forge", "forge could not be added", "forge is connected" or, when the last step kept it on SSH, "forge is connected over SSH". A failure shows on the step where it happened: what happened, that nothing was saved, and what to do, with the exact command and **Copy** when there is one (the `ssh` command that shows SSH's own words, `ssh-keygen -R` for a changed host key, or the commands that unpack the host archive). Sotto never runs those commands and changes nothing on the host machine itself. **Try again** adds it again. The host is saved only once it answers and pairs, named as the list names the device, or after the host you typed. From then on the dialog offers **Close** rather than **Cancel**, because the host stays added, and once the last step has run it says so and **Done** closes it. Close the dialog before the host is saved and nothing is kept. Add as many hosts as you like. The desktop uses your SSH configuration (aliases, users, ports and identity files) but turns connection sharing, and any `RemoteCommand` or `RequestTTY` it sets, off for its own connections. On Windows it uses Windows' own OpenSSH. Sotto needs OpenSSH 8.4 or later on this computer, and says so when it finds an older one.

Under **This computer**, the **Tailscale** row says whether Tailscale is running here: "Connected as millZach · 5 devices on your tailnet". When Tailscale is stopped or signed out, it offers **Connect to Tailscale**, which runs this computer's `tailscale up` with your existing Tailscale settings; if Tailscale asks you to sign in, its page opens in your browser and the list fills in once you have. While Sotto waits for that sign-in, the button reads **Open sign-in page** and opens the same page again; quitting Sotto stops the wait. When Tailscale is not installed, the row reads "Not installed. Any machine you reach over SSH works without it, and Sotto connects to it over SSH each time.", and **Get Tailscale** opens `tailscale.com/download`. Add host offers the same button when Tailscale is off or missing. Sotto finds the `tailscale` command on the PATH, or where the Windows installer or the macOS app puts it. To see a machine that is not listed, install Tailscale on it and sign in with the same account.

On Windows, connecting an SSH host needs Windows' .NET Framework 4 enabled. Its askpass helper runs only while connecting or answering SSH and is removed when the connection closes.

Sotto asks before trusting a new host key, and for a password or key passphrase when SSH needs one: in the Add host dialog while you add a host, and over whichever page is open when a saved host connects on its own, such as when Sotto starts. A host-key question starts with focus on the key text; Tab reaches **Trust host**. A password or passphrase question starts in its field; Enter runs **Continue**, and Tab reaches it before **Switch it off**. Escape dismisses that question without switching the host off. While SSH is still waiting, the host's row in **Settings > Hosts** says **Waiting for your answer**; press **Answer** to reopen the question. A new SSH question appears again. **Switch it off** there stops connecting to that host until you switch it on. You answer once per connect, although a connection runs several SSH commands. What you type goes only to ssh on this computer, is kept in memory until the connection closes, and is never written down or logged.

Each saved host's row says how it is connected and how it is ("Tailnet · Connected", "SSH forge · Connected", "Reconnecting…", "Switched off", or "Needs attention" with a sentence saying what to do), and has an **On/Off** switch. A host that is on stays connected: Sotto connects to it when it starts, in the background, and a dropped connection reconnects on its own, after 3, 4 and 8 seconds and then every 16 seconds. Its threads stay in the sidebar and in their panes meanwhile, reading Reconnecting, with their drafts, and carry on when it is back. Sotto shows no error for that by itself; something you do on one of its threads meanwhile says the host is disconnected and that nothing was sent. When only you can fix what went wrong, such as a refused sign-in, a changed host key, or a missing Node or host installation, Sotto stops retrying, the host's threads leave the page, and the row says what to do; **Connect again** tries once you have. Switching a host off disconnects it and keeps it off at launch; its row and pairing stay.

A host you add with **Add it** is reached over your tailnet as well. Adding it turns on the host's own Tailscale Serve setting for this computer, on your tailnet only. The form says so before you press **Add host**. Once the host is paired over SSH, the checklist's last step, **Reaching forge over your tailnet…**, turns that setting on and tries the address the host reports for it. You never type that address. When it answers, the step reads **Reached forge over your tailnet** with the address under it, Sotto closes the SSH connection, the dialog says "forge is added and connected over your tailnet", and the row reads "Tailnet · Connected".

When it does not, forge is still added, connected over SSH, and nothing is lost. The step reads **Could not reach forge over your tailnet** and says why: the tailnet did not answer at the address (Sotto tries it again every 5 minutes), forge has not said where your tailnet reaches it yet, Tailscale is not running on forge, the host is too old for it and needs updating, Sotto could not reach the host to turn the setting on, or the host did not turn the setting on, in the host's own words when it gave them. When forge's Tailscale Serve needs your SSH account to be Tailscale's operator, the step shows `sudo tailscale set --operator=$USER` with **Copy**, to run on forge. **Done** keeps what there is. **Try the tailnet again** chooses the tailnet again, which also has forge set up its Serve again, and the step follows it, as it follows a 5-minute check that reaches forge while the dialog is open. **Use SSH only**, there while forge still prefers the tailnet, chooses SSH and closes the dialog.

At the next launch, and after a dropped connection, Sotto connects over your tailnet first and starts no SSH at all. Tailscale SSH then has nothing to ask you to approve. While it does, the row reads "Tailnet · Reconnecting…". If the tailnet does not answer within 5 seconds, Sotto connects over SSH, and the row reads "SSH forge · Reconnecting…". After a dropped tailnet connection it first keeps trying the tailnet alone for a minute, since forge is most often still running and only this computer's network dropped. When you switch a host on, save **Edit connection** or press **Connect**, the row reads "Connecting over your tailnet…" and then, if it must, "Connecting over SSH…". Saving changed SSH settings in **Edit connection** always connects over SSH first, so the settings you saved are the ones it tries.

A host on its SSH connection although you chose the tailnet reads "SSH forge · Connected · Tailnet did not answer", or "Tailnet not ready" when the tailnet is not set up on forge yet. The line under it says why:

- The tailnet did not answer. Sotto tries it again every 5 minutes.
- Tailscale isn't running on the host.
- The host's Tailscale Serve needs `sudo tailscale set --operator=$USER` run there first. Sotto never runs it. Once it has been run, the next 5-minute check has the host set up its Serve again, over the SSH connection it is already on.
- The host hasn't said where your tailnet reaches it yet.

When the tailnet answers again, Sotto moves the host back without its threads leaving the page. A press still running over SSH, such as an update's download, finishes first, and a host being updated stays on SSH until the update ends. A host whose Tailscale is not running when you add it stays on SSH, and its row reads as it always has. So does a host you added before this. Pairing, the first connect and this computer's permission to answer still happen only over SSH. A connection over the tailnet that finds that permission missing leaves it for the next press that signs in over SSH. A press that needs the host's own commands, such as **Stop host**, **Forget**, updating the host and the **Phones…** dialog, signs in over SSH for as long as it runs. Tailscale's approval, if it asks, shows where you pressed.

**Edit connection** begins with **How Sotto connects**: **Over your tailnet, SSH when it can't**, which says the host's tailnet address and when this computer last reached it there, and that choosing it turns on Tailscale Serve on the host, on your tailnet only; and **SSH only**, where every connection signs in over SSH. The arrow keys move between them. Below them, under **SSH (for setup, updates and phones)**, are the SSH host, Username, Port and **Folders on the host**. Saving a new choice sets the host's own Serve setting first, over the host's SSH connection or, for a host on its tailnet connection, over an SSH connection of its own, so Tailscale may ask you to approve it. The host then moves to the connection you chose without its threads leaving the page. A choice that cannot reach the host, or that the host refuses, is put back and the dialog says why; nothing is changed. The setting is the host's, so on a host two computers share, SSH only on one moves the other to SSH too. A host this computer has never connected to has nothing to choose yet. Saving changed SSH settings connects again over SSH, and saving without changing anything does the same, to check them. Sotto checks the SSH settings before it changes anything, so a mistyped host name changes neither the choice nor the settings. When a save changes both, Sotto saves the SSH settings and connects with them first, then makes the choice over that connection; if the choice then fails, the settings stay saved and the dialog says so. While a save signs in over SSH, SSH's question and Tailscale's approval show in the dialog. Closing the dialog while it signs in for the choice stops that sign-in, and the choice does not change.

A host Sotto started keeps running until you stop it. Switching it off, quitting Sotto and a dropped connection all leave it working, so another paired client can keep using it and running turns finish. The row's **More** menu has **Start at boot…** or **Stop starting at boot…** for a connected Linux host (see [Start at boot](#start-at-boot)); **Stop host**, which stops a host Sotto started and switches it off; **Rename**, which changes only the name; **Edit connection**, which chooses how Sotto connects, changes the SSH settings and connects again if the host is on, and shows this computer's client ID on that host; and **Forget**, which revokes this computer's access, removes start at boot, stops a host Sotto started, even one that is switched off or not connected, and removes the saved connection. A host you started yourself is never stopped by Sotto. Forget revokes first, over the host's SSH connection, or, for a host that is switched off or not connected, over an SSH connection of its own that starts nothing on the host. Tailscale's approval, if it asks for one, shows in Forget's dialog, and SSH's question, if it asks one, opens over it. While Forget waits on either, **Keep host** stops it and nothing changes. If SSH cannot reach the host or its host is not running, Forget still removes it from this computer. If the host refuses the revoke, Forget removes it from this computer and leaves its host running. Either way the Hosts page says why, that the host still trusts this computer until it is removed there, and the one line to run on the host, with **Copy command** and **Dismiss**. Each forgotten host keeps its own notice until you dismiss it.

Because a host outlives updates to this computer, the two can run different versions of Sotto. That is fine while they speak the same host protocol ([docs/host-protocol.md](host-protocol.md)). When they do not, the host's row says which side to bring up to date. An older host: "This host is running a different version of Sotto. Nothing on the host was lost. Update it from the Threads page, or put the Sotto 0.1.16 host in its installation folder, press Stop host, then connect again." The version it names is this computer's, and the host archive goes first because connecting starts whatever is installed there: in a folder with a `current` file, unpack it into `versions/0.1.16` and write that version into `current`, and in one without, unpack it into the folder itself (see [Updating a host](#updating-a-host)); after Stop host, switch the host on to connect again. **Stop host** stays on the row for a host Sotto started; a host you started yourself you stop on that machine, and the sentence says so. A newer host: "This host is running a newer version of Sotto than this computer. Nothing on the host was lost. Update Sotto on this computer, then connect again." Whether or not the two speak the same protocol, an older host that Sotto can reach also shows on the Threads page, where Sotto can update it for you; see [Updating a host](#updating-a-host).

When you add a host over SSH, Sotto sets up this desktop's permission to answer requests and choose thread permissions on that host. There is no extra prompt or command to run. An existing desktop pairing without that permission gets it on its next connection. A permission you revoked stays revoked when the desktop reconnects.

A client that cannot pair itself over SSH enters a code shown on the host instead. On the host, from the extracted host folder, request a fresh code:

```sh
node host/index.js --data /path/to/sotto-data --pairing-code
```

The code expires after five minutes. Pairing by code admits this device; permission answers need a separate policy grant from the host's user. Creating or changing a thread to allow actions without asking needs that same grant, including when a new thread inherits the host's permission default or a provider profile. Choosing a mode that asks about everything needs no grant. Use the client ID the client shows, or the one **Edit connection** shows for a desktop connection, to grant, deny or revoke access explicitly:

```sh
node host/index.js --data /path/to/sotto-data --allow-answers CLIENT_UUID
node host/index.js --data /path/to/sotto-data --deny-answers CLIENT_UUID
node host/index.js --data /path/to/sotto-data --revoke-client CLIENT_UUID
```

If the host refuses a permission choice, the chip keeps the mode already in force and the line under it shows the host's reason. A refused choice is not a lost connection. Without an answers grant, **Ask for approval** remains available. To restore permission you previously revoked, run `--allow-answers` on the host for this desktop's client ID, then choose the mode again.

Threads from connected hosts share one sidebar. When a remote host is connected, each project shows a small badge with its host's name, this computer included, and each thread its host. With more than one host listed, **New thread** starts with a row of host buttons: choosing one lists that host's projects, and its folder source, **Folder on forge**, browses that host's folders the way Add project does. A folder you add becomes a project on the host you chose. A thread's host is fixed once it exists, and its composer says where it runs: **Run on** on the branch toolbar for a Git repository, and "Runs on forge" beside the model for any other folder. Threads from different hosts keep their own identities, drafts and actions. So a remote thread opens quickly, its host sends only the end of a long command output and the start of long thinking, tool input or a diff; opening the row brings the rest, which replaces the part in place, and until it arrives the block says so ("Getting earlier lines from forge…") and its Copy waits. If the host cannot send it, the row keeps the part, says nothing was lost and offers **Try again**; if the host is not connected, the rest shows once it reconnects. Turning **Run the local host** off takes effect after **Restart Sotto**, leaves saved data intact and keeps dictation available. For a remote thread, **Files**, **Changes** and **Agents** in Tools look the same as for a local thread, read from the thread's host, and the Tools footer ends with "on forge". What needs the thread on this computer is not there: Files and Changes have no **Show in File Explorer** (**Show in Finder** on a Mac), and Changes offers **Working tree** and **Branch changes** but no turns and no Checkpoints, since turn checkpoints are kept only for threads on this computer. **Copy path** copies the path on the host, written the host's way. Changes reads the host again when the thread's Git status changes, and Agents when its agent counts change; **Refresh files** and **Refresh diff** read at once. A host that runs an older Sotto shows a sentence naming the version instead. Terminal, Browser and iPhone, for a remote thread, explain that they run on the host machine. The branch toolbar, the Git action and the Pull request surface work the same as for a local thread, run by the thread's host. Dictation and paste remain on the desktop computer. Provider credentials and host administration stay on the host. A host connects the providers signed in on its own machine when it starts, and one you disconnect there stays off; see [Headless host](#headless-host). You can see, connect and sign in a host's providers from this computer; see [A host's providers](#a-hosts-providers).

After an interrupted command, reconnect and check its result before choosing to send again; Sotto never automatically repeats it.

### Updating a host

When a connected host runs an older Sotto than this computer, a small pill appears on the Threads page, just left of the window controls (at the top right on a Mac, where the window controls sit at the left, and on Linux, which draws none): "Update for forge", or "Updates for 2 hosts". A newer host is left alone. The pill comes before the thread panes when you move through the page with Tab, and beside two panes, or in a narrow window, it shrinks to its mark so the panes keep their titles. Press it to open a panel with each host that needs an update; Escape or a click outside closes it. Nothing updates until you press **Update forge**, and each host is updated on its own. **Not now** hides that host's update until Sotto next starts.

When none of the host's threads is working, Update starts at once. When some are, the panel asks first: "2 threads on forge are working. Updating restarts forge's host, which stops them." **Update when they finish** waits, reading "forge updates when its threads finish", and starts as soon as none is working. **Stop 2 threads and update** stops those turns the way their Stop button does, so each reads Stopped in its transcript; only the work in progress on them is lost, and drafts and history stay. **Cancel** leaves the host as it is.

An update also waits while the host is updating its clients, so its restart does not cut a client update off. The pill reads "forge waits for its clients", and the panel "forge updates once its client updates finish." The update starts by itself once the last client update ends. **Cancel update** leaves the host as it is. This holds whatever pressed Update: the pill, **Try again**, or Update all. An update that has already started runs on, and only its restart waits for a client update put in after it: the panel reads "forge restarts once its client updates finish."

An update has four steps, which the panel lists as they go, and the pill counts ("Updating forge · 2 of 4"):

1. **Download.** The host downloads this computer's version of the Sotto host for its own system from the releases page on GitHub. When it cannot reach GitHub, this computer downloads it and copies it to the host over SSH.
2. **Check.** Its checksum has to match the release's. A download that does not match is deleted, and nothing is installed.
3. **Install.** The new version is unpacked beside the one running, in the installation folder's `versions` folder. The old version stays until the new one runs.
4. **Restart.** The host saves its workspace and stops, the way Stop host stops it, and the new version starts. The host's threads stay in the sidebar and in their panes for those few seconds, reading Reconnecting, and a draft stays in its composer. Then this computer connects to the new host and the threads carry on. A host that [starts at boot](#start-at-boot) is restarted by its systemd unit, and the panel says so; it still starts at boot after.

**Cancel update** is there while it downloads and checks, and not once it installs. When it is done, the panel says "forge runs Sotto 0.1.24." and goes by itself after a few seconds, unless the pointer is on it or a control in it has focus; **Dismiss** puts it away at once. While an update runs, the host's Disconnect, Stop host, Forget, Edit connection and switch in Settings > Hosts wait for it.

A failed update says what happened and that the host still runs its old version with nothing lost, such as "The download on forge did not match the release's checksum, so Sotto deleted it and installed nothing." If the new version installed but would not start, Sotto starts the old one again and says so. **Try again** starts over, and **Copy commands** or **Show commands** gives you the commands to do it by hand on the host. Sotto never runs those itself.

If an existing `versions/<version>` folder differs from the downloaded release, Sotto preserves it and names the folder in the failure. Use a newer build, or stop the host, keep that folder as a backup and move it aside before trying again. The offered commands only inspect the conflicting folder.

The installation folder keeps the version running and the one before it, each in `versions/<version>`, with a file named `current` naming the one to start. A folder installed before host updates, with `host/index.js` in the folder itself, starts as it always did until its first update, and its files stay where they are. Sotto updates only a host it started. For a host you started yourself, the panel offers the commands instead of Update: unpack the new version, write `current`, stop the host, and connect again from Settings > Hosts, and Sotto starts the new version.

### Start at boot

On Linux, a host Sotto started can also start when its machine starts, so its threads come back after the machine restarts without this computer signing in over SSH. Sotto does it with a systemd user unit, `sotto-host.service`, in the account's systemd folder (`~/.config/systemd/user`), which runs a small script, `boot-start.sh`, kept beside the host in its installation folder. Nothing new is contacted: the commands Sotto runs there, `systemctl --user` and `loginctl`, talk only to that machine. A macOS or Windows host, and a Linux machine without a systemd user manager (WSL without systemd, a container), cannot start at boot. Add host's connected card says why in one sentence, and nothing is offered.

When you add a host, its connected card offers **Start forge's host at boot**. The card's words say what changes on forge, and one press does it. For a host you added before, the row's **More** menu has **Start at boot…**, which opens a modal listing what Sotto found on forge and what changes there. **Start at boot** does it; **Cancel** or Escape changes nothing. Either way it runs over the host's SSH connection.

**Linger comes first.** A user unit runs only while its account is signed in, unless the account lingers. Sotto turns linger on for the account, with `loginctl enable-linger` and without sudo, before it writes anything. If forge wants an administrator for that, nothing on forge changes: the host keeps running, this computer stays connected, and Sotto shows the command to run there, `sudo loginctl enable-linger <user>`, with **Copy**. Run it on forge, then press **Start at boot** again. Sotto never runs sudo.

**One restart.** Once the unit is in place, a host Sotto started stops the way Stop host stops it and starts again under the unit, and this computer connects again. Its threads stay in the sidebar and their panes for those seconds, reading Reconnecting. A host you started yourself keeps running, and the unit takes over the next time forge starts. When a thread on forge is working, Sotto asks first, the way Update does: "1 thread on forge is working. Starting at boot restarts forge's host, which stops it." **Wait until they finish** waits, through a dropped connection too, and the row reads "Starts at boot when its threads finish" if you close the modal. **Stop 1 thread now** stops those turns the way their Stop button does; only the work in progress on them is lost, and drafts and history stay. **Cancel** changes nothing.

**Stop starting at boot…** takes the unit and its script away. Its host restarts once outside the unit, so it keeps running, after the same question when a thread is working. After forge restarts, its host starts again only when this computer connects over SSH. Both items are in the menu while forge is connected; a host you switched off keeps starting at boot until you switch it on and stop it there, or Forget it.

You can close the modal while a change waits or runs, and it carries on. If it then fails, forge's row says what happened, with the command to run there when there is one, until you press **Dismiss**.

**Stop host** stops the unit's host and switches forge off on this computer. Its confirmation says "forge's host stops now and starts again when forge restarts or when you switch it on." **Forget** takes the unit away after it revokes this computer and before it stops the host, so a forgotten host does not come back at the next boot. When Sotto could not take it away, the Hosts page says so with the one line that does, to run on forge.

If linger is turned off on forge later, the next time this computer connects it turns start at boot off: the unit's host stops once, with any turns running on it, and starts again the usual way, and the unit's files stay. **Start at boot…** then shows the linger command again. When the unit will not start the host, the row says so and offers `journalctl --user -u sotto-host -n 50 --no-pager` to run on forge, which shows why.

### A host's providers

A connected host's row says how many of its providers are connected: "SSH forge · Connected · 1 provider". **Show providers** opens a tile for each of Claude Code, Codex, Grok Build and Devin, and in Owl Muse and OpenCode, under the row, and **Hide providers** closes them. A host that is not connected has neither. Each tile says how that provider is on the host, with one button, and every button acts on that host alone; nothing about this computer's providers changes:

- **Connected**, with what it is signed in with and its version ("ChatGPT · 0.155.1"), and **Disconnect**. A provider you disconnect is turned off: the host leaves it off, even when it starts again, until you press **Connect**.
- **Turned off**, with **Connect**.
- **Not signed in**, with its version and **Sign in**. Devin signs in from a terminal on the host, so its tile shows the command to run there, `devin auth login --force-manual-token-flow`, with **Copy**.
- **Not installed** ("Not on forge yet."), **Too old to use** ("0.9.12 on forge. Sotto needs 1.0.5 or later."), or **Can't be started** ("Installed, but forge's host could not find or start it."), with **Have my agent install it**, **Have my agent update it** or **Have my agent fix it** (see [An agent for a host's provider](#an-agent-for-a-hosts-provider)) and **Check again**, which has the host look for it and try it again. To do it yourself, install or update it on the host, then press Check again.

Under the tiles: "forge connects each provider that is signed in when its host starts. A provider you disconnect stays off."

When a host's client is behind the version its maker publishes, its tile says so under the version ("0.158.0 available") and offers **Update** beside Disconnect. Update runs on that host, the way the client was installed there: `MISE_MINIMUM_RELEASE_AGE=0s mise upgrade codex` for a client mise installed, and for Grok Build under mise also its package's install step, so the host starts the new program ("Updating to 1.0.43 · step 2 of 2…"). Your threads keep working, and each moves to the new version when it is idle. Beside **Show providers**, whether the tiles are open or not, a chip counts the host's updates ("3 updates") and opens **Client updates on forge**: a row for each client ("Codex 0.155.1 → 0.158.0"), **Not now** and **Update all**. A host runs one update at a time, so a tile you press while another runs waits ("Updates to 1.0.43 after Codex"), with **Cancel update**, and the chip says "Updating 2 of 3". If one does not update, Update all carries on with the rest, then says so: "Updated Claude Code and Grok Build on forge. Codex did not update." The failed tile keeps one line, such as "The download dropped partway. 0.155.1 is still installed.", with **Try again**; **Details** has the rest, the command to run on the host yourself, with **Copy**, and what the installer printed. An install Sotto will not update itself, such as one through a manager it does not drive or mise it cannot find, shows "By hand" in the popover and the command on its tile. **Done** puts away the updates that finished. When the maker publishes a newer version after an update finished or failed, the tile offers that version in its place. Nothing says a client is up to date, and a host that is not connected shows no updates. A host older than this computer's Sotto shows no updates on its tiles.

**Sign in** opens a small dialog, "Sign in to Claude Code on forge". The provider's own sign-in runs on the host, and you finish it in this computer's browser:

- **Codex and Grok Build** show a code, with **Copy code** and **Open sign-in page**, and say which page they are waiting on: "Waiting for you on auth.openai.com. The code lasts 15 minutes." Enter the code on that page; the host finishes signing in by itself and connects the provider, and the dialog says so.
- **Claude Code** signs in to your Claude subscription. **Open sign-in page** opens claude.com; once you have signed in there, it shows a code. Paste it into **Code from the page** and press **Finish sign-in** (or Enter). Sotto hands the code to Claude Code on the host and keeps nothing. If Claude Code does not accept it, the dialog says "Claude Code did not accept that code, so forge is still not signed in. Open the sign-in page again for a new code." and **Try again** starts a new sign-in.

In Owl, OpenCode's tile shows its version and connection like the others, with what its OpenCode is signed in to ("No model source signed in yet · 2.0.31"). OpenCode connects without a sign-in, so its tile has no **Sign in**: while it is connected, **OpenCode model sources on forge** sits under the tiles, the same Model sources block as on this computer's OpenCode tile in Settings → Providers, and **Add a model source** opens the same dialog, "Add a model source to OpenCode on forge". It signs in the host's own Sotto OpenCode, in its folder on forge, and each thread there moves to the new sign-ins when it next goes idle. A key you paste goes to forge once and is kept only by Sotto's OpenCode there. A browser sign-in opens its page in this computer's browser. One that shows a code to enter on the page, or asks for the code the page shows, works from here; one that would finish by sending your browser back to OpenCode on forge, such as ChatGPT's or DigitalOcean's, cannot reach forge from this computer, so Sotto stops it as it starts and says to choose another way, such as a key; while Settings → Hosts stays open, that way says it finishes on forge itself and cannot be pressed. A sign-in already on forge, such as an AWS profile there, is forge's. If forge stops answering while it signs in or out, forge may have saved the key or ended the sign-in all the same, so Sotto reads forge's model sources again: it says whether the source is signed in there now, or, when it cannot tell, says so and shows the list read again under the tiles. A browser sign-in that is still waiting keeps waiting through a missed answer, and a pasted code forge may not have had is asked for again. Updates and **Update all** work for OpenCode on a host the way they do on this computer. A host older than this computer's Sotto, or one where OpenCode does not run, has no OpenCode tile, and a line under its tiles says to put this computer's version of the host on it.

**Cancel**, or Escape, stops the sign-in on the host, even while the dialog still says it is starting; nothing is signed in. A sign-in that is not finished within 15 minutes is stopped the same way. If the host stops answering while the dialog waits, the dialog says so ("forge stopped answering while Grok Build was signing in. If its tile still says Not signed in, try again.") with **Try again**. Sotto opens only each provider's own sign-in page, and only when you press the button; see "Privacy and cost" in the [README](../README.md#privacy-and-cost). Signing in from here needs the host to be this computer's version of Sotto. See [ADR-0037](adr/0037-a-hosts-providers-are-connected-and-signed-in-from-this-computer.md).

### Having an agent set up a host

**Have my agent set this up** in Add host is for a machine that does not have the host yet, or where a step failed: a missing or wrong Node, no host files, a data folder the account cannot write, an SSH setup that needs a change. It is chosen first when it can run, with a **Model** picker that starts on the model you have the most threads with; the main button then reads **Start setup**. It needs the local host, because the agent works in a thread on this computer and reaches the machine through this computer's SSH setup, and a ready model from Claude Code, Codex or Grok Build. Otherwise it says why and **Add it** is chosen.

Start setup creates a normal thread named "Set up forge" in a project called **Host setup**, which Sotto keeps in its own folder, and sends it a fixed brief: the machine's name, its SSH address and port, the host installation and data folders, this computer's Sotto version, the failed step and its reason when there was one, and the install steps in [Headless host](#headless-host). The brief never includes a key, and tells the agent never to read or copy one. The thread starts in the permission mode that asks before everything, so you answer each command the agent wants to run, in the thread, like any other request. That mode is each provider's strictest, and each keeps exceptions Sotto cannot turn off: Codex runs commands it counts as safe, such as `ls` and `cat`, without asking, Claude Code reads and searches files without asking, and any provider runs what you have allowed in its own settings. Those reads can reach any file your account can on this computer, including `~/.ssh`; the brief tells the agent never to read a key, but Sotto cannot enforce it. A command that changes something, and every `ssh` command to the machine, still asks first unless the provider's own settings allow it. The thread is on the Threads page with its transcript, requests and Stop, and stays there until you archive it.

The thread gets a tool of Sotto's for this one machine, and no other thread gets it. With it the agent can read what Sotto knows about the machine, run Add host's own checks (reach it, sign in, check the installation, start the host), which save and pair nothing, and add the machine. Adding asks you first: the thread shows "Add forge as a host?" with **Add forge** and **Don't add**, and nothing is added until you press Add forge. The add then connects and pairs the way Add it does. If SSH asks a question or Tailscale asks for approval during a check or the add, it shows on its step in the setup's dialog, as it does for Add it. #### An agent for a host's provider

A provider tile that says **Not installed**, **Too old to use** or **Can't be started** offers an agent to do the work on the host: **Have my agent install it**, **Have my agent update it** or **Have my agent fix it**, beside **Check again**. Start creates a normal thread named "Install Devin on forge" in the Host setup project, in the permission mode that asks before everything, as a setup thread does, and sends it a fixed brief: the host's name and SSH address, the provider and the command that starts it, what the host reported (not found; the version found and the version needed; or the host's own sentence), where the host looks for the command (see [Headless host](#headless-host)), and the provider's own install method (Anthropic's installer for Claude Code, npm or OpenAI's installer for Codex, npm or xAI's installer for Grok Build, Cognition's installer for Devin). It tells the agent to update a client with the channel that installed it, to ask before `sudo` or anything outside the account's home folder, never to read or copy a key, a token, a password or a sign-in code, and never to sign the provider in. Every command it runs on the host goes over this computer's SSH and is a request you answer, as in a setup thread.

The thread gets a tool of Sotto's for that one host and that one provider, and no other thread gets it: it reads what Sotto knows about the provider on the host, and runs **Check again**, the host's own look for that provider. It takes no host or provider of its own, so it cannot reach another host or another provider. While it works, the tile reads "Agent is installing it" (updating, fixing) and "In the thread Install Devin on forge on this computer.", with **Show thread**, which opens the thread on the Threads page, and **Stop**, which stops the thread's turn and takes the tool away; whatever it installed stays on the host, and the tile says so. The agent never signs in. Quitting Sotto, archiving the thread or forgetting the host stops the job the way Stop does, and the thread stays as an ordinary thread. ### Hosts over Tailscale SSH

A machine on your tailnet can use Tailscale SSH instead of its own SSH server. The tailnet policy file, which the tailnet's admin edits in the Tailscale admin console, says for each rule in its `ssh` section what happens when someone connects:

- `"action": "accept"` lets the connection in on your tailnet identity alone.
- `"action": "check"` holds the connection until you approve it in a browser, signing in to Tailscale again. An approval lasts for the rule's `checkPeriod` (12 hours unless the rule says otherwise), so connections within that time are let in without asking.

Which one a machine uses is a choice about your tailnet's security, and Sotto leaves it to you. With `check`, Tailscale asks when Sotto connects, and again once the approval has run out. Add host then shows the step **Waiting for your approval in Tailscale**: Tailscale asks you to approve the connection in your browser, and Sotto waits up to 5 minutes and carries on when you approve, with nothing else to press. **Open approval page** opens the page Tailscale gave, in your default browser, only when you press it, and only a `https://login.tailscale.com/` page. **Why Tailscale asks** opens this section. The page's address reaches the dialog and your browser and is never written down or logged. If no approval comes within 5 minutes, Sotto stops connecting and says so, and nothing is saved.

A saved host that reconnects on its own, such as when Sotto starts after the approval has run out, waits the same way: its row reads "Waiting for your approval in Tailscale" and has **Open approval page**. A host you reach over your tailnet needs no approval there, so if nobody approves, Sotto goes on trying the tailnet and reconnects by itself once it answers; for its first minute after a drop it tries only the tailnet and asks SSH nothing, unless you press **Connect**. A host you reach over SSH only has no other way in: if nobody approves it, the row reads "Needs attention" and Sotto stops retrying; **Connect again** asks again. So does an approval nobody gave after you pressed Connect.

With a tailnet connection, Tailscale asks for approval only for a press that changes something on the host, opens its **Phones…** dialog or saves **Edit connection**, because only those sign in over SSH. The approval shows where you pressed: at the top of the Phones dialog, for example, with **Open approval page**.

While Tailscale holds a connection it answers nothing, so SSH's own keepalive would otherwise end it after 30 seconds with "Connection to … port 22 timed out". Sotto's commands allow 5 minutes while they sign in; the port forward, which is the connection a connected host lives on, still gives up after 30 seconds of silence. A rule whose `checkPeriod` is `always` asks for every connection, the port forward and the requests Sotto sends a connected host (Stop host, Forget) included. Sotto shows the forward's request for those 30 seconds and cannot show a request's, which then fails and says to switch the host off and on, so `always` works poorly with Sotto.

It answers questions and permissions on a computer only after you turn on **Can answer** for the iPhone in that computer's **Settings › Phones**, or run `--allow-answers` with its client ID on a host; until then the request says so. Changing Can answer updates a connected iPhone without reconnecting; an older computer may require reconnecting. A reply reads **Sending…** under it, an answer **Sending your answer…**, a stop **Stopping…**, and a queued reply, a steer, a removal or a compaction **Queuing…**, **Steering…**, **Removing…** or **Compacting…**, until the computer answers, and for as long as the computer says it is still carrying it out, which a provider starting up can make slow. Only one the computer couldn't confirm is marked, with **I checked** and **Check again**, and it is never sent again on its own. Only the answer command's own completed receipt with no error and confirmation of its successful outcome shows "Answer sent." If its request stops waiting or its thread disappears without that receipt, Sotto says "That request is no longer waiting." An error from another thread does not decide its delivery. An older computer cannot confirm its own answer outcome; that answer stays unconfirmed while waiting and settles neutrally when its request leaves. Live updates settle marked replies and clear answers that no longer need a response without another check. A working turn still offers Stop while its reply is unconfirmed. Terminal input, file contents and voice are not part of the iPhone app.

If secure storage is locked at launch, unlock the iPhone and return to Sotto. A damaged saved-computers list is rebuilt from readable saved pairings without replacing the damaged index. The recovery message appears only the first time. The app reports how many saved computers need pairing again, once for each unreadable item. If saved unconfirmed actions cannot be read, it asks you to check your threads before sending again; nothing is resent.

## Phones

If **Let phones connect** or **Name on phones** cannot be saved, the control says so beside it. The previous setting stays in use. Retry the switch or press Enter in the name field to save again.

If **Run the local host** cannot be saved, the control says so beside it. The previous setting stays in use. Retry the switch to save again.

*Development feature.*

While Sotto is open on the iPhone, a computer that loses its connection is tried again for about a minute, with waits from about one second up to thirty seconds, and reads **Connecting** meanwhile. A successful liveness check resets the waits; merely connecting does not. If it still can't be reached, or a computer doesn't answer the first time after you open Sotto, it reads **Can’t reach it** and its page says why. Nothing tries it again until you press **Try again** or **Reconnect**: coming back to Sotto and pulling to refresh leave it alone. A computer that doesn't answer is given up after about ten seconds. The thread you are reading stays on screen while it is read again, with **Reconnecting to** its computer over the reply box. Pending reads keep slow thread downloads connected for up to two minutes. A fresh connection refreshes threads and checks unconfirmed actions; it never resends them. Backgrounding stops connection attempts, and returning to Sotto connects every computer that hasn't given up. A changed computer identity or lost pairing still asks you to add the computer again.

Older phones and desktop connections allow two missed keep-alive rounds before closing. Frames sent since the previous check and bytes received before a whole frame arrives keep a round from counting as silent. A delayed reply can therefore arrive after one missed round without losing the connection.

**Settings > Phones** lets Sotto on your iPhone reach the threads this computer runs, over your own tailnet. It needs Tailscale installed and signed in on both, and the local host running (**Settings > Hosts**); with the local host off, the page says so and offers **Go to Hosts**. Each computer shares its own threads and, on a current desktop, its Terminal mode terminals. A phone paired with this computer sees its local work, and not your remote hosts.

Turn on **Let phones connect**. Sotto saves its phone access record before setup; if it cannot, phone access stays stopped and the page asks you to check access to its data folder and try again. Sotto then works down a checklist, and each row says whether its step worked, failed, or is still to come:

1. **Tailscale is running.** Sotto asks the `tailscale` command on this computer (on the PATH, or where the Windows installer or the macOS app puts it) whether Tailscale is signed in, and shows this computer's name on your tailnet. If it is not running, the row says so, nothing is changed, and Sotto looks again every half minute; **Try again** looks now.
2. **Tailscale Serve on port 8443.** Sotto opens a listener on this computer's loopback address only and asks Tailscale Serve to carry HTTPS on port 8443, on your tailnet, to it. It never uses Funnel, and it leaves port 443 to other apps. If another app already has something on 8443, Sotto leaves it alone and uses port 10000 instead, and the row says so. Only when other apps hold both ports does setup stop and say so. If your tailnet has not turned Serve on, the row says so and **Turn on Serve in Tailscale** opens the page Tailscale gave for it.
3. **Address phones use.** The private address, such as `https://laptop.tail1234.ts.net:8443` (or `:10000`), with **Copy address**.

Then pair a phone: on the iPhone, open Sotto, tap **Add computer** ([iPhone app](#iphone-app)), enter this computer's name on your tailnet, then press **Show a pairing code** here and type the code. A code is eight characters, works once and lasts five minutes, with a countdown; **Make a new code** replaces it and **Cancel code** (or Escape) withdraws it. Only one code is live at a time, and it is never written down or logged. When the phone pairs, the code closes and the phone appears under **Paired phones**.

Each paired phone shows its name with control characters removed and spacing cleaned up, when it paired and whether it is connected now. A paired phone reads threads and replies, and may read what Tools shows of a thread: the files in its working folder and their contents, its Git changes, and its agents. It answers questions and permissions only after you turn on its **Can answer** switch, which records your permission for that phone and nothing else (ADR-0004); turning it off takes that back. **Remove** asks first, then unpairs the phone and closes its connection at once. **Name on phones** is what phones list this computer's threads under; left empty, it is this computer's name on your tailnet.

Turning **Let phones connect** off removes Sotto's Serve setting, on 8443 or 10000, and closes the listener, which drops every phone's connection; paired phones stay paired for next time. If removal fails, the page says phones cannot connect while Sotto finishes cleanup. Sotto reserves its loopback port with a listener that closes connections and tries again while it is open; **Try again** retries cleanup too. If the saved cleanup record cannot be read, Sotto keeps cleanup pending. Remove Sotto's setting on port 8443 or 10000 in Tailscale, then press **Try again**. Quitting Sotto asks to remove the Serve setting too, and starting it puts the setting back while phone access is on. It goes back on the port it last used, so paired phones keep their address. If another app has taken that port in the meantime, Sotto uses the other one, and the iPhone finds the computer there. See [ADR-0033](adr/0033-the-desktop-lets-paired-phones-reach-its-threads.md).

### Phones on a host

A host you added in **Settings › Hosts** can serve its own threads to your iPhone too, so a machine with no screen, such as `forge`, never needs one (ADR-0050). Each connected host's row says **Phones off**, **Phones starting…**, **Phones on**, with how many are paired, or **Phones need you**, and **Phones…** opens **Phones on forge**. Escape or **Done** closes it. For a host on its tailnet connection, the dialog reads and changes phone access over an SSH connection of its own. While Tailscale holds that connection for your approval, the dialog says so at its top, with **Open approval page** and **Why Tailscale asks**, and lists **Let phones reach forge**, **Tailscale on forge**, **Tailscale Serve on port 8443** and **Paired phones** as not read yet. The switch shows once the host is read, so it never reads off before Sotto knows. When phone access was read before, the dialog keeps showing it while Tailscale waits, with the switch and the other controls off until you approve. If SSH asks for a password, a passphrase or to trust the host key, the question is asked at the top of the dialog too, with **Stop signing in**.

Turn on **Let phones reach forge**. The host checks the same three steps the Phones page does, on its own machine: **Tailscale on forge**, **Tailscale Serve on port 8443** and **Address phones use**. If another app on the host already uses 8443, the host uses 10000 instead and the step says so, as on this computer. Sotto installs nothing there. If Tailscale is not installed on the host, or not signed in, the first step says so and **Try again** checks again once it is. For its first five minutes after it starts, the host also checks again by itself every half minute, since a host that starts with its machine can come up before Tailscale does. If the tailnet has not turned Serve on, **Turn on Serve in Tailscale** opens Tailscale's page on this computer. On Linux, Tailscale lets an account change Serve only once that account is its operator; the step says so and shows `sudo tailscale set --operator=$USER`, with **Copy command**, to run on the host. Sotto never runs it.

Then **Pair a phone** shows a code from the host, with the same countdown, **Make a new code** and **Cancel code** (or Escape). On the iPhone, **Add computer**, enter the host's name on your tailnet, then the code. The phone appears under **Paired phones**, with **Can answer** and **Remove**, which asks in place before it unpairs the phone. While the dialog is open it reads the host every couple of seconds, so a phone that pairs or connects shows up there.

Phone access is the host's own setting. The host serves phones on a loopback port it remembers, puts Sotto's Serve setting back each time it starts and takes it away when it stops. Phones reach the host only while its host runs, and a host Sotto started runs until you stop it; after the machine restarts, it starts again when this computer connects. While the host is not connected, the dialog shows what it last said and changes nothing. Only phones that paired through phone access are listed; this computer, and any other desktop paired with the host, are not phones. A phone paired earlier with the host's own `--pairing-code` command stays paired but is not listed; use `--allow-answers` and `--revoke-client` for it.

## Headless host

*Development feature.*

The host can run under Node 24 on Windows or Linux without Electron or a display. It owns its providers, worktrees and saved history. Build from a checkout with `npm ci` and `npm run build:host`, then run:

```sh
# From a checkout, after npm run build:host
node out/host/index.js --data /path/to/sotto-data --key-file /path/to/private/sotto-key
```

From an extracted host archive the entry is `host/index.js` instead of `out/host/index.js`; the commands below use that form.

`SOTTO_HOST_DATA` and `SOTTO_HOST_KEY_FILE` provide the same options. The data folder must be explicit. Use a dedicated host folder; desktop credentials use the operating system store and cannot be opened with a host key file.

The key file contains a user-supplied secret of at least 16 characters. Keep it outside the data folder, restrict access to your account, and back it up separately. Sotto encrypts credentials with scrypt and authenticated AES-256-GCM using Node builtins. It never saves the key beside them. A missing or wrong key, or a damaged credential file, stops startup without replacing that file. A key saved in settings by an older version also requires the key file before startup; without it, the host leaves the saved key untouched. If writing it securely fails, the host removes it from settings, stops and asks you to enter it again on the host machine after restoring storage access. You may omit the key file while no credentials have been saved; saving a credential then requires restarting with one. Native provider sign-ins remain with their installed clients.

When it starts, a host connects every provider that is installed and signed in on its machine, whatever it had saved before. A provider that is not installed or not signed in shows its own error, and the host tries it again each time it starts. A provider you disconnect through the host stays off, even after the host restarts, until you connect it again. The host looks for each client the way the desktop does (see [Providers and models](#providers-and-models)), which matters here because the launch script starts it from a non-interactive SSH shell, whose PATH is often only `/usr/local/bin:/usr/bin:/bin`: a client installed through mise is found under mise's `installs/<tool>/latest`, never through mise's shims or a `~/.local/bin` wrapper that runs `mise x`. With no provider connected, creating a project or sending on that host says "No provider is connected on forge. Connect one in Settings > Hosts.", naming the host as you saved it, and adds "Your draft is saved." when you were sending. To connect one there, open the host's providers in **Settings > Hosts** and press **Sign in**, **Connect** or **Check again** on its tile (see [A host's providers](#a-hosts-providers)); or sign the client in on that machine and press **Check again**.

Settings are read from the data folder at startup. That includes the worktree cleanup rules: the host reclaims its own worktrees under them the way the desktop does, and every rule is off unless that folder's settings turn it on. No paired client can set them yet: to turn one on, stop the host, edit the `worktreeCleanup` object in the data folder's `settings.json` (`onSettle`, `unchanged` and `merged` are `true` or `false`; `afterDays` is `null` or 7, 14, 30 or 90 days without activity), and start it again. The merged rule asks GitHub through `gh` and its sign-in on the host machine. The host's own Git settings work the same way: `gitAutoPull` and `autoSettleMergedThreads` (`true` or `false`, both off) are read at startup, and `gitWritingStyle` (`"repository"`, `"conventional"` or `"custom"`), `gitWritingInstructions` and `followPullRequestTemplates` are read for each commit message and pull request the host writes; the desktop's own Settings do not reach a remote host. The headless entry exposes `startHeadlessHost({ dataDirectory, keyFile })` in-process; its `service` is the same `HostService` that the desktop uses. `close()` drains provider and reasoning processes, a worktree cleanup in progress, and durable writes. The command-line host handles SIGINT and SIGTERM and opens an authenticated loopback listener. Add `--port 4319` to keep a fixed port, or omit it to choose an available port. Readiness output names the host and port, and its health check names its Sotto version and the host features it offers. The private `host-listener.json` file includes a local administration credential; do not share it. An embedded host opens a listener only when given a `port` option.

Run `npm run test:host` for the plain-Node lifecycle and `npm run test:socket` for authenticated child-process client journeys. `npm run package:host` creates an archive and checksum with the platform in its filename, then extracts and smoke-tests it. See [host packaging](release/releasing.md). Deployment to a real Linux machine still needs a live check.

A normal stop removes the host's listener descriptor and lock. After a crash or a reboot, the next start finds the old `host-listener.lock`, checks that the process it names is gone or ran before the machine last restarted, and takes the folder over; nothing needs cleaning by hand, and when several hosts start at once, only one takes it. If that process is still running, startup refuses and names it, and a lock file it cannot read is left for you to look at. Only one host may use a data folder at a time. The SSH account needs Node 24. Sotto looks for it on the account's path, then through its login shell, then where nvm, fnm, mise, asdf, Volta and Homebrew keep it, and says which Node it found if none will do. When Sotto starts the host over SSH it passes no key file, so a data folder that already holds saved credentials needs `SOTTO_HOST_KEY_FILE` set for that account. A host that starts at boot does not read the account's shell profile, so Sotto writes that variable's path, never the key, into the script its unit runs.

A remote host keeps its own OpenRouter key, in its encrypted credential file, and never receives the desktop's: a paired client cannot send a credential. Without a key there, OpenRouter-hosted reasoning on that host stays off. Thread titles, branch names and Git drafts need no key on a host: the provider running each thread writes them (ADR-0026).

## Dictation and settings

### The Dictate room

The Dictate room is where your transcripts live. At the top, the dictate bar has the small wave, one sentence saying what Sotto is doing, **Start dictation** (or **Stop** while you talk) and your shortcut. When a dictation finishes, the sentence says where it went, such as **Pasted into Microsoft Outlook.**; a dictation Sotto copied without pasting says **Copied.** Errors, a kept recording and text Sotto could not copy show here as before, with **Try again**, **Discard recording**, **Dismiss** or **Copy text**.

Under the bar is the **Journal**: every saved transcript, grouped by day (Today, Yesterday, then the weekday and date), each day headed with its words and pace. It shows the last seven days, and **Show the 7 days before** adds a week at a time; after a quiet week it starts at the newest day you dictated. Type in **Search transcripts** to find words, and press a chip to see one app's transcripts (All, then the apps you dictated the most words into over the last 30 days; a transcript Sotto could not name an app for is only under All). Ctrl+K (Cmd+K on a Mac) opens the Dictate room on the search from any page, and Escape clears it. Press a row, or Tab to it and press Enter, to open it in place: the full text, how long you talked, its words and pace, its language, model and app, with **Copy** and **Delete**. Escape closes it. **Delete** asks first and removes the transcript and its numbers. **Clear history** is in the **···** menu beside the search, and in Settings under Application; it asks first and removes every transcript and every dictation's numbers.

Beside the Journal is a column of numbers, counted from each dictation's record: today's words and pace against your usual (your pace over the last 90 days), your speed on each of the last 30 days, your streak, the longest in the last year, and a calendar of the last 13 weeks, darker on days with more words, the apps your words went to over the last 30 days, and this month's time saved and busiest hour. Time saved compares how long you talked with how long typing the same words would take at your **Typing speed**, which you set in Settings under Dictation (40 words a minute unless you change it). When the room is narrower than 900 pixels, only today's and this month's numbers show, above the Journal. The numbers keep counting with **Keep local history** off, and they include dictations whose text history retention has trimmed. With history off, a line above the Journal says so; transcripts saved before stay listed until you delete them.

**Reset settings** restores defaults and reopens setup. It keeps your saved OpenRouter key, including when the reset fails, and the speech model you chose.

Press the global shortcut once to start and again to stop and transcribe. The default is `Ctrl+Shift+Space` on Windows and `⌃⇧Space` (the literal Control key) on macOS. `Escape` cancels an active session. The floating widget also starts dictation with a click and can be dragged anywhere.

Settings › Dictation shows the shortcut in the **Press to start and stop** row; Linux’s differences follow below. To change it, press the shortcut: the box reads **Press the new keys…**. Hold the keys you want, then let go to save; **Shortcut saved.** confirms it. `Esc`, **Cancel recording** or clicking away cancels and keeps the old shortcut. While you record, your dictation shortcuts do nothing, and pressing `Esc` in any app cancels the recording without transcribing anything. This shortcut needs a key besides the modifiers, such as Space. If another app already uses the keys, Settings says so and the old shortcut still works.

In Sotto Owl, Settings also offers more shortcuts:

- **Hold to dictate**: hold the keys, speak, then let go. New installs hold **Fn** on a Mac and **Ctrl+Win** on Windows. Pressing another key while you hold only modifiers cancels the dictation. A hold starts a new dictation unless one is already starting, listening or transcribing; while the last one's message still shows, holding starts the next, unless that message offers **Try again** for a recording it kept. If the screen locks or the computer sleeps during a hold, the hold is cancelled.
- **+ Add** after a row's shortcuts records another one, up to four per row. On a Mac it is a menu with **Record keys…** and **Fn on its own**. Extra shortcuts in the press row may use Fn or modifiers alone; the first one may not. A shortcut of modifiers alone must be Fn on its own or two modifiers together.
- The **×** after a shortcut removes it. The press row always keeps one shortcut that works on its own, so its last such shortcut has no ×.

On a Mac, if Fn opens the emoji picker or Apple's dictation, set System Settings › Keyboard › **Press 🌐 key to** to **Do Nothing**.

Hold shortcuts, Fn and shortcuts of modifiers alone need Sotto's key listener. It watches only modifier keys and your shortcuts' keys, and keeps nothing it sees. On a Mac it needs **Input Monitoring**: Settings says so beside the rows, and **Open System Settings** opens that list. Until you allow it, those shortcuts look dimmed and do nothing. After an update, macOS may need you to turn Sotto off and on again in that list. Sotto does not ask for Accessibility for this. Outside Owl, the key listener never runs and the shortcuts Owl saved are kept for later.

On Linux the keys are Hyprland **compositor bindings** that Sotto writes. Set up Sotto’s keys first, in the Omarchy step of first-run setup or the Omarchy block under the rows in Settings › Dictation (see [Sotto’s Omarchy setup](../apps/omarchy/README.md)). Until then the rows say the keys aren’t set up and offer **Set up the keys**; Sotto writes nothing on its own. Keys you bound by hand stay yours: the rows say so and leave them alone. Out of the box you hold F9 to talk and release it to finish, or press Super+Ctrl+X once to start and again to stop. These replace Voxtype’s F9 and Super+Ctrl+X bindings; its engine stays installed.

Change the **Press to start and stop** shortcut by pressing it, as on Windows and macOS; Linux names the keys Super, Ctrl, Alt and Shift. When you let go, Sotto rewrites its snippet, `~/.config/hypr/sotto-bindings.lua`, checks it with `luac`, reloads Hyprland and checks that Hyprland loaded the new keys. If Hyprland reports a new error, Sotto puts the previous keys back and shows Hyprland’s line in the row only, never in a log. Sotto never writes `bindings.lua` for a shortcut change, and the copy of it made at setup stays as it is; the snippet a change replaces is kept as `sotto-bindings.lua.bak`. A press shortcut runs `sotto dictation toggle`; a hold shortcut runs `start` when its keys go down and `stop` when they go up. A key Sotto gives up runs what Omarchy gave it before, Voxtype included.

Every Linux shortcut needs a key besides Super, Ctrl, Alt and Shift, and a hold shortcut is one F key on its own, such as F9: with a modifier, Hyprland can miss the release. Letters are recorded as your keyboard layout types them. Wayland gives Sotto’s window only the keys Hyprland doesn’t keep, so a key Hyprland already binds never reaches the recording: the row says Hyprland already uses it. Sotto also checks Hyprland’s active bindings before it writes and names the one in the way. While you record, Sotto’s own bindings start nothing; pressing one ends the recording and says Sotto already uses those keys. In Sotto Owl, the **Hold to dictate** row, extra shortcuts, **×** and **+ Add** work as above, without a key listener. Outside Owl only the press row shows, and F9 stays held to talk as it is; extra shortcuts Owl saved stay saved but unbound. **Reset settings** leaves Linux’s keys as they are.

A stop without a start does nothing, and another start while listening does nothing. Releasing F9 while the microphone connects cancels when it becomes ready, without keeping or transcribing audio. `Escape` cancels inside Sotto’s window. To cancel from another app, add a compositor binding that runs `sotto dictation cancel`.

An error stays on the widget until you dismiss it with its **×**, press **Dismiss** or `Escape` in Sotto's window, or start another dictation. When transcription fails, Sotto keeps the recording in memory, never on disk: the widget reads **Click to try again**, with what went wrong in its tooltip, and Dictate says what happened and offers **Try again** and **Discard recording**. A long dictation is transcribed in parts, so Try again sends only the parts that did not come back. If Try again fails too, the widget says **Failed again · retry** and Dictate says so; the recording is still kept. Cancelling a Try again while it runs keeps the recording as well. Discarding it, `Escape` in Sotto's window, starting another dictation or closing Sotto lets it go. In other apps `Escape` is theirs: on Windows and macOS Sotto claims that key across every app only while you dictate. On Linux, cancellation outside Sotto uses a compositor binding.

**Show floating widget when idle** keeps the small dictation sliver on screen between sessions. On Linux its shortcut hint names the default compositor binding, F9 to talk, even after you change the keys. While the Omarchy plugin is installed and Sotto publishes a live state file, the shell pill takes its place and the Electron widget stays hidden; Settings then says Sotto’s owl in the bar takes the widget’s place and leaves the switch unavailable. Removing the plugin, or Sotto losing its state file, brings the widget and the switch back. Turning it off hides the idle sliver. Dictation still brings the widget back while it runs.

Settings:

- Dictation: microphone, dictation shortcuts (compositor bindings Sotto writes on Linux), recording limit, local sound cues and **Typing speed**, in words per minute (10 to 150), which the Dictate room counts time saved against. Every dictation is transcribed in parts as you speak, cut at pauses, so a long one finishes almost as soon as you stop. A shortcut saves when you let go of the keys you recorded.

**Test microphone** checks the input selected for dictation. While listening, the button reads **Stop test**. Press it, hide the window, or leave Dictation to close the microphone. When the level rises during the test, Sotto says **Sotto heard you. The microphone is closed.** and offers **Test again**. If the input stays quiet, it says **Sotto did not hear anything. Check that the microphone is not muted.** and still offers **Test again**. Changing the input clears the previous test and stops its meter. Unplugging the microphone during a test closes it and reports the missing input. The reason stays visible when you return to Dictation. A missing selected microphone is reported as missing; Sotto does not silently test the default input instead.
- Transcription: the **Speech model** picker, then the chosen model's name, maker and languages and whether it is ready, loading, downloading or stopped, with **Try again**; and conservative whitespace formatting. The picker lists every speech model Sotto can run on this computer. Sotto's own, on every platform and in this order, are Parakeet Ultra, by Moondream, and Parakeet v3, by NVIDIA, which work out which of their 25 European languages you speak, and Parakeet v2, by NVIDIA, which is English only. Until one is downloaded it is listed under **Download** with its size, for example **Parakeet Ultra, 671 MB**, and choosing it starts the download. On an Apple silicon Mac the picker also lists the Core ML Parakeet models another app keeps in `~/Library/Application Support/FluidAudio/Models`: Parakeet Ultra (Core ML), Parakeet v3 (Core ML) and Parakeet v2 (Core ML). It then leaves out Sotto's download of any model that folder already holds, unless Sotto's copy is already downloaded or is the one chosen. Choosing a model switches dictation to it. Typed letters, and on Windows and Linux the arrow keys, move through the closed picker without choosing, and the line above it says to press Enter; Enter, or a click in the open list, chooses, and Escape goes back. The first time a Core ML model loads, macOS takes about 14 seconds to prepare it; after that it loads in under a second
- Cleanup: optional AI cleanup, a single switch with the OpenRouter API key it needs and a verify button under it, and the personal dictionary cleanup uses to spell your names and terms; and the switches for generated thread titles, commit messages and pull request text. The dictionary holds up to 4,000 characters and saves when you leave its field or Settings. The field explains the limit when you reach it and tells you when a paste is cut to fit. Editing back below the limit clears that message. An older save finishing while you type keeps your newer draft in place; if a save fails, leave the field again to retry. If saving fails after Settings closes, an app notice asks you to return to Cleanup and enter the unsaved edits again.
- Output: mandatory clipboard safety copy, optional automatic paste, paste delay, and success-message duration. The delay and duration save only when their value changes; tabbing through an unchanged field is quiet.
- Appearance: the color scheme (Light, Dark, or match the system), then one theme for light mode and one for dark, chosen in two columns. Sotto ships six themes of its own: Sotto, Hush, Linen, Nocturne, Tropic and Citrine. Sotto is the default, with an almost-black dark room and the app icon's teal (a deeper teal in light mode, so text and links stay readable). You can create a theme, import a T3 Code or VS Code theme file, or install one from Open VSX. Imported files and pasted theme JSON accept comments and trailing commas, as VS Code theme files do. Below the themes: the effort color and contrast. The window, menus, dialogs and the composer are always solid in your theme's colours. Diagrams keep their current colors while you drag a theme color and update after you pause.
- Updates: the version you are running and, on Windows and in Sotto Owl on a Mac, an automatic GitHub release check that is on by default and can be turned off, plus a manual check. On Linux it says Sotto never updates itself and how pacman brings the next version, with nothing to check or turn on
- Application and privacy: launch at login, start minimized, local history, retention, clear history, and reset settings; for threads, the working-copy default and the worktree cleanup rules
- Git: every Git setting, grouped under when it acts: the Commit and pull request style with its example; Follow pull request templates, Default merge method and Auto-settle merged threads; the diff defaults for Changes and Proactive panels; the Git fetch interval and Automatically pull

Turning **Keep local history** off stops saving new dictation transcripts. Older dictation transcripts stay listed in the Dictate room's Journal, even after Sotto restarts, until you delete them or clear history; you can copy them while history is off. **Delete** removes a retained transcript from this computer even while history is off; turning history back on does not restore it.

Sotto keeps a dictation record of every finished dictation, whether history is on or off: when it finished, how long you talked, how many words came out, and the delivered app, the name of the app that had focus when Sotto pasted or copied it, such as Microsoft Outlook or Windows Terminal. It is the app's name only, never a window title or anything read from the app, and reading it asks for no permission. With history on, the transcript carries the app name too. Records hold no text and no audio and stay on this computer in `dictation-records.jsonl`. History retention trims transcripts only; records are kept. **Delete** removes a transcript and its record, and **Clear history** removes every transcript and every record. The first time Sotto starts with this, it makes records from the transcripts already saved, without app names. If thread cleanup fails, Sotto retries while open; another Settings save retries it.

Retired Chats still follows **Keep local history**. With it on, Sotto preserves the old files. With it off, startup and Settings saves clear retained personal messages, activity, generated titles, submitted prompts and answers. Submitted personal answer forms in `request-drafts.json` are removed too. Unsent drafts and recovery identities remain; they are not shown or sent. Abandoned temporary chat-history files are cleared after the original can be read safely, or when it is missing; a missing original or folder is never created. An unreadable or malformed original and its temporary copies are left intact. A failed cleanup shows a notice. Repair the chat file or restore storage access, then save Settings or restart Sotto to retry chat cleanup and failed answer writes. If answer storage could not be read safely or its temporary files could not be cleared at startup, Sotto keeps saved answers unavailable for the session; repair local storage, then restart Sotto to retry. Turning history back on does not restore cleared content. Provider-owned native history is unaffected.

**Clear history** also removes dictation history backups and temporary files left by an interrupted save. Sotto removes those temporary files when it starts, without changing saved history.

Automatic paste is best effort. Windows blocks synthetic input into elevated applications, password fields, protected desktops, and some custom editors. macOS blocks it in secure input fields and until both the Automation and Accessibility grants exist. When paste is rejected, Sotto shows **Copied — paste manually** and leaves the complete text in the clipboard. If a Windows target app is running as administrator, either paste manually or run both apps at the same integrity level.

Sotto finishes each automatic paste before copying or pasting the next transcript. Copying from the Journal while a dictation is waiting to paste waits for that delivery to finish.

If the Windows paste helper does not become ready, the fallback can paste up to about 10 seconds after dictation ends, into whichever window has focus then. Once a paste has been dispatched, if the helper stops or does not confirm in time, Sotto keeps the copied result and does not repeat the paste. Check the target before pasting manually: the text may already have arrived.

## Updates

Automatic update checks are on by default. Shortly after launch and then every few minutes, the installed Windows app, or Sotto Owl on a Mac, asks the GitHub releases page whether a newer version exists, which means GitHub sees an ordinary web request from your computer: IP address, time, and the version you are running. The request also carries a random ID that the updater keeps in Sotto's data folder for this install. No audio, transcripts or settings are sent. Checks keep refreshing an offered release. A failed automatic or manual check keeps the previous download offer and records the error; a successful check replaces it or removes it when no newer release exists. A failed download keeps the offer, names the failed download and offers to retry. When a release is found, the update control at the end of the sidebar foot offers it: one press downloads it, the next press asks before restarting into the installer, and nothing is installed behind your back when you quit. The whole check can be turned off under Settings → Updates, and "Check for Updates…" runs one on demand: in the tray menu on Windows, in the Sotto menu in Sotto Owl on a Mac. Stable's macOS disk image carries no update feed, so on a Mac, download each new stable version from the [releases page](https://github.com/millZach/Sotto-releases/releases/latest).

Client update checks are on by default. When a provider connects, every five minutes while Sotto stays open, and when Sotto finds a new version of itself, Sotto asks the npm registry (registry.npmjs.org) which version that client publishes: Claude Code, Codex and Grok Build. Each host checks its own clients the same way. A newer version found while the card is put away brings it back. The request carries a package name and nothing else, and npm sees an ordinary web request from your computer. Devin is never asked about, because it ships inside the Devin app and updates itself. When a client is behind, a card in the bottom-right corner names the installed and published versions, and one press installs it the way that client installs: `npm install -g` for a package npm owns, under the folder npm installed it in, `mise upgrade <tool>` with `MISE_MINIMUM_RELEASE_AGE=0s` for the upgrade process of a client mise installed (and for Grok Build its package's install step after it), or the client's own updater when neither owns it. An explicit Update or Update all press skips mise's release-age delay on this computer and connected hosts; a check alone installs nothing. Sotto reads mise's local upgrade help to use only the flags that installed mise accepts. The supported release-age flag also skips a per-tool delay; older mise runs without it. Updates run one at a time. Updating a client leaves working threads running: the provider stays connected while the installer runs. Each thread runs its own copy of the client, and each moves to the new version when it is next idle. A thread with nothing to do moves at once, and one that is working finishes its turn on the old version first. A thread waiting for your answer keeps waiting, and nothing is answered for you. If the install fails, nothing changes. If the installer finishes but the client still reports its old version, Sotto says that rather than calling it updated, and if the new version will not start or is one Sotto does not support, it says why and your threads carry on with the version they have. The card then shows one line with Try again, and why under Details. Details hide absolute file paths and keep the error text, including stack locations and download links. Paths beginning with `~/` stay as printed. An install Sotto does not recognise shows the command to run instead of a button. Turn the whole check off with "Check for client updates" in Settings → Providers, which also carries each client's installed version and a Check again press. Check again asks the registry afresh, and also tries a provider that needs attention again, so after you sign a client in it is the press that sees it.

## Install in detail

### Windows

Run the `Sotto Setup <version>.exe` installer and choose the per-user installation folder. The desktop shortcut is optional and unchecked by default; the installer always creates a Start Menu shortcut. Uninstalling removes either shortcut but preserves settings and history by default so an accidental uninstall does not silently destroy local data.

Locally built artifacts are not code-signed because no Windows signing certificate is stored in this repository. Windows may therefore show an **Unknown publisher** or SmartScreen prompt. A public release should be Authenticode-signed by its distributor without changing application behavior.

### macOS

1. **Copy the app to Applications.** Open `Sotto-<version>-arm64.dmg` and drag **Sotto** onto the **Applications** shortcut in the same window, then eject the disk image and launch Sotto from Applications. Do not run Sotto from the mounted image: macOS App Translocation launches downloaded apps from a randomized read-only path, which changes the app location on every launch and makes permission grants and settings unreliable.

2. **Allow the unsigned build to open.** Sotto is ad-hoc signed but has no Apple Developer signature, so the first launch is refused with a message such as *"Sotto" is damaged and can't be opened* or *macOS cannot verify that this app is free from malware*. Open **System Settings → Privacy & Security**, scroll to the Security section, and click **Open Anyway** next to the message about Sotto, then confirm and launch Sotto again. Use this path first: macOS 15 and newer no longer offer the old Control-click → Open bypass for this case. As an alternative, clear the quarantine flag in Terminal and launch normally:

   ```bash
   xattr -dr com.apple.quarantine /Applications/Sotto.app
   ```

3. **Grant the permissions Sotto asks for.** The first dictation asks for microphone access. The first automatic paste asks for Automation ("Sotto wants to control System Events") and needs Sotto enabled in **System Settings → Privacy & Security → Accessibility** as well. Denying or missing either grant never loses a transcript: Sotto shows **Copied — paste manually** and leaves the complete text in the clipboard, and automatic paste starts working as soon as both grants are in place. A notice names the permission that stopped the paste, and its **Open System Settings** button opens that pane. The same button appears next to a blocked microphone test in setup and in Settings. If the first Automation prompt is still open after five seconds, that paste stays on the clipboard and the notice says so; answer the prompt, and the next paste works.

4. **Expect the permission prompts again after every update.** macOS keys these grants to the app's code signature, and an ad-hoc signed build gets a fresh identity on every rebuild. After installing a new version, macOS treats Sotto as a new app and asks for microphone, Automation, and Accessibility again; a stale entry may need to be removed from the list before the new one takes effect. The saved OpenRouter key is in a Keychain item named "Sotto Safe Storage", tied to the same signature, so the first transcription after an update may ask whether Sotto can use it. Choose **Always Allow**. If you deny it, nothing is deleted: Sotto says it could not read the saved OpenRouter key, and quitting and reopening Sotto brings the question back; allowing access then restores the key. This stops once Sotto ships Developer ID-signed builds.

### After install

First-run setup has nine steps in four groups, and the bar at the top says which step you are on. **Start** explains what leaves the computer and lets you choose the look: light, dark or your system's, and one of the six built-in themes, which paints at once. **Dictation** checks that Sotto hears your microphone, chooses a speech model, and shows the active shortcut and a safe paste-test field. **Agents** checks your coding agents and adds a first project. **Elsewhere** adds another computer to run agents on and gets the iPhone beta. Each step's button says what a press does: **Continue** once the step is done, **Skip for now** until then. Every step after the welcome can be skipped and finished later in Settings.

At the microphone step, choose the input you will speak into when there is more than one; Sotto lists them once it has microphone access, and only **Test microphone** opens the microphone. Then say a few words. Once Sotto hears you, the box turns green, says **Sotto heard you. Your microphone works.**, closes the microphone and the step's button reads **Continue**. While it listens, **Stop test** closes it; if it hears nothing for a few seconds it says so, so you can check that the input above is the one you speak into. **Skip for now** moves on without a test, and dictation waits until you run one in Settings, unless the test had already opened the microphone. If the test input ends, setup reports the missing microphone and asks you to retry or skip.

The speech model step, **Choose a speech model**, downloads nothing until you choose. It lists the speech models it found already on this computer first, with **Use** beside each, then **Download** for each of Sotto's models not here yet: Parakeet Ultra, Parakeet v3 and Parakeet v2 (English only), with its size (about 670 MB) beside it. The first in the list is the suggestion, the one strong button. On Windows and Linux, and on a Mac without FluidAudio's models, those three downloads are the choices and Parakeet Ultra is the suggestion; suggesting it downloads nothing until you press it. If you already use Parakeet v3, Sotto keeps it, and you can switch in Settings → Transcription. Once you choose, the step shows the model's status below, and setup can go on while it downloads. You can change the model later in Settings → Transcription.

The coding agents step lists Codex, Claude Code, Grok Build and Devin, and connects every one installed on this computer, as **Connect providers** does. Each row says **Ready**, **Not installed**, **Not signed in**, **Too old to use**, **Can't be started** or, for a client you turned off, **Turned off** with **Connect**, with the client's own sentence about what to do. **Install guide** opens the maker's install page in your browser, and **Check again** tries again the clients that had a problem and connects any you have installed since. Sotto signs in to nothing itself. The first project step adds a folder the way the sidebar's **Add project** does, and needs a connected agent. **Add a computer** opens the same Add host dialog as Settings → Hosts, with **Add it**; **Have my agent set this up** stays in Settings → Hosts, because its thread asks you questions in Threads. The iPhone step's **Get the iPhone beta** opens Apple's TestFlight page in your browser, and **Let phones connect** is the same setting as Settings → Phones, with a pairing code once it is on.

When setup finishes, the Threads page opens with the Threads tour: four short notes on the sidebar, **New thread**, the thread area and Settings. **Next** and **Back** move through it, and **Skip tour** or `Escape` ends it. It runs once, after setup. If access is blocked or no microphone is found, follow the recovery guidance and try again, or skip. The default global shortcut is `Ctrl+Shift+Space` on Windows and `⌃⇧Space` (the literal Control key) on macOS. Press it once to start and again to stop and transcribe. If you press it again while the microphone is connecting, Sotto cancels the session as soon as the microphone is ready. No audio is kept or transcribed. `Escape` cancels an active session.

Each time Sotto starts after setup, the window opens on the starting screen while your coding agents and hosts connect: the Sotto mark, a line saying what Sotto is doing, such as "Connecting Codex" or "Waiting for forge", and a dot for each agent and host that turns the accent colour once it is ready. An agent that is not installed, signed out or turned off, or a host that is switched off or waiting for your answer, does not hold it up. When everything has connected, the app takes the window. If something has not answered after ten seconds, the screen says so and offers **Open Sotto without** it, already focused, so `Enter` opens the app; Sotto keeps trying in the background. If a host's SSH question is open at that moment, it keeps the focus until you answer it. If Sotto has not loaded your threads by then, it says that instead and offers **Open Sotto now** the same way. Once the app has opened, reloading the window or opening it again from the tray goes straight to it. Reloading while the starting screen still shows brings it back, and the ten seconds keep counting from when it first appeared.

Sotto closes to the Windows notification area or the macOS menu bar. Use that menu to show the window, start or stop dictation, toggle automatic paste, or quit completely. Quitting gives cleanup up to ten seconds before Sotto exits. The window and tray stay until cleanup finishes or that time runs out. On macOS a log out, restart or shutdown does not wait for cleanup, so macOS never reports that Sotto held it up. Starting Sotto at login can need your approval on macOS: Settings says so, and Sotto starts at login once you allow it in System Settings → General → Login Items. On macOS the Dock icon and the menu-bar icon stay while Sotto runs, and clicking the Dock icon opens the window again. While Sotto runs, the Dock icon takes the colours of the saved theme the window shows, as the mark inside the window does, and changes once you save a theme or appearance, or when macOS switches between light and dark while Sotto follows the system. A theme you are still editing shows only inside the window. The widget floats over other apps, including full-screen ones; the main window behaves like any other app's window and stays off their full-screen desktops.

## Privacy in detail

The README's [Privacy and cost](../README.md#privacy-and-cost) section names every host Sotto connects to. This section says exactly what each one receives.

### Dictation and cleanup

Dictation is transcribed on this computer by the speech model you choose, and the audio never leaves it. Nothing downloads until you choose one of Sotto's speech models: Parakeet Ultra, by Moondream, which setup suggests because it is Parakeet v3 trained further and more accurate, Parakeet v3, by NVIDIA, or Parakeet v2, by NVIDIA, for English only. An install that already had Parakeet v3 keeps it. Then Sotto downloads that one once, about 670 MB from its own releases on GitHub (`github.com`, which serves the files from `release-assets.githubusercontent.com`), checks every file against the size and checksum it was built with, and resumes a download that stopped where it left off. Until the model is ready, dictation says so and records nothing. It stays loaded while Sotto runs, using about 0.7 GB of memory; switching to another keeps the first one's files, so switching back downloads nothing. Parakeet v3 and Ultra understand 25 European languages and work out which one you speak; none of them transcribes Japanese, Chinese, Korean, Hindi or Arabic. Names that sound like other words come out as they sound; AI cleanup, below, spells them from your dictionary.

On an Apple silicon Mac, Sotto also reads `~/Library/Application Support/FluidAudio/Models`, where apps such as Willow Voice keep FluidAudio's Core ML Parakeet models, and offers the ones it can run. Sotto only reads that folder: it never changes it and never downloads into it, and no new host is contacted. A small helper bundled with the Mac app, `sotto-coreml-asr`, built on FluidAudio, runs the chosen model on this computer and hands the text only to Sotto. Those models belong to the app that put them there. If it deletes or moves them, Sotto says the model's files are no longer on this computer, nothing is lost, and Settings → Transcription offers the models that are left.

Optional AI cleanup is off by default. When you enable it, the finished transcript (never audio) is sent to OpenRouter with the same key, where Anthropic's Claude Haiku 5.5 cleans up punctuation and self-corrections; Inception's Mercury 2 takes over when Haiku fails or runs long. If the network is slow or offline, Sotto delivers the raw transcript instead. Manual thread prompts and babysitting wake-ups go to the thread's own provider under its account and data policy. Saved reasoning credentials remain, but Sotto does not use them to interpret commands or generate follow-ups. Credentials are encrypted using the operating system credential store and are not returned to the UI.

Sotto has no analytics or crash upload. Dictation audio is never persisted; after a failed transcription it stays in memory until you try again, discard it, start another dictation or close Sotto. Transcript history is local, optional, bounded, searchable, and clearable. Dictation records, the numbers and app name of each dictation, are kept on this computer even with history off and are cleared with it. Two small diagnostic files in Sotto's data folder help explain a lost dictation: `polish-diagnostics.jsonl` records word counts around AI cleanup, and `transcription-diagnostics.jsonl` records why a part of a dictation was not transcribed (the speech model was not ready, it failed, or the audio was not usable), with the part's length and the time taken. They hold no words, audio or keys, each starts over past 256 KB with one older copy kept, and neither leaves this computer.

While **Keep local history** is on, the desktop keeps a startup copy of your threads in its window storage, so Threads can show them before providers reconnect. The copy is not encrypted. For each thread it holds your last message and the last reply, up to 2,000 characters each, and any request waiting for your answer, including a permission request's text and the command it would run. Whole conversations and attached images are not in it. Until fresh state arrives the copy is shown as out of date, offers nothing that needs a provider, and answers no request. Turning history off deletes the copy and stops new ones.

Spellcheck stays enabled, but Sotto blocks dictionary downloads in its windows and browser. The OS spellchecker remains available on Windows and macOS. A language that needs a downloaded dictionary may have no spelling suggestions.

### Thread titles, branch names and Git

Thread titles, new worktree branch names, commit message drafts and pull request drafts are written by the thread's own provider: Claude Code, Codex, Grok Build or, in Owl, OpenCode, on your account and the thread's model, in a separate one-off request that never enters the thread's own conversation. None of these four goes to OpenRouter or anywhere the thread was not already going. With Generated thread titles and Keep local history on, the provider is sent the thread's first message and first reply, each capped at 2,000 characters, to name the thread, and a new worktree's first prompt alone, capped at 2,000 characters, to name its temporary branch; no branch request is made for a shared project folder or an existing worktree. The Git action that commits from one press sends, when the commit dialog's message is left empty, the staged diff, the names of the staged files, the repository's last twenty commit subjects and its `AGENTS.md`, so the message follows the house style, and the pull request text is written from the branch's commit subjects, its file list, a capped diff and the repository's own pull request template where Sotto finds one; with **Follow pull request templates** off the template is not read or sent. With the **Commit and pull request style** set to **Custom instructions**, what you wrote there is sent with each of those two requests as well. When the provider writes nothing, the action commits under the subject "Update project files" rather than waiting. The action stages what it commits itself, everything or the files you chose, so anything staged by hand beforehand is staged again from the working tree; and it fetches first, under the same 15-second rule as a refresh, unless the Git fetch interval is Off. A push goes to the remote `branch.<name>.pushRemote` or `remote.pushDefault` names, else to the branch's upstream when it tracks a branch of the same name, else to `origin`, or the first remote when there is no origin, under the branch's own name. A pull comes from the upstream. Both use Git's existing authentication; after a push from a branch other than the default one, Sotto asks GitHub through `gh` whether it already has a pull request, and Create PR and Publish repository go to GitHub through `gh` on your own sign-in. These drafting requests count against the provider's usage limits like any other, at the lowest effort the thread's model offers. Muse side drafting is unavailable because MSP cannot disable all tools independently of its policy. Muse and Devin threads keep the opening words of their first message as their name and commit under the stand-in subject when the message is left empty, because Muse cannot safely draft without tools and Devin cannot answer once without keeping a session of its own. OpenCode drafts through its one-off generation, which keeps no session and offers no tools; a model source that refuses it, as OpenCode Zen's free models do, leaves the same opening words, temporary branch and stand-in subject. A failed or disconnected provider leaves the opening words of the first message as the name, the temporary branch or the stand-in subject, and the turn continues. Turn off Generated thread titles to stop both kinds of automatic naming. See [ADR-0026](adr/0026-short-writing-runs-on-the-threads-own-provider.md). Turning on **Start from origin** in the branch picker for a new worktree fetches that branch from the project's configured Git origin before setup. The fetch starts when you type the first message, even one you never send, except with the **Git fetch interval** Off, when only the send fetches; Git contacts that remote using its existing authentication. The worktree cleanup rule "when its pull request is merged" asks GitHub once an hour, through the `gh` command and its own sign-in, whether each candidate branch's pull request is merged, and skips the question until the next hour while GitHub is limiting your sign-in, as described below; the other rules read only the local repository and contact nothing. All of them are off until you turn one on. **Auto-settle merged threads**, also off until you turn it on, asks the same question on the same hourly schedule for the branch each thread last sent on, and asks once per branch when both want the answer. **Automatically pull**, off until you turn it on, runs `git pull --ff-only` against the branch's own upstream over Git's existing authentication, only for a folder on the default branch with no changes that is behind, and only when Sotto has just read the remote as described below. While the Sotto window is in front, Sotto also fetches each open thread's project from its Git origin at the **Git fetch interval** in Settings (every 30 seconds unless you change it), and when you refresh a thread's working copy, no more than once every 15 seconds, so the thread's branch knows whether it is ahead of or behind the remote; the fetch uses Git's existing authentication, never answers a prompt, and sends nothing but the fetch itself. With the interval Off, Sotto fetches nothing on its own: not on a refresh, not before a Git action and not while you type. Only a new worktree's Start from origin still fetches, on its first send. Ahead and behind compare with the remote as it was last fetched. On the same schedule, and whenever you refresh a thread's working copy, Sotto asks GitHub through `gh` on your own sign-in whether the branch has a pull request, for branches that have been pushed, and keeps the answer a while: a minute for an open pull request, five minutes when there is none, fifteen minutes for a merged or closed one or until the branch moves. The branches of one repository are asked about together, in one request. A branch is asked about when its repository is on github.com or on another GitHub host `gh` is signed in to, such as a company's GitHub Enterprise server; to tell, Sotto reads which host an SSH remote's name stands for from your SSH configuration, which connects to nothing, and, only for a remote whose name does not say GitHub, asks `gh auth status` which hosts you are signed in to, at most every ten minutes, reading the host names alone. GitHub limits how much a sign-in may ask, and your own agents' `gh` commands draw on the same rate limit, so Sotto reads what is left with every answer: on the schedule it stops asking while less than a tenth is left, and for a while after GitHub says it is asking too much, keeping the last answers until then. The same holds when the window re-reads a thread on its own, as it does when you come back to it or start typing. Pressing Refresh, a Git action and the Pull request surface still ask. The Pull request surface in Tools asks GitHub through the same `gh` only when you open it, press Refresh, or press one of its actions, in one request each time: it reads the pull request's description, checks, review decision and who approved it or asked for changes, mergeability, the merge methods the repository allows and how far the branch is behind its base, and it merges, marks ready or draft, closes, reopens, updates the branch or turns auto-merge on or off only on your press, the merge, auto-merge, closing and a rebase update after a confirmation. When GitHub has stopped answering your sign-in for a while, the surface says so and when to refresh, and keeps showing what it last read; the branch's pull request beside its name keeps its last answer and does not say so itself. Link pull request and Checkout pull request read the pull request you name through `gh` too (a checkout takes only a pull request of the project's own origin repository), and a Worktree checkout fetches its branch from the project's origin with Git's existing authentication. See [ADR-0027](adr/0027-git-the-way-t3-code-does-it.md). A thread that babysits a pull request has its host ask GitHub about it through the same `gh` every two minutes, whether or not a window is in front, in one request for up to 25 pull requests of a repository, and asks for a pull request's checks, with the checks its base branch requires, and its comments and reviews only when they moved. For a comment or review a bot account left, it asks the words, once, to tell a notice that the bot could not run; they stay on that computer and go to nobody. Those reads stop while less than a tenth of the rate limit is left, like the others. A wake-up sends the thread's provider the pull request's number, title and link, the names and links of failed checks, the base branch a conflict is with, and the logins of who commented or reviewed, with links, never what they wrote. Sotto's log keeps only that babysitting started, ended and why, or that a read failed, was rate-limited or could not reach GitHub. See [ADR-0061](adr/0061-a-thread-can-babysit-its-pull-request.md).

### Browser

The Tools browser contacts the HTTP(S) pages you open, including local development servers, and the subresources those pages request. Browser agents use Sotto's own pages through thread-scoped tools; providers that require MCP connect to an authenticated endpoint on `127.0.0.1` on this computer. When you authorize browser work or send selected page context, its screenshots and relevant page data go to that thread's provider under the provider's data policy. Sotto keeps browser-task evidence and page grants in memory, never in operational logs. Explicitly attached/sent material follows the existing draft and history controls. See [the browser decision](adr/0020-sotto-owned-browser-tasks.md).

### Remote hosts

When you connect a remote host, Sotto sends your thread reads, prompts and explicit request answers to the host you configured. To list the devices Add host offers, Sotto runs the `tailscale` command on this computer with fixed arguments and reads what it prints; that command talks to the local Tailscale service, so no new host is contacted, and the device names it returns are neither logged nor sent anywhere. **Connect to Tailscale** runs `tailscale up` and opens only a `login.tailscale.com` sign-in page, and only after you press it. When Tailscale SSH asks you to approve a connection, Sotto opens its `login.tailscale.com` approval page in your browser only when you press **Open approval page**, and keeps the page's address in memory only while the connection waits. When you sign in a host's provider from its tile, the host runs the provider's own sign-in and sends this computer the page's address and the code it asks for, and the code you paste back goes to the host; Sotto opens only the provider's own page (`auth.openai.com`, `accounts.x.ai`, `claude.com` or `claude.ai`), only when you press **Open sign-in page**, and none of it is logged or written down on either computer. When you browse a host's folders to add a project, the host sends back the names and paths of the folders you open, and nothing about any file; they are not logged on either computer. When you open Files, Changes or Agents for a thread on a host, the host sends this computer what that surface shows: the folder listings and file previews you open in that thread's working copy, its Git changes and diffs, and its agents. They are shown and not kept, and not logged on either computer. When you update a host, the host downloads the Sotto host and its checksum from the releases page on GitHub (`github.com`, served from `release-assets.githubusercontent.com`); when it cannot, this computer downloads the same files from the same places and copies them over your SSH connection. Nothing about you, the host or its threads is sent with them. The host socket listens only on its own loopback address. The desktop reaches it through your SSH connection, or, for a host you added with **Add it**, over your tailnet through the host's own Tailscale Serve setting, which carries the host's second loopback listener over HTTPS on your tailnet only and never through Funnel. That listener has no administrative routes, and this computer's pairing token is what it accepts there. Pairing identifies each client and can be revoked. Provider credentials stay on the host, and pairing does not approve permission requests. No public listener, relay account, analytics or new provider service is enabled by connecting a client.

### Phones

With phone access on, your threads, and the replies, photos and answers you send from a phone, travel between this computer and the iPhones you paired, over your tailnet through Tailscale Serve. A paired phone may also ask for a thread's files, Git changes and agents, as a paired computer does. A photo from a phone is kept here as a staged image, like a screenshot, and goes to the thread's provider with the reply. Sotto's listener binds this computer's loopback address only; Serve carries tailnet traffic to it, and Funnel, which would reach the internet, is never used. Sotto runs the `tailscale` command with fixed arguments and reads what it prints; that command talks to the local Tailscale service, so no new host is contacted. Pairing codes and tokens are never logged, and the listener has no administrative routes: codes, answers and removals are handled inside Sotto, from the Phones page.

A host's phone access works the same way on the host's machine: the host runs `tailscale` there, its tailnet listener binds that machine's loopback address, and your threads on that host travel to your paired phones over your tailnet. The same Tailscale Serve setting carries this computer's tailnet connection to the host, which Add host turns on with your consent. It has no administrative routes either. This computer changes it through the host's administrative routes on the port SSH forwards. The launch hands back the host's administrative token over SSH, and this computer keeps it in memory for that connection only, never on disk or in a log.

### Themes

Omarchy’s `sotto.dictation` plugin lives at `$HOME/.config/omarchy/plugins/sotto.dictation/`, even when `XDG_CONFIG_HOME` points elsewhere. Windows and macOS keep their existing widget and placement defaults.

Main publishes `$XDG_RUNTIME_DIR/sotto/dictation-state.json` in the same validated, private `0700` folder as the command socket. Each update replaces the file atomically with mode `0600`. It contains status and fixed user-facing copy only, never transcript text, error bodies or audio. Version 1 has this shape:

```json
{"version":1,"pid":12345,"pidStart":12345678,"dictation":null,"state":"idle","since":1791486000000,"updatedAt":1791486000000,"detail":null,"kept":false,"edge":"top"}
```

`pid` is Sotto’s main process ID, included in every write. `pidStart` is the integer start time from field 22 of `/proc/self/stat`, read once at Linux startup and retained in every write. If that read fails, Sotto still starts and omits the field. The plugin checks both fields against `/proc/<pid>/stat` before showing an active state left behind by a crash or kill, so a reused PID cannot keep the pill showing. Older files without `pidStart` use `pid` alone. These fields are additive; readers ignore unknown fields and the version stays 1.

`dictation` is an opaque string derived only from Sotto’s session identifier. It is new for each dictation and stays the same from starting through delivered, copied or failed, including Try again and edge-only placement. Idle and Cancel publish null; an error without a session also has null. It never comes from content. The plugin chooses the focused display when this field changes to a new non-null value, even if coalescing hides the transition between dictations. Older files fall back to the state sequence.

`state` is `idle`, `starting` (connecting the microphone), `listening`, `transcribing` (including preparation and delivery), `delivered`, `copied` or `failed`. Cancel maps to idle. `since` is the epoch millisecond when that state began; `updatedAt` is when its dictation identifier, status, detail, kept flag or edge last changed. `detail` is fixed copy under 60 characters or null. A copied result says “Copied — paste with Super+V”. `kept` is true only for a failure whose recording remains in memory for retry. Each kept failure names what happened and says “Recording kept.”; a key or credit problem also says what to fix before Try again. When audio was captured but not kept, the detail says the recording was lost or where the completed text remains. Delivery failures point to Dictate’s selectable text, which stays until dismissed or Sotto closes, even with history off or a failed history save. A history-only failure says the text is on the clipboard. Microphone failures before capture, setup, settings and no-speech failures need only the next step because nothing was recorded. If the microphone disappears while listening, the detail says “Microphone lost. Recording lost. Connect it again.”; that recording and its partial text are gone. An unknown failure says “Dictation failed.” and follows `kept` for the recording outcome. `edge` is `top`, `bottom`, `left` or `right`. There is no heartbeat; an unchanged `updatedAt` during a long dictation is normal. Meter and progress updates do not write the file. A burst is coalesced within 50 ms and keeps its final state. Sotto removes the file on quit. The commands retain the socket’s validation, event stamps and 40-byte request limit, including `place bottom --at <epoch-ns>`.

## Troubleshooting

If Sotto cannot read its saved keys, it preserves the encrypted file and shows a notice. Add your keys again in Settings.

### Either platform

- **Codex shows only your messages after a restart:** Open the thread while Codex is connected. Sotto reconciles repeated saved prompts without removing the original replies. **Show earlier messages** also reaches replies outside the newest ten turns.

- **Completed text could not be copied:** Open Dictate. The selectable text below the wave stays through page changes and later dictations. **Copy text** retries copying without transcribing or pasting again; if it still fails, select and copy the text yourself. **Dismiss text** removes that recovery entry. With local history off, recovery is only in memory and closing Sotto clears it. With history on, the completed transcript is also saved unless history storage fails. A paste-helper failure still leaves the normal copied result in the clipboard.
- **Shortcut conflict:** Choose another accelerator in Settings. Sotto keeps the last working shortcut if registration fails.
- **No speech detected:** Move closer to the microphone and confirm the level meter responds. Silence does not replace the clipboard or create history.
- **The OpenRouter key could not be stored securely:** If a key saved by an older version of Sotto cannot be moved into the credential store, Sotto removes the plaintext key from settings anyway. Settings says it could not be stored securely and asks you to enter it again.
- **"Sotto could not read the saved OpenRouter key":** The operating system credential store would not unlock the saved key. Nothing was deleted. Enter the key again in Settings → Cleanup; on macOS, allowing Keychain access also works (see below).
- **"No speech model chosen yet":** Sotto downloads nothing by itself. Choose a model in Settings → Transcription.
- **"The model's files are no longer on this computer":** The app that downloaded the chosen model removed or moved it. Nothing is lost. Choose another model in Settings → Transcription, or reinstall the model in that app.
- **"Model not ready" or "Speech model needed":** The speech model is still downloading or starting, or it stopped. Settings → Transcription shows which. A stopped model says why and offers **Try again**: after a dropped download it picks up where it stopped, and when the model would not start it checks every file, downloads any that went bad, and starts it again. Nothing is recorded until it is ready; a recording that met a model that stopped is kept until you try again or discard it.
- **"Couldn't transcribe":** The speech model could not turn a part of the recording into text. The recording is kept; press **Try again**. If it keeps happening, `transcription-diagnostics.jsonl` in the app's data folder records each failure's reason and length, without any of your words.
- **AI cleanup not applied:** Check that AI cleanup is enabled and that the computer is online. When cleanup fails or times out, Sotto delivers the raw transcript instead of failing the dictation.
- **Thread messages could not be saved:** Restore access to local storage and refresh. Sotto keeps failed messages in order and retries while it is open, waiting longer between repeated failures. Saving a thread name does not clear this warning. Quitting makes one final attempt, but messages still unsaved cannot survive a restart. Turning Keep local history off keeps pending messages only for this run; turning it back on does not save words from while it was off.
- **Terminal view could not load:** Press **Reload window** to try again. Terminals keep running and retain their output. Sotto saves thread drafts first and keeps the window open if any thread draft or question answer is not saved. Save those drafts, then try again.
- **Window disappeared:** Sotto is probably hidden in the Windows notification area or the macOS menu bar. Open it from that icon or start Sotto again; the existing instance will be shown. On macOS the Dock icon opens it too, which helps when Sotto is turned off in System Settings → Menu Bar.
- **A thread never asks:** If a provider asks for something Sotto cannot read, Sotto refuses the request and tells you it did not reach you. Codex also reports an approval with an unknown child thread ID on a thread's own process; Sotto cannot route that approval into the child thread. Nothing is approved. Answer in the provider's client meanwhile, and check **Settings → Providers** for a client update and Sotto for its own.

### Windows

- **Microphone denied:** Open Windows Settings → Privacy & security → Microphone, enable microphone access and desktop-app access, then retry.
- **No microphone found:** Connect or enable an input in Windows Settings → System → Sound, then select it in Sotto Settings.
- **Paste did not occur:** Paste manually with `Ctrl+V`; the transcript is already in the clipboard. Elevated and protected targets commonly reject automation.

### macOS

- **"Sotto is damaged and can't be opened":** This is Gatekeeper refusing an unsigned download, not a corrupted file. Use **System Settings → Privacy & Security → Open Anyway**, or run `xattr -dr com.apple.quarantine /Applications/Sotto.app`, then launch Sotto again.
- **Microphone denied:** Open System Settings → Privacy & Security → Microphone, allow Sotto, then retry.
- **Paste does nothing:** Sotto needs both System Settings → Privacy & Security → **Automation** (Sotto allowed to control System Events) and → **Accessibility**. The notice says which one stopped the paste; press **Open System Settings** on it to go to that pane. Enable both, then dictate again; meanwhile the transcript is already in the clipboard, so `⌘V` works. After an update, if Sotto is already on the Accessibility list and paste still fails, remove it from the list and add it again.
- **"Sotto could not read the saved OpenRouter key":** macOS asked whether Sotto may use its "Sotto Safe Storage" Keychain item and the answer was no, or the prompt was missed. The key is still saved. macOS asks once per run, so quit and reopen Sotto, dictate, and choose **Always Allow** when macOS asks, or enter the key again in Settings → Cleanup.
- **A permission prompt never reappears:** macOS remembers the denial. Reset the grants in Terminal and relaunch Sotto:

  ```bash
  tccutil reset Microphone com.sotto.desktop
  tccutil reset AppleEvents com.sotto.desktop
  tccutil reset Accessibility com.sotto.desktop
  ```

- **Sotto quits immediately after launching:** Check that the Mac has Apple silicon (Apple menu → About This Mac). Intel Macs are not supported and the arm64 build cannot run on them.

Watcher on Muse needs a Muse that can take Sotto's tools for one session (1.4.7 and newer can); an older Muse says to update it. Reloading the window before Watcher starts keeps your message there too.

While the room is empty, the first time and in a Watcher conversation with nothing in it yet (as after a provider change), a night is drawn behind it in text characters: hills with a river, two trees and a moon, in your theme's text colour, with its accent in the moon's glow, the river, a few stars and the owl's eyes. The night is decoration: screen readers and the keyboard pass it by, and it stops drawing whenever nothing moves or Sotto is hidden.

Your Watcher messages show what you wrote, on the desktop, in Copy and on your phone. Sotto tells Watcher which request a message started beside your words, not in them. Older messages that carried Sotto's routing line show without it. Text you wrote yourself is kept whole, even if it looks like Sotto's line.

A line under Watcher's header names each thread that needs you and why: a question, a permission or a failed turn. Press a name to go to that thread's card in Watcher's conversation; when the conversation on screen has none for it, the name opens the thread beside Watcher, at what it waits on, and you answer it there.

When a thread Watcher watches asks a question or a permission, its card appears in Watcher's conversation under the reply in which Watcher tells you about it: the thread's name, its provider and computer, whether it asks a question or a permission, **Open**, which opens the thread beside Watcher, and **Show what it said**, which unfolds the thread's last reply, or the start of a long one, which then says it was shortened. Escape folds it again. The card is the thread's own: your answer goes to that thread, as it would from the thread's pane, never to Watcher, and Watcher answers nothing. A card answered in one place shows as sending in the other. When a thread on another computer can't be answered right now, the card says why, such as **Reconnect Codex to answer.** Once the thread no longer waits, answered here, in its pane or on your phone, the card gives way to one line with **Open**: **You answered Fix login on staging: Use the staging key.** when you answered it from this window, or **Fix login on staging no longer waits on you.** when Sotto can't say how it was answered, as after a restart. An answer in your own words is never repeated there. **All threads**, beside Watcher's name, opens the **Overview** over the room: every other thread grouped as Needs you, Ready for review, Working, Landing, Quiet and Idle, with what a waiting thread asks and **Open to answer**, and with settled threads folded at the end of Idle. Type to filter it, settled threads included; Escape closes it. Pressing a thread opens it in its own pane beside Watcher, with its own composer, request cards and draft. Escape or Close puts the pane away and stops nothing, and the divider between the two panes resizes them. To work in the thread on the Threads page instead, hold Shift as you press it, or press **Open in Threads** in its pane. Its pull request badge does the same and opens the pull request in Tools there, since Watcher's room has no Tools panel, and so does a link that opens in Sotto's browser: Threads shows it in that thread's Tools > Browser. Links in Watcher's own replies open in your system browser.

Once Watcher runs, its header has **Conversation** and **Watched** beside All threads. **Watched** shows each thread Watcher watches as a card, grouped as the Overview groups them, with what Watcher last did, **Open to answer** when one waits on you, and **Stop watching**; **Watch a thread** opens All threads. The arrow keys move between the two. Watcher watches any number of threads and starts any number; there is no limit to set.

Under each of Watcher's replies, a card for each thing it did in that turn says what it did, **Started**, **Sent to**, **Stopped** or **Settled**, and to which thread, where that thread stands now, and its provider, its computer (**This computer** or the paired computer's name) and its project. Press the thread's name to open it beside Watcher. These cards, and the cards of questions and permissions waiting on you, are the only places a thread's name in Watcher's conversation opens it: Sotto never looks for names in what Watcher wrote. A card that begins **Could not send to** or **Could not start** means the action never reached the thread. When you send in a thread Watcher was driving for one of your requests, a quiet line from Sotto follows that turn: **You took over Auth refactor. Watcher stopped sending to it.**, with the thread's name opening it.

While threads Watcher started are running, **Stop all** sits at the end of Watcher's header. It asks first, **Stop the 2 threads Watcher started?**, naming each with what it is doing: each stops its current turn and keeps the work it has done, and threads you started or took over keep running. **Stop 2 threads** stops them, and the same place then says what came of each: stopped, a stop still waiting on its computer to confirm, or what went wrong and what to do. Escape or Cancel puts it away and stops nothing. Put away while it is stopping, the stop goes on, and pressing **Stop all** again shows what came of it. If Sotto loses the answer, it says it can't tell what stopped, and you open each thread to check.

Watcher's composer has its own permissions after its model and reasoning, as a thread's composer does: **Ask for approval**, **Allow edits**, **Auto** or **Full access** (Grok Build and Muse offer three of them), each with a line saying what Watcher does under it. Sotto remembers your choice, and a new Watcher starts on it; the first ever starts on **Ask for approval**. Until the provider confirms a change, the chip is dashed and the line beside it says what is still in force. Whatever you choose, when Watcher asks you can allow it once, not for good, and its instructions still tell it to hand changes to a thread. When Watcher changes files itself, one line under that reply says so: how many files, then the reason its reply gave on one line of its own beginning `Watcher change reason:`, or **It gave no reason**. The reply reads without that line, here, on the phone and when you copy it. **Show the files** lists them, and Escape folds them again. Only you answer its requests.

To move Watcher to another provider, pick one of that provider's models in Watcher's model picker; its list says that another provider's model starts a new Watcher. While Watcher works or one of its deliveries is on its way, Sotto says to wait and changes nothing; otherwise it starts the new Watcher, and the last one stays readable as Watcher history. If the last one said anything, a strip over the new Watcher's composer says **Sending starts the new Watcher with a handover of the last one**, what that carries and leaves out, such as **It carries 4 of 6 messages and leaves out 1 image and 12 records of its work.**, and **Read it** shows its words. The send button reads **Continue** while the strip is there: your first message goes with the handover ahead of it, as one message, so the new Watcher spends no turn on it. The conversation shows the handover as Sotto's, labelled **Handover** and **Context, not a new request.**, above your own words, with **Read the handover, word for word**. Press X on the strip, or Escape there or in the box, to start the new Watcher without it; nothing is sent. Sending from your phone first also starts it without the handover. A handover carries the last Watcher's messages as you saw them and never its attachments, images, visuals or the records of its work, such as tool calls, which it counts instead. With **Keep local history** off it holds only what Sotto kept since it last started, and says so. Restarting Sotto before you send drops the offer. Your phone shows your words without the handover.

To start Watcher afresh on the same model, press **New Watcher**, first in the row under Watcher's message box. It starts a new Watcher at once, with the same model, effort and permissions, and the last one stays readable as Watcher history. Watcher keeps watching your threads, and the threads it started keep working. The same strip offers the last Watcher's handover, and says **Sending starts the new Watcher with a handover of the last one.** without naming a provider, since it is the same one. Until you send, the new Watcher's conversation says which model it is on and where the last one went. **New Watcher** waits while Watcher works, while a question or permission of its own waits on you, or while your last message is still on its way, and it says **Wait for Watcher to finish before starting a new one.**; a Watcher you have not sent anything to has nothing to hand over, so it says so instead. If Sotto refuses, the reason shows under the box and nothing changes. New Watcher is on this computer only; your phone has no such button.

To give a thread to Watcher, press **Watch** in the thread's pane header, or the owl among its sidebar row's actions or at the end of its row in All threads. It acts at once, and a note above the composer says so, with **Undo**. Watcher can also watch a thread, or stop, with its own tools, and a thread it works on for one of your requests counts as watched while that request runs. A watched thread shows the owl right after its provider logo in the sidebar, the Overview and its pane's header, and its composer says **Watched by Watcher. It keeps this thread going and brings you its questions and permissions.** with **Stop watching**. It stays watched until you stop it, even after a request closes or Sotto restarts. Sending there yourself keeps it with Watcher: what Watcher had queued is dropped, and while your turn runs Watcher can only steer it, which the composer says meanwhile. Sotto's own messages there, such as pull request news, never count as yours. Once you stop watching a thread, Watcher can't watch it again by itself; press **Watch**, or ask it in a new message to Watcher. A thread watched only for a request is yours again once you send to it, and its composer says so instead: **Watched by Watcher. If you send here, Watcher stops sending to it.** Watched's line over its cards promises only what holds for the threads it lists. Watcher brings you a watched thread's questions and permissions, on their cards in its conversation, and never answers them. Watcher itself is not listed on the Threads page; Watcher history is.

When a watched thread's work is done, Watcher puts it away. **Settle finished threads**, under **Watched threads** in **Settings → Watcher**, is on until you turn it off. Done means the thread's turn finished, nothing is running, queued or waiting on you there or in a thread it delegated to, every pull request it has is merged or closed, and Watcher has heard all of it and finished its own turn. Watcher then settles the thread and stops watching it, with no notice and no message to you. A turn you sent there yourself counts too, and so does a thread on a paired host. A thread Sotto could not settle stays where it is and watched, and is tried again only after it finishes another turn. Restore a settled thread from Settled as usual; Watcher watches it again only when you press **Watch** or ask it to. Turning the setting on settles every watched thread that is already done.

Watcher is available only in Owl builds. Stable builds carrying the Watcher gate hide Watcher and its history, start none of them, and keep their records, thread kinds, settings and conversation histories whole for a later return to Owl, even with Keep local history off in stable. Pane layout and selection pointing at Watcher do not survive a stable session: stable handles those views like missing threads. The saved Watcher records remain available in Owl. To clear Watcher history, turn that setting off in Owl. Ordinary threads, drafts, keys and the dictation shortcut keep working. Older stable builds, including 0.1.35 and 0.1.36, still drop Watcher metadata on save; back up the closed profile before returning to one. See [the release procedure](release/releasing.md#cutting-a-sotto-owl-build) for tested data behavior and publishing steps. Owl comes for Windows, Apple silicon Macs and Linux on Omarchy; it updates itself on Windows and a Mac, and on Linux each Owl is installed with pacman.

Muse gives up on a tool call after 5 minutes. So when Watcher runs on Muse, a start or message it sends that is still on its way after nearly 5 minutes comes back to Watcher with its receipt and goes on; it is never sent twice, and Watcher reads how it went from the receipt.

Watcher starts any number of workers. When a start leaves more than ten threads working on this computer, its result says the computer may slow down or use its battery faster, and Watcher tells you; nothing is held back. Each target gets at most four automatic prompts in one Watcher turn, and retries do not renew that budget. A repeated call returns its original receipt; an uncertain receipt is reconciled rather than resent. A direct instruction or control fences earlier automation. A standing watch stays, while automatic sends wait for your turn and pending user work to finish. Answer questions and permissions on the worker's own card, in its pane or in Watcher's conversation; Watcher cannot answer or widen them. A worker Watcher starts gets no more permission than your new-thread default in **Settings → Agents**. A thread you already gave more, such as one on Full access while the default is Ask for approval, still takes Watcher's sends, queued prompts and steers, and keeps its own permission. Stop all confirms only eligible threads Watcher started and can report individual unconfirmed stops. A message you queue to Watcher while it works carries on what you asked it last. If you stopped that request while the message waited, or it had finished, Watcher takes the message as a new request, which can start and send to threads like any other. You can steer Watcher whenever it works, even while it reads news of your threads, and it can act on what you steered in straight away: start threads, watch them and send to them.

The same start capacity covers workers on supported paired hosts. A host must offer Watcher control and reads for request-bound operations and the additional standing-watch feature for durable watching. Older hosts refuse durable watching and keep their existing active-request behavior. The owning host checks pending cards and takeover again before sending, and a start's permission before starting. A native or phone instruction there counts as yours just as one on this computer does: a watched thread stays with Watcher, which can only steer it until your turn ends. Disconnect and restart preserve uncertain receipts and hold their slots until confirmed; they never retry a prompt automatically. A worker Watcher starts there gets no more than this computer's new-thread default, and no more than Ask for approval where that host does not let this computer answer. Watcher still sends to a thread there that already has more. These tools answer no request and change no permission policy. A Watcher on Muse reads and directs threads only on hosts updated to know it, and says to update any other.

A question, a permission request or a failure, failing checks included, reaches Watcher within two seconds, with at most five seconds during a burst. Other news waits until twenty seconds pass without more, and never more than a minute, so news that comes close together reaches Watcher once. A connected watched thread with no message, activity or background-work progress for twenty minutes can bring one quiet notice. An unanswered request or a disconnected thread is never treated as quiet. Your queued prompts stay ahead of the news, and a question answered before delivery is removed. Stop prevents news from restarting that request. News is Sotto's own background message to Watcher: it never shows in Watcher's conversation, the queue above its composer or the phone. You read Watcher's reply, in its place among your own turns. Its header says After news and how long Watcher worked; press that to see the work. A news turn that wrote no reply shows nothing, unless it failed or stopped. Watcher is woken when a watched thread finishes, fails, asks a question or a permission, or goes quiet. A pull request wakes it when its checks fail, or the checks its base branch requires pass, it merges or closes, it conflicts with its base, or a review or comment comes; checks that are still running, a new commit or a new link do not. A send of Watcher's own wakes it when it fails or may not have gone and Watcher's own tool call did not already say so, unless it was turned away because you sent to that thread yourself. A pull request's merge, checks or review reach Watcher once; the same facts are not sent again until one changes. News of a finished turn carries the first 500 characters of the thread's reply, so Watcher rarely needs to read the thread. A thread that a watched thread delegated to is that thread's to see through: Watcher hears nothing of it, except a question or permission request for you, which comes as news of the thread that delegated it. A thread's file and Git changes come with the news that its turn finished, or that the work the turn left running ended, not one by one.

A turn that finished with background work, sub-agents or monitoring still running is not done yet. Watcher hears that the turn finished, and how much was running, when that work has ended, as work-settled news. A question, a failure or twenty minutes without the work ending tells it sooner. After twenty minutes with nothing running in the thread, the news opens "Held 20 minutes, thread idle", with the start of the thread's last reply, so Watcher reads that thread instead of waiting on it. If Sotto restarts while sub-agents are running, it cannot see how they ended, so that news waits until the provider says. A paired host on an older version does not report its threads' background work, so Watcher hears when their turns finish but gets no work-settled news for them. Update the host to get it.

Background work never holds Watcher's messages. A thread whose turn has ended takes a message from Watcher straight away and starts a new turn, even while a test run, a sub-agent or a watch carries on, and a message Watcher queued goes as soon as the turn ends. Only a running turn, or the thread's own queue, makes Watcher wait, and Watcher is told which. Stop all keeps the messages you had queued on the threads it stopped until you review them, and they still go first, but it does not hold what Watcher queues for them after you ask it again.

Each start and send Watcher makes has an outcome: working, background (its turn ended with work still running), answered, failed, stopped, paused (your own turn in that thread took it over) or unknown (Sotto cannot prove what happened, as after a restart mid-turn; it is never taken as answered). The brief's own message ties it to the turn that answers it, so a steer shares its turn's answer and a queued send gets its own. A Claude reply whose turn Sotto observed stays tied to that turn when history is read again. News names the operation a finished turn answers, and Watcher reads the outcome with that turn's reply, labelled as the worker's words, without paging through the thread. With Keep local history off, a reply from before a restart is not kept, and Watcher is told so. Reading costs nothing. A paired host on an older version does not report outcomes, so its briefs read as unknown until it is updated.

Watcher can list the machines it may start workers on: this computer and each connected host, with its operating system, architecture, memory and CPUs, and how many threads it is running. A host on an older version does not say what kind of machine it is, so its facts read unknown until it is updated, and a host that is not connected says so. Only numbers and the system's own name are read, over the connection Sotto already keeps to that host.

Observed evidence is separate from what a worker said. Git totals describe the working copy, where other threads may also have edited. Completed checkpoints publish reliable file counts; an interrupted or overlapping capture says unavailable. Pull request checks are unknown until an existing GitHub reader has read them on that head. A review approval is GitHub's decision, not your permission to merge. Evidence older than five minutes is labelled stale for Git and GitHub; no timer fetches it just to refresh that label.

### Usage

Press **Usage** at the foot of the sidebar to open the dashboard. It counts all the work Claude Code and Codex did on each of your computers: in Sotto's threads, in the subagents those threads started, and in the same clients used outside Sotto, such as Claude Code itself, the Codex app, the Codex CLI, `codex exec`, Codex in VS Code and T3 Code. Grok Build, Devin, Muse and OpenCode are counted in Sotto's threads only. **Overview** starts with a headline index: Room left, Prompts, Tokens, Where, From cache, Most used model and Busiest hour. Pick one to see its details. **Where you work** has a bar for each place the work ran: Sotto threads, Sotto's subagents, then each app outside Sotto. **Subscriptions** shows each provider's account limits, and **Models** lists every model with its prompts, tokens and share from cache; press a model for its details.

**Prompts** and **Tokens** each draw a **Per day** chart. **Show** chooses what it draws: **Total**, **By provider**, one series for each provider with activity in the range, or **By model**, the five models with the most prompts (on Tokens, the most input and output tokens) and **Other** for the rest. **Bars | Lines** chooses how. Bars stack, so a day is as tall as its total; lines are drawn one per series, not stacked, so each can be followed on its own. A list above a split chart names every series with its total for the range; point at a day, or focus the chart and press Left or Right, and it shows that day's values instead, with Home and End for the ends and Escape back to the whole range. A screen reader hears every series' value for the day. On Tokens a value follows the rest of Usage: a dash, read as "Not reported", when no record reported it, and "at least" when some records left it out. Under a chart split by model, **Each model's provider, and what Other holds** opens a list of each drawn model with its provider and the models Other holds; Escape closes it. When a computer has more models than Usage lists, "Ranking is incomplete" beside the chart says the models drawn may not be the ones with the most prompts. A split is drawn only when every computer in the figures answered for it; when one did not, the chart says so, says nothing was lost, and offers **Try again**. Each provider has its own colour, and a model keeps its colour while it stays drawn. Devin reports no tokens, so it is never drawn on Tokens. Sotto remembers Show and Bars | Lines until it quits, on both charts and when you come back to Usage; they are not saved. When a range is longer than a year the chart is not drawn, and neither are its controls.

Use the date range, provider, computer and **Everywhere / In Sotto / Outside Sotto** menus to narrow the figures. Dates and hours use this computer's time zone on every host. A dash means a figure is unavailable; zero means a reported zero, ≥ marks an incomplete lower bound, and a share worked out from incomplete figures says about. Input already includes cache reads and writes, so they are shown as parts of input rather than added to the total. A prompt counts under the model that served it. Prompts outside Sotto are the clients' own user turns, including each `codex exec` run, which an agent may have started; Watcher and wake-ups have their own counts, and subagent work counts in tokens, never as prompts. Sotto's prompts from before Usage began come from its thread store; threads deleted before then, and work a client has deleted from its own records, cannot be counted.

Usage reads each client's own session files on the computer that ran the work, keeps the numbers, dates, model names and app names, and drops the rest as it reads. The first read of a computer's history takes a few minutes in the background. After that it reads only what was added, five seconds after Sotto starts, every five minutes and when you open Usage, so subagent work can take a few minutes to appear. Grok Build and Devin keep no token counts on the computer, so their work outside Sotto is not counted. Muse and OpenCode are counted from the token counts they report to Sotto's threads as the work happens, each model call once, under the model that served it; Sotto reads nothing from their own folders, so their work outside Sotto is not counted either. Muse tokens from before Sotto counted them are not read back; an OpenCode thread's earlier steps are counted the next time Sotto reads that thread.

Opening Usage reads each provider's account limits when the last reading is more than a minute old, and **Read again** reads them now. Codex, Grok Build, Claude Code and Muse answer with metadata and no model prompt; Claude Code answers through its own connection to its provider, and Sotto reads no credentials. Each window is named by its length, says when it was read and when it resets, and shows how much of its time is left. Grok Build reports when its week resets but not how much is used. Devin's limits are unavailable. Muse reports its 5-hour window and its week only after a Muse turn has run, and only to a Muse thread that is still running, so until then Subscriptions says there is no reading yet; Sotto keeps the newest reading it was given until it closes. OpenCode reports no account limits, so it is not on Subscriptions. When several computers read the same provider, Subscriptions shows the freshest reading and the others as a line each; their percentages are never added. Muse and OpenCode appear in Usage only where their own Owl providers are on.

Usage keeps only numeric records, dates, model names and app names on the computer that ran the work. It keeps no prompt or reply text and survives thread deletion, rewind and **Keep local history** being off. **Clear usage**, in the **…** menu, opens a confirmation for the supported computers currently selected. It removes all figures on those computers, including figures outside the current filters, and records from before the clear never return. A changed revision asks you to review and confirm again. Thread history, existing per-thread readouts, subscription limits and the clients' own records keep their own records.

All connected computers can report Usage when their own Sotto Owl host supports it, and a computer's history appears once its Owl host carries the history reader. An older or stable host stays connected and shows Usage unavailable until you choose its matching Owl host update. A computer that is offline cannot supply its saved figures. Stable shows and starts none of Usage while preserving its dormant numeric history for a return to Owl.

### Update all

In an Owl build, a card in the bottom-right corner lists everything that is out of date as the steps one press runs, in order: **Download Sotto Owl**, each provider client on this computer (**Update Codex**, with its versions), each connected host's clients and then that host's own Sotto (**Update forge's host**), and last **Restart Sotto**. Each step says where it happens ("This computer ·" or the host's name), and the head says Sotto's own versions, or how many steps are done while it runs. It appears when something new is published, and the chevron folds it into a small button in the same corner. **Update all** starts Sotto's download, updates every client Sotto can install, one at a time on each machine, and updates each host once the clients it was asked to update have finished. Threads keep working while clients update. A host restarts into its new version, so its threads are unavailable for a few seconds; a host with working threads waits until they finish, and the card offers **Stop N threads and update** if you would rather not wait, and **Cancel update**. That wait lasts while Sotto is open: if Sotto restarts first, the card offers the host again. A host also waits while its clients update, whatever started its update, including a step's **Try again**, and reads "Updates once forge's clients have." If a host restarts while one of its clients is waiting or updating, that client's update is lost with it. Its step reads "Waiting to hear from forge…" until forge is back, then "forge restarted before Codex updated. Nothing was changed. Try again." **Try again** puts it back in the host's line. If the update left the line some other way, as when you press **Cancel update** on the host's tile, the step reads "The Codex update on forge stopped before it finished." instead. A client installed with something Sotto does not drive, or a host Sotto did not start, is listed with the command to run yourself.

When Sotto finds a new version of itself, each connected host Sotto can update is listed straight away, aimed at that new version rather than the one running here, so a host is updated before Sotto restarts instead of after. Sotto first asks the releases page on GitHub whether that version's host is published for the host's own system; if it is not, the host is offered once Sotto has restarted. While Sotto asks, the host's step reads **Checking the releases page for its update…**, and **Update all** covers it: the host joins the press as soon as the answer comes, and the card asks to restart only after the host's update. A host Sotto has never reached over SSH is offered once Sotto has restarted, because Sotto does not know yet which system's host it needs. Until Sotto restarts, the host runs a newer Sotto than this computer. Its threads keep working, and if you press **Later**, it stays that way until Sotto next restarts. If Sotto stops offering that version while a host is still downloading it, the host's update stops and the host is offered this computer's version again; a host that has already begun installing it finishes, and its step says so. Finding a new version also has this computer and each connected host check their clients again at once, so a client published since the last check joins the list in the same card rather than after the restart. **Update all** does not wait for those checks: a client appears in the list when its answer arrives, and if a press is already under way it joins that press without another one.

Once Sotto's download is ready and the rest has finished, the card asks to restart, and its last step says what restarting installs, how many threads on this computer are working and whether they carry on after the restart. **Restart now** installs the update at once; while a host's update is still running it restarts nothing and says so, and you press it again once that update finishes. **Later** folds the card, and the update control keeps the download. **Not now** hides the card until something new is published or Sotto restarts. When a press ends with everything updated and nothing still waiting, the card reads **Updated** and goes by itself 5 seconds later, folded or not, as **Dismiss** would. It stays while the pointer is over it or focus is inside it, and counts the 5 seconds again once both have left. When something did not update, the card reads **Not everything updated** and stays, with **Try again** on each step that did not finish, until you press **Dismiss**. **Restart to finish** never goes by itself. In **Settings → Application → Updates**, Update all takes the place of Download and runs the same press. On a Mac or Linux, where Sotto does not update itself, the card covers clients and hosts only. In Owl the card replaces the client update card and the host update pill.

### Resume threads after a restart

In an Owl build, **Settings → Application → Resume threads after a restart** is on by default. When Sotto closes while a thread on this computer is working, for an update, a quit, a crash or a restart of the computer, the thread carries on when Sotto opens again: once its provider is back, Sotto sends it this note, shown in the thread as Sotto's with a **Resumed** tag:

> Sotto restarted while you were working on this, and your last turn stopped partway. Any command or tool that was running was stopped too, so its result may be missing. Check where things stand, then carry on.

Your own message is never sent again. Follow-ups you queued behind the stopped turn go after the resumed turn finishes. If the provider refuses the note, Sotto drops it and leaves the thread as it was, so nothing you send that thread waits behind it. A thread is resumed at most three times in a row; if Sotto stops a fourth time before a turn finishes, the thread waits for you. A thread settled or archived in the meantime is left alone. A request for permission that was waiting when Sotto closed was declined then; the agent asks again, and you answer it. Sotto keeps which threads were working in `restart-resume.json` in its data folder, thread IDs and times only. Turn the setting off and a stopped thread waits for you to send it a message. Threads on a remote host keep running when Sotto closes. Stable hosts resume their own threads once this feature reaches stable; matching Owl hosts follow their own feature list and setting.


### When main freezes, and Record a minute

In an Owl build, Sotto's main process watches how long it takes to answer. When it was blocked for more than half of the last minute, a **Main is slow** pill appears in the window's top row, left of the window controls. Press it for the numbers: how much of the minute main was blocked, its longest freeze, how many freezes lasted 100 ms or more, and a bar for each second of the minute. **Not now** hides the pill until main recovers and freezes again. Escape, a press outside or Tab out of it closes the popover. To stop the pill appearing at all, turn off **Settings → Performance → Tell me when main freezes**.

**Record a minute**, in the popover or in Settings → Performance, records one minute of what main and the window spend their time on, while you keep using Sotto as you were. The pill counts down (**Recording, 42 s**); **Stop without saving** keeps nothing. The recording is an activity recording: a folder named `sotto-activity-` and the time it started, in `performance-recordings` in Sotto's data folder (**Show in folder** opens it), holding `main.cpuprofile` and `window.cpuprofile`, which Chrome's and VS Code's profilers open, and `summary.json` with the minute's numbers. They hold function names, places in Sotto's own code and timings; no sound, nothing you dictated or typed, and no folder of your computer. Only the newest five are kept. When something else, such as DevTools, already holds the window's profiler, only main is recorded and the recording says so.

**Attach to a thread** opens a new thread in the current project, or asks which project when it is on another computer, with a draft that names the recording's folder and files; nothing is sent until you send it. **Show in folder** opens the folder with the recording selected. **Close** puts the pill away; the recording stays in its folder.

### Delegation between threads

In an Owl build, a Claude Code, Codex, Grok Build, Devin or Muse thread on this computer can hand work to another thread it starts, such as asking a thread on another provider to review what it built. The agent does it with Sotto's `delegate` tool; there is nothing to set up. The new thread is an ordinary thread in the same project, on the model, effort and permission your worker role for that kind of work gives it (see Worker roles below), or on what the agent named when you asked it for something else, sharing the project's checkout unless the agent asks for its own worktree. It has no more permission than the thread that started it or your new-thread default, whichever is narrower. Sotto never widens it afterwards; you can, in its own options.

A delegated thread asks you, never the thread that started it, for any permission or answer, on its own card. The thread that delegated waits for the outcome for up to five minutes in the same call. When the work takes longer, Sotto hands the result straight to the thread that delegated, as its next turn, when the delegated thread answers, fails, stops or is paused. A turn there that ended with background work still running is not done; if that work has not been seen to end after twenty minutes with nothing running in the delegated thread, the thread that delegated is told once that it was held that long, with the start of the delegated thread's last reply, so it can look rather than wait. An answer carries the delegated thread's reply, marked as that thread's words; any other outcome says only what happened and, for a brief that was never sent, why. You are not shown that message, in the thread, its queue or on your iPhone: the card under the reply that delegated shows the outcome, and the agent's next reply tells you what it learned. Only the thread's own turn holds the result back. A message you queued there that is ready to go goes first, and the result on the next free turn; a paused queue, Watcher's Stop all or a prompt you set aside does not hold it, and stays as it was. A thread you archived or settled gets nothing.

A delegated thread can delegate once more, so a builder's reviewer can ask a third thread something; the threads it starts cannot. A thread can start any number of delegated threads. When a start leaves more than ten threads working on this computer, the result says the computer may slow down or use its battery faster, and the thread tells you; nothing is held back. Each delegated thread takes up to four briefs for each message you send the thread that delegated; wake-ups and retries add none. A thread that delegated cannot send a delegated thread another brief while that thread's own queue is paused or holds a message whose result is unknown: you resume, clear or check it there first. Sotto's own messages in a delegated thread, such as the note that resumes it after a restart, are not yours, so they hold a brief back only until their turn ends.

**Stop** on a thread stops every delegated thread below it that is still working, at both levels. Stop on a delegated thread stops only that thread and what it delegated. When you send a message in a delegated thread, or have words waiting in its composer, briefs to it wait until your turn there ends. A brief that was waiting when you sent is dropped rather than sent on top of your message, and the thread that delegated is told it was paused. If Sotto restarts while a delegated thread is working, nothing is sent again, and the delegation's outcome reads unknown. Sotto keeps delegations in `delegations.json` in its data folder: thread IDs, message IDs and outcomes, and for a refused delegation the rule that refused it, never a brief or a reply. Threads on another machine cannot delegate yet. Stable builds offer none of this and leave that file as it is.

You see each delegation where it happens. Under the reply of the turn that delegated, a card says **Delegated to** and the delegated thread's name, which opens it. The card names the provider and the machine it runs on (This computer, for now), its outcome (Working, Background work, Answered, Failed, Stopped, Paused or Unknown), and how the wait went: how long the thread waits for it, that it waited and went on and the answer comes back as a wake-up, or how long the answer took. A delegation Sotto refuses as it is asked for, such as one wider than the thread's own permission, gets a card too: **Not delegated** and the kind of work, or **Not sent to** and the thread, with the provider and machine and why, in plain words. Nothing was started or sent, so it opens nothing. A delegated thread has no row in the sidebar, and a search does not find it. It is listed in **Tools → Agents** of the thread that delegated it, mixed with that thread's own agents, newest first, and a thread it delegated in turn is listed under it. Its row has its provider's mark and a **Thread** tag, its brief, then its provider, kind of work, model, effort and when it started, as far as Sotto knows them, its outcome and how long it has taken. Open the row for the brief and the latest outcome; the delegated thread's reply is not shown there. **Open as thread** shows it in the pane: the sidebar keeps the thread that delegated it marked, and Tools stays on that thread's roster, pinned, where the row says **In the pane**. When a delegated thread waits for your approval or answer, its row is marked and its button reads **Open to answer**, the row of the thread that delegated it says **Needs your approval** or **Needs your answer** in the sidebar, and a dot marks the Agents tab and the Tools icon. You answer in the delegated thread itself; nothing is answered from the roster. A thread in error below reads **Needs attention** on that row the same way, after any waiting request. A row in the roster says **Just finished** for a delegated thread that finished while no window showed it, until you open it. Settling a thread settles the threads it delegated with it, including any still working or waiting on you, so they stay in its roster rather than standing in the sidebar on their own; its row in Settled still says when one waits on you, and restoring it brings them back. A delegated thread that was babysitting a pull request stops, as any settled thread does, and does not start again when you restore it. Open one from the roster or its card to work in it; it stays settled. A delegated thread whose delegating thread is gone keeps its own row in the sidebar, and so does an open one whose delegating thread is settled, such as one it started after you settled it. A delegated thread on another connected computer shows only what this computer knows of it: Working, or waiting on you, with no start or brief, since its delegation is kept on that computer. The card's link in the transcript opens a delegated thread the same way. A delegated thread says **Delegated by** and the thread's name under its header, which takes you back, and shows each brief it was sent as that thread's, with a dashed edge, not as yours. While a thread that delegated is working, its Stop button names the delegated threads it will also stop, and the line under the composer says how many, such as "Stop also stops the 2 threads it delegated that are working." Under a delegated thread's composer, a line speaks only while something holds a send back: while your own turn there runs, it says the thread that delegated sends nothing there until it ends, and while that thread's brief is still being worked on, it says that a message of yours would hold it back.

### Worker roles

In an Owl build, **Settings → Watcher** holds **Settle finished threads** under **Watched threads**, and, under **Worker roles**, what each kind of work starts on. There is a card for each **worker role**: **Orchestrating**, which is Watcher itself, then **Building**, **UI**, **Code review**, **Research** and **Computer use**. Each card has a **Model**, an **Effort** and a **Permissions** field, the same controls a thread's composer has, and its **Defaults, in order** underneath: the first one whose provider is connected is used, marked **In use**, and the others say **Not connected** or **Not set up**. The model list holds every model from every provider set up on this computer, so any kind of work can run on any provider you have.

With Claude Code, Codex, Muse and Grok Build connected, the defaults are Opus for Orchestrating, Opus at Extra high for Building and UI, Muse Wonder Full at Extra high for Code review, Haiku for Research and GPT-6 Astra with Full access for Computer use. Building and UI may edit files without asking; Code review and Research ask first. With one provider, each role starts on that provider's own models. No worker starts wider than your new-thread default in **Settings → Agents**, so a card whose permission is wider says what its workers start on instead, with **Change it in Agents**. On Windows, Codex's Computer Use can be stopped by its own sandbox below Full access; the Computer use card says so when that applies.

Change any of a card's three fields and the whole card becomes **Your choice**, with an accent edge. A provider connecting or disconnecting never changes it: while its provider is away, the card says **Your choice, not available**, and new work starts on the role's next default until the provider is back. A card on its defaults moves to its next default on its own and says why, and a line over the cards names the provider that is away. **Reset to default** on a card, or **Reset all to defaults** over them, puts the defaults back, and a line says what was reset, with **Undo**.

The Orchestrating card sits beside a drawing of Watcher's composer: its model and effort are Watcher's own, the same choice its composer's chips show. Its model list holds every provider's models too, but Watcher does not run on Devin, so Devin's tile says Watcher can't run there yet; with only Muse connected, Watcher starts on Muse's own model. While Watcher runs, a change here, or a reset, changes Watcher the way its composer does, so another provider's model starts a new Watcher with the last one's handover; a change in its composer is remembered here for the next Watcher. Before Watcher starts, a change here also replaces what you picked in its first message's composer. Its permissions are Watcher's own, chosen in either place, and Reset leaves them as they are.

When Watcher starts a worker, it names the kind of work, and the thread starts on that role's model, effort and permission; a thread that delegates does the same. Words in your message win for that request: ask Watcher to start a build on Sonnet and it does, and its reply and the start's receipt say the request chose the model rather than the role. Stable builds show no Watcher page in Settings and keep your choices as they were for a later return to Owl.

A thread's own sub-agents follow the roles too. Every Claude Code, Codex and Grok Build thread on this computer is told, with its other instructions, what each kind of work runs on, and Watcher keeps its own instructions:

- **Claude Code** threads get one agent for each role whose model is a Claude model, named `sotto_building`, `sotto_ui`, `sotto_code_review`, `sotto_research` and `sotto_computer_use`, on the role's model and effort. Each gets the role's permission, but never more than the thread's own: a thread on Ask for approval gives every agent Ask for approval. Narrow the thread's permission below what its agents were given and the thread's Claude Code starts again, so none keeps more than the thread.
- **Codex** threads get one Codex agent role for each role whose model is a ready Codex model, with the same names. Sotto writes each as a small file in its own data folder, under `codex-roles`, never in your `~/.codex` and never in your `config.toml`, and hands it to the thread as the thread loads. Its permission is held to the thread's own the same way. A role whose model Codex does not list as ready is left out. A Codex older than the one this was checked on gets no roles; its threads are told the model and effort to ask `spawn_agent` for instead. A changed role reaches a running Codex thread the next time the thread loads: after Sotto closes an idle thread's Codex, after a client update, or when you narrow the thread's permission below its roles, which closes its Codex so the next message loads it again.
- **Grok Build** threads are told the model and effort for each role on Grok Build and asked to start their sub-agents on it when they can choose. Grok Build takes this only when a thread is made, so a changed role reaches new Grok Build threads.
- A role on another provider is reached by delegating: the thread is told to call `delegate` with that kind of work, so the new thread starts on the role's model (see Delegation above). A delegated thread is told the same, and one that may not delegate again, two levels down, is told to do that work itself.
- **Muse** and **Devin** threads are not told yet: neither has a way to carry standing instructions that Sotto has checked.

The thread's agent still decides when to start a sub-agent; the instructions say which one to use for which kind of work. Your words in a request still win. Stable builds send none of this.

### Continue a thread on another provider

In an Owl build, a thread on this computer can carry on with another provider without losing its place, most often when Claude Code stops a turn at your plan's usage limit. Sotto never moves the thread itself: it starts a new thread on the other provider, in the same project and the same folder, with the same title, and its first message hands over the thread so far.

When a turn stops at Claude Code's usage or spending limit, a row under the error reads **Or continue now on**, with a chip for each other provider that is connected, each on its default model, and **More** for the rest of a provider's models. A provider you turned on that cannot take the thread now keeps its chip, dashed, with why, such as **not signed in**. You can also start from the model chip of any thread that has already started: its list adds the other providers' models under **Continue in a new thread on Codex** (or whichever), and says that picking one starts a new thread there with a handover of this one, while this thread stays as it is. **Continue on another provider…** in the pane's More menu does the same with the model picker open.

Either way, nothing is sent yet. The composer becomes the new thread's first message: its button reads **Continue on Codex**, and its chips choose the new thread's model, effort and permissions. The permission starts as the old thread's own, the nearest the new provider offers and no wider than your new-thread default (Ask for approval when you have not chosen one); when that is narrower than the old thread's, the strip says so and why. Choose another on the chip before you send if you want. A strip above it says **Sending starts a new Codex thread with a handover of this one.**, where the new thread works (**Same folder**, or **New worktree from main**, made from the branch the thread is on) and on which machine (This computer, for now), and what the handover carries and leaves out, with **Read it** for its words. Press X on the strip, or Escape there or in the composer, to keep writing to this thread instead.

Send, and the new thread opens. Your message goes after the handover, as one message, so the new provider spends no turn on it. The new thread shows **Continued from** and the old thread's name at the top, with **Open it**, then the handover as Sotto's, labelled **Handover** and **Context, not a new request.**, then your words. The old thread stays as it was and can still be sent to: after the turn that was newest when you continued, it says **Continued in** and the new thread's name, with **Open it**, and under its composer, for example, **Continued in a Codex thread. You can still send here once Claude’s limit resets at 6pm.** Both links are kept on the threads' own records, so they survive a restart.

A handover carries what Sotto keeps of the thread (its first message, your latest request and its answer, and the newest messages that fit), never its images, attachments or the records of its work, which it counts instead. With **Keep local history** off it holds only what Sotto kept since it last started, and says so. A thread with a turn running or a question waiting cannot be continued until it finishes; a thread you have not sent anything to changes provider from its model chip instead. Threads on another machine cannot be continued from here yet. Stable builds offer none of this, and show a continued thread's first message whole.

### Continue an agent as its own thread

In an Owl build, open a finished agent's row in **Tools → Agents** on a Codex or Claude Code thread and press **Continue as a thread**. A form opens in the row itself: the model, **Same folder** or **New worktree from** the branch the thread works on, and where the thread runs (This computer, or the host's name). Same folder is the thread's own: its worktree when it works in one, else the project folder. **Start the thread** makes a new thread in the same project, named for the agent, and opens it; **Cancel** or Escape puts the form away. The agent, its row and its thread stay as they were. An agent that is still working says **It's still working. Continue it once it finishes.** One Sotto last saw working, before a restart or while its provider was disconnected, waits the same way until it shows as finished.

A Codex agent is forked by Codex itself: the new thread is Codex's own copy of the agent's whole conversation, its task included. Codex keeps that task encrypted, so the new thread opens with Sotto's note saying Codex forked the agent and that Sotto can't show its task, followed by the agent's own work and reply, with **Open** to go back to the thread it came from. Making the copy asks the model nothing; your next message is the first turn. The copy lives in the agent's conversation in Codex's own records, so if that record is removed from Codex, the thread says it can't be opened and keeps what it showed. If Codex no longer has the agent's conversation, the row says so, nothing is made, and **Start from a handover** offers a thin one instead. An agent whose conversation is archived in Codex is refused: unarchive it in Codex first; Sotto leaves Codex's archive as it is. A new worktree made for a fork Codex refused is removed again; if it can't be, the row says so and the worktree stays with an empty thread, so you can remove its folder or use it.

A Claude Code agent's thread starts from a **thin handover**: Claude Code keeps an agent's working history inside its own session, where Sotto can't copy it, so the handover carries only the task the agent was given and the result it reported. The new thread shows it as Sotto's, labelled **Handover, thin**, with **Read the handover, word for word**, and your first message goes with it ahead of your words, as one message, so no turn is spent on it. If Claude Code refuses that message, the handover goes with the next one. Afterwards the conversation shows the handover above your own words. With **Keep local history** off, Sotto does not keep the agent's name on the new thread's record, so after a restart the note says it came from one of the thread's agents. Grok Build and Devin report no agents to Sotto, so they have none to continue.

A thread on a paired host continues its agents on that host, once the host's Sotto is an Owl build that offers it; an older host says it can't yet, and nothing is made. Stable builds offer none of this and keep a continued thread as an ordinary one, its first message shown as it was sent.

### Fork a thread from a reply

In an Owl build, the newest reply of each finished turn offers **Fork from here** under it, beside the copy button. Its card opens in the transcript under that reply, and everything below it is marked **Not carried: this stays in** the thread's name. The card has the model (for Codex and Claude Code), **Same folder** or **New worktree from** the thread's branch, and where the thread runs; **Fork** makes a new thread titled "Fork of" the thread's title and opens it, and **Cancel** or Escape puts the card away and returns to the press. The thread you forked from stays as it is. While a turn is running, the press waits for it to finish, since a fork carries finished turns.

Codex and Claude Code make their own copy of the conversation up to that reply, and the new thread shows it with Sotto's note under the last reply it copied: **Forked from** the thread and at whose reply. Files aren't rewound: the new thread sees the folder as it is now. A Claude Code fork starts in its thread's own folder, so it offers no new worktree. Grok Build, Devin and Muse have no fork of their own, so their new thread starts from a handover of the conversation up to the reply, shown as Sotto's before your first message and sent with it, the way a continued Claude Code agent's thin handover is. Making a fork asks the model nothing; your next message is the first turn. On a paired host, the fork is made on that host.

### Watcher's context and state

Every message Watcher reads or sends reads its whole conversation again, so a long Watcher session costs more with each turn. In Owl, Sotto compacts Watcher's conversation once it passes 400k tokens, between turns: never while Watcher is working, answering a card, or has news or your messages waiting. Claude Code, Codex and Muse can compact; Grok Build can't, so a Grok Watcher keeps all of it.

Watcher keeps what it must not lose through compaction: your pending decisions and the standing rules you gave it, in your words, and the issues it filed. Sotto works out the rest from live data each time Watcher reads its state, so none of it goes out of date: the threads Watcher watches, what each waits on and its open pull requests, the merge queue (open pull requests that aren't drafts and whose checks passed, oldest pass first), and the finished threads Settle finished threads is waiting to settle and what holds each. Sotto also points out any kept note that names a settled or unwatched thread or a merged or closed pull request, so Watcher checks it rather than trusting it. After a compaction, Watcher reads all of that back before anything else. With Keep local history off, Watcher's kept words stay in memory only.

Press the owl in Watcher's header to see its context against the 400k point, **Compact context** to compact it now, and Watcher's state as it stands. The thin bar under the owl fills toward the point, and a dot shows when it is close. Escape closes the panel.

### Watcher permissions and standing watching

In Owl, Watcher uses the ordinary thread permission modes its provider offers: Ask for approval, Allow edits, Auto and Full access. On Muse, whatever Muse asks reaches you: Watcher's session never lets Muse's own reviewer decide for you. Its first mode is Ask for approval, and later Watchers use your last Watcher choice. Changing that mode does not change ordinary new-thread defaults. Remembered permission-card answers such as Always allow remain unavailable; the user still answers every question and permission card.

Ask Watcher to watch a thread, or every active thread. Watching sends nothing to that thread and stays until Stop watching, across closed requests and restarts. There is no watched-thread count limit, and no limit on how many workers Watcher starts. Watcher reads finished, work-settled, question, permission, failure, quiet and Git news and decides how to keep watched work moving. When you send directly, its automatic sends wait for your turn to finish; the watch stays. Opening or answering a thread's card does not pause watching.

For a thread under a standing watch on Watcher's own computer, a new instruction you give Watcher after your direct turn finishes can send work to it when Sotto can establish that order, including an instruction you queue while Watcher is still working. One you steer into Watcher's running turn stays part of that turn's request; leave it queued for it to start its own. If you give Watcher that instruction while your direct message is still queued and Sotto cannot identify its later echo, you may need to repeat the instruction after your turn finishes. Earlier requests stay fenced. A watch saved by an older build may lack that ordering evidence; its standing-watch continuation remains available, or Stop watching and Watch establishes a new assignment. On a paired computer, use its resumed standing watch; a new request alone does not clear its earlier takeover. Quiet news also covers a finished parent with sub-agents confirmed working, and All threads lists such a parent under Working. A change in their recorded counts restarts the twenty-minute wait. Agents whose state is unknown after a restart keep work unsettled but are not assumed to be making progress.

Watcher is instructed to give changing work to workers. If its own turn edits files, Sotto keeps a mark with that reply naming the files and its reason. Without the defined reason line it says It gave no reason. Changes made by another thread in a shared checkout are not attributed to Watcher. The mark follows Keep local history, like the reply itself.
