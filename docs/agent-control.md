# Sotto agent control

Sotto creates and manages coding threads through the installed Codex, Claude Code, Grok Build and Devin clients. Threads have Sotto-owned identities; each native client keeps its own sign-in, model catalog and conversation history. The providers can be connected together. Reading or sending a manual prompt does not grant Sotto permission to supervise a thread.

## Set up

1. Install and sign in to your chosen native coding client. Codex uses App Server, Claude Code uses stream-json and Grok Build uses ACP. Grok connection requires CLI 1.0.5 or newer and ACP 1; an older client produces an error before creating a session. Devin requires 3000.10.31 or newer. Sotto reports each connected client's version in Settings → Providers, with what its channel publishes (ADR-0021).
2. Open **Settings → Providers**. Select Codex, Claude Code, Grok Build or Devin in the list, then connect or enable it. Each row has its own status and switch; Configuration holds connection controls and a default model choice, while Models shows that provider's catalog. No server address or pairing token is needed.
3. In **New thread**, choose a model from any connected provider. That choice determines which client runs the thread. The same working folder can be used with different providers. Existing threads retain their provider; their model picker only offers models from that client. Unavailable models are reported rather than replaced.
4. Open **Settings → Agents**, directly below Providers, to configure the **Sotto coordinator** inline: its reasoning account, model and effort, plus the default projects directory. Native Codex, Claude and Grok subscriptions and explicitly configured OpenRouter and OpenAI API routes are supported. Changing this account does not change thread providers. Manual controls work without the coordinator.
5. Choose the speech route independently: **Grok voice** is the default and **Kokoro** is the cheaper option. Both use the configured hosted route; neither is a system voice. Save the relevant API key, select a voice and preview it. Sotto does not silently switch funding routes.
6. Configure compatible local wake-model and runtime directories before enabling voice. Wake detection runs locally. See the [wake verification record](verification/issue-9-wake.md) for model formats and distribution limits. Dictation remains available independently of agent control.

### Devin

Install Devin CLI 3000.10.31 and run `devin auth login` outside Sotto. Enable Devin in Providers, connect, and select a model returned by your account. No new API key is stored in Sotto. Devin uses ACP 1 and performs its own tools in the selected local checkout. Windows native verification is recorded; Apple silicon verification is pending.

Devin uses your native billing and data policies, including its local session records and provider analytics. **Keep local history** controls Sotto's copy only. Review your account's training and retention controls. See [the data-policy decision](adr/0017-devin-native-provider-data-policies.md).

The first release requires Sotto's verified approval profile. It refuses project-native Devin configuration, hooks, installed plugins, enabled MCP servers, and incompatible effective settings. It does not edit your global configuration. A permission shows its action before **Allow once** or **Deny**; a request cannot be answered for the rest of the session or for good. What Devin may do without asking at all is the thread's permission setting, below. Unsupported request forms stop the session safely. Reconnect after resolving the reported incompatibility.

Choose the model when creating the thread. Later model changes, images, skills, compaction, steering and native slash commands are unavailable. Permissions are not: a Devin thread offers Devin's own modes plus **Ask first**, which is Devin writing code while Sotto asks about everything. Only the modes Devin reports are offered. Each says what Sotto will still ask about under it, because what Sotto asks is decided by its own profile and not by the mode's name. Threads start on **Ask first** and keep it until you change it; changing it stops that thread's session and resumes it under the new profile on your next action, and a change is refused while the thread is working. See [the permission-mode decision](adr/0022-devin-permission-modes-are-owned-profiles.md). Devin is a thread provider; it is not a terminal launcher or a coordinator reasoning account.

Devin saves a native session after its first prompt. Sotto may renew the native handle of a confirmed, untouched empty thread after a clean shutdown, retaining its Sotto identity and chosen model. A dispatched, uncertain, missing, or crashed session is never silently replaced. If Devin is killed before its first clean shutdown, it can reload with a different model. Sotto keeps the original model and refuses to continue; restore that model in Devin and reconnect, or start a new thread. A session open in another native client must be released before Sotto can resume it. Separately authored native messages transfer it to manual control when replayed.

## Working with threads

A **monitoring task** is a provider-confirmed live watch, shown by the pixel creature above the thread composer. It works in manual and managed threads, including with the voice coordinator hidden. There is no elapsed-time threshold. Ordinary commands, long foreground work and unattended background processes do not qualify; short confirmed watches can appear briefly. The indicator is observational and cannot approve or send anything. It disappears for a pending question or permission, an error, a closed thread, interruption, disconnect or task completion. System or app reduced motion holds a still inspection pose.

Claude Code clients that emit native `task_started` events with `task_type: monitor` or `monitor_mcp` supply this evidence. Task progress and status updates refresh it; terminal statuses and end times clear it. Nested subagent, ambient and transcript-only tasks do not qualify. The adapter maps native task IDs to ephemeral Sotto IDs and does not restore monitoring from transcripts or cached threads. An active confirmed monitor keeps its Claude session alive so the idle reaper cannot abandon it. Codex terminal-interaction events do not identify a bounded monitoring interval; Codex, Grok Build and Devin therefore publish no inferred monitoring state.

**Background work** is the same creature's third pose: agent work started from the thread that the provider says is still running, read as **Working**. Claude Code supplies it with `task_started` events whose `task_type` is `local_workflow`, `local_agent`, `in_process_teammate` or `remote_agent`, at the root of the thread under the same ownership rules as a monitor, plus `owned_by_subagent` and a `spawn_depth` above one, which exclude agent work but not a monitor. A `local_agent` started with `is_backgrounded: false` is the turn's own blocking action and stays with the held action until a `task_updated` patch moves it to the background. The matching `task_notification`, a terminal status or an end time ends it; the turn's `result` does not. Interrupt, an error result, a disconnect, a process exit and a session restart clear it, it keeps its session from the idle reaper, and like monitoring it is never read from transcripts or restored from cached threads. The composer shows one creature: a monitoring task first, then background work, then a held action.

The **Threads** page lists threads across providers. Create a thread with its project, model and available options; open one to read messages, type a prompt or answer an outstanding request. Native adapters recover threads created by Sotto; they do not import unrelated conversations from your coding clients. Creating a new thread in a settled project returns the folder to the active sidebar with only the new thread; older threads stay in Settled.

Creating a manual thread leaves any saved coordinator prompt or answer with its original thread. That draft does not block **New thread**, including while the voice coordinator is hidden. Creating a managed thread still requires sending or clearing the current coordinator draft first.

Connecting a provider does not start a session for every thread it knows. Saved threads appear in the list straight away, idle, and a thread's provider session starts when you open it or act on it: the first prompt, answer, interrupt or settings change starts it before the action goes out. A session left alone for half an hour is stopped again, which you cannot see from the app: the thread keeps its place and its messages, and the next thing you do starts it again. A thread that is on screen, assigned or waiting on a queued prompt is the watched set, and its session is kept; one running a turn or holding an unanswered question is never stopped.

Disconnecting one provider leaves other providers usable and keeps its thread identities, saved draft and assignments. Its thread controls wait until that provider reconnects. Turning off agent control stops coordination and voice control while leaving native thread connections available. Connecting a provider does not turn the coordinator back on.

An interrupted Codex settings change is checked on reconnect without replaying its overrides. If Codex reports different settings, the provider stays connected and the thread remains readable. Choose that thread's settings again before sending. The unresolved change stays saved until Codex confirms a choice; a rejected replacement keeps the earlier unresolved change. Other threads remain usable.

A manual composer remains available when another thread owns a saved coordinator draft. You can prepare the next prompt while the current turn runs; sending waits for that turn to finish. Pressing send empties the composer and shows the message in the transcript at once, with its own state: **Queued**, **Sending**, **Unconfirmed** or **Not sent**. A prompt written while the thread is working joins the follow-up queue and is shown in both places until it is dispatched. It becomes a normal message when the provider's history carries it. **Unconfirmed** means Sotto has not established delivery; reconnecting or retrying reconciles the earlier action without automatically sending it twice. A refused prompt returns to the composer when nothing newer is written there, and is offered back with **Restore prompt** when something is. Per-thread composer drafts are saved locally with revision and delivery state for restart recovery. Recovery keeps the draft bound to its original thread and does not send it automatically.

New threads inherit the native subscription and model selected in Settings > Agents, or its account default when no model is selected. An unavailable inherited model remains selected; connect it or make an explicit choice in Thread options. Old separate thread defaults are ignored. With no native Agents subscription selected, an available native thread provider remains the starting choice. An explicit model choice and the choices restored after failed creation do not change when settings or provider catalogs update.

New threads use the project folder unless a global or project default selects a new worktree. Threads using the same folder share its unfinished edits and branch. The choice for one thread is made under its composer, on the **branch toolbar** (ADR-0027): **Workspace** offers **Current checkout**, **New worktree** for agents that need to work separately, and **Previous worktree** for a worktree another thread of the project already has, and locks once the thread has a message. For a new worktree the **branch picker** records the branch it starts from and its **Start from origin** switch says whether that branch is fetched first; the checkout is created on first send, a failed fetch stops setup so you can choose another source, and uncommitted project edits are not copied. For a folder that exists the picker searches the repository's refs and checks out the one you pick, `git checkout <ref> --`, with `--track` for a remote ref that has no local branch; a ref checked out in another worktree re-points a draft at that worktree; **Create new ref** makes a branch from HEAD; Git's refusal is shown under the row. **Run on** names the machine the thread runs on. Shortcuts: the picker on `mod+shift+g`, Workspace on `mod+shift+x`, the first Previous worktree on `mod+shift+l`, each left unclaimed when the dictation hotkey uses the same keys. Thread options in New thread holds the name, model, reasoning and permissions; the collapsed summary shows the current choices. Working-copy defaults for each project are in Settings > Application > Project defaults. Opening an empty thread creates no worktree. Existing provider sessions keep their original working directories.

The **Git action** sits at the end of the pane header (ADR-0027). Its label follows the folder's Git status and a press does what the label says: **Commit**, **Commit & push** (on the default branch or with an open pull request), **Commit, push & PR**; **Push** or **Push & create PR** for commits not yet pushed; **Pull** when the branch is behind (fast-forward only); **Create PR** for a branch ahead of the default one; **View PR** when one is open; **Publish repository** for a repository with no remote (GitHub, through `gh`); **Initialize Git** for a folder without Git. It is disabled with T3's reason when there is nothing to do, when HEAD is detached, or when the branch has diverged. The chevron beside it lists Commit, Push and Create PR or View PR, each disabled with its reason, and Publish repository while the repository has no remote. A commit opens **Commit changes**: the branch with a **Default branch** tag, the changed files with their line counts (Edit leaves files out), **Commit message (optional)** that the thread's own provider writes when left empty, and **Cancel**, **Commit on new branch** and the action. A push or pull request from the default branch asks **Push to default ref?** first: **Abort**, **Push to main**, or **Check out feature branch & continue**, which cuts a branch from HEAD, named after the commit, and continues on it. While the action runs, one notice above the composer shows its stage and the hook running; when it ends it shows the result with the next step (**Push**, **Create PR**, **View PR**), or **Action failed** with the host's words, until dismissed. Nothing is forced, merged or rebased. The Git actions drawer inside Changes is gone; Checkpoints stays there.

**Changes** in Tools is T3's diff panel (ADR-0027). Its scope menu offers **Working tree** (the working copy against HEAD, untracked files included, read through a copy of the index so the real one is never touched), **Branch changes** (`base...HEAD`; the base picker starts at **Automatic** and lists each branch once, in **Branch** and **Remote** columns, with **Use remote version** where both copies exist and a **Remote only** mark where only the remote one does), **Latest turn** and **Turn N**, read from Sotto's checkpoints rather than Git. A turn whose checkpoint is unavailable says so with the reason. The line of chrome shows the comparison's `+adds −dels` and **Refresh diff**; the bar under it holds **Expand all files** / **Collapse all files**, **Stacked diff view** and **Split diff view**, line wrapping, **Hide whitespace changes** and the file tree, which stands beside the files in a wide panel and above them in a narrow one. Each file is a block with its status, counts and **Copy path**; its name opens it in Files. **Diff layout**, **Hide whitespace changes** and **Default diff file state** in **Settings → Git** set where Changes starts. A choice made here holds until one of those settings changes or Sotto restarts. There is no staging: **Stage file**, **Unstage file** and the staged and unstaged comparisons are gone, and the commit dialog's file list is the choice. `mod+d` toggles Changes, or `mod+shift+d` when the dictation hotkey holds `mod+d`; focus inside a terminal keeps its own Ctrl+D.
T3's Git settings are in **Settings → Git**, grouped under when each acts (When a thread commits, When a pull request is made or merged, When you read Changes, In the background), read by the host that owns the thread (a remote host reads its own `settings.json`). **Automatically pull** (off) runs the Pull above on its own when a read of the remote finds the folder on the default branch, clean and only behind, and leaves a folder any thread is working or waiting in for the next read. It shows no notice: the pull shows only as the status changing, a Git action pressed on the same thread waits for it, and one pressed from another thread in the same folder is refused with **Sotto is pulling this folder. Try again in a moment.** **Auto-settle merged threads** (off) settles a thread at rest whose last-sent branch's pull request GitHub reports merged, on the worktree cleanup's hourly sweep through `gh`, once per thread and branch while Sotto runs; the on-settle cleanup rule, when on, then decides about the folder. **Proactive panels** (off) opens Changes on a closed, unpinned Tools panel when a turn leaves its folder with at least 3 more changed files or 50 more changed lines, leaving keyboard focus where it was. It compares the working copy's counts before and after the turn, not the turn's own diff, and counts only while the Threads page is open; a large turn in a pane not in focus waits until its thread is focused, and is let go once Changes has been opened for it. **Diff layout**, **Hide whitespace changes** and **Default diff file state** are where Changes starts, as above. **Default merge method** is the method the pull request checklist's merge starts on, read through `useMergeMethod`; under Last selected, a method picked beside that Merge is saved as the one to start on next. **Commit and pull request style** (Repository conventions, Conventional Commits, Custom instructions) adds its instruction to the commit message and pull request requests; the last two take precedence over the example, the recent subjects and what `AGENTS.md` says about style. **Follow pull request templates** (on) decides whether the thread's own model is given the repository's pull request template to follow when a Git action drafts a pull request: the first template file in GitHub's usual places, or the only one in a `PULL_REQUEST_TEMPLATE` folder.

The branch's pull request is a Tools surface, **Pull request** on the rail, its tile reading PR (ADR-0027). The badge on the branch toolbar opens it; it shows the branch's pull request, else the one linked last, read from GitHub through the host's `gh` when it opens and on **Refresh**, as the **merge checklist**: **Checks passing** (the first failing check named, with **Open check**), **Review approved** (who approved, or who asked for changes, with **Open review**; "No review required" where the repository asks for none), **Up to date with** the base (with **Update branch**), **No conflicts**, and **Ready for review** (with **Ready for review** for a draft). One large **Merge #N** is enabled only when no line holds it back, in the method beside it (Merge commit, Squash or Rebase), which starts on the Default merge method setting (#271); otherwise the hint counts the lines left and offers **Merge when ready**, GitHub's auto-merge, where the repository allows it. An armed auto-merge shows **Turn off**, a closed pull request **Reopen**, and a merged one when it merged. The description and **Linked pull requests** fold below. The ··· menu holds **Convert to draft** or **Ready for review**, **Update with rebase**, **Merge when ready (auto-merge)**, **Disable auto-merge**, **Copy link**, **Link pull request**, **Unlink from thread** and **Close pull request**; **Open on GitHub** and **Refresh** sit beside it. The merge, turning on auto-merge, closing and **Update with rebase**, which rewrites the branch on GitHub and leaves a local copy behind, ask first; nothing happens from viewing, and the host acts only on the branch's pull request or one linked to the thread. **Linked pull requests** lists the thread's links (created by its Git action, linked by you, or checked out) with the branch's own, and **Link pull request** takes a GitHub URL or `#42`. With no pull request yet the surface offers **Create PR**, which runs the Git action's own Create PR under the same rules, and Link pull request. In the branch picker, a pull request URL, `#42` or `gh pr checkout` line offers **Checkout pull request**, which takes only a pull request of the project's own origin repository. **Local** runs `gh pr checkout` in the thread's folder without forcing, and says first when it moves a draft set to a new worktree into the project checkout; and **Worktree**, for a thread that has not started, fetches the pull request's branch for the new worktree its first send makes. All of it runs on the thread's host, so a paired host's thread works the same way.

A **review comment** (#270) is T3's way of saying something about lines of Changes. Click a line, Shift+click to take more, and press **Comment**, or press a line number to comment on that line; the draft opens under the lines (**Add a comment…**, **Cancel**, **Comment**; Escape cancels, Ctrl+Enter adds). The comment becomes a chip on that thread's composer, named `file L12 to L20` from the new file's numbers or `file L4 to L5 (before)` when every line was removed, and a marker under its last line with **Delete comment**. A file's lines are one stop in the Tab order, followed by the Comment button and each comment's controls where they are drawn: the arrow keys, Home and End move, Shift extends, Space picks a line, Enter opens a draft on what is picked, and Escape lets go. The next prompt, queued follow-up or steer carries every comment as text after the user's message, so every provider reads the same thing:

````text
Tighten this before we merge.

Comment on `src/main/voice.ts L12 to L13`:

Say why it returns early.

```diff
+  if (!key) return { ok: false }
+  const clip = await speak(v, SAMPLE, 2)
```
````

A comment keeps its lines as they read when it was written. If the diff moves on, the comment still goes with those lines; its marker moves to the end of the file and says the lines have changed since, until the comment is sent or deleted. A line only past the first 3,000 rows drawn says to Show all instead. A comment on lines the comparison does not draw (its file committed or outside the scope, a mode or rename only, or a comparison that could not be read) is listed after the files under **Comments on lines this comparison does not show**, with Delete comment; a draft with words whose lines are not drawn is listed there too, so it can be finished or cancelled. An answer to a question does not carry comments; the composer says they wait for the next prompt. A message carries at most 20. Comments live in the window's memory for its thread until sent or deleted. They are never saved as comments and never reach a log; once written into a prompt they are part of its text, saved and sent as any prompt is.

The first prompt can give a new worktree's short temporary branch a descriptive name, written by the thread's own provider in a side call that never enters the thread (ADR-0026). Generated thread titles and Keep local history must both be on, and a Devin thread keeps its temporary name. The request runs in the background, never renames a branch the agent or user already changed, and leaves the turn running if naming fails.

The branch label is re-read after relevant work, when you start typing and when the window regains focus. Only a thread using the shared project folder shows **Branch changed** when its current named branch differs from its last send. The notice waits for a draft; sending continues on the current branch, **Restore branch** switches back after confirmation if changes are uncommitted, and **Dismiss** lasts for that branch pair through pane switches in the current app session. Worktree-backed threads do not show this notice. A missing Sotto-created working folder is put back on its recorded branch when possible before the next send; an occupied branch or invalid folder binding is reported without resetting or removing work.

Choose **Manage** to authorize supervision. **Pause managing** suspends automatic follow-ups. **Stop managing** removes the assignment without cancelling native work. Automatic follow-ups are limited to five by default and pause sooner on repeated failure without progress. New scope, human decisions, spending and permissions require the user's decision unless already authorized.

Questions and permissions on a thread with an assignment (managed, paused or taken over) enter the attention queue with their project and thread; a question on a managed thread waits outside it while supervision decides whether to answer. On any thread, with an assignment or not, the sidebar row reads **Needs your answer** or **Needs your approval** with its ring while a request is pending, from the queue item when there is one and otherwise from the thread's own requests, and the collapsed rail says the same in its title. **Next** and **Later** defer attention without answering. A composed answer stays bound to its question. Explicit **Allow** or **Deny** returns that decision to the native provider; skipping never approves. Unsupported interactive forms must be handled in the native client. Native hooks and permission settings still apply. Sotto claims each session's approval surface at launch, in every permission mode, so the requests only you can answer arrive here rather than being answered by the client. A client that refuses the surface, or that asks for you in a form the adapter cannot read, declines those requests itself while the thread keeps working, so the provider carries a plain-words error naming the client to update. See ADR-0021.

In a thread pane, pending questions sit above the composer. Structured choices are stacked and preserve the provider's IDs, multi-select rules, optional fields and unavailable fields. A provider label ending in `(Recommended)` is shown with a separate `(recommended)` marker; Sotto does not infer a recommendation. A custom-answer box is visible when free text is allowed. Typing selects that answer, but only **Send answer** submits; Enter adds a line. Changing choices retains the custom draft without including it in a different answer. Escape or the collapse control hides the form without discarding it. Structured forms and legacy option selections use the same saved-answer recovery and uncertain-delivery checks. Restarting restores a prepared legacy choice without sending it; a changed question keeps its old answer separately for recovery. Permission requests remain in the transcript with their native approval choices.

Every answered request leaves a record in the thread's own history saying which client answered it, and whether a follow-up came from Sotto's supervision rather than from you. The record holds the request, the choice and the client; it never holds the words of the answer, because an answer can read like a prompt. Today the only client is this app's window on this computer. The permission interface has no remote listener or paired clients. The thread browser uses a separate authenticated loopback MCP endpoint that exposes browser tools, never permission answers.

Sending directly through the same native provider session transfers that thread to manual control when its authored message is observed. Sotto continues monitoring and stops automatic replies. Reading or opening the native session is not takeover. Say “resume managing Workshop” or choose **Resume management** to authorize supervision again. Missing or locked native history can delay detection.

The composer’s effort chip opens the effort card: the level word, one line saying what the level costs, a Default button when the model reports a default, and a pill track with a stop for each level the model reports. Dragging previews the level and settles toward a stop; releasing saves it. The wheel over the track, the arrow keys, Home, End and the digits 1..N step; Escape, Tab out or a pointer outside closes the card. Failed saves restore the previous level. At the model’s highest level the word, the chip and the composer’s outline take the effort color chosen in **Settings → Appearance**, and reaching it plays the arrival once; reduced motion shows the settled state (ADR-0019). Claude’s Ultrathink action adds a visible instruction to the editable draft and follows that draft through sending or retry. It does not change the saved reasoning effort. Ultracode is not offered because the adapter cannot confirm workflow availability.

Model, effort, image and permission-mode controls reflect the adapter's verified capabilities. Paste, drop or attach screenshots with Codex models that accept images or with Claude Code. Screenshots can be sent alone, alongside text or in a queued follow-up. Codex also accepts screenshots when steering a running turn. Unsupported controls are unavailable. Grok currently selects model and effort at thread creation and does not support existing-thread configuration. The native client Sotto verified, Grok CLI 1.0.5, reports no image input through ACP, so screenshot attachments remain unavailable even when the underlying Grok model supports vision.

While a thread is running, **Steer now** beside a queued message sends that message into the current turn when the provider supports steering. The rest of the queue and any newer composer draft stay in place. An unconfirmed message cannot be steered again; use **Check again** to reconcile its delivery.

## Upgrading an older installation

An installation configured for the retired intermediary host is migrated before its saved state is interpreted as a native configuration. Sotto disables automatic connection, retains the draft and attachments without their old target, and preserves recovery evidence separately. Old assignments and uncertain actions are not transferred to a native provider or replayed. Existing thread bindings remain historical identities, never relabelled as native sessions.

The upgrade notice identifies the local recovery record. Check the original coding client before reusing a draft whose previous delivery was uncertain. A recovered answer is not permission to submit it to a new thread. Choose a native provider and explicitly prepare any new work. Installations already using a native provider keep their selection and recovery state.

## Data and accounts

Coding and reasoning usage belongs to the selected provider account. Sotto membership pays for coordination features and does not include model usage. Sotto never enables overages, buys credits or changes accounts automatically. Native clients retain subscription authentication; Sotto-owned API keys use the operating system's encrypted credential store. A locked vault reports an error without storing plaintext credentials.

Sotto stores thread bindings, assignment ownership, counters and dispatch identities locally. Assignment context expires after seven days without activity. **Keep local history** off suppresses supervision and clarification text. An unsent draft is the explicit exception: it remains local until sent or cleared. Recovery evidence follows the same history and expiry policy. Background audio and full native transcripts are not copied into coordinator state.

A thread's messages are Sotto's own record, kept in an event store rather than rebuilt from the provider each time Sotto starts. Each adapter appends only what is new to it — Claude from its transcript tail, Codex from the app-server stream and its rollouts, Grok from its update cursor, Devin from UUID-tagged native replay — and a thread nobody is looking at carries its summary rather than its history. A pane reads the newest ten turns from Sotto's event store and reads further back when you ask for earlier messages. A provider session starts when a thread is opened or sent to rather than at connect. Claude Code runs a process per thread, so when one ends on its own only that thread is affected: the provider stays connected, a running reply is marked failed with a line saying it may be cut short, lost background work leaves the thread needing attention, and the provider session resumes the next time the thread is opened or sent to. Nothing is resent. Devin separately replays native history to resume and confirm delivery, so a longer native thread can take longer to reconnect or send to. Replay is limited to 16 MiB of text and 20,000 messages; if it exceeds the limit, Sotto keeps saved history readable but refuses further native reconciliation or sends. It never resends uncertain work automatically. **Keep local history** off still means no message text is written at all, and turning it off removes what was written; what was not kept cannot be recovered. See ADR-0016.

Coordinator actions append bounded turn records containing timings, acted-on thread/project IDs, retrieved memory IDs, context estimates and outcomes. Draft edits are not turns. With local history off, message and error text are blanked while timings and identities remain. Developer builds can reveal the turn-record folder from the tray menu. Voice timing reports identify measured software milestones separately from acoustic output.

## Reported subagents in Tools

Choose **Agents** in Tools to inspect the focused thread's subagents. The roster, its details and its working indicator always belong to that thread. Pinning another working copy holds Browser, Terminal, Files and Changes there; it does not redirect Agents. A row shows the provider's task title, a brief task preview, the model the agent ran on, status and elapsed time when available. Expand it for the task, result and earlier assignments. Nested children follow their reported parent; siblings keep their spawn order. Claude Code does not stream a model for a workflow or a background agent, so Sotto reads it from the first reply in that agent's own transcript and nothing else from it; a workflow row lists up to four models its agents ran on. A model nothing names reads **Model not reported**. Providers without child observations show an empty view.

The dot above-left of the outside Tools icon appears only for confirmed working agents in its thread or a browser request waiting for your answer in the current or pinned working copy. It does not open Tools, switch its surface or grant permission. Inside Tools, the rail marks **Agents** with the same kind of dot while agents work, and says how many in words. A pinned thread remains observed even after its conversation pane closes. Disconnecting or restarting changes unfinished agents to **Last seen working** and freezes the clock until activity is confirmed.

Agent and assignment history uses bounded pages, independently of ordinary transcript activity. It follows **Keep local history**. There are no child command controls or full child transcripts in this view.

## Browser tasks in Tools

The browser stays in **Tools > Browser**. An agent browser task on the focused thread, or on the thread Tools is pinned to, shows a small page preview in the app corner; another thread's task waits in its own pane and in Tools. Open the preview to pin Tools to that task's thread and page while keeping your current conversation. **Dismiss preview** hides the thumbnail; **Pause** stops further browser actions. **Show browser previews** in Settings turns the preview off; the work carries on and Tools > Browser still shows it. A request waiting for your answer puts a dot on the Tools icon of the pane showing its thread, on **Browser** in the Tools rail and on its page tab in Tools > Browser. A thread with no open pane has no such mark: its request waits in Tools > Browser until you answer it or it expires. Finished tasks retain their summary, observed steps, screenshots and unchecked cases for the current app session.

Codex, Claude Code and Grok project threads receive Sotto browser tools through a thread-bound local MCP connection. The pinned Devin client does not support this connection; its browser remains available for manual use and draft feedback. The agent must use the URL of the app it actually started in that thread's working copy. It can inspect a shared page, read bounded console and network errors, scroll, change the viewport and capture screenshots. Opening a page, navigating, clicking and typing wait for your one-time answer in Sotto. A request to open a page also offers **Allow this thread to open pages**: that page opens, and the thread's later opens and navigations run without asking, shared the way Open and share shares a page, until you press **Stop** on the line Tools > Browser shows for it, the thread goes away or Sotto closes. Clicks and typing still ask every time. Reaching the browser is not one of those answers, so the provider does not ask its own question first; the answer that matters is the one you give in Sotto. Where a client asks anyway, the request says which page it would open or what it would do there, and answering it only lets the agent reach the browser. Grok reaches the browser through a tool of its own, and Codex asks about it as an app tool; both are read back to you the same way. The agent cannot answer those requests. Pausing, revoking sharing, closing the page or changing its context invalidates outstanding actions. A timeout never grants permission.

A page you open yourself stays private from the agent until you choose **Share with agent**. Sharing allows observation of that origin; it does not preapprove clicks or typed text. Revoking removes retained page observations. Browser page grants and task evidence are temporary and disappear when Sotto closes. Tool output may also be retained by the native provider under its own policy.

Use browser feedback to select an element or region and add a comment. The URL, selected context and screenshot go into that thread's editable composer draft, preserving existing text. Nothing is sent automatically. Image support follows the selected provider's capabilities; unavailable attachments are explained before adding the draft. Browser results report what the agent observed and what it left unchecked. They do not establish that the native desktop app or an unvisited flow passed.
