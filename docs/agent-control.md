# Sotto agent control

Sotto opens coding threads and routes manual commands through the installed Codex, Claude Code, Grok Build, Devin, Muse (ADR-0079) and OpenCode 2 (ADR-0087) clients. Threads have Sotto-owned identities; each native client keeps its own sign-in, model catalog and conversation history. The providers can be connected together. You send prompts, answer requests and stop work from each thread. Explicit pull request babysitting can send wake-ups but answers no request.

## Set up

1. Install and sign in to your chosen native coding client. Codex uses App Server, Claude Code uses stream-json and Grok Build uses ACP. Grok connection requires CLI 1.0.5 or newer and ACP 1; an older client produces an error before creating a session. Devin requires 3000.11.92 or newer. Sotto reports each connected client's version in Settings → Providers, with what its channel publishes (ADR-0042). Sotto finds a client on PATH, on your login shell's PATH, in `~/.local/bin`, where a version manager (mise, asdf, nvm, fnm, Volta, Homebrew) installed it, or in npm's global folder; the [guide](guide.md#providers-and-models) has the order (ADR-0036).
2. Open **Settings → Providers**. Select Codex, Claude Code, Grok Build, Devin, Muse or OpenCode in the list, then connect or enable it. **Connect providers** on the Threads page turns on and connects every client installed on this computer, Devin included, and leaves a provider you turned off as it is. The default stays as it is while its client is installed; otherwise it moves to the first of Codex, Claude Code, Grok Build and Devin that is. Each row has its own status and switch; Configuration holds connection controls and a default model choice, while Models shows that provider's catalog. No server address or pairing token is needed. A headless host has no Providers page: it connects every client that is installed and signed in on its machine when it starts, except one you disconnected through it (ADR-0036).
3. A thread in a project opens at once, on the model, reasoning effort and permission chosen in **Settings → Threads**' **New threads start with** row; change any of them for one thread from its own composer once it is open. That choice determines which client runs the thread. The same working folder can be used with different providers. Existing threads retain their provider; their model picker only offers models from that client. Unavailable models are reported rather than replaced.
4. Open **Settings → Threads**, directly below Hosts, to configure new-thread defaults and the default projects directory. The defaults are this computer's and apply on every connected host. Each computer has its own projects directory, so with a host connected the page lists one for each. Saved native subscription accounts still resolve the inherited model for new threads. Dormant reasoning and automatic-coordinator controls are hidden.

### Devin

Install Devin CLI 3000.11.92 or newer and run `devin auth login` outside Sotto. Enable Devin in Providers, connect, and select a model returned by your account. No new API key is stored in Sotto. Devin uses ACP 1 and performs its own tools in the selected local checkout. Windows native verification is recorded; Apple silicon verification is pending.

Devin uses your native billing and data policies, including its local session records and provider analytics. **Keep local history** controls Sotto's copy only. Review your account's training and retention controls. See [the data-policy decision](adr/0017-devin-native-provider-data-policies.md).

The first release requires Sotto's verified approval profile. It refuses project-native Devin configuration, hooks, installed plugins, enabled MCP servers, and incompatible effective settings. It does not edit your global configuration. A permission shows its action before **Allow once** or **Deny**; a request cannot be answered for the rest of the session or for good. What Devin may do without asking at all is the thread's permission setting, below. Unsupported request forms stop the session safely. Reconnect after resolving the reported incompatibility.

Choose the model when creating the thread. Later model changes, images, skills, compaction, steering and native slash commands are unavailable. Permissions are not: a Devin thread offers Devin's own modes plus **Ask first**, which is Devin writing code while Sotto asks about everything. Only the modes Devin reports are offered. Each says what Sotto will still ask about under it, because what Sotto asks is decided by its own profile and not by the mode's name. Threads start on **Ask first** and keep it until you change it; changing it stops that thread's session and resumes it under the new profile on your next action, and a change is refused while the thread is working. See [the permission-mode decision](adr/0022-devin-permission-modes-are-owned-profiles.md). Devin is a thread provider; it is not a terminal launcher or a coordinator reasoning account.

Devin saves a provider session only after its first prompt, so an empty provider session ends with the Devin process that made it. A thread with no messages, which Sotto has never sent to, gets a new provider session when Devin reports its old one missing, keeping its Sotto identity, model and permission setting; there is nothing to resend. A thread with any message is never silently replaced: a missing provider session there is an error on that thread. One thread that cannot be opened does not stop Devin connecting; the others stay usable. If Devin is killed before its first clean shutdown, it can reload with a different model. Sotto keeps the original model and refuses to continue; restore that model in Devin and reconnect, or start a new thread. A session open in another native client must be released before Sotto can resume it. Separately authored native messages remain visible when replayed and prevent a prepared reply to an older message from being sent.

## Working with threads

An uncertain direct prompt on this desktop offers **Continue with a new message**. It saves the choice to set that exact send aside without claiming delivery or replaying it. A new manual prompt can then go, while the old command and message identities remain available for deduplication and exact native confirmation. Confirmation of a new explicit prompt in that thread releases normal automatic updates, including after a restart. A rejection, uncertain new send or answer to a request does not release them. The old prompt remains unconfirmed and cannot be replayed. Setting it aside changes no question, permission or follow-up queue entry.

A **monitoring task** is a provider-confirmed live watch, shown by the pixel creature above the thread composer. It works in threads independently of dictation. There is no elapsed-time threshold. Ordinary commands, long foreground work and unattended background processes do not qualify; short confirmed watches can appear briefly. The indicator is observational and cannot approve or send anything. It disappears for a pending question or permission, an error, a closed thread, interruption, disconnect or task completion. System or app reduced motion holds a still inspection pose.

Claude Code clients that emit native `task_started` events with `task_type: monitor` or `monitor_mcp` supply this evidence. Task progress and status updates refresh it; terminal statuses and end times clear it. Nested subagent, ambient and transcript-only tasks do not qualify. The adapter maps native task IDs to ephemeral Sotto IDs and does not restore monitoring from transcripts or cached threads. An active confirmed monitor keeps its Claude session alive so the idle reaper cannot abandon it. Codex terminal-interaction events do not identify a bounded monitoring interval; Codex, Grok Build and Devin therefore publish no inferred monitoring state.

**Background work** is the same creature's third pose: agent work started from the thread that the provider says is still running, read as **Working**, or a shell command it sent to the background. Claude Code supplies it with `task_started` events whose `task_type` is `local_workflow`, `local_agent`, `in_process_teammate`, `remote_agent` or, for a command, `local_bash`, at the root of the thread under the same ownership rules as a monitor, plus `owned_by_subagent` and a `spawn_depth` above one, which exclude agent work but not a monitor. A `local_agent` or `local_bash` started with `is_backgrounded: false` is the turn's own blocking action and stays with the held action until a `task_updated` patch moves it to the background. The matching `task_notification`, a terminal status or an end time ends it; the turn's `result` does not. Interrupt, an error result, a disconnect, a process exit and a session restart clear it, it keeps its session from the idle reaper, and like monitoring it is never read from transcripts or restored from cached threads. A command waits rather than works: once the turn has ended it holds the hourglass, named by its description, and reads **Waiting**; beside agents it is only counted, *Working · 2 agents · 1 command*. The composer shows one creature: a monitoring task first, then background agents, then a held action, then a background command.

The **Threads** page lists threads across providers. Create a thread with its project, model and available options; open one to read messages, type a prompt or answer an outstanding request. Native adapters recover threads created by Sotto; they do not import unrelated conversations from your coding clients. Creating a new thread in a settled project returns the folder to the active sidebar with only the new thread; older threads stay in Settled.

Creating a thread leaves any saved prompt or answer with its original thread. That draft does not block **New thread**. The one way a coordinator draft leaves its thread is when that thread is no longer listed: with no pane open, the Threads page offers it as a leftover draft, and **New thread with this draft** moves its words and images into a new thread's composer. The coordinator's copy is cleared only after main confirms that composer is saved, so the draft is never held in neither place.

On iPhone, **New thread** chooses a connected computer, a project or an existing folder on it, then its model and effort. **Browse another folder** lists directories on that computer; **Use this folder** attaches it as a project when needed. The thread uses the shared project folder and its own composer. Its initial permission mode asks before actions; a more permissive choice needs this iPhone's **Can answer** policy there. Send the first message to start work on the chosen computer. An unconfirmed creation stays visible on Threads and is never sent again automatically.

Connecting a provider does not start a session for every thread it knows. Saved threads appear in the list straight away, idle, and a thread's provider session starts when you open it or act on it: the first prompt, answer, interrupt or settings change starts it before the action goes out. A Devin permission change is the exception: it waits for the thread's next action. Typing in a thread's composer starts its session as well (an early start, ADR-0057), so the send that follows does not wait for it; for a new thread it starts only the client that thread's first send will use, and creates nothing until you send. Claude Code's client runs in the thread's folder, so a new thread getting its own worktree, which the first send makes, gets none from Claude Code; Codex and Grok Build start theirs for it, and Devin starts nothing for a new thread. When that new worktree starts from origin, typing also fetches its base branch, so the send need not; the send uses that fetch for two minutes after it finished, and fetches again after that or after a failure. With the Git fetch interval Off, typing fetches nothing. A send made without typing, from the follow-up queue or babysitting, still starts a stopped session inside the send. At connect, Claude Code starts the watched threads' clients four at a time rather than one after another. A session left alone for half an hour is stopped again, which you cannot see from the app: the thread keeps its place and its messages, and the next thing you do starts it again. A thread that is on screen or waiting on a queued user prompt is the watched set, and its session is kept; one running a turn or holding an unanswered question is never stopped. Reading a quiet session's history does not restart its idle wait. A read already in progress finishes before the session is stopped.

Disconnecting one provider leaves other providers usable and keeps its thread identities and saved drafts. Its thread controls wait until that provider reconnects. Connecting a provider does not send a prompt.

A settings change goes to the provider without reading the thread first. The provider checks that the thread is idle and has no pending request before it changes anything. When it confirms the change, the settings it reports are the thread's settings in Sotto; Sotto reads the thread again only when the provider's adapter has no such answer to give. A change the provider does not confirm stays saved as unconfirmed and is reconciled against what the provider reports next, never sent twice. One that sets only a model or an effort holds nothing back meanwhile: the thread still sends, runs its queued follow-ups and takes another change, and a newer choice of the same setting replaces it. One that sets a permission mode or a provider mode still holds the thread until it is reconciled, since a turn under a wider mode than you chose could act without asking. See the amendment to [ADR-0007](adr/0007-native-thread-retirement-and-refresh.md).

A Claude Code model, effort or permission change goes to the thread's running session over its control channel, so the session carries on: its transcript, its watches and any background work. The chip shows the change once Claude Code confirms it. Sotto starts the session again with the new settings instead when none is running, when Claude Code refuses the change, and when the thread enters or leaves full access, which Claude Code allows only from launch. That restart is the one path that waits for background work; the change is refused and nothing changes. A model change takes the level you choose with it, or the new model's own default when you choose none. A change whose answer is lost stops the session, so nothing runs on settings the thread does not show; the next start carries the change, and the thread shows it from then. Stopping the session ends any background work it was running, so the thread shows an error and the message names the work that stopped, for you to start again if you still need it. The same happens if Claude Code takes part of a change, refuses the rest and will not undo the part it took while background work runs. A new session never starts while the one Sotto stopped is still exiting. See ADR-0023.

An interrupted Codex settings change is checked on reconnect without replaying its overrides. If Codex reports different settings, the provider stays connected and the thread remains readable. When the change set a permission or provider mode, choose that thread's settings again before sending; a model or effort change holds nothing back. The unresolved change stays saved until Codex confirms a choice; a rejected replacement keeps the earlier unresolved change. Other threads remain usable.

A manual composer remains available when another thread owns a saved coordinator draft. You can prepare the next prompt while the current turn runs; sending waits for that turn to finish. Pressing send empties the composer and shows the message in the transcript at once, with its own state: **Queued**, **Sending**, **Unconfirmed** or **Not sent**. A prompt written while the thread is working joins the follow-up queue instead, and is shown only there, above the composer, until the provider's history carries it; the transcript never draws it twice. A **wake-up** that has to wait joins the same queue after your prompts, as Sotto's own item: it can be removed but not edited or steered, later news about the thread's pull requests folds into it, and it goes when the queue would send the next item (ADR-0061). It becomes a normal message when the provider's history carries it. **Unconfirmed** means Sotto has not established delivery; reconnecting or retrying reconciles the earlier action without automatically sending it twice. A refused prompt returns to the composer when nothing newer is written there, and is offered back with **Restore prompt** when something is. Per-thread composer drafts are saved locally with revision and delivery state for restart recovery. Recovery keeps the draft bound to its original thread and does not send it automatically.

When main refuses a new thread with content to recover, the sidebar error says what is kept and names the project to open **New thread** in. Its submitted prompt, newer typing and screenshots stay in the window for the next **New thread** in that project. They return to the composer without being sent. If they exceed one prompt's text or screenshot limits, the remaining parts stay as **Not sent** messages with **Restore prompt**; the part in the composer stays recoverable too. A thread already published by main stays with its own prompts even if the creation reply is lost.

New threads follow **New threads start with** in Settings → Threads once it names a model; until it does, they inherit the native subscription and model selected for reasoning, or its account default when no model is selected. An unavailable model remains selected; connect it or choose another from the composer's own model chip once the thread is open. Old separate thread defaults are ignored. With no native Agents subscription selected, an available native thread provider remains the starting choice.

Questions and permissions come from the thread's own pending requests. Codex and Claude Code threads, and Grok Build threads at creation, are told to ask through their own question tool rather than only in a reply; Devin and Muse take no such instruction (ADR-0080). A question a model writes into a reply that a finished turn folds is quoted under the fold as a lifted question, which is for reading and is not a request. The sidebar reads **Needs your answer** or **Needs your approval** while one is waiting. A composed answer stays bound to its question. Explicit **Allow** or **Deny** returns that decision to the native provider. Unsupported interactive forms must be handled in the native client. Native hooks and permission settings still apply; Sotto keeps each session's approval surface so requests only you can answer arrive here (ADR-0043).

For Claude Code, the next message from Sotto restarts its client and resumes the updated native history after a message authored in the native client, even if background work is running. The restart stops that work, and the notice names what stopped.

The composer’s effort chip opens the effort card: the level word, one line saying what the level costs, a Default button when the model reports a default, and a pill track with a stop for each level the model reports. Dragging previews the level and settles toward a stop; releasing saves it. The wheel over the track, the arrow keys, Home, End and the digits 1..N step; Escape, Tab out or a pointer outside closes the card. Failed saves restore the previous level. At the model’s highest level the word, the chip and the composer’s outline take the effort color chosen in **Settings → Appearance**, and reaching it plays the arrival once; reduced motion shows the settled state (ADR-0019). Claude’s Ultrathink action adds a visible instruction to the editable draft and follows that draft through sending or retry. It does not change the saved reasoning effort. Ultracode is not offered because the adapter cannot confirm workflow availability.

Model, effort, image and permission-mode controls reflect the adapter's verified capabilities. Paste, drop or attach screenshots with Codex models that accept images or with Claude Code. Screenshots can be sent alone, alongside text or in a queued follow-up. Codex also accepts screenshots when steering a running turn. A screenshot past the screenshot bound, 2576 pixels on its longer side, is scaled down to it in the composer, in the same format (ADR-0030). Its chip says both sizes under the name, such as *Resized from 3840 x 2160 to 2576 x 1449*. A browser feedback screenshot is scaled the same way. Each screenshot is handed to the computer that runs the thread once, when it is attached, and drafts, queued messages and the state every window receives carry only a reference to it; its bytes are read again only to show its chip, its preview, and to send it to the provider (ADR-0031). Unsupported controls are unavailable. Grok currently selects model and effort at thread creation and does not support existing-thread configuration. The native client Sotto verified, Grok CLI 1.0.5, reports no image input through ACP, so screenshot attachments remain unavailable even when the underlying Grok model supports vision.

While a thread is running, **Steer now** beside a queued message sends that message into the current turn when the provider supports steering, as Codex and Claude Code do; **Steer now** beside the composer does the same for the draft, and Enter still queues. The rest of the queue and any newer composer draft stay in place. An unconfirmed message cannot be steered again; use **Check again** to reconcile its delivery. If Claude is thinking or writing, a steer cuts that step short and Claude answers the steer at once, as its next turn. What it was writing is dropped, and the turn it cut reads **Steered** where a turn you stop reads **Stopped**. If Claude is running a command or another tool, the steer waits for it and joins the same turn, and Stop still ends the command. A steer Claude has not read when you stop the turn still runs, because Claude Code already holds it ([ADR-0065](adr/0065-claude-threads-steer-and-the-iphone-queues-steers-and-compacts.md), [ADR-0075](adr/0075-a-claude-steer-cuts-the-step-claude-is-thinking-or-writing.md)).

Stop has independent admission through the coordinator and workspace, so a pending prompt acknowledgement or unresolved delivery cannot block cancellation. Its own saved intent leaves the original prompt and reconciliation record intact. A failure to save the queue pause does not block Stop and is reported separately from its completed turn record. A refused Stop does not cancel native work. Other storage failures can still prevent cancellation; Sotto reports the failure. No prompt is replayed automatically.

## Resuming after a restart

With **Resume threads after a restart** on (ADR-0076), the local host's coordinator records each thread a connected provider reports running in `restart-resume.json`: its Sotto thread ID, when the turn started and how many times in a row it has been resumed. A turn that ends while Sotto runs, however it ends, takes the thread out. The record stops changing as soon as Sotto starts closing, so a quit, an update restart and a crash all leave the threads that were working. On the next start each one is sent the resume note as a wake-up, through its own follow-up queue, once its provider is back and reports it idle. The thread is read first, so the note follows the turn the restart cut off even where the provider reports the thread idle before its turns are read, as Codex does for a thread nobody has opened since; a thread that read finds still working is left to carry on. If that read fails, the queue's own read before sending finds the turn, and the note follows it. **Resume queue** reads a thread whose turns are unread the same way before it resumes the queue. A thread is resumed at most three times in a row; settled and archived threads, and records older than seven days, are cleared unsent. A headless host takes its Owl list from its own version, so a stable host resumes from 0.1.40.

A dormant Muse thread keeps its resume record unchanged while Muse is held, including when the setting is off or the record is old. Returning to an available Muse build applies the normal resume limits; keeping the record grants no permission and sends nothing while the thread is dormant (ADR-0079).

## Working copies and Git

Git on the Threads page works the way T3 Code does it (ADR-0027): the working copy and branch are chosen on the branch toolbar under the composer, the Git action in the pane header commits, pushes and opens pull requests, **Changes** in Tools reads what changed, and **Pull request** in Tools reads and merges the branch's pull request. The branch toolbar, the Git action and Pull request run on the thread's own host, and Changes reads the thread's own host too: for a thread on a paired host it asks that host for Working tree and Branch changes (ADR-0025, October 5 amendment). GitHub is reached only through `gh` on your own sign-in; see the README's privacy section for what is fetched and when.

### Working copy and branch

New threads use the project folder unless a global or project default selects a new worktree. Threads using the same folder share its unfinished edits and branch. The choice for one thread is made under its composer, on the **branch toolbar** (ADR-0027): **Workspace** offers **Current checkout**, **New worktree** for agents that need to work separately, and **Previous worktree** for a worktree another thread of the project already has, and locks once the thread has a message. The workspace menu keeps Current checkout and New worktree at the top, then shows the five worktrees used most recently by this project’s threads. Search worktrees searches all available worktrees in the project by branch or folder, including older ones. For a new worktree the **branch picker** records the branch it starts from and its **Start from origin** switch says whether that branch is fetched first; the checkout is created on first send, a failed fetch stops setup so you can choose another source, and uncommitted project edits are not copied. For a folder that exists the picker searches the repository's refs and checks out the one you pick, `git checkout <ref> --`, with `--track` for a remote ref that has no local branch; a ref checked out in another worktree re-points a draft at that worktree; **Create new ref** makes a branch from HEAD; Git's refusal is shown under the row. **Run on** names the machine the thread runs on. Shortcuts: the picker on `mod+shift+g`, Workspace on `mod+shift+x`, the first Previous worktree on `mod+shift+l`, and `mod+shift+n` opens a new thread in the focused thread's project (or the project chooser when none is focused); each left unclaimed when the dictation hotkey uses the same keys. A new thread opens straight into its project's working copy, chosen the same way as for an existing thread. Working-copy defaults for each project are in Settings > Threads > Project defaults. Opening an empty thread creates no worktree. Existing provider sessions keep their original working directories.

The first prompt can give a new worktree's short temporary branch a descriptive name, written by the thread's own provider in a side call that never enters the thread (ADR-0026). Generated thread titles and Keep local history must both be on, and Muse and Devin threads keep their temporary names, as do OpenCode threads on a model source that refuses OpenCode's one-off generation, such as OpenCode Zen's free models (ADR-0087). Muse side writing is unavailable because MSP cannot disable every tool independently of its policy. The request runs in the background, never renames a branch the agent or user already changed, and leaves the turn running if naming fails.

The branch label is re-read after relevant work, when you start typing and when the window regains focus. Only a thread using the shared project folder shows **Branch changed** when its current named branch differs from its last send. A branch picked in the branch picker moves the last send's branch with it, so the notice is for a checkout moved some other way: by the agent, in a terminal or by another thread. The notice waits for a draft; sending continues on the current branch, **Restore branch** switches back after confirmation if changes are uncommitted, and **Dismiss** lasts for that branch pair through pane switches in the current app session. Worktree-backed threads do not show this notice. A missing Sotto-created working folder is put back on its recorded branch when possible before the next send; an occupied branch or invalid folder binding is reported without resetting or removing work.

A thread's own worktree can be given back (ADR-0041). **Remove worktree**, in the pane header's Working copy panel, removes the folder and keeps its branch, and the next send puts the folder back on that branch. Settling a worktree-backed thread asks **Remove its worktree too?**. Cleanup rules under Settings → Git & worktrees can do it on their own; every rule is off until turned on, and none removes uncommitted work. A thread using **Previous worktree** works in another thread's folder and cannot remove it; the thread that made it can, once no other thread is working there. **Auto-settle merged threads**, under Settings → Git & worktrees, settles a thread and asks nothing, so the folder goes only if the on-settle cleanup rule is on.

Both removal questions list ignored items other than installed dependencies and require **Delete these N ignored items with the folder** before discarding them. Main rechecks the list; a changed list removes nothing and requires reopening the question. Nested repositories and worktrees are flagged with a count of uncommitted changes. Repositories also show commits not on any remote, including retained history in clean or deinitialized submodules. A rule leaves unpublished submodule history alone; the tick permits deleting the listed history and uncommitted work. Ignored folders have one summary row each; files appearing or disappearing inside one require a fresh question. Rewriting an existing cache file is allowed because byte sizes are not compared.

### Git action

The **Git action** sits at the end of the pane header (ADR-0027). Its label follows the folder's Git status and a press does what the label says: **Commit**, **Commit & push** (on the default branch or with an open pull request), **Commit, push & PR**; **Push** or **Push & create PR** for commits not yet pushed; **Pull** when the branch is behind (fast-forward only); **Create PR** for a branch ahead of the default one; **View PR** when one is open; **Publish repository** for a repository with no remote (GitHub, through `gh`); **Initialize Git** for a folder without Git. It is disabled with T3's reason when there is nothing to do, when HEAD is detached, or when the branch has diverged. The chevron beside it lists Commit, Push and Create PR or View PR, each disabled with its reason, and Publish repository while the repository has no remote. A commit opens **Commit changes**: the branch with a **Default branch** tag, the changed files with their line counts (Edit leaves files out), **Commit message (optional)** that the thread's own provider writes when left empty, and **Cancel**, **Commit on new branch** and the action. A push or pull request from the default branch asks **Push to default ref?** first: **Abort**, **Push to** the default branch (**Push to main**, say), or **Check out feature branch & continue**, which cuts a branch from HEAD, named after the commit, and continues on it. While the action runs, one notice above the composer shows its stage and the hook running; when it ends it shows the result with the next step (**Push**, **Create PR**, **View PR**), or **Action failed** with the host's words, until dismissed. Nothing is forced or rebased, and nothing is merged but the merge commit you say yes to when you bring changes back. The Git actions drawer inside Changes is gone; Checkpoints stays there.

**Bring changes to main** (Owl, Work across machines; #1030, ADR-0027's October 23 amendment) is first in the chevron's menu and in a strip above the composer, on a thread in a new worktree made from the branch of the thread it began from, while that thread is still on it: a delegated thread, a continued thread, an agent continued as a thread, a fork at a reply, or a worker Watcher started from a thread's branch (`madeFrom` on its worktree record). `bringBackTarget` decides it from the records alone. A press is `bring-changes-back`; the host runs `GitActions.bringBack` on the thread's lane with the parent's folder held: uncommitted work in the worktree, a parent folder that is dirty, mid-merge or no longer on the branch, a check's snapshot among the commits, files the branch would gain that the parent's folder has as ignored files, and a conflict (found first with `git merge-tree --write-tree`) are refused, Git's own words for a conflict. Otherwise the branch is fast-forwarded in the parent's folder (`update-ref` by name from the tip read, then `read-tree -m -u`; put back if the folder switched branch or Git stopped part way), or Sotto asks **Make a merge commit on main?** and makes it with `git commit-tree` only on **Make merge commit**. The question and outcome go on the thread's `bringBack`, never saved. For a child on another machine the desktop's router (`bringBackAcross`) moves the child's committed branch first, with `DesktopBranchMoves.forStart`, into an incoming ref in the parent's project, and sends `bring-changes-back` with `away` to the parent's host, which runs the same press in the parent's folder, keeps the record on the parent's `broughtBack` naming the child, and removes the incoming ref once the press is over. Only a client the host recorded as a desktop may send `away`, and only a host that lists the `bring-changes-back` feature takes the command at all.

### Changes

**Changes** in Tools is T3's diff panel (ADR-0027). Its scope menu offers **Working tree** (the working copy against HEAD, untracked files included, read through a copy of the index so the real one is never touched), **Branch changes** (`base...HEAD`; the base picker starts at **Automatic** and lists each branch once, in **Branch** and **Remote** columns, with **Use remote version** where both copies exist and a **Remote only** mark where only the remote one does), **Latest turn** and **Turn N**, read from Sotto's checkpoints rather than Git. A turn whose checkpoint is unavailable says so with the reason. The line of chrome shows the comparison's `+adds −dels` and **Refresh diff**; the bar under it holds **Expand all files** / **Collapse all files**, **Stacked diff view** and **Split diff view**, line wrapping, **Hide whitespace changes** and the file tree, which stands beside the files in a wide panel and above them in a narrow one. Each file is a block with its status, counts and **Copy path**; its name opens it in Files. **Diff layout**, **Hide whitespace changes** and **Default diff file state** in **Settings → Git & worktrees** set where Changes starts. A choice made here holds until one of those settings changes or Sotto restarts. There is no staging: **Stage file**, **Unstage file** and the staged and unstaged comparisons are gone, and the commit dialog's file list is the choice. `mod+d` toggles Changes, or `mod+shift+d` when the dictation hotkey holds `mod+d`; focus inside a terminal keeps its own Ctrl+D. A thread on a paired host gets the same Changes, read from that host (ADR-0025, October 5 amendment), with **Working tree** and **Branch changes** only: its turn checkpoints are not kept here, so it has no **Latest turn**, **Turn N** or **Checkpoints**, and no **Show in File Explorer** either. **Copy path** copies the path on the host, in the host's format. With no watch on another machine, the window asks the host for the change list every four seconds while Changes shows the thread, and reads the comparison again when the list moved; **Refresh diff** reads at once. Files and Agents read the host the same way, with "on forge" in the Tools footer. Away from Changes, its dot on the rail follows the host's last read of the working copy: after each turn, on a refresh, and on the fetch timer. Proactive panels does not yet open Changes for a thread on a paired host. **Checkpoints**, on the same line of chrome, is Sotto's own: it lists the thread's turn checkpoints in this working copy, shows what a turn changed, and **Revert files and conversation** puts a whole turn back after you tick the confirmation. It is the one control on Changes that writes. **Proactive panels**, under Settings → Git & worktrees, can open Changes on its own after a large turn; it is off until you turn it on.

### Review comments

A **review comment** (#270) is T3's way of saying something about lines of Changes. Click a line, Shift+click to take more, and press **Comment**, or press a line number to comment on that line; the draft opens under the lines (**Add a comment…**, **Cancel**, **Comment**; Escape cancels, Ctrl+Enter adds). The comment becomes a chip on that thread's composer, named `file L12 to L20` from the new file's numbers or `file L4 to L5 (before)` when every line was removed, and a marker under its last line with **Delete comment**. A file's lines are one stop in the Tab order, followed by the Comment button and each comment's controls where they are drawn: the arrow keys, Home and End move, Shift extends, Space picks a line, Enter opens a draft on what is picked, and Escape lets go. The next prompt, queued follow-up or steer carries every comment as text after the user's message, so every provider reads the same thing:

````text
Tighten this before we merge.

Comment on `src/main/voice.ts L12 to L13`:

Say why it returns early.

```diff
+  if (!key) return { ok: false }
+  const clip = await speak(v, SAMPLE, 2)
```
````

A comment keeps its lines as they read when it was written. If the diff moves on, the comment still goes with those lines; its marker moves to the end of the file and says the lines have changed since, until the comment is sent or deleted. A line only past the first 3,000 rows drawn says to Show all instead. A comment on lines the comparison does not draw (its file committed or outside the scope, a mode or rename only, or a comparison that could not be read) is listed after the files under **Comments on lines this comparison does not show**, with Delete comment; a draft with words whose lines are not drawn is listed there too, so it can be finished or cancelled. An answer to a question does not carry comments; the composer says they wait for the next prompt. A message carries at most 20. Comments live in the window's memory for its thread until sent or deleted. They are never saved as comments and never reach a log; once written into a prompt they are part of its text, saved and sent as any prompt is.

### Pull request

The branch's pull request is a Tools surface, **Pull request** on the rail, its tile reading PR (ADR-0027). The badge on the branch toolbar opens it; it shows the branch's pull request, else the one linked last, read from GitHub through the host's `gh` when it opens and on **Refresh**, as the **merge checklist**: **Checks passing** (the first failing check named, with **Open check**), **Review approved** (who approved, or who asked for changes, with **Open review**; "No review required" where the repository asks for none), **Up to date with** the base (with **Update branch**), **No conflicts**, and **Ready for review** (with **Ready for review** for a draft). One large **Merge #N** is enabled only when no line holds it back, in the method beside it (Merge commit, Squash or Rebase), which starts on the Default merge method setting (#271); otherwise the hint counts the lines left and offers **Merge when ready**, GitHub's auto-merge, where the repository allows it. An armed auto-merge shows **Turn off**, a closed pull request **Reopen**, and a merged one when it merged. The description and **Linked pull requests** fold below. The ··· menu holds **Convert to draft** or **Ready for review**, **Update with rebase**, **Merge when ready (auto-merge)**, **Disable auto-merge**, **Babysit pull request**, **Copy link**, **Link pull request**, **Unlink from thread** and **Close pull request**; **Open on GitHub** and **Refresh** sit beside it. The merge, turning on auto-merge, closing and **Update with rebase**, which rewrites the branch on GitHub and leaves a local copy behind, ask first; nothing happens from viewing, and the host acts only on the branch's pull request or one linked to the thread. **Linked pull requests** lists the thread's links (created by its Git action, linked by you, or checked out) with the branch's own, and **Link pull request** takes a GitHub URL or `#42`. With no pull request yet the surface offers **Create PR**, which runs the Git action's own Create PR under the same rules, and Link pull request. In the branch picker, a pull request URL, `#42` or `gh pr checkout` line offers **Checkout pull request**, which takes only a pull request of the project's own origin repository. **Local** runs `gh pr checkout` in the thread's folder without forcing, and says first when it moves a draft set to a new worktree into the project checkout; and **Worktree**, for a thread that has not started, fetches the pull request's branch for the new worktree its first send makes. All of it runs on the thread's host, so a paired host's thread works the same way.

### Settings → Git & worktrees

T3's Git settings are in **Settings → Git & worktrees**, grouped under when each acts (When a thread commits, When a pull request is made or merged, When you read Changes, In the background), read by the host that owns the thread (a remote host reads its own `settings.json`). **Automatically pull** (off) runs the Pull above on its own when a read of the remote finds the folder on the default branch, clean and only behind, and leaves a folder any thread is working or waiting in for the next read. It shows no notice: the pull shows only as the status changing, a Git action pressed on the same thread waits for it, and one pressed from another thread in the same folder is refused with **Sotto is pulling this folder. Try again in a moment.** **Auto-settle merged threads** (off) settles a thread at rest whose last-sent branch's current commit matches a pull request GitHub reports merged, on the worktree cleanup's hourly sweep through `gh`, once per thread and branch while Sotto runs; the on-settle cleanup rule, when on, then decides about the folder. **Proactive panels** (off) opens Changes on a closed, unpinned Tools panel when a turn leaves its folder with at least 3 more changed files or 50 more changed lines, leaving keyboard focus where it was. It compares the working copy's counts before and after the turn, not the turn's own diff, and counts only while the Threads page is open; a large turn in a pane not in focus waits until its thread is focused, and is let go once Changes has been opened for it. **Diff layout**, **Hide whitespace changes** and **Default diff file state** are where Changes starts, as above. **Default merge method** is the method the pull request checklist's merge starts on, read through `useMergeMethod`; under Last selected, a method picked beside that Merge is saved as the one to start on next. **Commit and pull request style** (Repository conventions, Conventional Commits, Custom instructions) adds its instruction to the commit message and pull request requests; the last two take precedence over the example, the recent subjects and what `AGENTS.md` says about style. **Follow pull request templates** (on) decides whether the thread's own model is given the repository's pull request template to follow when a Git action drafts a pull request: the first template file in GitHub's usual places, or the only one in a `PULL_REQUEST_TEMPLATE` folder.

## Upgrading an older installation

An installation configured for the retired intermediary host is migrated before its saved state is interpreted as a native configuration. Sotto disables automatic connection, retains the draft and attachments without their old target, and preserves recovery evidence separately. Old assignments and uncertain actions are not transferred to a native provider or replayed. Existing thread bindings remain historical identities, never relabelled as native sessions.

The upgrade notice identifies the local recovery record. Check the original coding client before reusing a draft whose previous delivery was uncertain. A recovered answer is not permission to submit it to a new thread. Choose a native provider and explicitly prepare any new work. Installations already using a native provider keep their selection and recovery state.

## Data and accounts

Coding usage belongs to each thread's provider account. Sotto has no account or subscription. Sotto never enables overages, buys credits or changes accounts automatically. Native clients retain subscription authentication; Sotto-owned API keys use the operating system's encrypted credential store. A locked vault reports an error without storing plaintext credentials.

Sotto stores thread bindings, drafts, user follow-up queues, outbox entries and delivery evidence locally. Unsent drafts remain until sent or cleared. **Keep local history** controls message history, attachment storage and remote draft recovery copies. Dictation audio is never written to disk.

A thread's messages are Sotto's own record, kept in an event store rather than rebuilt from the provider each time Sotto starts. Each adapter appends only what is new to it — Claude from its transcript tail, Codex from the app-server stream and its rollouts, Grok from its update cursor, Devin from UUID-tagged native replay — and a thread nobody is looking at carries its summary rather than its history. A pane reads the newest ten turns from Sotto's event store and reads further back when you ask for earlier messages. A provider session starts when a thread is opened, sent to or typed in (an early start, ADR-0057) rather than at connect. Claude Code, Codex and Grok Build each run a process per thread (ADR-0038), so when one ends on its own only that thread is affected: the provider stays connected, a running reply is marked failed with a line saying it may be cut short, lost background work leaves the thread needing attention, and the provider session resumes the next time the thread is opened, sent to or typed in. Nothing is resent. A client update works the same way: the provider stays connected while the installer runs, an idle thread's process stops at once, and a working thread finishes its turn on the old client and moves to the new one when it is next idle. Devin separately replays native history to resume a thread and confirm delivery, so a longer native thread can take longer to reconnect or open. A send to a Devin thread Sotto already has open replays nothing first, since no other client can write to it meanwhile, unless an earlier prompt is still unconfirmed, and its reply shows as it streams. Replay is limited to 16 MiB of text and 20,000 messages; once a replay exceeds the limit, Sotto keeps saved history readable but refuses further native reconciliation and sends. A thread that is already open finds that out at its next replay, so it can take a prompt or two more first. It never resends uncertain work automatically. **Keep local history** off still means no message text is written at all, and turning it off removes what was written; what was not kept cannot be recovered. See ADR-0016.

Manual commands and babysitting wake-ups append bounded turn records containing timings, acted-on thread/project IDs and outcomes. Historical voice and automatic-follow-up records remain readable. Draft edits are not turns. Turn records never hold prompt, answer or error text. Timings, identities and fixed failure codes remain. A send's record also times each send stage between Send and the reply's first output, so it can be written after the command returns, once that output arrives; until then it is held in memory, and a crash loses it (`CONTEXT.md`, Send stage). Developer builds can reveal the turn-record folder from the tray menu.

## Reported subagents in Tools

Choose **Agents** in Tools to inspect the focused thread's subagents. The roster, its details and its working indicator always belong to that thread. Pinning another working copy holds Browser, Terminal, Files and Changes there; it does not redirect Agents. A row shows the provider's task title, a brief task preview, the model the agent ran on, status and elapsed time when available. Expand it for the task, result and earlier assignments. Nested children follow their reported parent; siblings keep their spawn order. Claude Code does not stream a model for a workflow or a background agent, so Sotto reads it from the first reply in that agent's own transcript and nothing else from it. A model nothing names reads **Model not reported**. A Claude Code workflow is one row named for the workflow, with a strip of one segment per agent and a count such as *4 of 6 finished · 1 failed*; pressing it opens the **workflow page**, which lists each of its agents as a row of its own with its label, model, status, task and result (#339). **All agents** or Escape returns to the roster. The roster's count is of agents, so a workflow of six adds six. Providers without child observations show an empty view.

The dot above-left of a pane's own Tools icon appears only for confirmed working agents in that pane's own thread or a browser request waiting for your answer there; a working copy pinned to another thread never lights it (#331). It does not open Tools, switch its surface or grant permission. Inside Tools, the rail marks **Agents** with the same kind of dot while agents work, and says how many in words. A pinned thread remains observed even after its conversation pane closes. Disconnecting or restarting changes unfinished agents to **Last seen working** and freezes the clock until activity is confirmed.

Agent and assignment history uses bounded pages, independently of ordinary transcript activity. It follows **Keep local history**. There are no child command controls or full child transcripts in this view.

## Browser tasks

An agent browser task on the focused thread shows in a floating **browser player**, above the composer, with the live page rather than a thumbnail; another thread's task never shows there, pinned or not, and waits in its own pane and in Tools. Drag the player's title bar to move it, or resize it from its corner; with either focused, the arrow keys do the same (Shift for bigger steps). **Move into Tools** sends its page to **Tools > Browser** without pinning, **Shrink** turns it into a small pill that restores it, and **Hide** leaves the agent working with Tools > Browser as the way back. Tools > Browser offers the way back the other direction too: while it shows the focused thread's own task, **Float the browser over the thread** closes Tools and brings the player back, again without pinning. **Pause** stops further browser actions. **Show the browser when an agent opens a page** in Settings turns off only the player opening on its own; the work carries on and Tools > Browser still shows it. A request waiting for your answer puts a dot on the Tools icon of the pane showing its thread, on **Browser** in the Tools rail and on its page tab in Tools > Browser. A thread with no open pane has no such mark: its request waits in Tools > Browser until you answer it or it expires. Finished tasks retain their summary, observed steps, screenshots and unchecked cases for the current app session.

The browser's **test iPhone** (ADR-0045) is a page drawn as an iPhone 15 Pro: 393 by 852 CSS pixels, iOS Safari's user agent and touch. `iphone_open` opens a URL on the thread's one phone and starts a browser task there, asking or running exactly as `browser_open` does; `browser_action` drives it with `tap`, `swipe`, `type`, `key`, `inspect` and `screenshot`, in the phone's CSS pixels. The grant covers `tap` and `key` as it covers `click` and `type`; `swipe` never asks, and a `viewport` action is refused because the phone keeps its size. Its task floats in the **phone player** rather than the browser player, and **Tools > iPhone** holds its address, sharing, steps and requests. An agent reporting on it should say it tested a web build at phone size, not iOS.

A **cloud iPhone** (ADR-0047) is a run.cloud iOS simulator for a native build, on the same endpoint. `iphone_cloud_open {buildPath, description}` names a simulator build inside the thread's working copy and waits for the user's **Start cloud iPhone** in the thread; it is refused, with nothing uploaded, when no run.cloud key is saved or the month's minutes have reached the cap. `iphone_cloud_action` then taps, swipes, types, presses a key or a button, opens a URL, reads the accessibility tree or takes a screenshot, in iOS points; none of these ask. `iphone_cloud_status` reads the session and `iphone_cloud_finish` ends it with a summary and unchecked cases. The user watches in the phone player and can end it, and an idle session ends on its own.

Codex, Claude Code, Grok, Devin, Muse and OpenCode project threads receive Sotto browser tools through a thread-bound local MCP connection. Muse gets them when its client grants tools for one session (ADR-0079), on every start and every resume on a new Muse process. Devin gets them from CLI 3000.11.92, on every session Sotto makes or loads for the thread (ADR-0056). OpenCode gets each of Sotto's servers as a remote MCP server added to the thread's own OpenCode server each time it starts, with the thread's token, and taken off again when the thread's session ends (ADR-0087); code mode is off, so each tool reaches the model under its own name, such as `sotto_browser_browser_open`. A server OpenCode refuses or does not connect leaves the thread without Sotto's tools, which the thread then says, as a Muse thread does. The agent must use the URL of the app it actually started in that thread's working copy. It can inspect a shared page, read bounded console and network errors, scroll, change the viewport and capture screenshots. Every project thread has a browser grant by default (ADR-0029): while **Let agents use the browser without asking** is on in Settings, opening a page, navigating, clicking and typing all run without your one-time answer, and a page the grant opens is shared the way Open and share shares a page. Turn the setting off, or press **Stop** on the line Tools > Browser shows for a thread, and that thread's opens, navigations, clicks and typing wait for your one-time answer again; a waiting request also offers **Allow this thread to use the browser** beside Allow once, which grants that thread the browser until you stop it or Sotto closes. Reaching the browser is not one of those answers, so the provider does not ask its own question first; the answer that matters is the one you give in Sotto. Claude Code and Codex are told at launch not to ask, and an OpenCode thread's rule set allows each tool of the Sotto servers its OpenCode server was given and connected, by its own name, after the permission mode's rules, which takes no tool away and widens nothing else; a provider session made before the thread had those tools gets the allows when it is opened again. Devin is told by its Sotto-owned profile (version 3), which allows the thread's own Sotto servers by their exact names (`mcp__sotto_browser__*` and the others) while every other MCP tool still asks. A request for one of them that arrives anyway is shown, named "Use Sotto's browser_open tool" and the like with the call's whole input, for you to answer. Grok and Muse cannot be told, so when one asks to use one of the thread's own Sotto tools by its full name (Grok's `sotto_browser__…`, Muse's `mcp__sotto_browser_<suffix>__…`, where the suffix is new for each thread each time Sotto starts, so another server cannot take the name), Sotto answers that question with the client's one-time allow and does not show it; any other tool, including one with the same name on another server, still asks you. Muse gives up on a tool call after 5 minutes and cannot be told to wait longer, so on Muse a browser request still waiting for your answer after 4 minutes returns to the agent, says so, and stays open for you; the agent reads `browser_status` before asking again. Where a client asks anyway and names Sotto's browser tool in full, the request says which page it would open or what it would do there, and answering it only lets the agent reach the browser. A Grok call that gives only the bare tool name does not say which server it is for, so it shows as Grok sent it. The agent cannot answer those requests. Pausing, revoking sharing, closing the page or changing its context invalidates outstanding actions. A timeout never grants permission.

While the thread has a browser grant, every page in its browser is shared with it, pages you open included, and a shared page stays shared as it moves to another origin, a server's redirect included. **Stop sharing** makes one page private until you choose **Share with agent** again. Without a grant, a page you open yourself stays private from the agent until you choose **Share with agent**, and sharing allows observation of that origin only. When a grant ends, a page it shared keeps its sharing on the origin it is on, until it leaves that origin or you press **Stop sharing**. Sharing does not preapprove clicks or typed text. Revoking removes retained page observations. Browser page grants and task evidence are temporary and disappear when Sotto closes. Tool output may also be retained by the native provider under its own policy.

Use browser feedback to select an element or region and add a comment. The URL, selected context and screenshot go into that thread's editable composer draft, preserving existing text. Nothing is sent automatically. Image support follows the selected provider's capabilities; unavailable attachments are explained before adding the draft. Browser results report what the agent observed and what it left unchecked. They do not establish that the native desktop app or an unvisited flow passed.

## Host setup threads

A thread started by **Have my agent set this up** in Settings > Hosts & phones is a normal thread, "Set up forge" in the **Host setup** project, with one addition: while its setup runs it gets Sotto's host setup tools (`sotto_host_setup`) beside the browser's, over the same kind of thread-bound local MCP connection, and no other thread gets them. Codex, Claude Code and Grok are given them the way they are given the browser tools, without the provider's own question; Devin is not offered either: how long its client waits on one tool call has not been checked, and in the asking mode a setup starts in it would ask before every check as well. Nor does it offer Muse, which gives up on a tool call after 5 minutes, as long as a check can wait for a Tailscale approval, nor yet OpenCode, which takes Sotto's tools but has not been checked running a setup (#1107). Which providers a setup may run on is a list of its own (`hostSetupThreads.ts`), not the providers that take Sotto's tools. The tools check and add only the device the setup names. Adding is a **Sotto request** in the thread, "Add forge as a host?", which you answer on its card like any other request; Sotto acts on the answer itself and the provider never sees it. A desktop connected through your SSH account can answer it after setup; a device paired by code needs your separate permission, as for every request. The setup is an ordinary user-started thread. Only you answer its request cards. See [the guide](guide.md#having-an-agent-set-up-a-host) and [ADR-0035](adr/0035-an-agent-can-set-up-a-host-from-add-host.md).

Codex, Claude Code, Grok, Devin, Muse and OpenCode project threads also get Sotto's visual tool (`sotto_visual`, one tool, `visualize`) over the same kind of connection, while **Let agents draw visuals in threads** is on in Settings. Its tool description tells the agent to draw a diagram when a picture explains how something works, and whenever asked: Mermaid source for a flowchart, sequence, state, class or entity relationship diagram, a title, an optional intro and up to 12 steps naming the parts each is about. Main checks the call against the same rules the card draws by, keeps the visual with the thread, anchored to the newest message, and answers in plain words: what was shown and where, or why nothing was drawn. Drawing changes nothing outside the thread, so the provider is told not to ask and Sotto asks nothing; Grok's own question for `sotto_visual__visualize` is answered with its one-time allow. Devin's profile allows it by name, and so does an OpenCode thread's rule set. Threads on another host get no such server, and with the setting off a new launch gets none and a running session's call is refused. Visual messages are left out of sidebar summaries, search and generated titles. With kind `interactive` the agent sends its own HTML page instead, up to 60,000 characters; the description tells it the page cannot load anything, to colour it with the `--sotto-*` variables and to listen for `sotto-visual-step` and `sotto-visual-theme` window messages. Main serves the page once, from its store, into a sealed `<webview>` guest ([ADR-0060](adr/0060-an-interactive-visual-runs-in-a-sealed-page.md)). See [the guide](guide.md#visuals) and [ADR-0056](adr/0056-an-agent-can-draw-a-visual-in-its-thread.md).

The same threads get Sotto's pull request tools (`sotto_pull_requests`: `babysit_pull_request`, `stop_babysitting` and `list_babysitting`) while **Let agents babysit pull requests** is on. `babysit_pull_request` babysits the thread's branch's own pull request, or one the agent names by URL or number, which is linked to the thread first by Link pull request's rules when the thread does not know it. Its description tells the agent to call it and end its turn instead of polling `gh` or sleeping, and to stop babysitting before handing the work back. Starting asks nobody, so the provider is told not to ask either, as for visuals. Devin's profile allows it by name, and so does an OpenCode thread's rule set. The thread's host then reads GitHub every two minutes and sends a **wake-up** through the thread's own send path when a check fails, or fails again after a rerun, every check the base branch requires has passed (again after a rerun turns one green), someone else comments or reviews (not a bot saying only that it could not run), the branch starts to conflict, or the pull request merges or closes: at once when the thread is ready, otherwise as Sotto's own item in the follow-up queue. Its turn record's source is `wake-up`, and the message is marked as Sotto's from the host's record of sending it. Stop, settling, archiving, unlinking and the switch end babysitting and send nothing, and take back a wake-up still waiting. With the setting off, a new launch gets no server, a running session's call is refused, and what agents started ends; what the user started stays. Threads on another host, and a thread whose client withheld Sotto's tools, get no server; the user babysits them from the Pull request surface through the `babysit-pull-request` and `stop-babysitting` commands. See [ADR-0061](adr/0061-a-thread-can-babysit-its-pull-request.md).

## Watcher tools

Paired-host routing uses optional host-v1 `watcher-control` and `watcher-reads` operations, with explicit owning-host IDs. Main reserves shared capacity and receipts before transmitting; the owning host reuses these coordinator lanes and writer guards. Its authenticated SSH-recorded desktop, original master/request identity and permission ceiling are retained as text-free attribution. The ceiling holds starts only: a send, queue or steer is compared with no permission ceiling, on either computer, because it gives the thread nothing (#1145). Reconnect and host restart reconcile without replay. Native and phone instructions publish generation takeover on the host. Older hosts refuse automation before any new request is sent. No local tool bearer travels remotely, and no ordinary privileged command is a fallback. The protocol reference records the closed envelopes and positional reads.

Main owns one Watcher service and its thread-bound sotto_threads server. Its durable creation intent includes the exact model and effort; recovery keeps its minted Sotto ID. The neutral watcher/workspace folder is excluded from ordinary project choices. A user Send supplies a main-minted request reference to the native Watcher turn in its request note, which names that request and the local host and no projects. The adapter gives the note to the model through the provider's own context for that turn: Codex `turn/start` `additionalContext` as application context, and Claude Code a UserPromptSubmit hook answered on the CLI's own control channel. Grok Build has no such channel, so its prompt carries the note as one bracketed line after the user's words. Muse has none either: its prompt carries Grok's line and, ahead of the user's words of a conversation's first message on a host and again after a compaction, Watcher's instructions as Sotto's own text part, with the worker-role lines when that feature is on, and its turn names the message alone as `displayText`, which is what Muse records and the adapter shows (ADR-0079). Every surface shows the message as typed: the coordinator's snapshot removes only Sotto's exact line, Grok's line or the project-listing footer older sends carried, and only from the Watcher user message whose own request it names; anything the user typed stays. Tools cannot create that reference. A standing watch can also authorize a fresh bounded continuation scope tied to the current master turn. Closed or stopped scopes are never revived. Watcher's own replies show without the one reason line its own-change mark read, through the same snapshot.

The fourteen frozen tool names are watch_thread, unwatch_thread, list_threads, read_thread, start_thread, send_to_thread, stop_thread, settle_thread, list_projects, keep_state, read_state, list_machines, list_working_copies and read_operation. send_to_thread takes an optional `mergeTurn: { pullRequest }` for a send that gives a thread its merge turn (#1339, ADR-0106): `invokeNow` takes it off before `mutate`, so the digest, retry, dispatch and a paired host's packet are as without it, and `noteMergeTurn` remembers the operation in memory once it is admitted (`CallProgress.admitted`), the newest 50. `readMergeTurns`, behind `sotto:watcher:read-merge-turns`, gives Watcher's picture those merge turns and read_state's merge queue, worked out for the watched rows of the room last published (`publishedWatched`, kept by reference), so it walks no history and builds no room; each mark keeps its thread from admission. The picture asks for it only while it shows, at most every three seconds. keep_state and read_state (#1189) run on this computer: keep_state replaces each list it is given of Watcher's kept decisions, rules and issues (`WatcherStateStore`, `watcher-state.json` only while Keep local history is on, removed with its recovery copies through `privacyChanged` when it is turned off), and read_state returns them with each watched thread, what it waits on (`watcherWaitsOn`) and its open pull requests, and Watcher's context against `WATCHER_COMPACT_AT_TOKENS`. read_state also works out from live data at each read (#1274, `watcherComputedState.ts`): the merge queue, open non-draft pull requests of watched threads whose checks passed, ordered by `WatcherEvidenceStore.checksPassedSince` (in memory, so a restart counts a pass from its first read again); the pending settles, from the same `settleHold` that Settle finished threads asks, with `settlesFinishedThreads` saying whether the setting is on; and `staleNotes`, each kept line that names a thread that is settled or not watched, by title or Sotto thread ID, or a pull request that is merged or closed, by link or number. ## Delegation tools

ADR-0081 (#1029), an Owl feature (`thread-delegation`), sent to stable. Main's `DelegationService` (`delegation.ts`) and its scoped loopback server `sotto_delegate` (`delegationTools.ts`) let an ordinary Claude Code, Codex, Grok Build, Devin, Muse or OpenCode thread on this computer start threads and send them briefs. The server joins `useThreadTools` beside the visual and pull request servers and answers a thread only while `admits` does: a project thread this host holds, whose provider takes Sotto's servers, outside Watcher's and host setup's folders, and not started by a delegated thread. Watcher's launch filter never passes it, a headless host builds none, and a build with delegation off, such as stable 0.1.39 and earlier, builds neither the service nor the server. Its client timeout (`timeoutMs`, which sets Codex's `tool_timeout_sec` and Claude Code's `MCP_TOOL_TIMEOUT`) sits thirty seconds above the longest wait, three hundred seconds; Grok Build and Muse get the same bound from the service, and Muse's declared wait shortens it; OpenCode is given it as its wait for one call.

The three tools are `delegate`, `read_delegation` and `cancel_delegation`, and a fourth, `list_machines`, while Work across machines is on and Watcher runs (#1032): the same list Watcher's tool gives, read through `WatcherService.machines`. Then `delegate` also takes `machine` or `os` for a new thread, placed by `WatcherService.placement` as This computer first, whatever `newWorkerMachine` says. A delegated thread starts only on This computer until delegation reaches other machines (#1316), so a placement anywhere else, or one Watcher's placement refuses, is a recorded `MACHINE_UNAVAILABLE` refusal; with neither named and new workers set to start on another machine, the result's `placement` notes that the thread started here. A brief to an existing thread takes neither. With it on, `delegate` also takes `from_my_branch` and `test_run` for a new thread (#1033): `fromBranch` copies the calling thread's branch, or with `test_run` a test-run snapshot of its working copy, into the incoming ref of a move of its own in the calling thread's project, before admission; admission's refusal lets the ref go (`forgetHere`), and a branch that cannot go is a recorded `BRANCH_UNAVAILABLE` refusal with the move's sentence. The new thread is created in a new worktree with `startFromMove`, and the result's `startedFrom` says "Started on This computer from feat/x." Without `from_my_branch`, a new delegated worktree is made from the calling thread's branch while Work across machines is on, so it can bring its changes back (#1030). A shared working copy beside `from_my_branch` is refused as invalid. Main attributes each call to the calling thread through its tool token and roots it in that thread's newest user message that is not a wake-up; a wake-up turn keeps the root before it. `delegate` names the work, the brief and, for a new thread, the provider, model, effort and permission explicitly (an effort only when the model offers one), until worker roles (#1041) fill them in; the permission is never wider than the narrower of the calling thread's own and the new-thread default, compared as Watcher compares, and a provider profile that cannot be compared is refused. No limit holds a start back (#1183); a start that leaves more than ten working threads on this computer, counting the new one, carries `warning` in `delegate`'s result. A send is charged against four briefs per delegated thread per root. A retry key returns the first delegation. The new thread is created with `commandFromDelegation`, which carries a main-owned guard through the coordinator's lanes and the workspace's guarded writer and is never taken for the user's command, then linked on its own record (`delegatedBy`, in the snapshot) before its first send, so its first launch knows its level.

A brief to a busy delegated thread waits in memory only. Every brief carries the delegated thread's newest user message as the delegating thread last saw it (`seenHead`, set by an accepted brief and by `read_delegation`); the guard refuses it as `TARGET_CHANGED` when that has moved, and as paused while the user's own turn runs there, they have words in its composer, or they sent since. That head skips the host's recorded wake-ups (`wakeUpMessageIds`, a message's `wakeUp`), and a running turn whose message is a wake-up is not the user's, so a resume note or other news in a delegated thread holds a brief only until its turn ends; where the messages before a wake-up are not loaded, the head stands as the host gives it. Admission refuses a send as `QUEUE_HELD` while the delegated thread's own queue holds paused or failed follow-ups or a send with an unknown result (`pendingThreadWorkReason`), and a waiting brief whose thread's queue comes to hold paused or failed follow-ups ends unsent as paused. Each way a brief ends unsent has its own note in `read_delegation` (`FAILURE_NOTES`). The coordinator's `userCommand` hook pauses a delegated thread on the user's own send and fails briefs still waiting for it; an `interrupt`, the user's or Watcher's, stops every working thread below, both levels, with machine-origin interrupts; the thread stopped, and any between, are not woken by news of those stops. Watcher's sends pause nothing, and delegation's own interrupts are not handed back to it.

Outcomes reuse Watcher's (`watcherTurnOutcome`). The `observe` hook reads the snapshot's thread list once per pass, only while a delegation is open or a thread is paused, and asks nothing per thread it does not need (`delegationObserveCounts.test.ts`). An outcome a waiting call does not take goes to the delegating thread as a hidden wake-up through the follow-up queue, news source `delegation` (ADR-0081, October 19, 2026): one per delegating thread once the pass is over, however many outcomes moved, counted as told only once the queue saved it and offered again on a later pass when it did not. The queue keeps identities only and folds later news into it while it waits; it never folds with other news, and a visible wake-up an earlier build folded it into is set apart first (`separateWakeUps`).
