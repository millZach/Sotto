# Worker roles say what each kind of work starts on

## Status

Accepted by Zach on October 14, 2026, in the Watcher engine ticket map (#1023): worker roles are an Owl feature with E4 to E10 (decision 12), every role's picker offers any model from any connected provider and Computer use defaults to GPT-6 Astra (decision 13), and Settings uses variant C of the prototype at `prototype/watcher-worker-roles`, with Computer use on Full access, still capped by the new-thread default (decision 15). Built with [#1041](https://github.com/millZach/Sotto/issues/1041) (E13). It amends [ADR-0073](0073-watcher-coordinates-threads-with-its-providers-own-tools.md) and [ADR-0081](0081-a-thread-may-delegate-work-to-threads-it-starts.md), and it is the Owl feature `worker-roles` ([ADR-0072](0072-sotto-owl-is-a-windows-preview-release-track.md)).

Amended October 29, 2026 by [ADR-0162](0162-worker-swarms-give-each-angle-a-worktree-and-one-lead.md): the Owl feature `worker-swarms` adds per-role Workers, queued machine ceilings and one-call swarms with an independent worktree per angle and one lead. The behavior below remains in force with that feature off.

## Context

Watcher's `start_thread` and a thread's `delegate` each named a model, an effort and a permission for every start. The agent picked them, so the right model for the work was whichever one the agent thought of: Opus for a review that Zach runs on Muse, a reasoning level nobody asked for, a permission the ceiling then refused. Zach already knows what each kind of work should run on, and wanted to say it once, in Settings, with defaults that follow the providers he has connected.

## Decision

**1. Six worker roles.** A **worker role** (CONTEXT.md) is a kind of work and what it starts on: Orchestrating, which is Watcher itself, and the five kinds a start names, Building, UI, Code review, Research and Computer use. Each has a list of defaults in order, and the first whose model is ready is the one in force. With Claude Code, Codex, Muse and Grok Build connected: Orchestrating on Opus at High; Building on Opus at Extra high, then Sonnet; UI on Opus at Extra high; Code review on Muse Wonder Full at Extra high; Research on Haiku; Computer use on GPT-6 Astra. Each list goes on to the other providers' models (the prototype's orders), and a role none of whose defaults is ready takes the first ready model of a provider that can do the work, so one subscription gets its own models. Building and UI may edit without asking, Code review and Research ask first, and Computer use has Full access, because Codex's sandbox on Windows can stop Computer Use below it. Orchestrating's permission is Watcher's own mode.

**2. Only the user's choices are saved.** Settings keeps `workerRoles`, the rows the user chose, by role. A row is the user's choice once any of its three settings changes, and a row set back to exactly its default in force stops being one. A provider connecting or disconnecting never overwrites a choice: while a chosen model's provider is away, new work in that role starts on the role's default in force, and the row says so. Reset to defaults removes rows, one or all. Rows are read one at a time, so a damaged row costs only itself.

**3. Every model from every provider.** A role's model picker lists every model this computer's providers offer, so any role can use any provider the user has. Orchestrating lists them too, and a provider Watcher does not run on, Devin, keeps its tile in the menu and says why, as the composer's menu says why a provider cannot take a choice now. Watcher runs on Muse since [#1087](https://github.com/millZach/Sotto/pull/1087), so with only Muse connected Orchestrating starts on Muse's own model.

**4. Starts by role.** `start_thread` takes a `role`; `delegate` already names its kind of `work` (ADR-0081 decision 9). Main fills in what the start leaves out from the role when the start is asked, from the setting and the model catalog it already holds, and never on the update path. The ceilings stay as they are: a worker never starts wider than the user's new-thread default (ADR-0073), and a delegated thread never wider than the narrower of that and the delegating thread's own permission (ADR-0081 decision 4). A permission that comes from the role is held to the ceiling rather than refused, since the user set both; a permission the request names keeps today's refusal. Whatever the request names in its own words overrides the role for that start only, and the receipt says which settings the request named, which came from the role, and when a ceiling held a permission back, naming the limit that did: the new-thread default, or the delegating thread's own permission. A start on a paired host travels exactly as before, with the model, effort and permission filled in and no role, so no host feature is needed and an older host accepts it.

**5. Orchestrating is one choice in two places.** Its model and effort are Watcher's own, the ones its composer's chips show. Watcher's first message starts it on the role, and a change to the role in Settings replaces a pick made in that first message's composer. While a Watcher runs, a change in Settings, Reset and Reset all change it the way its composer does, the model and effort together, and another provider's model starts a new Watcher that offers the last one's handover (ADR-0073); a change in its composer saves the role for the next Watcher. Its permission is Watcher's own mode in both places, and Reset leaves it as it is.

**6. The agents are told.** Watcher's instructions and `delegate`'s description name the roles, say a start should name one and leave the rest to the user's Settings, and say that the user's words in a request override a role for that request. `read_delegation` lists what each kind of work starts on now.

**7. Stable has none of it.** With the Owl feature off, Settings shows no Watcher page, neither tool offers a role, and the saved rows are kept whole: a whole save or a reset keeps them and a change to them is refused, so turning the feature on brings them back as they were.

**8. One reader.** `src/shared/workerRoles.ts` holds the roles, their defaults and the resolution every part asks: Settings, both tools, and each provider's own sub-agents ([#1042](https://github.com/millZach/Sotto/issues/1042), E14, decision 9).

**9. Each provider's own sub-agents follow the roles (E14, October 16, 2026).** Every ordinary thread on this computer carries the role table in its provider's background channel, read once when the thread launches and never on the update path: Claude Code's appended system prompt, Codex's developer instructions, Grok Build's session rules. The table names, for each of the five kinds of work, the agent to use, the model to ask for, or the delegation that reaches it. Watcher keeps its own prompt (decision 6) and starts its workers through `start_thread`.

- *Claude Code:* one agent per role whose model is a ready Claude model, passed at `initialize` as Claude Code's own agent definitions (`agents`, the SDK's `AgentDefinition`: model, effort, permission mode) and named `sotto_<role>`. Since October 26, 2026, each also says when to use it rather than what it can do, and carries a turn cap (`maxTurns`): 40 for Research, 60 for the others. Research gets a tool list (`tools`) with no Edit or Write tools, which also leaves out every MCP tool definition, and its prompt says not to change project files; it keeps the shell, which research needs, under the role's permission, Ask first by default; the others keep every tool. A subagent's first turn fell from 31k to 6.6k tokens with a tool list, and agents past 40 turns carried 54% of worker input (October 9, 2026). Each agent's permission is the role's, capped at the thread's own. A thread's permission narrowing below the widest agent's starts its CLI again, which is the path every restart-only settings change already takes; widening needs nothing.
- *Codex:* Codex 0.162.1 takes per-thread agent roles in `thread/start` and `thread/resume` config (`agents.<name> = { description, config_file }`), and only through a file (the codex-roles check on #1042). Sotto writes one TOML file per role whose model is ready in Codex's own list, with an effort that model offers, under its data folder at `codex-roles/<thread permission>/sotto_<role>.toml`, and passes them from the one place every load is built: a start, a resume, and a fork (`thread/fork`, which continues an agent or a thread at a reply, ADR-0090), which takes the same config. That a fork reads them is Codex's shared config path rather than a separate check. The file holds the model, the effort, `sandbox_mode`, `approval_policy` and `approvals_reviewer` for the role's permission capped at the thread's, and a line saying what the worker is for; never prompt text. One folder per permission keeps a thread from ever being pointed at a file wider than itself. A load writes what changed; a Settings change rewrites every folder already in use. Codex reads a role when a thread loads, so a change reaches a running thread on its next load; a thread whose confirmed permission is narrower than its role files, whether Codex confirms at once or later, lets its app-server go so the next action loads it again. A Codex older than 0.162.1, the version checked, or one whose version cannot be read gets no role files, and its threads are told to name the model and effort in `spawn_agent` instead. Codex's "Ignoring malformed agent role definition" warning for a `sotto_` role is Sotto's fault and is logged as `codex-role-malformed`, a stable name; a file that cannot be written leaves its role out and logs `codex-role-file-failed`. This is not a provider's native configuration in ADR-0017's sense: the user's `~/.codex` and `config.toml` are never written, and the files are Sotto's, passed per thread like its tool servers. The names are prefixed because a role with a built-in or user role's name was accepted without a word, and which wins is unverified.
- *Grok Build:* instructions only, in the rules a session is made with, until its sub-agents' model settings are checked. Grok Build takes rules only at creation, so a changed table reaches threads made after it.
- *Muse and Devin:* none yet. Neither MSP nor the Devin adapter has a standing-instructions channel Sotto has checked (Watcher on Muse, #1087, sends its instructions with each message instead), so neither is told until one is.
- *Another provider:* a role whose model is on another provider is reached by `delegate` with that kind of work (decision 4, ADR-0081). A launch that was offered `sotto_delegate` is told so; one that was not, such as a second-level delegated thread, is told to do that work itself. A delegated thread carries the table like any other, so its own sub-agents follow it.
- *Stable and hosts:* the runtime hands adapters the table only while `worker-roles` is on and only on this computer; stable and a headless host send none of it. A paired host's threads are not told yet: the host would read the table from its own Settings, which have no roles, and E13 starts a host's workers concretely.

## Consequences

- The model for the work is the one the user chose for that kind of work, without the agent having to know it, and the user's words still win for one request.
- A role's model can be on a provider the user has disconnected; the row says what starts meanwhile, and nothing the user chose is lost.
- Not yet built: when Watcher's own provider disconnects, offering a new Watcher on Orchestrating's next default when the user sends. Watcher does not switch by itself; until the follow-up, the room says its provider is not connected, as today.
- Provider sub-agents follow the roles (decision 9) on Claude Code and Codex by name, on Grok Build by instruction, and not yet on Muse, Devin or a paired host. That a real Codex sub-agent started as `sotto_<role>` runs on the role's model was checked once on October 16, 2026, on Codex 0.163.0, with the live check behind `SOTTO_CODEX_LIVE` (`codexSubagentRoleLive.test.ts`, one short turn): a parent on GPT-6 Astra at low effort started `sotto_research`, and its child session recorded that role and ran GPT-6 Luna, the role's model, at medium effort. A fork's role files rest on the same config path and were not checked live.

## Proof

Unit tests of the reader for one, two and four connected providers, a choice through a provider disconnecting and connecting, and Reset; for decision 9, unit tests of the role table, its instructions, Claude Code's agent definitions and Codex's role files, and integration over the fake Claude Code, Codex and Grok Build clients for agents and role files at launch, each held to the thread's permission, a narrowing that loads the thread again, a Settings change rewriting the files, a malformed role logged by name, and none of it without the feature; integration over fake providers for starts by role through `start_thread` and `delegate`, the ceiling holding a role's permission, a request's words overriding a role with the receipt saying so, and both tools without the feature; the settings repository keeping rows whole without the feature; and an end-to-end journey through Settings, under Watcher, with one delegation started by role.
