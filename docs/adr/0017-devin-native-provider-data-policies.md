# Devin keeps its native provider data policies

Accepted September 19, 2026 following Zach's explicit decision on issue #150.

Amended September 22, 2026 by ADR-0022: the single ask profile below is now one of three. A Devin thread keeps every supported request with the user only on the asking settings (Ask first, Ask and Plan). Code and Smart let Devin edit unasked, and Bypass Permissions lets it act unasked, because the user chose them; each is its own owned profile, written and read back the same way. Everything else here stands. An explicitly connected Devin CLI may use Cognition's documented hosted processing, native persistence, and provider-side usage analytics. Since October 9, 2026 (ADR-0036's amendment of that date), **Connect providers** and first-run setup's coding agents step connect an installed Devin CLI along with the other clients, at the owner's choice, as a host already did; turning Devin off in Settings › Providers keeps it off, and the CLI's own policies apply once it is connected. Sotto remains telemetry-free: it adds no analytics or crash upload, never copies native credentials, and does not log prompts, transcripts, provider protocol bodies, or keys. This separates Sotto's own privacy promise from the connected provider's policies; it does not claim an analytics opt-out that the CLI has not established.

Provider setup and the README disclose that distinction, native-account billing, and the limits of Keep local history: that setting controls Sotto's copy, not Devin's records. Cognition's account-specific training and retention settings remain the user's native provider controls; Sotto must not describe them as disabled or zero-retention without evidence. See [Cognition's CLI controls](https://docs.devin.ai/cli/enterprise/controls) and [data policies](https://docs.devin.ai/admin/security).

This decision does not relax permission authority (ADR-0004), authorize automatic permission answers, enable cloud handoff, or make unverified versions/platforms supported. The native compatibility gate remains required. Actual integration destinations and permission enforcement must be recorded before provider registration; see the [compatibility evidence](../verification/2026-09-19-devin-native-compatibility.md).

The Windows native experiment observed TLS connections to server.codeium.com and o4507463137361920.ingest.us.sentry.io during authenticated discovery and a synthetic model turn. A local CONNECT tunnel recorded only hostnames; it did not decrypt payloads, so the Sentry destination is disclosed as provider telemetry without asserting its payload. Updates and imported client configuration are disabled in the Sotto-owned profile. Enabled native MCP servers, installed plugins, native hooks, and project-native configuration are refused by the initial compatibility policy. Other account routes are not declared tested on this evidence.

Approval-required means the tested, read-back Sotto ask profile, not Devin's ineffective ACP Normal selector. The adapter pins CLI 3000.10.31, verifies the profile and native integrations before dispatch, and keeps every supported request with the user. Existing native configuration is never edited. These restrictions may reject projects or account setups that work in the standalone CLI; the error must explain how to preserve the thread and continue.

On September 20 Zach deferred native Apple silicon verification because no Mac is available and authorized completing this PR against Windows checks. This narrows the initial issue's verification scope; it does not turn fixture results into Mac evidence.

Devin native recovery uses bounded full replay because the tested ACP interface has no verified incremental cursor. The explicit exception to native recovery cost is recorded in [ADR-0016](0016-sotto-owned-history-on-an-event-store.md#amendment-bounded-devin-native-replay-september-20-2026-150); Sotto's event store and windowed history remain unchanged.

## Amendment: the compatibility boundary is the working folder and its ancestors (September 21, 2026)

The initial gate also refused native configuration anywhere below the working folder, which required walking the whole tree and bounding that walk at 25,000 directories and 250,000 entries. That half was a precaution rather than a finding: nothing recorded an observation that the CLI reads `.devin` from a descendant.

It does not. The [descendant experiment](../verification/2026-09-21-devin-config-discovery.md) against the pinned CLI 3000.10.31 on Windows shows a `.devin/mcp_config.json` resolved from the working folder and from every ancestor, and ignored one level below it — with the control that the identical file is honoured the moment its own directory becomes the working folder. What was measured is how the CLI resolves the `.devin` directory the five gated files share; `mcp_config.json` is the file that was observed taking effect, and the other four were not measured individually. The experiment also did not establish that a project-level `.devin/config.json` is read at all, so the gate keeps refusing it where it could reach a session, which stays fail-closed on the unresolved half.

The walk below the working folder, both traversal bounds, the "too large" refusal and the linked-directory refusal are therefore removed. The gate keeps the working folder and its ancestors, which is a bounded number of presence checks. Nothing else about this decision relaxes: native files are still never read, and refusals still explain how the thread is preserved.

The precaution had also made the provider unusable. Connecting passed Sotto's own user-data directory as the discovery session's working folder, and that directory holds one checkout per worktree-backed thread (ADR-0014) — past the bound on a real installation, and growing. The catalog session has no project to check: it exists only to read the model list and is deleted before any prompt. It now runs in an empty folder Sotto owns, so connecting costs the same whatever the user's threads contain. This also brings Devin in line with the other three providers, which learn their models without opening a session and read no directories to connect.

A refusal Devin states — a missing or too-old client, a compatibility check that fails, an account with no models — now reports itself in the provider snapshot rather than by throwing, as Claude's adapter does for an unready account. An uncertain connection still throws, because it has no verdict to report, and so does one a later connect has superseded; the provider switch turns both into the same refused state. Refusal is unchanged either way: the provider stays disconnected, no prompt is sent, and `providerSwitch.ts` keeps offering no model as ready while it is disconnected. Replacing this process's threads is now the last thing a connection does, so a refusal leaves the threads and messages Sotto already had instead of publishing empty ones over them.

This evidence is specific to the pinned CLI on Windows. A version that resolved configuration differently would need the gate reconsidered, which is what the version pin is for.

## Amendment: an empty thread gets a new provider session, and one thread cannot stop Devin connecting (September 26, 2026)

The [native compatibility note](../verification/2026-09-19-devin-native-compatibility.md) limited renewal to a confirmed, untouched empty thread after a clean shutdown, and kept a crashed or uncertain empty provider session as an error. That rule protected nothing. Devin saves a provider session only from its first prompt, and a [native control](../verification/2026-09-26-devin-empty-session.md) confirms that an unprompted one cannot be loaded even by the process that made it. Every empty provider session is gone the moment its process ends, however it ends. A thread whose creation stopped after Devin answered `session/new`, or whose owner crashed, therefore pointed at a provider session that would never exist again, and the thread could not recover.

A thread with no messages, which Sotto has never sent to, now gets a new provider session when Devin reports its old one missing, under the thread's recorded model and permission setting. Nothing is resent because nothing was sent. Sotto records a send, and the thread stops counting as empty, before the prompt goes out. A thread with any message keeps the old refusal, and its missing provider session is never replaced. This also changes the rule about a lost acknowledgement. When the answer to a `session/new` is lost, the next open asks Devin for the old provider session and makes another. The one whose answer was lost is left behind empty, and Devin never saves it.

Connecting also reopened every observed thread and failed the whole provider when one of them could not be opened. A single broken thread left Devin marked as needing attention, and Retry connection could not clear it while that thread stayed open in a pane. A thread that cannot be opened while connecting is now an error on that thread, with Devin's reason in the provider snapshot. The provider stays connected, and its other threads stay usable. An uncertain or superseded connection still throws, as before.

## Amendment: a send checks once and reads nothing while Sotto holds the session (October 6, 2026, #770)

"Verifies the profile and native integrations before dispatch" stays a fresh check before every prompt. Nothing here caches it: a plugin or MCP server added between two sends is refused at the second. What changed is that it runs once and side by side. A send used to check three times before `session/prompt` (its own check, the check inside a history read, and a revalidation after that read), each running `plugins list` and then `mcp list` one after the other. It now runs the profile's presence checks, then both lists and the thread's own process reading the profile back, all together, and judges them in a fixed order so a refusal reads the same however they finish. When opening the session was part of the same send, that open's check is the send's and is not repeated; checks are numbered as they start, so a clock that steps back cannot make an old check pass for a new one. Starting a process still checks the lists before the process exists, and opening or creating a session still checks again after Devin has loaded it, because a load is what can turn an integration on. A first send to a thread with no session open therefore still runs the lists twice: once so nothing starts with an integration on, once after the load. One case is refused a prompt later than before. A replay read loads the session in a second Devin process, so it can turn an integration on too. The read before a send used to come before the prompt, and its revalidation refused that prompt. Now the read that turns it on may be the one confirming a prompt already sent: that prompt stays uncertain and is never resent, and the next send is refused by its own check (`devinPolicyBoundary.test.ts`).

A send no longer reads history before its prompt when every earlier dispatch on the thread is confirmed. A history read of a held session starts a second Devin process that loads the session, replays all of it, and is then refused the session because the thread's own Devin process holds it. The [native compatibility note](../verification/2026-09-19-devin-native-compatibility.md) recorded that refusal during a turn, and the [send-path note](../verification/2026-10-06-devin-send-path.md) records it between turns. While the thread's own process holds the session no other client can write to it, so the replay that process loaded when it opened and its stream since are the whole history. The stale-input check before a guarded follow-up compares against that. Any other refresh of a held session reads the replay only when a dispatch is still unconfirmed. The read before a send leaves that to the send, which makes it just before its prompt, so a replay that contradicts an earlier dispatch refuses the send as it always did. The poll still reads each watched thread Sotto holds every fifteen seconds, as before. A session Sotto does not hold is read as before, and separately authored input is still found when its replay is read. A thread that has just been opened or created has just been read, so the poll's fifteen seconds start there.

Acceptance still comes from native evidence and an uncertain prompt is still never resent. Devin sends no echo of a prompt, so a send now takes the thread's own stream as evidence first. Devin streams a turn's work (message and thought chunks, a new tool call, a plan, a permission or question request) only while a prompt runs, and only the process holding the session can prompt it, so work streamed after the prompt went out is that prompt being worked on. A tool call update is not counted, because background work from an earlier turn may still report. When the stream shows nothing for a second and a half, or the turn ends without showing any work, the send reads the replay of its saved dispatch identity, then again every second and a half, until the request deadline. The reply is shown as it streams from the moment the stream shows the prompt was taken.

This makes delivery evidence weaker in one respect, which is accepted. A prompt taken on the stream is reported accepted before any replay has shown its dispatch identity. The replay still confirms it afterwards: on one read of the adapter's own once the turn ends however it ends, on any other read of the thread before that, or at the latest just before the next send. The coordinator's read after an accepted send is not one of them, since the workspace answers it from the echo it already holds (#765). A replay that does not match the saved digest then leaves that dispatch uncertain, says so as a provider notice, and refuses the next send; it does not turn the earlier send back into an uncertain one. While a turn runs, the poll reads it at the busy pace only until the turn shows it was taken; after that the thread's own stream carries it and the poll reads it at the idle pace.

The replay's size limit (ADR-0016) is met only where a replay is read. A send to a held thread with every dispatch confirmed reads none, so a thread whose history has grown past the limit is found at the next replay read instead. A poll that fails on it says so as a provider notice; the read that confirms the next turn fails the same way, which leaves that dispatch unconfirmed, so the send after it reads the replay first and is refused. The limit can therefore stop a thread a prompt or two later than it did; nothing is resent either way.

## Amendment: Devin's telemetry export is pinned off, and a newer Devin says so (October 14, 2026, #1045)

Devin CLI 3000.11.1 added OpenTelemetry export, and `_cognition.ai/config/read` began returning a top-level `otel` block. The readback refuses any block it does not know, so updating Devin stopped every Devin thread. The refusal also reached the provider tile only as "Devin sent an invalid response.", because the process treated a readback that throws as a garbled reply. Nothing was lost, but nothing could run.

Sotto's owned profiles now pin export off with `"otel": { "enabled": false }`. An owned profile is never rewritten, since a changed one is refused, so this is a new profile version: `approval-policy-v2.json`, with `-edits` and `-everything` beside it. The asking profile keeps the unsuffixed name of its version, which amends ADR-0022's note that it keeps the original file name. Version 1 files are left where they are, unused. The pin is explicit rather than inferred from no endpoint being set. Before this, export stayed off only because nothing named a destination, and a destination added later would have started it.

What the pin does was checked on Windows on October 14. Neither run sent `session/prompt`, and no Devin turn ran.

- **3000.11.3 reads the block from the `--config` profile.** With an endpoint pointing at a local listener and an empty session open, it posted to `/v1/logs` and `/v1/metrics`. With the same endpoint and `enabled: false`, it posted nothing.
- **The pinned 3000.10.31 accepts the key.** It initialises, its readback passes, and `plugins list` and `mcp list` answer as before.
- **Both CLIs connect through the adapter with the new profile.** The run went through the integration lists, `initialize`, `session/new` and the readback, then `session/delete`. 3000.11.3 connects as a newer, unverified version, as the tile already says for one.

The readback accepts four answers and refuses everything else, any endpoint, header or resource attribute included:

- `otel` absent, because a CLI older than the block may drop it.
- The block exactly as the profile writes it.
- The pinned block filled in with defaults, which 3000.11.3 usually reports.
- The CLI's own default, `enabled: true` with no destination and every other field at its default.

The last two answers were not steady. 3000.11.3 sometimes read back its own default while the profile pinned export off, and 3000.10.31 sometimes left the block out and sometimes echoed it. Both behaviours came in runs a few minutes apart, and nothing Sotto controls explained them. None of the four answers can export. Export needs an endpoint in the block. `devinEnvironment` passes Devin no `OTEL_*` variable, and Devin's own documentation says a variable cannot start export without one. Refusing the default block would have made Devin threads stop at random, which is the failure this amendment fixes.

A refusal is now worded for the user. It reaches the provider tile, or the send it stops, as it is (`DevinRefusal`), and nothing has been sent when it does. Any other `otel` block says Devin reports telemetry settings that Sotto's profile does not set, such as a collector to send to. Any other top-level block the readback has never seen says the Devin version is newer than the one Sotto checked, and that the threads are kept. A block Sotto knows that reads back wrong keeps the old refusal.

This changes nothing else in this decision. `DEVIN_CLI_VERSION` stays at 3000.10.31. Sotto still passes Devin no tool servers; that is E12 (#1040), which this unblocks.

## Amendment: Devin threads get Sotto's tools, from CLI 3000.11.92 (October 16, 2026, #1040)

Devin CLI 3000.10.31 starts and initializes the MCP servers a client passes on ACP `session/new`, but never attaches them to the session, so a thread could not have Sotto's tools. 3000.11.1 fixed that ("ACP clients can use MCP servers supplied in `session/new` or `session/load`"). Sotto's floor, `DEVIN_CLI_VERSION`, moves from 3000.10.31 to 3000.11.92, the newest release on October 16, and a Devin thread is now given Sotto's own servers as Claude Code, Codex, Grok Build and Muse threads are (ADR-0056). An older client is refused at connect as too old, with the version to install, and its threads are kept. Sotto still writes none of Devin's configuration.

What was checked on Windows on October 16, against 3000.11.92 unpacked from its zip and never installed. No `session/prompt` was sent, and no Devin turn ran. Devin's own folders were backed up first and restored afterwards with identical SHA-256 manifests.

- **Servers attach.** Through Sotto's own adapter, a thread was made under each of the three owned profiles with the browser server, the visual server and a probe server, and made again after a reconnect. Devin initialized the browser and visual servers for every thread, which its cache recorded with each server's own instructions. The probe offered an MCP prompt, which joined the first session's commands (52 before, 53 after). Devin did not connect to the probe again: its address and token never changed, and Devin keeps what it learned of a server by its configuration. Over raw ACP, a new stdio probe and a new HTTP probe both joined (52, 53, 54).
- **The readback names four new defaults,** and Sotto's profile is unchanged (version 2). `proxy.gzip` reads `true` and `agent.subagent_model` reads `null`; both are now part of the expected readback. `typewriter` is how streamed text is drawn. `local_tools_bypass_permissions` would start `devin connect` sessions in Bypass Permissions, so the readback accepts it only as `false`. Anything else still refuses.
- **`mcp list` adds a `Source:` line** naming the file or plugin each server came from. The parser accepts at most one per server and still refuses any enabled server. `plugins list` still says "No plugins installed." on the checked account.
- **Rules stay within the working folder and its ancestors.** `devin rules list` from a working folder lists `.devin/rules/` at that folder and its ancestors, including subfolders of a rules folder, and not one in a folder below the working folder. With `read_config_from.windsurf` off, `.windsurf/rules/` is not listed. Rules are instructions to the model, like `AGENTS.md`, not configuration the gate refuses. Rules Devin finds while a turn reads files below the working folder were not checked, because that needs a turn.
- **Sign-in and the model catalogue read as before.** `initialize` still offers `devin-browser`, and a session still lists its models under `model`. The checked account lists one model, on 3000.10.31 and 3000.11.92 alike.
- **Locks, lost turns and Bypass Permissions need no change.** A lock refusal is still `-32015`, and Sotto keeps only the code, never the text that now names the holding process. Sotto never asks Devin to force a session open. A prompt answered with an error, now a structured retryable one when Devin's channel closes, stays uncertain and is never resent, as before. Bypass Permissions no longer opening an editor review for an edit matches the `everything` allowance, which already lets Devin edit unasked.

How the servers are passed. The thread's own process passes them on every `session/new` and `session/load` it sends, so a session made again or loaded later has them too. The catalog session and a history read never prompt, and get none. A client that does not say it takes HTTP servers gets none, and its thread says its tools were withheld.

Devin writes its own cache of them. Passing servers makes Devin rewrite `%LOCALAPPDATA%\devin\cli\mcp\descriptions.json`, with one entry per server configuration, keyed by a hash. Each Sotto thread's servers carry their own token, so each adds entries, and the rewrite dropped the one entry the cache held before. This is Devin writing its own cache, not Sotto writing native configuration.

Devin asks before every call to one of them, and the user answers. The asking profiles (Ask first, Code, Smart, Ask and Plan) keep `mcp__*` among the rules that ask, so Devin sends `session/request_permission` before each call to one of Sotto's tools. Sotto shows it as "Use Sotto's visualize tool", with the call's whole input, and offers only Allow once and Deny. It refuses to show any request whose input Devin says it cut short, and any for an MCP tool that is not one of this session's own, whatever its input looks like. An answer goes only while the call still names the same tool with the same input; otherwise nothing is allowed and the session stops, as for a command whose input changed. Unlike Grok Build and Muse, nothing answers Devin's question on the user's behalf (ADR-0004). Bypass Permissions allows `mcp__*`, so there Devin calls them unasked.

Two things are not yet proven, because each needs a turn: that the model sees the tools, since Devin calls no `tools/list` before a prompt, and that a loaded session keeps them. Which field of Devin's tool call carries the tool's name was not seen either; Sotto accepts the meta's tool name or the title. One live check behind `SOTTO_DEVIN_LIVE` settles all three (`devinLive.test.ts`, two turns). Under ADR-0020's rule that a client passes actual call verification before it gets Sotto's tools, this change does not ship until that check has passed.
