# Devin keeps its native provider data policies

Accepted September 19, 2026 following Zach's explicit decision on issue #150.

Amended September 22, 2026 by ADR-0022: the single ask profile below is now one of three. A Devin thread keeps every supported request with the user only on the asking settings (Ask first, Ask and Plan). Code and Smart let Devin edit unasked, and Bypass Permissions lets it act unasked, because the user chose them; each is its own owned profile, written and read back the same way. Everything else here stands. An explicitly connected Devin CLI may use Cognition's documented hosted processing, native persistence, and provider-side usage analytics. Sotto remains telemetry-free: it adds no analytics or crash upload, never copies native credentials, and does not log prompts, transcripts, provider protocol bodies, or keys. This separates Sotto's own privacy promise from the connected provider's policies; it does not claim an analytics opt-out that the CLI has not established.

Provider setup and the README disclose that distinction, native-account billing, and the limits of Keep local history: that setting controls Sotto's copy, not Devin's records. Cognition's account-specific training and retention settings remain the user's native provider controls; Sotto must not describe them as disabled or zero-retention without evidence. See [Cognition's CLI controls](https://docs.devin.ai/cli/enterprise/controls) and [data policies](https://docs.devin.ai/admin/security).

This decision does not relax permission authority (ADR-0004), authorize automatic permission answers, enable cloud handoff, or make unverified versions/platforms supported. The native compatibility gate remains required. Actual integration destinations and permission enforcement must be recorded before provider registration; see the [compatibility evidence](../verification/2026-09-19-devin-native-compatibility.md).

The Windows native experiment observed TLS connections to server.codeium.com and o4507463137361920.ingest.us.sentry.io during authenticated discovery and a synthetic model turn. A local CONNECT tunnel recorded only hostnames; it did not decrypt payloads, so the Sentry destination is disclosed as provider telemetry without asserting its payload. Updates and imported client configuration are disabled in the Sotto-owned profile. Enabled native MCP servers, installed plugins, native hooks, and project-native configuration are refused by the initial compatibility policy. Other account routes are not declared tested on this evidence.

Approval-required means the tested, read-back Sotto ask profile, not Devin's ineffective ACP Normal selector. The adapter pins CLI 3000.10.31, verifies the profile and native integrations before dispatch, and keeps every supported request with the user. Existing native configuration is never edited. These restrictions may reject projects or account setups that work in the standalone CLI; the error must explain how to preserve the thread and continue.

On September 20 Zach deferred native Apple silicon verification because no Mac is available and authorized completing this PR against Windows checks. This narrows the initial issue's verification scope; it does not turn fixture results into Mac evidence.

Devin native recovery uses bounded full replay because the tested ACP interface has no verified incremental cursor. The explicit exception to native recovery cost is recorded in [ADR-0016](0016-sotto-owned-history-on-an-event-store.md#amendment-bounded-devin-native-replay-september-20-2026-150); Sotto's event store and windowed history remain unchanged.

## Amendment: the compatibility boundary is the working folder and its ancestors (September 21, 2026)

The initial gate also refused native configuration anywhere below the working folder, which required walking the whole tree and bounding that walk at 25,000 directories and 250,000 entries. That half was a precaution rather than a finding: nothing recorded an observation that the CLI reads `.devin` from a descendant.

It does not. The [descendant experiment](../verification/2026-09-21-devin-config-discovery.md) against the pinned CLI 3000.10.31 on Windows shows a `.devin/mcp_config.json` resolved from the working folder and from every ancestor, and ignored one level below it — with the control that the identical file is honoured the moment its own directory becomes the working folder. What was measured is how the CLI resolves the `.devin` directory the five gated files share; `mcp_config.json` is the file that was observed taking effect, and the other four were not measured individually. The experiment also did not establish that a project-level `.devin/config.json` is read at all, so the gate keeps refusing it where it could reach a session, which stays fail-closed on the unresolved half.

The walk below the working folder, both traversal bounds, the "too large" refusal and the linked-directory refusal are therefore removed. The gate keeps the working folder and its ancestors, which is a bounded number of presence checks. Nothing else about this decision relaxes: native files are still never read, and refusals still explain how the thread is preserved.

The precaution had also made the provider unusable. Connecting passed Sotto's own user-data directory as the discovery session's working folder, and that directory holds one checkout per worktree-backed thread (ADR-0014) — past the bound on a real installation, and growing. The catalog session has no project to check: it exists only to read the model list and is deleted before any prompt. It now runs in an empty folder Sotto owns, so connecting costs the same whatever the user's threads contain. This also brings Devin in line with the other three providers, which learn their models without opening a session and read no directories to connect.

A refusal Devin states — a missing or too-old client, a compatibility check that fails, an account with no models — now reports itself in the provider snapshot rather than by throwing, as Claude's adapter does for an unready account. An uncertain connection still throws, because it has no verdict to report, and so does one a later connect has superseded; the provider switch turns both into the same refused state. Refusal is unchanged either way: the provider stays disconnected, no prompt is sent, and `providerSwitch.ts` keeps offering no model as ready while it is disconnected. Replacing this process's threads is now the last thing a connection does, so a refusal leaves the threads and messages Sotto already had instead of publishing empty ones over them.

This evidence is specific to the pinned CLI on Windows. A version that resolved configuration differently would need the gate reconsidered, which is what the version pin is for.
