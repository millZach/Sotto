# A thread shows the pictures its agent made as tiles

## Status

Accepted October 31, 2026, by Zach's picks on `docs/prototypes/inline-media-prototype.html`: B (tiles), scene 2 (the owl at the easel), an Owl feature first, and all four sources. **Number provisional until merge** (docs/agents/domain.md). The plan is `docs/plans/inline-media.md`.

Amends [ADR-0031](0031-images-are-staged-once-and-carried-by-handle.md): a second store, kept the same way, holds the pictures an agent made. Leaves [ADR-0056](0056-an-agent-can-draw-a-visual-in-its-thread.md)'s visuals as they are.

## Context

Agents look at pictures and make them. Sotto's browser and the cloud iPhone hand a screenshot back to every provider; Claude Code reads a picture file as an image; Codex and Cursor generate images; agents write screenshots, GIFs and recordings to the working copy. Until now Sotto kept only the words of a tool result and dropped every picture on purpose. A picture arrives as base64 inside the provider's message, sometimes megabytes of it, and the activity record it would ride in is copied, compared and broadcast many times a second while a thread works (`streamingCopyBudget.perf.test.ts`, `ownerScaleWorkBudget.perf.test.ts`).

Zach wants those pictures in the thread, on the desktop and the iPhone, and wants Sotto no slower for it.

## Decision

**1. Handles, never bytes.** An activity record carries an optional `media` list, at most eight handles, each the picture's digest, type, size in bytes and pixels, name and where it came from. The bytes go to the **thread media store** once, by SHA-256, as staged images do (ADR-0031). A record, a window broadcast, a saved thread and the iPhone's live updates carry the handle alone. The record's change signature counts its handles, so a record that gained a picture is sent again.

**2. The thread media store.** `<dataDir>/thread-media/`, one file per content, beside `thread-media.json`, which holds each picture's size and when it was last captured: no names, no text, no thread. Part 4 adds the files of the videos turns wrote, by digest (decision 13). It keeps the newest 1 GiB, and past that the pictures captured longest ago go first. While Keep local history is off it holds the pictures in memory alone, at most 128 MiB, as the attachment store holds staged images; turning history off lets every picture go at once. Its upkeep reads its own index, so its cost follows the number of pictures, never the length of a history. A picture that is not one of the four image types, that is not the type it claims, or that is over 10 MiB gets no handle.

The store does not track which thread captured a picture. Inside an adapter a thread is the provider's session, not Sotto's thread (ADR-0002), so a sweep that kept "what a living thread captured" would have to map sessions to threads, and a wrong answer would delete someone's pictures. A size limit lets nothing go that is still new.

**3. Captured where the adapter reads the tool result.** The adapter decodes the image content once, hashes it and puts the handle on the row it is already writing, and hands the bytes to the store, which writes them off the update path. A replayed history meets content the store already holds and writes nothing. A picture is captured only from the thread's own tool results, never from text the agent wrote.

**4. Tiles.** A turn's pictures show as 208x140 tiles under its work, whether its steps are open or folded, in threads and in Watcher. A press opens the viewer (#1059). A tile asks for its thumbnail when it comes within a screen and a half of view, and lets it go once it is further than that; the window keeps the newest 48 thumbnails between scrolls. On the desktop, main makes the thumbnail at tile size with Electron's image tools, and the window never decodes the full picture for a tile. A remote host's picture is read whole from its host, once, and its thumbnail is made by the desktop.

**5. The iPhone reads a picture when its tile shows.** `thread-media` is a new host feature and a new request of that name, answered with the picture's bytes only for a handle on a record the host holds for that thread, on the same one-at-a-time guard as a sent photo's preview. The phone makes its own thumbnail, as it does for sent photos.

**6. Owl first.** All of it sits behind the Owl feature `inline-media`. With it off, Sotto captures nothing, shows no tile and offers no command, and a record saved with handles keeps them for a build that has it.

## Generated images (part 2), October 31, 2026

**7. An image an agent generates is a step that makes an image.** Codex's `imageGeneration` item and Cursor's `cursor/generate_image` each become a tool step marked `generates: 'image'`, titled by what the image shows when the provider says. Codex's step was dropped until now; Cursor's named only the file. The marker is on the record and in the summary the iPhone is sent, so both clients know a step is making an image before any picture exists.

**8. A generated image is captured from its bytes, or from the file its provider saved.** Like the step itself, only while `inline-media` is on; stable shows Codex's image items no more than it did. Codex's finished item carries the image's base64 bytes, captured as a tool result's are, its type read from the bytes. When it carries only the file Codex saved it to, as Cursor's always does, the adapter reads that file once, off the update path, and adds the handle to the step when the read lands. The file is read only for the step the provider made, only up to the 10 MiB image limit, and is kept only if its own first bytes say it is one of the four image types, whatever its name. A Cursor path that is not absolute is read from the thread's folder.

**9. The owl at the easel plays while an image is made.** A step that makes an image, runs, and holds no picture yet shows a tile of the same size with Zach's scene 2: the owl paints on an easel under the night sky, in text, on a 12-row grid with air between its lines, so its characters stay readable in a tile. No provider says how far an image has got, so the painting slows as it goes and the picture arriving ends it. It draws nothing until it first comes on screen, then writes at most twelve frames a second straight into the page, never through React, only while it is on screen and the window is shown; off screen, hidden or once the picture lands it draws nothing and holds no timer, and under reduced motion it draws one still frame when it first shows and holds it. The iPhone plays the same scene, ported to Swift, on the same terms. `inlineMediaTranscript.perf.test.tsx` holds it to that.

## Pictures from the other tools (part 3), November 1, 2026

**10. Every provider's tool pictures, by the same rules.** Grok Build, Devin, DeepSeek Harness and Cursor hand a tool's picture back as ACP image content, captured as decision 3 says. An update that holds no more pictures than its step has handles for hashes nothing, and Cursor's replay of a thread, which comes each time its provider session opens, takes the handles the thread's step already holds. Codex's Computer Use hands its screenshots back as MCP image content (`nodeRepl.emitImage`), so they are an MCP tool's pictures, on its Computer Use step.

**11. A picture Codex viewed is read from the file it names.** Codex's `view_image` arrives as an `imageView` item that names a file and carries no bytes. With `inline-media` on it becomes a **View image** step naming the file, and once the step is done its file is read as decision 8 reads a saved image: once, a file that held no picture included, off the update path, only up to the image limit, its type from its own bytes, and only for a path Codex resolved, never one relative to Sotto's own folder. Without the feature the item stays dropped, as before.

## Files an agent writes (part 4), November 1, 2026

Zach's picks on November 1: written files in git-ignored folders count too, and a video plays from where it was written rather than being copied.

**12. A turn's written pictures and videos are found once, when it ends.** With `inline-media` on, the workspace notes when each send begins a turn and the folder it goes to, and nothing more while the turn works. When the thread stops running, it lists that folder's picture and video files with Git, once, off the update path: tracked files changed since the last commit, untracked files and git-ignored files (Playwright's `test-results/`, `artifacts/`), never `node_modules`, and none at all past 5,000 or outside a Git working copy. A file whose last change came after the turn began is one the turn wrote; the newest eight are kept. A file another thread or program changed in the same folder during the turn is taken for this turn's: the folder does not say who wrote it. Every host does this, headless ones too, since the workspace runs on each.

**13. One step shows them.** The turn gains a Sotto step, **Pictures and videos it wrote**, of the kind that changes files, naming each file as written, placed with the turn's work. Its name is each client's own words, since the step is Sotto's. A written picture or GIF up to the image limit is kept in the thread media store as any picture is. A video (MP4, QuickTime or WebM, by its own first bytes) up to 200 MiB is not copied: its handle carries the SHA-256 of its bytes, read once in parts, its size and its name, and no path. Where it is, its size and when it last changed go to the thread media store's index under that digest, on the host alone, the newest 1,000 of them, and with Keep local history off in memory only. It is read only while the file is still that size and changed last then; a file written again since is no longer the video, and its tile says it could not play and to ask the agent to write it again. The step's files are named relative to the thread's folder, as any file change's are.

**14. Videos and GIFs play inline, never on their own.** On the desktop a video's tile loads only its first frame when it comes near the screen, lets go of it further away, plays when pressed, and pauses the moment it leaves the screen. The window's player reads it through `sotto-media://video/<thread>/<record>/<handle>`, which main answers a range at a time from the 8 MiB part that holds it, read from the file on this computer or asked of the host that runs the thread (`thread-media-part`); the window never sees a path. A GIF's tile shows its first frame still, with a button that plays it in the tile until it is pressed again or leaves the screen, on the desktop and the iPhone. The viewer steps through pictures; a video plays in its own tile.

**15. The iPhone fetches a video only when it is tapped.** `thread-media-video` is a new host feature and `thread-media-part` its request, on the same one-at-a-time guard as `thread-media`. A tapped video up to 50 MiB comes in its 8 MiB parts, each written to a file as it arrives and the whole checked against its digest, then plays in its tile; it pauses when it scrolls away. A larger one says to play it on the desktop. An iPhone from before this part shows no video tile, since it draws only pictures.

## Mark up (part 5), November 1, 2026

The prototype's Mark up view, which Zach saw when he picked, is the design: five tools, three inks, Undo and Redo, Cancel and Add to reply, and on the unfolded Duo the pen drawing while a finger moves the picture.

**16. Any picture in a thread can be marked up, and the copy goes into the reply.** With `inline-media` on, the viewer of a thread pane, the desktop's or the iPhone's (Watcher's on the iPhone too), has **Mark up**: an agent's picture or the user's own sent image. The editor draws an arrow, a circle, a box, a pen line or a note over the picture in its own pixels, with Undo and Redo, and on the desktop lists the marks beside it, each with a button that takes it off. **Add to reply** draws the marks onto a copy and adds it to that pane's reply box exactly as a pasted or chosen image goes in: the box's own limits, refusals, resizing and staging (ADR-0030, ADR-0031). Nothing about the marks is kept: the copy is the only record, and the picture in the thread is never changed. A box that can't take a picture says why before the editor opens, for the reasons that box refuses any picture: on the desktop an archived thread, an answer pending, a model that reads no images or a draft already holding all it can; on the iPhone a computer not connected, a model that reads no images or a full box. A refusal after drawing, such as a copy too large for what the draft already holds, keeps the editor open with its marks: on the iPhone the copy is prepared and checked before Add to reply closes the editor. A viewer outside a thread pane has no Mark up, since its copy would have no reply to go to.

**17. The inks are the theme's.** Red and amber are the theme's error and warning colours at full strength (`--tt-ink-red` and `--tt-ink-amber` on the desktop, the danger and warning roles on the iPhone), since the text roles are tuned for the theme's surfaces and on some themes (Omarchy's) read as the text colour itself; plain is the theme's text. A note's words take whichever of the theme's canvas and text reads better on its ink. The editor reads the inks when it opens and again when the theme or appearance changes, and the copy takes them as they are when it is made.

**18. The copy is made where the picture already is.** On the desktop the copy is the full picture the viewer holds, drawn on a canvas at its own size and sent as a PNG, so a 1920x1200 screenshot goes in at 1920x1200 before the reply box's usual resizing. On the iPhone it is the picture the viewer holds, at most 2048 pixels on its longer side, so marking asks the computer for nothing more. The editor reads nothing either: it draws the viewer's picture. A pen's pressure widens its line on both. On the iPhone, once an Apple Pencil has drawn, or when Only Draw with Apple Pencil is on, the pen draws and a finger moves and zooms the picture, until **Draw with a finger too** says otherwise. From the desktop's keyboard, A, O, B, P and T pick a tool, the picture takes focus and Enter starts a mark at a cross the arrow keys move, and Enter ends it; Ctrl+Z, Ctrl+Shift+Z and Ctrl+Enter (Command on a Mac) undo, redo and add, unless the dictation hotkey holds the chord.

## Consequences

- A thread's pictures cost disk, at most 1 GiB, while history is kept. Deleting a thread does not let its pictures go at once; they go as newer ones take their place, or all at once when history is turned off.
- On the iPhone this first part shows a thread's pictures; Watcher's page on the phone carries no steps yet, so Watcher's own pictures show on the desktop only.
- Pictures an agent saw that were never in a tool result (a page it read as text, a picture only in its own reasoning) still do not show.
- A generated image a provider saved outside the thread's folder is read from where the provider said it saved it, on the computer the thread runs on. Nothing else in that folder is read.
- A generation that fails or is stopped shows no tile; its step says what happened, in Codex's case why when Codex says (its usage limit).
- A Codex item that names its image only by `fileId`, Codex's own attachment store, with neither bytes nor `savedPath`, shows the step without a picture: Sotto has no documented way to read that store.
- Every later part of the plan (generated images, other providers, written files and video, mark up, callouts) adds sources and actions to these handles and tiles, not a new path for bytes. Part 4's videos are the one exception to the store: they are read from where they were written, by handle, and never copied.
- A video a turn wrote is gone from its tile once the agent writes over it, moves it or deletes it, and a turn that wrote more than eight pictures and videos shows its newest eight.
- A marked copy is a new attachment: the agent sees the marks, never the marks as data, and once it is sent it is a sent image like any other. Marks can't be taken back off a copy already added; Undo works only while the editor is open.
- Mark up adds nothing to a thread until it is opened: no state, no reads and no work on the update path.
