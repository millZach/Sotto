# Antigravity is a thread provider, run as T3 Code runs it

## Status

Accepted November 20, 2026. Zach asked for Google Antigravity as a provider, "reference how T3 code does it and match that as close as possible", and answered the question cards the same day. Where T3 Code's way and Sotto's conventions part, he chose T3's every time: stable rather than Owl, all four of `agy`'s sign-ins, Sotto downloading `agy` itself, token counts and the account's limits, and T3's four permission modes with Sotto answering `agy`'s requests by the mode. He chose Watcher and short text on Antigravity, paired hosts and phones in the same change, and design B of the [design drafts](https://github.com/millZach/Sotto/blob/prototype/antigravity-provider/docs/prototypes/antigravity-provider-prototype.html) (tag `prototype/antigravity-provider`): signing in on the row, the model menu grouped by maker. ## Decision

**The provider.** Antigravity joins as a thread provider, id `antigravity`, shown as **Antigravity**, on stable with no Owl gate. Its adapter speaks ACP over `agy acp` on stdio, one process per thread (ADR-0038): `initialize` with protocol 1, then `authenticate` with the sign-in method on every start, as T3 sends it eagerly; `session/new` or `session/resume`; `session/prompt`; `session/cancel`; `session/update`; and `session/request_permission`. The floor is 1.5.0, T3's, read from `initialize.agentInfo.version`; 1.5.13 is the version built against.

**Sotto's own Antigravity folder.** Every `agy` Sotto starts runs with `--gemini-dir <directory>/antigravity/gemini --app-data-dir antigravity-acp` and `GEMINI_HOME` set to the same folder, as T3 gives each instance a profile of its own, so a thread never reads or writes the user's own `~/.gemini`, and the user's own `agy` never lists Sotto's conversations. The one exception is the user's own MCP servers: since parity slice 3, Sotto reads `~/.gemini/config/mcp_config.json` (`agy`'s own global file) each time a provider session starts or resumes and hands its servers to `session/new` and `session/resume` after Sotto's own, as Claude Code reads the user's own setup. Local servers go to every `agy`; HTTP ones only where it takes HTTP servers, and `agy` sends their headers to their own addresses, as it does when the user runs it. A server with the name of one of Sotto's is left out, and so is one that needs a setting ACP cannot carry (`enabledTools`, `disabledTools`, `cwd`, `oauth`, `authProviderType`), since `agy` 1.5.14 ignores them in `session/new` and the server would otherwise run with tools the user hid, in another folder or without its sign-in. Watcher's thread gets none of them. Their variables and headers, keys among them, go to `agy` on that computer only and are never logged; on a host, the host's own file is read. The environment is Sotto's allow-list, so no Google key or project variable of the user's reaches it, plus T3's: `AGY_ACP_FORCE_FILE_STORAGE=1`, `AGY_CLI_DISABLE_AUTO_UPDATE=1`, temporary files under Sotto's folder, and for a Google account `SSH_CONNECTION`, which makes 1.5 keep the sign-in in that folder rather than the system keyring. `BROWSER` is never set for a thread. On a headless host the folder is under the host's data directory.

**Getting `agy`.** Sotto downloads it, as T3 does: Google's platform manifest from `antigravity-cli-auto-updater-974169037036.us-central1.run.app`, the build itself only from `storage.googleapis.com/antigravity-public/antigravity-cli/`, refused unless its SHA-512 matches the manifest's, into `antigravity/runtime/<platform>-<arch>/versions/<version>/`. On Windows the build is `agy.exe` itself; elsewhere a `.tar.gz` holding one file, read out with the system's own `tar`. A version a running thread uses is leased and never removed under it. Antigravity's row offers Install, with its progress in plain words, Cancel and **Remove downloaded Antigravity**; the update line updates a copy Sotto downloaded and names any other. Once `agy` is updated, each thread moves onto it as it goes idle, and the account's models are read again from the new client, as a connect reads them (parity slice 8); a read that fails keeps the list from before until the next connect. The program is looked for in T3's order: the binary path in Settings, then Sotto's download, then `agy` or `antigravity` by Sotto's CLI lookup (ADR-0036). Only a program named `agy` or `antigravity` is started, and only this machine's own Settings set the binary path; a paired client is refused.

**Signing in, design B.** The row offers `agy`'s four methods as one choice, each with its steps in the opened row:

- **Google account**, the default: T3's argv plus `--login`, through Sotto's paste-code sign-in (ADR-0200, ADR-0037). Main opens the `accounts.google.com` page only on a press, and the user pastes back the code, or the whole address, of the `antigravity.google` page Google lands on. On a host the page opens in this computer's browser and the code goes to the host's `agy`.
- **Gemini Enterprise**: ACP `authenticate` with `oauth-business`, the Google Cloud project and location written to `agy`'s own settings, finished in a browser on this computer, only on a press of Sign in, with fifteen minutes to finish. A host cannot finish it, since the page returns to `agy`'s own callback on the machine it runs on; T3 forwards that callback, which this version does not.
- **Gemini API key** and **Agent Platform** (Vertex AI, with a key or a project and location): the key is the credential store's `antigravity` slot on this computer, handed to `agy` in its environment only (`GEMINI_API_KEY` or `GOOGLE_API_KEY`), never in a file, an argument or a log, and the window learns only whether one is saved. A key is not copied to a paired host.

**Sign out** stops Antigravity's processes and sends `agy`'s ACP `logout` in Sotto's own folder; threads and their history are kept.

**Models.** The account's own, read from a session's `model` option on connect in a scratch session, each model chosen in turn to read its thinking levels, then that session's files removed; never a list shipped with Sotto. A `thought_level` option's values are the model's effort levels in Sotto's order (ADR-0044), set with `session/set_config_option` before the prompt that needs them, as the model is. The menu groups the models by **model maker** (Google, Anthropic, OpenAI), as Cursor's does (ADR-0128), and the model `agy` starts on leads.

**Permissions.** T3's four modes. **Auto** runs `agy`'s own Auto mode, offered only where the account's sessions offer it, and leaves every request `agy` still raises to the user. `agy` refuses an edit-only or run-everything session mode, so **Ask for approval**, **Allow edits** and **Full access** run `agy`'s `default` mode and Sotto answers by the thread's mode, as T3 does: on Allow edits, a request whose tool is an edit, delete or move is allowed once; on Full access, every permission request is allowed once. Ask for approval leaves all of them to the user. Sotto changes a thread's settings only while it rests with no request waiting, as for every provider, and a mode change reaches `agy` at once, before the next prompt; if `agy` will not take it, a turn it is running is stopped. Sotto answers allow once or reject only, never allow always, which would save a rule in Sotto's folder for every later thread. A request whose tool call ID starts `interaction_` is a question as T3 reads one, and is a question card answered with the chosen option, never an approval, on every mode. `agy`'s own `ask_question` tool asks through ACP's `elicitation/create`, which 1.5.14 sends only to a client that offers `elicitation.form` and otherwise writes into its reply as text; so Sotto offers forms (parity slice 4), shows the form's questions as one question card, each with its choices, several where the question takes several, and the user's own words where it offers an "Other" field, and answers `accept` with them, `decline` when the user skips the card, or `cancel` when the turn ends first. A question may be left unanswered, since `agy`'s form as 1.5.14 sends it requires none; one a form does require takes one of its choices, never words alone, so its own field is always filled. A form of any other shape is refused, and `agy` asks in text instead, as is one with a form-wide rule or a field constraint Sotto would not keep, or whose `required` names anything but one of its questions. Only a thread's own process is offered forms: never Watcher's, whose questions are Sotto's `ask_user` (ADR-0073), nor the short processes for titles, models and the sign-in. Watcher's native permissions and questions go to the user. Its calls to the Sotto tools attached to its own session follow [ADR-0073](0073-watcher-coordinates-threads-with-its-providers-own-tools.md). Sotto admits each such call once, after checking the current Watcher identity and the tool offered to that session. Each tool still checks what Watcher may do for the user.

**Threads.** Replies, reasoning, commands, file changes, reads, tools, plans and `agy`'s subagent calls as activity; images; skills and commands as `/name` from `available_commands_update`; stopping. A thread resumes after a restart with `session/resume`, which replays nothing, so no earlier tool call shows or runs again, and its history is Sotto's event store's (ADR-0016). A message sent while a turn works is steered in as a new `session/prompt` into the running session, as T3 does on 1.5, and the turn ends with the answer to its newest prompt. Not offered: rewinding; Fork from here starts a new thread from a handover, as for Cursor. Compaction sends `agy`'s own `/compact` as a prompt (November 21, 2026): `agy` 1.5.13 answers it as a quiet turn with no reply, and its next turn reports the smaller context. The compaction's record is kept in memory, as the token count is.

**Watcher and short text.** Watcher runs on Antigravity, its instructions in the session's `_meta.antigravity.systemPrompt.append`, which `agy` advertises, never in the user's words; a client that does not advertise it is refused for Watcher in words. Short text (ADR-0026) is one prompt in a session of its own in the thread's folder, with no tool servers, on the thread's model at its least effort; a request is cancelled and a tool call stops the call, which then writes nothing, and the side session's files are removed.

**Usage.** Token counts are read the way T3 reads them, from `agy`'s conversation files in Sotto's folder and in the user's own `~/.gemini/antigravity*` and `~/.config/antigravity` folders, keeping only counts, dates, model names and app names, as Usage keeps Claude Code's and Codex's. The account's limits are read from `daily-cloudcode-pa.googleapis.com` and `cloudcode-pa.googleapis.com` with `agy`'s own sign-in token from Sotto's folder; an older `acp_token.json` is renewed at `oauth2.googleapis.com` as T3 renews it. The token stays in main and is never logged. Limits show as Gemini 5-hour and weekly windows and a shared Claude and GPT window. A Gemini Enterprise sign-in kept only in the system keyring is not read.

**Hosts and phones.** A paired host offers Antigravity (`provider-antigravity`), runs the `agy` installed there in a folder of its own, and signs a Google account in from this computer. Sotto's own download runs on this computer only in this version. The iPhone and Android clients name Antigravity, show its models and open threads on it.

## Consequences

- Sotto answers some of `agy`'s permission requests on the user's behalf: a thread's mode, chosen by the user for that thread, is the authority, recorded with the thread, as T3 treats it. ADR-0004's amendment says so.
- Sotto holds a second key the user chose, the user's own Google one, on this computer only.
- Sotto contacts Google's download hosts for things the user asked for: Install, Update and the hourly update check. It no longer contacts Google's limits hosts (the amendment below).
- Not yet matched from T3: Sotto's own download on a paired host and Gemini Enterprise on a host. Reading a failed turn from the conversation file's last step is now matched (`antigravityTurnOutcome.ts`: read-only, bounded, unlinked file check under Sotto's own app data). A child agent `agy` launches is read from its records in `brain` (parity slice 7, November 21, 2026; extended with live child steps November 22, 2026, Zach's pick: Variant A, straight to stable): the parent's `subagents` record, the inboxes, and the child's own `brain/<child>/.system_generated/logs/transcript.jsonl` (incremental, bounded, read-only, realpath-inside-`brain`, non-symlink check), linked by the launching `invoke_subagent` or `start_subagent` tool call, so Tools › Agents shows the child's active step on its row and its chronological steps while working until its answer reaches the parent, and detached child watches are persisted across a Sotto restart within their four-hour window. Only Sotto's own download and Gemini Enterprise on a paired host remain. A finished edit is placed on its lines (parity slice 5, November 21, 2026; Zach picked variant B of the prototype kept as the tag `prototype/antigravity-edit-lines`): `agy` 1.5.14 reports the whole file before and after, and an older one may report a snippet, so Sotto reads the file once the edit is done, finds the new text in it exactly once, and shows only the changed lines, numbered as the file is now, as a Codex edit row does; one it cannot place stays as reported. A thread's token count and how full its context is now come from each prompt's answer and `agy`'s `usage_update` (November 21, 2026); Usage still reads its counts from `agy`'s conversation files, so they are never counted twice.
- Verified with a fake `agy` through the adapter contract; the live check on the laptop is in [the verification note](../verification/2026-11-20-antigravity-provider.md).

## Amendment, November 21, 2026: Google's terms

Google's Antigravity terms let it suspend an account used through third-party software. Accounts were suspended for taking `agy`'s OAuth token out of it or passing it through something else, for calling Antigravity's servers directly, and for wrapping `agy` in another company's agent loop; Claude and other non-Gemini models are allowed only in Google's own app, CLI and supported IDEs. Driving Google's own `agy acp`, which keeps its own sign-in, is the gray area T3 Code is in, and it is the risk Zach accepts. The rest is changed so Sotto does none of the named things, at Zach's request:

- **No account limits.** Sotto never reads `agy`'s sign-in token and never calls `daily-cloudcode-pa.googleapis.com`, `cloudcode-pa.googleapis.com` or `oauth2.googleapis.com`. Zach chose removing the limits read over keeping it behind a switch. Usage still counts Antigravity's tokens from `agy`'s own conversation files, and leaves Antigravity off Subscriptions, as it leaves OpenCode off. A desktop names the limit providers it asks a host to read again, so a host from before this change is never asked for Antigravity's, and drops the Antigravity limits such a host still sends with an ordinary read rather than refusing the host's whole read. That host still reads them for its own ordinary read until it updates; only the November 21, 2026 Owl ever shipped the reader. A host's own catalog is kept to Gemini the same way when the desktop reads it.
- **Gemini only.** Sotto lists only the account's Gemini models (every Gemini ID `agy` 1.5 lists starts `gemini-`), never switches `agy` to another, even to read its thinking levels, and refuses to send on a thread made earlier on a Claude or GPT model, saying in words to choose a Gemini model. With one maker the menu is one list, not grouped by **model maker**. This applies wherever a model is chosen, since the thread menu, Watcher's model, worker roles, the phones and new-thread defaults all read the adapter's list; owlets never run on Antigravity (ADR-0213).
- **The warning.** The opened Antigravity row in Settings > Providers always says, above the sign-in method, that the user's own Google account carries the risk, and names the specifics: Sotto never reads `agy`'s sign-in or calls Google's servers with it; only Gemini models; running `agy` from another app is still a gray area. Zach picked variant A of three, the notice in the opened row; the prototype is kept as `prototype/antigravity-terms-warning`. It names Google's terms without a link until the page's address is confirmed.
- **Before more is built.** A follow-up that hands `agy` anything more of the user's, such as the MCP servers set up for it in `~/.gemini` (parity slice 3), is checked against these terms first.
- **The user's own MCP servers (parity slice 3), checked November 21, 2026.** Clause 6 of Google's Antigravity terms names using third-party software to access the service, such as another tool holding Antigravity's OAuth sign-in; no clause names MCP servers, and clause 4 makes the user responsible for the data and systems they connect an agent to. Handing `agy` the servers the user set up for their own `agy` reads no sign-in, calls no Google server and changes no model: `agy` starts and calls them itself, as it does from Google's own CLI, through ACP's own `session/new`. So it adds nothing the reported suspensions name, and was built. Google's FAQ (antigravity.google/docs/faq) also says wrapping `agy` inside third-party coding agents or applications "is not supported under consumer plans" and recommends a Gemini Enterprise or AI Studio API key for them. That is about running `agy` from Sotto at all, the risk this amendment already names, and this slice does not widen it.

## Amendment, November 21, 2026: Watcher follows its permission mode

Under [ADR-0073](0073-watcher-coordinates-threads-with-its-providers-own-tools.md) (October 13, 2026 amendment), Watcher uses the same user-selected runtime permission modes as ordinary threads across Codex, Claude Code, Grok Build, Muse and Cursor. Leaving Antigravity Watcher prompting for native commands while set to **Full access** broke that parity, and Zach chose on November 21, 2026 to have Antigravity Watcher obey its permission mode and amend this ADR accordingly.

- **Same permission rules as ordinary Antigravity threads.** On **Full access**, Sotto allows any `session/request_permission` request that offers a nonblank `allow_once` option once; on **Allow edits**, requests whose tool kind is `edit`, `delete` or `move` are allowed once; on **Ask for approval** and **Auto**, native asks reach the user. Switching Watcher's mode takes effect immediately for future requests, and widening to **Allow edits** or **Full access** answers any waiting permission cards on Watcher that the new mode allows.
- **Unchanged boundaries.** Watcher's scoped Sotto MCP tools (`sotto_threads`, `sotto_pull_requests`, read-only `sotto_plugins`) remain admitted once on every permission mode, and unadvertised MCP tools fall through to the thread's permission mode. Questions (`interaction_*`) always reach the user, and `elicitation/create` forms stay disabled and refused on Watcher (`ask_user` remains Watcher's question card). Sotto never selects `allow_always` (so a request offering only `allow_always` still reaches the user). Watcher runs on this computer only, never widens paired-host ceilings or answers worker cards, and every Sotto tool continues enforcing Watcher's identity, budgets and authority on every call.

## Amendment, November 23, 2026: Updating standalone `agy` installs

On paired hosts, Sotto's own download UI is desktop-only and host setup installs Google's standalone `agy` in `~/.local/bin/agy`. Treating every copy outside Sotto's own download folder as `unknown` left no **Update** button and skipped Antigravity in **Update all** for paired hosts and for desktops running Google's standalone installer. On November 23, 2026 (#2842), Zach chose to update standalone installs in place with `agy update`, matching Claude Code, Grok Build, OpenCode and Cursor ([ADR-0042](0042-provider-client-updates.md)):

- **Sotto's downloaded copy** (inside `<dataDir>/antigravity/runtime/`) keeps updating via Sotto's verified `AntigravityRuntime` download, with side-by-side version folders and leases.
- **Google's standalone install** (inside `~/.local/bin` on macOS and Linux, or `%LOCALAPPDATA%\agy\bin` and `~/.local/bin` on Windows, and not resolving into another package manager such as Homebrew or mise) uses `channel: 'self-update'` and updates in place via `agy update`, with `agy update` shown as its by-hand command on failure. `AGY_CLI_DISABLE_AUTO_UPDATE` is stripped if inherited from the host environment so an explicit update is never suppressed.
- **Any other copy** (such as a custom binary path in Settings or a symlink owned by another package manager) remains `channel: 'unknown'` and is never replaced.
