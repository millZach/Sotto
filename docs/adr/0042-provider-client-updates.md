# Provider client updates

Amended October 6, 2026: standalone Chats was retired under ADR-0010. References below to personal chats, their provider connections and their voice or memory paths describe historical behavior; those paths are removed. Thread behavior and the remaining beta gates continue as described.

Accepted September 21, 2026. Sotto drives four installed clients and until now said nothing when they fell behind. Two of them, Grok Build and Devin, refused every version but the one they were verified against, so the installed Grok client stayed on 1.0.5 while x.ai published 1.0.40. The pin was keeping the client old, and nothing in the app said so.

**Sotto asks the npm registry what is published.** Once an hour at most, per provider, `registry.npmjs.org` answers with the version its package's `latest` tag points at. The request carries a package name and nothing else: no key, no prompt, no transcript, no identifier beyond the ordinary web request any computer makes. This adds one host to the README's list, alongside the GitHub check the app already makes for itself, and it obeys the same shape: on by default, one line in Settings that turns it off, nothing installed behind the user's back. A provider that is not connected has no known installed version, so it is not compared.

**The channel that installed a client is the channel that updates it.** The resolved executable path and the npm global root say which, and the first live run of this feature is what taught Sotto to read them. A binary with `node_modules` above it is npm's, and so is a client whose package sits in the npm global root even when its real binary lives somewhere else entirely: Grok Build is 142 MB of `~/.grok/bin/grok.exe` that npm's install script put there, and `grok update --check --json` answers `"installer":"npm"` about itself. Only a client npm does not own, like Claude Code's installer in `~/.local/bin`, updates itself with `<client> update`. Devin ships inside the Devin desktop app, which updates itself; Sotto reports Devin's version and never offers to replace it. An install under any other manager is named, not driven: Sotto shows the command and lets the user run it. Guessing at another manager's layout is how a working install gets a broken second copy.

**npm runs as npm, not as a shell line.** `npm-cli.js` runs under this process's own Node, through `ELECTRON_RUN_AS_NODE`. The shell hop is where the live run broke: a `cmd /s /c` line naming npm's batch file loses its quoting and answers "operable program or batch file", which is not a sentence anyone can act on. No shell, no quoting, same npm.

**A client is replaced while nothing is using it.** (Superseded by the amendment of September 28, 2026, below: the client is now replaced while threads keep working.) Sotto disconnects the provider, runs the update, then reconnects and reads the new version. Windows refuses to overwrite a running executable, so this is what makes the update work at all, and a turn in flight would be lost either way. A provider with a working thread is refused until the user presses Update anyway, which says in the notice what it will stop. Two updates never run at once. An installer that finishes without the version moving is reported as it is — the client that is open is the one still answering — because "updated" next to the old version is a lie the user can check.

*Amended September 25, 2026.* "Nothing is using it" has to include Sotto. The provider's automatic reconnect used to fire five seconds into a longer install and start the old binary again, which the update's own reconnect then found connected, so nearly every first update from the card reported the old version. A provider being updated is now left alone until the update hands it back, and a Connect pressed meanwhile says so instead of connecting. Personal chats run their own copy of each client; they let go of it before the install and take it back after, rather than running the old version until Sotto restarts.

*Amended September 28, 2026.* The disconnect rested on a wrong premise, and it cut off every working thread on the provider for as long as npm ran. Measured on Windows 11 ([evidence](../verification/2026-09-28-client-update-over-running-executable.md)): a running executable cannot be overwritten in place, but its folder can be renamed while the process keeps running, and a real `npm install -g` of a package whose executable was running exited 0, installed the new version, and let the old process run to completion, warning only that it could not clean up the old folder. Grok Build's own installer moves its running `grok.exe` aside to `grok.exe.old`, and Claude Code's updater replaces `~/.local/bin/claude.exe` while sessions run. So Sotto now does what T3 Code does: the installer runs while threads keep working, and nothing disconnects, reconnects or stops a turn. After a good install each host finds the client again, reads the version from the binary on disk, and moves each thread to the new client as it goes idle: an idle thread's process stops at once the way the idle reaper stops one, so its next action starts on the new client, and a working thread finishes on the old process and stops when it next goes idle. Personal chats are told the same way and stay connected. That needs one process per thread, which [ADR-0038](0038-one-client-process-per-thread.md) records. A failed install changes nothing and needs no reconnect. A working thread no longer refuses an update, so "Update anyway" means nothing; the command still accepts its `force` field and ignores it, because host protocol version 1 is frozen (ADR-0025) and a paired phone or older client may still send it. Two updates still never run at once, and an installer that finishes without the version on disk moving is still reported as it is. The Connect refusal and the retry hold from the earlier amendment go with the disconnect they guarded. npm is now run with `--allow-scripts=<package>`, as T3 Code runs it, because npm 12 runs no install scripts by default and still exits 0, and Grok Build's package finishes its install in one; an older npm warns about the unknown setting and installs all the same.

The card changed with it. Nothing warns that updating stops a thread, because nothing does, and the Update press is the same whether a thread is working or not. After the install the card says which version is now in use ("Codex is now 0.59.1.") and nothing about a thread still finishing on the old one: that thread moves over when it is idle, and every new turn already runs the new client, so nothing on screen is wrong. Of three mock-ups (saying nothing, the card following each thread until it has moved, and a note on the working thread itself), the user picked saying nothing. See `design/provider-updates/bumpless-update-card.html`.

*Amended October 3, 2026.* npm's leftover folder is cleared before npm runs. The folder npm moves the old package to (`.codex-<hash>` beside `codex`) is not random: npm derives its name from the package's path, so every update of a client in one place uses the same name ([evidence](../verification/2026-10-03-npm-leftover-folder.md)). An update made while a thread works leaves it behind, because npm cannot delete a program that is still running. The next update then fails with `EBUSY … copyfile` if anything from before the first update still runs there. On the development machine that was Codex processes an editor plugin had left running. So before an npm update on Windows, Sotto deletes each such folder that nothing runs from. One that something still runs from is moved to a name of its own (`.codex-<hash>.old-<time>`), which frees npm's name and leaves the running program alone, and is deleted before a later update once it has stopped. A program is running when Windows will not open it for writing, which tells without changing anything. Nothing else beside the package is touched.

**An exact version pin becomes a verified minimum.** Grok Build and Devin connected only to one exact version. They now connect to that version or newer and record that the installed client is past what Sotto verified; older is still refused, because the adapters read protocol shapes those versions were checked against. A newer client that changes its protocol fails visibly at `initialize`, which is a better failure than a client the user cannot update. The verified versions themselves stay where they are until someone checks a newer one against the adapter contract.

**The notice is one card in the corner.** Every behind client is a row in it, with one press to update them all, over the composer's corner in the region the toast already uses. Sotto considered a toast per provider and a pill that waits; four stacked toasts bury the composer, and a pill that announces nothing is a pill nobody presses. The card says what is installed, what is published, what a press will do, and after an update whether it worked and what to reconnect. See `design/provider-updates/provider-update-notice.html` for the three shapes and `docs/plans/2026-09-21-provider-client-updates.md` for the choice.

*Amended September 29, 2026 (#480).* **mise is a channel Sotto drives, and a host's clients update from this computer.** Forge's clients were all mise installs (its `~/.config/mise/config.toml` asks for `latest` of `claude`, `codex` and `npm:@xai-official/grok`), and mise never moves an install it already has unless `mise upgrade` runs, so every one of them had fallen behind while the tiles in Settings > Hosts showed only the version. Guessing at a manager's layout was the risk this ADR named; mise's layout is plain enough to read instead. A client is mise's when its path, or the path it links to, is in mise's installs folder (`MISE_DATA_DIR`, else the XDG data home, else `~/.local/share/mise`, `%LOCALAPPDATA%\mise` on Windows; any `mise/installs` folder counts), and the tool's name is the one mise wrote beside it (`.mise.backend.toml`, `short = "…"`), else the name Sotto knows for the folder (`npm-xai-official-grok` is `npm:@xai-official/grok`). Grok Build's program lives in `~/.grok/bin`, where its package's install step puts it, so it is mise's when npm does not hold the package and mise holds `npm:@xai-official/grok` with a version installed. An update runs `mise upgrade <tool>` through the mise binary itself, found the way a client is (ADR-0036) and accepted only when its real name is `mise` and it is not a script, so never a shim, which would run the tool. mise's npm backend skips the package's install step, and Sotto starts `~/.grok/bin/grok`, so for Grok Build the update has a second step: `node bin/postinstall.js` in the package folder `mise where npm:@xai-official/grok` names, run on the host's own Node (checked on forge: it needs no network, and its `npm config get` fails harmlessly). The two steps are reported apart, so a failure says which one did not finish. The published version is still read from the npm registry. Without a mise binary the client is named, not driven: its tile shows `mise upgrade <tool>` to run by hand. asdf, Volta, Homebrew, bun and pnpm installs stay that way too.

A host's readings reach this computer when the host lists the `client-updates` feature (ADR-0025): the router hands each host's `clientUpdates` to its tiles, and to nothing else, so the corner card and Settings > Providers stay this computer's own. A tile says what is available and offers **Update** beside Disconnect; a chip beside Show providers counts the host's updates and opens **Update all** (variant D of `prototype/host-client-updates`, the owner's pick; see the issue for the words). Both send `queue-client-updates`, a new command on the remote allow-list that only a listener offering the feature accepts; `update-client` stays host-local because it holds the request open for as long as the installer runs. Each machine runs its updates in one **client update line**, one at a time, which `update-client` joins too: Update all carries on past a client that did not update and also retries ones that failed, and a client still waiting can be taken out with `cancel-client-updates`. Updates stay bumpless as the September 28 amendment has them. A paired device may queue updates because updating a client answers no permission request and replaces nothing the user made, the same trust as `connect`. The iPhone client does not send them, and an older host shows nothing new. The `mise` channel and the `queued` state are new values of fields protocol v1 already carries, so a host sends them only to a client whose hello accepts `client-updates`, and `unknown` and `idle` to any other; a desktop from before this change keeps reading a newer host's shell.

*Amended September 25, 2026.* A card about one client that failed, did not change, or is updating is one line: what happened, Try again and Dismiss, with the reason (and the installer's own words) under Details. The list, with no press in the "did not change" state and the same sentence shown twice, left the user going to Settings to try again. Of three mock-ups (a row press, a footer step, and the one line), the user picked the one line. A card about several clients keeps the list, and a row that did not change now has Try again too.
