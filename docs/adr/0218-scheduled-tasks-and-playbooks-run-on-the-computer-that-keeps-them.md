# Scheduled tasks and playbooks run on the computer that keeps them

## Status

Proposed on November 26, 2026, for Zach's review. **Number provisional until merge** (`0218` is free after ADR-0217, Mods; recheck before merging per `docs/agents/domain.md`). It is an Owl feature (`scheduled-tasks`, `sentToStable: false` in `src/shared/owlFeatures.ts`, per [ADR-0072](0072-sotto-owl-is-a-windows-preview-release-track.md)). It keeps [ADR-0002](0002-sotto-owned-thread-identity.md) and [ADR-0004](0004-authority-in-policy-records.md) whole and adds no exception to "the user answers every permission". Its Settings page follows the Mods and Council pages' titled groups; no HTML mock-up was made for it, so its layout is open to a design review before it goes to stable (see Consequences).

## Context

Sotto only acts when someone sends: the user, Watcher, babysitting, delegation or the Council. A recurring chore (review last night's commits, triage a new issue, run the checks and ask before a pull request) needs the user to remember it. T3 Code's comparison asked for scheduled prompts and durable multi-step runs that survive a restart without doing a step twice, and that start from outside: on a webhook or a new GitHub issue. Three things are expensive to get wrong here: an outside event must never become an instruction or an approval, a step that may have taken effect must never run again on Sotto's own say, and a closed or switched-off Sotto must not silently fire a backlog.

"Workflow" already names Claude Code's own multi-agent mode in this glossary (**Workflow page**), so a multi-step run is a **playbook** here.

## Decisions

1. **A scheduled task is one prompt or one playbook, a target and its triggers.** The user writes it on Settings › Scheduled tasks: a name; what it runs; where (a new thread each run, in a chosen project on a chosen model, with an effort, a permission mode and a working copy, or, for a prompt, one existing thread); when (once at an instant, every 5 minutes to 28 days from an instant, or on chosen weekdays at up to twelve wall-clock times in a named IANA time zone); what to do with a missed time (run once, late, or skip) and with a time that comes while the task's last run still goes (skip it, or run once that run ends); and whether a signed webhook or new GitHub issues and pull requests also start it. Each task keeps its 30 newest ended runs as its history. Run now, Pause, Resume, Change and Remove act on it there.
2. **The host that runs a task owns it.** Tasks, runs and their delivery keys are kept in `scheduled-tasks.json` in Sotto's data folder on the computer whose local host runs them, and a task names only that computer's projects, threads and models. Where this computer hosts no agents (the local host off), the page says so and nothing runs. A remote host's threads are refused when a task is saved and reported as **On another computer** if one moves away later; running tasks on a headless or paired host is left for later, since its scheduler would need its own switch, file and Settings view. The file is written atomically; a file from a newer Sotto, or one that can't be read, is kept unchanged and nothing is saved over it until it is fixed or moved.
3. **One switch, off by default.** **Run scheduled tasks** (`scheduledTasksEnabled`) starts nothing until the user turns it on. Off, no task starts, no webhook listener is open and GitHub is not asked; tasks, runs and playbooks are kept whole, and a step already in a thread is still followed to its end. A time that passes while the switch is off, or while Sotto is closed, counts as missed: the newest is run late or skipped as the task says, and the rest are recorded as one **missed** entry with their count, never fired as a burst. A paused task owes nothing when resumed: its webhook answers that it is paused, and the times and GitHub issues that came meanwhile start no runs. Where the Owl answer is off, nothing of the feature exists and its file is kept.
4. **Times are read as the wall clock in the task's zone.** A time the clock skips when summer time starts runs that much later, and a time it shows twice when it ends runs the first time only (the Temporal proposal's `compatible` reading). A task's last-read time only moves on: a clock set back owes nothing until it passes that time again, so no time runs twice. A time read within two minutes of when it fell is on time; later is late.
5. **A playbook is a local JSON file of ordered steps.** `playbooks/<id>.json` in Sotto's data folder, written by the user or by a thread, at most 50 files of 128 KB and 30 steps each, `format: 1`. A step is an **agent** step (a prompt, in a new thread or one an earlier step made, on the project's checkout or in a worktree of its own, optionally ending in a `sotto-output` block whose fields the step declares and checks), a **code** step (one program and its arguments, run without a shell in the project folder or an earlier step's thread folder, with a timeout, its standard output kept as text or one JSON object), or a **decision** (a question to the user, optionally with a note the user writes). Inputs are declared with a type, and later steps read `{{inputs.x}}` and `{{steps.id.output.field}}`, `reply`, `note`, `stdout` and `exitCode`. The file is checked as a whole before any run uses it; a step that refers to a later step or to nothing real is refused with the reason. Add the example writes `triage-and-fix.json`: triage an issue, ask whether to fix it, fix it in a worktree, run `npm test` there, and ask before the pull request.
6. **A run is written down before each effect and again once its result is acknowledged.** A run snapshots the playbook as it was when it started. Each step's state, tries, thread, draft and message IDs go to disk before its prompt is recorded or its command runs, and its output goes to disk before the next step starts. After a restart a run resumes from its first step that is not done, and a done step is never run again. An agent step is followed by the message that began it, as the Council follows its seats: its prompt is recorded as Sotto's before the provider hears it, so no window shows it as the user's.
7. **An uncertain step is held, never redone on Sotto's own say.** A command that was running when Sotto stopped, a prompt on its way whose echo never came, a step whose thread went away, or a turn whose end can't be read makes the step **uncertain** and the run **held**. The user looks at its thread and chooses Do it again or Go on as done. A failed step is tried again after 30 seconds, doubling to at most ten minutes, up to the step's `retries` (at most 3); a run that fails, stops or ends unknown can be told to go on from that step.
8. **Bounded.** At most three runs of all tasks run at once on a computer, one per task, and a playbook's `concurrency` (1 to 5, default 1) caps its runs that are running or waiting. A run waiting on the user holds no slot in the computer-wide limit and queues for one when it resumes. A run's waiting turn never interrupts the user: an agent step sends only when its thread is free (on this computer, connected, open, at rest, asking nothing and holding no other work), as a wake-up does.
9. **Outside words are data, and approve nothing** ([ADR-0004](0004-authority-in-policy-records.md)). A webhook's body and a GitHub issue or pull request are carried to the run as data. A prompt task shows them below its prompt in a fenced JSON block headed by whose words they are; a playbook binds them only to the inputs its file declares, never to one the user set on the task, and a filled input goes into a prompt as a quoted JSON string with a line saying it came from outside and approves nothing. They never choose a task, a step, a thread or a command: code steps' arguments may hold no template at all, and a run's inputs and earlier outputs reach a command only as the `SOTTO_PLAYBOOK_INPUTS` and `SOTTO_PLAYBOOK_OUTPUTS` environment variables.
10. **Only the user answers.** A decision step waits for the user's choice on the page; no webhook, issue, agent or other task can give one. A task's link to the coordinator admits three commands only (make a thread, send a step's prompt, stop a turn) and refuses any answer to a card or change of permission. A thread a run made asks the user as any thread does, under the permission mode the task chose; a run whose thread asks waits for the user's answer in the thread. A code step's command is first classified as `classifyRiskyAction` classifies a permission request: one that looks like it would spend, publish, delete or overwrite work, or skip a check runs only under a matching policy record or after the user's **Allow once** for that attempt. A playbook with code steps runs commands only from a revision (a SHA-256 of its file's bytes) the user allowed on the task; a changed file asks again before its next command.
11. **Webhooks are loopback only, signed, replay-proof and bounded.** The listener opens on `127.0.0.1`, on the port it had last time when free, only while scheduled tasks are on and a task has its webhook on. A program on this computer, or one the user carries here over their own tailnet, posts a JSON object to `/v1/scheduled-tasks/<task>/runs` with `X-Sotto-Delivery` (a new ID per request), `X-Sotto-Timestamp` (Unix seconds) and `X-Sotto-Signature` (`sha256=` and the HMAC-SHA256 of `timestamp.delivery.body` with the task's secret). A timestamp more than five minutes from this computer's clock, a wrong signature, a body that is not one JSON object or is longer than 64 KB, a request carrying an `Origin` (a web page) and more than 30 requests a minute for a task or 120 in all are refused; a delivery ID the task has seen answers that it was a duplicate and starts nothing. Each task's secret is 32 random bytes kept in the operating system's credential store (`scheduled-task-webhook:<task>`): New secret puts it on the clipboard from main, it never reaches the window, and turning the webhook off or removing the task deletes it.
12. **GitHub through `gh`, every two minutes.** A GitHub trigger asks GitHub, through `gh` and the sign-in already on this computer, for issues and pull requests opened since the trigger was saved, optionally carrying one label, in the project's repository or one named `owner/name`. GitHub can't reach this computer, so Sotto asks while scheduled tasks are on and any task has a GitHub trigger; no token of Sotto's and no new host is involved. Each issue or pull request starts one run, known by `github:<owner/name>#<number>`, and a read's failure shows on the task in Sotto's words.
13. **Privacy.** Nothing is logged but stable event names (`scheduled-tasks-unreadable`, `scheduled-task-github-read-failed`, `scheduled-task-webhooks-failed`): never a prompt, a payload, an issue's words, a secret or a task's name. A run's inputs and outside data stay in its record only while it can still go on; a run that ended any other way keeps none of them. With thread history off, a step's output and printed text are not kept once its run ends. No new host and no new runtime dependency.

## Considered options

- **A cron expression.** Precise, but a five-field string is easy to get wrong in a way that fires every minute. The three kinds of schedule cover the asked-for cases with fields the page can check.
- **Workflows as code.** A JavaScript or shell playbook would let an author do anything, and let a payload that reaches it do anything too. A declared JSON file whose steps are agent turns, one argv command and decisions keeps what runs in the file the user allowed.
- **A parallel coordinator for runs.** Runs use the coordinator's own create, send and stop, as the Council does, so queueing, outbox, guards, permission modes and delivery evidence are the ones every thread has.
- **Webhooks on the host protocol listener or a public tunnel.** The host protocol is for paired Sotto clients with their own trust; a public address would be a new host and an inbound path from the internet. Loopback with per-task signatures serves local automation and anything the user tunnels themselves.
- **Fire every missed time.** A Sotto closed over a weekend would start dozens of runs at once. One late run and one missed entry is predictable and visible.

## Consequences

A run can wait on the user for days at a decision without holding a slot. The scheduler reads its clock at least once a minute while tasks are on. The Settings page has no mock-up of its own and should get a design review before stable. Running tasks on headless and paired hosts, a cron-like schedule, and more step kinds (wait for a check, branch on an output) are later decisions.
