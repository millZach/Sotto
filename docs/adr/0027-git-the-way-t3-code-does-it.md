# Git the way T3 Code does it

Accepted September 23, 2026. Issue #127; the plan is `docs/plans/2026-09-23-git-interface.md`. Amended September 23 and 24, 2026, once for each ticket or pair that decided something of its own (#265 to #267, #268, #269, #270, #271), in that order below. Where an amendment changes an earlier line it says so there. The whole interface is proved in the built app in `docs/verification/2026-09-24-git-interface.md`.

## Context

Sotto's Git work grew in two halves that did not know each other: a Changes surface in the Tools panel that stages files, commits, switches branches and opens a pull request from Electron main, and a working-copy record on each thread that the host keeps (ADR-0014, ADR-0041). Nothing pulled, nothing fetched outside worktree setup, nothing pushed outside the pull request form, and no surface said whether a branch was ahead or behind. Every day started and ended in a terminal.

T3 Code, the reference for the Threads page, does Git as one model: a status the server streams (branch, upstream, ahead and behind, dirty, the default branch, the branch's pull request), a branch picker and workspace choice on the composer, one adaptive Git action in the header that commits, pushes and opens the pull request from a press, a diff panel with scopes and no staging, and pull requests through `gh`. Zach chose that model outright on September 23 rather than a Sotto variation of it. The plan records the model as read from T3's source at `7810fb26` and maps it onto Sotto's surfaces.

## Decision

Sotto builds T3's Git model piece for piece, in the order the plan's tickets give (#264 through #272). The decisions that are Sotto's own, because T3's model meets a rule Sotto has, are these:

1. **The background fetch is a setting, on by default, and it runs only while the window is in front.** T3's status depends on a fetch; without one Pull never appears and Push is blind. Sotto runs `git fetch --quiet --no-tags origin` for each open thread's project, with prompts disabled so nothing is ever answered on the user's behalf, on a timer at the **Git fetch interval** (30 seconds unless changed), when the user refreshes a working copy and when a Git action reads the remote before it acts, never more than once in 15 seconds (T3's figure), and only while the window is in front: showing and focused, or focused within the last 45 seconds; a headless host counts a connected client as its window. A fetch that fails backs off and status reads on from the last fetched refs. Off stops every fetch Sotto makes, not only the timer's: the timer's reads stop, and a refresh and a Git action compare with the remote-tracking refs as they were last fetched. A refresh still asks for the branch's pull request (decision 2). ADR-0041 refused an hourly fetch for the cleanup rules and is not reopened by this: the fetch here is the user's own remote, named in the README, under a setting.
2. **The branch's pull request is read through `gh` on refresh and on the same timer**, cached a minute and asked again after a Git action, for branches that have been pushed. The README says so beside the cleanup rule that already asked.
3. **Status lives on the thread's worktree record.** The host reads it after a turn (local only), on a refresh (remote too) and on the timer for the threads a window is looking at, and publishes only a status that changed. Riding on the record means every client, local or paired, gets it through the state stream Sotto already pushes, and no new socket operation is needed for it. What a control reads once when it opens, the branch picker's refs and the commit dialog's changed files, is a host operation advertised as a host feature (`git-refs`, `git-changed-files`, ADR-0025) rather than a field on every state. Commit and pull request text read more of the repository than before, as T3's do (recent subjects, `AGENTS.md`, the pull request template); ADR-0026's side call already goes to the thread's provider in the working folder, so nothing new leaves the machine. The README sentence that said "the staged diff alone" changed with the actions (#265) and now names each of these.
4. **Staging leaves the UI.** T3 has none; the commit dialog's file list is the choice. Sotto's Stage and Unstage file, and the staged and unstaged scopes, go with their tests when the Changes surface is rebuilt.
5. **A branch switch keeps the thread right.** T3 switches without asking and lets Git refuse when work would be lost; Sotto does the same and refreshes the thread record afterwards so the label, `sentBranch` and the shared-folder notice follow (ADR-0014). Restore branch keeps its confirmation.
6. **One press may commit, push and open a pull request.** The control's name says all three. Pushing from the default branch asks first, as in T3. T3's Proactive panels, which open its diff panel (Sotto's Changes) unasked, ship as a setting that is off until turned on.
7. **GitHub only, through `gh` on its own sign-in.** T3 supports five hosting providers; another is an ADR and a README line.
8. **Git runs on the host.** The status reader and the actions are built Electron-free beside `ThreadWorktrees` and wired in `createAgentRuntime`, so a remote thread gets the same button; the remote command list carries `git-action`, `git-pull`, `git-switch-branch`, `git-init` and `git-publish`, none of which needs an answer policy: Git refuses a switch that would lose work, a push is never forced, and a pull is fast-forward only. A created pull request is linked to its thread (#269); the branch's pull request is also read back into the status. One departure from T3 in the push: a `pushRemote` or `remote.pushDefault` that names a remote other than the upstream's is honoured, the way Git's own `git push` honours it, so a triangular workflow pushes to its fork. Sotto's checkpoints stay Sotto's: turn diffs come from the content-addressed blobs, not from Git refs.

## Amendment: the actions, the branch toolbar and the Git action (#265, #266, #267)

The working copy is chosen where T3 chooses it, on the branch toolbar under the composer, and New thread keeps the project and its Thread options (name, model, reasoning and permissions). What #265, #266 and #267 decided beyond T3:

- **Run on is static text.** The host is chosen when the thread is made (ADR-0025), so there is nothing for Run on to open and `mod+shift+h` is not claimed. The other three shortcuts (`mod+shift+g`, `mod+shift+x`, `mod+shift+l`) answer only for the focused pane, and only while no dialog is open. Each is left unclaimed when the dictation hotkey uses the same keys.
- **A switch in the branch picker moves the sent branch with it**, in the same publish as the branch, so the branch-changed notice stays for a checkout moved elsewhere (decision 5; ADR-0014's note). A draft pointed at another thread's worktree with Previous worktree lists that worktree's refs but does not switch its branch before the first send, because until then the worktree is the other thread's.
- **Progress is one notice above the composer of the thread that acted, not a toast in the window's corner.** It carries T3's stage lines and T3's toast text with its next step (Push, Create PR, View PR), and stays until dismissed, so a result is not lost to a timer or shown against another thread. A second Git action on a folder is refused, "Git action in progress.", while one is running there.
- **The commit dialog's primary button says the whole action** ("Commit & push", "Commit, push & PR") where T3's says Commit, because a control's name says what a press does. Its file list is what the host read when the dialog opened.
- **Check out feature branch & continue** names the branch from the commit's subject, or from HEAD's last subject for a push with no new commit, rather than asking the provider a second time.
- **Publish repository is one dialog** (the GitHub owner/name and Private or Public) rather than T3's stepped wizard, since GitHub is the only host (decision 7). **Initialize Git** takes Git's own default branch; Sotto does not choose one for the user.

## Amendment: the Changes rebuild (#268)

Staging has left the UI as decision 4 said: Stage file, Unstage file and the staged and unstaged comparisons are gone with their tests, and so are the Electron-side `commit`, `checkout` and `create-branch` actions, the branch list and the commit message draft that only the old drawers reached. Changes now reads only; its main-process side is the change list, one `review` read per comparison, Copy path and reveal. What #268 decided beyond T3:

- **Working tree** diffs HEAD through a copy of the index with untracked files marked intent-to-add, as T3 does, so the user's index is never written. Untracked files larger than 512 KiB, or that are not regular files inside the folder, are listed without their text.
- **Automatic** is T3's base order (the branch's `gh-merge-base`, the remote's default branch, `main`, `master`, the primary remote's copy preferred). With no base found, Branch changes says so and asks for one rather than guessing.
- **Turns** are diffed in the renderer from the before and after text the checkpoint already hands to the Checkpoints drawer, with a line diff of Sotto's own (no new dependency). A turn's number is its place among the thread's checkpoints in that working copy, oldest first, because a checkpoint records no turn number of its own.
- **The shortcut.** Bend 9 left the fallback chord open: it is `mod+shift+d`, taken only when the dictation hotkey holds `mod+d`, and dropped when it holds both. Focus inside a terminal keeps Ctrl+D for the shell.
- Layout, wrapping, whitespace, the file tree and collapsed files are session state until #271 adds their settings. (#271 did: layout, whitespace and collapsed files now start where Settings → Git says, decision 6 of that amendment; wrapping and the file tree stay session state.)
- Changes still reads Git from Electron main, so it reads only local threads; its base picker already uses the host-capable `git-refs` read. A remote thread's Changes stays unavailable until Changes itself moves to the host, which decision 8 leaves for later.

## Amendment: the pull request surface (#269)

The pull request is a Tools surface, Pull request on the rail (its tile reads PR), read on request through a `git-pull-request` host operation advertised as a host feature, the way the branch picker's refs are. Four commands act on it and are on the remote command list, since each is a press the user makes and none answers a permission: `git-pull-request-action` (merge with a method, ready or draft, close or reopen, update the branch with a merge or a rebase, auto-merge on or off), `git-link-pull-request`, `git-unlink-pull-request` and `git-checkout-pull-request`. The merge, turning on auto-merge and closing ask first in T3's words, and so does Update with rebase, which T3 runs at once: it rewrites the pull request's branch on GitHub and leaves any local copy diverged, so Sotto says so before it happens. Merge when ready (GitHub's auto-merge) is offered only where the repository allows it; the host acts only on a pull request the thread knows (its branch's own or a linked one), and a press whose reply was lost is settled by reading the pull request again, never by pressing twice. Linked pull requests live on the thread record. Links and actions take GitHub URLs only (T3's pattern, `github.com`), keeping to decision 7. Both checkouts take the pull request from `origin` by number, so a pull request of another repository is refused in plain words rather than answered with this repository's pull request of the same number. Checkout Local runs `gh pr checkout` without `--force`, departing from T3, which forces: Git refuses rather than reset a local branch that has commits of its own. Checkout Worktree is for a thread that has not started; the pull request's head becomes a branch (`sotto/pr-<number>/<head>` for a fork, in T3's `t3code/pr-` place), and the new worktree checks that branch out as it stands on first send, rather than cutting a temporary branch from it. The merge starts on the Default merge method setting (#271, below), read through one hook, `usePullRequestMergeMethod`, on `useMergeMethod`: a pick beside Merge holds for the surface, and under Last selected it is saved as `lastMergeMethod`; under a fixed default nothing is saved. The window's own `localStorage` choice the surface kept before #271 landed is gone. Comments, requesting reviewers and labels, the Timeline and Code tabs, and the repository's pull request page are later tickets. The checklist reads who has reviewed (Who reviewed, below) but cannot ask anyone to review.

The surface's layout is the owner's pick among three prototypes of #127's pull request interaction (variant C, "Checklist to merge", September 23): the merge checklist, one large Merge enabled only when the checklist has nothing left, and the rest folded below or in the ··· menu. Where the prototype faked a reading, Sotto reads it or says it cannot:

- **Who reviewed.** The host's GraphQL read, the one that already counts how far the branch is behind, also asks for each reviewer's latest review that took a side (`latestOpinionatedReviews`): the login, approved or changes requested, and the review's GitHub link, which Open review opens. A review link outside `github.com` is dropped; nothing of it is logged.
- **What GitHub does not require.** A repository with no review rule answers no review decision, and a branch with no checks answers none; those lines read "No review required" and "No checks" and count as done, rather than claiming an approval or a pass nobody gave. Where no review is required, a reviewer's request for changes that still stands is said on the review line with Open review, whatever came after it, and does not hold the merge back, because GitHub does not.
- **What GitHub could not say.** A base it could not compare reads so and does not hold the merge back, since nothing on the surface could fix it and GitHub decides when Merge is pressed. Mergeability still being worked out does hold it back, as "GitHub is still checking", because a Refresh settles it.
- **How it merged.** GitHub records when a pull request merged, not how, so the merged block gives the time and not the method.
- **Create PR** with no pull request is the Git action's own press (`git-action` with `create_pr`), enabled and explained by the same rules, and its progress shows in the pane's Git notice.

Variant A's controls that C did not show are kept or dropped this way: Open on GitHub and Refresh stay beside the menu; Update with rebase, Convert to draft, Copy link, Link pull request, Unlink from thread and Close pull request are in the ··· menu; Merge now is dropped, since Merge waits for the checklist and Merge when ready covers the rest; the list of every check and the head and base line are dropped for the checklist's lines, with the full list on GitHub; the separate Linked pull requests view is now the fold, and unlinking any but the pull request shown is done by opening it first.

## Amendment: review comments (#270)

Zach picked T3's way from the prototypes on September 23 (`docs/prototypes/git-interface-surfaces/review-comments.html` on the `prototype/git-interface-surfaces` branch, variant A; the pick is in that folder's `VERDICT.md`): pick lines, write the comment under them, a chip on the composer and a marker on the diff until the message goes. What #270 decided beyond T3:

- **A comment is text in the prompt, not a new field.** At the press the composer writes each comment after the user's message, in the order written: `Comment on` and the comment's name as a code span (`src/main/voice.ts L12 to L13`, `L4 to L5 (before)` when every line was removed), a blank line, the user's words, a blank line, then the lines as a ```` ```diff ```` fence with `+`, `-` or a space before each. A fence or code span is always longer than any run of backticks it quotes. Nothing in main, the command schemas or the four adapters changes, so every provider reads the same message, and the file mention's `@path` rules are untouched.
- **The comments go into the revision that is sent.** The composer writes them into the draft's text as a new revision just before submitting it, so the saved revision, the delivery's digest and the sent message agree, and a refused prompt comes back to the composer with its comments written in rather than lost. A queued follow-up and a steer carry them the same way; an answer to a question does not, and the composer says they wait for the next prompt.
- **Comments are held in the window, not saved with the draft.** They live in the renderer per thread until sent or deleted and are gone when the window closes or reloads. Saving them would add a field to the durable draft, its schema, the follow-up queue and the delivery digest for a note that is only minutes old; that is left until someone misses one. They are never saved as comments and never logged. Once written into a prompt they are part of it: the prompt's revision is saved as any draft is, so a refused prompt comes back with them in its text, and a sent one is the thread's history.
- **A comment keeps the lines it was written on.** When the diff changes, the comment still sends those lines. Its marker stays under the row that draws a line of the same kind, numbers and text, and when there is none it moves to the end of the file and says the lines have changed since (or, when its line is only past the first 3,000 rows drawn, says to Show all). A comment on lines the comparison on screen does not draw (a file committed since or outside the turn picked, a file whose only change is its mode or name, or a comparison that could not be read) is listed after the files under **Comments on lines this comparison does not show**, with Delete comment, and so is a draft with words whose lines are not drawn, with its text field and Cancel. So a comment stays in sight in Changes until it is sent, as #270 asks. A draft with words in it is never replaced by opening another; a click elsewhere drops only an empty one.
- **The keyboard path.** Each file's lines are one grid and one stop in the Tab order, with the Comment button and each comment's controls after them where they are drawn: the arrow keys, Home and End move, Shift extends, Space picks, Enter opens the draft on what is picked (or the line under focus), Escape lets go (from the lines, the Comment button or a marker) and leaves the panel's own Escape alone when nothing is picked. In the draft, Escape cancels and Ctrl+Enter (Command+Enter) adds. None of these is a global chord, so none can meet the dictation hotkey; `mod+d` still toggles Changes from the draft and the draft is still there when Changes reopens.
- **At most 20 comments a message**, said on the draft and the Comment button rather than dropped.

## Amendment: the settings (#271)

T3's Git and diff settings land as `gitAutoPull`, `defaultMergeMethod` and `lastMergeMethod`, `diffLayout`, `diffHideWhitespace`, `diffFileState`, `gitWritingStyle` and `gitWritingInstructions`, `followPullRequestTemplates`, `autoSettleMergedThreads` and `proactivePanels`, each on the IPC patch allow-list. What Sotto decided rather than followed:

1. **Everything that acts on its own starts off**: Automatically pull, Auto-settle merged threads (on in T3) and Proactive panels. The rest start where T3 does: Last selected starting from Merge, stacked, whitespace hidden, files collapsed, the repository's conventions, templates followed.
2. **Automatically pull is T3's rule on the host**: at a remote status read, a folder on the default branch, clean, tracking an upstream and only behind is pulled with the Pull action's `--ff-only`, and a folder any thread is working, waiting, setting up or running a Git action in is left for the next read. The desktop reads the setting live; a headless host reads it at start.
3. **Auto-settle merged threads rides the worktree cleanup's hourly sweep** and its `gh` question rather than the status stream's pull request, so it asks GitHub no more often than the merged rule already did, and once per branch when both want the answer. It settles a thread at rest by the branch it last sent on (a worktree's own branch before its first send), never the default branch, and once per thread and branch while Sotto runs, so a restored thread stays restored; after a restart one that is still on its merged branch may be settled again. Settling removes nothing; the on-settle cleanup rule decides about the folder as it does for any settle.
4. **Proactive panels opens only a closed panel** that is not pinned to another thread, and it does not move keyboard focus. A turn is large when its thread's Git counts grew by at least 3 files or 50 lines (T3's measure) between the turn's start and the host's first read after it ends. These are the working copy's counts, not the turn's own diff: edits by hand or by another thread in the same folder during the turn count too, and a file the turn changed that was already changed does not. The watch lives in the Tools panel, so it counts only while the Threads page is open, and a turn that ends while another page is showing is not measured. A large turn waits with its thread until that thread is focused, and Changes opens then; it is let go once the thread has been focused, whether or not the panel could open, or once Changes is opened for that thread. It lives on the Tools panel store, not in Changes.
5. **The last merge method is remembered only while the default is Last selected**, in settings, so it survives a restart and a second window.
6. **Changes starts where the settings say, and so does the checklist's merge.** The rebuilt Changes (#268) takes Diff layout, Hide whitespace changes and Default diff file state through `useDiffPreferences` as its starting view: layout and whitespace when Changes first opens and whenever a setting changes, collapsed files for each comparison as it is first read. What the controls choose lasts until one of the three settings changes or Sotto restarts (a change to any of them sets layout and whitespace again together), which amends #268's "session state until #271". Changes waits for settings before its first read, so a cold start does not read once with whitespace shown and again with it hidden. The merge method is saved and exposed through `useMergeMethod`, which the pull request checklist reads (the #269 amendment above): its merge starts on this method, as the Settings copy says, and under Last selected a pick beside it is saved back.
7. **One Git section, grouped by moment.** Of three layouts prototyped (`docs/prototypes/git-interface-surfaces/settings.html` on the branch `prototype/git-interface-surfaces`, with the owner's verdict in `VERDICT.md` beside it), the owner picked B on September 23, 2026: every setting above, and the Git fetch interval from decision 1, sit in Settings → Git under When a thread commits, When a pull request is made or merged, When you read Changes and In the background, rather than at the ends of Application and Cleanup. Each description is a sentence about what Sotto will do with the value shown and changes with it. The style row carries an example subject and title; the prototype had it rewrite the example from custom instructions with a few pattern rules, which would guess at a model's answer, so the built example keeps the plain subject under Custom and says the thread's own model applies the instructions when it drafts. The worktree cleanup rules stay under Application and the Generated switches under Cleanup, where the prototype left them.

## Amendment: a bounded workspace menu (September 28, 2026)

Zach chose prototype A: a compact menu anchored above Workspace, with search at the top and Current checkout and New worktree always available. The first view shows five recent worktrees, named by branch rather than repeating “Previous worktree” on every row. Search covers every available worktree belonging to another thread in the same project, by branch or folder. Recency is the latest recorded provider activity or message time of the threads using that folder; Git polling does not count as use. Repeated folders appear once, using their newest thread record. The recent list scrolls when space is limited, while the starting choices remain visible. The menu stays inside the pane and window, and can open below its trigger when there is more space there.

The project header reserves space for its actions instead of overlaying them on the host badge. Below a 340px sidebar width, the host badge becomes an icon; its tooltip and the project button’s accessible name retain the host name. This changes neither working-copy ownership nor first-send setup.

## Amendment: preserve staging during commits (September 30, 2026)

The commit action keeps staged hunks in selected files and stages selected files with no staged changes in full. It temporarily excludes staging for files left out, then restores that staging after success. Any failure before the commit completes restores the original index without changing working files. A selected rename includes both paths, and paths are resolved from the checkout root even when the thread works in a subfolder. This departs from resetting and re-adding whole files: the user's staging is work to preserve (#500, #501, #503).

## Amendment: checkpoint retention (September 30, 2026)

Turn checkpoints follow Keep local history. Turning it off or forgetting a thread deletes its saved checkpoints at once, along with file backups that no other checkpoint needs. Turning history off, forgetting a thread and the age and size limits keep unfinished revert records and their file backups until recovery finishes. Completed checkpoints expire after 30 days; checkpoint storage is capped at 500 MB, removing the oldest checkpoints and recovery backups first. Turning history back on starts fresh checkpoints.

## Amendment: checkpoint file recovery (September 30, 2026)

The checkpoint file records which storage format it uses. If it is damaged, Sotto keeps readable records and backs up the original beside `checkpoints.json` as `checkpoints.json.corrupt-<id>`. The Checkpoints drawer names the backup file without its folder and says Sotto kept the readable checkpoints. Readable interrupted reverts still require recovery before more work; unreadable records cannot be restored. Backups share the storage limit, expire after 30 days and are erased when Keep local history is turned off or a thread they mention is forgotten.


## Correction, October 1, 2026: reserve the checkout (#502)

Git actions, branch restore and checkpoint rollback or recovery share one checkout guard with sends, on desktop and headless hosts. It reserves the checkout before asynchronous checks or side calls and releases it after completion or refusal. Identity follows the canonical checkout root, including subdirectories and path aliases; linked worktrees stay separate. Active or pending thread work prevents mutations, and a mutation prevents sibling sends. Checkpoint snapshots also hold a read reservation.

## Amendment: what a send pays for its checkpoint (October 5, 2026, #764)

Every send took a file checkpoint before the provider heard the prompt, and on the development machine 981 of 987 of them were unavailable: 754 over the size limit, 220 in folders Git does not know, 3 out of memory, and 4 for reasons that come after a capture (a turn that changed Git history, two binding changes and an overlap with another thread). Most were found out by reading files one at a time until a limit was reached. Zach decided to keep the limits (10,000 files, 64 MiB in all, 8 MiB a file) and make the capture cheap rather than rebuild checkpoints on Git. What the checkpoint restores, the recovery records' guarantees and the words for each limit are unchanged.

- The send's hook takes the checkpoint from the thread the coordinator read just before the send. It no longer reads the thread again, which had also undone the Codex newest-turn check (ADR-0005), and it settles the previous turn's checkpoint once, not twice. Every send the coordinator makes reads first: a manual send, a coordinator draft, a supervision follow-up and a queued follow-up, which until now had only the hook's read.
- Every listed file is `lstat`ed, and the limits checked, before any file is read. A directory's safety is checked once for all the files in it, and files are read eight at a time. Once a read fails no other starts, and the capture waits for those already started before it gives up.
- A file keeps the hash its folder's last snapshot recorded while its size, modification time, change time, inode and mode are all as they were, its backup is still kept, and its times were more than three seconds older than that snapshot: a file written that close to a snapshot could be written again within the same timestamp tick (Git's "racily clean" case). So a file edited in the last three seconds before a snapshot is read again by the next one. The check before a revert reads every file.
- A folder that could not be captured keeps that verdict and its reason while nothing that decided it moves: Git's `HEAD`, its reflog, the index's size, the folder's own listing, Git's ignore files, and the paths the verdict names. The ignore files are `info/exclude` where Git reads it (a linked worktree shares its main checkout's), each `.gitignore` from the top of the working tree down to the folder, and every `.gitignore` the folder's listing names. Over the total size the paths named are the largest files that alone exceed it; over the size of a file, that file; for a link, a hard link or a file name storage cannot hold, the path and the directory holding it, or for a name inside a directory whose own name storage cannot hold, the nearest directory above that can be watched; over the file count, every directory holding a listed file. A verdict that would watch more than 1,000 paths drops the paths it names and keeps the ignore files, and one with more than 1,000 ignore files watches only Git's state and the top-level listing. Holding a verdict costs a few `lstat`s and no Git command. A verdict is not held when a path it watches changed in the three seconds before the capture. A listing that outgrew Git's buffer is a verdict, and reads as over the file count. A listing Git refused for any other reason, in a folder it does not know or does not trust, holds no verdict: Git is asked again on every send, which costs the refused listing and, for a folder it has never known, a `rev-parse`. A folder becomes listable in ways an `lstat` cannot see (an ownership change, `safe.directory` in any of Git's configuration files), so asking is the only reliable check. A backup removed from `blobs` outside Sotto is forgotten at the next save, so the capture after it writes the file's backup again. A timeout, a Git that could not be started and a file that could not be read are not verdicts, and are tried again. Git's global ignore file is not watched, nor a `.gitignore` created after the verdict in a folder whose listing is not watched, so a folder that falls under the limits only through one of those keeps its verdict until something else moves or Sotto restarts. The cost of a verdict held too long is a checkpoint not taken, never a wrong revert. Folders and verdicts are kept in memory for the 32 folders used last, with at most 50,000 remembered files across them (about 25 MB), and forgotten when Keep local history is turned off.
- A send adds its checkpoint record to `checkpoints.journal` beside `checkpoints.json` and waits for it to reach the disk, instead of rewriting the whole file. The completion of a turn whose checkpoint was captured, a revert, recovery, forgetting a thread, the hourly sweep, any save that removes a record and the first save after one that failed still rewrite the file, and each rewrite folds the journal into it. So does the start, and a send once the journal has outgrown the file. A turn whose checkpoint was unavailable from the start rewrites nothing when it completes. A save counts the file backups of only the records added or changed since the last one, so a send's save does not grow with the saved history. The file carries a generation and each journal line the generation it was written against; a line from another generation is ignored, so a record removed from the file never returns from a journal that could not be deleted. Before each append Sotto cuts the journal back to what its earlier appends wrote, so a line never lands on a write that failed part-way or on a journal that could not be removed. A short Windows lock is retried. An append that still fails, or a journal shorter than its appends, rewrites the file instead, recreating the checkpoint folder if it has gone. A line cut short at the end is an append that never finished, and its send never went, so it is dropped quietly; a damaged line anywhere else sets the journal aside as `checkpoints.json.corrupt-<id>`, as a damaged file is.
- The file with a journal is storage format 2; format 1 is still read, and rewritten as 2 at start. An older Sotto reads a format 2 file as damaged: it sets it aside, keeps its records and ignores the journal, so going back loses the records of sends whose turns had not completed when the file was last rewritten. Going back is otherwise unsupported. Keeping format 1 was considered. The generation has to change in the same atomic write as the records, so it lives in the file, and format 1's schema refuses a field it does not know. Matching journal lines to the file by its contents instead would keep format 1, but an older Sotto would still ignore the journal and lose the same records; it would only be spared the set-aside notice and backup.

The before and after figures are `docs/perf/2026-10-05-checkpoint-send.md`.

## Amendment, October 6, 2026: a send never waits for a fetch or a GitHub lookup (#766)

Decision 3's reads ran in the thread's own order of work on the host, so a send waited behind any of them: the timer's remote read with its `git fetch` and its `gh` question, the read after a Git action, the refresh a draft starts and the re-read after a turn. A fetch that took its full five seconds held the prompt for five seconds.

Only the slow half of a read leaves that order now: the fetch and the pull request lookup. They run outside it, in the thread's folder as before, so Git and gh resolve its remotes, relative remote URLs and `safe.directory` exactly as a terminal there would; run from the repository's common Git directory they failed quietly for a relative remote URL, a `safe.directory` entry naming the checkout, or a bare repository with worktrees. The fetch writes no `FETCH_HEAD` (`--no-write-fetch-head`, Git 2.29 and later; an older Git fetches without it): nothing in Sotto reads it, and a fetch writing it beside a pull in the same checkout can leave that pull two heads to choose from. Because these calls run in the folder, Remove worktree and a cleanup rule hold the folder first, so no new one starts in it or in a folder inside it (where a project that is a subfolder of its repository works), and wait for any still running there before deleting it; on Windows a folder another process is working in cannot be deleted whole. What they bring is taken by a local read in the thread's own order: the fetched refs are already in the repository and GitHub's answer is in the status reader's cache, so that read is the same `git status` and counts it always was. It also decides Automatically pull, and the pull runs there, because a pull changes the folder. Every remote round reads the folder in that order first, so the lookup asks about the branch the folder is on now, even after a switch made in a terminal; the read that takes what the fetch brought is a read of its own, never one begun before the fetch landed.

Everything else stays in the thread's own order with its sends, as before #766: every local read, Git's inspection of the folder after a send, after a turn and on a refresh, every write to the worktree record, and an error a refresh finds. A send therefore waits at most for a local read or an inspection already under way, 150 to 300 ms of Git on the development machine (`docs/perf/2026-10-06-git-off-send-path.md`), and never for a fetch or a GitHub lookup of its own. The one exception is a send queued behind Remove worktree or a cleanup rule: the removal waits for a fetch or lookup still running in the folder, at most the fetch's 5 seconds or the lookup's 30, and the send waits for the removal. The first version of #766 moved all of those reads beside the thread's order instead, so a send waited for none of them. Three reviews found races that overlap opened, and each fix opened another: an inspection landing inside a switch and undoing the sent branch it moved, a refresh reading a folder halfway through being put back, a refresh that could no longer mark a broken folder as an error, and a status read holding open a folder Remove worktree was deleting. Ordering them with the send again closes all of them, at the cost of that wait.

A Git action, a pull request action and a branch switch make their change and read the folder's local status in the thread's order, as before, and the remote half follows once the order is free: their own answer waits for it, and a send behind them does not. Restore branch drops the reader's caches after its switch and reads locally, as before. A refresh answers once the record is read, and its remote half follows; in the coordinator it holds the thread lane as before, now for that local work only.

The status reader keeps its answers honest across a Git action that runs while a remote half is out. A fetch begun before the action does not set when the next one is due, and a caller after the action waits for it and fetches again rather than sharing it. A pull request answer asked for before the action is asked for again after it rather than standing for a minute, and never lands over one asked for after it. Callers asking for the same folder at once still share one read, except where a decision about to change the folder rests on it. The automatic pull decides again from a read of its own under the checkout guard, since a shared read may have begun before another thread or a terminal moved the folder. A Git action's own reads are its own too, since a read begun before its commit would have its push skip the commit as already up to date. A read begun before a Git action is not shared with a caller after it.

The checkout guard above now finds the checkout root from the `.git` entries on disk, the way Git's own discovery does, and asks Git only when the files do not settle it.

Every Git command started through the worktree runner (`runWorktreeGitProcess`: thread worktrees, the terminal's workspace service and worktree cleanup) runs with `GIT_OPTIONAL_LOCKS=0`. Git's inspection now runs beside an agent that may be committing in the same folder, and without optional locks a `git status` from Sotto never takes the index lock to write back what it refreshed, so the agent's commit never finds the lock taken. Commands that change the repository take their locks as before. The cost is that Sotto's reads no longer refresh the index for the reads after them: a file whose times changed while its content did not is compared again by each status until something else refreshes the index, such as the agent's own Git or the next commit. In a large repository with many such files each of Sotto's status reads does more work; on the common path that work is Git's inspection after a send, not the send itself.

## Amendment, October 7, 2026: asking GitHub within its rate limit (#820)

Decision 2 had the status reader ask GitHub about each watched branch on its own, with `gh pr list --head <branch>`, a minute's answer at a time, on the timer and on every refresh. Ten threads on ten pushed branches cost 600 gh processes and about as many GraphQL points an hour of the sign-in's 5,000, which the user's own agents share. Nothing recognised a rate-limited answer, the match was by branch name alone, and a Git action made every repository's answers stale. T3 Code reworked the same reads after `7810fb26`; the study is `docs/research/2026-10-07-t3-github-rate-limits.md`. Sotto takes the parts that keep to decision 7. Everything still goes through `gh` on the user's own sign-in: Sotto calls no GitHub API itself and holds no token, which is the part of T3's work it does not take. What this decides:

- **One question per repository.** Pull request lookups of one repository that arrive within a short window (50 ms for a read the user is waiting on, 500 ms for the timer's) go in one `gh api graphql` query: an aliased `pullRequests(headRefName: $hN, ...)` per branch, each branch name passed as a variable and never written into the query, up to 25 a query (T3's `buildPullRequestsByHeadQuery`). All three states are always wanted, so they are written into the query rather than passed. A lookup of a repository and branch already waiting or in flight is shared. The workspace timer reads its watched threads together so their lookups meet; each thread's own reads still run in its lane, as the #766 amendment requires.
- **The head repository matches.** The query goes to the repository gh reads pull requests from in the folder, picked as gh picks it without a prompt (T3's `selectGitHubBaseRepository`): the remote `gh repo set-default` marked, as itself or as the `owner/name` the mark names, else the first of `upstream`, `github` and `origin`, else the first remote. A fork cloned as `origin` beside its parent as `upstream` is asked about at the parent, where its pull requests are. A remote behind an SSH alias for GitHub (`git@github-work:...`, `ssh.github.com`) is asked through github.com, as T3's `gitHubApiHostForRemote` does, so it shares github.com's allowance. A pull request counts as the branch's own only when its head is in the repository the branch is pushed to (Git's push remote for it, decision 8), by `headRepositoryOwner` and `isCrossRepository`. A fork's `main` is no longer shown on the user's `main`, and a triangular branch pushed to a fork still finds the pull request it opened against `origin`. A remote that is not on GitHub, a local path among them, is not asked about.
- **Answers last as long as they safely can.** An open pull request is kept a minute, none five minutes (T3 #13189), a merged or closed one fifteen minutes or until the branch's tip moves. This amends decision 2's "cached a minute".
- **The reserve and the pause.** Every query asks for `rateLimit { limit remaining resetAt }` and the signed-in login, at no extra cost, and one allowance per process keeps the latest reading per GitHub host and sign-in; the status reader and the Pull request surface share it. The timer's reads are background reads: they stop while less than 10% of the points remain, until the reset GitHub gave. A read the user asked for (a refresh, a Git action, the Pull request surface) may spend the rest. A rate-limited answer, primary or secondary, as gh words it on its error output, pauses every background question to that host: until the reset for a primary limit with a known reading, otherwise 30 seconds doubling up to 15 minutes. This replaces each branch backing off on its own; other failures keep the per-branch back-off. A read the user asked for goes through a pause and is refused without asking only when GitHub last reported nothing left. While paused, the last answers stand, and the timer asks nothing at all for a branch whose host is paused, Git included. Only the stable event names `github-rate-limited` and `github-reserve-reached` are logged, never gh's words.
- **A refusal the user sees.** A Pull request surface read held back by the limit says so in plain words with the time it may be asked again, in the window's own clock, over the reading it already shows; the Link and Checkout dialogs say it too, and a press says when to try again in minutes. The host protocol's `git-pull-request` answer gains `{ limited: { retryAt } }` for it. A desktop older than this reads it as a read that failed and says so in its usual words, so no feature flag guards it.
- **An action refreshes only its own repository.** A Git action, a pull request press or Restore branch makes only its own repository's fetch timing, default branch, branch list and pull request answers stale; the #766 amendment's rule that an answer asked before an action never lands over one asked after it now holds per repository. A folder the reader has not read yet still makes every repository stale.
- **The Pull request surface reads once.** Its `gh pr view` and the `gh api graphql` read beside it are one GraphQL query: the pull request, its checks, the reviews that took a side, how far it is behind its base (compared through GitHub's own `refs/pull/<number>/head`, which the base repository has for a fork's pull request too), and the repository's merge methods, which are then kept for 15 minutes per repository and left out of the query. A part GitHub refuses, such as a comparison it cannot make, shows as unknown rather than failing the read. The read a press makes to settle itself stands, once and for 15 seconds, for the window's read that follows, so a press costs one read rather than two.
- **The cleanup sweep runs when its rules change.** A settings save sweeps worktrees only when the cleanup rules or Auto-settle merged threads changed, so the #271 amendment's merged check (decision 3 there) asks GitHub no more often than the hourly sweep and a settle.

Before and after, measured over a scripted gh and Git: ten threads on ten branches for an hour with the window in front cost 600 gh processes before and 60 after with an open pull request on every branch, 12 with none; opening the Pull request surface costs one gh process instead of two, and a merge from it two instead of five (`docs/verification/2026-10-07-github-rate-limit.md`).
