# Git the way T3 Code does it

Accepted September 23, 2026. Issue #127; the plan is `docs/plans/2026-09-23-git-interface.md`.

## Context

Sotto's Git work grew in two halves that did not know each other: a Changes surface in the Tools panel that stages files, commits, switches branches and opens a pull request from Electron main, and a working-copy record on each thread that the host keeps (ADR-0014, ADR-0019). Nothing pulled, nothing fetched outside worktree setup, nothing pushed outside the pull request form, and no surface said whether a branch was ahead or behind. Every day started and ended in a terminal.

T3 Code, the reference for the Threads page, does Git as one model: a status the server streams (branch, upstream, ahead and behind, dirty, the default branch, the branch's pull request), a branch picker and workspace choice on the composer, one adaptive Git action in the header that commits, pushes and opens the pull request from a press, a diff panel with scopes and no staging, and pull requests through `gh`. Zach chose that model outright on September 23 rather than a Sotto variation of it. The plan records the model as read from T3's source at `7810fb26` and maps it onto Sotto's surfaces.

## Decision

Sotto builds T3's Git model piece for piece, in the order the plan's tickets give (#264 through #272). The decisions that are Sotto's own, because T3's model meets a rule Sotto has, are these:

1. **The background fetch is a setting, on by default, and it runs only while the window is in front.** T3's status depends on a fetch; without one Pull never appears and Push is blind. Sotto runs `git fetch --quiet --no-tags origin` for each open thread's project, with prompts disabled so nothing is ever answered on the user's behalf, on a timer at the **Git fetch interval** (30 seconds unless changed; Off stops the timer's fetches) and when the user refreshes a working copy, never more than once in 15 seconds (T3's figure), and only while the window is in front: showing and focused, or focused within the last 45 seconds; a headless host counts a connected client as its window. A fetch that fails backs off and status reads on from the last fetched refs. ADR-0019 refused an hourly fetch for the cleanup rules and is not reopened by this: the fetch here is the user's own remote, named in the README, under a setting.
2. **The branch's pull request is read through `gh` on refresh and on the same timer**, cached a minute and asked again after a Git action, for branches that have been pushed. The README says so beside the cleanup rule that already asked.
3. **Status lives on the thread's worktree record.** The host reads it after a turn (local only), on a refresh (remote too) and on the timer for the threads a window is looking at, and publishes only a status that changed. Riding on the record means every client, local or paired, gets it through the state stream Sotto already pushes, and no new socket operation is needed for it. What a control reads once when it opens, the branch picker's refs and the commit dialog's changed files, is a host operation advertised as a host feature (`git-refs`, `git-changed-files`, ADR-0025) rather than a field on every state. Commit and pull request text read more of the repository than before, as T3's do (recent subjects, `AGENTS.md`, the pull request template); ADR-0026's side call already goes to the thread's provider in the working folder, so nothing new leaves the machine, and the README sentence that said "the staged diff alone" changes when that lands.
4. **Staging leaves the UI.** T3 has none; the commit dialog's file list is the choice. Sotto's Stage and Unstage file, and the staged and unstaged scopes, go with their tests when the Changes surface is rebuilt.
5. **A branch switch keeps the thread right.** T3 switches without asking and lets Git refuse when work would be lost; Sotto does the same and refreshes the thread record afterwards so the label, `sentBranch` and the shared-folder notice follow (ADR-0014). Restore branch keeps its confirmation.
6. **One press may commit, push and open a pull request.** The control's name says all three. Pushing from the default branch asks first, as in T3. T3's Proactive panels, which open the diff unasked, ship as a setting that is off until turned on.
7. **GitHub only, through `gh` on its own sign-in.** T3 supports five hosting providers; another is an ADR and a README line.
8. **Git runs on the host.** The status reader and the actions are built Electron-free beside `ThreadWorktrees` and wired in `createAgentRuntime`, so a remote thread gets the same button; the remote command list carries `git-action`, `git-pull`, `git-switch-branch`, `git-init` and `git-publish`, none of which needs an answer policy: Git refuses a switch that would lose work, a push is never forced, and a pull is fast-forward only. Commit and pull request text read the repository's recent subjects, its `AGENTS.md` and its pull request template, as T3's do. Linking a created pull request to its thread waits for the pull request surface (#269); until then the branch's pull request is read back into the status. One departure from T3 in the push: a `pushRemote` or `remote.pushDefault` that names a remote other than the upstream's is honoured, the way Git's own `git push` honours it, so a triangular workflow pushes to its fork. Sotto's checkpoints stay Sotto's: turn diffs come from the content-addressed blobs, not from Git refs.

## Consequences

`gitFetchIntervalSeconds` is a new setting on the IPC patch allow-list, with a control under Settings → Application (since moved to Settings → Git, decision 7 of the #271 amendment). `AgentWorktree` gains `git`, a `GitStatus` from `src/shared/gitStatus.ts`. The README's privacy section names the fetch and the pull request lookups. `ThreadWorktrees` still switches nothing on its own; the status reader reads and fetches and changes no ref of the user's.

The later tickets amend this record where they decide something rather than follow it: the Changes rebuild (#268) when staging goes, the actions (#265) when the remote command list grows, the settings (#271) when Proactive panels land.

## Amendment: the Changes rebuild (#268)

Staging has left the UI as decision 4 said: Stage file, Unstage file and the staged and unstaged comparisons are gone with their tests, and so are the Electron-side `commit`, `checkout` and `create-branch` actions, the branch list and the commit message draft that only the old drawers reached. Changes now reads only; its main-process side is the change list, one `review` read per comparison, Copy path and reveal. What #268 decided beyond T3:

- **Working tree** diffs HEAD through a copy of the index with untracked files marked intent-to-add, as T3 does, so the user's index is never written. Untracked files larger than 512 KiB, or that are not regular files inside the folder, are listed without their text.
- **Automatic** is T3's base order (the branch's `gh-merge-base`, the remote's default branch, `main`, `master`, the primary remote's copy preferred). With no base found, Branch changes says so and asks for one rather than guessing.
- **Turns** are diffed in the renderer from the before and after text the checkpoint already hands to the Checkpoints drawer, with a line diff of Sotto's own (no new dependency). A turn's number is its place among the thread's checkpoints in that working copy, oldest first, because a checkpoint records no turn number of its own.
- **The shortcut.** Bend 9 left the fallback chord open: it is `mod+shift+d`, taken only when the dictation hotkey holds `mod+d`, and dropped when it holds both. Focus inside a terminal keeps Ctrl+D for the shell.
- Layout, wrapping, whitespace, the file tree and collapsed files are session state until #271 adds their settings.
- Changes still reads Git from Electron main, so it reads only local threads; its base picker already uses the host-capable `git-refs` read. A remote thread's Changes stays unavailable until Changes itself moves to the host, which decision 8 leaves for later.

## Amendment: the settings (#271)

T3's Git and diff settings land as `gitAutoPull`, `defaultMergeMethod` and `lastMergeMethod`, `diffLayout`, `diffHideWhitespace`, `diffFileState`, `gitWritingStyle` and `gitWritingInstructions`, `followPullRequestTemplates`, `autoSettleMergedThreads` and `proactivePanels`, each on the IPC patch allow-list. What Sotto decided rather than followed:

1. **Everything that acts on its own starts off**: Automatically pull, Auto-settle merged threads (on in T3) and Proactive panels. The rest start where T3 does: Last selected starting from Merge, stacked, whitespace hidden, files collapsed, the repository's conventions, templates followed.
2. **Automatically pull is T3's rule on the host**: at a remote status read, a folder on the default branch, clean, tracking an upstream and only behind is pulled with the Pull action's `--ff-only`, and a folder any thread is working, waiting, setting up or running a Git action in is left for the next read. The desktop reads the setting live; a headless host reads it at start.
3. **Auto-settle merged threads rides the worktree cleanup's hourly sweep** and its `gh` question rather than the status stream's pull request, so it asks GitHub no more often than the merged rule already did, and once per branch when both want the answer. It settles a thread at rest by the branch it last sent on (a worktree's own branch before its first send), never the default branch, and once per thread and branch while Sotto runs, so a restored thread stays restored; after a restart one that is still on its merged branch may be settled again. Settling removes nothing; the on-settle cleanup rule decides about the folder as it does for any settle.
4. **Proactive panels opens only a closed panel** that is not pinned to another thread, and it does not move keyboard focus. A turn is large when its thread's Git counts grew by at least 3 files or 50 lines (T3's measure) between the turn's start and the host's first read after it ends. These are the working copy's counts, not the turn's own diff: edits by hand or by another thread in the same folder during the turn count too, and a file the turn changed that was already changed does not. The watch lives in the Tools panel, so it counts only while the Threads page is open, and a turn that ends while another page is showing is not measured. A large turn waits with its thread until that thread is focused, and Changes opens then; it is let go once the thread has been focused, whether or not the panel could open, or once Changes is opened for that thread. It lives on the Tools panel store, not in Changes.
5. **The last merge method is remembered only while the default is Last selected**, in settings, so it survives a restart and a second window.
6. **Changes starts where the settings say, and the merge method waits.** The rebuilt Changes (#268) takes Diff layout, Hide whitespace changes and Default diff file state through `useDiffPreferences` as its starting view: layout and whitespace when Changes first opens and whenever a setting changes, collapsed files for each comparison as it is first read. What the controls choose lasts until one of the three settings changes or Sotto restarts (a change to any of them sets layout and whitespace again together), which amends #268's "session state until #271". Changes waits for settings before its first read, so a cold start does not read once with whitespace shown and again with it hidden. The merge method is saved and exposed through `useMergeMethod`, but nothing reads it until the pull request checklist (#294) adds its merge. The Settings copy describes that merge, which starts on this method.
7. **One Git section, grouped by moment.** Of three layouts prototyped (`docs/prototypes/git-interface-surfaces/settings.html` on the branch `prototype/git-interface-surfaces`, with the owner's verdict in `VERDICT.md` beside it), the owner picked B on September 23, 2026: every setting above, and the Git fetch interval from decision 1, sit in Settings → Git under When a thread commits, When a pull request is made or merged, When you read Changes and In the background, rather than at the ends of Application and Cleanup. Each description is a sentence about what Sotto will do with the value shown and changes with it. The style row carries an example subject and title; the prototype had it rewrite the example from custom instructions with a few pattern rules, which would guess at a model's answer, so the built example keeps the plain subject under Custom and says the thread's own model applies the instructions when it drafts. The worktree cleanup rules stay under Application and the Generated switches under Cleanup, where the prototype left them.

## Amendment: review comments (#270)

Zach picked T3's way from the prototypes on September 23 (`docs/prototypes/git-interface-surfaces/review-comments.html` on the `prototype/git-interface-surfaces` branch, variant A; the pick is in that folder's `VERDICT.md`): pick lines, write the comment under them, a chip on the composer and a marker on the diff until the message goes. What #270 decided beyond T3:

- **A comment is text in the prompt, not a new field.** At the press the composer writes each comment after the user's message, in the order written: `Comment on` and the comment's name as a code span (`src/main/voice.ts L12 to L13`, `L4 to L5 (before)` when every line was removed), a blank line, the user's words, a blank line, then the lines as a ```` ```diff ```` fence with `+`, `-` or a space before each. A fence or code span is always longer than any run of backticks it quotes. Nothing in main, the command schemas or the four adapters changes, so every provider reads the same message, and the file mention's `@path` rules are untouched.
- **The comments go into the revision that is sent.** The composer writes them into the draft's text as a new revision just before submitting it, so the saved revision, the delivery's digest and the sent message agree, and a refused prompt comes back to the composer with its comments written in rather than lost. A queued follow-up and a steer carry them the same way; an answer to a question does not, and the composer says they wait for the next prompt.
- **Comments are held in the window, not saved with the draft.** They live in the renderer per thread until sent or deleted and are gone when the window closes or reloads. Saving them would add a field to the durable draft, its schema, the follow-up queue and the delivery digest for a note that is only minutes old; that is left until someone misses one. They are never saved as comments and never logged. Once written into a prompt they are part of it: the prompt's revision is saved as any draft is, so a refused prompt comes back with them in its text, and a sent one is the thread's history.
- **A comment keeps the lines it was written on.** When the diff changes, the comment still sends those lines. Its marker stays under the row that draws a line of the same kind, numbers and text, and when there is none it moves to the end of the file and says the lines have changed since (or, when its line is only past the first 3,000 rows drawn, says to Show all). A comment on lines the comparison on screen does not draw (a file committed since or outside the turn picked, a file whose only change is its mode or name, or a comparison that could not be read) is listed after the files under **Comments on lines this comparison does not show**, with Delete comment, and so is a draft with words whose lines are not drawn, with its text field and Cancel. So a comment stays in sight in Changes until it is sent, as #270 asks. A draft with words in it is never replaced by opening another; a click elsewhere drops only an empty one.
- **The keyboard path.** Each file's lines are one grid and one stop in the Tab order, with the Comment button and each comment's controls after them where they are drawn: the arrow keys, Home and End move, Shift extends, Space picks, Enter opens the draft on what is picked (or the line under focus), Escape lets go (from the lines, the Comment button or a marker) and leaves the panel's own Escape alone when nothing is picked. In the draft, Escape cancels and Ctrl+Enter (Command+Enter) adds. None of these is a global chord, so none can meet the dictation hotkey; `mod+d` still toggles Changes from the draft and the draft is still there when Changes reopens.
- **At most 20 comments a message**, said on the draft and the Comment button rather than dropped.
