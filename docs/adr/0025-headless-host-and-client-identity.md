# A Node host on Forge, with clients that keep the host's identity

Accepted in scope for #134's implementation on September 20, 2026: Zach requested the Forge host and desktop/phone clients, with parallel work on its tickets. This records the headless runtime and persistent host identity decisions from proposed PR #133. That PR used number 0017, which is now occupied by the Devin data-policy decision; this record neither replaces Devin nor claims that PR merged. It was written as 0022 and renumbered 0024 on September 22, when main's Devin permission-mode decision took 0022 and its effort-order and background-work decisions took 0023 first, then renumbered 0025 the same day because open PR #253's palette decision claims 0024; either can now merge first without a third duplicate. It amends ADR-0016, which had left the remote path and the pairing flow open and added no listening socket. The owner selected pairing variant B on September 21: read a code from Forge and enter it on the client. This selects the code-entry flow without granting any permission authority. The first phone target is an iOS app similar to T3 Code, following the owner's September 21 correction. This supersedes the earlier browser assumption; it does not select an app framework. In the subsequent September 21 answers, the owner accepted requiring Tailscale and an existing-thread first release, and reported an Apple developer account; TestFlight is the planned delivery path. Account enrollment, signing and build access remain unverified.

The host owns its workspace, providers, worktrees and retained history in one Node process. The desktop keeps Electron windows, dictation, hotkeys, paste, tray and updates. Both entry points share the agent runtime. Provider identifiers stay inside their adapters under ADR-0002; remote clients address a Sotto thread within the host that owns it. A separate repository would introduce a second release cadence and shared package before either is useful.

Each host mints a persistent UUID in its data folder. Threads, projects and published state carry that host ID; a client keys its local state by the pair of host ID and entity ID. A route or SSH address changing does not rename a host. Existing organization data is stamped idempotently, and a failed migration leaves its original file intact. Host IDs are names, not credentials or permission grants.

The headless entry uses built-in Node cryptography for an encrypted credential file with a user-supplied key kept separately. It uses the existing credential slots and does not copy native provider sign-ins. The desktop keeps its OS credential store. A wrong key or corrupt encrypted file must refuse startup without replacing the file. Production dependencies remain zod and node-pty under ADR-0018; no Electron import belongs in the host entry's import graph.

SSH remains the first planned remote path: the desktop launches the platform's SSH executable, forwards a port to a loopback host listener, and starts or discovers the host. Pairing supplies client attribution; only the user's answers and policy records supply authority under ADR-0004. Transport, SSH launch, optional local host and remote client selection remain the dependent tickets #137, #138 and #142; these foundations add no production listener.

Linux is host-only. Its intended release is a plain archive of built Node output, dependency/runtime inventory, provenance and checksums, published beside desktop installers. It needs a native Linux startup/socket contract gate, but no Linux window or desktop design gate. Packaging, pinned runtime details and publication are #140; this decision is not evidence that an archive has shipped. Desktop design checks remain required for desktop UI, and iOS simulator and real-device checks for the later phone app. Native app packaging, signing, connection credential storage and foreground/background recovery need their own implementation and verification; HTML mock-ups do not satisfy those checks.

Host identity migration preserves the existing privacy recovery rule. When Keep local history is off, a syntactically invalid or schema-invalid workspace snapshot follows the existing recovery path, which discards that unreadable snapshot and removes Sotto's abandoned private copies. Those two parse failures are the only exceptions: file access errors, refused writes, an invalid host identity and a valid workspace owned by a different host stop startup without changing the workspace. With history enabled, even malformed workspace bytes remain untouched after failed initialization and disposal.

## Implementation of remote clients (September 21)

The authenticated host transport uses versioned JSON over a WebSocket served by Node's built-in HTTP and socket primitives. The listener binds only to loopback; the desktop reaches it through a directly spawned SSH tunnel and the iOS app reaches it through private Tailscale HTTPS. Pairing B exchanges a short-lived host-displayed code for a revocable client credential. Credential presentation obtains a signed session, and each operation is checked against that session and the existing host policy. The listener never accepts a client-supplied grant identity. Pairing and remote request answers do not create policy records.

Each client owns its navigation, observation set and detail revision bases. A reconnect fetches the current shell and selected detail as well as retained events after its last sequence, because message events alone cannot reconstruct shell changes. (Amended September 23, below: the desktop reads no events, so it asks for none.) An uncertain command is reconciled, not resent automatically. Payloads and buffered output are bounded. Tokens, pairing codes, prompt bodies and transcripts are never ordinary logs. The local administrative command may display a pairing code explicitly to the user. Host control and code issuance are limited to the local administrative path, not unauthenticated remote requests.

The desktop may show local and connected remote threads together, using host-qualified identities. Routing is resolved before decoding an entity ID to its host-local value. Remote folder, terminal and paste actions explain the owning machine; none silently run against the laptop. A disabled local host starts no provider/coordinator runtime and removes no saved data. Dictation remains local and available.

The first iOS package uses SwiftUI, Foundation networking and Keychain in a separate apps/ios directory. T3 provides the native-client and lifecycle reference; SwiftUI is selected for this iOS-only scope to avoid a second JavaScript runtime and third-party mobile dependencies while using native accessibility, signing and storage. The wire protocol, rather than UI or Node code, is shared across platforms. The app needs independent native codec/reconnect tests, simulator and real-device verification, and its own signing/release instructions. The existing desktop/host dependency allow-list remains unchanged. TestFlight is planned; credentials and signing access must be verified before any upload.
## September 21 amendments after the T3 Code comparison

Over SSH the desktop pairs itself. The tunnel is already the user's authenticated session, so asking the user to copy a code from one window to another proves nothing more; the desktop asks the launch script (the fixed Node script it runs over SSH to find, start and stop the host) for a code and redeems it, the way T3 Code's desktop issues its own pairing credential over SSH. The code-entry flow remains for the phone, which has no SSH session. A host that the desktop started runs detached and outlives the SSH connection; a dropped connection is not a decision to stop work, and a host Sotto found already running is never stopped. The desktop reconnects a dropped connection with capped backoff, restoring the forward before the socket, which fetches the current shell again (and, since September 23, no events; see below). Errors that need the user (a prompt, a changed host key, a missing archive) stop the retries and say so. Pairing still grants no authority: a paired computer's permission answers count only after the host's policy record allows them.

## September 22 amendment: the host outlives the desktop

A host Sotto started keeps running when the desktop disconnects, quits or crashes, and stops only when the user presses Stop host or Forget while connected. This is where Sotto departs from T3 Code, whose tunnel finalizer stops a managed server on orderly close and app quit and whose reconnect path restarts it. Two things Sotto has and T3 does not decide it: a phone client that needs the host up with no desktop attached, and provider processes mid-turn that a restart would kill. The cost is a host nobody is watching, so Disconnect and Stop host are separate controls whose names say what a press does, and the Hosts page says the host keeps running. A host that cannot be reached can still be forgotten; the desktop then says its access on the host stays until revoked there.

A remote host reads its OpenRouter key from its own encrypted credential file, not from the desktop: a paired client may not send a credential, and the desktop's key never leaves it. OpenRouter-hosted reasoning on a remote host therefore needs a copy of the key placed on that machine. This is the one-key rule applied per machine rather than a second kind of key; the README says so beside the host commands. (Amended by [ADR-0026](0026-short-writing-runs-on-the-threads-own-provider.md): thread titles and branch names no longer use the key; the provider running each thread writes them, so a host needs no key for them.)

Because a host may now outlive a reboot of its machine, a host starting into a data folder whose `host-listener.lock` names a process that no longer exists reclaims the lock instead of refusing, and the launch script waits for a host whose lock holder is alive but not yet listening, so two clients connecting at once do not race to start two hosts. A lock whose holder still runs, or one that cannot be read, is refused without being touched. Reclaiming is atomic: starting hosts take turns to clear a stale lock through `host-listener.lock.reclaim`, and in its turn a host reads the lock again and removes it only if it is still the dead holder's lease, so however many hosts start together after a crash, only one owns the folder and a live lock is never moved. The removal also moves the lock to a name only that host uses and checks what it moved, putting back anything else; that guards the one case the turn does not, two hosts holding the turn together after a host stopped in the middle of its own, and a lock that cannot be put back then is logged and refused in words that say another host may have the folder. A turn left by a host that stopped is cleared the same careful way. The lease also records the machine's boot, so a process that took the old holder's pid after a reboot is not mistaken for it, and a process another account owns counts as running. The launch script's own check must follow that rule too, but it does not yet: it still counts a process it may not signal as gone, and it does not read the boot. Bringing it into line is the launcher half of #242. Until then, a pid another account took after a reboot makes the launch script start a host where it should have waited, and that host reclaims the folder correctly.

## September 22 amendment: what a paired client may send

"Checked against that session and the existing host policy" left open which commands a paired device may send at all. The answer is a closed list in `src/host/remoteCommands.ts`. Every command type and every field a paired client may carry is named there. A command or field added to the command schema is refused remotely until someone adds it on purpose, and a unit test fails until each one is decided either way. Host-local stays host-local: credentials, membership, the voice commands and voice engine, reasoning checks, opening a folder on the host machine, and installing provider client updates. A paired device is not the user at that computer, so what it may do is decided command by command rather than inherited from the desktop's IPC surface.

Some commands on the list are the user's answer to a question in another form, so they need the same `remote-answer` policy record, scoped `client:<clientId>`, that an answer needs under ADR-0004. They are: an answer; a runtime mode other than approval-required, on New thread or a thread's settings; a provider mode whose allowance is more than nothing; and reclaiming a worktree or restoring a branch with `withUncommittedChanges`, which discards work the user has not committed. A permission setting is judged by what it allows, not by where the provider lists it, because a provider's list is only the modes it happens to report. A setting that grants nothing is free, so a device without the policy can always put a thread back to asking. Without the policy the host refuses with `forbidden`, and the refusal says to check the device's permission policy or finish on the host.

`configure` carries only these coordinator settings: provider, enabled providers, enabled, default model, reasoning, reasoning model, reasoning effort, follow-up limit, orb colour and spoken replies. Spoken replies and the orb colour are preferences. The follow-up limit only bounds work the user already assigned, and a paired device may send those follow-ups itself. None of them answers a request. Keys, endpoints and the voice engine (speech provider, voices, wake word) stay on the host.

## September 23 amendment: the host reclaims its own worktrees

A headless host owns worktrees as the desktop's local host does, so it reclaims them the same way (ADR-0019, #245). The worktree cleanup is built by the shared agent runtime rather than by the desktop's entry, and both entries start it once they are up; closing the runtime drains a sweep in progress, letting it finish the worktree in hand and start no other, before the coordinator and the workspace close. A host follows the cleanup rules in its own data folder's settings, read at start and all off by default, and asks GitHub through the host machine's own `gh` sign-in only when the merged rule is on there. A paired client cannot change those rules yet; they are not on the remote command list.

## September 23 amendment: what a reconnect downloads, and the listener's budgets

Two findings from the third review of #181 (#241 and #243) changed how a connection spends the host's time.

Nothing on the desktop reads a host's event log. The router draws threads from the shell and from the details the window observes, and message events cannot rebuild a shell anyway. Yet the desktop client opened every connection from sequence 0 and paged through the whole log, 256 events at a time, and on a long log those requests passed the 100 messages a second that close a peer, which started the reconnect over from 0. The desktop client now asks for no events: its hello names a sequence past any the host can reach, and it follows no catch-up a push offers and reads no page after a command. Everything else a reconnect fetches is unchanged: the current shell, and the detail of each thread observed on that connection. Those are what the desktop shows. The alternative was to save the last sequence per saved host so a reconnect asked only for what is new. It was not chosen because it would store a cursor to protect a download nothing reads, and would still download each host's whole log once. A client that does read events, the phone, keeps its cursor and resumes from it as above. The listener paces event pages on their own budget, 100 a second, where a page past the budget waits for the next second instead of counting towards the cutoff. A client reading a long log one page after another is doing what the protocol asks, and closing its socket would only have it start again.

The HTTP listener used to count every request against one budget of 120 a minute, so a loop on the unauthenticated health or pairing endpoint could stop every paired client from opening a session. It now counts per endpoint class. Health is not counted: refusing it costs the host as much as answering it, and the launch script polls it while a host starts. Pairing has 10 a minute of its own. Sessions and revocations have 120 a minute for each paired client, and the administrative path has 120, each counted only after its token checks out, so a loop on a bad token spends nobody's budget. Past a budget the host answers 429. A client says the host is busy, nothing was lost, and to try again in a moment. It is not a pairing failure: the desktop keeps its credential, does not pair again, and a reconnect keeps retrying. When the desktop is already pairing again because the host no longer knows it, a busy answer to that pairing is likewise not final, and the reconnect retries it.

## September 23 amendment: protocol v1 is frozen, and how versions meet

The wire protocol described in "Implementation of remote clients" is version 1, and it is frozen from the pull request for #238 and #239, before the iPhone client (#225) builds against it. [The host protocol](../host-protocol.md) lists every message. Two things went in first, because neither can be added to a frozen protocol without breaking a client that exists.

Detail over the socket travels as deltas. The desktop's IPC already sends a viewed thread's change as `AgentThreadDetailDelta` rather than the whole thread, and #181 coalesced socket pushes and made an oversize one an explicit `too_large` error. The host now forwards the delta its detail stream publishes as a `detail-delta` push instead of reading the whole thread again for every change. A client applies one only to the revision it holds and otherwise reads the whole thread once, the rule the window already follows. The `too_large` error names the thread whether it replaced a detail or a delta, and a client does not keep asking for a thread it was told is too large.

Hosts and clients now say which Sotto they are. `/v1/health`, `host-listener.json` and the hello reply carry `sottoVersion` and `features`, the list of host features the host offers. A client reads health before it opens a session and uses only what is listed; it never learns what a host supports by sending a request and reading the refusal. The first feature is `detail-delta`, and a client asks for it by name in hello's `accepts`, so a client written before the freeze keeps receiving whole details from a newer host rather than a push it cannot read.

The version rule: `v` stays 1, and v1 changes only by adding an optional field, a feature in `features`, or a push form a client asks for in `accepts`. Anything else is version 2 with its own support window. `sottoVersion` alone is not a compatibility test, because a host outlives desktop updates on purpose and a restart interrupts its turns; a patch release that changes nothing on the wire must not force one. A host with no `features` predates the freeze. The desktop sends it nothing more and says which side to bring up to date: for an older host, to put this computer's version of the host in its installation folder, press Stop host (or stop it on that machine, for a host Sotto did not start) and connect again, because Connect starts whatever is installed; for a newer host, to update Sotto on this computer. Stop host stays on the Hosts page for an older host Sotto started. Between two v1 builds of different Sotto versions the thread and command shapes can still differ, so a host of another version refusing a request as unreadable, or sending what the client cannot read, produces the same sentence rather than "This request is not supported" or a closed socket. To make that possible the host now answers an unreadable request from an authenticated session with `invalid_request` by its ID instead of closing the socket. Requests stay strict (`.strict()`), so an unknown field is still refused rather than ignored; only feature names are read leniently, so an unknown one is skipped.

The issue asked for "a capabilities list". The hello reply already had `capabilities`, which is what this client may do on this host (`mayAnswer`), and the shell's `capabilities` are what a provider can do. A third meaning under the same word is what `CONTEXT.md` exists to prevent, and changing hello's `capabilities` would have broken every desktop already released, so the list is named `features` and the glossary has **Host feature**.
