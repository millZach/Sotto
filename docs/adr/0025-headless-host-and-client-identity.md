# A Node host on Forge, with clients that keep the host's identity

## October 5 amendment: a tailnet connection, and a host that starts at boot

[ADR-0053](0053-a-desktop-reaches-a-host-over-its-tailnet-first.md) and [ADR-0054](0054-a-host-can-start-at-boot-on-linux.md), accepted October 5, 2026 under the owner's delegation, change several statements below. Where they disagree with this ADR, they win.

- **SSH is no longer the only path** (the decision's "SSH remains the first planned remote path", and the September 21 transport paragraph). A desktop paired with a host reaches it first through the host's tailnet address, over the host's tailnet listener carried by Tailscale Serve, and uses its SSH connection when the tailnet does not answer or the owner chose SSH only. The listener still binds loopback only. Pairing, the `remote-answer` grant and every launch script operation stay on SSH, and the desktop never pairs on the tailnet.
- **The forward is no longer the only connection** (the September 23 amendment's "the `-N -L` port forward is the only long-lived ssh, and its exit is what a dropped connection is"). On the SSH connection the forward still carries the socket, as below. On a tailnet connection there is no forward, and a press that needs the launch script opens an admin connection, an SSH connection with no socket on it that closes 60 seconds after its last use. A dropped connection is the socket closing, on either connection.
- **Failure codes** (the September 23 amendment's typed codes). A tailnet connection adds its own classes: unreachable, wrong host and a client the host does not know as a desktop fall back to SSH, a refused pairing pairs again over SSH, and a version mismatch is final, as now. Retry decisions still read the code alone, and a final code still stops them.
- **A dropped connection keeps the host's threads** (the September 21 amendments' reconnect). A drop, or a move between the tailnet and SSH, marks the threads as reconnecting and swaps the connection in place, as a host update does (ADR-0040). A final failure still takes them away and the row says what to do.
- **The desktop's grant is honoured on the tailnet** (the September 29 amendment). It is still written only over SSH, but the desktop's token, and the grant with it, now works from any device on the owner's tailnet. ADR-0053's first consequence says what that changes.
- **A host that starts at boot** (the September 22 amendment, "stops only when the user presses Stop host or Forget"). On Linux with a systemd user manager, a host can also be started by its boot unit, which records `startedBy: "boot"` (the September 23 amendment's "who started a host"). Such a host counts as started by Sotto. Stop host stops it until the machine restarts or the owner switches it on, and Forget removes the unit.

## September 29 amendment: an SSH desktop can answer at setup

Zach chose automatic desktop authority when setting up a remote PC, without another prompt. This amends the earlier requirement to run `--allow-answers` separately for a desktop that connects through the user's authenticated SSH session. After the host confirms the desktop's actual paired client ID, the SSH launch script creates one `remote-answer` policy record for that client if it has never had one. The record, with source `user` and a note naming the authenticated SSH connection, is still what authorizes answers, permissive thread modes and the other commands that require it; pairing alone never does.

The script writes that one policy through an atomic conditional insert in the host's existing policy database. This also repairs an existing desktop pairing with no policy and works with the existing host archive: no new socket request, client-supplied authority or host upgrade is needed. It checks the running host's identity and that the client is still paired before writing. Concurrent connections cannot create duplicate grants. Any previous policy for that client, including a revoked, expired or always-confirm record, prevents the default grant. Reconnecting never restores revoked authority, and an unreadable pairing or policy store refuses setup without replacing either.

The user still chooses each thread's permission mode and answers each request. Code-entry and phone pairing receive no default authority and retain their explicit grant controls. No additional host, credential transfer, automatic request answer or setup control is introduced.

Accepted in scope for #134's implementation on September 20, 2026: Zach requested the Forge host and desktop/phone clients, with parallel work on its tickets. This records the headless runtime and persistent host identity decisions from proposed PR #133. That PR used number 0017, which is now occupied by the Devin data-policy decision; this record neither replaces Devin nor claims that PR merged. It was written as 0022 and renumbered 0024 on September 22, when main's Devin permission-mode decision took 0022 and its effort-order and background-work decisions took 0023 first, then renumbered 0025 the same day because open PR #253's palette decision claims 0024; either can now merge first without a third duplicate. It amends ADR-0016, which had left the remote path and the pairing flow open and added no listening socket. The owner selected pairing variant B on September 21: read a code from Forge and enter it on the client. This selects the code-entry flow without granting any permission authority. The first phone target is an iOS app similar to T3 Code, following the owner's September 21 correction. This supersedes the earlier browser assumption; it does not select an app framework. In the subsequent September 21 answers, the owner accepted requiring Tailscale and an existing-thread first release, and reported an Apple developer account; TestFlight is the planned delivery path. Account enrollment, signing and build access remain unverified.

The host owns its workspace, providers, worktrees and retained history in one Node process. The desktop keeps Electron windows, dictation, hotkeys, paste, tray and updates. Both entry points share the agent runtime. (Amended by [ADR-0036](0036-a-host-connects-every-signed-in-provider-it-can-find.md): a headless host connects every provider signed in on its machine when it starts, except the ones the user turned off, rather than only the providers its saved settings name.) Provider identifiers stay inside their adapters under ADR-0002; remote clients address a Sotto thread within the host that owns it. A separate repository would introduce a second release cadence and shared package before either is useful.

Each host mints a persistent UUID in its data folder. Threads, projects and published state carry that host ID; a client keys its local state by the pair of host ID and entity ID. A route or SSH address changing does not rename a host. Existing organization data is stamped idempotently, and a failed migration leaves its original file intact. Host IDs are names, not credentials or permission grants.

Project working-copy defaults stored on the desktop use the host-local project ID for local projects, which is what the local runtime reads, and the host-qualified client key for remote projects. Startup repairs local defaults saved under client keys by the former Settings row (#497). An existing host-local override wins if both entries exist; remote entries stay qualified and unchanged.

The headless entry uses built-in Node cryptography for an encrypted credential file with a user-supplied key kept separately. It uses the existing credential slots and does not copy native provider sign-ins. The desktop keeps its OS credential store. A wrong key or corrupt encrypted file must refuse startup without replacing the file. Production dependencies remain zod and node-pty under ADR-0018; no Electron import belongs in the host entry's import graph.

SSH remains the first planned remote path: the desktop launches the platform's SSH executable, forwards a port to a loopback host listener, and starts or discovers the host. Pairing supplies client attribution; only the user's answers and policy records supply authority under ADR-0004. Transport, SSH launch, optional local host and remote client selection remain the dependent tickets #137, #138 and #142; these foundations add no production listener. (Amended by [ADR-0033](0033-the-desktop-lets-paired-phones-reach-its-threads.md): with phone access on, the desktop opens the same listener on loopback over its own local host, reached by paired phones through Tailscale Serve.)

Linux is host-only. Its intended release is a plain archive of built Node output, dependency/runtime inventory, provenance and checksums, published beside desktop installers. It needs a native Linux startup/socket contract gate, but no Linux window or desktop design gate. Packaging, pinned runtime details and publication are #140; this decision is not evidence that an archive has shipped. Desktop design checks remain required for desktop UI, and iOS simulator and real-device checks for the later phone app. Native app packaging, signing, connection credential storage and foreground/background recovery need their own implementation and verification; HTML mock-ups do not satisfy those checks.

Host identity migration preserves the existing privacy recovery rule. When Keep local history is off, a syntactically invalid or schema-invalid workspace snapshot follows the existing recovery path, which discards that unreadable snapshot and removes Sotto's abandoned private copies. Those two parse failures are the only exceptions: file access errors, refused writes, an invalid host identity and a valid workspace owned by a different host stop startup without changing the workspace. With history enabled, even malformed workspace bytes remain untouched after failed initialization and disposal.

## Implementation of remote clients (September 21)

The authenticated host transport uses versioned JSON over a WebSocket served by Node's built-in HTTP and socket primitives. The listener binds only to loopback; the desktop reaches it through a directly spawned SSH tunnel and the iOS app reaches it through private Tailscale HTTPS. Pairing B exchanges a short-lived host-displayed code for a revocable client credential. Credential presentation obtains a signed session, and each operation is checked against that session and the existing host policy. The listener never accepts a client-supplied grant identity. Pairing and remote request answers do not create policy records.

Each client owns its navigation, observation set and detail revision bases. A reconnect fetches the current shell and selected detail as well as retained events after its last sequence, because message events alone cannot reconstruct shell changes. (Amended September 23, below: the desktop reads no events, so it asks for none.) An uncertain command is reconciled, not resent automatically. Payloads and buffered output are bounded. Tokens, pairing codes, prompt bodies and transcripts are never ordinary logs. The local administrative command may display a pairing code explicitly to the user. Host control and code issuance are limited to the local administrative path, not unauthenticated remote requests. (Amended by [ADR-0033](0033-the-desktop-lets-paired-phones-reach-its-threads.md): the desktop's phone listener has no administrative routes; it issues codes and grants answers in-process, from Settings > Phones.)

The desktop may show local and connected remote threads together, using host-qualified identities. Routing is resolved before decoding an entity ID to its host-local value. Remote folder, terminal and paste actions explain the owning machine; none silently run against the laptop. A disabled local host starts no provider/coordinator runtime and removes no saved data. Dictation remains local and available.

The first iOS package uses SwiftUI, Foundation networking and Keychain in a separate apps/ios directory. T3 provides the native-client and lifecycle reference; SwiftUI is selected for this iOS-only scope to avoid a second JavaScript runtime and third-party mobile dependencies while using native accessibility, signing and storage. The wire protocol, rather than UI or Node code, is shared across platforms. The app needs independent native codec/reconnect tests, simulator and real-device verification, and its own signing/release instructions. The existing desktop/host dependency allow-list remains unchanged. TestFlight is planned; credentials and signing access must be verified before any upload.
## September 21 amendments after the T3 Code comparison

Over SSH the desktop pairs itself. The tunnel is already the user's authenticated session, so asking the user to copy a code from one window to another proves nothing more; the desktop asks the launch script (the fixed Node script it runs over SSH to find, start and stop the host) for a code and redeems it, the way T3 Code's desktop issues its own pairing credential over SSH. The code-entry flow remains for the phone, which has no SSH session. A host that the desktop started runs detached and outlives the SSH connection; a dropped connection is not a decision to stop work, and a host Sotto found already running is never stopped. The desktop reconnects a dropped connection with capped backoff, restoring the forward before the socket, which fetches the current shell again (and, since September 23, no events; see below). Errors that need the user (a prompt, a changed host key, a missing archive) stop the retries and say so. Pairing still grants no authority: a paired computer's permission answers count only after the host's policy record allows them.

## September 22 amendment: the host outlives the desktop

A host Sotto started keeps running when the desktop disconnects, quits or crashes, and stops only when the user presses Stop host or Forget while connected. This is where Sotto departs from T3 Code, whose tunnel finalizer stops a managed server on orderly close and app quit and whose reconnect path restarts it. Two things Sotto has and T3 does not decide it: a phone client that needs the host up with no desktop attached, and provider processes mid-turn that a restart would kill. The cost is a host nobody is watching, so Disconnect and Stop host are separate controls whose names say what a press does, and the Hosts page says the host keeps running. A host that cannot be reached can still be forgotten; the desktop then says its access on the host stays until revoked there.

A remote host reads its OpenRouter key from its own encrypted credential file, not from the desktop: a paired client may not send a credential, and the desktop's key never leaves it. OpenRouter-hosted reasoning on a remote host therefore needs a copy of the key placed on that machine. This is the one-key rule applied per machine rather than a second kind of key; the README says so beside the host commands. (Amended by [ADR-0026](0026-short-writing-runs-on-the-threads-own-provider.md): thread titles and branch names no longer use the key; the provider running each thread writes them, so a host needs no key for them.)

Because a host may now outlive a reboot of its machine, a host starting into a data folder whose `host-listener.lock` names a process that no longer exists reclaims the lock instead of refusing, and the launch script waits for a host whose lock holder is alive but not yet listening, so two clients connecting at once do not race to start two hosts. A lock whose holder still runs, or one that cannot be read, is refused without being touched. Reclaiming is atomic: starting hosts take turns to clear a stale lock through `host-listener.lock.reclaim`, and in its turn a host reads the lock again and removes it only if it is still the dead holder's lease, so however many hosts start together after a crash, only one owns the folder and a live lock is never moved. The removal also moves the lock to a name only that host uses and checks what it moved, putting back anything else; that guards the one case the turn does not, two hosts holding the turn together after a host stopped in the middle of its own, and a lock that cannot be put back then is logged and refused in words that say another host may have the folder. A turn left by a host that stopped is cleared the same careful way. The lease also records the machine's boot, so a process that took the old holder's pid after a reboot is not mistaken for it, and a process another account owns counts as running. The launch script's own check must follow that rule too, but it does not yet: it still counts a process it may not signal as gone, and it does not read the boot. Bringing it into line is the launcher half of #242. Until then, a pid another account took after a reboot makes the launch script start a host where it should have waited, and that host reclaims the folder correctly.

## September 22 amendment: what a paired client may send

"Checked against that session and the existing host policy" left open which commands a paired device may send at all. The answer is a closed list in `src/host/remoteCommands.ts`. Every command type and every field a paired client may carry is named there. A command or field added to the command schema is refused remotely until someone adds it on purpose, and a unit test fails until each one is decided either way. Host-local stays host-local: credentials, the voice commands and voice engine, reasoning checks, opening a folder on the host machine, and installing provider client updates. A paired device is not the user at that computer, so what it may do is decided command by command rather than inherited from the desktop's IPC surface. (Amended by [ADR-0037](0037-a-hosts-providers-are-connected-and-signed-in-from-this-computer.md): the list also names the four requests of a provider's sign-in on the host, which a headless host answers only to the client that started it.)

Some commands on the list are the user's answer to a question in another form, so they need the same `remote-answer` policy record, scoped `client:<clientId>`, that an answer needs under ADR-0004. They are: an answer; a runtime mode other than approval-required, on New thread or a thread's settings; a provider mode whose allowance is more than nothing; and reclaiming a worktree or restoring a branch with `withUncommittedChanges`, which discards work the user has not committed. A permission setting is judged by what it allows, not by where the provider lists it, because a provider's list is only the modes it happens to report. A setting that grants nothing is free, so a device without the policy can always put a thread back to asking. Without the policy the host refuses with `forbidden`, and the refusal says to check the device's permission policy or finish on the host.

`configure` carries only these coordinator settings: provider, enabled providers, enabled, default model, reasoning, reasoning model, reasoning effort, follow-up limit, orb colour and spoken replies. Spoken replies and the orb colour are preferences. The follow-up limit only bounds work the user already assigned, and a paired device may send those follow-ups itself. None of them answers a request. Keys, endpoints and the voice engine (speech provider, voices, wake word) stay on the host.

## September 23 amendment: the host reclaims its own worktrees

A headless host owns worktrees as the desktop's local host does, so it reclaims them the same way (ADR-0041, #245). The worktree cleanup is built by the shared agent runtime rather than by the desktop's entry, and both entries start it once they are up; closing the runtime drains a sweep in progress, letting it finish the worktree in hand and start no other, before the coordinator and the workspace close. A host follows the cleanup rules in its own data folder's settings, read at start and all off by default, and asks GitHub through the host machine's own `gh` sign-in only when the merged rule is on there. A paired client cannot change those rules yet; they are not on the remote command list.

## September 23 amendment: what a reconnect downloads, and the listener's budgets

Two findings from the third review of #181 (#241 and #243) changed how a connection spends the host's time.

Nothing on the desktop reads a host's event log. The router draws threads from the shell and from the details the window observes, and message events cannot rebuild a shell anyway. Yet the desktop client opened every connection from sequence 0 and paged through the whole log, 256 events at a time, and on a long log those requests passed the 100 messages a second that close a peer, which started the reconnect over from 0. The desktop client now asks for no events: its hello names a sequence past any the host can reach, and it follows no catch-up a push offers and reads no page after a command. Everything else a reconnect fetches is unchanged: the current shell, and the detail of each thread observed on that connection. Those are what the desktop shows. The alternative was to save the last sequence per saved host so a reconnect asked only for what is new. It was not chosen because it would store a cursor to protect a download nothing reads, and would still download each host's whole log once. A client that does read events, the phone, keeps its cursor and resumes from it as above. The listener paces event pages on their own budget, 100 a second, where a page past the budget waits for the next second instead of counting towards the cutoff. A client reading a long log one page after another is doing what the protocol asks, and closing its socket would only have it start again.

The HTTP listener used to count every request against one budget of 120 a minute, so a loop on the unauthenticated health or pairing endpoint could stop every paired client from opening a session. It now counts per endpoint class. Health is not counted: refusing it costs the host as much as answering it, and the launch script polls it while a host starts. Failed pairing redemptions have 10 a minute per caller. The listener reserves an attempt before checking the code and refunds it only on success. A caller at its attempt limit must wait; another caller keeps its own budget. The listener binds only loopback, which is already the host account’s administration boundary. For Serve traffic it uses the single IP address in `X-Forwarded-For`: [Serve replaces that header with the connecting device address](https://github.com/tailscale/tailscale/blob/main/ipn/ipnlocal/serve.go). Direct loopback connections without that header share the local budget. This address scopes pacing only and grants no client identity or authority. Proxy configurations must preserve that replacement; an arbitrary externally exposed forwarding proxy is outside this listener’s supported transport. Successful redemptions do not spend the failure budget. Sessions and revocations have 120 a minute for each paired client, and the administrative path has 120, each counted only after its token checks out, so a loop on a bad token spends nobody's budget. Past a budget the host answers 429. A client says the host is busy, nothing was lost, and to try again in a moment. It is not a pairing failure: the desktop keeps its credential, does not pair again, and a reconnect keeps retrying. When the desktop is already pairing again because the host no longer knows it, a busy answer to that pairing is likewise not final, and the reconnect retries it.

## September 23 amendment: protocol v1 is frozen, and how versions meet

The wire protocol described in "Implementation of remote clients" is version 1, and it is frozen from the pull request for #238 and #239, before the iPhone client (#225) builds against it. [The host protocol](../host-protocol.md) lists every message. Two things went in first, because neither can be added to a frozen protocol without breaking a client that exists.

Detail over the socket travels as deltas. The desktop's IPC already sends a viewed thread's change as `AgentThreadDetailDelta` rather than the whole thread, and #181 coalesced socket pushes and made an oversize one an explicit `too_large` error. The host now forwards the delta its detail stream publishes as a `detail-delta` push instead of reading the whole thread again for every change. A client applies one only to the revision it holds and otherwise reads the whole thread once, the rule the window already follows. The `too_large` error names the thread whether it replaced a detail or a delta, and a client does not keep asking for a thread it was told is too large.

Hosts and clients now say which Sotto they are. `/v1/health`, `host-listener.json` and the hello reply carry `sottoVersion` and `features`, the list of host features the host offers. A client reads health before it opens a session and uses only what is listed; it never learns what a host supports by sending a request and reading the refusal. The first feature is `detail-delta`, and a client asks for it by name in hello's `accepts`, so a client written before the freeze keeps receiving whole details from a newer host rather than a push it cannot read.

The version rule: `v` stays 1, and v1 changes only by adding an optional field, a feature in `features`, or a push form a client asks for in `accepts`. Anything else is version 2 with its own support window. `sottoVersion` alone is not a compatibility test, because a host outlives desktop updates on purpose and a restart interrupts its turns; a patch release that changes nothing on the wire must not force one. A host with no `features` predates the freeze. The desktop sends it nothing more and says which side to bring up to date: for an older host, to put this computer's version of the host in its installation folder, press Stop host (or stop it on that machine, for a host Sotto did not start) and connect again, because Connect starts whatever is installed; for a newer host, to update Sotto on this computer. Stop host stays on the Hosts page for an older host Sotto started. Between two v1 builds of different Sotto versions the thread and command shapes can still differ, so a host of another version refusing a request as unreadable, or sending what the client cannot read, produces the same sentence rather than "This request is not supported" or a closed socket. To make that possible the host now answers an unreadable request from an authenticated session with `invalid_request` by its ID instead of closing the socket. Requests stay strict (`.strict()`), so an unknown field is still refused rather than ignored; only feature names are read leniently, so an unknown one is skipped.

The issue asked for "a capabilities list". The hello reply already had `capabilities`, which is what this client may do on this host (`mayAnswer`), and the shell's `capabilities` are what a provider can do. A third meaning under the same word is what `CONTEXT.md` exists to prevent, and changing hello's `capabilities` would have broken every desktop already released, so the list is named `features` and the glossary has **Host feature**.

## September 23 amendment: one-shot SSH commands, askpass, and who started a host

The launch script no longer lives as long as the connection. Each control operation (find or start the host, read a pairing code, revoke a client, stop the host) is one `ssh` command that pipes the launch script to Node on stdin, passes its configuration as one quoted JSON argument, reads one JSON result line from stdout and exits. The `-N -L` port forward is the only long-lived ssh, and its exit is what a dropped connection is. This is T3 Code's shape (#236, #205). It removes the terminal the old session needed, and with it the request and reply markers, the echo a pseudo-terminal adds, the question of ConPTY reflowing long lines, and node-pty from the SSH path; node-pty stays for terminals alone (ADR-0018). The script's source never appears in the remote process list.

Every ssh Sotto starts passes `ControlMaster=no`, `ControlPath=none` and `ControlPersist=no`, so a user's connection sharing cannot detach the process Sotto watches from the connection it depends on. They also pass `RemoteCommand=none` and `RequestTTY=no`, since a configured remote command (`RemoteCommand tmux new -A`) makes ssh refuse any command given on its command line. The target is first read with `ssh -G`, so aliases, users, ports and identity files come from the user's own SSH configuration. On Windows Sotto runs Windows' own OpenSSH from `System32\OpenSSH`, not whichever ssh is first on the path.

Prompts reach the user through `SSH_ASKPASS` with `SSH_ASKPASS_REQUIRE=force`, which needs OpenSSH 8.4 or later; the Windows 11 development machine has 9.5p2. Connect reads `ssh -V` once for each ssh executable and stops with `ssh-too-old` when it reports an older version, since an older ssh would sign in with no way to ask; a version `ssh -V` does not print is let through. The askpass helper Sotto writes to a private temporary folder is a small Node script run with `ELECTRON_RUN_AS_NODE` through a shell script on macOS and Linux. On Windows it is a small executable, compiled in that folder with the Windows .NET Framework 4 compiler and started directly by OpenSSH. The source and executable are removed when the broker closes. This uses the framework supplied with Windows 10 and 11; it adds no bundled binary or npm runtime dependency. The helper carries OpenSSH's question to the desktop over a listener bound to 127.0.0.1, with a random token only its own ssh process holds, and prints the answer back to ssh. Neither end logs the question or the answer. The Windows executable receives the complete question, including line breaks, as an argument. Windows ssh still runs at `LogLevel=DEBUG1`, and the desktop can restore a missing key fingerprint from that same process's `Server host key` line before asking. An answer is kept in memory for the life of the connection and given again when another ssh process of the same connection asks the same question, so a password is typed once per connect however many commands the connection runs; a process that asks again after being answered was refused, and the user is asked instead. A reconnect is a new connect and asks again. OpenSSH also runs the helper for a notice that asks nothing (`SSH_ASKPASS_PROMPT=none`, such as "Confirm user presence for key ..." while it waits for a security key to be touched); Sotto answers a notice at once with nothing and shows no field for it, so nothing typed there can be kept and given to ssh as a password. ssh kills its helper when it stops waiting, so a question whose helper goes away before it is answered is taken off the Hosts page at once, not when the whole ssh process ends, which for the port forward is the end of the connection.

Before the launch script runs, a short POSIX shell finds Node: the plain path, then the account's login shell, then where nvm, fnm, mise, asdf, Volta and Homebrew keep it. It uses the first Node that satisfies the range in the installed archive's `runtime-manifest.json` (the desktop's own range for an archive without one), and otherwise reports `node-missing`, `node-too-old` or `node-too-new` with the version it found. A remote exit of 127 is reported as Node missing, never as SSH refusing.

Failures carry a typed code (`SshFailure`) as well as a plain message, and the desktop decides whether to retry on the code alone, so rewording a message changes no decision. An OpenSSH older than 8.4 on this computer, a refused sign-in, a changed or untrusted host key, an unanswered prompt, a missing identity file, a missing or unsuitable Node, a missing installation and an unreadable connection record stop the retries and say what to do; everything else is retried after 3, 4 and 8 seconds and then every 16 seconds (T3 Code's supervisor backoff) until the user presses Disconnect. This replaces matching words in the English message.

A host the launch script starts is told so in its environment, and records `startedBy: "launch-script"` in its own listener descriptor once it holds the data folder's lock. That is what "started by Sotto" means from now on. Only the lock holder writes the descriptor, so two launches racing to start a host cannot take the mark from each other or from the host that won, and a host Sotto started stays stoppable across every reconnect (#242). The launch script no longer writes `host-launcher.json`; it still honours one that names the live host, so a host an earlier version started can be stopped, and removes it when it stops that host. The launch script counts a process another account owns as running, as the host's own lock does.

## September 23 amendment: Add host connects first, and saved hosts reconnect at launch

Until now a saved host was a connection Sotto forgot at every launch: the user saved it, pressed Connect, and pressed it again after each restart. From #206 (the owner's pick of variant A, recorded in `docs/plans/forge-clients-134.md`), it works the way T3 Code's saved environments do.

Add host connects before it saves. The dialog sends one command; main runs the same connect a saved host runs (SSH, find or start the host, self-pairing over the tunnel) and saves the host only when the host answers and the pairing succeeds. Until then the attempt is not a saved host: it has no row, its SSH questions are asked in the dialog, and on any failure, a Cancel or a quit, nothing is written, the pairing credential is removed and a pairing the host already recorded is revoked while the connection is still open. A quit waits for that. A pairing that completes only after the connection closed is kept nowhere on the desktop and stays revocable on the host. The one exception is a host that answers with another Sotto version: it is the right host, so it is saved, and its row says which side to update and offers Stop host as before. A second saved route to a host already saved, by target or by host ID, is refused. The username and port the dialog takes travel the routes ssh already had, `user@target` and `-p`; everything else still comes from the user's SSH configuration.

Each saved host has a switch, stored as `enabled` in the saved-hosts file and written only when it is off, so a file from before the switch reads every host as on. The owner decided on September 23 that hosts already saved start switched on. A host that is on connects when Sotto starts, in the background, and is treated from its first attempt the way a dropped connection is: Reconnecting… on its row, the same 3, 4, 8 and 16 second backoff, and a stop, with the sentence that says why, at a failure only the user can fix. Switching a host off disconnects it and cancels any retry and nothing more: its row, its pairing and a host Sotto started all stay, so turns running there finish (the September 22 amendment still holds). Switching it on connects now and at every launch, and is how a host that needs attention is tried again once its cause is fixed. Because a host that is on now connects with nobody on the Hosts page, an SSH question from a saved host (a password, a key passphrase, a new host key) is asked over whichever page is open, not only on the Hosts page; otherwise a launch reconnect that needs an answer would wait unseen until SSH gave up. It waits while a Hosts dialog is open, and its cancel, Switch it off, switches the host off. Stop host now also switches the host off, since a switched-on host would start again at the next launch and undo the stop. Disconnect as a separate control is gone: the switch is the only way to stop connecting, and its name says what a press does.

The suggestions in Add host come from reading `~/.ssh/config`, following `Include`, and `~/.ssh/known_hosts` on this computer, the way T3 Code's `discoverSshHosts` does. Main reads them when the dialog asks, hands the window only the names, and logs nothing; no host is contacted to make them.

## September 26 amendment: staged images

A draft's images no longer travel inside drafts, commands and the shell ([ADR-0031](0031-images-are-staged-once-and-carried-by-handle.md)). They are staged once, on the host that runs the thread, through the new host feature `attachment-staging`: `stage-attachment` sends an image's bytes and answers with its handle, and `attachment-content` hands them back by digest for a chip. Drafts, follow-ups and commands carry the handle. The envelope stays version 1; the draft's attachment shape changes inside it, which a host and a client of different Sotto versions already meet as the version sentence, and a desktop sends no image to a host that does not list the feature.

## September 26 amendment: a paired computer lists the host's folders

Add project used to open Windows' own folder dialog, which can only show this computer's disks, and it refused outright while a remote host was selected: a project on Forge had to be added on Forge. The owner asked to choose the computer first and then browse that computer's folders from any Sotto, and picked variant A of the `prototype/host-folder-browser` prototype on September 26, 2026 (`docs/plans/host-folder-browser.md`).

A host now answers a new request, `host-folders`, behind the host feature of the same name: the subfolders of one folder, by name and full path, with whether each holds a Git repository. It is a read, like `git-refs`, not a command, so it is not on the remote command list, and every paired client may send it. It lists folders only. No file is listed and nothing inside a file is read, and names starting with a dot are left out, as are Windows' own `$` folders and `System Volume Information`. Any folder the host's account can read may be listed, from its home folder up to the top of the machine (the drives, on Windows), because a project can live anywhere the account can reach, and `create-project` already lets a paired client name any path. The host refuses a Windows network share or device path (`\\server\share`, `\\?\`) as unreadable, so a paired device cannot name another machine for the host to connect to and hand it the account's sign-in. A link or a mapped drive that is already on the host is followed the way the host's account would follow it; a paired client cannot make one, since nothing here writes. Paths travel in the host's own format and the host lists and splits them, so a Windows desktop browses a Linux host without translating. The one join the window makes is a new folder's name onto the folder listed, with the separator the host names, and it checks that name by the host's own rules: Windows refuses more characters and ignores case, Linux and macOS refuse only `/`. The host checks a project's name the same way when it adds the project. A listing carries at most 1000 folders and says when it was cut short. Folder names and paths are never logged, on either side.

Nothing new writes to the host. New folder in the browser is only a name until Use this folder, when the existing `create-project` makes the folder as it adds the project, so a cancelled dialog leaves nothing behind. This computer's folders are listed the same way, and the browser also offers its own system folder dialog there (File Explorer, or Finder on a Mac), which cannot see a remote host's disks and so is not offered for one. The listing grants nothing: choosing a folder is the user's own press, and a project added this way is added the way any other is.

## September 27 amendment: Add host says which step it is on, and waits for a Tailscale approval

Adding forge from the Windows laptop failed with SSH's catch-all sentence (#429). Nothing was wrong with SSH: forge's tailnet policy puts Tailscale SSH in `check` mode, so Tailscale held the connection and printed its approval request on ssh's stderr, which Sotto never showed; Tailscale answers no keepalive while it holds a connection, so `ServerAliveInterval=15` and `ServerAliveCountMax=2` ended it after 30 seconds with "Connection to 100.106.126.4 port 22 timed out", which the classification did not read. The owner picked the design on September 27 through `prototype/host-setup-checklist` (round 1, variant A: the checklist takes over the dialog).

The launcher now reports which step a connect is on: reach, the Tailscale approval, sign-in, the host installation, the host's start; the desktop adds pairing. Signing in is seen from the launch command's first output, which the Node probe now makes a `signed-in` line, so the step moves before a slow probe has found Node. Reaching the host is seen from SSH asking a question, from its own `Connection established` or `Server host key` lines where it prints them (Windows, at DEBUG1), or from signing in. Steps only move forward within a connect. Each failure code belongs to a step (a timeout or the catch-all stays on the step the connect had reached), and main hands the window the step, the sentence and, where there is exactly one, the command that fixes it; Sotto never runs that command.

ssh off Windows now runs at `LogLevel=INFO` rather than `ERROR`, because INFO is the lowest level at which OpenSSH prints a server's banner, and Tailscale's request is a banner. When the launcher reads Tailscale's check banner it reports the approval, with the page's URL when it is an `https://login.tailscale.com/` page, and gives the connect five minutes from then instead of the sign-in budget. The keepalive stays for the live connection: the port forward keeps 15 x 2 seconds, while the one-shot commands, which may be the one Tailscale holds, allow 15 x 21, a little over the approval budget, so Sotto's own timer ends an unanswered wait first with `tailscale-unapproved`, a failure only the user can fix. We chose a longer budget during sign-in over reconnecting once approval is seen, because an approval is tied to the held connection's check and a second connection could ask again. The cost is that a one-shot command whose network dies while it signs in is ended by Sotto's own budget rather than after 30 seconds.

Only the commands Sotto sends while it connects wait out a hold. The port forward starts moments after the launch signed in, inside the check period that approval began, so Tailscale is not expected to hold it. If it does (a rule whose `checkPeriod` is `always`, or one that ran out in between), the checklist shows the approval on the Tailscale step with the 30 seconds the forward's keepalive gives it, and a forward that closes unapproved says so rather than claiming five minutes. A forward the host answered through counts as signed in, so its dropping later reads as a dropped connection. A request sent once the host is connected (a pairing code, Forget, Stop host) keeps the live keepalive as well: nothing shows an approval then, so a request Tailscale holds ends after 30 seconds and says to switch the host off and on, which asks for the approval while Sotto connects, instead of waiting two minutes unseen. `Connection to <host> port <n> timed out` now reads as a timeout.

The approval page is opened only on the user's press and only by main: the window sends `open-approval` with the host's ID, and main opens the URL it holds, checked again, in the default browser. The URL reaches the window's state and the browser and never a log or the saved-hosts file. A saved host reconnecting on its own shows the same wait and button on its row. It is not yet asked over whichever page is open, the way a saved host's SSH question is.

## September 28 amendment: the phone reads snapshots too

The statement above that the phone consumes events was inaccurate: its lists and conversations use only the shell and observed thread detail. Its hello nevertheless started at sequence zero, downloading retained events and decoding their bodies without using them. The phone now makes the same snapshot-only hello as desktop. Saving an event cursor would preserve a download it does not need; making events authoritative would add a second state model for no displayed behavior.

The phone also accepts the existing v1 `detail-delta` extension. A full observed detail starts the conversation; subsequent updates carry changed messages and activities. A missing base or append target causes one full detail read, and stale revisions and prior connections cannot replace the selected thread. Older hosts may continue sending full details. Frame decoding runs outside the UI actor, in receive order. This changes no protocol version, host, credential, permission authority or delivery retry policy. A failure to read a thread is reported on that thread without disconnecting an otherwise online computer.

## September 30 amendment: retired account fields in v1

Sotto no longer has membership. Protocol v1 still sends `membership` as `{ status: 'beta', label: '', expiresAt: null }` and `configuration.membershipEndpoint` as an empty string because older desktops require both fields. Receivers accept shells with or without these fields and discard them before domain validation. They grant no authority and contact no service. These wire fields can be dropped only in a later protocol version that no longer supports v1 desktops; a Sotto release alone does not retire them.

## September 30 amendment: live answer authority

The optional v1 shell field `clientCapabilities.mayAnswer` reports the policy for the authenticated client receiving that shell. A Can answer change publishes it immediately, on the desktop phone listener and the headless host. The iPhone refreshes its controls only from a newer shell; an older host without the field keeps hello behavior. This grants no authority: dispatch still checks the host policy for the authenticated client, and no answer is sent automatically.

## September 30 amendment: an answer receipt records its own outcome

A completed transport receipt did not establish answer delivery: the coordinator catches a provider failure into its published shared error and still resolves the command. Inspecting that shared error is also unsafe when another thread fails at the same time.

For a socket answer, the coordinator returns the command-local failure as the response's error, separately from the published shell. The socket uses that outcome to add optional `answerDelivered` evidence to the existing v1 receipt. Only a completed receipt with no error and `answerDelivered: true` confirms the phone's answer. Refusal or uncertainty records false with a generic error. The command still answers with the existing shell, and neither a receipt nor its replay sends another answer.

Older hosts omit the field. The iPhone keeps their still-waiting answers unconfirmed and clears a vanished request with neutral copy, never claiming the phone's answer arrived. This adds evidence rather than authority: the user's explicit answer and the host's policy remain the only grants. No additional host, network request or permission is introduced.

## October 1 amendment: draft commands follow client selection

Remote navigation belongs to each client and never selects the coordinator’s own thread. The listener passes that client’s selected Sotto thread ID to the host service for compose, send, cancel-draft, pause-draft and cancel-request. Drafts on other threads stay intact. Each peer projects its active remote edits into the existing composer fields, so successive edits and Send remain available without resuming a paused draft or exposing another thread’s active draft. An ordinary draft retains its null question binding when a question arrives. The v1 allow-list retains these commands; question drafts and sends still require remote-answer authority (#489). This replaces the September 30 narrowing, which broke the managed composer and contradicted v1’s additive compatibility rule.

## September 30 amendment: connection liveness and phone recovery

Clients initiate keep-alive pings every 25 seconds; the listener only answers. The phone allows ten seconds for a pong, any received message, or growth in the WebSocket task’s received-byte count. Partial large frames count as progress. The listener counts all incoming bytes, including pings, as liveness and closes a peer only after 75 seconds without traffic and with no buffered output. Node desktop clients also initiate pings, clearing a pending pong on any incoming bytes and deferring missed-pong closure while output remains buffered. A full listener answers an authenticated upgrade with 503, leaving pairing intact. An older host’s upgrade 401 likewise does not discard pairing: `/v1/session` detects revocation.

While active, the iPhone retries a dropped connection with exponential waits starting at one second and capped at thirty seconds, with a 0.8–1.2 random multiplier before the cap. A successful liveness round resets the wait; hello alone does not. Backgrounding or removing a computer cancels retries; activation connects again. Invalid identity, incompatible protocol and refused pairing stop retries for the user to resolve. Reconnecting refreshes observed details and reconciles pending commands through receipts; it never resends them (#524). Pairing pacing retains at most 1,024 source buckets, evicts the oldest on insertion at capacity, and expires buckets after a minute.

## September 30 amendment: device names in attribution

Pairing records a plain, bounded device name: Unicode compatibility normalisation, control and formatting characters removed, and whitespace collapsed. Existing saved names receive the same normalisation when read for display or attribution. An answer records the permanent paired client ID beside that name, as it already does, so the chosen name is a label rather than an identity (#582).

## October 1 amendment: older idle clients

Client-owned pings require `client-liveness` in hello's `accepts`, an additive v1 feature. Only opted-in peers get the 75-second idle close, deferred while output is buffered. Older clients keep host pings every 25 seconds; a missed pong closes them only when no other traffic arrived and no output remains buffered. Their WebSocket implementations can answer host pings while the app is idle. This replaces the earlier listener-only-answer rule for clients without the opt-in.

## October 1 amendment: phone reads on slow links

The phone no longer relies on the WebSocket task's byte counter. Each ten-second liveness round checks completed messages and pong replies, and closes only after two consecutive silent rounds. A request still awaiting its reply within its own deadline prevents silence from accumulating. Detail and observe reads have 120-second deadlines; other requests retain 30 seconds. A connection with no requests closes at the second round, about 60 seconds after opening; an unanswered detail expires at 120 seconds and cannot protect a dead connection indefinitely. Only an actual message or pong resets reconnect backoff. This replaces the earlier byte-progress rule.

## October 1 clarification: a question draft keeps its answer outcome

A socket `send` of a question-bound draft executes an answer inside the coordinator. It returns the same command-local failure as an explicit answer, even though the shared desktop shell remains clear of answer uncertainty. The listener carries that result in the sending client's reply and receipt, retains its active editor on uncertainty, and replays an unsuccessful receipt without sending another answer. The desktop socket adapter keeps that command-local outcome through state refreshes, so a later shell cannot replace it. This extends the existing outcome evidence to the draft path; it changes no permission rule or v1 command.

## October 2 amendment: late pongs and drained tunnel writes

Both host pings for older clients and Node desktop-client pings require two consecutive silent rounds. Any received bytes reset silence. Frames written since the previous ping or output still buffered prevent a round from being silent, because loopback tunnels can drain Node's buffer before the peer receives the frames. The heartbeat's own ping never renews progress. A completely silent peer closes at 75 seconds; after final incoming traffic or a drained application write, it closes within 75 seconds. Opted-in listener peers count outgoing frames too and close within 100 seconds of the last progress once output drains. Continuing traffic and buffered output defer those bounds.

The phone also accepts growth in URLSession's received-byte counter as progress, sampled across rounds. This supplements rather than replaces pending-read protection: partial-frame counter updates are not guaranteed. An unrequested slow push without counter updates remains a real-device verification limitation. This amends the October 1 silence rules without changing protocol fields, permission authority or reconnect replay behavior.

## October 2 clarification: retained-event cursors

A hello without `afterSeq` asks for no retained events, like the desktop and phone snapshot-only hello. An explicit cursor still pages history. After a hello or event page is delivered, the listener uses that page's last sequence for subsequent shell pushes, so a page already sent is not repeated. Reading older pages never moves the cursor backward, except when a snapshot-only peer explicitly reads an unfiltered event page: its snapshot-only cursor becomes that page's last sequence so later shells can continue the history. A thread-filtered page leaves the general shell cursor alone. Shell pushes wait until the hello reply has been delivered; a v1 client that never sends hello receives no shell pushes.

## October 3 amendment: activity summaries for a phone

A thread's detail carried every activity record whole to every socket client. On the owner's bug-audit thread that was 842 records and 3.53 MB, 2.61 MB of it command output, while the iPhone's activity list reads only each record's kind, status, title, command, exit code, start, duration and changed paths (#701). The listener now offers `activity-summaries`, an add-only v1 host feature on the headless host and the desktop's phone listener alike. A client that accepts it in hello is sent each activity record as its activity summary in every `detail` push, `detail-delta` push and `detail` answer; the fields kept are listed in `docs/host-protocol.md`. A summary keeps the record's ID, turn and sequence and still parses as an activity record, so revisions and delta arithmetic are unchanged and a client applies a delta of summaries as it would any other. The listener makes a thread's summaries once per update and sends the same ones to every client that accepts them.

Clients that do not accept the feature, the desktop's own host client among them, are sent every record whole, as before. The iPhone accepts it from its next build; an iPhone build from before it does not ask, and keeps receiving whole records. A client that later needs a record's output asks for it some other way; no such request exists yet, and adding one is its own change. This changes no permission rule, host, credential or command.
