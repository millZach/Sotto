# A terminal's agent reports state through hooks for that run

## Status

Decided October 9, 2026, for [#882](https://github.com/millZach/Sotto/issues/882). The desktop states are implemented by [#883](https://github.com/millZach/Sotto/issues/883); the iPhone extension is implemented by #884, with native compilation and simulator verification remaining macOS checks. ADR-0066 was free on `origin/main` and in open pull request diffs on October 9; #880 already uses ADR-0065. Check the number again before merge, as [domain.md](../agents/domain.md) requires.

## Context

Terminal mode starts the provider CLI itself, but today its sidebar knows only whether output arrived in the last four seconds. A quiet agent can be working, and an animated permission prompt can look busy. [The research note](../research/2026-10-09-herdr-terminals.md) records the alternatives and the owner's choices. The [prototype](../prototypes/terminal-agent-state-prototype.html?variant=B) records Variant B: Needs you across projects first, Working next, the rest by project, then Closed; a thin header edge on the pane that needs the user; and terminals beside threads on the phone. Both files are preserved byte for byte. Their simulated keystroke answers, Codex approval cards and persistent choices are illustrations, not a transport or an authority decision.

Inspection also confirmed that the preserved prototype's finish simulation checks only its focused pane: a visible unfocused pane incorrectly earns Just finished. The owner's later on-screen rule in the research note and #882, recorded below, governs implementation. This historical prototype is evidence of the look, not an executable state specification.

## Decision

### States belong to main and to one terminal run

These states apply to a provider CLI launched by Terminal mode. They do not change a thread, the Tools terminal or the Terminal drawer. Plain shells keep Running for output in the last four seconds and Idle otherwise, with Starting and Exited for their process lifecycle. Closed is the existing shelf for a terminal the user closed, not a seventh agent state.

| State | Evidence and transition |
| --- | --- |
| Starting | Main is launching the CLI. A ready hook or a recognised live input prompt changes it to Idle; a submitted turn changes it to Working. A failed launch ends in Exited with an error. |
| Working | A turn started, a tool is running or a bundled screen rule recognises current work. Silence alone cannot end known work. |
| Idle | The CLI is ready for input, with no pending request, work or unread completion. A ready input prompt after an interruption or failure can return here but earns no completion. |
| Needs you | A current hook reports an approval, or a strict rule recognises a live approval or question. This outranks Working and a completion signal. Being quiet, saying something about permission, or printing a question mark is insufficient. |
| Just finished | A successful completed turn reached Idle while no client showed the terminal. It wears the threads' dot and bold title. Viewing it clears the mark for every client; new work or a request clears it too. |
| Exited | The launched CLI's process ended, including a failed launch or a user Stop. Exit outranks delayed events and earns no completion. Its output remains readable until Close or Reopen, as today. |

Main owns the unread mark and merges the clients' current visible terminals. A desktop pane that is on screen counts, focused or not, including an unfocused pane in a split. A minimised, hidden or tray window does not count. A foreground phone's open terminal detail counts; a sidebar row, list card, notification or selection alone does not. Disconnecting or backgrounding a client withdraws its visible set. Anything shown when it finishes earns nothing, and leaving afterwards does not mark it later. A mark is held until viewing, new work, a request or exit, without a timer. It lives in memory for this run; restart creates no inferred completion.

This follows [ADR-0046](0046-the-host-keeps-a-finished-thread-unread-until-a-client-shows-it.md)'s meaning of unread and its no-retroactive-mark rule. It deliberately uses #882's **on screen, focused or not** rule for terminals. ADR-0046's local desktop thread focus requirement and durable thread marks remain unchanged.

### Claude Code uses run-only settings and a blocking permission hook

Sotto chooses a UUID and launches `claude --session-id <uuid> --settings <run-settings-file>` in the chosen working copy, with the user's chosen model and permission mode. The file contains only Sotto's hooks for that run, in Sotto's private temporary area, not in the working copy. Sotto never edits user, project or local Claude settings. Existing native settings and hooks still apply; a provider's own allow rule is not a Sotto grant. Reopen starts a new run with a new secret and UUID; any later resume feature must bind its existing provider session explicitly.

`SessionStart` binds the run but stays Starting until the live input prompt confirms readiness; it fires before the CLI is necessarily ready. The helper maps `UserPromptSubmit`, `PreToolUse` and `PostToolUse` to Working. `PermissionRequest` creates Needs you and holds its connection open for an answer to that particular invocation. `Stop` is completion evidence only when no request or background task remains and the live CLI is ready; `stop_hook_active` or a continuing Stop hook must not mark a turn finished early. `StopFailure`, a user interrupt or `SessionEnd` clears pending requests and work without marking completion. Main's actual PTY exit is final even if no end hook arrives.

The helper reports a recognised continuing Stop, or a Stop with remaining background tasks or session crons, as Working with the continuing phase below. That work remains known even while the CLI redraws its input prompt, until a successful Stop and ready screen settle it, or cancellation or exit ends it. Unknown Stop shapes report nothing. After ordinary work, ready output and Stop can arrive in either order: main remembers a pane shown between them so the delayed callback cannot mark already-viewed work unread. A ready prompt redrawn during known continuation is still Working, not a completion observation; viewing that ongoing work does not suppress a later successful finish while hidden. If the successful Stop arrives first, showing the pane before its ready output counts as viewing the completion. A new submission or explicit continuation starts a fresh observation; a late tool callback alone does not erase it.

`Notification(permission_prompt)` corroborates a request; it is delayed and is not a second approval. A notification without a live blocking permission connection, including a sandbox network prompt, can set Needs you only while its native prompt is still visible and cannot offer Sotto answer buttons. `idle_prompt` corroborates Idle, never invents a completed turn and never clears Just finished. Supported elicitation or question notifications need the same live-prompt check; unknown notification types change nothing. A question that the CLI renders is answered in the CLI: this spike proved permission decisions, not structured question answers. Allowing `AskUserQuestion` as a tool is not an answer to its question.

For a supported tool approval the helper keeps the native payload in its own memory, creates an opaque approval ID and sends only the state and IDs. Main does not receive the tool input. The helper recognises the tested permission shape and an unchanged-input tool decision; unknown forms, `AskUserQuestion` and permission-mode or plan changes stay in the native CLI without Sotto answer controls. A user's Yes or No for that run and approval ID returns through the same open connection. The helper writes `hookSpecificOutput: { hookEventName: "PermissionRequest", decision: { behavior: "allow" | "deny" } }` to its own stdout. It never supplies `updatedInput` or `updatedPermissions`, and stdout goes to Claude, not a log. This is the path proved by the spike; it needs no terminal keystrokes.

### Codex notify supplies completion and the provider session, not an answer channel

Launch Codex with a run-only `-c 'notify=[<helper-runner>,<helper>,<run-arguments>]'` override. It chooses its provider session ID. An authenticated `agent-turn-complete` payload supplies a candidate as `thread-id`, with `turn-id` identifying the turn. Main binds it only when the live CLI is ready and the run has reported one consistent candidate. Until then it is unknown; never read a global last-session record or choose a different terminal's ID. If the run reports different session IDs, clear the binding and keep it unknown: a companion completion cannot choose the parent's session. That run uses screen state and cannot supply an ID for a future resume. Sotto does not edit `~/.codex/config.toml` or project configuration.

The helper discards `cwd`, `input-messages`, `last-assistant-message`, `client` and every other unneeded field before connecting to main. Notify is one-way: its stdout is not an approval response. The installed CLI emitted no approval-specific notify event in the spike, even with a native approval menu on screen. Its `tui.notifications`/OSC/BEL facility is a separate terminal notification, not an authenticated request or callback. Do not turn it into an approval channel.

Codex therefore uses notify for completion and identity, and bundled screen rules for Starting, Working, Idle and Needs you. A completion signal is reconciled with the **current** screen before marking Idle or Just finished: the probe observed a completion callback before the approval menu was detected, so a callback alone cannot overrule a visible request. Codex approvals and questions say Needs you but are answered in the native desktop CLI. The phone can show the state and direct the user there; it offers no Yes or No for Codex. Codex also documents a separate native PermissionRequest hook that can report and answer approvals. Its run-only inline overrides did not deliver even SessionStart in this installed-client probe, and an external scratch profile was refused because --profile requires a plain name under CODEX_HOME. This ADR therefore admits the proved notify path only; the native hook needs a successful run-only injection and response proof before Sotto offers Codex answers. That proof must trust Sotto's helper without bypassing trust for other configured hooks. This is a compatibility restriction, not a claim that Codex has no approval hooks. The app-server thread adapter is not evidence for the interactive CLI.

### Screen rules read the live screen, conservatively

Grok Build and any provider without the needed hooks use versioned, per-provider rules shipped with the app. There is no rule download or new host. Rules read the active terminal buffer's bottom rows at its current size, after terminal control sequences have been applied, never raw output tails, saved scrollback or transcripts. The implementation must keep a screen in memory on the machine owning the PTY so a hidden pane still has current evidence; this ADR chooses that requirement without adding a runtime dependency.

Needs you requires a known prompt anchored in the current bottom rows, its expected choice/input controls and no current work indicator. A quoted example, old prompt in scrollback or a lone bell cannot match. Input or a redraw invalidates that match and requires a fresh read. A known work indicator means Working; a known input prompt means Idle. Only an observed Working-to-ready completion can earn Just finished, excluding cancellation, errors and requests. Unknown versions or unmatched output keep the last reliable state while its evidence remains valid; otherwise use output activity as conservative Working/Idle evidence, never Needs you or Just finished. Starting ends once the PTY is live under that fallback. Show that state detection is unavailable in the terminal detail rather than claim a request can be answered. Plain shells are not inspected for agent prompts.

### The hook channel is local, authenticated and disposable

Main opens one local TCP socket per run, bound to 127.0.0.1 on an ephemeral port, on all three platforms. This is the loopback path the spike proved, using Node builtins without another runtime dependency (ADR-0018). The helper uses the app's packaged Node-capable runner, not a separately installed Node. Each run gets a random secret, passed to its CLI environment, not command-line text, a settings file or a log. The endpoint and secret are not phone access and are never forwarded over the tailnet. Authentication, an 8 KiB frame limit, a schema allow-list and bounded connections prevent other local callers from using the channel without its secret. Another process running as the same user can potentially read that environment and is not isolated by the secret; neither a hook nor its reported state can grant authority. Named pipes or Unix-domain sockets were considered, but would add a transport to verify without improving the authority boundary.

An event contains a normalised state name and opaque terminal, run, event, provider-session, turn and request/approval IDs where applicable, plus the authentication secret. Working events may also carry one closed, normalised work phase: `submitted`, `tool-start`, `tool-end` or `continuing`. This implementation refinement distinguishes new or continued work from late tool callbacks without forwarding a native payload or relying on delivery order. Answers contain the same binding, an answer ID and the one-time allowed/denied state. No prompt text, command body, tool input/output, question choices, transcript path, working folder, arbitrary hook JSON or key enters this channel. The helper parses the CLI's raw input in memory and never opens its transcript. Main logs stable state/event names and opaque IDs only; it never logs the secret, endpoint or raw hook input, including on malformed input, authentication failure and timeout. The CLI's own history remains the CLI's; Sotto makes no copy of it.

Run identity prevents an old process from updating a reopened terminal. Event IDs deduplicate deliveries; turn IDs bind events to their turn. Independent hook processes need not arrive in order, so main reconciles concurrent notifications with the live request and screen rather than trusting receipt order. There is no heartbeat deadline that turns a quiet working agent idle. A missing helper, socket failure, unsupported shape or stale event withdraws answer controls and uses the conservative screen fallback. Exited stays final for that run.

A blocking Claude helper waits at most 110 seconds inside a 120-second CLI hook timeout, returning no decision if its connection fails or no user answers. Its request then stops being answerable in Sotto; the native prompt remains the fallback. Failure never prints an allow or a denial pretending to be the user's choice. Once the hook connection closes, main expires its approval ID. A late, duplicated or competing answer cannot be redirected to another request or converted to a keystroke. Restart cancels all such connections, tokens and requests. Only acknowledgement that the still-live hook wrote its decision settles delivery to the hook; it does not claim that the tool ran or that native policy accepted an allow. An uncertain answer is reconciled, never replayed automatically.

### Authority stays with the user, including on the phone

Under [ADR-0004](0004-authority-in-policy-records.md), every answer sent by Sotto is the user's explicit press for one live approval. Hooks, screen matches, memories, supervision, imports and provider confirmations approve nothing. No Sotto policy is written by a one-time answer. Desktop and phone race for the same request: main accepts at most one answer, atomically, and checks its binding again at dispatch.

On a paired phone the dispatch also checks its current, active **Can answer** (`remote-answer`) policy for this host and client, as [ADR-0033](0033-the-desktop-lets-paired-phones-reach-its-threads.md) requires. Pairing alone permits reading, not answering. Revocation, removal, expiry or disconnection before dispatch prevents delivery. A phone cannot send terminal input, execute commands, launch or resume a terminal, widen a permission mode, or answer a screen-only request.

Sotto offers **Yes** and **No**, for this request only. It does not offer **Yes, and do not ask again** on either device, including under More choices. Persistent native choices stay in the native desktop CLI under the user's provider settings; they establish no Sotto policy or remote grant. The prototype's persistent choices are not adopted. Adding them to Sotto later requires an explicit policy decision defining scope, expiry, revocation and the interaction with always-confirm boundaries, rather than echoing Claude's permission suggestions into settings.

The iPhone work may add a terminal **Host feature** to the existing paired host connection: terminal state/IDs, visibility observations and exact-approval answers with existing command receipts. The host advertises it through `features`; a client uses it only when advertised and opts in to new pushes through hello's `accepts`. Feature support is separate from the client's **Can answer** authority, which dispatch still checks for every answer. Older v1 clients continue with threads only. The October 9 amendment below extends ADR-0033's thread-only surface, not permission for a general terminal on a phone or for terminals on remote hosts. A phone approval card also needs a separate, request-bound **read-only preview of the live bottom of the screen**, taken by the PTY owner, held only in memory and sent only to the paired client over its existing tailnet connection. That preview is user-visible content, never hook/state-channel metadata or a log. It is invalidated with the approval ID; without a current reviewable preview, Yes is unavailable. It grants no arbitrary screen-read or input command. The October 9 amendment defines that additive Host feature; the README and guide describe its approval-only phone surface. Native verification remains required before shipping it. There is no new contacted host or rule server.

## October 9 amendment: paired phones see terminals

Issue #884 implements the iPhone extension on the desktop's existing phone listener. The additive v1 Host feature is `terminals`. Only a listener given the desktop's Terminal mode workspace advertises it; headless hosts do not. Hello's `accepts: ["terminals"]` opts a phone into optional `shell.terminals` rows and their state updates. Older phones receive the original thread-only shell; a new phone uses no terminal operations on an older host.

Rows contain the terminal's ID, title, project, provider, state, detection availability and opening time, plus the exact run/request/approval binding when one supported blocking Claude request is live. No screen text, launch arguments, folder or hook secret is in a row. Closed terminals leave the phone list. Plain shells retain output-based Running and Idle and never earn a completion mark.

`terminal-approval` reads at most eight current bottom screen rows, each at most 512 characters, only for that live request. Main requires a reliable, fresh screen that recognizes a request; otherwise it offers no preview or answer controls. The returned fingerprint binds the exact terminal, run, request, approval and reviewed lines. `answer-terminal` carries that binding, the fingerprint and a one-time `allow` or `deny`. The listener requires that this connection received the preview and that the current screen still agrees, rechecks its session, pairing, connection and Can answer at hook dispatch, and waits for the hook's matching acknowledgement. Existing client-scoped command receipts distinguish pending, acknowledged and unconfirmed delivery; an uncertain answer is never replayed automatically. The receipt keeps a digest and opaque binding, not the reviewed words. Neither device offers a persistent grant through More choices.

`observe-terminals` replaces one connection's visible terminal IDs. Only a foreground terminal detail counts; list cards do not. Backgrounding, disconnecting and closing the listener withdraw that connection. Main merges it with actual desktop panes, so Just finished clears everywhere and cannot appear retroactively. The approved variant B list mixes terminals into Needs you, Working and Recent in the existing Glow room. Tapping a terminal opens a small status view. Codex, Grok and screen-only requests direct the user to the native desktop CLI without answer controls.

Android remains a follow-up when its JDK/build environment is available. Native iPhone compilation and simulator verification require the macOS check; Windows evidence alone does not establish them.

## Evidence

On Windows 11 on October 9, 2026, against installed Claude Code **2.1.295** and Codex **0.162.0**, the spike ran outside every repository in `%TEMP%/sotto-882-hook-spike`. Node's PTY drove the installed native executables and a loopback listener authenticated a per-run secret. The experimental listener recorded event names, IDs and key names only; CLI output stayed in memory. No spike code is included in this branch. SHA-256 checks before and after the runs found both `~/.claude/settings.json` and `~/.codex/config.toml` unchanged. No project settings were written. Fresh marker files were the only requested tool work.

- **Claude:** `claude <short-scratch-task> --session-id <uuid> --settings <scratch-settings.json> --setting-sources "" --strict-mcp-config --mcp-config '{"mcpServers":{}}' --model haiku --effort low --permission-mode manual --tools Write`. One print-mode control also used `-p --no-session-persistence --max-budget-usd 0.15`. The prompt preceded the variadic `--tools`; early probes with it after that flag submitted no turn and supplied no permission/completion evidence. The successful interactive run reported `SessionStart → UserPromptSubmit → PreToolUse → PermissionRequest → Notification(permission_prompt) → PostToolUse → Stop → Notification(idle_prompt) → SessionEnd`, always with the UUID passed at launch. The listener waited eight seconds, then returned the one-time `allow` hook response above; the marker was created and both successful runs exited 0. No approval keystroke was sent. Waiting for `idle_prompt` added about a minute of idle time, not another model turn.
- **Claude shapes:** common keys included `hook_event_name`, `session_id`, `cwd`, `transcript_path` and, on the interactive run, `scratchpad_dir`. Submission added `prompt`/`prompt_id`; permission added `tool_name`, `tool_input` and `permission_suggestions` but no `tool_use_id`; the tool input's key names were `content` and `file_path`. Notifications added `notification_type` and `message`. Stop added `stop_hook_active`, `last_assistant_message`, `background_tasks` and `session_crons`. These content-bearing fields were not recorded as values or forwarded as product metadata.
- **Codex:** `codex --no-daemon -m gpt-6-luna -c 'model_reasoning_effort="low"' -c 'notify=[<node>,<scratch-helper>,"codex"]' -c 'tui.notifications=false' -c 'mcp_servers={}' -c 'history.persistence="none"' -s read-only -a on-request --no-alt-screen <short-scratch-task>`. The no-tools completion control emitted `agent-turn-complete` and exited 0. Its keys were `type`, `thread-id`, `turn-id`, `cwd`, `input-messages`, `last-assistant-message` and `client`; the chosen session UUID arrived in `thread-id`, not from Sotto. A separate single-command approval probe showed the native approval menu for its fresh marker while that file did not exist. Notify emitted only `agent-turn-complete`, with the same shape, and no approval-specific event. A completion callback had already arrived before the menu was detected; the helper therefore cannot establish readiness or permission state on its own. The test sent the native No choice; the marker remained absent, but a clean denial acknowledgement and quit were not established. It terminated the CLI at the 65-second bound; ConPTY cleanup reported `AttachConsole failed`. This does not affect the recorded hook delivery, and is not a successful denial or shutdown claim. The observation establishes no approval callback through the tested notify path, not the absence of every present or future Codex integration.

An additional Codex control supplied run-only `-c features.hooks=true` and `-c 'hooks.<Event>=[{hooks=[{type="command",command=<scratch-helper-command>,timeout=<seconds>}]}]'` for SessionStart, UserPromptSubmit, PreToolUse, PermissionRequest, PostToolUse, Stop, SessionEnd and Interrupt, with `--dangerously-bypass-hook-trust` for the experiment. It emitted no native lifecycle hook to the listener. Notify delivered completion events with two different `thread-id` values during that one process run; the marker was eventually present, but there was no hook approval and no claim of a reliably denied native prompt. A later completion-only control with the original notify flags also reported two session IDs during one process run and reached the bounded termination rather than a verified clean exit. A separate `-p <absolute-scratch-profile-without-suffix>` attempt exited 2 before a model request: the CLI requires a plain profile name. The profile existed only in the scratch directory; no file was created under the user's Codex home. Those failed admission attempts explain the conservative identity and answer restrictions above; they do not establish that file-configured native hooks are unavailable.

Haiku and GPT-6 Luna were the low-cost choices for these installed clients; [Codex pricing](https://learn.chatgpt.com/docs/pricing) lists GPT-6 Luna below the older GPT-5.6 Luna. Inherited parent-agent session variables were removed for isolation; native sign-in remained in place. The test listener's automatic answer was confined to the expressly requested scratch permission experiment; production requires a user's press.

The [Claude hook reference](https://code.claude.com/docs/en/hooks#permissionrequest) documents the decision response, and [Codex advanced configuration](https://learn.chatgpt.com/docs/config-file/config-advanced#notifications) distinguishes external notify from TUI notifications. The [Codex hook reference](https://learn.chatgpt.com/docs/hooks#permissionrequest) documents native approval hooks separately from notify. The live events above, rather than documentation alone, establish the paths admitted here. Denial through a Claude hook, structured questions, background/continuing Stop hooks, stale-answer races, unavailable helpers and macOS/Linux execution were not live-tested here; the implementation lanes must exercise those paths before calling them supported.

## Consequences

The desktop lane implements the reducer, packaged helper and screen rules with recorded synthetic fixtures and privacy checks. It proves exact request binding, two-device races, expiry, revocation, cancellation, missing hooks, changed provider versions, live-screen matching and the unread visibility rule. The iPhone lane adds the bounded preview and checks the Host feature, Can answer policy and command receipts separately; a state label alone never enables an answer. Both preserve the approved look and the existing theme, keyboard and beta-gate requirements. Neither turns a terminal into a thread, auto-answers a request, saves terminal output or fetches detection rules. No product code or runtime dependency changes in this ADR lane.
