# Project-free personal chats have their own durable identity

Amended October 6, 2026: Zach chose to retire standalone Chats and keep project-bound Threads. The Chats page, personal voice and Generate prompt, its service and bridge, and provider personal-conversation paths are removed. With Keep local history on, existing `personal-chat/` files and personal records in `request-drafts.json` are preserved without being exposed as drafts. Sotto starts no personal provider connections and performs no migration into Threads. Provider-owned native history is untouched. The decisions below record the retired feature; its former connection behavior no longer describes the running app.

Clarified October 6, 2026 after review: retirement does not override Keep local history. While it is off, startup and Settings saves run local cleanup without connecting a provider. The retained `personal-chat/chats.json` loses messages, requests, activities, its generated title, submitted prompt text and skills, and submitted answer and request bodies; decisions keep only delivery recovery metadata. Unsent chat drafts and recovery identities remain, as before. Submitted or held personal forms in `request-drafts.json` are removed, including their question and answer text; unsent personal forms and every thread form remain. Abandoned `chats.json.tmp-*` copies from atomic writes are removed only after the primary can be read safely. An unreadable primary is never reset or replaced. A failed cleanup is reported and retried on the next Settings save or startup. Turning history back on cannot restore redacted content. This local cleanup never alters provider-owned native history.

Accepted September 13, 2026 for #68. A personal chat is a distinct conversation kind, not a project thread with an empty or invented project. It has its own Sotto-owned ID, provider binding, drafts, uncertain submission intents and cached native history. The existing project ThreadRegistry and public AgentThread project invariant remain unchanged. Using the project registry would either weaken project memory/authority boundaries or manufacture a project the user never selected.

The personal-chat service reuses CodexAppServerHost with a separate child process, alias directory and neutral app-data working directory. Its private conversation union permits a personal alias without projectId; public project snapshots filter it out. Only the dedicated personal snapshot and creation methods expose this kind. No native ID is transferred to the renderer. Normal native tools, skill discovery and provider-owned rollout persistence remain enabled; the constrained coordinator command parser is not involved.

New local chats capture the configured Codex model and effort. Unsupported coordinators report unavailable rather than silently choosing Codex. Creation/submission and answer intent are saved before their respective native writes. Draft revisions advance independently of network waits; accepting an older revision cannot erase newer text. Restart converts unfinished intents to uncertain and only reads the same owned native conversation. No uncertain operation is automatically replayed or rebound, including creation whose native ID was never received.

Relevant existing global preferences are retrieved through the existing explicit-memory query without project or thread scope, and are supplied as context, never grants. Initial context goes on thread/start because installed Codex 0.154 cannot resume an unmaterialized thread; subsequent turns refresh developer instructions through thread/resume. Native user text, client message IDs, command origins and assistant message IDs stay unchanged. Questions and approvals reuse the shared answer contract and require exact explicit user decisions; no personal-chat management or policy-writing path exists.

The history cache honors Keep local history: disabling it removes transcript, activity, generated title and submitted-answer/prompt copies from disk while preserving unsent drafts and recovery identities. Codex owns its separate native history and account configuration, as for project threads. Disconnect ends only the personal connection, declines pending requests and keeps recovery data; view navigation merely unsubscribes. Rendered presentation and the combined Phase 3 journey remain the integrator's responsibility.

Amended September 23, 2026: chats connect on their own. At launch the service connects every provider with a saved chat, plus the coordinator's provider so a new chat can send at once, without holding up start. When a connected provider drops without a Disconnect, or an automatic connect fails, Sotto tries again after 5 seconds, then 15, 45, 120 and 300. After the fifth failed try the error waits for Connect, because the personal hosts report only connected and an error, not the transport-versus-account distinction Threads retries on, so a lasting failure (no account, no installed client) must not retry forever. A connection that holds for a minute starts the waits again from the first; one that falls straight back, such as a client that exits as it starts, keeps counting. Disconnect ends every personal connection as before and holds auto-connect off for the session; Connect re-arms it and reaches every provider with a saved chat, and a restart re-arms it too. Reconnecting only reads native state through the same connect and accept path; no uncertain submission or answer is replayed.


Amended September 30, 2026 for Claude personal chats: retrieval changes wait for background work to finish before restarting the client. A committed deletion of a memory in the running context is a user action and forces the next send to restart, stopping background work. Deletion notifications include every purged member of a supersession chain, and only reach the personal service when memory is enabled. This refreshes the client's supplied context; it does not erase the provider's earlier conversation history.
