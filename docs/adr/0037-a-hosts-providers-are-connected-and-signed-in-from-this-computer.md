# A host's providers are connected and signed in from this computer

## Status

Accepted September 28, 2026, for issue #460, part of map #134. The design is layout B, Tiles, of `prototype/host-providers` (commits 5ab1f7b2 and 90361e37), picked by the owner on September 28. Builds on [ADR-0036](0036-a-host-connects-every-signed-in-provider-it-can-find.md), which has a host connect every provider signed in on its machine, and adds to the remote allow-list of [ADR-0025](0025-headless-host-and-client-identity.md). The answers to the issue's four open questions below were proposed by the orchestrating session for the owner to confirm; they are listed as such in the pull request.

## Context

Nothing on this computer could see or fix a remote host's providers. Settings → Providers acts only on this computer's. When forge had no connected provider, the only way out was SSH and hand-editing `~/.sotto/agents.json`. The desktop already receives each host's provider statuses in `clientHosts[].providers`, and a paired client may already send a host `connect`, `disconnect` and `refresh` for one provider. What was missing was a place that shows them, a way to send those three to that host and no other, and a way to sign a provider in on a machine the user is not sitting at.

A provider's status said only `connected`, `connecting`, `disconnected` or `error` with a sentence. A tile has to choose between Sign in and Check again, and the sentence cannot be what it decides on. Codex also connected whether or not it was signed in, so a signed-out Codex looked connected until a turn failed.

Each client's sign-in was checked on September 28 against the versions on this computer and on forge, with throwaway homes and cancelled before completing. Codex 0.158.0's `codex login --device-auth` and Grok Build 1.0.41's `grok login --device-auth` run without a terminal: each prints a page and a code into a pipe and waits for the code to be entered there. Codex prints `https://auth.openai.com/codex/device` and says the code expires in 15 minutes; Grok Build prints `https://accounts.x.ai/oauth2/device?user_code=…` and no expiry. Claude Code 2.1.284's `claude auth login` reads the code a line at a time from standard input (its bundled source uses `readline` on `process.stdin`), prints "If the browser didn't open, visit: " and a `https://claude.com/cai/oauth/authorize` page, and expects the code the page shows, a code and a state joined by `#`; a refused code ends it with "Login failed" and a non-zero exit. Devin 3000.10.31's `devin auth login --force-manual-token-flow` prints an `https://app.devin.ai/auth/cli/continue` page, but asks for the code in a full-screen terminal prompt, and opens a browser on the machine it runs on even with that flag.

## Decision

**Tiles under the host.** In Settings → Hosts a connected host's row says how many of its providers are connected ("SSH forge · Connected · 1 provider"), and **Show providers** opens a tile for each of Claude Code, Codex, Grok Build and Devin under it; **Hide providers** closes them. A host that is not connected has neither. Each tile has the provider's mark and name, a state line with a dot, a detail line and one action:

- Connected: "Connected", then what it is signed in with and its version ("ChatGPT · 0.155.1"), with **Disconnect**.
- Turned off: "Turned off", with **Connect**. The issue's copy said "Switched off", which the glossary keeps for a saved host; a host's provider that the user disconnected is **turned off** (ADR-0036).
- Not signed in: "Not signed in", then its version, with **Sign in**; Devin shows `devin auth login --force-manual-token-flow` to run on the host, with Copy.
- Not installed, too old, or can't be started: "Not installed" ("Not on forge yet."), "Too old to use" or "Can't be started", with **Check again**. Beside it, **Have my agent install it** (update it, fix it) starts an agent's provider job (ADR-0035, amended for #461).

Under the grid: "forge connects each provider that is signed in when its host starts. A provider you disconnect stays off."

**Why a provider is not connected is a code, not a sentence.** A provider status gains `problem` (`not-installed`, `too-old`, `signed-out`, `cannot-start`) and, while connected, `account`, a kind of account and never an address ("ChatGPT", "API key", "Claude Max"). Each adapter names the problem where it finds it: no client is `not-installed`; a client older than the adapter's floor (Grok Build's and Devin's version floors, Claude Code's missing flags) is `too-old`; Claude Code's own sign-in status, Grok Build's refused cached sign-in, Devin listing no models, and Codex's account read are `signed-out`. An error without one reads as can't be started. Codex now reads its account (`account/read`) when it connects and refuses to connect without one, on this computer as on a host, so Settings → Providers says to sign in instead of a turn failing later; a client that cannot answer the read connects as before.

**Connect, Disconnect and Check again go to that host alone.** They are the host's own `connect`, `disconnect` and `refresh` for that provider, sent to the host by its saved ID rather than through the router's selected host, so nothing about this computer's providers changes. A refusal comes back to the tile rather than to the Threads page. `refresh` for a provider whose last connect failed now tries it again, which is Check again; for a connected provider it reads it again, as before, and it never changes which providers are turned off.

**Sign in from this computer.** Sign in opens a small dialog, "Sign in to Claude Code on forge", with Cancel; Escape and Cancel stop the sign-in on the host. The provider's own client runs on the host as a child process with pipes (the host has no terminal and no `node-pty`; its only runtime dependency stays `zod`), started the way its adapter finds and starts it (ADR-0036), with the adapter's own environment, so the credential lands where the adapter looks. The user finishes it in this computer's browser. Two shapes:

- Device code (Codex, Grok Build): the dialog shows the code, **Copy code** and **Open sign-in page**, and says "Waiting for you on auth.openai.com. The code lasts 15 minutes." (the minutes only when the client printed them). The client finishes by itself.
- Code pasted back (Claude Code): **Open sign-in page**, then a **Code from the page** field and **Finish sign-in**. Sotto hands the code to the client on the host as one line and keeps nothing. A code without its `#` is refused before the client sees it. A code the client refuses ends the sign-in: "Claude Code did not accept that code, so forge is still not signed in. Open the sign-in page again for a new code.", with **Try again**, which starts a new sign-in and so a new page.

When the client ends well the host connects that provider for the client that asked (which also clears it from the turned-off set, as any connect by name does), and the tile turns Connected. One sign-in runs per provider per host; starting another stops the first.

**The new remote operations.** A new host feature, `provider-sign-in`, with four requests: `sign-in-start` (a provider), `sign-in-read`, `sign-in-code` (a pasted code) and `sign-in-cancel`, each answering with the sign-in or null. They are on the remote allow-list in `src/host/remoteCommands.ts` (`REMOTE_SIGN_IN_OPERATIONS`). Pairing is enough to send them, as it is for `connect`: signing a provider in answers no permission request, and the account it signs in is the user's own, finished in the user's own browser. Only the client that started a sign-in may read it, send its code or cancel it, and its page and code are never in the shell every client receives. Only a headless host offers the feature; the desktop's phone listener (ADR-0033) does not, and the iPhone client does not send them.

**What passes, and where it stays.** The page's address and the device code travel from the host to the client that started the sign-in; the pasted code travels from this computer's window through main to the host and into the client's input. None of them is logged or written to disk on either side, and the host drops them when the sign-in ends, is cancelled, or reaches fifteen minutes, when it stops the client. On this computer main never keeps them: the window is given the code to show and never the address; **Open sign-in page** has main ask the host for the address again, check it and open it. How a sign-in ended stays on the host for two minutes, without the address or the code, so the dialog can say so.

**The pages Sotto opens.** Only `https` pages, with no port and no user, on each provider's own sign-in host exactly: `auth.openai.com` for Codex, `accounts.x.ai` for Grok Build (the host its device sign-in prints; its browser sign-in uses `auth.x.ai`, which Sotto does not run), and `claude.com` or `claude.ai` for Claude Code (2.1.284 prints `claude.com`; older versions printed `claude.ai`). Devin has none. They open from main, in the default browser, only on the user's press, as the Tailscale approval page does (ADR-0025). A client that prints any other page fails its sign-in with a sentence saying to sign in on the host itself.

**Claude Code signs in to the subscription only.** The host runs `claude auth login --claudeai`, never `--console`, and no client is ever given an API key: Codex and Grok Build use their device sign-ins, and Sotto never switches a host to API billing.

## Consequences

- The README's "Privacy and cost" names the three sign-in pages and what passes; `docs/host-protocol.md` lists the four requests; the guide's Remote hosts section describes the tiles and the dialog.
- A host needs this computer's version to sign in from here: an older host does not list `provider-sign-in`, and the dialog says to update it.
- Codex on this computer now shows "Sign in to Codex on this machine, then connect it again." when it is signed out, where it used to connect and fail at the first turn.
- Claude Code tries to open a browser on the host when its sign-in starts. On a machine without a desktop, such as forge, nothing opens; on a Mac used as a host, a browser page may open there as well.
- The live checks (sign Claude Code in on forge from this computer, and Codex and Grok Build) are the owner's; the integration test and the end-to-end spec run fake clients that print a device code or wait for a pasted code.

## Considered options

- **Pairing does not grant sign-in; a `remote-answer` policy record does.** Signing a provider in answers no request and grants no thread anything; the policy record is the user's word that a device's answers count, which is a different question. Asking for it would leave the desktop, which pairs itself over the user's own SSH session, unable to do what the user is sitting in front of it to do.
- **Record a client's kind at pairing and refuse phones.** A client names itself, the desktop's pairings from before this carry no kind, and the phone's pairing and the desktop's both redeem a code from the host's administrative path. The feature is left off the phone listener, and the iPhone client does not implement it, instead. October 5, 2026: [ADR-0053](0053-a-desktop-reaches-a-host-over-its-tailnet-first.md), proposed for the owner to confirm, brings desktops onto that listener and so records a kind after all, but not this one: the launch script records a desktop over SSH, never from what the client says, earlier desktop pairings gain it at their next SSH connect, and every client it has not recorded is a phone, which keeps sign-in off it.
- **Put the sign-in in the shell.** Every paired client receives the shell, including a phone, and the device code and page would reach all of them.
- **Run the sign-in in a terminal on the host.** The host has no terminal library and adding `node-pty` to it is a new runtime dependency; every client but Devin's works over pipes.
- **Drive Devin's paste prompt over pipes.** Its prompt is a full-screen terminal control that was not seen to read a piped line, and it opens a browser on the host; its tile shows the command instead, until Devin's sign-in has a shape that works without a terminal.
