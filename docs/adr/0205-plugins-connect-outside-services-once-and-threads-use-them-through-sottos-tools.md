# Plugins connect outside services once, and threads use them through Sotto's tools

## Status

Accepted by Zach on November 11, 2026, on question cards and against the prototype `docs/prototypes/plugins-settings-prototype.html`. He asked for "plugins for the app that give agents a known place where things are connected", with its own tab in Settings. An **Owl feature** (`plugins`, [ADR-0072](0072-sotto-owl-is-a-windows-preview-release-track.md)). Nothing is built yet; `docs/plans/2026-11-11-plugins.md` is the build in slices. **Number provisional until merge** (docs/agents/domain.md).

It amends [ADR-0025](0025-headless-host-and-client-identity.md), which says a paired client may not send a credential: the desktop now sends a plugin account's secret to the user's own paired hosts (decision 4). It adds standing exceptions to "the user answers every permission" of the kind [ADR-0029](0029-a-thread-uses-the-browser-without-asking-by-default.md) says need their own record (decisions 7 and 8). It widens "One key" in `AGENTS.md`: each plugin account is a secret Sotto holds. Each plugin adds hosts, so each gets its `README.md` entry in the pull request that builds it. [ADR-0141](0141-a-thread-makes-3d-models-with-meshy-and-asks-before-each.md)'s Meshy decision stands and is built as a plugin; where the two disagree on where the key is entered and whether it is copied, this record wins. ADR-0141 also says a host's threads always ask and that each computer counts its own credits; for a copied account decision 4 replaces both. Grok Bot, which drives Sotto and is not a service agents use, is [ADR-0206](0206-an-assistant-drives-sotto-over-the-tailnet-and-never-answers.md).

## Context

A thread's agent that needs Vercel, mail or a paid media service today finds whatever the shell happens to hold: an environment variable, a CLI's own login, a key in a file. Nothing says which accounts exist, nothing asks before a deploy or an email, nothing is recorded, and the agent holds the secret itself. The same accounts have to be set up again on every computer that runs threads.

What Sotto already has: a credential store only main reads, encrypted by the operating system, where the window learns only "saved" (`src/main/agents/credentials.ts`); a paired host with its own encrypted file and key file (`src/host/credentials.ts`); tool servers on loopback with one token per thread, which Claude Code, Codex, Grok Build, Muse, OpenCode and Pi take with no adapter change, and Devin once its list of Sotto's servers names the new one (`src/main/agents/threadToolServer.ts`, `devinPolicy.ts`); and tool calls that wait on the user's answer in Sotto, as the browser and the cloud iPhone do. The closest built precedent for a paid outside service is the cloud iPhone's run.cloud key ([ADR-0047](0047-a-cloud-iphone-runs-on-run-cloud-and-asks-before-each-session.md)); Meshy (ADR-0141) is decided and not built.

The services' own facts, read from their documentation on November 11, 2026, are in the table under decision 2. The options Zach was shown and did not choose are under Considered options.

## Decision

1. **A plugin is an outside service from a fixed list; an account is one sign-in to it.** Sotto ships the list: GitHub, Vercel, Gmail, Proton Mail, X, ElevenLabs, Higgsfield and Meshy. The user adds an **account**, names it (Work, Personal), and may add several to one plugin. There is no way to add a service that is not on the list, and Sotto loads no third-party plugin code: "plugin" here is Zach's word for a service Sotto knows how to reach, not an extension mechanism.

2. **Each plugin signs in the plainest way its service allows a single person.**

   | Plugin | Sign-in | Hosts | Cost and terms the page must say |
   |---|---|---|---|
   | GitHub | The `gh` command's own sign-in on each computer ([ADR-0027](0027-git-the-way-t3-code-does-it.md)). Sotto stores nothing and copies nothing. | Those `gh` already reaches | Free |
   | Vercel | A token the user pastes | `api.vercel.com` | Free API |
   | Gmail | The address and an app password, over IMAP and SMTP. Needs 2-Step Verification. | `imap.gmail.com`, `smtp.gmail.com` | Free. Google gives an app password the whole mailbox; Sotto's tools are what limit it. |
   | Proton Mail | Proton Mail Bridge running on the same computer: the Bridge address and Bridge password | `127.0.0.1` only (Bridge's own ports) | Needs a paid Proton plan with Bridge |
   | X | Sign-in in the browser (OAuth with PKCE, no client secret) | `api.x.com`, `x.com` | Paid per call, reads included. X's rules want automated accounts labelled. |
   | ElevenLabs | A key the user pastes | `api.elevenlabs.io` | Paid by use. May train on what is sent unless turned off in the ElevenLabs account. |
   | Higgsfield | A key ID and secret the user pastes | `api.higgsfield.ai` | Paid from a prepaid balance. May train on what is sent. |
   | Meshy | A key the user pastes | `api.meshy.ai`, `assets.meshy.ai` | Paid by the credit, as ADR-0141. May train on what is sent. |

   Host names not confirmed on a vendor page (Gmail's, and Higgsfield's console) are confirmed in the slice that builds the plugin, and that slice adds the plugin's `README.md` entry under "Privacy and cost". A plugin whose slice finds a fact here wrong amends this table with the date.

3. **Secrets live in Sotto's credential store, one slot per account, and are never shown again.** Main alone reads them. The window gets "saved" and the date, and offers **Replace**. No secret reaches a renderer, a log, a product event, an agent, a phone or a plain file. An account's name and address are the user's own details: they stay out of logs and product events ([ADR-0179](0179-sotto-sends-product-events-unless-turned-off.md)) too.

4. **An account added on the desktop is copied to the user's own paired hosts. This amends ADR-0025.** ADR-0025 said "a paired client may not send a credential, and the desktop's key never leaves it", so a host's keys were typed on the host. For plugin accounts, and only for them:
   - The desktop sends an account's secret and settings to each paired host over the connection it already holds to that host, and the host keeps it in its own encrypted credential file. This is an **account copy**.
   - **Copy new accounts to every computer I pair** is on by default. Each account has a switch per host that stops or starts its copy. A host that is not connected gets the copy when it next connects, and the page says it is waiting.
   - An account kept to chosen projects (decision 9) is never copied. A project is a folder on one computer, which another computer does not have, so that account's secret stays on the desktop: its switch for each host is off, cannot be pressed and says why, and a copy a host already holds is taken back when the account is narrowed. Given back to every project, it is copied as its switch was left. Zach picked this on November 12, 2026, from a mock-up, over finding the same project on a host by its GitHub repository and over a list of projects for each computer.
   - Only the desktop that set a host up may send one: the client that holds that host's desktop grant (ADR-0025's September 29 amendment). A phone, an app on this computer ([ADR-0180](0180-apps-on-this-computer-connect-without-a-pairing-code.md)), an assistant (ADR-0206) and a team link ([ADR-0186](0186-a-team-link-joins-two-owners-computers-over-a-closed-list.md)) can neither send nor read one. A host never sends a secret back.
   - Removing an account removes every copy; a host that is not connected removes its copy when it next connects, and the page says so until it has. Replacing a secret replaces the copies.
   - A host with no key file cannot keep a copy, and the page says so for that host, as it does for a host's own keys today.
   - **One limit and one switch, wherever the account is.** A monthly limit is one figure for the account: the desktop and each host holding a copy report what they spent to each other while connected, and a host that cannot reach the desktop keeps to what was left when it last heard. An **Ask before each** switch turned off on the desktop applies to a host's threads too. A request from a host's thread reaches the user as that host's requests already do.
   - Every other credential keeps ADR-0025's rule: the OpenRouter and run.cloud keys and provider sign-ins are still never sent.

   Zach chose this over typing accounts in again on each computer, and over the desktop answering a host's calls, because forge runs threads while the laptop is closed.

5. **An agent reaches a plugin only through Sotto's tools.** One tool server, `sotto_plugins`, served the way Sotto's other tools are, to every provider that takes them, on the desktop and on a host that holds copies. Sotto makes the call with the secret and hands back the result. No secret is put in an environment variable, a config file or an agent's hands, and there is no `sotto` command for it. An agent's own shell is unchanged: where `gh` or another CLI is signed in on the computer, the agent can still run it as it can today, and nothing here claims otherwise.

6. **Reads go through one tool; every change is its own named tool.**
   - `plugin_accounts` lists the plugins and accounts this thread may use, by name.
   - `plugin_read` reads from any part of a plugin's API: a `GET` to that plugin's hosts and no others, with the secret added by Sotto. For GitHub it is `gh api` with `GET`. A short refuse list per plugin covers reads that hand back other secrets (Vercel's decrypted environment variables, token lists). Mail has no HTTP API here, so for a mail account the same tool takes a search or a message to open in place of an address.
   - A **plugin change** (anything that sends, posts, deploys, deletes or spends to make something; a read is never one, even where the service charges for it) is a named tool with typed arguments, such as a preview deploy, sending an email or making a 3D model. A change with no named tool cannot be made through a plugin until one is added.

   Named changes are what let a card say in plain words what will happen ([ADR-0185](0185-a-permission-card-shows-readable-words-not-raw-input.md)); a card that showed a method and an address would not.

7. **Reading never asks; a change asks each time; a few changes have a switch.** Sotto holds a change's tool call until the user answers a card that names the thread, the account and what will happen, in the way the browser's and the cloud iPhone's requests wait today. It counts in **Needs you**, only the user's explicit choice answers it, and nothing reaches the service before that. Spending, publishing and destroying are ADR-0004's risk classes and are checked as any risky action is.
   - **Always ask, with no switch:** sending an email, deleting or moving mail, posting on X, a production deploy, deleting anything, merging on GitHub.
   - **Ask before each, a switch on the account, on by default:** a preview deploy (Vercel); a sound (ElevenLabs), a video (Higgsfield) and a 3D model (Meshy), each bounded by the account's monthly limit as ADR-0141 bounds Meshy's.
   - Turning a switch off is a standing grant the user makes: it reaches only that account and that kind of change, only up to the limit where there is one, every use still shows in the thread and in the record, and turning it back on ends it at once. A memory, a repetition or a provider's confirmation never turns one off.
   - Paid reads (X charges for them) do not ask but count against the account's monthly limit, and Sotto refuses a read that would pass it.

8. **Mail: each thread asks once before it reads an account.** What a thread reads goes to that thread's provider, so the first read of a mail account by a thread waits on a card that names the account and the provider. The answer is a **mail grant** for that thread and that account, until the user stops it or the thread is settled. It covers searching and reading, never sending.

9. **An account works in every thread, and a project can narrow it.** Each account has an on switch. By default every thread on every project may use it; an account can instead be limited to chosen projects, so a work project never touches a personal account. Watcher gets the reading tools only: it can list accounts and read from a plugin, such as a deploy's status, and has no tool that makes a change. It starts or steers a thread for that, as it does for other work.

10. **Sotto keeps a record of each use, without its content.** It was part of the choice Zach made for decision 5 ("Sotto can ask you first and keeps a record") and is the **Recent use** list in the prototype he picked from. The thread, the account, what was done in plain words, how it was answered and when. Never message text, addresses, file contents or what a read returned. It follows Keep local history and forgetting a thread, and the account's page shows the recent ones.

11. **Settings › Plugins is one list.** Zach's pick A of three: every plugin is a row, grouped (code and deploys, mail, 3D models, sound and video, posting, assistants that drive Sotto), in the manner of Providers, and a row opens in place to show its accounts, each with its settings. A plugin's row shows the service's own icon, drawn in one colour from the theme as a provider's mark is (`ProviderMark.tsx`). The page sits after Providers. An **Other computers** group holds the copy default and says which hosts hold copies.

12. **Each plugin sits behind one adapter in main that imports nothing from Electron**, so the host runs the same code, and speaks to its service with Node's `fetch` or sockets: no vendor SDK and no new runtime dependency ([ADR-0018](0018-terminals-run-on-node-pty.md)). Everything else addresses an account by Sotto's own ID.

13. **Owl only.** Stable shows no page and serves no plugin tools, and keeps accounts, copies and records whole, so a return to Owl finds them.

## November 12, 2026: what Vercel's pages say, and how its reads are held

Slice 3 confirmed Vercel's row of the table on Vercel's own documentation on November 12, 2026, and found more than decision 6's refuse list allowed for.

- **Confirmed.** Requests go to `api.vercel.com` with `Authorization: Bearer`. `GET /v2/user` says whose a token is. A token Vercel will not take answers 403 with `invalidToken`; a token that may not read one thing answers 403 without it. Tokens are made at vercel.com/account/tokens, scoped to the account, a team or a project.
- **Not confirmed.** Whether an environment variable's value comes back in the clear by default, whether `api.vercel.com` is the only host, where its documented `302` leads, and what a project object carries beyond its documented example, which shows `env`, deploy hook addresses and protection bypass secrets.

So a Vercel read is held four ways rather than one, and this is the pattern for a plugin read over `fetch`:

1. **A refuse list of path parts**, in any version of the API: environment variables, tokens, secrets, Edge Config under both its names (`edge-config` and `global-config`), drains, webhooks, certificates, integrations, stores, a deployment's files, a domain's transfer code and the account's activity log, and the `decrypt` query parameter. Refused before anything is sent.
2. **Fields are taken out of every answer.** An allowed read can still carry a credential, as a project does, so the answer must be JSON, and `env`, deploy hooks, protection bypass, a team's invite code, and any field whose name ends in secret, token, password, key or credential are replaced before the agent sees it. The user's email address goes too: it is theirs, and an answer goes on to the thread's provider. An answer that is not JSON is not handed over.
3. **No redirect is followed**, so a token cannot be carried to another host.
4. **The token itself is taken out of whatever comes back.** A service can echo a request's credential, so the account's own token is removed from an answer, and of an error only the status and Vercel's short code are passed on, never its message.

The cost is that a project named `env` or `files` cannot be read by name, and that a field Vercel adds later under a name this does not know would pass. The first is rare and the refusal says why; the second is why the list is by ending, not by exact name.

## November 12, 2026: how a change waits

Slice 4 built decision 7 and settled what it left open.

- **A change is one of Sotto's own requests in its thread**, as host setup's question is, not a new kind of card. That is what puts it in Needs you and on a paired phone, and what holds it to the coordinator's rules for who may answer: the user's explicit choice, never a wake-up turn. It offers two choices, allow this once and no. There is no "always" on the card; a standing answer is an account's **Ask before each** switch, where the decision gives it one.
- **It lapses after five minutes**, as the browser's and the cloud iPhone's asks do, and the agent is told to say what it wanted rather than ask again. A client that says it waits less than that for a call gets a card that lapses a minute before its wait ends, so the change and its result still fit.
- **A card lives no longer than the call it is for.** It stops when the client's connection closes before the answer, as it does when a turn is stopped; when its thread is settled, archived or deleted; and when Sotto closes. An allowed change is not made once any of those has happened. Otherwise an Allow could act for an agent that will never hear of it, and that would ask again.
- **The card is worded by Sotto from arguments it has checked**, never from the agent's own description of what it is doing, and shows everything that will be sent. Where the words need something from the service, as a Vercel deployment's project and whether it is production, Sotto reads it first; that is a read, and nothing it returns decides whether the change may go.
- **What is sent never travels in a command's arguments.** A GitHub comment goes to `gh` as JSON on standard input, so its words cannot be read as flags or as a file to send.
- **Watcher is not offered a change's tool**, and a call to one from Watcher's thread is refused without asking, so decision 12 does not rest on the list alone.
- **The use record keeps how a change was answered**: done, failed, denied or lapsed. A stopped ask keeps nothing.

Zach chose the first named changes on November 12: for GitHub, comment, open an issue, and close or reopen an issue; for Vercel, redeploy as a preview, promote to production, cancel a build and roll back. Redeploy as a preview is held back: Vercel's pages say that without a target the branch decides production or preview, so it ships only after a check against a real project.

The second pull request of the slice added the rest, and settled three things.

- **Closing and reopening are for issues, and the issue is read first.** GitHub's address for an issue also answers for a pull request, and Zach chose issues. So Sotto reads the number before it asks: a pull request's is refused, an issue already in the asked state is said without a card, and the card names the issue by GitHub's own title for it. An opened issue carries a title and a body and nothing else.
- **Promote and roll back take the project from Vercel's own read of the deployment.** Both calls address the project by its ID, which the agent does not give. Sotto reads the deployment with the account's token to word the card, and uses the project ID that read returned, kept only when it is shaped as Vercel's IDs are. This is the one place a card's read feeds the call, and it is why a deployment that cannot be read is refused before anyone is asked: with no project to name there is nothing honest to show. The paths are Vercel's documented ones as of November 12, 2026: `POST /v10/projects/{projectId}/promote/{deploymentId}` and `POST /v1/projects/{projectId}/rollback/{deploymentId}`.
- **A card that moves production says what follows.** Vercel's pages say a promotion does not build again, and that after a rollback it "turns off auto-assignment of production domains", so new pushes to the production branch stay out of production until a deployment is promoted. Both are on the cards. Both ask every time, as decision 7 says of anything that changes production.
- **Promote and roll back take a production deployment and no other.** Vercel's promote moves production to a deployment that was built for production, and its own command line builds a preview again rather than promote it. So a deployment whose target is not production is refused before anyone is asked: the card's "it is not built again" would otherwise be untrue. Putting a preview's code in production is a deploy, and belongs with redeploy (#2516).
- **A change is done only when the service's answer shows it.** GitHub redirects a moved issue and a renamed repository, and a redirected change arrives as a read that changes nothing and still answers. So the issue read for a card must be the issue asked for, by number and repository, and a change counts as made only when the answer is the thing made or carries the state asked for. When no answer comes back, the agent is told Sotto cannot say whether the change was made, so it looks before it asks the user again: an issue opened twice cannot be taken back.

## November 12, 2026: which threads may use an account

Slice 5 built decision 9 and settled what it left open.

- **The rule is asked at every call.** Whether a thread may use an account is read when its agent calls a tool, never when the tools were handed out, so a switch turned off or a project taken away takes effect at the next call. A change the user allowed on a card is looked at once more before it is sent: an account switched off, narrowed or removed while the card waited sends nothing.
- **An account a thread may not use is not named to it.** The thread is told that the plugin has an account it cannot use, so its agent can tell the user, and nothing more.
- **Watcher is in no project.** An account kept to chosen projects is for those projects' threads and nobody else, so Watcher, which belongs to none, may use only an account for every project. This is the narrower reading of "so a work project never touches a personal account"; the other reading, that Watcher may read through any account that is on, would let an account kept to one project be read from the thread that watches all of them. The page says so beside the projects.
- **GitHub has no switch.** Its account is `gh`'s own sign-in on the computer, which a thread's shell can use whatever Sotto does, so a switch on its row would promise more than it could keep. The mock-up Zach picked shows GitHub as every project's.
- **A project is its folder.** Each provider gives the same folder a project ID of its own, so an account kept to a provider's project would refuse the same folder's threads on another provider, and the page would offer the folder twice under one name. An account is kept to folders instead, each under a name of Sotto's own that says nothing of where it is; the page offers each folder once, as the project chooser does. Zach picked this on November 12, 2026, over a chip for each provider's project.
- **An older build must not misread the record.** The switch and the projects are written only where they are not the default, and the record's version is 2 only while some account is off or kept to projects. A build from before the switch reads a record of ordinary accounts as it always did, and refuses one that holds an account it would otherwise treat as open to every thread.
- **Projects are this computer's.** An account is kept to this computer's folders. A project that is later deleted stays on the account as "a project that is gone" until the user lets it go, rather than quietly widening the account to every project. So an account kept to projects has no account copy (decision 4).

## November 12, 2026: a host keeps an account copy

Slice 7 is built in three parts. The first is the host's side, and it settled how a copy is kept.

- **A copy is one of the host's own plugin accounts.** It is kept under the desktop's own ID for the account, in the same record and the same credential slots a desktop uses, so the host's threads will use a copy exactly as a desktop's threads use an account, and the desktop can name a copy to replace or remove it.
- **Only the recorded desktop may send one.** The host takes a copy only from a client the launch script recorded as its desktop, the same test it makes for the desktop's defaults. Being paired is not enough, and neither is being on the tailnet: a phone is paired too. The feature is not offered to any other client, and the request is refused for one that sends it anyway.
- **A copy belongs to the desktop that sent it.** A host can record more than one desktop. Each is told of its own copies alone and may replace or remove only those, so one desktop cannot put its secret under another's account. Revoking a desktop deletes the copies it sent, and their secrets, from the host.
- **A host holds one account of a name.** Its threads will name an account by it. A desktop's new copy takes the place of its own stale one of the same name, which a removal that never arrived leaves behind; another desktop's account of that name is refused.
- **A secret goes one way.** The host answers whether it kept a copy and lists which accounts it holds. No request reads a secret back, and the listing's own shape has no room for one.
- **The host asks no service anything.** The desktop checked the secret before it kept it. A host that cannot keep a secret, as one started without a key file cannot, keeps nothing and says so, so the desktop can tell the user why forge has no copy.
- **An older host is never sent a secret.** A host that keeps copies lists a feature, and a desktop sends one only to a host that lists it.
- **The list is what says a desktop may send.** A host lists account copies only to a desktop its launch script recorded, and for a host being added that record is written a moment after the desktop's first hello, so that hello lists none. The desktop therefore asks a host whose health lists the feature which copies it holds: a request that carries no secret, and one the host answers only after reading its record of desktops again. An answer is the host saying this desktop may send. Until the hello or that answer has said so, nothing with a secret leaves the desktop.
- **The desktop asks what a host holds, and makes it agree.** On every connection, and after every change to an account or a choice, the desktop reads the copies the host holds of its own, removes each one no longer wanted, and then sends each wanted account the host lacks or holds differently. Removals go first, so a host holding as many accounts as a plugin takes has room for the copy that replaces one. That is how a removed account, a replaced secret or a copy switched off reaches a host that was away. One look at a host runs at a time, and a look that failed is tried again, after longer each time.
- **A copy sent cannot be unsent.** A look reads what the user wants, then waits on the host. Every change to an account or a choice is counted as it is asked for, and a look that began before the newest one sends no secret: it reads the account again and checks the count in the same breath as it sends, so an account narrowed or a copy switched off while the host was answering is not sent. The change has already asked for another look, which sends what is still wanted, and asks for one even when the choice could not be written down. A look waits for a choice that is being written before it reads the choices. Choices are changed one at a time, each from the choices as the change before left them, so two made a moment apart cannot undo one another.
- **A host's threads use its copies, and the host makes each call.** A headless host whose Owl answer turns on plugins serves `sotto_plugins` to its own threads over the copies it holds, with the tools, refusals and scrubbing a desktop's threads get: one wiring builds the handlers for both (`pluginToolHandlers`). A copy's token is read from the host's encrypted credential file for one call and goes to its service from the host, so a thread there works while the desktop is off. No agent, client or log holds it.
- **GitHub on a host is that host's own `gh`.** GitHub's account was never copied: it is `gh`'s sign-in on each computer. A host's thread reads and changes GitHub as whoever `gh` is signed in to on the host, which may not be the desktop's account, and the card names that account. The page says so beside GitHub once another computer is paired, and shows it: GitHub's row lists each paired computer with who `gh` is signed in as there, read from the host over its connection (`plugin-github-sign-in`), or why it cannot say: `gh` is signed out or not installed there, the computer is not connected, its Sotto runs no plugin tools, or its Sotto runs them and is from before it could be asked. That last one is told apart by the account copies it keeps, which a host that runs plugin tools has always listed: its threads use its own `gh` all the same, so the notes about another computer's `gh` stay for it. Only a desktop the launch script recorded is told, since the account is the host owner's own detail, and what crosses is a name and never a token. There is no way to sign `gh` in on a host from the desktop: the row says to run `gh auth login` there. The mock-up Zach picked showed a Sign in button for a host; it is left out, since signing in is `gh`'s own conversation in a terminal on that machine.
- **A change on a host waits on a card in its thread.** It is one of the host's own requests, so it reaches the user wherever that thread is shown, a desktop or a phone, counts in **Needs you**, and is answered only by a client the host lets answer there (ADR-0025's desktop grant, ADR-0004). The card is in the host's English: a host has no interface language and cannot load Lingui ([ADR-0123](0123-sottos-interface-speaks-the-computers-language.md)), so it words the card itself, sentence for sentence as the desktop does, and a test holds the two together. A client words it in its own language once the host protocol carries the change itself.
- **A copy is used only while its desktop is paired.** Revoking a desktop deletes the copies it sent, but that delete can fail, as when the credential file cannot be written, or the host can go away before it runs, and a revoked desktop can never ask for it again. So a host's thread is handed a copy only when the desktop that sent it is still paired: who sent each copy is read at every call, and whether that desktop is paired is asked as the account is looked for and again as its token is read. A copy whose sender cannot be read is nobody's. What no paired desktop sent is deleted when the host next starts, before any thread does.
- **Every copy is for every project.** An account kept to chosen projects is never copied, so a host asks no thread for its project. A copy that names projects all the same, as none should, is used by no thread there.
- **A host keeps no record of use.** **Recent use** on the desktop lists the desktop's own threads, and says so once another computer is paired. Showing a host's uses needs a read the host protocol does not have yet.
- **Only the host can say it holds no copy.** Switching a copy off, or narrowing its account, decides that no copy is wanted; the secret is on the host until the host has let it go. The page says "No copy" outright only for a host that did not list the account or answered its removal. Until then it says what is still to happen: Sotto is taking the copy back from a host known to hold it, or making sure of one that has not yet said what it holds; a host that is away deletes a copy it holds when it next connects; and a host whose Sotto keeps no account copies now, as one moved from Owl to stable does not, cannot say whether it holds one from before and deletes it once it is updated. **Other computers** counts the copies a host has said it holds, a copy it is letting go among them, and none whose presence is not known. It is a count alone, not "of" the accounts: an account switched off for a host, or kept to projects, was never going to be there.
- **A choice is written down when an account and a computer first meet.** It follows **Copy new accounts to every computer I pair** as that stood then, so turning the default off later stops no copy already made, and turning it on later starts none the user did not ask for. The choices are a file of the desktop's own beside the record of accounts; a file that cannot be read, as one a newer Sotto wrote cannot, copies nothing, rather than everything. It does not stop a copy being taken back: an account removed, or kept to chosen projects, has no copy whatever the choices say, so those copies are still removed, and only the copy of an account that may be copied is left as it is. The page says the record cannot be read, shows what each host has said it holds, and lets no choice be changed.

One limit across computers, which the slice also names, has nothing to count until a plugin that spends exists. It moves to the first one, Meshy.

## November 13, 2026: how mail is read

Slice 8 is built in parts. The first is the mail adapter alone, with no account, tool or page, and it settled how a mail account is read.

- **Every read is a connection of its own.** It signs in, does one search or opens one message, and says goodbye. Nothing stays signed in between reads, so there is no connection to keep alive, share between threads or leave open when an account is switched off.
- **Nothing here can change a mailbox.** A mailbox is opened for reading only (`EXAMINE`), a message is fetched without being marked as read (`BODY.PEEK`), and the adapter has no command that sends, moves, flags or deletes. Reading a message through a plugin leaves it unread for the user. Sending is slice 9's named change.
- **A search is in IMAP's own terms, not Gmail's.** Sender, recipient, subject, words anywhere, received since and before a day, and unread, in one mailbox. Gmail's own search syntax would read better to an agent, but Proton Mail Bridge does not speak it, and decision 2 puts both on one mail path. A mailbox is named by what it is for (`inbox`, `all`, `sent`, `drafts`, `trash`, `spam`, `starred`), which a server marks whatever language its names are in, or by its own name.
- **A search lists; opening reads.** A search returns up to 50 messages, newest first, and says how many matched. With nothing to look for it lists the mailbox's newest, without asking the server to number every message. Each is listed with who it is from and to, its subject, when the server received it, whether it is unread and its size. Opening one returns its text, cut at 200,000 characters. A message with no plain text is read from its HTML, made into text, and says so. A header line and a file's name are one line each, whatever their sender wrote into them.
- **A file that came with a message is named, never fetched.** Its name, kind and size are listed. A part with a file name, or sent as attached, or inside a group sent as attached, is a file and is never read as the message's text, even where it is the whole message. Reading attachments is not part of this slice: a file is not text an agent reads, and it can be large.
- **A message's name says where it is.** It holds the mailbox, how many times the server has rebuilt that mailbox, and the message's number there, so a message a search listed is opened in the mailbox it was found in: two mailboxes number their messages alike. If the server has rebuilt the mailbox since the search, the number may be another message's, so the open is refused and the agent searches again.
- **The connection is TLS from its first byte, to the one server it is given.** The server's certificate is checked as any is. A server that says it takes no password on the connection is sent none, and one that greets the connection as signed in already is not read from.
- **What a server sends is counted.** A line, a piece of a message and a whole connection each have a size past which the connection is ended, and one read has thirty seconds. The password is in no error and no result, and a server's own words for a refusal are dropped where they repeat the password or the address.
- **No library.** IMAP and the decoding of a message are written out in `src/main/plugins/mail/`, on Node's `tls` alone, as ADR-0018 asks.

## November 13, 2026: a thread's first read of a mail account

Slice 8's second part gives the desktop's threads a Gmail account to read: the account in the account store, `plugin_read` for mail, and the mail grant. No row on the page adds a Gmail account yet; that is the slice's last part.

- **Gmail's server is the one Google names.** `imap.gmail.com`, port 993, TLS from the first byte, read on November 13, 2026 on Google's page for mail programs (developers.google.com/workspace/gmail/imap/imap-smtp). Google's help says IMAP is always on for a personal account, and that an app password needs 2-Step Verification. The same help now calls app passwords "not recommended" and prefers Sign in with Google. Decision 2 stands, for the reason under Considered options: Google's sign-in lapses every seven days for a project in Testing. It is said here so that it is known.
- **A mail account is an address and a password.** The address is kept in the record of accounts, beside the name, and is what signs in; the password is the account's secret. The window is shown the address, as it is the user's own. An agent is not: `plugin_accounts` lists a mail account by its name.
- **A Gmail app password is kept without its spaces.** Google shows it in four groups; the password is the sixteen letters.
- **The record of accounts says when it holds a mail account.** Its version is 3 while it does. A build from before mail would drop the account as one of no plugin it knows, write the rest back, and leave the password in the credential store with nothing to find it by; it refuses a version 3 record whole instead.
- **The card is one of Sotto's own requests, as a change's card is.** It names the plugin, the account as the user named it, and the provider the thread runs on, and says that what is read goes there, that the thread cannot send, move or delete mail, and that every other thread asks for itself. Its buttons are **Let this thread read it** and **Don't allow**. It counts in **Needs you**, lapses after five minutes, and only the user's own answer answers it.
- **The card does not hold the address.** A card's words travel further than the card: a Watcher that is replaced hands the words of its open cards to the next provider. The address is the user's own until they have said yes, so the card names the account by the name they gave it.
- **A no refuses that read, and the next read asks again.** The agent is told not to ask again unless the user tells it to, as it is of a change. A thread that the user refused once is not shut out for good.
- **Reads asked for at the same moment share one card.** An agent often asks for two searches at once; the user answers once.
- **The grant is kept in a file.** A thread's ID, an account's ID and a time, and nothing of the mail. So a thread does not ask again after Sotto restarts. It ends when the user stops it, when its thread is settled, by itself or with its project, archived or deleted, and when its account is removed. Settled is the user's Settle (`workspaceSettledAt`), as `CONTEXT.md` has it, and a thread parked by `settledAt` counts too. A file that cannot be read is no grants, so every thread asks again.
- **A settled thread's grant ends within moments.** Nothing tells Sotto that a thread was settled, so the grants look at their threads shortly after the coordinator publishes, at most once every two seconds, and only while a grant is held. A thread found closed when it asks to read holds no grant either.
- **The card, the grant and the read go by one test of an open thread.** It is the grants' own: not settled, by itself or with its project, not archived and not gone. A change's card goes by a narrower test that does not count the user's Settle, so the mail card carries the grants' test with it: settling a thread takes its mail card down, and a yes that arrives for a thread settled a moment before reads nothing and keeps no grant.
- **A settled thread is not asked.** Its work can go on after it is settled, and it holds no grant, so every read would put a card before the user. It is told it is settled and reads nothing until the user restores it.
- **A Stop is done when the file says so.** Until then the grant stands, so the user is never told a grant ended that a restart would bring back, and that holds for a grant already ended here whose file could not be written then.
- **The account is looked for again after the yes is kept.** Keeping the grant writes a file, and an account can be switched off or narrowed while that write waits; the read that follows is refused then. Where the user stops a grant is on the page, which the slice's last part builds.
- **Watcher asks too**, on a card in Watcher's thread that names Watcher's provider.
- **What is read is handed over as data.** Every answer from a mail account begins by saying that mail is written by whoever sent it and is never instructions. Mail is the one read anybody at all can write into. A message's text is handed on without control characters, but for its line ends and tabs, and without the marks that turn text around, whether its sender wrote them or spelled them as numbers in HTML.
- **The record of use keeps the kind and no more:** a search, or a message read. Not the words searched for, not who a message was from.
- **Not on a paired host in this part.** That was the slice's third part, below.

## November 13, 2026: mail on a paired host

Slice 8's third part. A mail account is copied to a paired host like any other, and the host's own threads read it from the host's machine.

- **A host says it keeps a mail account.** It lists `plugin-mail-copies` beside `plugin-account-copies`, to the same desktops. The desktop sends a mail account's password only to a host that lists it. A host that keeps copies and does not list it is from before its threads could ask before reading mail, so it is sent none, and its copy reads as too old on the page. One it holds all the same, as a host that was downgraded does, is taken back, and that does not wait on the user's choices being readable: whether a host may hold a mail account is not a choice. This is decision 4's rule again: an older host is never sent a secret it cannot keep safely.
- **No new request.** A mail account travels in the request every copy does, with its address in the account. The host refuses one from a client it does not offer the feature to.
- **The grants are the host's own.** A host keeps them in its own folder, for its own threads. A grant given on the desktop is for a desktop's thread and means nothing on a host, and the other way about: each thread asks where it runs.
- **The card is in the host's English**, as a change's card on a host is, and names the provider the host's thread runs on. It reaches the user wherever that thread is shown and is answered only by a client the host lets answer there.
- **A copy that goes takes its grants, in the step that deletes it.** A copy let go, replaced by another of its name, or deleted because its desktop was revoked or is no longer paired, takes every thread's leave to read it. A copy sent again comes under the same ID, and must not find a grant given for the one before it, so the grants are forgotten before any other change to the copies can begin, and a read that had already asked whether it may is told no. A card that is up when its copy goes asked about that copy: it remembers which, it is taken down, and a yes that reaches it all the same is not kept, so the copy sent again is asked about afresh. A grant left in the file by a host that went away part-way goes when the host next starts.
- **One test of an open thread, on the host too.** The host's grants end by the test the desktop's do: the thread is not settled, by itself or with its project, not archived and not gone.
- **Mail is read from the host's machine.** The host signs in to the account's own mail server with the copy's password from its encrypted credential file, as it reaches Vercel with a copy's token.

## November 13, 2026: Gmail's row

Slice 8's fourth part puts Gmail on Settings › Plugins, in a **Mail** group of its own, as the mock-up Zach picked for the page has it.

- **An account is a name, an address and an app password.** The form says where an app password is made (myaccount.google.com/apppasswords, from Google's own help page, read that day) and that it needs 2-Step Verification. It is kept without the spaces Google shows it with, so it can be pasted as shown.
- **The page shows the address; an agent is told the name.** The address is on the account's card, since it is the user's own and tells two accounts apart. It is not on the card that asks, and `plugin_accounts` does not list it.
- **The row says what a thread may do.** That each thread asks once, in the thread, before it reads an account; that what it reads goes to the thread's provider; and that a thread cannot send, move or delete mail and leaves a message unread.
- **The page's first sentence says so too.** It said "Reading never asks you." With mail that is no longer the whole of it: "Reading never asks you, except that each thread asks once before it reads a mail account."
- **An agent is told of Gmail whether or not an account is added.** With none, `plugin_accounts` says to ask the user to add one, as it does for Vercel. Before the row existed it left Gmail out, so that no agent sent the user looking for a way to add one.
- **A first read the user did not allow reads as what was asked.** Recent use says "Asked to search mail" with "You said no." or "Nobody answered in time.", as it does of a change that was not made.
- **Where a grant is stopped is the thread.** Zach decided on November 13, 2026, on a question card, from a mock-up with three answers kept as the tag `prototype/plugin-mail-grants`: a list of threads on the account's row with Stop, an item in the thread's ··· menu, or both. He picked the menu item, **Ask before this thread reads** the account, shown only while the thread can read it, as the browser's is. The page lists no threads. That is the slice's last part; until it lands a grant ends when its thread is settled, archived or deleted, or its account is removed.

## Considered options

- **Where secrets live.** Each computer its own, as ADR-0025 has it (rejected: every account typed in on every computer). The desktop keeps them and answers a host's calls (rejected: forge's threads would lose plugins while the laptop is closed). One operating-system keychain entry per account (rejected: a native dependency, which ADR-0018 says needs its own ADR).
- **How agents reach a plugin.** Environment variables (rejected: every agent would hold every secret, and nothing could ask first or record). Tools plus a per-plugin switch that also sets a variable (not chosen). A `sotto` command (not chosen: a new program to ship and keep on `PATH`).
- **Tool shape.** The whole API through one tool, changes included (rejected: a change's card would show a method and an address). Named tools only (rejected: slow to build, and agents could read only what was listed).
- **Watcher.** No plugin tools, or every tool as any thread. Zach chose reads only.
- **A limit on a copied account.** Each computer counting its own, as ADR-0141 did. Zach chose one limit across computers.
- **Asking.** Every change always asks with no switches; a switch for every plugin, email and X included; each thread asks once per plugin. Zach chose reads free, changes asking, and switches only where a limit or a preview bounds the harm.
- **Gmail.** Google sign-in with the user's own Cloud project: Google itself would enforce read-only against send, but the sign-in lapses every 7 days while the project is in Testing. Not chosen; an app password shares one mail path with Proton Mail Bridge.
- **The page.** B, accounts first with a side sheet; C, a list beside the chosen account's detail. Both are in the prototype.

## Consequences

- Sotto holds more secrets than one. `AGENTS.md`'s "One key" names this record, and its permission rule names the switches of decision 7 beside ADR-0029 and ADR-0141.
- A secret now crosses from the desktop to a host. It travels only over the connection the desktop already holds to that host (its tailnet listener carried by Tailscale Serve, or SSH), and a host that is taken over yields every copied account. The switch per account and the default are the user's control over that.
- A limit shared across computers is only as exact as their last contact: a host cut off from the desktop can spend what was left when it last heard, and no more, so the two together can pass the limit by at most that remainder.
- ADR-0141's two rules for a host, that its threads always ask and that it counts its own credits, give way to decision 4 for a copied account. ADR-0141 carries the note.
- Watcher can read from a plugin, so what it reads goes to Watcher's provider as a thread's does. A mail account still asks once before Watcher's first read of it.
- GitHub through Sotto's tools asks before a change while an agent's own shell does not. The page says so rather than implying a protection that is not there.
- An app password is all-or-nothing at Google and at Proton Mail Bridge. Decisions 6 to 8 are the only thing between an agent and the whole mailbox, so they are tested as a boundary, not as a convenience.
- A thread's provider sees whatever a read returns: mail, build logs, project names. The mail card says so; the page says it once for every plugin.
- Vendor icons are drawn from each service's own mark, with the source of each recorded beside it as provider marks record theirs. The trademarks belong to their owners.
- Still to settle on a card when each slice starts: X's monthly limit and whether Sotto sets the automated label; what ElevenLabs is for beside files in a thread's folder, given that nothing in Sotto speaks ([ADR-0068](0068-remove-voice-control-and-thread-management.md)); Higgsfield's limit.
