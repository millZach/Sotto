# Sotto's own history, on an event store the host owns and a client reads

Accepted September 19, 2026, so that a thread's history stops being something a provider is asked to rebuild, and so the same split serves a machine the user is not sitting at. Transport beyond loopback — which remote path ships first, and what the pairing flow looks like to the user — is left open for the owner to decide and is marked as open below.

## Context

Every message of every thread lives in one file. `WorkspaceHost` reads `workspace.json` at startup, holds the whole snapshot in memory, clones it on each publish and rewrites it on each save, so the cost of opening the app, of drawing the sidebar and of one streamed chunk all grow with everything the user has ever said. The 0.1.3 startup crash was that cost meeting a large file. Grok's uncapped history polling is the same shape from the other end.

Underneath it, the provider is treated as the history of record. Codex loads both registries at connect and reads a thread's turns when it is opened (ADR-0005 as amended), Grok calls `session/load` for every known alias at connect and then polls each one, and Claude spawns a CLI per observed thread and replays its transcript from the first byte unless a cursor and the messages that account for it are handed back together (ADR-0015). Sotto's copy exists, but as a cache the adapters are expected to be able to reconstruct. That is why a provider that loses a session loses Sotto's memory of the thread with it, and why reconnect work scales with history rather than with what happened while Sotto was away.

The next step is not a bigger cache. Sotto is heading for threads that run on a machine the user is not looking at, which needs a clean line between the part that owns providers, worktrees and history, and the part that draws a window. T3 Code already runs this way: its own event store, projections for reading, provider sessions resumed lazily, history read in windows, and no provider transcript replayed on reload.

`workspace.json` also holds organization that has nothing to do with history — projects, threads, creations, aliases, settled state — and that part is small, is genuinely Sotto's and is fine where it is.

## Decision

**Messages live in Sotto's own event store, and providers are read to append to it.** A single SQLite database, `threads.sqlite` in the user data folder, opened with `node:sqlite` the way the memory store already is (ADR-0003), behind `ThreadStore` in `src/main/agents/threadStore.ts`. Production dependencies stay exactly `zod`. The `events` table is append-only: `seq INTEGER PRIMARY KEY AUTOINCREMENT`, `thread_id`, `kind`, `at`, and a JSON `payload`. The first cut has five kinds. `message-added` is a new message. `message-text-appended` is a streaming message that grew by a suffix. `message-replaced` is a whole message that changed in a way an append cannot say. `messages-reset` is a confirmed rewind: the thread's history before that point is gone, and the event carries the new `historyEpoch`. `answer-given` is an answer to a permission request or a question, with its attribution. Nothing edits or deletes a row to change what happened; a rewind is an event like any other.

**A projection is what the renderer reads.** The `messages` table holds `(thread_id, position, message_id, role, text, created_at, command_id, attachments JSON)`, indexed by `(thread_id, position)`, and it is derived: it is rebuilt from the log only when it is missing or when the schema version moves. The two kinds of read the app makes are then both cheap. A window of history is an indexed range over `messages`. A client catching up is `ThreadStore.eventsAfter(seq, threadId?)` — everything after sequence N — which is how the window resumes after a reload and how a remote client will resume after a reconnection. The revision the thread detail already carries (`AgentThreadDetail.revision`) is the client-side counterpart it always was; the sequence number is the store's.

**`workspace.json` keeps organization only.** Threads, projects, creations and aliases stay; a thread's `messages` array stays in the schema and stays empty, so nothing downstream has to learn a second shape at once. A one-time migration on first start moves every message out of the snapshot into the store in `createdAt` then array order, and then rewrites the file without them. It is idempotent, so a half-finished run costs a repeat and not a duplicate, and a failure leaves `workspace.json` exactly as it was; the app then starts on the old path rather than starting empty.

**History is read in windows.** `ThreadStore.readMessages(threadId, { limit, beforePosition? })` returns the newest messages first: ten turns to open a pane, where a turn is a user message and the assistant messages that follow it, and twenty more per request after that. The detail the window receives carries `earlierAvailable`, and the pane offers a plain "Show earlier messages" control above the oldest message it holds. A thread with ten thousand messages costs the same to open as a thread with thirty.

**Memory follows the watched set.** `WorkspaceHost` holds messages in memory only for the threads in the watched set — what `observeThreads` already names: the threads on screen, plus assigned or queued ones. Every other thread carries its `summary` and nothing else, which is what the sidebar reads and what `agentShell` already publishes. Startup cost and publish cost therefore follow the panes that are open, not the total history, and the clone on each publish stops carrying the archive.

**Keep local history off is a property of the store, not a pass over its output.** With the setting off no message text is written at all: messages are held in memory for the run and are gone when Sotto quits, an ephemeral stream. Turning it off deletes every row of `messages` and redacts the `payload` of every message event down to its id and its timestamps, so the shape of what happened survives and the words do not. Turning it back on resumes writing from that moment. What was not kept is not recoverable, and that is the promise the setting makes.

**Adapters append; they do not rebuild.** Each adapter publishes deltas through one append path — `message-added` and `message-text-appended` — rather than handing up a rebuilt `messages` array: Claude from its transcript tail behind the cursor of ADR-0015, Codex from the app-server stream and from rollouts, Grok from its update cursor. Takeover detection is unchanged and is one of the sources these events come from. The snapshot the renderer draws is derived by the projection, and no adapter holds a full `messages` array for a thread outside the watched set. This supersedes the part of ADR-0015 that made `WorkspaceHost`'s cache the history of record between runs: the store is, and `restoreThreadHistory` is served from it. The cursor's own rule is untouched — it is trusted only beside the history it accounts for, and with Keep local history off there is no history to hand back, so the transcript is read whole.

**Provider sessions start when something needs them.** Connect starts no per-thread provider session. A session starts on the first command for a thread, or when the thread enters the watched set; this is ADR-0005's "resume a thread when it is opened" extended to Claude and Grok, and the exception ADR-0005 records stands, because a personal chat owns its own native request channel and has no other opening step. A session reaper sweeps every five minutes and stops a session idle for thirty minutes. It never stops one with a running turn, one with a pending request, or one in the watched set. The resume cursor is host state, kept where the adapter already keeps its alias, so a stopped session costs a resume and never a re-read.

**An answer says who gave it.** Every `answer-given` event carries `{ clientId, user, transport }`, where `transport` is `ipc` for the desktop window on this machine or `socket` for a paired remote client. This is attribution, which is evidence of who answered and never authority in itself: policy records decide whether an answer counts as a grant (ADR-0004), and the local desktop window always may answer. The rule that the user answers every permission is unchanged; recording which client the user answered from is how that rule survives a second client.

**The host owns; the client reads.** The host is the process that owns the providers, the worktrees and the store. The client speaks only the event stream and commands, and holds no provider identity of its own — threads are addressed by Sotto thread ID either way (ADR-0002). Locally both live in this app: the host is Electron main, the client is the window, and the transport between them is the IPC the preload bridge already carries. Remotely, IPC first and a socket second. Beyond loopback the shape is the one T3 uses: a pairing flow that issues a client token, signed sessions over it, TLS through Tailscale Serve rather than a certificate Sotto manages, and an origin check on the local socket too. An SSH device host — a helper started on the remote machine over the user's existing SSH, inheriting its authentication and exposing no port — is the cheapest first remote step. **Which of those ships first, and what pairing looks like to the user, are open and are the owner's to decide.** Nothing here adds a listening socket; the first change that does is a README "Privacy and cost" change before it is a patch.

## Considered options

- **Keep `workspace.json` and split it per thread.** Smaller files, and the same two problems: a thread still rewrites its whole file on every chunk, and history is still a cache the providers are expected to be able to rebuild.
- **One append-only JSONL file per thread.** Appending is cheap and the format is readable, but there is no indexed read: a window of the last ten turns means scanning to the end, and the projection is a rescan on every open. The rewind and redaction rules would each need a compaction pass of their own.
- **Leave the provider transcripts as the source of truth.** What exists today. Cost grows with history on every connect, a provider that loses a session loses Sotto's memory of the thread, and a remote client would have to reach the providers rather than the host.
- **A third-party event store or an ORM.** Sotto's production dependencies are exactly `zod`; `node:sqlite` is already the memory store's engine, already proven in the packaged runtime, and adding a runtime dependency would be an ADR of its own before it was a schema.

## Consequences

Opening the app costs the watched set. Opening a pane costs ten turns. Reconnecting costs what was appended while Sotto was away, and reloading the window costs everything after a sequence number. None of those grow with the archive, which is the point.

The store becomes the thing whose loss matters: losing `threads.sqlite` loses history Sotto can no longer ask a provider to rebuild, so backup and repair of that file are real work rather than an afterthought, and the migration is written to fail safe because the snapshot it reads from is the only other copy. ADR-0015 is amended rather than reversed — its cursor rule survives, its claim about where the history of record lives does not.

Two details settled in implementation. The `answer-given` event carries no answer text: an answer can read like a prompt, so the record is the request, the choice, a question's chosen option ids and the client, and the schema's `answer` field is left optional for the events already written. And "policy records decide whether an answer counts as a grant" became `Authority.mayGrant(client)`, answered from a `remote-answer` policy record scoped `client:<clientId>`; the local window always may, and a record scoped `global` is not an answer about any one client. The host/client boundary shipped as `HostService`, pairing records and tokens shipped without a listener, and the pairing UX and the first remote path remain the owner's open decisions.

Four implementation tickets hang off this: the store and its migration, windowed reads and the pane control, lazy sessions with the reaper, and attribution on answers. The host and client split is already true locally the day the store lands, which is what makes the remote step a transport decision rather than a rewrite.
