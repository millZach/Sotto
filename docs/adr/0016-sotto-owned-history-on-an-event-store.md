# Sotto's own history, on an event store the host owns and a client reads

Accepted September 19, 2026, so that a thread's history stops being something a provider is asked to rebuild, and so the same split serves a machine the user is not sitting at. Transport beyond loopback — which remote path ships first, and what the pairing flow looks like to the user — is left open for the owner to decide and is marked as open below.

Amended September 22, 2026 by ADR-0025: the owner decided both. SSH ships first, with the desktop pairing itself over the SSH session and a phone entering a code read on the host; the host listens on its own loopback address, reached through the SSH forward or Tailscale Serve, and the README's "Privacy and cost" section names that path. Everything else here stands.

## Context

Every message of every thread lives in one file. `WorkspaceHost` reads `workspace.json` at startup, holds the whole snapshot in memory, clones it on each publish and rewrites it on each save, so the cost of opening the app, of drawing the sidebar and of one streamed chunk all grow with everything the user has ever said. The 0.1.3 startup crash was that cost meeting a large file. Grok's uncapped history polling is the same shape from the other end.

Underneath it, the provider is treated as the history of record. Codex loads both registries at connect and reads a thread's turns when it is opened (ADR-0005 as amended), Grok calls `session/load` for every known alias at connect and then polls each one, and Claude spawns a CLI per observed thread and replays its transcript from the first byte unless a cursor and the messages that account for it are handed back together (ADR-0015). Sotto's copy exists, but as a cache the adapters are expected to be able to reconstruct. That is why a provider that loses a session loses Sotto's memory of the thread with it, and why reconnect work scales with history rather than with what happened while Sotto was away.

The next step is not a bigger cache. Sotto is heading for threads that run on a machine the user is not looking at, which needs a clean line between the part that owns providers, worktrees and history, and the part that draws a window. T3 Code already runs this way: its own event store, projections for reading, provider sessions resumed lazily, history read in windows, and no provider transcript replayed on reload.

`workspace.json` also holds organization that has nothing to do with history — projects, threads, creations, aliases, settled state — and that part is small, is genuinely Sotto's and is fine where it is.

## Decision

**Messages live in Sotto's own event store, and providers are read to append to it.** A single SQLite database, `threads.sqlite` in the user data folder, opened with `node:sqlite` the way the memory store already is (ADR-0003), behind `ThreadStore` in `src/main/agents/threadStore.ts`. Production dependencies gain nothing here (they are `zod` and, since ADR-0018, `node-pty`). The `events` table is append-only: `seq INTEGER PRIMARY KEY AUTOINCREMENT`, `thread_id`, `kind`, `at`, and a JSON `payload`. The first cut has five kinds. `message-added` is a new message. `message-text-appended` is a streaming message that grew by a suffix. `message-replaced` is a whole message that changed in a way an append cannot say. `messages-reset` is a confirmed rewind: the thread's history before that point is gone, and the event carries the new `historyEpoch`. `answer-given` is an answer to a permission request or a question, with its attribution. Nothing edits or deletes a row to change what happened; a rewind is an event like any other.

**A projection is what the renderer reads.** The `messages` table holds `(thread_id, position, message_id, role, text, created_at, command_id, attachments JSON)`, indexed by `(thread_id, position)`, and it is derived: it is rebuilt from the log only when it is missing or when the schema version moves. The two kinds of read the app makes are then both cheap. A window of history is an indexed range over `messages`. A client catching up is `ThreadStore.eventsAfter(seq, threadId?)` — everything after sequence N — which is how the window resumes after a reload and how a remote client will resume after a reconnection. The revision the thread detail already carries (`AgentThreadDetail.revision`) is the client-side counterpart it always was; the sequence number is the store's.

**`workspace.json` keeps organization only.** Threads, projects, creations and aliases stay; a thread's `messages` array stays in the schema and stays empty, so nothing downstream has to learn a second shape at once. A one-time migration on first start moves every message out of the snapshot into the store in `createdAt` then array order, and then rewrites the file without them. It is idempotent, so a half-finished run costs a repeat and not a duplicate, and a failure leaves `workspace.json` exactly as it was; the app then starts on the old path rather than starting empty.

**History is read in windows.** `ThreadStore.readMessages(threadId, { limit, beforePosition? })` returns the newest messages first: ten turns to open a pane, where a turn is a user message and the assistant messages that follow it, and twenty more per request after that. The detail the window receives carries `earlierAvailable`, and the pane offers a plain "Show earlier messages" control above the oldest message it holds. A thread with ten thousand messages costs the same to open as a thread with thirty.

**Memory follows the watched set.** `WorkspaceHost` holds messages in memory only for the threads in the watched set — what `observeThreads` already names: the threads on screen, plus assigned or queued ones. Every other thread carries its `summary` and nothing else, which is what the sidebar reads and what `agentShell` already publishes. Startup cost and publish cost therefore follow the panes that are open, not the total history, and the clone on each publish stops carrying the archive.

**Keep local history off is a property of the store, not a pass over its output.** With the setting off no message text is written at all: messages are held in memory for the run and are gone when Sotto quits, an ephemeral stream. Turning it off deletes every row of `messages` and redacts the `payload` of every message event down to its id and its timestamps, so the shape of what happened survives and the words do not. Turning it back on resumes writing from that moment. What was not kept is not recoverable, and that is the promise the setting makes.

**Adapters append; they do not rebuild.** Each adapter publishes deltas through one append path — `message-added` and `message-text-appended` — rather than handing up a rebuilt `messages` array: Claude from its transcript tail behind the cursor of ADR-0015, Codex from the app-server stream and from rollouts, Grok from its update cursor. Takeover detection is unchanged and is one of the sources these events come from. The snapshot the renderer draws is derived by the projection, and no adapter holds a full `messages` array for a thread outside the watched set. This supersedes the part of ADR-0015 that made `WorkspaceHost`'s cache the history of record between runs: the store is, and `restoreThreadHistory` is served from it. The cursor's own rule is untouched — it is trusted only beside the history it accounts for, and with Keep local history off there is no history to hand back, so the transcript is read whole.

**Provider sessions start when something needs them.** Connect starts no per-thread provider session. A session starts on the first command for a thread, or when the thread enters the watched set; this is ADR-0005's "resume a thread when it is opened" extended to Claude and Grok, and the exception ADR-0005 records stands, because a personal chat owns its own native request channel and has no other opening step. A session reaper sweeps every five minutes and stops a session idle for thirty minutes. It never stops one with a running turn, one with a pending request, one with a confirmed live monitoring task or confirmed background work (ADR-0023), or one in the watched set. Monitoring observations are ephemeral: keeping the session alive does not persist the watch or grant authority. The resume cursor is host state, kept where the adapter already keeps its alias, so a stopped session costs a resume and never a re-read.

**An answer says who gave it.** Every `answer-given` event carries `{ clientId, user, transport }`, where `transport` is `ipc` for the desktop window on this machine or `socket` for a paired remote client. This is attribution, which is evidence of who answered and never authority in itself: policy records decide whether an answer counts as a grant (ADR-0004), and the local desktop window always may answer. The rule that the user answers every permission is unchanged; recording which client the user answered from is how that rule survives a second client.

**The host owns; the client reads.** The host is the process that owns the providers, the worktrees and the store. The client speaks only the event stream and commands, and holds no provider identity of its own — threads are addressed by Sotto thread ID either way (ADR-0002). Locally both live in this app: the host is Electron main, the client is the window, and the transport between them is the IPC the preload bridge already carries. Remotely, IPC first and a socket second. Beyond loopback the shape is the one T3 uses: a pairing flow that issues a client token, signed sessions over it, TLS through Tailscale Serve rather than a certificate Sotto manages, and an origin check on the local socket too. An SSH device host — a helper started on the remote machine over the user's existing SSH, inheriting its authentication and exposing no port — is the cheapest first remote step. **Which of those ships first, and what pairing looks like to the user, are open and are the owner's to decide.** Nothing here adds a listening socket; the first change that does is a README "Privacy and cost" change before it is a patch.


## Considered options

- **Keep `workspace.json` and split it per thread.** Smaller files, and the same two problems: a thread still rewrites its whole file on every chunk, and history is still a cache the providers are expected to be able to rebuild.
- **One append-only JSONL file per thread.** Appending is cheap and the format is readable, but there is no indexed read: a window of the last ten turns means scanning to the end, and the projection is a rescan on every open. The rewind and redaction rules would each need a compaction pass of their own.
- **Leave the provider transcripts as the source of truth.** What exists today. Cost grows with history on every connect, a provider that loses a session loses Sotto's memory of the thread, and a remote client would have to reach the providers rather than the host.
- **A third-party event store or an ORM.** Sotto's production dependencies are `zod` and `node-pty` (ADR-0018); `node:sqlite` is already the memory store's engine, already proven in the packaged runtime, and adding a runtime dependency would be an ADR of its own before it was a schema.

## Consequences

Opening the app costs the watched set. Opening a pane costs ten turns. Reconnecting costs what was appended while Sotto was away, and reloading the window costs everything after a sequence number. None of those grow with the archive, which is the point.

The store becomes the thing whose loss matters: losing `threads.sqlite` loses history Sotto can no longer ask a provider to rebuild, so backup and repair of that file are real work rather than an afterthought, and the migration is written to fail safe because the snapshot it reads from is the only other copy. ADR-0015 is amended rather than reversed — its cursor rule survives, its claim about where the history of record lives does not.

Two details settled in implementation. The `answer-given` event carries no answer text: an answer can read like a prompt, so the record is the request, the choice, a question's chosen option ids and the client, and the schema's `answer` field is left optional for the events already written. Chosen option ids may contain the provider's option labels, so forgetting a thread or turning Keep local history off removes them along with any legacy answer text; attribution remains. And "policy records decide whether an answer counts as a grant" became `Authority.mayGrant(client)`, answered from a `remote-answer` policy record scoped `client:<clientId>`; the local window always may, and a record scoped `global` is not an answer about any one client. The host/client boundary shipped as `HostService`, pairing records and tokens shipped without a listener, and the pairing UX and the first remote path remain the owner's open decisions.

Four implementation tickets hang off this: the store and its migration, windowed reads and the pane control, lazy sessions with the reaper, and attribution on answers. The host and client split is already true locally the day the store lands, which is what makes the remote step a transport decision rather than a rewrite.

Amended September 20, 2026: the store explicitly keeps WAL with `synchronous=FULL`. Provider transcript cursors are saved independently of the event store, so a cursor that survives a power loss could skip messages lost from a less durable store. Every committed event, including answers and migrated history, keeps the same durability. Prepared statements are reused for the life of the connection to avoid compiling them on each read and streamed update; closing the connection drops them.

## Amendment: bounded Devin native replay (September 20, 2026, #150)

Devin CLI 3000.10.31 has a verified ACP session/load replay but no verified incremental transcript cursor. Its prompt response reports completion, so Sotto also needs replayed dispatch identities to confirm delivery without resending uncertain work. Devin is an explicit exception to this ADR's native resume-without-re-reading and incremental reconnect-cost guarantees. Sotto keeps its own event store as the history of record and preserves windowed renderer reads; those guarantees do not depend on Devin replay speed.

The adapter reads native history within a 16 MiB text limit and a 20,000-message limit. UUID identities deduplicate replay against the event store, and only observed changes are appended. Watched idle threads are checked every fifteen seconds; running turns and pending requests use a shorter cadence. Explicit refresh and send request a fresh history check, sharing one already in progress. Lazy per-thread startup and the session reaper remain unchanged.

Native resume, reconciliation, and polling therefore cost a bounded read of the provider transcript, not only its new tail. A long Devin thread can take longer to reconnect or send to. If native history exceeds the supported limit, Sotto refuses that read and cannot safely reconcile or continue the thread through Devin; saved Sotto history remains readable, and uncertain work is never resent automatically. The limit is a safe refusal, not a claim that only the newest part was read.

Since October 6, 2026 (#770), a send to a thread whose Devin session Sotto already holds replays nothing before its prompt, and its acceptance can come from the session's own stream; the replay confirms the dispatch afterwards. Opening a session, reconnecting and reading a session Sotto does not hold still replay it whole. See [ADR-0017's amendment](0017-devin-native-provider-data-policies.md#amendment-a-send-checks-once-and-reads-nothing-while-sotto-holds-the-session-october-6-2026-770).

This exception accepts a verified protocol limitation instead of inventing a cursor or weakening delivery evidence. It does not change history retention, permission authority, or provider data policies. See the [native compatibility evidence](../verification/2026-09-19-devin-native-compatibility.md) and [Devin data-policy decision](0017-devin-native-provider-data-policies.md).


## Amendment: incremental activity persistence (September 20, 2026)

Retained thread activity moves out of `workspace.json` into indexed rows in the same `threads.sqlite`. The previous message migration left activity output in the organization snapshot; one small provider update still copied and rewrote the entire archive. Activity keeps its existing bounded timeline, ordering, IDs, nested output and history-epoch behavior. Changed records are upserted, missing records are removed, and unchanged records require no JSON encoding or database transaction. This is a retained observation table, not a change to the append-only message event protocol.

Legacy JSON activity is imported before the JSON copy is removed. A committed SQLite list and its epoch take precedence if an interrupted save leaves both copies; legacy activity is imported only when no committed list exists. An explicit marker preserves the distinction between an observed empty list and missing activity evidence, including an unversioned list. Stale legacy messages from a different epoch are not relabeled and re-imported. A failed activity migration keeps the legacy copy available and reports the storage problem. WAL and `synchronous=FULL` remain unchanged. Organization JSON remains an atomic, ordered save; an identical value is skipped only against the last successfully completed save.

Keep local history governs activity too. Turning it off scrubs durable output and continues the current view in memory. Hashes of erased thread/activity identities are retained without text, so re-enabling history or replaying a provider cannot restore erased activity. New activity identities may be retained after history is enabled again. Migration, replay, restart and privacy transitions are regression-tested.

Internal provider and workspace snapshots still isolate mutable objects and arrays for their consumers. Their plain-data copy preserves immutable string values instead of serializing large output strings again. This changes copy cost, not the renderer transport, history window, permission behavior or user-visible timeline.

### Amendment: owned activity publications (September 23, 2026)

An optional internal `subscribeActivitySnapshots` path shares deeply immutable activity trees through the native adapter, Sotto identity wrapper, provider switch, workspace and coordinator. All other snapshot containers remain isolated per consumer. Public `snapshot`, `workspaceSnapshot` and ordinary `subscribe` results still give callers independently writable activity copies. IPC and socket formats, display cadence and immediate command/permission behavior are unchanged.

The ownership module copies unowned input before recursively freezing it. It certifies only the objects it owns; a caller's shallow-frozen array or unchanged mutable array identity is not evidence. An adapter installs the owned array and its projectors replace changed records/arrays. Already-owned descendants can be shared when a new array is installed. The certificate is held in a weak set and is never serialized, persisted or interpreted as authority.

The workspace treats a certified array as an activity revision, reuses unchanged merged history and merges only changed input records. A different epoch, replacement of the held result, legacy mutable input or privacy transition forces reconciliation. Status, requests, usage, provider connection state and time-dependent background work still pass through on every snapshot; unchanged activities do not suppress those changes. Branch-movement and activity-summary work follow activity changes independently of message text.

The activity store may skip a certified revision only after a successful save, with the same activity epoch, message-reset sequence and redaction generation. A failed transaction remains eligible for retry. Closing or replacing the store clears its successful-input cache; redaction invalidates it. SQLite durability and all history-off rules remain unchanged. The older copy/reconcile path remains valid for hosts without the optional subscription.

## Amendment: retained subagent observations (September 20, 2026, #124)

The Agents view keeps an indexed observational roster and each child's assignments in a separate `subagents.sqlite`, owned by `WorkspaceHost` and read through a main-window-only preload bridge. This supplements the message event store; these records are provider observations rather than message events or permission grants. The separate projection avoids coupling its migration and privacy lifecycle to the message event log. Child identities remain display-only adapter identities under a Sotto thread ID (ADR-0002). Subagent task and result text stays in this store alone. The ordinary activity store and its JSON migration fallback retain only text-free task classification and observational identities. Legacy child tasks are retained in the roster before that classification replaces their activity payload. The history source also supports an indexed lookup by activity identity, so a late Claude completion remains recognizable even when its start has left the bounded activity window before restart. These lookups preserve the thread-ID mapping and epoch checks from the cursor handoff; no archive is loaded at startup.

The general activity stream retains 2,000 records and can contain several tool actions for one child. Deriving the roster from that stream on every render would both double-count agents and silently lose earlier assignments. A normalized child observation instead updates its own indexed row and assignment; the thread snapshot carries only small current counts. Initial reads return at most 50 agent rows; assignment details return ten tasks per page. A changed row travels separately from older history. Renderer caches and live updates are bounded, and explicit paging is the only way to read more history.

The store deduplicates observations, preserves spawn order and earlier assignments when an agent is reused, and keeps late results on their own assignment. A parent/tool finishing cannot finish its child. Restart and disconnection mark working children uncertain; only fresh provider evidence restores the working indicator. Reported model metadata is displayed as supplied, and missing models stay missing rather than inheriting an assumed parent model.

Keep local history governs this store too. With it disabled, observations use an in-memory database. Disabling it deletes the durable roster and tasks, checkpoints the WAL and clears free pages; enabling it starts retention for fresh assignments. A separate indexed table keeps only SHA-256 hashes of erased observational identities, so provider replay cannot restore deleted words after a restart. Explicit history changes preserve generic unfinished status and text-free classification/aliases for those current assignments, allowing late completion and reuse after restart without restoring erased words. An erased assignment remains text-free even if it later reports a result; a reused agent needs a fresh assignment identity to retain new text. No new host is contacted, no title-generation model is invoked, and none of these observations can answer a permission request.

The activity snapshot also records the sequence of the latest committed message reset. On restart, the committed message generation outranks older activity or organization JSON; mismatched activity is discarded rather than relabeled. An indexed reset lookup distinguishes no reset from an explicit unversioned reset, including resets that leave no messages. This protects recovery when message events commit before activity synchronization finishes.

## Amendment: activity windowed with its messages (September 22, 2026, #257)

A thread detail carries a window of messages but used to carry every activity record the thread keeps. A record whose message was above the window had nowhere to go, so the pane drew it under the newest answer. The renderer could guess from first-observed order which turns were older, but a provider that reads its history again after a restart hands back old records the store no longer held, and they are numbered after everything else.

The detail now windows activity with the messages, and main decides it where the store is. It decides a turn at a time. A turn's anchors are the messages its records followed and its own ID when that names a message. A turn with an anchor among the loaded messages is inside the window. A turn whose anchors the store holds, but not in the window, is above it: it waits with its messages and is given again when Show earlier messages reaches them. A turn the store knows nothing of is given, and the pane places it as before. The live turn is always given: the turn of the latest running turn record or, with none and the thread running, the turn of its newest record. A stray running record, such as a re-read tool call with no result, does not make an old turn live. A thread no pane is looking at holds no messages, so its detail carries only its live turn.

This is a view for the detail alone. The activity store, the sidebar summary, the adapters' activity handoff and `workspace.json` keep every record. The cost is one indexed lookup per anchor the pane has not asked about before, cached per watched thread until a reset, a failed write, a store switch or the pane closing. It is never a read of the whole thread, so opening a pane still costs its window.

## Amendment: no messages for a subscriber that keeps history from events (September 26, 2026, #322)

The owned activity publication above shares activity trees but still copied messages. Every native adapter emit copied every held thread's messages four times: the message log's `structuredClone` of the held window, the adapter's own `cloneActivitySnapshot`, and the provider switch's copy on acceptance and again on publication. A held thread (`CONTEXT.md`) is one whose messages the adapter keeps in memory: it is in the watched set or its provider session is open. The reaper keeps an idle session for thirty minutes, so during a working session that is most of them. The workspace then discarded every copy: a host that publishes thread events has already said what each thread said, and the workspace keeps history from those events, not from the snapshot. The switch's slot also retained its copy between emits.

Now a subscriber that keeps history from those events says so, with `historyFromEvents` on `subscribeActivitySnapshots`, and an adapter that publishes `subscribeEvents` hands that subscriber every thread the way it hands over a thread nobody is watching: an empty `messages` array and its summary from the log's own facts, whether or not the messages are in hand. The workspace asks whenever its host publishes events. The provider switch passes the request on to a provider only when that provider publishes events, every one of the switch's activity subscribers made it, and nothing reads its ordinary `subscribe`. It asks again whenever a subscriber comes or goes, and when messages are wanted again it reads each connected provider afresh, since what they last published carries none. A subscriber that does not ask, such as a coordinator wired straight to an adapter in a test, still gets the messages, and so do the adapters' public `snapshot`, `connect`, `refreshThread` and command results (narrowed for the workspace by the #368 amendment below). The switch's own `connect` is not one of those: for a provider already connected it returns what that provider last published, which for the workspace carries no messages, and the workspace reads none from it. Nothing is put away by this: the watched set, pinning and the reaper decide what the log holds exactly as before, and the workspace's own snapshots, which the coordinator reads, are unchanged.

With eight held Claude threads of 1,001 messages each, one emit through the adapter, switch and workspace fell from about 11 ms to about 0.2 ms, and the retained heap by about 9 MiB (`docs/perf/2026-09-26-snapshot-cloning.md`).

## Amendment: no messages in a thread refresh or settings result for the workspace (September 27, 2026, #368)

The amendment above left the messages in the adapters' public snapshot, and so in a thread refresh and in the snapshot a confirmed settings change hands back. The workspace reads both and discards their messages, as it discards an activity snapshot's: it keeps history from events. With eight long held threads each of these still copied every held history in the adapter, and the provider switch copied it twice more on the way, on acceptance and in the aggregate it returns. The coordinator reads the thread before every send, so this was on the send path.

Now a caller that keeps history from events says so for these too: `historyFromEvents` on the `ThreadReadPurpose` a refresh carries, and on the `configure-thread` command. An adapter that publishes events then hands back every thread the way it hands an activity subscriber that asked: its summary, no messages, and shared activity trees. The workspace asks whenever its host publishes events and never otherwise, whatever its own caller asked. The provider switch passes the request on only when its activity subscription to that provider asked the same, because what a read hands back becomes the provider's slot, which every subscriber is published next; otherwise it asks for the messages. If a subscriber that reads messages arrives while a result without them is on the way, the switch reads the provider whole and takes that in instead. Every other reader leaves the option unset and gets the messages as before: a coordinator wired straight to an adapter, an adapter's reads of its own threads, personal chats, and every adapter contract case but the two that check the option. No adapter's refresh loads an earlier window: Show earlier messages widens the workspace's window from its own store, which this does not touch. The adapters' `connect` and `snapshot` still carry the messages, and so do the switch's project checks in `create-thread`, which read `snapshot`.

The option never crosses the host socket. A remote host runs its own workspace over its own provider switch in one process, and the socket carries coordinator commands, so the protocol is unchanged and an older host needs nothing.

With eight held Claude threads of 1,001 messages each, the copies a refresh makes on its way to the workspace fell from about 14-17 ms to about 0.2 ms and a settings result's from about 12-13 ms to about 0.1 ms, and what the switch hands the workspace from 8,083 objects to 98 (`docs/perf/2026-09-27-workspace-results-without-history.md`).


## Amendment: retry failed event batches (September 27, 2026, #378)

A workspace removes a pending event batch only after its SQLite transaction commits. Later events for the same thread join behind it; another thread can still commit. A failed batch has its own warning, independent of organization saves. Retry starts after one second and doubles up to thirty seconds while storage remains unavailable, so streaming and reads cannot turn a storage failure into a write attempt per chunk. A successful retry refreshes the thread's window even without a new provider event. Normal streaming keeps the same coalesced transaction boundary.

Shutdown makes a final attempt and reports failure if events remain; it cannot promise recovery across a restart while storage is still unavailable. Pending words are not put in another file. Turning retention off moves pending batches to the ephemeral store after durable redaction. Turning it back on discards any still-pending ephemeral batch before opening the durable connection, so words received while retention was off never reach disk through a retry.

A retry also checks the retention setting against its connection. If another store fails to redact before the history connection switches, pending words cannot enter that still-durable connection. Pending batches remember that retention was off; enabling it discards them even when the interrupted transition never reached the ephemeral connection.


## Amendment: corroborated duplicate receipts (September 29, 2026)

Codex can report one authored message under its live client identity and a native rollout identity. Removing the duplicate only from the adapter's held messages leaves it in the event-store projection. After restart, enough replayed user receipts fill the opening window and hide earlier replies even though their text is intact.

Record `message-aliased` with the duplicate and canonical message IDs when the adapter has exact, unambiguous native identity evidence. The projection removes the duplicate only when both saved receipts agree on role and text, and the duplicate carries no differing command or attachments. Original events remain; replaying them with the alias event reproduces the repaired view. This is identity repair, not a rewind, so it changes no history epoch or permission. Equal words alone never establish an alias. Codex applies the same proof before publishing rollout receipts and on opening an already affected thread.

This extends the event kinds above. `messages-reset` remains reserved for replacing a history epoch; using it for repair would overwrite unrelated or newer stored messages.


Both the adapter log and the projection use the same content comparison. Seeded identities alone cannot prove equality: repair reads just the two indexed saved messages, and leaves both alone if either is unavailable. The host exposes these events only to clients accepting `message-aliases`; other clients receive the corrected thread detail and a cursor advanced past the internal repair.


## Amendment: diagnostic turn records contain no text (September 30, 2026, #608)

The owner chose the privacy rule in AGENTS.md over the glossary's former description of content-bearing diagnostic turn records. `turns.jsonl` is diagnostic evidence, separate from thread history: it keeps event names, identities, outcomes, timing and context counts, never prompt, answer or error text, even with Keep local history on.

Before the coordinator starts, its recorder scrubs existing records through the current schema and atomically replaces the file. Unknown fields and malformed lines are discarded so old content cannot survive outside the schema. This runs once per recorder lifetime and rewrites only when needed, so an interrupted upgrade retries at the next start. A scrub retries temporary read and rewrite locks briefly. If reading or rewriting still fails, it deletes the diagnostic file. Only a failed deletion stops startup, with instructions to close apps using the file and restart. Failed records carry a fixed code from a closed set; no free-text reason is retained. Appends and bounded compaction share that recorder's write lane.
