# Sotto's own history, on an event store the host owns and a client reads

Amended October 6, 2026: standalone Chats was retired under ADR-0010. References below to personal-chat readers describe historical behavior; Sotto no longer opens or connects those conversations. Their retained Sotto copies still follow Keep local history: retirement preserves them while it is on, and local cleanup removes transcripts and submitted answers while it is off. The thread history, before-send checks, event-store decisions and beta gates remain in force.

Accepted September 19, 2026, so that a thread's history stops being something a provider is asked to rebuild, and so the same split serves a machine the user is not sitting at. Transport beyond loopback — which remote path ships first, and what the pairing flow looks like to the user — is left open for the owner to decide and is marked as open below.

Amended September 22, 2026 by ADR-0025: the owner decided both. SSH ships first, with the desktop pairing itself over the SSH session and a phone entering a code read on the host; the host listens on its own loopback address, reached through the SSH forward or Tailscale Serve, and the README's "Privacy and cost" section names that path. Everything else here stands.

## Context

Every message of every thread lives in one file. `WorkspaceHost` reads `workspace.json` at startup, holds the whole snapshot in memory, clones it on each publish and rewrites it on each save, so the cost of opening the app, of drawing the sidebar and of one streamed chunk all grow with everything the user has ever said. The 0.1.3 startup crash was that cost meeting a large file. Grok's uncapped history polling is the same shape from the other end.

Underneath it, the provider is treated as the history of record. Codex loads both registries at connect and reads a thread's turns when it is opened (ADR-0005 as amended), Grok calls `session/load` for every known alias at connect and then polls each one, and Claude spawns a CLI per observed thread and replays its transcript from the first byte unless a cursor and the messages that account for it are handed back together (ADR-0015). Sotto's copy exists, but as a cache the adapters are expected to be able to reconstruct. That is why a provider that loses a session loses Sotto's memory of the thread with it, and why reconnect work scales with history rather than with what happened while Sotto was away.

The next step is not a bigger cache. Sotto is heading for threads that run on a machine the user is not looking at, which needs a clean line between the part that owns providers, worktrees and history, and the part that draws a window. T3 Code already runs this way: its own event store, projections for reading, provider sessions resumed lazily, history read in windows, and no provider transcript replayed on reload.

`workspace.json` also holds organization that has nothing to do with history — projects, threads, creations, aliases, settled state — and that part is small, is genuinely Sotto's and is fine where it is.

## Decision

**Messages live in Sotto's own event store, and providers are read to append to it.** A single SQLite database, `threads.sqlite` in the user data folder, opened with `node:sqlite` the way the memory store already is (ADR-0003), behind `ThreadStore` in `src/main/agents/threadStore.ts`. Production dependencies gain nothing here (they are `zod` and, since ADR-0018, `node-pty`). The `events` table is append-only: `seq INTEGER PRIMARY KEY AUTOINCREMENT`, `thread_id`, `kind`, `at`, and a JSON `payload`. The first cut has five kinds. `message-added` is a new message. `message-text-appended` is a streaming message that grew by a suffix. `message-replaced` is a whole message that changed in a way an append cannot say. `messages-reset` is a confirmed rewind: the thread's history before that point is gone, and the event carries the new `historyEpoch`. `answer-given` is an answer to a permission request or a question, with its attribution. Nothing edits or deletes a row to change what happened; a rewind is an event like any other.

**A projection is what the renderer reads.** The `messages` table holds `(thread_id, position, message_id, role, text, created_at, command_id, attachments JSON)`, indexed by `(thread_id, position)`, and it is derived: it is rebuilt from the log only when it is missing or when the schema version moves. The two kinds of read the app makes are then both cheap. A window of history is an indexed range over `messages`. A client catching up is `ThreadStore.eventsAfter(seq, threadId?)` — everything after sequence N — which is how the window resumes after a reload and how a remote client will resume after a reconnection. The revision the thread detail already carries (`AgentThreadDetail.revision`) is the client-side counterpart it always was; the sequence number is the store's.

**`workspace.json` keeps organization only.** Threads, projects, creations and aliases stay; a thread's `messages` array stays in the schema and stays empty, so nothing downstream has to learn a second shape at once. A one-time migration on first start moves every message out of the snapshot into the store in `createdAt` then array order, and then rewrites the file without them. It is idempotent, so a half-finished run costs a repeat and not a duplicate, and a failure leaves `workspace.json` exactly as it was; the app then starts on the old path rather than starting empty.

**History is read in windows.** `ThreadStore.readMessages(threadId, { limit, beforePosition? })` returns the newest messages first: ten turns to open a pane, where a turn is a user message and the assistant messages that follow it, and twenty more per request after that. The detail the window receives carries `earlierAvailable`, and the pane offers a plain "Show earlier messages" control above the oldest message it holds. A thread with ten thousand messages costs the same to open as a thread with thirty.

**Memory follows the watched set.** `WorkspaceHost` holds messages in memory only for the threads in the watched set — what `observeThreads` already names: the threads on screen, plus assigned or queued ones. Every other thread carries its `summary` and nothing else, which is what the sidebar reads and what `agentShell` already publishes. Startup cost and publish cost therefore follow the panes that are open, not the total history, and the clone on each publish stops carrying the archive.

**Keep local history off is a property of the store, not a pass over its output.** With the setting off no message text is written at all: messages are held in memory for the run and are gone when Sotto quits, an ephemeral stream. Turning it off deletes every row of `messages` and redacts the `payload` of every message event down to its id and its timestamps, so the shape of what happened survives and the words do not. Turning it back on resumes writing from that moment. What was not kept is not recoverable, and that is the promise the setting makes.

**Adapters append; they do not rebuild.** Each adapter publishes deltas through one append path — `message-added` and `message-text-appended` — rather than handing up a rebuilt `messages` array: Claude from its transcript tail behind the cursor of ADR-0015, Codex from the app-server stream and from rollouts, Grok from its update cursor. Takeover detection is unchanged and is one of the sources these events come from. The snapshot the renderer draws is derived by the projection, and no adapter holds a full `messages` array for a thread outside the watched set. This supersedes the part of ADR-0015 that made `WorkspaceHost`'s cache the history of record between runs: the store is, and `restoreThreadHistory` is served from it. The cursor's own rule is untouched — it is trusted only beside the history it accounts for, and with Keep local history off there is no history to hand back, so the transcript is read whole.

**Provider sessions start when something needs them.** Connect starts no per-thread provider session. A session starts on the first command for a thread, or when the thread enters the watched set; this is ADR-0005's "resume a thread when it is opened" extended to Claude and Grok, and the exception ADR-0005 records stands, because a personal chat owns its own native request channel and has no other opening step. A session reaper sweeps every five minutes and stops a session idle for thirty minutes. It never stops one with a running turn, one with a pending request, one with a confirmed live monitoring task or confirmed background work (ADR-0023), or one in the watched set. Monitoring observations are ephemeral: keeping the session alive does not persist the watch or grant authority. The resume cursor is host state, kept where the adapter already keeps its alias, so a stopped session costs a resume and never a re-read. (November 1, 2026: for Claude Code, a thread entering the watched set no longer starts a session, and the reaper's exception is the live-session set; see the amendment of that date below.)

**An answer says who gave it.** Every `answer-given` event carries `{ clientId, user, transport }`, where `transport` is `ipc` for the desktop window on this machine or `socket` for a paired remote client. This is attribution, which is evidence of who answered and never authority in itself: policy records decide whether an answer counts as a grant (ADR-0004), and the local desktop window always may answer. The rule that the user answers every permission is unchanged; recording which client the user answered from is how that rule survives a second client.

**The host owns; the client reads.** The host is the process that owns the providers, the worktrees and the store. The client speaks only the event stream and commands, and holds no provider identity of its own — threads are addressed by Sotto thread ID either way (ADR-0002). Locally both live in this app: the host is Electron main, the client is the window, and the transport between them is the IPC the preload bridge already carries. Remotely, IPC first and a socket second. Beyond loopback the shape is the one T3 uses: a pairing flow that issues a client token, signed sessions over it, TLS through Tailscale Serve rather than a certificate Sotto manages, and an origin check on the local socket too. An SSH device host — a helper started on the remote machine over the user's existing SSH, inheriting its authentication and exposing no port — is the cheapest first remote step. **Which of those ships first, and what pairing looks like to the user, are open and are the owner's to decide.** Nothing here adds a listening socket; the first change that does is a README "Privacy and cost" change before it is a patch.


## Considered options

- **Keep `workspace.json` and split it per thread.** Smaller files, and the same two problems: a thread still rewrites its whole file on every chunk, and history is still a cache the providers are expected to be able to rebuild.
- **One append-only JSONL file per thread.** Appending is cheap and the format is readable, but there is no indexed read: a window of the last ten turns means scanning to the end, and the projection is a rescan on every open. The rewind and redaction rules would each need a compaction pass of their own.
- **Leave the provider transcripts as the source of truth.** What exists today. Cost grows with history on every connect, a provider that loses a session loses Sotto's memory of the thread, and a remote client would have to reach the providers rather than the host.
- **A third-party event store or an ORM.** Sotto's production dependencies are `zod` and `node-pty` (ADR-0018); `node:sqlite` is already the memory store's engine, already proven in the packaged runtime, and adding a runtime dependency would be an ADR of its own before it was a schema.

## Consequences

Opening the app costs the watched set. Opening a pane costs ten turns. Reconnecting costs what was appended while Sotto was away, and reloading the window costs everything after a sequence number. None of those grow with the archive, which is the point.

The store becomes the thing whose loss matters: losing `threads.sqlite` loses history Sotto can no longer ask a provider to rebuild, so backup and repair of that file are real work rather than an afterthought, and the migration is written to fail safe because the snapshot it reads from is the only other copy. ADR-0015 is amended rather than reversed — its cursor rule survives, its claim about where the history of record lives does not.

Two details settled in implementation. The `answer-given` event carries no answer text: an answer can read like a prompt, so the record is the request, the choice, a question's chosen option ids and the client, and the schema's `answer` field is left optional for the events already written. Chosen option ids may contain the provider's option labels, so forgetting a thread or turning Keep local history off removes them along with any legacy answer text; attribution remains. And "policy records decide whether an answer counts as a grant" became `Authority.mayGrant(client)`, answered from a `remote-answer` policy record scoped `client:<clientId>`; the local window always may, and a record scoped `global` is not an answer about any one client. The host/client boundary shipped as `HostService`, pairing records and tokens shipped without a listener, and the pairing UX and the first remote path remain the owner's open decisions.

Four implementation tickets hang off this: the store and its migration, windowed reads and the pane control, lazy sessions with the reaper, and attribution on answers. The host and client split is already true locally the day the store lands, which is what makes the remote step a transport decision rather than a rewrite.

Amended September 20, 2026 (ordinary saves moved to `synchronous=NORMAL` on October 19, 2026; see that amendment): the store explicitly keeps WAL with `synchronous=FULL`. Provider transcript cursors are saved independently of the event store, so a cursor that survives a power loss could skip messages lost from a less durable store. Every committed event, including answers and migrated history, keeps the same durability. Prepared statements are reused for the life of the connection to avoid compiling them on each read and streamed update; closing the connection drops them.

## Amendment: bounded Devin native replay (September 20, 2026, #150)

Devin CLI 3000.10.31 has a verified ACP session/load replay but no verified incremental transcript cursor. Its prompt response reports completion, so Sotto also needs replayed dispatch identities to confirm delivery without resending uncertain work. Devin is an explicit exception to this ADR's native resume-without-re-reading and incremental reconnect-cost guarantees. Sotto keeps its own event store as the history of record and preserves windowed renderer reads; those guarantees do not depend on Devin replay speed.

The adapter reads native history within a 16 MiB text limit and a 20,000-message limit. UUID identities deduplicate replay against the event store, and only observed changes are appended. Watched idle threads are checked every fifteen seconds; running turns and pending requests use a shorter cadence. Explicit refresh and send request a fresh history check, sharing one already in progress. Lazy per-thread startup and the session reaper remain unchanged.

Native resume, reconciliation, and polling therefore cost a bounded read of the provider transcript, not only its new tail. A long Devin thread can take longer to reconnect or send to. If native history exceeds the supported limit, Sotto refuses that read and cannot safely reconcile or continue the thread through Devin; saved Sotto history remains readable, and uncertain work is never resent automatically. The limit is a safe refusal, not a claim that only the newest part was read.

Since October 6, 2026 (#770), some of the above has changed for a thread whose Devin session Sotto already holds. A send replays nothing before its prompt unless an earlier dispatch is still unconfirmed, and an explicit refresh replays only then. Its acceptance can come from the session's own stream before any replay shows its dispatch identity, which weakens delivery evidence in that one respect: the replay confirms the dispatch afterwards, and one that contradicts it refuses the next send rather than making the accepted send uncertain. A running turn is read at the shorter cadence only until its stream shows Devin took the prompt, and a pending request no longer shortens it. The read limit is therefore met at the next replay read rather than at every send, so it can stop a thread a prompt or two later. Opening a session, reconnecting, the poll of a watched thread and reading a session Sotto does not hold still replay it whole. See [ADR-0017's amendment](0017-devin-native-provider-data-policies.md#amendment-a-send-checks-once-and-reads-nothing-while-sotto-holds-the-session-october-6-2026-770).

This exception accepts a verified protocol limitation instead of inventing a cursor. Apart from the #770 change above, which takes a held session's own stream as the first evidence that Devin took a prompt, it does not weaken delivery evidence. It does not change history retention, permission authority, or provider data policies. See the [native compatibility evidence](../verification/2026-09-19-devin-native-compatibility.md) and [Devin data-policy decision](0017-devin-native-provider-data-policies.md).


## Amendment: incremental activity persistence (September 20, 2026)

Retained thread activity moves out of `workspace.json` into indexed rows in the same `threads.sqlite`. The previous message migration left activity output in the organization snapshot; one small provider update still copied and rewrote the entire archive. Activity keeps its existing bounded timeline, ordering, IDs, nested output and history-epoch behavior. Changed records are upserted, missing records are removed, and unchanged records require no JSON encoding or database transaction. This is a retained observation table, not a change to the append-only message event protocol.

Legacy JSON activity is imported before the JSON copy is removed. A committed SQLite list and its epoch take precedence if an interrupted save leaves both copies; legacy activity is imported only when no committed list exists. An explicit marker preserves the distinction between an observed empty list and missing activity evidence, including an unversioned list. Stale legacy messages from a different epoch are not relabeled and re-imported. A failed activity migration keeps the legacy copy available and reports the storage problem. WAL and `synchronous=FULL` remain unchanged. Organization JSON remains an atomic, ordered save; an identical value is skipped only against the last successfully completed save.

Keep local history governs activity too. Turning it off scrubs durable output and continues the current view in memory. Hashes of erased thread/activity identities are retained without text, so re-enabling history or replaying a provider cannot restore erased activity. New activity identities may be retained after history is enabled again. Migration, replay, restart and privacy transitions are regression-tested.

Internal provider and workspace snapshots still isolate mutable objects and arrays for their consumers. Their plain-data copy preserves immutable string values instead of serializing large output strings again. This changes copy cost, not the renderer transport, history window, permission behavior or user-visible timeline.

### Amendment: owned activity publications (September 23, 2026)

An optional internal `subscribeActivitySnapshots` path shares deeply immutable activity trees through the native adapter, Sotto identity wrapper, provider switch, workspace and coordinator. All other snapshot containers remain isolated per consumer. Public `snapshot`, `workspaceSnapshot` and ordinary `subscribe` results still give callers independently writable activity copies. IPC and socket formats, display cadence and immediate command/permission behavior are unchanged.

The ownership module copies unowned input before recursively freezing it. It certifies only the objects it owns; a caller's shallow-frozen array or unchanged mutable array identity is not evidence. An adapter installs the owned array and its projectors replace changed records/arrays. Already-owned descendants can be shared when a new array is installed. The certificate is held in a weak set and is never serialized, persisted or interpreted as authority.

The workspace treats a certified array as an activity revision, reuses unchanged merged history and merges only changed input records. A different epoch, replacement of the held result, legacy mutable input or privacy transition forces reconciliation. Status, requests, usage, provider connection state and time-dependent background work still pass through on every snapshot; unchanged activities do not suppress those changes. Branch-movement and activity-summary work follow activity changes independently of message text.

The activity store may skip a certified revision only after a successful save, with the same activity epoch, message-reset sequence and redaction generation. A failed transaction remains eligible for retry. Closing or replacing the store clears its successful-input cache; redaction invalidates it. SQLite durability and all history-off rules remain unchanged. The older copy/reconcile path remains valid for hosts without the optional subscription.

## Amendment: retained subagent observations (September 20, 2026, #124)

The Agents view keeps an indexed observational roster and each child's assignments in a separate `subagents.sqlite`, owned by `WorkspaceHost` and read through a main-window-only preload bridge. This supplements the message event store; these records are provider observations rather than message events or permission grants. The separate projection avoids coupling its migration and privacy lifecycle to the message event log. Child identities remain display-only adapter identities under a Sotto thread ID (ADR-0002). Subagent task and result text stays in this store alone. The ordinary activity store and its JSON migration fallback retain only text-free task classification and observational identities. Legacy child tasks are retained in the roster before that classification replaces their activity payload. The history source also supports an indexed lookup by activity identity, so a late Claude completion remains recognizable even when its start has left the bounded activity window before restart. These lookups preserve the thread-ID mapping and epoch checks from the cursor handoff; no archive is loaded at startup.

The general activity stream retains 2,000 records and can contain several tool actions for one child. Deriving the roster from that stream on every render would both double-count agents and silently lose earlier assignments. A normalized child observation instead updates its own indexed row and assignment; the thread snapshot carries only small current counts. Initial reads return at most 50 agent rows; assignment details return ten tasks per page. A changed row travels separately from older history. Renderer caches and live updates are bounded, and explicit paging is the only way to read more history.

The store deduplicates observations, preserves spawn order and earlier assignments when an agent is reused, and keeps late results on their own assignment. A parent/tool finishing cannot finish its child. Restart and disconnection mark working children uncertain; only fresh provider evidence restores the working indicator. Reported model metadata is displayed as supplied, and missing models stay missing rather than inheriting an assumed parent model.

Keep local history governs this store too. With it disabled, observations use an in-memory database. Disabling it deletes the durable roster and tasks, checkpoints the WAL and clears free pages; enabling it starts retention for fresh assignments. A separate indexed table keeps only SHA-256 hashes of erased observational identities, so provider replay cannot restore deleted words after a restart. Explicit history changes preserve generic unfinished status and text-free classification/aliases for those current assignments, allowing late completion and reuse after restart without restoring erased words. An erased assignment remains text-free even if it later reports a result; a reused agent needs a fresh assignment identity to retain new text. No new host is contacted, no title-generation model is invoked, and none of these observations can answer a permission request.

The activity snapshot also records the sequence of the latest committed message reset. On restart, the committed message generation outranks older activity or organization JSON; mismatched activity is discarded rather than relabeled. An indexed reset lookup distinguishes no reset from an explicit unversioned reset, including resets that leave no messages. This protects recovery when message events commit before activity synchronization finishes.

## Amendment: activity windowed with its messages (September 22, 2026, #257)

A thread detail carries a window of messages but used to carry every activity record the thread keeps. A record whose message was above the window had nowhere to go, so the pane drew it under the newest answer. The renderer could guess from first-observed order which turns were older, but a provider that reads its history again after a restart hands back old records the store no longer held, and they are numbered after everything else.

The detail now windows activity with the messages, and main decides it where the store is. It decides a turn at a time. A turn's anchors are the messages its records followed and its own ID when that names a message. A turn with an anchor among the loaded messages is inside the window. A turn whose anchors the store holds, but not in the window, is above it: it waits with its messages and is given again when Show earlier messages reaches them. A turn the store knows nothing of is given, and the pane places it as before. The live turn is always given: the turn of the latest running turn record or, with none and the thread running, the turn of its newest record. A stray running record, such as a re-read tool call with no result, does not make an old turn live. A thread no pane is looking at holds no messages, so its detail carries only its live turn.

This is a view for the detail alone. The activity store, the sidebar summary, the adapters' activity handoff and `workspace.json` keep every record. The cost is one indexed lookup per anchor the pane has not asked about before, cached per watched thread until a reset, a failed write, a store switch or the pane closing. It is never a read of the whole thread, so opening a pane still costs its window.

## Amendment: no messages for a subscriber that keeps history from events (September 26, 2026, #322)

The owned activity publication above shares activity trees but still copied messages. Every native adapter emit copied every held thread's messages four times: the message log's `structuredClone` of the held window, the adapter's own `cloneActivitySnapshot`, and the provider switch's copy on acceptance and again on publication. A held thread (`CONTEXT.md`) is one whose messages the adapter keeps in memory: it is in the watched set or its provider session is open. The reaper keeps an idle session for thirty minutes, so during a working session that is most of them. The workspace then discarded every copy: a host that publishes thread events has already said what each thread said, and the workspace keeps history from those events, not from the snapshot. The switch's slot also retained its copy between emits.

Now a subscriber that keeps history from those events says so, with `historyFromEvents` on `subscribeActivitySnapshots`, and an adapter that publishes `subscribeEvents` hands that subscriber every thread the way it hands over a thread nobody is watching: an empty `messages` array and its summary from the log's own facts, whether or not the messages are in hand. The workspace asks whenever its host publishes events. The provider switch passes the request on to a provider only when that provider publishes events, every one of the switch's activity subscribers made it, and nothing reads its ordinary `subscribe`. It asks again whenever a subscriber comes or goes, and when messages are wanted again it reads each connected provider afresh, since what they last published carries none. A subscriber that does not ask, such as a coordinator wired straight to an adapter in a test, still gets the messages, and so do the adapters' public `snapshot`, `connect`, `refreshThread` and command results (narrowed for the workspace by the #368 amendment below). The switch's own `connect` is not one of those: for a provider already connected it returns what that provider last published, which for the workspace carries no messages, and the workspace reads none from it. Nothing is put away by this: the watched set, pinning and the reaper decide what the log holds exactly as before, and the workspace's own snapshots, which the coordinator reads, are unchanged.

With eight held Claude threads of 1,001 messages each, one emit through the adapter, switch and workspace fell from about 11 ms to about 0.2 ms, and the retained heap by about 9 MiB (`docs/perf/2026-09-26-snapshot-cloning.md`).

## Amendment: no messages in a thread refresh or settings result for the workspace (September 27, 2026, #368)

The amendment above left the messages in the adapters' public snapshot, and so in a thread refresh and in the snapshot a confirmed settings change hands back. The workspace reads both and discards their messages, as it discards an activity snapshot's: it keeps history from events. With eight long held threads each of these still copied every held history in the adapter, and the provider switch copied it twice more on the way, on acceptance and in the aggregate it returns. The coordinator reads the thread before every send, so this was on the send path.

Now a caller that keeps history from events says so for these too: `historyFromEvents` on the `ThreadReadPurpose` a refresh carries, and on the `configure-thread` command. An adapter that publishes events then hands back every thread the way it hands an activity subscriber that asked: its summary, no messages, and shared activity trees. The workspace asks whenever its host publishes events and never otherwise, whatever its own caller asked. The provider switch passes the request on only when its activity subscription to that provider asked the same, because what a read hands back becomes the provider's slot, which every subscriber is published next; otherwise it asks for the messages. If a subscriber that reads messages arrives while a result without them is on the way, the switch reads the provider whole and takes that in instead. Every other reader leaves the option unset and gets the messages as before: a coordinator wired straight to an adapter, an adapter's reads of its own threads, personal chats, and every adapter contract case but the two that check the option. No adapter's refresh loads an earlier window: Show earlier messages widens the workspace's window from its own store, which this does not touch. The adapters' `connect` and `snapshot` still carry the messages, and so do the switch's project checks in `create-thread`, which read `snapshot`.

The option never crosses the host socket. A remote host runs its own workspace over its own provider switch in one process, and the socket carries coordinator commands, so the protocol is unchanged and an older host needs nothing.

With eight held Claude threads of 1,001 messages each, the copies a refresh makes on its way to the workspace fell from about 14-17 ms to about 0.2 ms and a settings result's from about 12-13 ms to about 0.1 ms, and what the switch hands the workspace from 8,083 objects to 98 (`docs/perf/2026-09-27-workspace-results-without-history.md`).


## Amendment: retry failed event batches (September 27, 2026, #378)

A workspace removes a pending event batch only after its SQLite transaction commits. Later events for the same thread join behind it; another thread can still commit. A failed batch has its own warning, independent of organization saves. Retry starts after one second and doubles up to thirty seconds while storage remains unavailable, so streaming and reads cannot turn a storage failure into a write attempt per chunk. A successful retry refreshes the thread's window even without a new provider event. Normal streaming keeps the same coalesced transaction boundary.

Shutdown makes a final attempt and reports failure if events remain; it cannot promise recovery across a restart while storage is still unavailable. Pending words are not put in another file. Turning retention off moves pending batches to the ephemeral store after durable redaction. Turning it back on discards any still-pending ephemeral batch before opening the durable connection, so words received while retention was off never reach disk through a retry.

A retry also checks the retention setting against its connection. If another store fails to redact before the history connection switches, pending words cannot enter that still-durable connection. Pending batches remember that retention was off; enabling it discards them even when the interrupted transition never reached the ephemeral connection.


## Amendment: corroborated duplicate receipts (September 29, 2026)

Codex can report one authored message under its live client identity and a native rollout identity. Removing the duplicate only from the adapter's held messages leaves it in the event-store projection. After restart, enough replayed user receipts fill the opening window and hide earlier replies even though their text is intact.

Record `message-aliased` with the duplicate and canonical message IDs when the adapter has exact, unambiguous native identity evidence. The projection removes the duplicate only when both saved receipts agree on role and text, and the duplicate carries no differing command or attachments. Original events remain; replaying them with the alias event reproduces the repaired view. This is identity repair, not a rewind, so it changes no history epoch or permission. Equal words alone never establish an alias. Codex applies the same proof before publishing rollout receipts and on opening an already affected thread.

This extends the event kinds above. `messages-reset` remains reserved for replacing a history epoch; using it for repair would overwrite unrelated or newer stored messages.


Both the adapter log and the projection use the same content comparison. Seeded identities alone cannot prove equality: repair reads just the two indexed saved messages, and leaves both alone if either is unavailable. The host exposes these events only to clients accepting `message-aliases`; other clients receive the corrected thread detail and a cursor advanced past the internal repair.


## Amendment: diagnostic turn records contain no text (September 30, 2026, #608)

The owner chose the privacy rule in AGENTS.md over the glossary's former description of content-bearing diagnostic turn records. `turns.jsonl` is diagnostic evidence, separate from thread history: it keeps event names, identities, outcomes, timing and context counts, never prompt, answer or error text, even with Keep local history on.

Before the coordinator starts, its recorder scrubs existing records through the current schema and atomically replaces the file. Unknown fields and malformed lines are discarded so old content cannot survive outside the schema. This runs once per recorder lifetime and rewrites only when needed, so an interrupted upgrade retries at the next start. A scrub retries temporary read and rewrite locks briefly. If reading or rewriting still fails, it deletes the diagnostic file. Only a failed deletion stops startup, with instructions to close apps using the file and restart. Failed records carry a fixed code from a closed set; no free-text reason is retained. Appends and bounded compaction share that recorder's write lane.

## Amendment: stored activity (October 10, 2026, #918)

The September 22 amendment said the activity store, the sidebar summary, the adapters' activity handoff and `workspace.json` keep every record. The store still keeps every record and `workspace.json` none, but memory no longer holds them for a thread nobody is looking at. On the owner's machine that was 2,000 records for each of 196 threads, about 108 MB, held whether a thread was ever opened or not.

At start the workspace reads each thread's activity marker, reset sequence and record count, not its records. A thread whose records are only in the store has stored activity (`CONTEXT.md`). Its records are read back into memory when a window observes the thread, before the observation reaches its provider, and when its provider publishes a record that is new or changed for it; a record still running in the store becomes unknown, as the eager start-up read made it. They are let go again after a save that succeeded, once no window is looking at the thread and nothing in it is running. A thread leaving view asks for that save, and a release is published, so the coordinator lets go of the lists it was handed too. What the workspace keeps to recognise a provider publishing the same list again is that list only while the provider is still publishing it, so it holds nothing the provider does not. Before any window has said what it shows, every thread counts as in view and nothing is let go, but nothing is read back on that basis either.

One start reads every record as starts used to: the first after this change, or on any store that has not yet recorded `subagentWordsMoved` in its `meta` table. Before the September 20 roster amendment a subagent record kept its task's words in the activity table, and reading the records in at start is what moves those words to the roster and saving them back is what strips them. The store records the move after that start's first successful save, and every later start reads none. That start reads only the threads it shows, so a thread it did not, such as a Watcher thread hidden then, can still have words in its rows; whenever records are read back, any subagent record still carrying words goes to the roster first, the way that start moved them. On the archive-startup benchmark at 200 threads, the records read at start fell from 20,000 to none and the heap retained after start from 32.8 MB to 1.4 MB (`docs/perf/stored-activity.md`).

A stored thread's list is never saved, so the whole-list sync cannot remove its records. Its provider publishing no list, an empty list or the same certified list as when it was let go leaves it stored. Anything else reads the stored list back and merges onto it, so each record keeps its sequence, its anchor and a finished state; merging onto nothing would renumber them. A new history epoch still replaces the list. The sidebar counts a stored thread's records from the store's marker, and it has no running turn by the rule above. A Git refresh compares new records with the list read back, not with nothing. A thread is let go only while the store holds its list as this run shows it: a live subagent record still carrying its task's words, which the store keeps only the classification of, keeps the thread in memory.

The adapters' handoff reads a stored thread's records from the store without keeping them, mapped as above. `hasActivities` says whether the handoff would answer for a history epoch without reading a record, which is what Claude now resumes its cursor on (ADR-0015, October 10 amendment). Once a read of the store has failed it says no, the failed read turns saving off as a failed start-up read does, and the user is told that the activity could not be read. Claude reads the records through the handoff the first time something changes that thread's activity, so it holds records only for threads that changed this run, where it used to copy every saved thread's at connect and publish them back on every emit.

Turning Keep local history off erases a stored thread's records with the rest of the file. They are not read back first, so this run shows none for that thread until its provider brings them again, as a thread out of view has no messages after the switch; their identities are suppressed like those held in memory. Records let go while history is off sit in the in-memory store and are gone when it is turned back on, as that run's messages are.

A detail read for a thread no window has observed, such as a remote client's before it observes, carries no records for a thread that is not running; the September 22 view already gave such a thread only its live turn once anything had declared. A send's first-output baseline taken from a thread that is not open counts records read back later as new, which only moves a timing mark. A send waiting in the outbox observes its thread first; a babysitting wake-up, which stays out of the watched set, can mark its first output early.

## Amendment: saves do not wait for the disk (October 19, 2026)

Zach decided this: the thread store (`threads.sqlite`), the usage store (`usage.sqlite`) and the sub-agent store (`subagents.sqlite`) keep WAL and save at `synchronous=NORMAL`. That accepts a small loss on a power cut so that saves no longer wait for the disk. `secure_delete` and foreign keys are unchanged. This replaces the September 20 amendment's FULL for ordinary saves. The sub-agent store set no level before, so it ran at SQLite's default, FULL. All three take the level from `SAVE_SYNCHRONOUS` (`src/main/storage/sqliteDurability.ts`), and the desktop and the headless host open the same stores.

The reason is main's thread, which is the window's UI thread. On a large synthetic thread store, every commit at FULL waited for the disk, and NORMAL roughly halves an ordinary commit's median (`docs/perf/2026-10-19-history-save-sync.md`).

**What a crash or a power cut can lose.** With WAL and NORMAL, a commit is written to the log but not flushed to the disk. Sotto quitting or crashing loses no commit, because the operating system still writes out what Sotto handed it; the appends still waiting for the 250 ms write window are lost as the October 13 amendment says. A power cut or an operating system crash can lose the commits made since the log was last flushed. SQLite flushes it at every checkpoint, which runs once the log reaches about 1,000 pages (4 MB), and Sotto flushes it at every removal the user asks for (below). So the loss is at most about the last 4 MB of saves (for the thread store, the October 23 amendment makes this typically about the last second, without a firm bound). While threads stream, that is a few seconds; when little is being written, it can stretch over a longer time. The database is never damaged: SQLite reopens it at the last flushed commit.

In Sotto's terms, what a power cut can take is the last moments of thread activity before it: streamed message text, answers, activity records, visuals and wake-up marks, with the usage records and sub-agent roster changes saved in those moments. The October 13 promise that answers and additions are durable before anything can act on them now holds against Sotto quitting or crashing, not against a power cut. A provider's transcript cursor is saved apart from this store. No cursor is saved past text the store has not committed, but a commit is no longer a flush, so a thread whose cursor survived the cut can skip the lost messages instead of reading them again. The provider's own transcript still has them.

**What the user takes out stays out.** A deletion that a power cut undid would bring back words the user removed. So every removal the user asks for commits at FULL (`flushedCommits`), and flushing the log flushes every commit ahead of it too. That covers forgetting a thread, turning Keep local history off (`redactAll` and the sub-agent erase), a redacted activity identity, a rewind's messages and visuals, and clearing usage. A rewind takes its turns out with a `messages-reset` event through the ordinary append, so any commit that carries a reset waits for the disk, whichever path wrote it. A rewind also takes out the thread's sub-agent tasks when the roster sees the new history epoch, so that commit waits for the disk too. Task words moved into the sub-agent roster, from records a save is about to strip of them (#918) or from `workspace.json`'s legacy activity, are the roster's only copy once the strip or the JSON write lands, so the roster is put on the disk before that save, with a commit that waits for it rather than a checkpoint a reader could hold back. The commit counts up a marker row, so it always writes and always flushes. When the roster cannot take the words or be put on the disk, nothing is stripped: that save writes every record to the store with its words, so new activity is still saved, and a thread leaves memory only once the store holds it as Sotto showed it. A roster that could not take the words keeps every save that way, and its warning up, until Sotto restarts; the next start moves the words again from the records it reads back. workspace.json keeps a failed migration's records with their task words, as it had them, until the roster can take them. The one-time move of a thread's activity out of `workspace.json` also waits for the disk before the flush that drops the records from the JSON file, so a power cut between the two cannot lose them. The scrub that follows a thread or sub-agent redaction already runs a TRUNCATE checkpoint, which flushes the log and the file; the FULL commit also covers a scrub that fails partway. While history is off, the sub-agent store's attached `privacy` file holds only erased identities and stays at SQLite's default, FULL. Removals Sotto makes on its own, such as a provider's refreshed activity replacing older records, save at NORMAL like any other save.

**Checkpoints stay where SQLite runs them.** (For the thread store, the October 23 amendment replaces this paragraph.) A worker thread that ran PASSIVE checkpoints on its own connection was built, measured and dropped. While threads stream, main commits in every publish window (16 ms), which is sooner than a checkpoint can flush a large file. So a passive checkpoint never catches up with the log, and the log never starts over: it grew past 18,000 pages (74 MB) in 2,000 commits. Catching up would take a FULL or RESTART checkpoint, which blocks main's next commit for the same flush, or a fallback to inline checkpoints during streaming, which is when the stalls happen. A commit that runs SQLite's checkpoint still holds main for about 80 to 115 ms at the median, roughly once every hundred commits; the perf note has the figures.

## Amendment: log checkpoints run off main (October 23, 2026, #1451)

The October 19 amendment left the thread store's checkpoints where SQLite runs them: inside the commit that grows the log past 1,000 pages. A one-minute profile of the owner's Owl build (0.1.38-owl.20261023.3) had main held for 1.19 s by one event commit in the middle of a publish, 1.08 s of it under the commit, against an 860 MB `threads.sqlite`. A synthetic store of that size and shape reproduced it: the commits that ran the checkpoint held main for 0.15 to 0.86 s, and for seconds while the disk was busy, against 0.3 ms at the median for the rest (`docs/perf/2026-10-23-checkpoints-off-main.md`).

The thread store's **log checkpoints** now run on a worker thread with a connection of its own (`walCheckpointer.ts`), and main's connection sets `wal_autocheckpoint=0`, so no save on main runs one. Half a second after its last checkpoint finished, the worker runs a PASSIVE checkpoint, which takes no lock a save waits for. The objection that dropped the first such worker, a passive checkpoint that never catches up while main commits in every publish window, is answered by a RESTART once the log holds 4,096 pages (16 MB): it holds main's next save only while it copies and flushes what the passive checkpoint just before it left, which puts the whole log in the file, so the save after it starts the log over. The RESTART needs the write lock, which each save holds for a moment, so it waits up to 10 ms for it, and when it still loses to the saves the worker tries again 2 ms later rather than a pass later. Answering busy at once, it lost to a steady stream of saves: on Linux, with saves back to back, two RESTARTs in three came back busy and the log reached 20,000 pages at a 200-page restart size; with the wait, one in twenty did and it peaked at 5,000 to 8,000. The wait itself costs main nothing, since the RESTART takes the lock only when no save has it. What main pays is the hold that follows, while the RESTART copies and flushes what the passive checkpoint left. That is the trade-off chosen: a save next to a RESTART waited 11 to 23 ms at the median and at most 37 ms on Windows, about a frame, and on Linux, under tens of thousands of saves a second, up to 35 to 180 ms. It happens at most once for every 16 MB saved, and it is not a bound. Where the worker cannot run, or goes, main's connection gets SQLite's automatic checkpoint back. The usage store and the sub-agent store keep SQLite's own.

What reaches the disk is unchanged, and so is how: saves stay at NORMAL, and a checkpoint still flushes the log before it copies and the file after it, on the worker now. A power cut can lose the saves made since the worker's last checkpoint began. That is typically about the last second while threads save, where it was up to the last 4 MB, but it is not a bound: the next checkpoint starts half a second after the last one finished, so while a slow checkpoint runs on a busy disk, newer saves can wait several seconds for their flush, and where the worker cannot run or has gone, SQLite's own checkpoint at 4 MB applies as before. Removals the user asks for keep their promise exactly: they commit at FULL on main, and their scrub runs its TRUNCATE checkpoint on main with the worker held aside, waiting out a checkpoint in flight; a scrub that still finds the log busy fails, and the removal is retried as a failed one, rather than leaving the words in the log. `secure_delete` is unchanged. Closing the store stops the worker and closes its connection first, so main's close is the file's last and checkpoints the log as before.

In a benchmark of streamed saves against a 555 MB store, the time main spent held by saves fell from 6.2 to 10.0 s to 2.2 to 3.7 s, and the worst save from 1.2 to 2.2 s to 0.65 to 0.85 s. Main still writes its saves to the log on its own thread, and on Windows a write waits while another thread flushes a large file on the same disk, so the worker's flushes still reach main now and then, in smaller and fewer pieces. Taking those waits off main means taking the saves off main, which this amendment does not do; neither does it stop a publish writing or read a stored thread's records off main. Those parts of #1451 stay open.

Subscribers stay the same. This was the draft's recommendation, because it is the narrower change.
2. **Each layer passes on only what changed (picked).** A publication names the threads that changed and the threads that went, and every layer and subscriber keeps its own map of thread records. It costs nothing per unchanged thread, not even a check, so the cost follows the change whatever the threads number. It is the wider change: every activity subscriber moves to applying changes. That covers the coordinator, usage, Watcher, delegation, the router, the host socket and the phone path.
3. **Fewer layers.** Fold the wrapper's ID binding and the switch's provider IDs into the adapter or the workspace. This removes two passes but keeps a new record per thread in the others. It moves Sotto's thread IDs inside the adapter boundary, against ADR-0002.
4. **Publish less often**, with a wider publish window. This is cheap, but it changes how streamed text feels, and a publish still costs what it does today.

**The decision.** The activity subscription carries **thread changes** instead of a whole snapshot each time:
- **A first publication is whole.** It starts the subscriber's map, as does any publication after a gap.
- **Every later one is a change.** It carries the threads upserted (whole frozen records), the thread IDs removed, and the rest of the snapshot (providers, catalog, projects, connection) only when it changed.
- **Changes are numbered.** Each publication carries a sequence number. A subscriber that sees a gap asks its publisher for a whole one rather than guessing.
- **Each layer keeps a map** of its own records by Sotto thread ID, applies what it receives, and transforms and passes on only the upserts and removals. The wrapper binds IDs, the switch names providers, the workspace merges, and the host stamp tags hosts.
- **Records are frozen and only ever replaced.** As the October 22 amendment made the workspace's records, every record is now frozen and shared across layers.

What does not change:
- `snapshot`, `workspaceSnapshot`, ordinary `subscribe` and command replies are built whole from the maps when asked, and stay independently writable copies.
- IPC and socket formats, the publish cadence, history and permissions are unchanged.
- Nothing a user sees changes.
- The window's broadcast already sends thread records by change (ADR-0028), and this feeds it the changes directly.

An adapter must know which threads changed. Every path that changes a thread's state marks the thread. Until an adapter marks its own, a shim at its boundary works the changes out by comparing each thread's record with the one it published last. That costs one check per thread, as option 1 would, and only that adapter's threads pay it.

**What it means for #1457.** Zach asked for #925 first, and option 2 is close to what #1457 needs:
- **The workspace already holds the change.** Each publish tells it exactly which threads changed, so its saves and event batch look only at those.
- **A store worker gets the changes as they are.** #1457 moves the thread store's writes off main, and the workspace can post it the upserts, removals and events unchanged. Moving the store off main then costs in proportion to the change.
- **A worker's list goes in as an upsert.** Opening a stored thread can read and parse its list on the worker and hand it back as an upsert of frozen records.

## Amendment: the store worker writes and reads stored threads back (October 26, 2026, #1457)

**Accepted October 26, 2026.** Zach picked these on October 26, 2026, and accepted this amendment the same day. The plan, with what main relies on today and the steps, is in `docs/plans/store-worker.md`.

The October 23 amendment took the log's checkpoints off main and left two parts of #1451 open. A publish still commits its events on main, inside `publishNow`: 0.65 s of a minute at 16:54 on October 23 (0.1.41-owl.20261023.5), and on Windows one save can still wait about 0.85 s while the checkpoint worker flushes a large file on the same disk. Opening a stored thread still reads and parses its whole activity on main: 0.61 s for one thread of 2,000 records, about 10 MB.

**One store worker writes.** A worker thread with its own connection to `threads.sqlite` makes every write: event batches, activity syncs and releases, visuals, wake-ups, message replacements, removals and the privacy switch. It also runs the log's checkpoints, so the October 23 checkpoint worker folds into it, and with no other writer its RESTART no longer waits for a save. Main's connection only reads. Main posts each write in order, and the worker commits them in the order posted, in the transactions they use today, then answers with what committed and what failed. Main holds every posted write in memory until the worker says it committed, as it holds a waiting batch today, and a failed one is retried as the September 27 amendment says. Two writers, with only the publish's events moved, was not picked: main's other saves would wait on the worker's write lock.

**What main reads straight after a write still sees it.** The publish lays every posted event over the stored message window and summary, as the October 13 amendment lays waiting appends today, so a publish never waits for the disk. A read whose caller is synchronous lays them on too: message identities, recorded user messages, a stored message's words and the handover; a single stored message (`message`) answers not yet while anything is held for its thread, as it does for a waiting batch today. A read whose caller can wait waits until the worker has committed what was posted for that thread, then reads: prompts, earlier turns, a visual being anchored, Watcher's read and Usage's import. An answer waits behind whatever its thread still holds, a batch in flight or a failed batch waiting for its retry, so it commits after the words it answers. A catching-up client's `eventsAfter` runs on every push and never waits: it answers with what has committed, and a posted event takes its sequence when it commits and reaches the client with the publish its confirmation brings (step 1, `docs/plans/store-worker.md`). The cursor gate keeps its promise: `flushEvents` resolves once the worker has committed what waited for that thread, so no provider cursor is saved past text the store has not committed. It does so whatever the `streaming-publish-cost` answer, so with it off a cursor is held back while a batch is held, where the October 13 amendment held none back.

**Durability.** Closing the store waits for the worker to commit everything posted before it stops, so quitting loses no commit. A crash takes the writes posted but not yet committed, typically the last publish window, because the worker is a thread of the same process. The October 19 amendment's "Sotto quitting or crashing loses no commit" becomes: quitting loses no commit, and a crash loses no commit the worker made. That widens the October 13 trade from streamed appends to every write in that window, bounded the same way: no cursor is saved past an uncommitted write, so the provider supplies those events again. Answers and rewinds stay durable before anything can act on them, because whatever acts waits for the worker's commit. Removals the user asks for commit at FULL on the worker and run their scrub's TRUNCATE checkpoint there, and the removal is reported done only once the worker says so. Saves stay at NORMAL, and what a power cut can lose is unchanged. Clearing a thread posts its forget and nothing of the thread after it, so nothing it said commits after the removal; words it still held go with it, and if the forget fails they are kept, with the thread.

**A stored thread's records are read on the worker, and its provider waits for them.** This changes the October 10 amendment (#918). When a window observes a stored thread, the worker reads its activity, parses each row and checks it against the schema, then hands the records back; main holds them as before. The observation of that thread reaches its provider only once they have arrived, where before they were read before the observation went at all, and other threads in the same observation go at once. A record the provider publishes for a thread whose list is still on its way waits and merges once the list arrives, so each record still keeps its sequence, its anchor and a finished state. The pane shows the thread's messages at once and its activity a moment later. The adapters' handoff still reads on main's connection, once per thread per run.

**Where the worker cannot run, or goes,** main opens its connection for writing and writes and reads back on main as before, and says so in the log by a stable event name.

**Step 2, the worker writes (October 26, 2026).** Building it settled what the amendment above left open:
- **A single message is laid over, not refused.** `message` reads the one message and lays over it what is posted for its thread, and what waits behind it; it answers not yet only while words wait that are not posted, behind a failed batch or a thread being cleared. A message's identities are laid over the same way, without reading the words. Codex aliases a rollout's duplicate by asking for the canonical message, and while its thread streamed it heard not yet, added the duplicate and showed it until the next reconcile.
- **One write of events per thread in flight.** An answer posted on its own holds the thread's next batch until it is confirmed, and so does a write of a host that publishes whole histories, which keeps what that host publishes meanwhile and compares it once the write is confirmed. They hold each other too: an answer waits behind a history write in flight, or one that failed until its retry lands, or the history held for its thread, whose write it follows; a history write waits behind an answer or a batch. A failed history write is compared again at the history retry, as a failed batch is, and a comparison that finds the store already holds it ends the failure. So nothing commits ahead of a write that failed, and main can tell what the worker committed before its confirmation arrives: it counts the thread's events past the newest it held when the first unconfirmed one was sent, in the same read transaction as the window, and lays only the rest.
- **Activity lists cross as changes.** A thread's list sent before goes as the order of its identities and the records that are not the same frozen record as last time; the worker rebuilds it from the list it last committed. A worker that lacks that list fails the save, and the next sends it whole.
- **Keep local history off.** The worker takes the file's words out, waiting for the disk, then closes it and stops; main goes on in memory without a second pass over the file, and writes this run there itself. Turning it back on starts a worker again.
- **When the worker goes.** Main finishes every write it had not answered, in order: one it had begun is looked for in the file first (events by counting them, a visual by its identity), and any other is applied again, since applying it twice changes nothing. Closing waits a minute at most from when it begins, the flush and the confirmations before the store closes included; what the worker has not answered by then is reported as not saved. A write main makes itself after the worker went, and SQLite's close, run to their end once begun.
- **Built on its own.** The worker is built as one file with everything it imports, beside main's bundle and the headless host's, so the thread store's code stays in the bundle that starts it.

**Step 3, the worker reads stored threads back (October 26, 2026).** Building it settled what the amendment above left open:
- **The list comes back in pieces.** Receiving a list is a structured-clone read on main, and 2,000 records of about 11 MB held main 8 to 9 ms in one piece on the development laptop, a cost that grows with the records' size. The worker hands it back 500 records at a time, and main asks for each next piece from a task of its own once the one before is in, so the window paints between them; a piece held main about 2 to 3 ms (`docs/perf/2026-10-27-store-worker-reads.md`). The worker reads the whole list first, so every piece comes from the file as it stood at the read.
- **The read waits only for writes main has sent.** It goes to the worker behind every write posted before it. While writes wait unsent, behind a privacy switch or the worker going, the thread is read on main at once, as before.
- **What a list on its way meets.** Each record the provider publishes for the thread meanwhile is kept, and merged onto the list in the order it came once the list arrives; the same array published again counts once. A window that stops looking meanwhile does not undo the read: the records are held when they arrive, as a read on main held them, until a save lets them go. A new history epoch's list, Keep local history turning off, or a clear that goes through lets the read go for good: it takes nothing when it arrives, and a later read of what the thread holds then starts afresh. A list that arrives while its thread is being cleared waits to hear how the clear went; one that fails keeps the thread, and the list is held with what was published behind it, as the clear promises. A list the worker cannot read is a failed read, as on main: saving activity stops and the notice says so. A worker that goes before the list is all back is waited out, while closing too: main finishes the writes it left, then reads the list itself.
- **Closing waits for a list on its way,** within closing's minute, so what the provider published behind it is in the last save.
- **The provider is told once for a batch.** It takes the whole observation each time, so it is told when no thread the window looks at has a list on its way: a window opening many stored threads tells it as it looks and once more when the last list is in, rather than once for each.
- **What stays on main.** A record the provider publishes for a stored thread no window is looking at, with no read on its way, still reads the list back on main, as do the adapters' handoff and the start's read of a profile whose subagent words have not moved.

## Amendment: the provider switch's reads share certified activity (October 30, 2026, #1645)

The October 24 amendment kept `snapshot` and every other whole result independently writable. The provider switch's
are the exception now. Its `connect`, `snapshot`, `refreshThread` and confirmed settings results share the activity lists
and the model catalog it holds certified, frozen, as its subscribers are handed them. Every thread record and every
other part is still the caller's own copy.

The read before every send went through `refreshThread`, and its deep copy of every thread's activity records reached
the workspace uncertified. The workspace then merged every record of every thread again and kept the result
uncertified, and the thread store's worker was sent those lists whole: with three long threads on screen, 76.6 MB for one
send (`docs/perf/2026-10-30-send-read-copies.md`). A caller that would change a returned activity list or catalog in place
now throws, as a subscriber always has. The only production caller, the workspace, builds new lists when it merges.
`snapshot` and `workspaceSnapshot` of the workspace, ordinary `subscribe` and command replies stay writable copies.

The workspace still reconciles every record a read brings, as it did when reads came as copies. Only a publication may
take the merge it gave last time for the same certified list; at the record limit that would keep a different set of the
oldest records. A read's record that comes out the same as the record held is the record held.

## Amendment: a background turn reads its thread's records on the worker (October 30, 2026, #1645)

This changes step 3's "What stays on main" above. A record a provider publishes for a stored thread no window looks at
now reads the thread's list back on the store worker, as a window's read does. The record waits, and is merged onto the
list once it arrives, in the order it came. Each merges as it did when the list was read on main at once: a record a read
brought reconciles whole, as a read's does, and only the same certified list published again counts once. A window's
read keeps its own rule, the same array counting once whatever brought it. Before, the list was read on main at once. That was every turn of a thread
run out of view: worker swarms, delegated threads, Watcher's workers and babysat threads. At the owner's scale it held
main about 12 ms a turn for a thread of 2,000 records (`docs/perf/2026-10-30-background-turn-readback.md`), and 0.61 s
in the owner's recording of one such read. Nothing about the thread waits on the list but its records, which no pane
shows. The other fields of what the provider published are taken in at once. While closing, and wherever the worker cannot
read, the list is still read on main at once, so the last save keeps what was published.

The worker keeps the list it read as the one it last holds for the thread. The thread's next save is sent as what
changed since then, rather than whole. A merge onto a list just read back gives each record that comes out the same as
the record read that record, as a read's merge does. A list saved, released or forgotten while a read is on its way
replaces what the worker keeps, so main does not send changes against that read. What the store keeps is unchanged:
each save still writes the list the workspace holds. The adapters' handoff, Watcher's recent activity and a start whose
subagent words have not moved still read on main.

## Amendment: Claude reads a transcript each second only while its thread is in use (October 30, 2026, #992)

Zach decided on October 29, 2026: check every second only threads open in a pane, working, or watched by Watcher. Every
other thread, settled or not, catches up when it is opened or sent to, with no slower sweep. A thread he comes back to
must not open slower.

Claude's adapter opened and read every saved thread's transcript every second, whether anyone used the thread or not.
At 132 saved threads that was 3.4 to 3.8 ms of main's CPU a second on forge, at 264 it was 7.1 to 7.6 ms, and #992
measured 18.8 ms at 132 on Windows (`docs/perf/2026-10-30-claude-transcript-poll.md`).

**The poll reads only the threads in use.** Each second it reads the transcript of each thread the coordinator observes,
which covers a pane, the active thread, a draft, Watcher's watched threads, a delegation, the follow-up queue and the
outbox. It also reads each thread that is working: a turn, a request waiting, a live watch, background work, a
compaction or a command mid-dispatch. And it reads each thread whose CLI did anything since the last tick, so a turn begun
and ended between two ticks is read too. A thread that leaves those is read once more on the next tick, so the last
lines of its turn land. A read that fails, or that finds the transcript and cannot open it, is tried again on the next
tick, as every read was, and one that keeps failing holds up no other thread's read. A transcript nothing was written to
since its last read is not opened: one stat says so.

**Every other thread catches up from its cursor.** Its transcript is read as soon as the thread comes into view, when it
is sent to, since a send reads the thread before anything else, and at connect, which still reads every saved thread
once. That connect read keeps each thread's transcript cursor current, so opening a thread reads only what was written
since. An untouched thread opens as before, reading nothing. One with work done in Claude Code outside Sotto reads that
work as it comes into view, and shows twenty such entries 2 to 4 ms later.

**What this changes for the user.** Work done in Claude Code outside Sotto on a thread nobody looks at, that Watcher does
not watch and that is not working, shows when the thread is opened or sent to, or at the next start, rather than within
a second. Sidebar rows of such threads show it then too. Nothing of it is lost. A send still reads the thread before it writes, so takeover refusal is unchanged. A
whole read of the adapter, which a send's read after the prompt asks for, still reads every transcript, as before. A
subagent's model, read from its own transcript, is read when its thread's transcript is. Codex's rollouts follow the same
rule, read on from a saved position (ADR-0005, October 30 amendment).

## Amendment: Claude Code starts when you type, send, or Watcher watches the thread (November 1, 2026, #992)

Zach approved this in the plan for the second performance round: "Claude Code starts when you start typing, send, or
Watcher watches the thread", with this ADR and ADR-0038 amended.

Putting a Claude thread on screen started its Claude Code CLI, because the decision above starts a session when the
thread enters the watched set, and a pane, the active thread and a draft are all in it. The reaper never stops a session
in the watched set, so a CLI behind a pane stayed for as long as the pane was open. Each Claude Code CLI is 104 to 308 MB
resident on forge (ps, October 31, 2026) and 270 to 295 MB on Windows (#992), so browsing ten saved threads held 1 to
3 GB (`docs/perf/2026-11-01-claude-start-on-demand.md`).

**A thread on screen is read, not started.** For Claude Code the watched set now decides only what it decides for memory
and reading: the thread's transcript is read as it comes into view and each second while it is observed (the October 30
amendment above), and its messages are held. It starts no CLI. A thread's CLI starts on any command for it (a send, an
answer, an interrupt, a settings change, a compaction, a rewind), on a read made before acting on it (a send's, a
review's, Watcher's), and when the user starts typing in its composer (ADR-0057's early start).

**The live-session set keeps a session running.** The threads Sotto sends to unasked or waits on keep a CLI, as the whole
watched set did: Watcher's watched threads, the threads a delegation follows, threads with a queued follow-up of the
user's (a waiting wake-up alone still keeps none, ADR-0061), threads with an outbox entry, and a send's own thread while
it is sent. `CONTEXT.md` has the term. The coordinator names the set to its host (`keepSessionsLive`) each time it names
the watched set, just before it, and each layer passes it on the way it passes the watched set, by its own IDs; the
workspace holds back a thread whose stored records are still on their way, as it holds back its observation. Claude
Code's adapter starts a CLI for each thread in the set, starts only these at connect, four at a time as before, starts
only these again after a client update (ADR-0038), and its reaper never stops one of them. Every thread in the set is
also observed, so its transcript is read as before.

**Other providers are unchanged.** Codex, Grok Build, Devin and the rest do not take the set and start a session for
every observed thread, as before. A Claude adapter that has not been told a live-session set, such as one a test drives
directly, keeps the old rule too.

**What this changes for the user.** Opening a Claude thread shows its messages as before and starts nothing. A CLI behind
a pane, started by typing or a send, stops after thirty idle minutes like any idle session; nothing on screen changes,
and typing starts it again. The cost is the first send to a thread that was opened and sent to without typing: it pays
the CLI's start inside the send, 1.0 to 1.5 s on Claude Code 2.1.289 (`docs/perf/2026-10-06-early-start.md`). Typing,
pasting and dictating into the composer all start the CLI early, because each is an edit of the composer; dictation does
so when its words land, so a send pressed straight after still waits for most of the start. A next prompt taken with Tab,
and words that Screenshot to message puts in the composer, are not edits and start nothing early. What the CLI says as
it starts now comes when the user types or sends rather than when the thread is opened: the user's own Claude Code hooks
and MCP servers start then, Claude Code's question about compacting an old session it resumes is asked then, and whether
the client offers manual compaction is learnt then; until it is, the pane offers Compact context, as it always did for a
thread nobody had opened.
