# A thread may delegate work to threads it starts

## Status

Accepted by Zach on October 14, 2026. It is built with #1029 (ticket E6). Zach settled the shape on October 14 in the Watcher engine ticket map (#1023): ordinary threads can start threads, sharing Watcher's starts limit, with the user's typing pausing it (decision 2), and later that day that delegation goes two levels deep (decision 11), and the word is **delegation**, with its **outcome** (decision 3). This record settles the rest. It amends [ADR-0073](0073-watcher-coordinates-threads-with-its-providers-own-tools.md)'s start authority and keeps [ADR-0004](0004-authority-in-policy-records.md) whole. It is an Owl feature ([ADR-0072](0072-sotto-owl-is-a-windows-preview-release-track.md)).

## Context

Zach already hands work from one agent to another by hand. The `code-review` skill runs `codex exec -s read-only`; `crew` runs `claude -p --resume` and `grok -p`. Sotto sees none of it. There is no thread to open, no request card when the second agent asks something, nothing stops when the first thread stops, and the results land in temporary files that only the first agent reads.

Watcher already starts and briefs threads under rules main enforces (ADR-0073): a Watcher request rooted in a user's message, a permission ceiling at the user's new-thread default, a computer-wide limit on new starts and four prompts per target per request. E2 gives each brief an outcome Watcher can read. This record lets an ordinary thread do a narrower version of the same thing, through the same machinery, instead of through a shell.

## Decision

**1. A scoped server, `sotto_delegate`, on ordinary Claude Code, Codex and Grok Build threads.** It joins the scoped thread tool servers ([ADR-0056](0056-an-agent-can-draw-a-visual-in-its-thread.md), [ADR-0061](0061-a-thread-can-babysit-its-pull-request.md)) on the same loopback transport, and offers three tools: `delegate`, `read_delegation` and `cancel_delegation`. Devin and Muse cannot attach Sotto's servers today, so their threads cannot delegate until [#1040](https://github.com/millZach/Sotto/issues/1040) and [#1039](https://github.com/millZach/Sotto/issues/1039) find a way; a request to do so is refused in plain words, as the browser and Watcher already are. The server is not offered to Watcher, which has its own tools, nor to a host setup thread or a provider job's thread, which have only their own job's tools.

**2. A delegated thread is an ordinary Sotto thread linked to the thread that started it.** It has its own Sotto thread ID (ADR-0002), its own pane, its own request cards and its own history. The link names the delegating thread by its Sotto thread ID and nothing else. It goes two levels deep. A delegated thread is offered `sotto_delegate` too, so it can hand work to a thread on any provider, such as a builder asking for a review on another provider. The threads it starts are not offered it, so they cannot start threads of their own.

**3. Authority stays in policy records.** The model passes no authority, and nothing a delegating thread sends approves anything (ADR-0004). Main attributes each call to the calling thread through the thread's tool token, which says which thread is calling and nothing more (`threadToolServer.ts`), and to the user's latest message to that thread, which plays the part a Watcher request's root message plays in ADR-0073. A wake-up turn keeps that message as its root and renews no budget (decision 5). A delegated thread's question or permission request reaches the user on its own card, answered only by the user; the delegating thread is told that the delegated thread is waiting and nothing more.

**4. The permission ceiling.** A delegated thread starts no wider than the narrower of the delegating thread's own permissions and the user's new-thread default, compared the way Watcher compares (`watcher.ts`, the permission check). Where the two cannot be compared, as with a provider profile that allows more than nothing, the start is refused in plain words and nothing is started. An explicit narrower choice is allowed when it can be compared. Sotto never widens a delegated thread's permissions afterwards; the user can, in the thread's own options, as on any thread.

**5. Limits.** A start takes a slot from the same starts-only limit Watcher's new starts take (ADR-0073's in-flight limit, per machine once E9 lands), so delegation adds no second budget. There are four prompts per delegated thread per turn of the delegating thread, counting the brief that started it; the turn is the one the user's message started, and the wake-up turns that follow it share its budget. Retries, reads, wake-ups and restarts renew neither budget. A full limit refuses with how many are in flight and starts nothing. Amended October 19, 2026 (#1183): Zach removed the starts-only limit, "if someone wants to spin up a ton of threads, that is on them", so a start takes no slot and nothing refuses one for how many are working. When more than ten threads are working on this computer after a start, counting the new one, `delegate`'s result carries `warning`, "11 threads are working. This computer may slow down or use its battery faster.", and the tool's description says to tell the user (ADR-0073, October 19, 2026, variant D). A retry with the same key returns the first delegation without it, since it started nothing. The four-prompt budget is unchanged. A refusal recorded as `IN_FLIGHT_LIMIT` before then still reads, in words that say Sotto no longer has the limit.

**6. Stopping and pausing.** Stop on a delegating thread, the user's or Watcher's, stops every delegated thread below it that is still working, at both levels, in the same press; Stop on a second-level thread stops only that thread. When the user types or sends in a delegated thread, delegated sends to it pause until the user's turn there ends, the way a standing watch pauses Watcher's sends. The user's draft, queue and turn are kept, and the pause shows as the delegation's outcome. Every delegated send carries the identity of the delegated thread's last user message that the delegating thread saw when it asked, as Watcher's `expectedLastUserMessageId` does; when the user has sent since, the send is refused as the target having changed (`TARGET_CHANGED`) and delivers nothing, so a send queued before the user's turn never lands on top of a newer instruction.

**7. Outcomes and results.** Each delegation has an outcome, as E2 defines it for Watcher's briefs: `working`, `background`, `answered`, `failed`, `stopped`, `paused` or `unknown`. A delegation main refuses as it is asked for has one more, `refused`: the permission ceiling, a full limit (before October 19, 2026), the second level, a thread that may not delegate (a provider that cannot take Sotto's tools, or a thread on another machine), a used-up prompt budget, the user's turn or newer message in the delegated thread, or a model not ready. It is recorded with the rule and its plain words, names no started thread, holds no start slot, charges no budget, sends nothing and is never news, since the call that asked was told; `read_delegation` and the window read it by its ID. A call whose arguments need correcting, a retry key used twice, or Sotto stopping refuses without a record, since the rules turned down no delegation. `read_delegation` returns the outcome and, once answered, the delegated thread's reply to that brief, labelled as that thread's words. When an outcome changes while the delegating thread is not waiting on it, the news reaches it as a wake-up through ADR-0061's follow-up queue, as a new news source carrying only identities: the delegation, the delegated thread, the turn and the outcome. The delegated thread's words travel only when the delegating thread asks for them with `read_delegation`. A restart leaves an unconfirmed outcome `unknown` and resends nothing (ADR-0058's outbox rules). During a run, a brief whose delivery was not confirmed holds its slot while the coordinator still holds its send unresolved, as Watcher's uncertain start does, and is `unknown` once nothing can prove it landed; a brief whose delegated thread is gone ends too. Either way the delegating thread is told. Amended October 19, 2026 (below): the news goes to the delegating thread's agent privately, carries an answered delegation's reply, and only that thread's own turn holds it.

**8. Waiting.** `delegate` may wait for the outcome up to a set time, so a short review can return in the same tool call. Codex's per-server `tool_timeout_sec`, which Sotto already sets for its scoped servers (`codex.ts`), bounds that wait on Codex; Claude Code and Grok Build get the same bound from Sotto's side. When the wait ends first, the call returns `working` with the delegation's identity, the delegated thread keeps working, and the result arrives later as a wake-up.

**9. Which model.** `delegate` names the kind of work (building, UI, code review, research, computer use). Once [#1041](https://github.com/millZach/Sotto/issues/1041) lands, Sotto fills in the provider, model, effort and permission from the worker roles in Settings, within the ceiling of decision 4; until then the call names them itself. Amended October 16, 2026 by [ADR-0091](0091-worker-roles-say-what-each-kind-of-work-starts-on.md): with worker roles on, a new delegation that names neither provider nor model starts on its kind of work's role, a role's permission is held to this ceiling rather than refused, and what the call names overrides the role for that delegation, as its result says.

**10. Where it runs.** A delegated thread starts on the delegating thread's own host by default. Once [#1032](https://github.com/millZach/Sotto/issues/1032) (E9) lands, `delegate` also takes a machine, defaulting to the setting E9 adds. Paired hosts take part only through an optional host-v1 feature, as Watcher's paths do; a host without it refuses before anything crosses the wire. Amended October 23, 2026 (below): `delegate` takes a machine or a system, and a delegated thread still starts only on This computer until #1316. Amended again October 23, 2026 (#1310, below): a thread on a headless host delegates to threads on its own machine.

**11. Settling.** Settling a thread settles every delegated thread below it that is still unsettled, at both levels, under the delegating thread's own timestamp, so none is left in the sidebar's Open on its own (Zach, October 20, 2026). That includes one still working or waiting on the user: it stays in the settled thread's roster, and the settled thread's row in Settled says when one waits, as the roll-up does. Restoring the delegating thread restores the delegated threads that still carry that timestamp. Settling ends a settled delegated thread's babysitting as it ends any thread's (ADR-0061), and restoring does not start it again; Zach accepted that on October 20 rather than leave a babysitting thread in Open. The user picks one out by opening it from the roster or its row of delegated work in the transcript, which shows it in the pane and leaves it settled; the roster has no Restore of its own. A delegated thread settled or restored by itself keeps its own state, so settling a thread that is already settled moves none of them, and an open one below a settled thread, such as one started after the settle, still stands in Open on its own as the October 18 change keeps it. Settling a whole project is unchanged, since it settles every thread in it. Like the rest of delegation, this holds only where the Owl list turns delegation on; stable settles each thread by itself.

## Amends ADR-0073

ADR-0073 gives start and send authority to Watcher alone, rooted in a Watcher request. This record extends that authority, within the same limits, to an ordinary thread rooted in the user's latest message to it, with the narrower ceiling of decision 4 and the two-level rule of decision 2. ADR-0073's own text is amended when this lands with E6's code, not before.

## Consequences

- Zach's own `code-review` and `crew` skills can delegate inside Sotto rather than through shells, and their second agents become threads he can open, answer and stop.
- Nothing here answers a question or permission, changes a policy record or widens a thread's permissions. The standing exceptions stay ADR-0029's browser alone.
- The delegated thread is a full thread, so it costs what a thread costs: a provider session, a pane's worth of history and a slot in the starts limit.
- A delegating thread may ask for work the user did not mean. Main can enforce identity, ceilings and budgets; it cannot prove a brief faithfully reflects what the user asked. The user's own message, the delegated thread and its outcome remain visible.
- Needs a prototype before it is built: delegated threads under the thread that started them, and the room's limit counting them. Amended October 17, 2026: the first build listed them under the thread that started them in the sidebar, and an orchestrating thread that starts many crowded it. Zach chose variant B of the delegated threads roster prototype: delegated threads live in the delegating thread's Tools › Agents, mixed with its provider's own agents by start time, newest first, and each opens there as a thread. The sidebar has no row for one, and a search finds none, except one whose delegating thread is gone, which stays listed so it is never out of reach. When a delegated thread below a thread waits on the user, the delegating thread's row says Needs your approval or Needs your answer as its own request would. Opening one from the roster pins Tools to the thread whose roster it was, so the next is a press away.

## Amended October 19, 2026: results go straight back to the thread that delegated

On October 19, 2026, news of delegations sat for hours in the queues of the threads that had delegated, on Zach's machine. Watcher's Stop all on a thread Watcher had started held every item that was not Watcher's, the news among them; a paused or failed prompt of the user's at the head of the queue held everything behind it; and a prompt the user had set aside held every wake-up. Each showed as a **Sotto · Wake-up** message in the thread and its queue panel, which the user did not need to see. Zach decided three things that day, and four faults were fixed with them.

**Decision A. The thread that delegated shows nothing new.** When a delegated thread's outcome changes, Sotto hands the news straight to the delegating thread's agent as its next turn, privately: no message in its conversation, nothing in its queue panel, nothing on the phone, and its sidebar row never quotes it. Its row of delegated work in the turn that delegated still shows the outcome, from delegation's own record (a card under the reply until October 24, 2026; see **Delegated work** in `CONTEXT.md`). In Zach's words: "delegated threads don't need to send their messages in the thread, they should just send directly back to the parent, main thread does not need to see that." Delegation news waits in a hidden wake-up of its own, one a thread, modelled on Watcher's (ADR-0073): no one edits, reorders, pauses or resumes it, and later news folds into it while it waits. News an earlier build folded into a visible wake-up beside a resume note or babysitting's news is set apart into it. The provider still gets the words, since the agent must read them; what is hidden is the user's view. The host marks the message as one no one is shown from its own record of the send (`hiddenWakeUps` beside `wakeUps` on the thread's record in `workspace.json`, IDs only, kept whatever Keep local history says, and a mark beside the wake-up's identity in the thread store, which keeps every one), never from the words, so a restart or a history read again keeps it hidden however many come after. The news tells the agent the user is not shown it, so the agent's reply says what it learned.

**Decision B. Only the delegating thread's own turn holds it.** The hidden news waits while that thread's turn runs, a request waits on it, its provider is disconnected, a send of the thread's is still unresolved (in the outbox, or a prompt or delivery the queue holds as dispatching, submitting or unconfirmed, as after a stop between the queue's claim and the send's outbox entry; a set-aside one does not hold it), or the thread is closed, settled or archived, asked again at the native writer after the thread's preparation: what makes a send impossible. Nothing else holds it: not a machine Stop or Stop all, not a paused or failed prompt of the user's (it goes past them and leaves them in place and in order), not a prompt the user set aside, and not prompts of the user's that are themselves held. A ready prompt of the user's at the head of the queue goes first, as before, and the news goes on the next free turn. A queue the last turn left unreviewed is paused first, as before. Prompts of the user's that a machine Stop holds are paused first too, with a plain note asking for review, before the news goes: the news turn completes like any other, and without the pause they would send unreviewed once the Stop's hold lifted, against ADR-0073's rule that a machine Stop leaves the user's queue for their review. They then wait for the user's Resume, whatever turn completes next. A thread the user archived or settled still gets nothing. A send of it that surely did not go waits again, ten seconds later; one that may have gone is never sent again, as decision 7 asks.

**Decision C. The answer comes with the news.** When the outcome is `answered`, the news carries the delegated thread's reply, labelled as that thread's own words, not Sotto's or the user's, and cut as `read_delegation` cuts it (`WATCHER_REPLY_BYTES_MAX`), so the delegating thread needs no round trip. It is read from delegation's record as the news is sent, never kept in the queue, and Keep local history is respected as `read_delegation` respects it: off, a reply from before a restart is not kept, and the news says so. A reply that does not fit beside the rest of the news says to read it with `read_delegation`. Every other outcome keeps its identities-only line. This amends decision 7, under which the words travelled only when asked for.

**The fixes.**

1. A wake-up in a delegated thread is Sotto's, not the user's. A resume note after a restart, babysitting's news or a delegation's news was taken for the user's message: a send to that thread was refused as the user's turn (`PAUSED`) or newer message (`TARGET_CHANGED`), or failed as it went. The head a brief is checked against now skips the host's recorded wake-ups, and a running turn whose message is a wake-up is not the user's, so a brief waits for it and goes when the thread is free. Where the messages before a wake-up are not loaded, the head stands as the host gives it, which can only refuse. Watcher's own sends to a delegated thread are not yet told apart from the user's.
2. A restart tells the delegating thread once. Recovery made every open brief `unknown` and counted it as told, so a delegating thread waiting for the outcome was never told (#1194). It is now told once; `unknown` still never moves, and nothing is resent.
3. A brief that never went says why. Each way a brief can end unsent (the user's newer message, the user's work there, a Stop, a send Sotto could not make, a restart) has its own note: what happened, that nothing was sent, and what to do, never the delegated thread's words or a code. A send to a delegated thread whose own queue is paused or failed, or holds a message with an unknown result, is refused as it is asked for (`QUEUE_HELD`), since only the user can resume, clear or check it there; a waiting brief whose thread's queue comes to be held that way ends unsent rather than waiting unseen.
4. A delegated thread whose last turn was stopped, or cut short by a restart, takes the next brief once it is free.

## Proof, when built

Integration over fake providers: a Claude Code thread delegates to a Codex thread and the wait returns the answer; a wait that ends first becomes a wake-up; Stop cascades; the ceiling refuses a wider start; a delegated send queued before the user's newer message is refused, not delivered; a second-level thread is offered no `sotto_delegate`; Stop on the top thread stops both levels; typing in a delegated thread pauses delegated sends; a restart leaves `unknown` and resends nothing.

## Amended October 21, 2026: a held `background` outcome is released (#1263)

A delegation whose turn ended with background work stays `background` until that work ends, and the delegating thread is told then. When the work is never seen to end, as with the Codex sub-agent of #1261, the delegating thread waited for good: on October 21, for 7.5 hours.

Now, once the delegated thread has sat idle, no turn running, for twenty minutes since the outcome became `background` or since it was last seen working, whichever is later, the delegating thread is told once, through the same hidden news: the delegation was held that many minutes, its thread is idle, no turn has run there since, and Sotto has not seen the work end, with the start of the delegated thread's last reply, labelled as its own words. It says so only while the delegated thread is idle: a release that waited for the delegating thread's own turn, by when the delegated thread is working again, goes as the plain `background` line and is not used up: it comes again once the thread has been idle twenty minutes more. One whose thread has run another turn since the brief's says that instead of "no turn has run there since", without a later turn's words. `read_delegation` says the same while the outcome stands. The outcome itself stays `background`, and work-settled news still comes if the work ends. A wait runs only while a `background` outcome is waiting for its release; nothing is polled.

A brief to a thread already delegated to takes neither, since that thread runs where it runs.

## Amended October 23, 2026: a thread on another machine delegates on its own machine (#1310)

Decision 10 kept delegation to this computer's own threads: a headless host built no delegation service and no tool server, so a parent Zach started on forge could start nothing. Zach decided on October 21 that a parent may run on any machine, and accepted [ADR-0105](0105-hosts-reach-each-other-over-host-links-the-desktop-sets-up.md) on October 23, whose decision 6 makes children on the parent's own machine the first step. With the Owl feature Work across machines on, as the host's own release track answers it:

- **The host builds delegation for its own threads.** The same `DelegationService` and `sotto_delegate` server run on the headless host, on its own loopback, with its own tool tokens, under every rule above: the two levels, the four briefs per delegated thread per turn of the delegating thread, Stop and settling cascading, outcomes and refusals recorded in its own `delegations.json`. Outcomes and the hidden wake-up stay on that machine (the October 19 amendment); nothing crosses to the desktop but the threads themselves, which the desktop already joins. A host on stable, or older than this, builds none of it, and its threads are offered no `sotto_delegate`.
- **Desktop defaults hold the ceiling (decision 4).** A host's own stored new-thread default never applies, as it never does to Watcher's workers there (ADR-0074). The desktop sends each host that lists the new optional host-v1 feature `host-delegation` its new-thread default and, while worker roles are on, its worker roles, when it connects and whenever either changes, as **desktop defaults** (`desktop-defaults`). The new-thread default it sends is the one Settings applies: this computer's while its own host runs, and the selected host's own while it is off (ADR-0074). The host keeps each desktop's, with its client ID, across restarts. With several desktops, the last ones sent apply, among the desktops still paired there with a `remote-answer` grant (#1196), read afresh at every start (Zach, October 23): a desktop forgotten, revoked or without a grant stops counting at once and after a restart, and the most recent defaults from a desktop that still counts apply instead, since a wider start needs a desktop that may answer there (ADR-0074 decision 3). A delegated start there is held to the narrower of the delegating thread's own permission and that default. A host never told holds every delegated start to Ask for approval, and so does one where no desktop that told it still counts; a refusal or a role's receipt says which. Worker roles there are those of the defaults that apply, or the roles' defaults when they carry none or none apply.
- **Its own machine only.** `list_machines` lists that machine alone, as **This machine**, and `delegate` there takes `machine` or `os` only to name it; another machine or a system it is not is refused as asked for, recorded as `MACHINE_UNAVAILABLE`, until #1316 carries delegations between machines. Above ten working threads on that machine after a start, counting the new one, the result warns in that machine's words ("11 threads are working on this machine. This machine may slow down.").
- **Not yet.** `sotto_visual` and `sotto_pull_requests` are not registered on hosts; each is its own change, beside `sotto_delegate` in the host's tool list. The browser stays this computer's. The desktop's roster of such a thread's delegated threads came after, below.

## Amended October 23, 2026: the desktop's roster of a remote parent's delegated threads (#1310)

The amendment above left the desktop's Tools › Agents listing a remote parent's delegated threads from their `delegatedBy` links alone, with no brief, outcome or row of delegated work in the parent's transcript, since the delegation record is the host's. Zach picked variant B of the remote roster prototype on October 23, 2026, and decided that a machine's rows keep their last outcome while it is away. With the Owl feature Work across machines on, on the desktop and on the host:

- **The host answers the window's read.** A host that runs delegation for its own threads lists the optional host-v1 feature `delegation-views` to a recorded desktop and answers `delegation-views` and `delegation-brief` from its own record, as the desktop's window reads this computer's: what a thread delegated and was sent, each delegation's outcome and timing, and a delegated thread's newest brief, never a reply (decision 7). It pushes `delegations-changed` to a desktop that accepts it, naming the threads whose delegations changed, and the window reads again those it shows. Every ID is the host's own; the desktop keys them by that host, as it keys its threads. A host older than this, or on stable, is asked nothing, and its threads' rows stay as they were, with a line saying that host's Sotto does not report them.
- **One heading per machine.** Tools › Agents groups a roster's delegated threads under a heading per machine, the delegating thread's own first, with its count ("forge 4 threads · 2 working"), where the delegating thread or one of its delegated threads runs on another machine than this computer. A roster of this computer's threads alone keeps its single list. Before #1316 every delegated thread runs on its delegating thread's machine, so there is one heading. The rows of delegated work in the parent's transcript are the same rows as for a thread on this computer, and name the machine.
- **Away, the last read stands.** While a machine is not connected, each of its rows keeps the outcome Sotto last read there, greyed and said as such ("Working when last read"), with when that read stood, which is when the connection was lost, and its clock stops. A notice above the roster says the machine is not connected, that the threads are as Sotto last read them, and that losing the connection stops nothing there. Its rows of delegated work in the parent's transcript say the same. The desktop keeps the last read of each thread it read, at most 256, in memory only. Once the machine connects again every one is read afresh, and what the host's own record says then is what shows: `unknown` only when that record cannot prove the outcome, as after the host restarted mid-turn.
- **Why a start was held.** A role's permission a host held to Ask for approval is recorded on the delegation as `held`: `not-told`, `no-answer-grant`, or `answers-revoked` when the desktop whose defaults would apply had its answers grant taken away. Its row in Tools › Agents and its row of delegated work say so: "Started at Ask for approval: forge had no new-thread default from this computer yet." (the prototype's words), "Held at Ask for approval: this computer can't answer on forge." (Zach, October 23, 2026: the reason only, until a control of its own lets this computer answer there, #1447), or, revoked, "Held at Ask for approval: forge no longer lets this computer answer there.", with no fix, since setting the host up again does not restore a revoked grant.
- **The refusal before #1316.** A thread on another machine that asks for another machine or system is refused as before (`MACHINE_UNAVAILABLE`), and the record now keeps what it asked for (`asked`: a host ID or a system), so its row of delegated work names it (Zach, October 23, 2026): "Asked for this computer. forge can start threads only on forge for now. Nothing was started." A record from before it keeps the prototype's words: "This thread runs on forge, and a thread on forge can start threads only on forge. Nothing was started. Ask again without naming a machine to start it on forge."

Nothing new leaves either machine but the identities, outcomes and briefs this computer's own window already reads of its own threads, over the paired connection the desktop already holds. Stable shows none of it, asks no host for it and is pushed none of it.

## Amended October 28, 2026: Stop, settling and the roster across machines (#1316 part 3)

Since #1316 a delegated thread may run on another machine than the thread that delegated to it: through the desktop relay, or as a remote delegation on a paired host. Decisions 6 and 11 and the roster now reach it, with the Owl feature Work across machines on.

- **The roster.** The window keys a delegated thread's link to the thread that delegated by the window's own key for that thread, whichever machine runs each: a child the relay started on This computer names its parent `host:<hostId>:<threadId>`, and a child on a host names a desktop's caller `relay:<client>:<caller>`, which the desktop resolves to its own key only when `<client>` is the client ID that host knows this desktop by, since another desktop's thread may carry the same ID. With Work across machines off, as in Stable, every link is keyed by its own host as before, saved ones included, so a child whose link finds no thread keeps its own row in the sidebar. So the child is listed in its parent's Tools › Agents and has no sidebar row, under its own machine's heading with that heading's count, away rows and reads on reconnect as in the amendment above. A second-level thread on another machine than its first-level one stands on its own under its machine's heading, still naming the thread that delegated to it. Its row is read from its own machine's record of the briefs it was sent, as any delegated thread's is when its parent's read does not hold its start, and is greyed as last read only when its own machine is not connected or its own read says so: a parent's machine that is away does not grey a row on a machine that is connected, and that row's own read wins over the parent's last one. The rows of delegated work in the parent's transcript do not list it yet.
- **Stop (decision 6).** Stop on a thread also stops what it, and the threads below it, delegated on other machines: each such delegated thread once, through the cancel each side already asks of the other, which on the far side stops it and whatever it delegated, and cascades again from there. It is a stop the thread asked for, so its news does not wake the thread. A thread whose delegated threads all run elsewhere is stopped the same way. No new host operation: the asks already sit behind Work across machines, so a stable host takes none of them. A machine this computer is not connected to is not reached and nothing is queued for it; the window then says which machines, and how many delegated threads that were working when last read it left on each, and that they may still be working there (`stopUnreachedWords`, settled with Zach on October 28). For a thread on this computer, once every cancel its Stop sent has answered or been lost, the window also says which delegated threads on machines that are connected it did not see stop, a cancel refused or one whose answer was lost, and that they may still be working there; it never says they stopped (`stopUnconfirmedWords`, drafted). A thread on a host keeps that account on its host, so for it the window says only what it can see: the machines it is not connected to. After a lost answer, the delegation stays as ADR-0058 leaves it: read exactly on reconnect, nothing sent again.
- **Settling (decision 11).** The window's Settle of a thread settles each open delegated thread below it on another machine, and each one back on its own machine whose link runs through a thread on another, which neither machine's own settle reaches, as that machine's own Settle, once, as the thread goes from open to settled. The window keeps which it settled and which it could not in `cross-machine-settles.json` in its data folder, the threads' keys only, so a Restore after a restart still finds them. A thread's record lasts until its Restore through the window, its deletion or clearing, or its next Settle; only a guard far above use, against a runaway file, lets an older one go. Restore brings back only those its Settle settled that are still settled within `SETTLE_CASCADE_SKEW_MS` (two minutes, settled with Zach on October 28) of the thread, since each machine stamps its own time; one settled on its own a minute before is left, as one machine leaves a thread that carries its own timestamp. A machine that is not connected, or that refuses, keeps its own, and the window says by machine how many it could not settle or restore (`settleLeftWords`, `restoreLeftWords`, drafted). A later Settle of the settled thread settles those its first Settle could not reach and that are still open, and nothing else, as a repeated Settle on one machine moves none of the others; one the user settled by hand since keeps its own, and its Restore leaves it. A settle whose answer was lost is never sent again, and Restore brings that thread back only if it is seen settled within the skew of the thread. Settling from Watcher, Auto-settle merged threads or a phone stays on the thread's own machine.
