# An agent can set up a host from Add host

October 9, 2026 amendment: [ADR-0066](0066-remove-voice-control-and-thread-management.md) records the removal. The voice gate, managed assignments and supervision references below are historical. Host setup and provider jobs remain ordinary user-started threads; only the user answers their request cards.

## Status

Accepted September 28, 2026, for issue #431, part of map #134. The design is placement A2, "choose first", from round 2 of `prototype/host-setup-checklist` (commit bd54b00b), drawn with the device list in round 3 (commit 14fd23a6, moments 6 and 7), both picked by the owner on September 27. It lands before #207, the self-contained host archive, and before #430, the device list; see Consequences for what changes when each lands. Amends nothing: ADR-0004 and ADR-0012 apply unchanged, and the tool's transport is ADR-0020's, used for a second server.

## Context

Adding a host is one press only when the machine already has the host, Node 24 and a data folder the account can write. When it does not, Add host's checklist (#429) says which step failed and gives a command to copy, and the rest is the user's: install Node, download the archive, unpack it, fix a folder, sometimes change the SSH setup. The owner wants that to be one step as well: put the machine on the tailnet, press a button, and have an agent do the installing and troubleshooting, with the user answering each command it runs.

Sotto already has everything an agent needs to do that except a way to finish: a thread can run commands on this computer, and so `ssh` to the machine, with every command a request the user answers. What it cannot do is run Add host's own checks or add the host, and a thread needs a project, which nothing in Add host has. Six questions were left for this ADR by the issue.

## Decision

**Two ways to add.** Under the Device list, or the SSH host field when a host is typed, Add host offers **Have my agent set this up** ("For a machine without the host yet. The agent installs it, fixes what is missing and adds the host. It works in a new thread, and you answer each command it wants to run.") and **Add it** ("For a machine that already has the host."). The agent choice has a **Model** picker and its main button reads **Start setup**. A step that fails on the Add it path offers **Have my agent fix this**, with the same picker, under its sentence and command. Both start the same setup.

**A normal thread, the host setup thread.** Start setup creates a normal thread named "Set up forge" on this computer's local host and sends it a fixed brief. It is on the Threads page with its request cards, transcript and Stop like any other thread, and stays there until archived. Add host becomes the setup view: "Setting up forge", a line saying which model is working in which thread with **Open thread**, the host setup checklist following the agent's checks and add, **Close** and **Stop setup**. Close hides the dialog and the thread keeps going; the Hosts page then says a setup is running, with **Show setup** to open it again. Stop setup stops the thread's turn, cancels a check or add in flight, ends the thread's tool and saves nothing as a host; whatever the agent installed on the machine stays there. An add that has already paired cannot be cancelled, so a stop that lands as it saves the host waits for it and forgets the host again, as its row's Forget would; if that fails, the setup says the host is saved instead of saying nothing was. One setup runs at a time.

**The setup thread's project and folder: a Sotto-owned project.** The thread goes in a project named **Host setup**, at `host-setup` in Sotto's user data folder on this computer, as a shared folder with no worktree. Sotto creates the project the first time and reuses it after. This is the least surprising place the code supports. A thread needs a project and a folder (`create-thread` takes both), and the work happens on another machine over SSH, so none of it belongs in one of the user's repositories, where a stray download or a worktree would be a surprise. The personal-chat folder (`native-workspace`) was the other candidate and was rejected: a personal chat is not on the Threads page, gets none of Sotto's thread tools and is a different kind of conversation, while this is a thread the user watches and answers. The project shows in the sidebar with its setup threads under it, which is where the user looks for them.

**The model.** The picker lists the local host's ready models and starts on the one the user uses most: the model with the most threads on this computer, else the default for new threads. The setup thread starts in the permission mode that asks before everything (`approval-required`, or the provider's own mode that allows nothing), whatever the new-thread default is, because the promise is that the user answers each command. The user can change it on the thread like any other; the add still asks.

That mode is each provider's strictest, and each still has exceptions of its own that Sotto cannot turn off. Codex's `approval-required` is its `untrusted` approval policy with a read-only sandbox: commands Codex counts as safe, such as `ls` and `cat`, run without a request, and the read-only sandbox can still read anything the account can, including `~/.ssh` on this computer. Codex has no stricter policy to choose. Claude Code's default mode reads and searches files without asking, and any provider runs what the user has already allowed in its own settings. So the promise is narrower than "every command": a command that changes something asks first, including every `ssh` command to the machine, unless the provider's own settings allow it, while reads on this computer may not. The brief tells the agent never to read a key, and nothing but the provider's own judgement enforces that. The guide and the README say so.

**The fixed brief.** The brief names the device, its SSH target and port, the host installation and data folders, the step and reason code of the failure that led to **Have my agent fix this** when there is one, this computer's Sotto version, and the install steps `docs/guide.md` and `docs/release/releasing.md` give today: Node 24 for the SSH account, the `Sotto-host-X.Y.Z-linux-x64.tar.gz` archive from the releases page checked and unpacked into the installation folder, a data folder the account can write. It says to start with a check, fix what the check reports, add the host once a check gets as far as starting the host, and to ask before changing the SSH server's or Tailscale's settings. It never includes a key, a token or a password, tells the agent never to read or copy one, and never mentions or reaches the desktop's credential store. It is written in `src/main/hosts/hostSetupBrief.ts` and is not editable. Because #207 is not merged, the brief carries the install steps itself; when #207 lets the desktop install the host, the brief shortens to the troubleshooting that automation cannot do.

**The tool: `sotto_host_setup`, scoped to one thread and one device.** A second loopback MCP server beside `sotto_browser`, on the same transport (`ThreadToolServer`): `127.0.0.1` only, one bearer token per thread, no origin, bounded bodies. It is offered only to the host setup thread, only while its setup runs; every other thread's launch gets no such server, and a token is revoked when the setup ends, is stopped, or Sotto quits. The device is fixed when the setup starts: no tool takes a target, so the agent can check or add that one device and nothing else. It has three tools and no others:

- `host_status`: what the setup knows (the device, its connection, the folders, the last check or add and where it stopped, with its reason code and sentence).
- `host_check`: runs Add host's own connect on the device, reach, Tailscale's approval, sign-in, the installation check and the host's start, and then disconnects without pairing or saving anything. It can start a host that is installed but not running, as Add host does. It says which step it stopped at, why, and the command that fixes it where Add host has one.
- `host_add`: asks the user in the thread, then runs Add host's add on the device, which saves the host only once it answers and pairs.

Claude Code, Codex and Grok Build get the server the way they get `sotto_browser`: allowed without the provider's own prompt, because the answer that matters is Sotto's. Devin gets neither, since its pinned client ignores supplied MCP servers.

**Adding is a request card the user answers.** `host_add` puts a Sotto-owned permission request in the setup thread, "Add forge as a host?", with **Add forge** and **Don't add**, and waits for the answer. The host is added only on **Add forge**; **Don't add** tells the agent the user declined, and nothing is saved. The request is answered like any other in the thread, and only by a client that may grant (ADR-0004): a paired phone without a policy record cannot answer it, and pairing grants no answer authority until #208 decides otherwise. The coordinator's supervision, a memory or the agent itself never answers it. `host_check` asks nothing of its own, because it saves and pairs nothing and runs only Add host's own steps on the device the user chose by pressing Start setup; its SSH questions and Tailscale approvals are answered on their steps in the setup's dialog, as Add host's are. Because the thread cannot say anything while its tool call waits, and the dialog may be closed, the same question or approval is also asked over whichever page is open, the way a saved host's SSH question is, with **Not now** to leave it for **Show setup**, and the Hosts page line says what the setup waits for.

**The dialog follows the setup.** The checklist shows the latest check or add the tool ran, with each step done, under way, waiting for the user or still to come. A step that failed in an earlier check and passed later reads "by the agent". A step the latest check stopped at shows the reason quietly, since the agent is working on it, rather than as a failure to act on. While the thread waits for an answer, a card on the current step says so, "The agent wants to run a command on forge. Answer it in the thread to carry on." or "Sotto is asking in the thread whether to add forge as a host.", with **Open thread**. When the add connects, the dialog reads "forge is connected", says which model set it up in which thread, and **Done** closes it. Answering the add takes the user to the Threads page, so an ended setup stays on the Hosts page as a line with **Show setup** and **Dismiss** until it is put away. A machine that answers with another Sotto version is saved, as Add host saves it, and the setup ends there, saying what the host's row asks for.

**Outside the voice gate.** Start setup is a button the user presses, not coordinator management: the thread is not managed or assigned, nothing speaks or listens, and supervision does not follow it. It therefore sits outside `voiceCoordinatorEnabled` (ADR-0012) and is there with voice off.

**Privacy.** The setup thread's provider receives the brief and the output of every command the agent runs, which on this thread is the SSH session's output from the machine being set up: file listings, error messages, versions, whatever a command prints. That is what any thread's provider receives for the commands it runs, but here it is about another machine, so the README's "Privacy and cost" says so. No new host is contacted by Sotto itself; the machine may download the host archive from the releases page, which the brief names, and when it cannot, the brief tells the agent to download it on this computer, a command the user answers, and copy it over with `scp`.

**What does not survive a restart.** The setup lives in memory. Quitting Sotto ends it the way Stop setup does: the tool's token goes, a check or add in flight is cancelled, and the thread stays as an ordinary thread without the tool. Starting a setup again starts a new thread.

## Amendment: an agent for a host's provider

*Amended September 28, 2026, for issue #461, part of map #134. The design is layout B, Tiles, round 2 of `prototype/host-providers` (commit 90361e37), picked by the owner on September 28.*

A provider that is missing from a host, too old, or installed where the host cannot find or start it needed someone at that machine's terminal. The provider tiles (ADR-0037) now offer the same machinery as host setup for it, rather than a second mechanism.

**Three cases, one button each.** A tile whose provider is not installed offers **Have my agent install it**, one too old **Have my agent update it**, and one that cannot be found or started **Have my agent fix it**, each beside **Check again**. The case is decided by the provider's problem code (`not-installed`, `too-old`, `cannot-start`), never by its sentence. The button opens a dialog titled "Install Devin on forge" (Update, Fix) with the setup's **Model** picker and **Start install** (Start update, Start fix).

**A provider job, run as a setup is.** Start creates a normal thread named "Install Devin on forge" on this computer, in the same **Host setup** project, in the permission mode that asks before everything, and sends it a fixed brief (`src/main/hosts/hostProviderBrief.ts`). The brief names the host and its SSH address, the provider and its command, the case and what the host reported (the version found and the version needed, and the host's own sentence), where #459's lookup searches (ADR-0036), and the provider's official install method as its maker documents it. It never includes a key, a token, a password or a sign-in code, and tells the agent never to read one and never to sign the provider in. `HostProviderJobs` (`src/main/hosts/hostProviderJob.ts`) holds the job in memory beside the host setup; quitting, archiving its thread or forgetting its host ends it as Stop does.

**The same server, two more tools.** `sotto_host_setup` now serves two kinds of job. A provider job's thread is given `provider_status` (what Sotto knows about that provider on that host, where the host looks, and the official install) and `provider_check` (the host's own `refresh` for that provider, which is Check again on its tile). Neither takes an argument: the host and the provider are fixed when the job starts, so the thread cannot act on another host or provider. Each thread's `tools/list` shows only its own job's tools, and a call to the other job's tools is refused; the clients' allow-lists name all five, because the answer that matters is Sotto's. The token is revoked when the job ends.

**Every command is still a request the user answers.** The agent reaches the host only through `ssh` on this computer, and ADR-0004 is unchanged: the tool installs nothing and answers nothing.

**One agent job at a time.** A host setup and a provider job each refuse to start while the other runs, with a sentence naming the one running, so there is never more than one thread holding one of these tools.

**It stops at found.** The job ends when the host finds the provider and can start it: it connected, or it started and said it is not signed in. That is noticed whenever the host publishes its providers, whoever made it look again, and the tool's own check says so. The tile then offers Sign in (ADR-0037). While the job runs, the tile reads "Agent is installing it" (updating, fixing), names the thread, and offers **Show thread** and **Stop**; Stop interrupts the thread and leaves whatever it installed.

**Too old needs a floor, and the floors are the adapters' own.** Sotto already refused clients older than the versions its adapters were checked against (ADR-0042): Grok Build 1.0.5 and Devin 3000.10.31. Each floor and its reason is now written next to the adapter (`GROK_CLI_VERSION`, `DEVIN_CLI_VERSION`), and a provider refused as too old carries the floor as `requiredVersion`, which the tile and the brief name. Claude Code's floor is the set of flags Sotto runs it with (`REQUIRED_FLAGS`, beside it), with no version number to name, so its tile says "Sotto needs a newer version". Codex has no floor, and none was added: nothing Sotto uses has been found missing from a Codex client that starts.

**Privacy.** The job thread's provider receives the brief and what the agent's commands print on the host, as a setup thread's does; the README's "Privacy and cost" says so. Sotto contacts no new host itself; the host may download the provider from its maker, which is what the user asked for.

## Consequences

- A thread can now add a host, but only the one device its setup names, and only after the user answers its card. A second tool surface for threads is a second place Sotto must keep scoped; `ThreadToolServer` is the one transport both use.
- `AgentControl` can now carry a request Sotto owns rather than a provider, merged into its thread's requests and answered in place (`SottoThreadRequests`). This is the first; any other is an ADR of its own.
- The setup needs the local host, since the thread runs on this computer and reaches the machine through this computer's SSH setup. With the local host off, Have my agent set this up says so and is not offered.
- When #207 lands, the brief's install steps shrink to what automation cannot fix, and a check may report an archive the desktop could copy itself.
- When #430 lands, the two choices sit under its device list instead of the host field; nothing else moves.
- When #208 lets a paired client answer, the add card follows the same rule as every other request, with no change here.
- Since #461, a thread can also make a connected host look for one provider again, but only the host and provider its job names. `sotto_host_setup` is still the one extra tool surface, now with two kinds of job, which keeps the scoping in one place.
