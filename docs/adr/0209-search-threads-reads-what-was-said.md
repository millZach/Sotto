# Search threads reads what was said

Accepted November 19, 2026. Zach asked for it ("so the key phrase doesn't just need to be in the title"), lifted the feature freeze for it, and picked from `docs/prototypes/thread-word-search-prototype.html`: variant A, the user's messages and the agents' replies, the desktop and the iPhone with each computer searching its own threads, and stable rather than Owl.

Search threads, on the desktop's sidebar and the iPhone's Threads page, already matched what a row says: its title, project, provider, model, what it is doing and the user's last message. It now also finds a thread by anything the user or its agent said in it. A thread found only that way is a **word match**: it lists after the rows found by their own words, in the same group, and quotes its newest matching message under its name, "You: …" or the provider's name, with the words marked and how many other messages match.

Decisions:

1. **What is searched.** The thread store's `messages` table: the user's messages and the agents' replies, never a wake-up, which is Sotto's, and never a step's command, output or file names. Steps are about 316,000 JSON records on the owner's laptop, around a second to read for every search, against a tenth of that for the messages. Settled threads are searched too, as a title search already finds them.
2. **No index.** Each search reads every message once with SQLite's `LIKE`, which ignores the case of ASCII letters only. On the owner's laptop store (1.6 GB, 994 threads, 75,897 messages, 30 MiB of their words) a search takes 55 to 116 ms, and 5 to 12 ms on forge's 203 threads; `tests/perf/threadWords.perf.test.ts` holds a store of the same size to 400 ms. A trigram full-text index answered in 1 to 10 ms but would add about 160 MiB to the store and take 4.7 s to build, and it would add work to every message written. A search typed after a pause is a user action, not an update, so the read may grow with the history; it never runs on main's thread while the store worker runs.
3. **Where it runs.** On the store worker, behind every write posted before it, as the message scrubber's read does (ADR-0109); on main only with no worker. An Owl build may read this computer's file from `sotto-engine` instead (ADR-0215). That read waits for the same writes, answers nothing while they are held or the store cannot be read, and names only threads this host lists. The renderer asks 200 ms after the last key, and keeps the last answer's matches whose quote still holds a longer search until the new one arrives. Nothing is published or kept; one answer names at most 200 threads, the newest matches first, with a quote of at most 180 characters each.
4. **Every computer searches its own.** The desktop asks this computer and every connected paired host at once and joins what comes back, leaving out a host that has not answered within 3 s. A host lists the `thread-words` feature on every listener where it keeps a store, and answers `thread-words`; for a phone whose hello accepts `thread-words`, its `settled-threads` search then also finds the held-back settled threads whose words match, so the iPhone's Settled shelf finds them (ADR-0028, November 1 amendment, part 2). One read answers both for three seconds. An older phone, which cannot quote such a thread, keeps today's settled search. A host that does not list it is searched by what its rows say, as before. Host protocol version 1 is unchanged.

Nothing leaves the computers the threads are on except to the user's own desktop and iPhone, over the connections that already carry those threads.
