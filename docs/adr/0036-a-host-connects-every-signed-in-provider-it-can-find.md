# A host connects every signed-in provider it can find

## Status

Accepted September 28, 2026, for issue #459, part of map #134. Found on forge the same day, with Sotto 0.1.22. Amends ADR-0025, which left a host's providers to the saved coordinator settings it shares with the desktop, and changes where every adapter looks for its client, on the desktop as well as on a host.

October 5, 2026 amendment (#479, #169): a desktop on macOS or Linux whose inherited PATH looks like a Dock or Finder launch's (none of `~/.local/bin`, `/usr/local/bin` or, on macOS, `/opt/homebrew/bin`) now reads the login shell's PATH once at startup, before anything else runs (`src/main/app/guiPath.ts`), and puts its folders, nvm's default Node, Homebrew and `~/.local/bin` on PATH for the whole process. Git, the terminal and every client then see what Terminal would. The shell is started interactive (`-ilc`), with a minimal environment, four seconds and nothing on stdin. A shell that stalls, or one whose background job holds its output, costs those four seconds once and leaves PATH as it was plus the fixed folders. A launch whose PATH is already full keeps its order and only gains missing folders at the end. Windows is unchanged. The per-client lookup below stays, and its login-shell step now usually finds nothing PATH has not already found. On the desktop, pressing **Connect providers** when the saved provider's client is missing switches to an installed one, never one the user turned off. The connect Sotto starts on its own at launch still changes nothing the user chose.

## Context

Opening a project or a thread on forge failed with "Reconnect the provider before sending. Your draft is saved." The host was up and paired, and no provider was connected on it. Two faults combined.

A host connected only its saved providers. A new host saves the same coordinator settings a desktop does, and forge's said `enabledProviders: ["claude"]`. Claude Code was not signed in on forge, so nothing connected, while Codex, signed in there, was never tried. On the desktop the user picks providers in Settings → Providers; on a host nobody does, because no client can yet see a host's providers (that is #460). And the saved set could not be read as the user's word: an enabled set left at its default and one the user trimmed look the same.

A host could not find a client a version manager installed. The launch script starts the host from a non-interactive SSH shell, whose PATH on forge was `/usr/local/bin:/usr/bin:/bin`. The launch script's Node probe already looks through the login shell and the version managers' folders; provider lookup did not. Each adapter had its own: Claude Code tried `~/.local/bin` and PATH, Codex PATH, npm's Windows folder and `~/.codex/bin`, Grok Build `~/.grok/bin` and PATH, Devin PATH, `~/.local/bin` and its app. On forge every client comes from mise: `~/.local/bin/{claude,codex,grok}` are bash wrappers that run `mise x`, the binaries are under `~/.local/share/mise/installs/<tool>/latest`, and mise's shims resolve to the `mise` binary. Codex, which starts only a native binary, rejected the wrapper and had nowhere else to look.

## Decision

**A host connects every provider that is installed and signed in, except the ones the user turned off.** When the headless host starts, its coordinator sets its enabled providers to all four minus the ones turned off and connects them. Trying a provider is how Sotto learns whether it is installed and signed in: one that is not ends in its own error ("Install Codex and sign in before connecting this provider.") and is not retried, and the host stays up for the ones that did connect. The desktop keeps what it did: it connects the providers the user connected in Settings → Providers. The coordinator knows which it is from its constructor: `src/host/index.ts` builds the runtime with `runsAs: 'headless-host'`, and nothing else does.

**Turning a provider off is recorded as a choice.** The coordinator settings gain `disconnectedProviders`, written only once the user turns one off. Disconnecting a provider by name adds it; Disconnect with no provider adds all four; a changed enabled set adds what it left out and removes what it put back; connecting a provider by name removes it. A host reads it at start, so a provider disconnected through the host stays off across restarts until it is connected again. A paired client changes it only through those commands: it is not on the remote configuration list. A host saved before this has no record, so it tries every provider once; a provider someone had trimmed from the enabled set by hand before then connects again if it is signed in, which was the only way to tell "never asked" from "turned off". The one exception is an empty enabled set, which only Disconnect (or disconnecting each provider) wrote and no default produces: a host that saved one starts with all four turned off, as the user left it.

**One CLI lookup for every adapter** (`src/main/agents/cliLookup.ts`), in this order:

1. the provider's own install folder when it prefers one: Grok Build's `~/.grok/bin`, where its installer, npm's included, keeps the native binary;
2. PATH;
3. the login shell's PATH (`$SHELL -l -c`), asked once per process with five seconds and nothing on stdin, as the Node probe does; not on Windows;
4. `~/.local/bin`;
5. the version managers: mise's `installs/<tool>/latest` (its `bin`, its top folder for a download such as Claude Code, and `node_modules/.bin` for an npm package such as Grok Build), asdf's, nvm's and fnm's newest versions and fnm's default alias, Volta's installed packages and Node, and Homebrew (`HOMEBREW_PREFIX`, `/opt/homebrew/bin`, `/usr/local/bin`, and Linuxbrew's `/home/linuxbrew/.linuxbrew/bin` and `~/.linuxbrew/bin`); on Windows only mise, under `%LOCALAPPDATA%`;
6. the npm global prefix: `npm_config_prefix`, a `prefix` in `~/.npmrc`, `~/.npm-global` and `~/.local/share/npm`, and `%APPDATA%\npm` on Windows;
7. the provider's other install folders: `~/.codex/bin` and the Devin app.

A manager's shim is never the client. Started by its path, a mise shim runs `mise` and a Volta shim `volta-shim`, so a candidate whose real path is one of those is passed over, and the mise and asdf shim folders are not searched even when PATH names them. Nor is a script that runs its command through a manager (`mise x`, `mise exec`, `asdf exec`), such as forge's `~/.local/bin/claude`: it runs `mise use -g` first, which rewrites mise's global settings on every start, possibly from several processes at once, and it makes the client look like its own installer's to the update check. The lookup goes on to the install the wrapper would have run. Each client keeps its own rule for what it will start. Codex's stays: only a native binary, found through a link to it, or inside its npm package's vendor folder; a wrapper script is passed over and the binary it wraps is taken. The others take any other file that may be executed, an npm package's `#!/usr/bin/env node` launcher included. Windows names are unchanged (`claude.exe`, `codex.exe`, `grok.exe`, `devin.exe`), and npm's `.cmd` shims are never started.

Two orders changed from the adapters' own. Claude Code now tries PATH before `~/.local/bin`, the lookup's order; where both hold a `claude` they are almost always the same one. Grok Build keeps `~/.grok/bin` ahead of PATH, because an npm install puts a launcher on PATH, and the native binary is the one `~/.grok/bin` holds.

**A client found outside PATH gets its manager's PATH.** A client started by its full path can still need what its manager puts on PATH: an npm package's `#!/usr/bin/env node`, or the tools the agent runs. Such a client's process gets its own folder and the folder of the Node the same lookup finds ahead of the inherited PATH, and the login shell's other folders after it. Only PATH changes, and only inside each adapter's own environment allow-list; nothing the allow-list drops comes back. A client's own updater (`claude update`, `grok update`) runs with the same PATH. A client found on the inherited PATH, and one a test or a setting names directly, keeps the PATH it was given.

**The refusal names the machine and the page.** With no provider connected, a create or a send is refused with "No provider is connected on forge. Connect one in Settings > Hosts." A host cannot know the name a desktop saved it under, so it says "this host" and the desktop's router puts the saved name in; a phone shows "this host". The desktop's own coordinator says "No provider is connected on this computer. Connect one in Settings > Providers." "Your draft is saved." follows only where a draft is: a send, a steer, a follow-up or an answer, not a create, a thread setting, a stop or a compaction. One thread's provider being down while others are connected keeps its own refusal, "Reconnect this thread provider before sending."

## Consequences

- forge's two workarounds (Codex added to `enabledProviders`, and `~/.codex/bin/codex` linked to mise's binary) are no longer needed; the owner removes them and restarts the host as the live check.
- A host tries a provider that is not installed at every start. That costs a failed lookup, and each such provider shows its own error in the host's provider list, which #460 draws as tiles.
- On a desktop started from the Dock or Finder, a client in a version manager is found too, and on macOS and Linux the login shell is started once to ask for its PATH when a client is not on the inherited one.
- Update checks treat a client under mise's or asdf's installs as that manager's, so Sotto shows the command rather than running npm, which would install a second copy elsewhere.
- The integration test runs a scripted Claude Code from a mise layout with PATH `/usr/local/bin:/usr/bin:/bin`; it and the lookup's login-shell and link cases skip on Windows and run in the Linux CI job (`npm run test:socket`).

## Considered options

- **Keep the saved set and have the host save every provider on first start.** It would fix a new host and leave every existing one, forge included, exactly as broken, and still could not say which providers a user turned off.
- **Probe sign-in without connecting.** Each client reports its sign-in its own way, so this would be a second check per adapter beside the one connecting already makes. Connecting is the check each adapter trusts, and it leaves the provider connected, which is the point.
- **Run the client through the login shell** (`$SHELL -l -c claude`). It would find everything the user's shell finds, and it would put a shell between Sotto and every provider process, with the user's profile in the path of every spawn and every signal. The lookup reads the shell's PATH once and starts the client directly.
- **Follow mise's shims.** Shims find the tool mise would pick for the current folder, but started by path they run mise, and Codex's native-binary rule would take mise itself. The `latest` install is what `mise use -g` selects on forge.
