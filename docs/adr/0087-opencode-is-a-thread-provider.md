# OpenCode is a thread provider

Accepted October 16, 2026. Zach asked for OpenCode the way T3 Code has it, and chose the shape the same day: an Owl feature (ADR-0072), OpenCode 2 only, a full Threads provider as Muse is (ADR-0079), a data folder of Sotto's own, and model menu variant C, model source first. He first chose to share the data folder of the OpenCode he runs himself, and changed that the same day after a scratch test (see Sign-in and the data folder). The wire facts below were checked live against OpenCode 2.0.31 on the Windows laptop on October 16, 2026, and T3 Code's two OpenCode adapters were read at `e58a4857`; [the research note](../research/2026-10-16-t3-opencode.md) records both.

OpenCode joins Codex, Claude Code, Grok Build, Devin and Muse as a thread provider, id `opencode`, shown as **OpenCode**. Its adapter speaks OpenCode 2's HTTP server, not its ACP mode: one `opencode serve --hostname=127.0.0.1 --port=0` per thread (ADR-0038), reached on the port it prints with HTTP Basic and a password Sotto makes for that process alone, with live work read from the server's event stream. Several servers share Sotto's own OpenCode folder once its database exists, so the first server on that folder while it has none starts alone. A server is stopped with its process tree, because stopping the server alone leaves a running tool's processes behind on Windows. That holds for a server that exits on its own too: its tools outlive it, so Sotto ends them, on Windows by the parent each one still records and elsewhere through the server's process group. Each server is written down under Sotto's OpenCode folder while it runs, with its PID, when Sotto started it, on macOS and Linux the start `ps` reports for it, and which Sotto process did, and the record goes when the server and what it left are gone. Each record is written whole beside its place and renamed into it, so a sweep never reads half of one; a record a sweep cannot read is kept while it is under five seconds old or while the PID it is named for runs OpenCode's server. A Sotto that crashes leaves its records, and the next connect ends the servers they name, with their tools, before it starts any: only a process that still has the recorded PID, started when the record says and running OpenCode's server, is ended, and a record whose Sotto is still running is left to it. Started when the record says means from 2.5 seconds before to 10 seconds after Sotto's clock read starting it, which a record written before `ps` answered matches by too, or, on macOS and Linux, within a second of the start `ps` reported for it then. Linux's `ps` reads up to two seconds behind the clock, and a wall-clock step after the record moves what it reads by the size of the step, so the second rule matches on an unstepped clock and Sotto's clock still matches after a forward step of up to about eight seconds. A larger forward step, or a backward one of more than a second, can leave the server running with its record cleared. On Windows Node's job object already ends a server with Sotto (checked against 2.0.31 by killing its parent outright), so there the sweep ends only the tools a crash left; on macOS and Linux the server runs on in its own process group until the sweep. A Sotto that exits without quitting, as on `process.exit` or an uncaught error, sends each server it still runs a hard stop to its process group as it goes, and leaves the records for the sweep (October 26, 2026). A sweep that finds a server it cannot show has ended, because it would not stop or `ps` did not answer while its PID still runs, keeps its record for the next connect rather than clearing it. OpenCode ignores the end of its input, so it cannot be stopped the way Muse and Grok Build stop when Sotto goes.

## OpenCode 2, not 1

OpenCode ships two lines. The 1.x line (`opencode-ai`, `opencode.ai/install`, scoop's `opencode`, the tap's `opencode`, the desktop app) and the 2.x line (`@opencode/cli`, `opencode.ai/v2/install`, Homebrew core, the tap's `opencode-v2`, scoop's `versions/opencode2`, Arch's `extra`) have different servers, and T3 Code keeps an adapter for each. Sotto supports 2 only. The verified version is 2.0.31; a 1.x client, or a 2.x older than it, is refused at connect with the version it reported and where OpenCode 2 comes from. OpenCode 2 prints its version as `opencode v2.0.31`.

## The gate

OpenCode is an Owl feature (`opencode` in `src/shared/owlFeatures.ts`), held off stable the way Muse is: a stand-in host that connects nothing and refuses work in words, provider lists that ask the gate before showing an OpenCode tile or row, and saved records left whole so returning to Owl restores the provider. Muse's gate checks are hand-written at each site; OpenCode's work first turns them into one gate per provider that both use, so a third held provider is one entry rather than another two dozen sites.

## Sign-in and the data folder

OpenCode keeps its own sign-ins, one per model source, and Sotto stores no key for it. Sotto's OpenCode servers use a folder of Sotto's own: every OpenCode process Sotto starts (a thread's server, the server that checks the client when it connects, and any later side call) runs with `XDG_DATA_HOME`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME` and `XDG_CACHE_HOME` pointing at `opencode/data`, `opencode/config`, `opencode/state` and `opencode/cache` under Sotto's user data, or under its data directory on a headless host, made on first use. The user's own XDG values are never passed through, and the user's own OpenCode folders (its data, config, state and cache under those XDG values) are never read or written. OpenCode still reads the config it finds beside a thread's project and in the user's home, as it does when the user runs it; the amendment of October 24, below, says what (#1425). The environment its processes get is otherwise the shared allow-list without other providers' keys.

Zach first chose to share his own OpenCode folder, so a thread would run on the sign-ins, settings and skills of the OpenCode he runs. A scratch test the same day showed that OpenCode 2 opening the folder OpenCode Desktop 1.19.3 uses rewrites part of its database for good, emptying its event log, dropping three of its tables and rebuilding its workspaces, and that afterwards the two keep diverging histories under the same session IDs. Zach saw that and chose a separate folder on October 16, 2026. So:

- Sotto's folder starts with no sign-ins. A fresh install lists only OpenCode Zen's free models until the user signs in to a model source inside it (#1104 adds the sign-in), and a connected OpenCode says no model source is signed in yet.
- Grants the user saved in their own OpenCode do not reach Sotto's threads, and Sotto never creates one: it answers OpenCode only with its one-time allow or its reject.
- The user's own OpenCode never sees Sotto's provider sessions. OpenCode does not lock a provider session to one process, so Sotto drives a thread's provider session only from that thread's own server.

Sotto's servers run with `share` set to `disabled`, so a thread is never published as an OpenCode share link, and with OpenCode's own update check off, so a thread's server neither checks for nor installs a new client.

## Finding and updating the client

Settings gives OpenCode the same connection, version, model and update controls as the other providers. Sotto finds `opencode` by its CLI lookup (ADR-0036), plus `~/.opencode/bin`, where the v2 install script puts it.

Amended October 18, 2026: the lookup missed OpenCode 2 installed from npm on Windows, where npm's folder holds only `.cmd` and `sh` launchers and the program is under `node_modules\@opencode\cli`, and Sotto's own refusal tells people to install from there. OpenCode's lookup (`src/main/agents/opencodeLookup.ts`) now finds OpenCode 2 however it was installed. It tries `opencode2` beside `opencode` in every folder. A launcher is read, never run, for the program it starts: npm's, pnpm's and yarn's `.cmd` and `sh` launchers, and a scoop shim's `.shim`. A launcher that names a network path is not followed. bun's Windows launcher keeps its target in a form of bun's own, so it is passed over for bun's global packages. `@opencode/cli` ships a stand-in program that its install script replaces, and pnpm and bun skip that script by default, so the stand-in is never taken: the lookup goes on to the program packages for this computer (`@opencode/cli-<os>-<arch>`, then its baseline and musl builds, and on Windows ARM the x64 ones last), inside the package, beside it, or in pnpm's store, offering each in turn so a build this processor cannot run is followed by the next. They follow the package's own program too, when its install script did copy one. Each build starts with its own folder ahead of PATH, as the first one found does. After the shared order it searches Windows' own PATH as the registry holds it now (read with `reg.exe`, no shell, bounded, fresh for fifteen seconds), its folders' variables expanded from the registry's own before Sotto's, so a copy installed after Sotto started is found on the next connect even when its installer set a variable such as `PNPM_HOME` for it, then bun, pnpm, yarn, scoop, WinGet, Chocolatey, the nix profiles, `/usr/bin` and `/usr/local/bin`. WinGet, Chocolatey and nixpkgs give OpenCode 1, so a computer can have an OpenCode 1 ahead of an OpenCode 2: connect asks each OpenCode found for its version, in order and only while the ones before it are refused, and uses the first OpenCode 2 Sotto drives. The first gets the usual ten seconds to answer, and the rest share another ten. When none will do, connect refuses with what the first said. After an update, the client in use is asked first and kept when it still will do. Presence asks for the first only, and the update check asks about the OpenCode connect chose while it is still there, so it never checks an OpenCode 1 found ahead of it. A copy yarn installed is left to yarn, as bun's and pnpm's are, wherever `BUN_INSTALL` or `PNPM_HOME` puts them. No other provider's lookup changed.

Updates follow ADR-0042: the channel that installed the client updates it. An npm install is checked against `@opencode/cli` on `registry.npmjs.org`, which the README already names, and updated by Sotto's npm runner. A copy npm does not own, such as the v2 install script's, updates itself with `opencode upgrade`. A copy Homebrew, scoop or pacman owns shows the command to run by hand. A copy bun, pnpm, yarn, Volta or asdf installed is left to that tool, as ADR-0042 has it for every other client, and only the program's own prefix makes a copy npm's, so a global `@opencode/cli` elsewhere never claims the install script's copy or a system package's. Sotto never moves an install between the 1.x and 2.x packages.

## Permissions

A thread's permission mode becomes its provider session's rule set, sent when the provider session is created and changed while it lives: **Ask for approval** asks for every action OpenCode's own agent rules do not already decide, **Auto-accept edits** allows edits, and **Full access** allows everything. OpenCode has no mode of its own that matches **Automatic**, so it is not offered. Concretely, **Ask for approval** and **Auto-accept edits** set commands, steps outside the project folder, web fetches, web searches, subagents and, under Ask for approval, edits to ask, as Claude Code and Devin ask before reaching the web and a subagent runs on rules of its own; they deny nothing: OpenCode Zen's free models refuse a provider session whose rules take a tool away, and take this one (checked against 2.0.31). A project's own `opencode.json` rules apply where the session's name nothing, but cannot widen what they ask for: with the project allowing edits, web fetches and commands, the session's asks were still asked, and with the session allowing everything, the project's own ask for edits was not (checked against 2.0.31). Project config stays on, since it also carries the user's own MCP servers and instructions. A permission OpenCode asks for arrives with the files and diff it would change and is shown as a request card. The user answers every one (ADR-0004) with allow once or reject, and a reject reaches the model as a failed tool call, so the turn goes on. Disconnecting sends no decision.

## Questions

OpenCode's question tool arrives as a form. A form Sotto can draw, with text, number, yes-or-no and choice fields, is shown as a question card and answered with the user's words. One it cannot draw, such as a field shown only for another field's answer, is cancelled with a sentence saying so, and the model is told.

## Models and the model menu

Every model OpenCode lists is offered under its **model source**: where it runs, which is OpenCode Zen for the free models and otherwise a company the user signed in to inside Sotto's OpenCode folder, such as Anthropic, OpenAI or OpenRouter. The model menu opens on OpenCode's model sources and then shows the chosen source's models, as Zach picked from the [prototype](https://github.com/millZach/Sotto/blob/da06200653ea228993b00a44757da509d669cd56/docs/prototypes/opencode-model-menu-prototype.html) (variant C); typing searches every source at once. The chip shows the OpenCode mark and names the source, so an OpenCode thread on an Anthropic model never reads as a Claude Code thread. A model's variants are its effort levels in Sotto's order, and its image input decides whether images can be attached. OpenCode's mark is adapted from T3 Code's (MIT).

How the menu was built (#1105): it opens on model sources for any provider whose models name one, decided from the models rather than the provider ID. Escape steps back one level at a time, clearing a search, then leaving a source with focus on its row, then closing; other providers keep their one-step Escape. The chip reads "Anthropic / Claude Sonnet 5" and may be 320px wide; a source name longer than nine characters gives way first, down to 4.5em, and a shorter one never does, because a floor of 4.5em on a short name such as OpenAI would leave a gap. The chip keeps "Thread model" as its accessible name, since the notice under the chips finds it by that name. "Claude Sonnet 5 from Anthropic, in OpenCode" is its tooltip and accessible description.

## What an OpenCode thread can do in this first version

Streaming replies with reasoning, tools, file changes and commands as thread activity; steering a running turn and queueing behind it; stopping; images; effort per turn; model and permission changes on the live provider session; resume after Sotto restarts (ADR-0076), where a turn whose server died reads as stopped rather than running forever. One OpenCode execution can carry several prompts, so the adapter follows each prompt by its own message, not by the execution.

**Sotto's tools.** They reach an OpenCode thread as remote MCP servers, one for each of Sotto's servers the thread is given (the browser's, and each scoped server that answers for it, as Grok Build and Muse get them), added to that thread's own server with `PUT /api/experimental/mcp/{name}` for its provider session's folder, with the thread's bearer token, each time that server starts, and taken off with `DELETE` when the thread's session ends (#1106). OpenCode keeps them per process and per folder until it ends and writes nothing to its config folder. Code mode is off for them (`codemode: false`): with it on, as 2.0.31 has it by default, the model is offered only a JavaScript `execute` tool that calls MCP tools from a script; with it off, each tool is offered as `<server>_<tool>`, such as `sotto_browser_browser_open`, which is also the action its permission request names. OpenCode either holds the add while it connects, about 30 seconds against a server that never answers, or answers it at once and lists the server as `pending` in `GET /api/mcp` until it has connected; Sotto reads the list again while any of the thread's servers is pending, for up to 45 seconds from the add. All of it runs beside the thread's start, and a send waits at most two seconds for it before it goes. A browser call may wait 6 minutes for the user's answer, as Claude Code and Codex are told, and a scoped server's call its own `timeoutMs` (`timeout.execution`, in milliseconds). A server OpenCode refuses, or does not list as connected in `GET /api/mcp` once it is no longer pending, marks the thread `sottoToolsWithheld`, and Sotto offers no control that needs its tools. A new server clears a mark an earlier one left before it asks for the servers, since the scoped servers answer no thread so marked, and asks once more after the first ones connect, so an idle restart gives every server again. After the mode's rules, the rule set allows each tool of the servers the thread's server was given and connected, by its own action name, as Claude Code's launch allows Sotto's tools by name and Grok Build's own one-time allow admits them. A server the thread was not given, such as the visual tool's while visuals are off, gets no allow, so a project's own MCP server by that name is still asked about as the project says. The allows are set when the provider session is made, changed by PATCH once the servers connect, and checked again whenever a server opens an existing provider session, so one made before the thread had its tools gets them on its next opening; a mode change keeps them. That takes no tool away, which Zen's free models would refuse, and Zen ran a turn that called a Sotto server's tool with it (checked against 2.0.31). Each thread has a server of its own and runtime MCP servers are per process, so the rules allow that thread's servers and no other thread's. When the thread's session ends, its servers are taken off before its OpenCode server stops, and Sotto's disconnect waits for both. OpenCode asks nothing about them, and Sotto's own rules decide what each tool may do (ADR-0020, ADR-0029).

**Side calls.** A side call (ADR-0026) is one `POST /api/experimental/generate` on the thread's own server, with the thread's model at its least effort and the instruction and material as its one prompt. A thread whose provider session is not known to exist, such as one whose creation's answer was lost, gets no side text, and no server is started for one, as a Grok Build thread with no session gets none. It creates no provider session and is one generation, not a turn with tools. Checked against 2.0.31 with a local model source signed in to Sotto's folder (`opencodeLive.test.ts`, #1106): the session list was the same before and after the call, and the one model request it caused carried a single user message and no `tools` field. The adapter also reads the session list before and after each call, and writes nothing when a provider session it did not make has appeared. OpenCode Zen's free models refuse the route with a 503 that names the model source (`service: "opencode"`), which Sotto does not retry the way it retries a folder still starting (`service: "plugin"`). A refused call writes no side text, and the first-message title, temporary branch or stand-in subject stays, as on Devin. There is no fallback to a provider session.

**Not yet.** Watcher is refused before its process starts, as on Devin. OpenCode is outside Usage's numeric history in this version (ADR-0078); a thread keeps its own per-turn token readout. (Superseded October 21, 2026: see the Usage amendment at the end.) There is no terminal-mode entry.

## Hosts and phones

The headless host runs the same adapter under the same gate, with its own Sotto OpenCode folder under its data directory (`<dataDirectory>/opencode/{data,config,state,cache}`, checked on a headless host with OpenCode 2.0.31 itself), so a paired host offers OpenCode where the host machine has OpenCode 2 installed, on the model sources signed in to in that folder. The iPhone and Android clients name the provider, show a model's model source beside it, and may open threads on it. This is #1107; until it landed a headless host held OpenCode whatever its Owl answers were (`heldOnHost`), and Settings > Hosts drew no OpenCode tile. Host protocol version 1 carries provider IDs, but a desktop from before OpenCode reads them against a list without `opencode` and refuses a whole shell that names one, so OpenCode has a host feature of its own, `provider-opencode`: a host sends OpenCode's provider row, models, projects and threads only to a client whose hello accepts it, and hides every OpenCode thread from any other client as a phone's Watcher threads are hidden. Both phones accept it from #1107 on; an older phone, which reads provider IDs as plain strings, would only have named OpenCode "The agent". The rest of the hosts section is the amendment below.

## Privacy

Sotto itself contacts no new host for OpenCode: its update check reads `registry.npmjs.org`, which the README already names, and Sotto's servers turn OpenCode's own update check off. OpenCode's client talks to the model sources it is signed in to, as every provider's client talks to its provider: OpenCode Zen's models run on `opencode.ai`. The README says so in the change that adds the provider (#1103), and names `opencode.ai` among the makers a host may download a client from in the change that installs and updates it (#1104).

## Amended October 16, 2026: signing in and updating (#1104)

Zach picked variant A of the [sign-in prototype](https://github.com/millZach/Sotto/blob/prototype/opencode-sign-in/docs/prototypes/opencode-sign-in-prototype.html) the same day: a **Model sources** block on the OpenCode tile and an **Add a model source** dialog, with no offer to copy sign-ins from the user's own OpenCode. Building it settled these, checked on a scratch OpenCode 2.0.31 folder with a fake model source and made-up keys only:

- **Who is signed in is read without a secret.** `GET /api/integration` lists every model source with its sign-ins as `connections`, each a credential ID, label and method and never its value. Sotto reads the Model sources block from that and signs out with `DELETE /api/credential/{id}`; it never calls `GET /api/credential`, which answers with the secrets themselves.
- **OpenCode keeps a key without trying it.** `connect/key` answered 204 to a made-up key, and to an empty one, without one request reaching the model source, and the model list did not change either. So Sotto refuses an empty key itself, the tile says after a key sign-in that OpenCode tries the key when a thread first uses it, and a turn a signed-in source refuses says which source refused the sign-in and to sign out and paste the key again.
- **Sign-ins run on a short-lived server** of Sotto's own on its OpenCode folder, started on first use while OpenCode is connected and stopped a minute after its last use, except while a browser sign-in waits, because OpenCode keeps a waiting sign-in in that server's memory. A key passes from the window to main once and from main to that server once; the page OpenCode gives is opened from main, only when it is `https:`. OpenCode starts device-code sign-ins as `auto` and gives the code in its instructions, so the dialog shows a code when the instructions hold one, a field when the mode is `code`, and otherwise that the page finishes by itself. Methods OpenCode calls legacy, its environment variables and its commands are left out, and so is a method whose form asks something Sotto cannot draw.
- **A sign-in moves threads like a client update.** Each thread server reads the sign-ins when it starts, so after a sign-in or sign-out every thread server becomes an outdated process (ADR-0038) and moves to a fresh one as its thread goes idle; the catalog is read again at once for the model menu.
- **Updates.** OpenCode 1 connects as too old rather than as not startable, so first-run setup offers OpenCode 2's install guide for it; the guide is `opencode.ai/v2/docs/`, since `opencode.ai/docs` installs OpenCode 1. `opencode upgrade` runs on Sotto's OpenCode folders and the shared allow-list, like every OpenCode process Sotto starts. A copy Homebrew owns is named by its Cellar formula (`brew upgrade opencode` or `brew upgrade opencode-v2`), one scoop owns by its app (`scoop update opencode2`), and one pacman owns by the package whose record holds the program.

- **Host setup** stays on Codex, Claude Code and Grok Build. #1106 is on this branch now and gives a local OpenCode thread Sotto's tools, but a setup thread has not been checked running on OpenCode: its check wait as `timeout.execution`, the asking mode it starts in, and the Add host request card.

- **A prompt whose answer was lost keeps its thread server for a minute.** Running the host contract on OpenCode found that a thread nobody watched had its server stopped while OpenCode might still be taking a prompt whose acknowledgement was lost, ending that turn and the stream that would confirm it. The server is now kept while such a prompt is unconfirmed, for at most a minute from when its answer was lost, since a cold start can spend most of a minute before the prompt is asked; after that the next open reads it from history.

## Amended October 21, 2026: OpenCode in Usage

Zach decided on October 21, 2026 that Usage (ADR-0083) counts OpenCode's work in Sotto's threads, and leaves OpenCode off Subscriptions entirely. This replaces the Usage sentence under "Not yet". OpenCode's usage exists only where both its own gate and Usage's are on.

**What is counted.** Each OpenCode prompt Sotto sends counts as an accepted prompt once OpenCode's echo of it arrives. Tokens come from each finished step, `session.step.ended`, one row per step, named by the provider session and the step's assistant message ID. Reading the session back gives the same rows from its history, so a step seen live and again counts once, and the session total `session.usage.updated` reports is never added on top. OpenCode counts cache reads and writes apart from input, and reasoning apart from output, and prices reasoning as output, so Usage's input is all three input figures and its output includes reasoning, the way Codex and Claude Code report them. The model is the one the step said it ran on, as `provider_id/model_id`. A step from before Clear usage is not counted again. Nothing is read from the user's own OpenCode folders, which this record keeps Sotto out of, so OpenCode used outside Sotto is not counted.

**No subscription limits.** OpenCode's server has no route that reports account limits, and the only source of any is OpenCode Zen's own billing, which needs a second key; the one-key rule (AGENTS.md) rules that out. So OpenCode has no Subscriptions card, gauge, ring or line saying its limits cannot be read, and nothing asks it for any.

## Amended October 24, 2026: the config OpenCode finds for itself (#1425)

Zach decided to say this rather than stop it. Sotto's OpenCode folder holds its sign-ins and its own servers, but OpenCode 2 also looks for config wherever a thread runs, as it does when the user runs it, and Sotto passes it the user's home folder in the shared environment. Read from OpenCode 2.0.31's `packages/core/src/config/discovery.ts` (2.1.4's is the same), every OpenCode process Sotto starts reads:

- **The thread's project and every folder above it, to the drive's root:** an `opencode.json` or `opencode.jsonc`, and the `.opencode`, `.claude` and `.agents` folders in each. For a project under the home folder that includes the user's own `~/.opencode`, and an `opencode.json` in a folder above a project applies to all of its threads.
- **Always:** `~/.claude` and `~/.agents` in the user's home folder.
- **OpenCode's system folder:** `%ProgramData%\opencode` on Windows, `/Library/Application Support/opencode` and any managed preferences profile on macOS, and `/etc/opencode` on Linux.

What these hold applies to Sotto's OpenCode threads: model sources and models, MCP servers, plugins, agents, commands, skills and instructions. A plugin or an MCP server named there runs in the thread's OpenCode process. Permission is still Sotto's: a thread's permission mode is set as rules on its own provider session, which win over a project's (Permissions, above), so a file here cannot widen what a thread's mode asks about (checked against 2.0.31).
