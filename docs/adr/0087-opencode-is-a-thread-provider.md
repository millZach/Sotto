# OpenCode is a thread provider

Accepted October 16, 2026. Zach asked for OpenCode the way T3 Code has it, and chose the shape the same day: an Owl feature (ADR-0072), OpenCode 2 only, a full Threads provider as Muse is (ADR-0079), a data folder of Sotto's own, and model menu variant C, model source first. He first chose to share the data folder of the OpenCode he runs himself, and changed that the same day after a scratch test (see Sign-in and the data folder). The wire facts below were checked live against OpenCode 2.0.31 on the Windows laptop on October 16, 2026, and T3 Code's two OpenCode adapters were read at `e58a4857`; [the research note](../research/2026-10-16-t3-opencode.md) records both.

OpenCode joins Codex, Claude Code, Grok Build, Devin and Muse as a thread provider, id `opencode`, shown as **OpenCode**. Its adapter speaks OpenCode 2's HTTP server, not its ACP mode: one `opencode serve --hostname=127.0.0.1 --port=0` per thread (ADR-0038), reached on the port it prints with HTTP Basic and a password Sotto makes for that process alone, with live work read from the server's event stream. Several servers share Sotto's own OpenCode folder once its database exists, so the first server on that folder while it has none starts alone. A server is stopped with its process tree, because stopping the server alone leaves a running tool's processes behind on Windows. That holds for a server that exits on its own too: its tools outlive it, so Sotto ends them, on Windows by the parent each one still records and elsewhere through the server's process group. Each server is written down under Sotto's OpenCode folder while it runs, with its PID, when Sotto started it and which Sotto process did, and the record goes when the server and what it left are gone. A Sotto that crashes leaves its records, and the next connect ends the servers they name, with their tools, before it starts any: only a process that still has the recorded PID, started when the record says and running OpenCode's server, is ended, and a record whose Sotto is still running is left to it. On Windows Node's job object already ends a server with Sotto (checked against 2.0.31 by killing its parent outright), so there the sweep ends only the tools a crash left; on macOS and Linux the server runs on in its own process group until the sweep. OpenCode ignores the end of its input, so it cannot be stopped the way Muse and Grok Build stop when Sotto goes.

## OpenCode 2, not 1

OpenCode ships two lines. The 1.x line (`opencode-ai`, `opencode.ai/install`, scoop's `opencode`, the tap's `opencode`, the desktop app) and the 2.x line (`@opencode/cli`, `opencode.ai/v2/install`, Homebrew core, the tap's `opencode-v2`, scoop's `versions/opencode2`, Arch's `extra`) have different servers, and T3 Code keeps an adapter for each. Sotto supports 2 only. The verified version is 2.0.31; a 1.x client, or a 2.x older than it, is refused at connect with the version it reported and where OpenCode 2 comes from. OpenCode 2 prints its version as `opencode v2.0.31`.

## The gate

OpenCode is an Owl feature (`opencode` in `src/shared/owlFeatures.ts`), held off stable the way Muse is: a stand-in host that connects nothing and refuses work in words, provider lists that ask the gate before showing an OpenCode tile or row, and saved records left whole so returning to Owl restores the provider. Muse's gate checks are hand-written at each site; OpenCode's work first turns them into one gate per provider that both use, so a third held provider is one entry rather than another two dozen sites.

## Sign-in and the data folder

OpenCode keeps its own sign-ins, one per model source, and Sotto stores no key for it. Sotto's OpenCode servers use a folder of Sotto's own: every OpenCode process Sotto starts (a thread's server, the server that checks the client when it connects, and any later side call) runs with `XDG_DATA_HOME`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME` and `XDG_CACHE_HOME` pointing at `opencode/data`, `opencode/config`, `opencode/state` and `opencode/cache` under Sotto's user data, or under its data directory on a headless host, made on first use. The user's own XDG values are never passed through, and the user's own OpenCode folders are never read or written. The environment its processes get is otherwise the shared allow-list without other providers' keys.

Zach first chose to share his own OpenCode folder, so a thread would run on the sign-ins, settings and skills of the OpenCode he runs. A scratch test the same day showed that OpenCode 2 opening the folder OpenCode Desktop 1.19.3 uses rewrites part of its database for good, emptying its event log, dropping three of its tables and rebuilding its workspaces, and that afterwards the two keep diverging histories under the same session IDs. Zach saw that and chose a separate folder on October 16, 2026. So:

- Sotto's folder starts with no sign-ins. A fresh install lists only OpenCode Zen's free models until the user signs in to a model source inside it (#1104 adds the sign-in), and a connected OpenCode says no model source is signed in yet.
- Grants the user saved in their own OpenCode do not reach Sotto's threads, and Sotto never creates one: it answers OpenCode only with its one-time allow or its reject.
- The user's own OpenCode never sees Sotto's provider sessions. OpenCode does not lock a provider session to one process, so Sotto drives a thread's provider session only from that thread's own server.

Sotto's servers run with `share` set to `disabled`, so a thread is never published as an OpenCode share link, and with OpenCode's own update check off, so a thread's server neither checks for nor installs a new client.

## Finding and updating the client

Settings gives OpenCode the same connection, version, model and update controls as the other providers. Sotto finds `opencode` by its CLI lookup (ADR-0036), plus `~/.opencode/bin`, where the v2 install script puts it. Updates follow ADR-0042: the channel that installed the client updates it. An npm install is checked against `@opencode/cli` on `registry.npmjs.org`, which the README already names, and updated by Sotto's npm runner. A copy npm does not own, such as the v2 install script's, updates itself with `opencode upgrade`. A copy Homebrew, scoop or pacman owns shows the command to run by hand. Sotto never moves an install between the 1.x and 2.x packages.

## Permissions

A thread's permission mode becomes its provider session's rule set, sent when the provider session is created and changed while it lives: **Ask for approval** asks for every action OpenCode's own agent rules do not already decide, **Auto-accept edits** allows edits, and **Full access** allows everything. OpenCode has no mode of its own that matches **Automatic**, so it is not offered. Concretely, **Ask for approval** and **Auto-accept edits** set commands, steps outside the project folder, web fetches, web searches, subagents and, under Ask for approval, edits to ask, as Claude Code and Devin ask before reaching the web and a subagent runs on rules of its own; they deny nothing: OpenCode Zen's free models refuse a provider session whose rules take a tool away, and take this one (checked against 2.0.31). A project's own `opencode.json` rules apply where the session's name nothing, but cannot widen what they ask for: with the project allowing edits, web fetches and commands, the session's asks were still asked, and with the session allowing everything, the project's own ask for edits was not (checked against 2.0.31). Project config stays on, since it also carries the user's own MCP servers and instructions. A permission OpenCode asks for arrives with the files and diff it would change and is shown as a request card. The user answers every one (ADR-0004) with allow once or reject, and a reject reaches the model as a failed tool call, so the turn goes on. Disconnecting sends no decision.

## Questions

OpenCode's question tool arrives as a form. A form Sotto can draw, with text, number, yes-or-no and choice fields, is shown as a question card and answered with the user's words. One it cannot draw, such as a field shown only for another field's answer, is cancelled with a sentence saying so, and the model is told.

## Models and the model menu

Every model OpenCode lists is offered under its **model source**: where it runs, which is OpenCode Zen for the free models and otherwise a company the user signed in to inside Sotto's OpenCode folder, such as Anthropic, OpenAI or OpenRouter. The model menu opens on OpenCode's model sources and then shows the chosen source's models, as Zach picked from the [prototype](https://github.com/millZach/Sotto/blob/da06200653ea228993b00a44757da509d669cd56/docs/prototypes/opencode-model-menu-prototype.html) (variant C); typing searches every source at once. The chip shows the OpenCode mark and names the source, so an OpenCode thread on an Anthropic model never reads as a Claude Code thread. A model's variants are its effort levels in Sotto's order, and its image input decides whether images can be attached. OpenCode's mark is adapted from T3 Code's (MIT).

## What an OpenCode thread can do in this first version

Streaming replies with reasoning, tools, file changes and commands as thread activity; steering a running turn and queueing behind it; stopping; images; effort per turn; model and permission changes on the live provider session; resume after Sotto restarts (ADR-0076), where a turn whose server died reads as stopped rather than running forever. One OpenCode execution can carry several prompts, so the adapter follows each prompt by its own message, not by the execution.

**Sotto's tools.** They reach an OpenCode thread as a remote MCP server added to that thread's own server, with the thread's bearer token, so its browser, visuals and thread tools work there. The rule set allows that server's tools and no other thread's, as Claude Code's launch allows Sotto's tools by name and Grok Build's own one-time allow admits them. OpenCode asks nothing about them, and Sotto's own rules decide what each tool may do (ADR-0020).

**Side calls.** A side call (ADR-0026) uses OpenCode's stateless generation route on the thread's own server, with the thread's model. It creates no provider session, so nothing appears in the session list of Sotto's OpenCode folder, and it is one generation, not a turn with tools. It was only tried against OpenCode Zen, whose free models refuse it, so ticket #1106 checks on a signed-in model source that it lists nothing and offers the model no tools. Where it is refused or cannot be shown to keep both promises, OpenCode writes no side text, and the first-message title, temporary branch or stand-in subject stays, as on Devin.

**Not yet.** Watcher is refused before its process starts, as on Devin. OpenCode is outside Usage's numeric history in this version (ADR-0078); a thread keeps its own per-turn token readout. There is no terminal-mode entry.

## Hosts and phones

The headless host runs the same adapter under the same gate, with its own Sotto OpenCode folder under its data directory (`<dataDirectory>/opencode/{data,config,state,cache}`, checked on a headless host with OpenCode 2.0.31 itself), so a paired host offers OpenCode where the host machine has OpenCode 2 installed, on the model sources signed in to in that folder. The iPhone and Android clients name the provider, show a model's model source beside it, and may open threads on it. This is #1107; until it landed a headless host held OpenCode whatever its Owl answers were (`heldOnHost`), and Settings > Hosts drew no OpenCode tile. Host protocol version 1 carries provider IDs, but a desktop from before OpenCode reads them against a list without `opencode` and refuses a whole shell that names one, so OpenCode has a host feature of its own, `provider-opencode`: a host sends OpenCode's provider row, models, projects and threads only to a client whose hello accepts it, and hides every OpenCode thread from any other client as a phone's Watcher threads are hidden. Both phones accept it from #1107 on; an older phone, which reads provider IDs as plain strings, would only have named OpenCode "The agent". The rest of the hosts section is the amendment below.

## Privacy

Sotto itself contacts no new host for OpenCode: its update check reads `registry.npmjs.org`, which the README already names, and Sotto's servers turn OpenCode's own update check off. OpenCode's client talks to the model sources it is signed in to, as every provider's client talks to its provider: OpenCode Zen's models run on `opencode.ai`. The README says so in the change that adds the provider (#1103), and names `opencode.ai` among the makers a host may download a client from in the change that installs and updates it (#1104).

## Amended October 16, 2026: signing in and updating (#1104)

Zach picked variant A of the [sign-in prototype](https://github.com/millZach/Sotto/blob/prototype/opencode-sign-in/docs/prototypes/opencode-sign-in-prototype.html) the same day: a **Model sources** block on the OpenCode tile and an **Add a model source** dialog, with no offer to copy sign-ins from the user's own OpenCode. Building it settled these, checked on a scratch OpenCode 2.0.31 folder with a fake model source and made-up keys only:

- **Who is signed in is read without a secret.** `GET /api/integration` lists every model source with its sign-ins as `connections`, each a credential ID, label and method and never its value. Sotto reads the Model sources block from that and signs out with `DELETE /api/credential/{id}`; it never calls `GET /api/credential`, which answers with the secrets themselves.
- **OpenCode keeps a key without trying it.** `connect/key` answered 204 to a made-up key, and to an empty one, without one request reaching the model source, and the model list did not change either. So Sotto refuses an empty key itself, the tile says after a key sign-in that OpenCode tries the key when a thread first uses it, and a turn a signed-in source refuses says which source refused the sign-in and to sign out and paste the key again.
- **Sign-ins run on a short-lived server** of Sotto's own on its OpenCode folder, started on first use while OpenCode is connected and stopped a minute after its last use, except while a browser sign-in waits, because OpenCode keeps a waiting sign-in in that server's memory. A key passes from the window to main once and from main to that server once; the page OpenCode gives is opened from main, only when it is `https:`. OpenCode starts device-code sign-ins as `auto` and gives the code in its instructions, so the dialog shows a code when the instructions hold one, a field when the mode is `code`, and otherwise that the page finishes by itself. Methods OpenCode calls legacy, its environment variables and its commands are left out, and so is a method whose form asks something Sotto cannot draw.
- **A sign-in moves threads like a client update.** Each thread server reads the sign-ins when it starts, so after a sign-in or sign-out every thread server becomes an outdated process (ADR-0038) and moves to a fresh one as its thread goes idle; the catalog is read again at once for the model menu.
- **Updates.** OpenCode 1 connects as too old rather than as not startable, so first-run setup offers OpenCode 2's install guide for it; the guide is `opencode.ai/v2/docs/`, since `opencode.ai/docs` installs OpenCode 1. `opencode upgrade` runs on Sotto's OpenCode folders and the shared allow-list, like every OpenCode process Sotto starts. A copy Homebrew owns is named by its Cellar formula (`brew upgrade opencode` or `brew upgrade opencode-v2`), one scoop owns by its app (`scoop update opencode2`), and one pacman owns by the package whose record holds the program.


## Amended October 17, 2026: hosts and phones (#1107)

- **Sign-in on a host uses the same dialog.** #1107's issue said a host's tile would show OpenCode's sign-in command, but that predates Zach's pick of the Add a model source dialog, and a command run on the host by hand cannot reach Sotto's folder there. So a connected host's OpenCode gets the Model sources block under its tiles in Settings > Hosts, and its Add a model source dialog drives the host's own OpenCode over the host connection: one `opencode-sign-in` request per call, behind the `opencode-sign-in` host feature, which only a headless host whose OpenCode runs offers, and only to a desktop. A host without it gets a sentence saying to put this computer's version of the host on it. A key goes from this computer's window to its main once, from main to the host once, and from the host to its OpenCode once; neither side's Sotto keeps or logs it. Only the client that started a browser sign-in reads, finishes or cancels it. The page opens in this computer's browser: the host answers with the page's address, which this computer's main checks is https and opens (ADR-0037).
- **A browser sign-in that returns to OpenCode's own machine is refused on a host.** Checked against a scratch OpenCode 2.0.31 on October 17: every `auto` sign-in that gives no code (DigitalOcean, OpenAI's ChatGPT sign-ins, Poe) sends the browser back to `localhost` or `127.0.0.1` on the machine OpenCode runs on, so a browser on this computer cannot finish one for a host. The ones that give a device code (xAI's SuperGrok, OpenAI's Codex device code) finish by themselves on OpenCode's side, and the `code` ones take the code the page shows. On a host, Sotto cancels an `auto` sign-in without a code as soon as it starts and says to choose another way, such as a key, and the dialog does not offer that method again while Settings > Hosts stays open; OpenCode names a method's mode only when it starts, so the choice cannot be made earlier.
- **Updates on a host** follow #1104's channels: the host's own update line runs `opencode upgrade` on its Sotto OpenCode folder for a copy in `~/.opencode/bin`, npm for an npm copy, and shows a manager's command for the rest. The host provider job's brief restores OpenCode's install recipe, with OpenCode 2's channels and `~/.opencode/bin` first in the lookup.
- **Host setup** stays on Codex, Claude Code and Grok Build until OpenCode's Sotto tools (#1106) are on the same branch and a setup thread has been checked running on OpenCode: its check wait as `timeout.execution`, the asking mode it starts in, and the Add host request card.
- **A prompt whose answer was lost keeps its thread server for a minute.** Running the host contract on OpenCode found that a thread nobody watched had its server stopped while OpenCode might still be taking a prompt whose acknowledgement was lost, ending that turn and the stream that would confirm it. The server is now kept while such a prompt is unconfirmed, for at most a minute; after that the next open reads it from history.
