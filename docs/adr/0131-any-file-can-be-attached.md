# Any file can be attached

## Status

Accepted October 24, 2026, as an Owl feature (`attach-any-file`). Zach asked to attach any file and picked B, Pills, of `docs/prototypes/attach-any-file-prototype.html` (kept as the tag `prototype/attach-any-file`); the decisions and the build are in `docs/plans/attach-any-file.md`. Amends [ADR-0031](0031-images-are-staged-once-and-carried-by-handle.md), which staged images only and had every adapter hand its provider images alone, and [ADR-0030](0030-screenshots-are-scaled-to-the-longest-edge-a-model-reads.md) only by name: screenshots are still scaled, files never are. Builds on [ADR-0072](0072-sotto-owl-is-a-windows-preview-release-track.md) (Owl features). **Number provisional until merge** (docs/agents/domain.md).

## Context

The composer attached PNG, JPEG, GIF and WebP screenshots and nothing else. A user who wanted an agent to read a PDF, a log or an archive had to save it into the thread's folder and name it by hand.

The six providers differ in what they take as part of a prompt (research, October 24, 2026). Claude Code's stream-json input takes `image` blocks and, as a real Claude Code 2.1.310 run showed that day, base64 PDF `document` blocks. OpenCode takes `file` parts, a PDF among them for a model whose catalog lists PDF input. Codex's app-server has no input type for a file. Grok Build and Devin take text alone, and Muse images and text. Every one of them runs in a working folder its agent can read. The Anthropic API holds a request to 32 MB and a PDF to 100 pages under a 200K context, and a `document` block Claude cannot read stays in the session and fails every later turn.

## Decision

**1. An attachment is an image or a file.** An image is one of the four raster types and keeps every rule of ADR-0030 and ADR-0031: its signature is checked, it is scaled to the screenshot bound, and a chip draws it. Anything else is an **attached file**: any well-formed MIME type (`type/subtype`, lowercase, at most 127 characters), `application/octet-stream` when the browser gives none, whose bytes Sotto never inspects while staging. `isImageAttachment` in `src/shared/agents.ts` is the one test.

**2. Limits by kind.** An image is at most 10 MiB and the images in a set at most 20 MiB between them, as before, which keeps a Claude request under its 32 MB cap. A file is at most 25 MiB. A set holds at most 8 attachments and 50 MiB in all. The composer refuses each before it reads anything, in the plan's sentences; the schemas and the store check them again.

**3. One store, one handle.** A file is staged once and carried by handle exactly as an image is. The store keeps it as `attachments/<digest>.bin`, its MIME type in the index alone. `attachment-content` answers for images only, since a file draws no chip; a submitted preview names a file's handle for its tile and owns none of its bytes. Content is kept once per digest, but each handle keeps the type it was attached as: the same bytes attached as an image and as a file are an image and a file, so a text-only model is sent the file by path rather than refused it as an image. A handle describes kept content when the sizes agree and, for an image, the types agree, since an image's signature was checked for its type and a file's bytes never are. Content first kept as a file and then attached as an image is kept as that image from then on (`keepAsImage`): the image's file is written and indexed before the `.bin` goes, and a read that meets the move follows the new entry. A crash between the two leaves both files; at the next start the image's file wins and the `.bin` goes as a copy, whatever the index says, since the image's was written only after its signature was checked.

**4. Remote hosts take files in parts.** A file in base64 can be larger than a 16 MiB frame, so the host feature `file-staging` adds `stage-file-part`: at most 8 MiB of bytes a part, in order, each naming the upload, the file's name, type, size and digest. The host keeps one upload per paired client in memory, by its client ID however many sockets it opens, a new one replacing any other that client had under way, lets it go two minutes after its last part or when the client's last socket closes, and checks the size and digest once the last part arrives. Images still go by `stage-attachment`. A desktop asks a host that does not list the feature to keep no file, and says to update it; a desktop whose own Owl answer is off asks no host to keep a file at all.

**5. A file reaches the agent through its working folder.** This is what ADR-0031's "Adapters build the provider's form at the protocol boundary" now says for files. At the same boundary, where an adapter reads its staged images, `src/main/agents/attachedFiles.ts` copies each attached file into the thread's working folder, at `.sotto/attachments/<first 12 hex of its digest>/<safe name>`, beside the terminal's `.sotto/clipboard/`, and names it in a note the adapter adds to what the provider receives, apart from the user's words:

```
<sotto-attached-files>
The user attached these files. They are saved in this working folder:
- .sotto/attachments/3f2a9c1e0b7d/quarterly-report.pdf (quarterly-report.pdf, PDF, 2.4 MB)
</sotto-attached-files>
```

Every provider can read a file by its path, so every provider takes files, Grok and Devin included, which still refuse images. Claude gets the note as a text block of its own after the user's words, Codex as a `text` input item of its own, and OpenCode, Grok, Devin and Muse after the user's words in the text they send, Muse with the user's words as its display text.

- **The safe name** is the base name only: separators, control and bidi characters, `<>:"/\|?*` and whitespace runs become `-`, leading and trailing dots and spaces go, a Windows device name (`CON`, `NUL`, `COM1`...) is prefixed with `_`, and it is at most 120 characters with its extension kept, or `file` when nothing is left. It never holds a space, so it can be named as an `@path` token.
- **No traversal and no following links.** Every folder from `.sotto` down is checked with `lstat`, and a symbolic link, a junction or anything that is not a folder is refused, then checked once more where it resolves to. The file is written with `wx` and mode `0o644`, so nothing is made executable and nothing is overwritten. When it is already there with the same content, as when the same file is sent twice, it is used as it is; with different content the send is refused. `.sotto/attachments/.gitignore` holds `*`, written once with `wx`, so Git ignores the folder and nothing of the user's own changes. One already there is kept only while one of its lines is exactly `*`; otherwise the send is refused before anything is written, saying to put `*` back. Sotto never opens or runs what it wrote.
- **Refusals come before the provider hears anything**, each saying what happened, that nothing was sent and the draft is saved, and what to do. A thread with no working folder refuses files: "This thread has no working folder, so files cannot be attached. Remove them, then send again. Your draft is saved." A model without image support refuses images only, with ADR-0031's sentence.
- **Nothing logs** a name, a path or a byte.

**6. PDFs also go natively where a provider reads them.** Claude gets a `document` block (`source: { type: 'base64', media_type: 'application/pdf', data }`, `title` the file's name) and OpenCode a `file` part with a `data:application/pdf` URL when the thread's model lists `pdf` among its catalog's inputs. Because a block that fails poisons Claude's session, the rule is conservative (`src/main/agents/pdfPages.ts`): the bytes must start as a PDF, and the page count is read from the uncompressed page tree: every `N G obj ... endobj` object is read with stream bodies skipped and `%` comments outside strings left out, the leaf `/Type /Page` objects are counted, and the root page tree is the `/Pages` of the catalog the newest trailer's `/Root` names. The count stands only when there is at least one page and the leaves equal the root's `/Count`. A count that disagrees, a PDF that is encrypted or keeps objects in a compressed object stream, and anything the reader cannot follow count as unknown, and a PDF goes by path alone when its count is unknown, when it has more than 100 pages, or when it would push the message's native bytes, images included, past 20 MiB. The PDF is in the working folder and the note either way.

**7. The thread shows the user's words.** The origin's digest and the message text Sotto records are the user's own text. Wherever an adapter reads a user message back from the provider's own history, its stream or its session log (`claudeUserText`, Codex's `textOf` and its rollout reader, OpenCode's `recordUser`, Muse's `foldItem`, Grok's history and stream, Devin's replay), the note is taken off only when Sotto put it there: the reader tries the text without the note, in exactly the generated form, and keeps that only when the origin it then matches, by message ID or by the adapter's digest, recorded at least one attachment that is not an image (`readBackUserText`, or the same check where an adapter matches its own way). Otherwise the text is shown and matched as it is, so a prompt the user typed in the note's shape, on stable too, reads back whole, and a reader with no origin to check keeps the text whole. The thread never shows Sotto's note, after a reload or a restart too. Grok and Devin, which never carried images, now record the attachments' references on their origins, so a sent file's tile shows whichever way the message is read back.

**8. Owl first.** With `attach-any-file` off, the composer, its words, its limits and every sent message are exactly as before, main and the host refuse to stage anything but the four image types, and main refuses a send, a queued follow-up or a draft send that names a file all the same, a defence behind the composer. Main and the headless host read the answer once at start; a host lists `file-staging` only on its own answer.

## Consequences

- Private file bytes live beside staged images in `attachments/` on the machine that runs the thread, under the same ownership and one-hour rule. A sent file is also copied into the thread's working folder under `.sotto/attachments/`, where it stays until the user removes it, as `.sotto/clipboard/` does; the README says so under "Privacy and cost". A worktree removed with its thread takes its copies with it.
- A PDF sent to Claude or OpenCode goes as part of the prompt, to the same provider that already hears the thread. No new host is contacted.
- An attached file costs the provider a few lines of note and, for a native PDF, its bytes. A model that reads no images still takes files; only an image is refused there, by name.
- The note is visible to the agent as Sotto's words, not the user's, and an agent may still decide not to open a file it names. Sotto does not check that it did.
- The folder checks guard against a link that is already there. A link swapped in between the checks and the write is caught by the check of where the folder resolves to, but not between that check and the write itself; the working folder is the user's own, and an agent that can already write there can already write anywhere it reaches.
- Going back to a build from before this record is not safe with a file in a draft or the queue, for the reason ADR-0031 records for images: the older build cannot read the handle. Someone who must go back sends or clears those drafts and follow-ups first.
- `tests/integration/adapterContract.ts` sends a staged text file and a PDF through every adapter and checks the working folder, what the provider heard and the thread's text, after a restart where the fixture has one.

## Amendment, October 25, 2026: files from the iPhone

The iPhone attaches files to a reply, and opens a sent file on the phone. Zach chose these from `docs/prototypes/iphone-file-attach-prototype.html`: **A · Pills**, **Quick Look**, the **`attach-any-file`** switch, and the **iPhone's own words** for photos on a text-only model. Two of them need things this record and ADR-0031's October 3 amendment did not allow: a host request that hands the phone a sent file's bytes, and a copy of a file on the phone's disk while it is open.

**Where it is offered.** The reply box's + menu gains **Files** beside Photo library and Camera. It is offered when the thread's computer lists `file-staging`, which only a host whose own `attach-any-file` answer is on does (decision 4). A computer that doesn't list it keeps the item in the menu, unavailable, with the reason beneath it: "This computer cannot keep files yet. Update Sotto there to attach them." Files work on any model. A text-only model refuses only photos, in the phone's own words ("This thread's model can't take photos. Change the model on <computer> to attach them.").

**A file is read, not imported.** The system document picker runs outside the app and hands over only the files chosen. Sotto opens them in place (`asCopy: false`), reads each one's size from its resource values first, and refuses before reading anything past the limits: 25 MB a file, 50 MB in all, and 8 attachments with the photos. The sentences are the desktop's (decision 2). It then reads the bytes into memory under the file's security-scoped access and gives that access back. Nothing is copied into the app's folders, so a file waiting in a reply lives only in memory, as a photo does (ADR-0031, October 3). The type comes from the file's extension through UTType, and is `application/octet-stream` when there is none.

**Staging.** A file goes up with `stage-file-part` in 8 MiB parts (decision 4), on the same per-computer queue as photos, one large request at a time. The October 3 rules for staging again apply unchanged: a file staged 45 minutes ago or more, one staged over a connection that has since ended, and one in a refused reply put back in the box are staged again when the reply is sent. A reply's handles carry files as the desktop's do, and the computer delivers them through the thread's working folder like any other (decision 5).

**Look.** A file waits as a one-line pill under the photos, inside the words' column, as on the desktop: type symbol, the name cut in the middle so the extension stays, the size, and a remove button named "Remove <name>". While a file is uploading its pill shows a percentage. A sent file is the same pill above the words.

**A sent file opens in Quick Look.** A new host feature, `attachment-files`, adds one request, `attachment-file`. It names a thread, a message and an attachment, as `preview` does, plus a part index. The host answers only for a file that message carries and that its store still keeps, in parts of at most 8 MiB, since a 25 MB file is more than a frame: the part's bytes in base64, its index and the part count. It answers nothing for an image, which `preview` already serves. Naming the message rather than a bare digest means a phone can fetch only what a thread it reads carries. The request takes the socket's preview guard, as `preview` does, and the host holds one such read for each paired client across all its sockets, so one client has at most one file part being read for it. A file the host no longer keeps answers null, and the phone says so: "This file is no longer kept on <computer>, so it can’t open here. Look for it in the thread’s working folder there, under .sotto/attachments." A host that doesn't list the feature leaves sent files as they are today: their name, with "(open on the desktop)".

**The temporary copy.** Quick Look reads a file from disk, so this is the one place the phone writes what a reply carried. It writes it only for the file the user just pressed, only once all of its parts have arrived and match the handle's size and digest:

- into a new folder of random name under the app's temporary directory, under the file's safe name (decision 5's rule);
- with complete file protection, so it is unreadable while the phone is locked, and excluded from backup;
- one at a time: opening another file removes the first, and a copy written for a file no longer wanted is removed by its own folder, never the one being shown.

It is removed when the preview closes, when the app moves to the background, and, for anything a crash left, at the next launch. Its bytes are never logged. Quick Look's own Share button stays, so the user can save or send the file themselves, as they could from the desktop. That is the user's choice, not something Sotto does.

**Built on the shared reply box.** #1446 (photos to Watcher) moved the phone's reply box onto one box for a thread or Watcher. Files ride on it: the + menu, the eight attachments the photos and files share, and the per-computer queue are the box's. Only a thread's box offers Files. A file chosen in Files that is one of the four photo types goes as a photo, made ready as one from the library is. A sent file being brought back shows how much has come on its own pill, in place of its size, rather than on a page of its own, and Quick Look opens over whatever is showing once it is in.

**Not in this amendment.** Watcher's reply box on the phone (#1446 adds photos there) takes files later, through the same box abstraction. Files from the Android client follow ADR-0059's port.

Consequences:

- **No new host.** `HOST_FEATURES` gains `attachment-files`. Protocol version stays 1: a phone uses the request only when the host lists the feature, and a host never sends anything new unasked.
- **Privacy.** The README's "Privacy and cost" gains one sentence: an opened file sits in the iPhone app's temporary folder until its preview closes.
