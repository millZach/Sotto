# Muse is a thread provider

Accepted October 12, 2026. Zach chose the release shape the same day: an Owl feature (ADR-0072), a full Threads provider rather than a thread-only minimum, Muse's own sign-in with no key in Sotto, and paired hosts and the phone clients included. The wire facts below were checked live against Muse 1.1.1 on October 12, 2026; the verification note records the probes.

Muse joins Codex, Claude Code, Grok Build and Devin as a thread provider, id `muse`, shown as **Muse**. Its adapter speaks MSP, Muse's own machine protocol, over `muse serve` on stdio: one serve host process per thread (ADR-0038), identified at start, with the session loaded by `session/resume`, which serves the folded history and subscribes the connection to the view stream. `session/read` and `view/page` are in the published schema but the 1.1.1 client does not serve them, so history is read by resuming and the stream carries live work; a `view/gap` is answered by resuming again, and the adapter's one append path recognises what it already recorded. Unknown notifications and unknown item kinds are read for what they carry and never guessed at, as MSP promises additive growth.

## The gate

Muse is an Owl feature (`muse` in `src/shared/owlFeatures.ts`). On stable, main and the headless host register a stand-in host that connects nothing, lists nothing and refuses work in words, the renderer's provider lists ask the gate before showing a Muse tile or row, and the adapter's saved records (`muse-threads.json`, `muse-projects.json`, thread bindings) stay on disk untouched, so returning to Owl restores the provider whole. Its saved workspace organization, history, drafts, follow-ups and answer ownership are dormant too, including when stable clears ordinary history. Stable ignores Muse during provider discovery and uses an available ordinary default; saved Muse defaults stay parked until Owl restores them. Sending it to stable is the one-line `sentToStable` change ADR-0072 describes.

The restart-resume record stays dormant with its thread too (ADR-0076): a hidden Muse thread is not a deleted one. Resuming cannot prune or send its saved note while Muse is held. Update all (ADR-0077) uses Muse's existing native-feed updater when Muse is available; a client-version check from a Muse-held desktop refuses a target that would enumerate connected Muse rather than contacting its feed.

Usage's retained numeric history and native account limits (ADR-0078) cover Codex, Claude Code, Grok Build and Devin. Muse remains outside that contract in this version. Sending or steering a Muse thread retains its ordinary per-thread accounting without creating a Usage row or querying account limits. An Owl desktop with Muse enabled targets a matching Owl headless host, as one with Usage enabled does; the host still decides whether Muse is available from its own packaged version.

## Sign-in and the floor

Muse keeps its own sign-in (`muse login`, or credentials it stores itself); Sotto stores no key for it, and the environment its processes get is the shared allow-list without `META_API_KEY`, so a thread always runs on the account Muse holds, never on a key that happened to be in Sotto's environment. A host tile shows `muse login` as Devin's shows its command, because the sign-in runs on the host itself. The floor is Muse 1.1.1 speaking MSP 1 (ADR-0042): an older client or another MSP version is refused at connect with the version it reported. A client with no sign-in resolves no model catalog, which is the refusal the tile offers the sign-in command for.

## Finding and updating the client

Settings gives Muse the same connection, version, model and update controls as the other providers (ADR-0042). Muse's maker installer keeps a launcher, a `.muse-version` record and a versioned native binary in one directory. Sotto reads that bounded record and starts the corresponding native binary directly: connecting or starting a thread never invokes the launcher's background updater. An unrelated wrapper or an invalid record is not evidence of a usable native client.

Zach chose prototype A, retaining the existing provider page, and asked for the actual Muse logo. [Meta's Muse launch announcement](https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/) links to `muse.ai`, whose declared [product favicon](https://muse.ai/images/favicon/app-squiggle.svg) supplies the unchanged squiggle geometry. Sotto uses this current Muse product mark in the same theme role as its other provider marks; no separate Code-specific mark was established. The documentation SDK's purple M badge was a prototype placeholder and is not used. The [captured prototype](https://github.com/millZach/Sotto/blob/a495286160a60a4e29f409a80f4a773ecfa8a2d2/docs/prototypes/muse-provider-settings.prototype.html) is retained by `prototype/muse-provider-settings-973`, outside the implementation branch.

An update check reads only the installed channel's public feed on `api.meta.ai`; a failed check means the published version is unknown. Pressing Update reruns the maker's installer from `dev.meta.ai` into the same recognized maker-owned directory, with login and PATH changes disabled. The installer obtains its launcher and release information from `api.meta.ai` and its verified payload from `lookaside.facebook.com`. These requests carry no thread material. A manager-owned install stays that manager's to update; Sotto refuses to replace a copy whose ownership it cannot establish. The user signs in separately. The existing update coordinator checks the new client before handing idle threads to it, and working threads retain their process until they finish. The [Windows installer](https://dev.meta.ai/install.ps1), [macOS and Linux installer](https://dev.meta.ai/install.sh) and [public channel feed](https://api.meta.ai/muse-code/channels/muse-stable) were inspected on October 12, 2026.

## Permissions

MSP splits permission into a sandbox posture sealed when the host starts and an approval mode chosen per session. The sealed mode is a ceiling: a session may select only a mode at or below it, and on the checked machine the default ceiling refused both `allowAll` and `onRequest`. So which of Sotto's modes a Muse thread may be offered is probed, not assumed: connecting starts throwaway sessions on a memory-only host and offers only the modes the client accepted, beside **Ask for approval**, which a session always starts on (`promptUnmatched`, where the client's own policy decides what asks). **Automatic** is `onRequest` and **Full access** is `allowAll`, offered only where the probe could select them. An approval the client asks about arrives as a notification and is shown as a request card with Muse's own choice labels; the user answers every one (ADR-0004), and a plain allow or deny takes the one-time form of it. Disconnecting sends no decision: the host settles its own pending approvals when it ends.

## What a Muse thread can and cannot do in this first version

Streaming replies with reasoning, tools, file changes, commands, subagents, workflows, plans and compaction as thread activity; steering; images; effort per turn from MSP's closed tier list; model and permission changes on the live session; message origins through MSP's idempotency command IDs, which also finish a creation or a send whose acknowledgement was lost without repeating it.

This version of Sotto's Muse adapter does not attach Sotto's tool servers to a session. The published MSP schema includes MCP configuration, but that integration has not been checked at the supported client floor. A Muse thread therefore cannot be given Sotto's browser or thread tools, and cannot host Watcher: the adapter refuses a Watcher thread in plain words before its process starts, as Devin's does, and the browser surfaces say this provider does not support Sotto browser tools. Skills are not offered: MSP has no skill catalog a client may read. Token counts are shown without a price, because the catalog carries none Sotto could check. Muse is not a subscription reasoning provider: dictation cleanup and Watcher reasoning stay on the accounts ADR-0069 names, as Devin is outside them too. There is no terminal-mode entry yet.

## Hosts and phones

The headless host runs the same adapter under the same gate, read from its own release track, so a paired host offers Muse where the host machine has the client installed and signed in. The iPhone and Android clients name the provider and may open threads on it like any other; host protocol version 1 already carries provider IDs without a closed list on the desktop side, so no protocol change was needed.

## After review: side writing stays unavailable

The approval mode `denyUnmatched` denies only unmatched actions; a native policy may still allow matched tools. MSP at the checked floor publishes no independently enforced all-tools disable control. Muse therefore does not generate thread titles, branch names, commit messages or pull request drafts: side writing returns no text before any host is started, and the existing opening words, temporary branch or stand-in subject remain (ADR-0026). This replaces the earlier assumption that the strictest approval mode meant no tools. A future side-writing implementation needs a checked native mechanism that disables every tool before sending material. [Muse’s approval documentation](https://meta-models.github.io/muse-code-sdk/next/guides/msp-concepts/approvals/) and [the stable MSP schema](https://github.com/meta-models/muse-code-sdk/blob/a0c8611b382584eb5091942b477f30e92e1c8d18/schema/msp/stable/msp.schema.json) record the distinction.
