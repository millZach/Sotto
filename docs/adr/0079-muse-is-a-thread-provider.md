# Muse is a thread provider

Accepted October 12, 2026. Zach chose the release shape the same day: an Owl feature (ADR-0072), a full Threads provider rather than a thread-only minimum, Muse's own sign-in with no key in Sotto, and paired hosts and the phone clients included. The wire facts below were checked live against Muse 1.1.1 on October 12, 2026; the verification note records the probes.

Muse joins Codex, Claude Code, Grok Build and Devin as a thread provider, id `muse`, shown as **Muse**. Its adapter speaks MSP, Muse's own machine protocol, over `muse serve` on stdio: one serve host process per thread (ADR-0038), identified at start, with the session loaded by `session/resume`, which serves the folded history and subscribes the connection to the view stream. `session/read` and `view/page` are in the published schema but the 1.1.1 client does not serve them, so history is read by resuming and the stream carries live work; a `view/gap` is answered by resuming again, and the adapter's one append path recognises what it already recorded. Unknown notifications and unknown item kinds are read for what they carry and never guessed at, as MSP promises additive growth.

## The gate

Muse is an Owl feature (`muse` in `src/shared/owlFeatures.ts`). On stable, main and the headless host register a stand-in host that connects nothing, lists nothing and refuses work in words, the renderer's provider lists ask the gate before showing a Muse tile or row, and the adapter's saved records (`muse-threads.json`, `muse-projects.json`, thread bindings) stay on disk untouched, so returning to Owl restores the provider whole. Its saved workspace organization, history, drafts, follow-ups and answer ownership are dormant too, including when stable clears ordinary history. Stable ignores Muse during provider discovery and uses an available ordinary default; saved Muse defaults stay parked until Owl restores them. Sending it to stable is the one-line `sentToStable` change ADR-0072 describes.

Amended October 16, 2026 (#1102). Muse's gate is now the general **held provider** gate that ADR-0087 needs for OpenCode: Muse is one entry in `src/shared/heldProviders.ts`, its checks live in `src/main/agents/heldProviderGate.ts`, and the stand-in is a `HeldProviderHost` for Muse. What stable does with Muse is unchanged, word for word, including the saved `dormantMuseConfiguration` record.

The restart-resume record stays dormant with its thread too (ADR-0076): a hidden Muse thread is not a deleted one. Resuming cannot prune or send its saved note while Muse is held. Update all (ADR-0077) uses Muse's existing native-feed updater when Muse is available; a client-version check from a Muse-held desktop refuses a target that would enumerate connected Muse rather than contacting its feed.

Usage's retained numeric history and native account limits (ADR-0078) cover Codex, Claude Code, Grok Build and Devin. Muse remains outside that contract in this version (superseded October 21, 2026: see the amendment at the end). Sending or steering a Muse thread retains its ordinary per-thread accounting without creating a Usage row or querying account limits. An Owl desktop with Muse enabled targets a matching Owl headless host, as one with Usage enabled does; the host still decides whether Muse is available from its own packaged version.

## Sign-in and the floor

Muse keeps its own sign-in (`muse login`, or credentials it stores itself); Sotto stores no key for it, and the environment its processes get is the shared allow-list without `META_API_KEY`, so a thread always runs on the account Muse holds, never on a key that happened to be in Sotto's environment. A host tile shows `muse login` as Devin's shows its command, because the sign-in runs on the host itself. The floor is Muse 1.1.1 speaking MSP 1 (ADR-0042): an older client or another MSP version is refused at connect with the version it reported. A client with no sign-in resolves no model catalog, which is the refusal the tile offers the sign-in command for. October 16, 2026: only an empty `bundledCatalog` is read as no sign-in. Checked live against 1.4.8 and 1.4.9, a client with no sign-in answers `model/list` with `bundledCatalog` and no models, online or offline, and a signed-in one answers `providerCatalog` with its models even with its network cut off. An empty catalog from any other source is refused as a client that cannot start, saying Muse listed no models, because signing in again would not change it. MSP 1 requires the source, so a catalog that names none is read the same way.

## Finding and updating the client

Settings gives Muse the same connection, version, model and update controls as the other providers (ADR-0042). Muse's maker installer keeps a launcher, a `.muse-version` record and a versioned native binary in one directory. Sotto reads that bounded record and starts the corresponding native binary directly: connecting or starting a thread never invokes the launcher's background updater. An unrelated wrapper or an invalid record is not evidence of a usable native client.

Zach chose prototype A, retaining the existing provider page, and asked for the actual Muse logo. [Meta's Muse launch announcement](https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/) links to `muse.ai`, whose declared [product favicon](https://muse.ai/images/favicon/app-squiggle.svg) supplies the unchanged squiggle geometry. Sotto uses this current Muse product mark in the same theme role as its other provider marks; no separate Code-specific mark was established. The documentation SDK's purple M badge was a prototype placeholder and is not used. The [captured prototype](https://github.com/millZach/Sotto/blob/a495286160a60a4e29f409a80f4a773ecfa8a2d2/docs/prototypes/muse-provider-settings.prototype.html) is retained by `prototype/muse-provider-settings-973`, outside the implementation branch.

An update check reads only the installed channel's public feed on `api.meta.ai`; a failed check means the published version is unknown. Pressing Update reruns the maker's installer from `dev.meta.ai` into the same recognized maker-owned directory, with login and PATH changes disabled. The installer obtains its launcher and release information from `api.meta.ai` and its verified payload from `lookaside.facebook.com`. These requests carry no thread material. A manager-owned install stays that manager's to update; Sotto refuses to replace a copy whose ownership it cannot establish. The user signs in separately. The existing update coordinator checks the new client before handing idle threads to it, and working threads retain their process until they finish. The [Windows installer](https://dev.meta.ai/install.ps1), [macOS and Linux installer](https://dev.meta.ai/install.sh) and [public channel feed](https://api.meta.ai/muse-code/channels/muse-stable) were inspected on October 12, 2026.

## Permissions

MSP splits permission into a sandbox posture sealed when the host starts and an approval mode chosen per session. The sealed mode is a ceiling: a session may select only a mode at or below it, and on the checked machine the default ceiling refused both `allowAll` and `onRequest`. So which of Sotto's modes a Muse thread may be offered is probed, not assumed: connecting starts throwaway sessions on a memory-only host and offers only the modes the client accepted, beside **Ask for approval**, which a session always starts on (`promptUnmatched`, where the client's own policy decides what asks). **Automatic** is `onRequest` and **Full access** is `allowAll`, offered only where the probe could select them. An approval the client asks about arrives as a notification and is shown as a request card with Muse's own choice labels; the user answers every one (ADR-0004), and a plain allow or deny takes the one-time form of it. Disconnecting sends no decision: the host settles its own pending approvals when it ends.

## What a Muse thread can and cannot do in this first version

Streaming replies with reasoning, tools, file changes, commands, subagents, workflows, plans and compaction as thread activity; steering; images; effort per turn from MSP's closed tier list; model and permission changes on the live session; message origins through MSP's idempotency command IDs, which also finish a creation or a send whose acknowledgement was lost without repeating it.

October 14, 2026: the tool servers half of this paragraph is replaced by **Amendment: Muse threads get Sotto's tools** below. October 16, 2026: the Watcher half is replaced by **Amendment: Watcher runs on Muse**. This version of Sotto's Muse adapter does not attach Sotto's tool servers to a session. The published MSP schema includes MCP configuration, but that integration has not been checked at the supported client floor. A Muse thread therefore cannot be given Sotto's browser or thread tools, and cannot host Watcher: the adapter refuses a Watcher thread in plain words before its process starts, as Devin's does, and the browser surfaces say this provider does not support Sotto browser tools. Skills are not offered: MSP has no skill catalog a client may read. Token counts are shown without a price, because the catalog carries none Sotto could check. Muse is not a subscription reasoning provider: dictation cleanup and Watcher reasoning stay on the accounts ADR-0069 names, as Devin is outside them too. There is no terminal-mode entry yet.

## Hosts and phones

The headless host runs the same adapter under the same gate, read from its own release track, so a paired host offers Muse where the host machine has the client installed and signed in. The iPhone and Android clients name the provider and may open threads on it like any other; host protocol version 1 already carries provider IDs without a closed list on the desktop side, so no protocol change was needed.

## After review: side writing stays unavailable

The approval mode `denyUnmatched` denies only unmatched actions; a native policy may still allow matched tools. MSP at the checked floor publishes no independently enforced all-tools disable control. Muse therefore does not generate thread titles, branch names, commit messages or pull request drafts: side writing returns no text before any host is started, and the existing opening words, temporary branch or stand-in subject remain (ADR-0026). This replaces the earlier assumption that the strictest approval mode meant no tools. A future side-writing implementation needs a checked native mechanism that disables every tool before sending material. [Muse’s approval documentation](https://meta-models.github.io/muse-code-sdk/next/guides/msp-concepts/approvals/) and [the stable MSP schema](https://github.com/meta-models/muse-code-sdk/blob/a0c8611b382584eb5091942b477f30e92e1c8d18/schema/msp/stable/msp.schema.json) record the distinction.

## Amendment: Muse threads get Sotto's tools (October 14, 2026)

Zach decided on October 14 (#1039) that Muse threads get Sotto's scoped tools the way Claude Code, Codex and Grok Build threads do: the browser, the visual tool and pull request babysitting, and the delegation tools when they come. A test that day against Muse 1.4.7, then the native Windows 1.4.8, showed how MSP takes them, without running a turn.

**Asked for, not assumed.** `session/start` and `session/resume` take `config.mcpServers` only on a connection granted the `sessionMcp` capability; without it the start fails `capabilityRequired`. Every `muse serve` host Sotto starts asks for it at `initialize`, and a thread's host gives its session Sotto's servers only when it was granted. A client that does not grant it gets nothing, and its sessions start as before. Such a thread says so (`sottoToolsWithheld`), and Sotto offers it none of the controls that need the tools: no visuals, no babysitting tools, no Share with agent in Tools. The 1.1.1 floor stays: the grant is the check, not the version, and a client that does not know the name leaves it out of its grant.

**Every start, and every new host.** Muse attaches session servers only when it builds a session's runtime, and keeps none when its host ends. So the start, and the first resume on each new host, carry Sotto's servers: the browser's and each scoped server that answers for the thread (ADR-0056), each as `{ transport: 'streamableHttp', url, headers: { Authorization }, mode: 'required' }` with that run's loopback address and token. A later resume on the same host carries none. Muse keeps the set it was built with and refuses a different one (`session_configuration_conflict`), and a session started bare cannot gain servers on a resume. The connect probe and its mode probes stay bare. Personal chats and Devin get nothing, as before.

**A start that cannot be replayed.** A start whose acknowledgement was lost is finished by replaying it, and Muse refuses a replay whose payload changed (`command_id_conflict`). After a restart Sotto's servers have a new address and token, so the replay cannot be the same. Sotto never learned that session, so no turn can have run in it: the adapter starts afresh under a new command ID, and the first session is left empty in Muse.

**Sotto admits its own tools, under ADR-0004.** MCP calls go through Muse's ordinary approval policy, and MSP has no way to pre-allow one server's tools: a session server has no allow field, and policy is not written over the wire. So when Muse asks before a call to one of this thread's own Sotto tools, the adapter answers with Muse's one-time allow and shows nothing, as Grok's adapter answers Grok's (ADR-0020's September 25 amendment, ADR-0035, ADR-0056). It does this only when the approval's subject is a `tool` named exactly `mcp__<server>__<tool>` for a tool this session was given, and Muse offers a one-time allow. Any other subject reaches the user untouched, including a tool of the same name on another server. A request already showing is the user's to answer, and one the adapter could not answer is shown after all. A later stage of an admitted approval is admitted the same way, by the subject it names. This is not answering the user's question for them. The prompt admits the agent to Sotto's own thread-bound endpoint and nothing more, and the tools still ask the user wherever they always do: the browser through Tools and its grant (ADR-0029), adding a host, starting a cloud iPhone. As with Grok, a server is known by its name, but on Muse the name Sotto gives it is not its plain one. Muse turns every character but a letter or digit into `_` in the tool names it shows, and refuses a session server only when its name is exactly a configured one, so a user's own server named `sotto-browser` would show the same `mcp__sotto_browser__…` names as Sotto's `sotto_browser` (review of #1046). The approval carries only the folded tool name, not the server it came from. So each of Sotto's servers goes by its own name and a random suffix, `sotto_browser_<10 hex digits>`, fresh for each thread in each run of Sotto and kept the same within a run so a replayed start still matches. Every such name is letters and digits joined by single underscores, which Muse shows unchanged, so a tool name the adapter admits belongs to exactly one server Sotto supplied to that session. A server configured beforehand cannot know the suffix, so its prompts reach the user. The tools that only read carry `readOnlyHint` (`browser_pages`, `browser_status`, `iphone_cloud_status`, `list_babysitting`), which Muse's **Automatic** (`onRequest`) reads as needing no prompt.

**Muse's own reviewer.** By default Muse's approval judge and its Auto-review permission profile may decide eligible requests before Sotto sees them. That applies to every Muse tool, not only Sotto's, and did before this change. Watcher's session is kept out of it (October 16, below).

**Five minutes.** Muse waits 300 seconds for a tool call. It has no per-session setting, and `muse serve -c` refuses every key tried for it on 1.4.8 (`tool_timeout_sec`, `mcp_tool_timeout_sec`, `mcp.tool_timeout_sec`, `tools.tool_timeout_sec`, `mcp_servers.<name>.tool_timeout_sec`). `tool_timeout_sec` exists only on servers in Muse's own settings, and a session server may not share a settings server's name. Sotto's browser waits up to 5 minutes for the user's answer and then runs the action, which the 360 seconds Codex and Claude Code are given covers. So Muse sends each of Sotto's servers `Sotto-Tool-Wait: 300` with every request, and the browser's waits (`browser_open`, `iphone_open`, `browser_action`, `iphone_cloud_open`) return a minute before it. The request stays open in Sotto, the reply says the user has not answered yet, and the agent reads `browser_status` or `iphone_cloud_status` before asking again. The header can only shorten a wait. Other clients send none and wait as before. Host setup and provider jobs can wait 5 minutes for a Tailscale approval, so their model picker does not offer Muse.

**Silent failure.** A start can succeed while no server connects: a Muse with no sign-in builds no runtime. `mode: 'required'` makes a server that fails to start block the session's turns, and Muse's turn failure says so.

**Out of scope: Watcher on Muse.** Replaced on October 16 by **Amendment: Watcher runs on Muse** below. Muse attached a server of the shape `sotto_threads` has, but Watcher on Muse waited for #1038 and needed its own approvals work: Claude Code and Grok Build run Watcher with host-answered prompts, and Muse has no switch for that.

The live check behind `SOTTO_MUSE_LIVE` (`tests/integration/museThreadToolsLive.test.ts`) starts one session with Sotto's servers on the installed Muse, sees Muse list them, and resumes it on a second host to see them listed again, with no turn.

## Amendment: Watcher runs on Muse (October 16, 2026)

This is the rest of #1039 (E11 of the Watcher orchestration plan, decision 16). Watcher may run on Muse wherever the client grants `sessionMcp`, inside Watcher's Owl gate as Muse sits inside its own. The October 12 paragraph's sentence that a Muse thread cannot host Watcher, and `refuseWatcher` with it, are replaced; nothing else about ordinary Muse threads changes.

**Its tools.** A thread with Watcher's launch profile (ADR-0073) has its `muse serve` host started for Watcher. Its session is given Watcher's own `sotto_threads` server and the scoped servers Watcher takes (`sotto_visual`, `sotto_pull_requests`), never the browser or host setup, under the thread's random suffix, on the start and on the first resume on each new host, exactly as an ordinary thread gets its servers. A host that did not grant `sessionMcp` never starts Watcher: the first send is refused before anything reaches Muse, in words that say to update Muse to 1.4.7 or newer or to choose a Codex, Claude Code or Grok Build model. A Watcher thread whose profile main can no longer verify is stopped and its tools revoked, as on the other providers.

**Approvals.** Sotto admits a call to Watcher's own tools the way it admits an ordinary thread's above, and the way Grok's adapter admits Watcher's: only a `tool` subject named `mcp__<server>_<suffix>__<tool>` for a tool this session was given, with Muse's one-time allow. A user's server whose name folds to the same tool name reaches the user as an ordinary card. The tools themselves still answer no request and change no policy.

**Muse's reviewer stays out of Watcher.** Muse's default permission profile, **Auto-review**, lets a model of Muse's decide eligible approval requests before Sotto sees them. Muse 1.4.9's own catalog (`permissionProfile/list`, read on a memory-only host with no session) describes it as "Same access as Ask me; AI reviews eligible actions", and **Ask me** as the same access with the user as reviewer. So Watcher's session starts on Ask me (`permissionProfile: ':ask-me'` on `session/start`, a stable member). MSP selects a profile only at a start, and a resume keeps the one Muse committed. Watcher's host also asks for MSP's experimental surface, where a session reports its permission state, and every session Muse reports for Watcher, on a start, a resume or a re-read, must name the user as its reviewer; when a reply leaves it out, `session/read` reads it back. A session reviewed by anyone else, or one Muse cannot show, is stopped before anything is sent, and so is a client that refuses the profile, in plain words. This fails closed on purpose: a Muse that ignored the profile would otherwise start Watcher reviewed, unnoticed. Whether Muse 1.4.9 reports the state this way is what the live check below must show first. Ordinary Muse threads keep Muse's default profile. Watcher's permission modes are its ordinary ones on Muse: **Ask for approval** (`promptUnmatched`), **Automatic** (`onRequest`) and **Full access** (`allowAll`), as far as the connect probe offers them. Under each, what Muse asks reaches the user, and only a one-time answer is accepted. A change from Watcher's room or a phone is checked again before Muse is told. Codex's Automatic hands eligible requests to its own reviewer; Watcher on Muse never does.

**Instructions and the request note.** MSP takes no system prompt or instructions from a client, and no per-turn context beside the user's words. So Watcher's instructions travel as a text part ahead of each message Sotto sends Watcher, marked as Sotto's and not the user's, and the request note goes as Grok's bracketed line after the user's words (ADR-0073). `turn/start` carries the message alone as `displayText`, which Muse keeps on the user message and never shows the model. Sotto shows a message it sent by that text, so every surface shows the message as typed and no line has to come off. If Muse keeps no display text, or cuts the message short, the adapter takes Sotto's own instructions and note off the wire text instead, only from a message Sotto recorded sending that begins with the exact instructions, and keeps the words that match the digest it recorded when it sent them (review of #1087). Muse 1.4.9 kept the display text in the live check. A steer carries neither. The instructions cost their tokens on every Watcher turn. (Amended October 23, 2026: they go once per conversation; see below.)

**Long waits.** Muse gives up on a tool call after 300 seconds, and each of Sotto's servers is told so (`Sotto-Tool-Wait`). Watcher's tools never wait on purpose, but a start or send waits for its worker's provider to take the prompt, and a read of a paired host waits on that host. So every `sotto_threads` call from a client that declares its wait is answered five seconds before it. A start, send, stop or settle still under way then answers `DELIVERY_UNCERTAIN` with its receipt and says it will not be sent twice. It carries on, `read_operation` reads how it went, and the same retry key returns the same receipt. A call still being admitted says to call again with the same retry key, and a read says to read again. Codex, Claude Code and Grok Build declare no wait, and their calls are answered as before.

**Paired hosts.** A host checks the Watcher identity a desktop sends, and one from before this change does not know `muse` as Watcher's provider. A host that does lists the optional host-v1 feature `watcher-muse`. A Watcher on Muse reads and directs threads only on hosts that list it, and says to update any other.

**Checked live once.** Integration over the fake MSP host covers the above (`watcherOnMuse.test.ts`, and the Muse cases of `watcherOwnTools.test.ts` and `watcherOrdinaryThreads.test.ts`). The live check behind `SOTTO_MUSE_LIVE` (`watcherOnMuseLive.test.ts`) runs one short Watcher turn on the installed Muse, so it spends. It passed on October 16, 2026, against native Windows Muse 1.4.9: Muse reported the user as the session's reviewer on the Ask me profile, Watcher's `list_threads` call returned without a card waiting on the user, and exactly one turn went to Muse.

## Amendment: Muse's shell sandbox can be turned off per machine (October 18, 2026)

Zach decided on October 18 that a machine where Muse's sandbox cannot be set up — on his Windows laptop the one-time elevated sandbox setup does not run, so every shell command in a Muse thread fails — may run Muse without it. The prototype is `docs/prototypes/muse-sandbox-prototype.html`; he chose variant A, a switch row.

**One saved switch, captured at connect.** `museDisableSandbox` on the agent configuration (default `false`) is read when Muse connects, and every `muse serve` host that connection spawns — the connect and client-update probes included — then starts with `--disable-sandbox` or without it, for the host's whole life. Changing the switch changes nothing running; Settings → Providers → Muse says a reconnect is owed while the saved switch and the running hosts' reported posture (`sandboxDisabled` on Muse's provider status, while connected) disagree, and offers Reconnect. With the flag, Muse's shell commands and file tools run with the user's own access: they can reach files outside the project and the network, because Muse no longer enforces its permission profile's filesystem and network limits. Settings, the guide and the README say so in those words. Approval modes are untouched: sandbox off is not approvals off, so a thread on Ask for approval still asks, while Automatic and Full access, which do not ask, now run without the sandbox. The configuration patch re-extends the field without its default, as every defaulted field does, so a patch that omits it cannot reset it.

**This computer's switch.** The switch belongs to the computer whose Muse it starts, as **Check for client updates** does. Settings → Providers is this computer's page (ADR-0074), so a window joined to other hosts reads this computer's saved switch from its own client-host entry and names this computer on the save and on Reconnect, which is Disconnect and then Connect; Reconnect stops a Muse reply still under way, and the page says so. A paired client may turn a host's sandbox back on but never off (Zach, October 18). Back on grants nothing, so `museDisableSandbox` is on the paired client's configuration list (`REMOTE_CONFIGURATION_FIELDS`) and `false` passes from any paired client, phone or desktop. Off stays the host's own Settings' to choose, whatever the client's remote-answer policy: unlike a new-thread permission default that skips asking (ADR-0074), which a client with that policy may set, it changes what every Muse command on the machine can reach rather than what one user answer allows. The host refuses `true` from any paired client before the coordinator sees it, and the coordinator refuses it again for any client that is not this computer's own window.

**Watcher's host too.** A Watcher thread's `muse serve` host (the October 16 amendment) is spawned by the same connection as every other, so it starts with or without `--disable-sandbox` as they do, and its shell commands and file tools then reach as far as any thread's. Watcher on a computer whose Muse cannot set its sandbox up would otherwise fail every shell command in the same way. Its session still starts on Ask me, and every approval still reaches the user: the sandbox is where a command runs, not who allows it.

**The flag.** `--disable-sandbox` is `muse serve`'s own flag, listed under "Sandbox posture (fixed for the host's lifetime)" in Muse 1.4.9's `muse serve --help`. The same build describes it as turning "the operational sandbox off for direct shell execution; permission-profile filesystem and local-command network restrictions remain recorded but are not enforced". The review of #1161 read Muse's changelog the same way: from 1.4.4 its file tools read and write outside the workspace with the sandbox off, whatever the trust or permission profile, and from 1.1.1 direct shell commands lose the profile's filesystem and network limits. The fake MSP host records the arguments each host started with (`argv.jsonl`), and `museAdapter.test.ts` and `watcherOnMuse.test.ts` check them.

## Amendment: a Muse thread's model is the one Muse accepted (October 18, 2026)

Muse 1.4.10 runs a session on the model it started on or was last set to, and says so in its start reply and with
`session/modelChanged`; its own session log records that model on every turn. But it describes a resumed or read
session by its catalog's default model. Sotto took that description as the session's model, so every Muse thread on a
model other than the default read as unconfirmed once it was reopened, after a restart or reconnect, and every send
was refused until it was confirmed, which it never was. The owner's Watcher and several delegated reviews on
`muse-wonder-full-1.0` were stuck that way while Muse was running them on that model.

A Muse thread's model is now the one Muse started it on or accepted from `session/setModel`, and `session/modelChanged`
still changes it. A reopened session's description never does: where it names another model, or Muse has not accepted
the thread's own, Sotto sets the thread's model again and counts it as Muse's once Muse accepts, unless a turn is
running, when the next send asks instead. Creation and a model change are confirmed the same way, by Muse's acceptance,
not by reading the session back. A model change Muse refuses changes nothing: the user is told, the thread stays on the
model Muse last accepted, and nothing asks for the refused model again. One whose answer was lost stays wanted, since
Muse may have taken it. A model Muse has not confirmed never holds a send or a steer back (Zach's call, October 18,
2026: nothing blocks sending another message or changing the model). Before a new turn Sotto asks for the thread's
model again, and if Muse refuses, the turn runs on the model Muse has, which the thread's model chip shows. A
permission mode Muse has not confirmed still holds a send back, since a turn under a wider mode than the user chose
could act without asking.

Bug Bot's review added three details. When Muse moves a session to another model on its own, with
`session/modelChanged`, that model becomes the thread's, so no later send sets the one before it back; when Muse moves
it while answering Sotto's own `session/setModel`, the newest model Muse named wins. When Muse refuses to set a reopened
thread's model again, the model Muse last accepted stays the chip's, since Muse 1.4.10 describes a reopened session by
its default; the description stands in only when Sotto never recorded one, and the
thread's own, where it differs, stays unconfirmed for the next send to ask again. A model Muse has not confirmed leaves the thread idle,
not in error, so a queued follow-up runs as it would on any thread; only a permission mode Muse has not confirmed reads
as an error.

A second review settled the order of things when Muse moves a session while Sotto waits on it. A change sets a model
only when it names one, so a permission or effort change keeps whatever model Muse has moved the thread to meanwhile.
A model change saves the model it wants before it asks Muse, so one whose answer is lost is still wanted after a
reconnect, and a refusal goes back only to the model the thread had before anything was awaited, never over one Muse
named since. A reopened session's description counts as older than any model change Muse announced after the resume
was asked for, and a reopen leaves the model alone while a turn runs, including one that started while the resume was
answered. Once Muse accepts the thread's own model on a reopen, the next send asks for nothing.

Muse can accept a model change without announcing it, and a resync can ask for a model again outside the order the
user's changes keep. So an accepted change makes its model the one Muse runs unless Muse named another since, and the
thread's own unless something chose another since: a late answer to an older request never undoes a newer choice.
A model Muse refuses outright when a send asks for it is not asked for again; the thread takes the model Muse has.
That also bounds a refused change a failed save or an exit left wanted: it is asked for once more, then dropped.

## Amended October 21, 2026: Muse in Usage

Zach decided on October 21, 2026 that Usage (ADR-0083) counts Muse's work in Sotto's threads and reads Muse's subscription limits. This replaces the paragraph above that kept Muse outside Usage. Muse's usage exists only where both its own gate and Usage's are on: a desktop with Muse held asks no computer for Muse's rows.

**What is counted.** Each Muse prompt Sotto sends counts as an accepted prompt once Muse's echo of it arrives, as on the other providers. Tokens come from `session/tokenUsage`, which MSP sends once per model completion. Each completion is one row, named by the durable records Muse folded it from (`sourceRange`), so a completion seen twice counts once; one that names neither records nor a turn is left out rather than risk counting it twice. Input is MSP's `promptTokens`, counted once under the provider's cache convention; output, cache reads and cache writes are Muse's own counters. The row is dated when Sotto sees it and grouped under Muse's turn, whose live start lets work after Clear usage count. A completion on another session, such as a subagent's, is not this thread's and is not counted. The thread's own readout is unchanged. Muse's own session log is undocumented, so nothing outside Sotto, and nothing Muse did before this version, is read back.

**Subscription limits.** Muse's MSP Developer Preview method `usage/read` returns the serve host's last-observed subscription window without a model call. Checked live on October 21, 2026 against Muse Code 1.4.9 (launched through WSL Ubuntu), with one minimal turn on a `--no-session-log` host in an empty temporary folder and the prompt "Reply with the word ok.": `usage/read` answered without the experimental API being granted; a fresh host answered `{}`; after the turn it answered `{ usage: { observedAtMs, tier, window: { resetsAtMs, usedPercent, windowDurationMins: 300 }, weekly: { resetsAtMs, usedPercent } } }`, times in epoch milliseconds and percents whole; and a host that had asked for the experimental API also sent the same object as `usage/changed` after `turn/completed`. `host/readLimits` does not exist. The window is Usage's primary window and the weekly block its weekly one, each named by its length. The tier is the provider's own ID and is not kept. A block Sotto cannot read is left out, and an answer it cannot read at all is no reading.

Each serve host keeps its reading in memory, and Sotto's thread hosts still do not ask for the experimental API. So the adapter asks the host that ran a turn with `usage/read` when the turn completes, asks every running thread host when Usage reads or **Read again** is pressed, takes `usage/changed` when a host sends one, and keeps the newest reading it was given while Sotto runs. With no reading yet, Subscriptions says Muse reports its limits after a Muse turn runs. A client without `usage/read` reads as one whose limits Sotto cannot read. The request goes to the local Muse client over its existing stdio connection and contacts no new host, and none of what it returns is logged.

## Amended October 23, 2026: Watcher's instructions once, and the finish wait (#1417, #1418, #1420)

A study of a Muse Watcher on `muse-wonder-full-1.0` at xhigh (`docs/research/2026-10-23-watcher-on-muse-latency.md`) found Muse slow per model call and slow to finish a turn after its last output, and three things on Sotto's side that made it worse or could not be seen.

- **The profile's instructions.** The adapter sent Watcher's base prompt whatever the profile said, so with worker roles on, a Muse Watcher never got the roles lines. It now sends the profile's instructions, or the base prompt when the profile has none, as Claude Code, Codex and Grok Build do.
- **Once per conversation.** The instructions went ahead of every message, wake-up news included: 19 copies of a 3.7k-character prompt in one hour. They now go with the first message a Watcher's session is sent on a host, and again when its conversation may have lost them: after Sotto asks Muse to compact it, after a compaction item in Muse's stream, and when the note says the conversation is new or was compacted (ADR-0073, #1189), which also catches a compaction Muse made by itself. That line stays in each note until Watcher reads its state, so only the first note to carry it asks for them again. A new host, after a restart, a lost process or an idle close, sends them again with the first message to the session it resumes. A send Muse did not start keeps them owed. Their opening line now says they come with the first message and again after a compaction or resume. The adapter still takes them off a message whose display text Muse did not keep, in either wording and with or without the roles lines, and takes the request note off a message that carries the note alone. Words the user typed that look like either stay, since the digest proves them, the whole message first.
- **The finish wait.** Sotto recorded when a send was acknowledged and when its first output arrived, not when the turn's last output came. The adapter now notes when Muse starts the turn, when its first and last output arrive (an item other than the user's message, a delta, or a token record), and when Muse says the turn finished, and reports two gaps to the send's turn record: `turnFirstOutputMs` and `turnFinishWaitMs`. Numbers only. The record waits for them after the first output, at most thirty minutes, and no longer once the thread shows the turn ended, the thread is sent to again or Sotto stops, including when Muse's answer to the send, which is when the adapter holds the record, comes after the first output. Only Muse reports them; the other providers' records are unchanged. If the wait is Muse's, these numbers are what to show its maintainers.
