# The command center is a read-only thread

Accepted October 9, 2026, following [ADR-0065](0065-remove-voice-control-and-thread-management.md) and [the command-center plan](../plans/2026-10-08-command-center.md). Zach chose the A2 room, phone scope and provider-change continuity on October 8. This record establishes the contract; the Windows live check below now admits Codex only.

Sotto has one current **Command center** on this computer, identified by its durable local host and Sotto thread IDs, special thread kind, project and creation operation. It is an ordinary native conversation on the user's Claude Code, Codex or Grok Build account and plan, never Devin, an OpenRouter reasoning account or a second API key. Its neutral Sotto-owned folder is separate from registered user projects. A paired headless host gets workers, not another command center. Creation and recovery preserve [ADR-0002](0002-sotto-owned-thread-identity.md)'s immutable bindings and flush-before-dispatch rule and extend [ADR-0035](0035-an-agent-can-set-up-a-host-from-add-host.md)'s special-thread admission pattern with a durable identity. Titles establish no identity.

The command center has an immutable read-only launch and turn profile. It has only the closed `sotto_threads` tools, with no native project writes, shell, extra MCP servers, browser, user/project executable customization or native delegation around that boundary. Sotto brokers bounded, contained reads of registered project files; roots displayed to the model confer no filesystem capability. Admission combines a reviewed live check with the startup reports described below, including startup and resume. An unverified combination is refused, with no asking-mode or prompt-only fallback. Native authentication and provider-owned session/cache persistence remain separate from Sotto's history promise.

## Admission chosen by Zach on October 9, 2026

Zach chose live proof followed by per-process checks rather than a refusal until a client reports every part of its harness. `commandCenterAdmission.ts` contains the reviewed list of **Admitted combinations**: provider, platform (`win32` or `darwin`), client version, Grok build where applicable, and the verification note proving the live check. The list started empty. The October 9 Windows live check admits Codex 0.162.0 on `win32`, documented in [the verification note](../verification/2026-10-09-command-center-live-windows.md); Claude Code and Grok Build remain unadmitted. The lead runs the live suite, reviews its evidence, writes a verification note and adds the literal entry in a reviewed source change. A setting, environment variable, command, phone or paired host cannot add or widen it. Test constructors may supply a list; production wiring never supplies one. Devin remains refused. Linux has no admission path in this ticket. macOS requires its own live check and verification note before a `darwin` entry exists; a Windows pass proves nothing about macOS.

Claude Code and Codex admit the checked version and newer stable versions on the same platform, provided the process's own report matches on every launch. Older or unreadable versions are refused. This includes new sessions, resume, cold load, early start, model or effort changes and replacement clients. A missing, unreadable or mismatched required report stops the captured process and revokes its tool endpoint before another turn frame is handled. Native skills and side calls do not provide another launch route. The refusal keeps `READ_ONLY_PROFILE_UNAVAILABLE` internally; the user sees what happened, whether anything was sent, and how to continue in an ordinary thread or obtain an update.

### Claude Code

The implementation is checked against client 2.1.296 and SDK 0.3.270. The `initialize` control response reports `commands`, `agents` and `models`, but no native tool catalog. Before writing the first prompt, Sotto checks an empty command catalog and only the built-in agent names `claude`, `Explore`, `general-purpose` and `Plan` (a subset is allowed), `current_permission_mode` and `claude_code_version` when the client supplies them, and the native `get_settings` control response (`effective`, `sources`, `applied.model` and any errors). Only the flag and administrator sources may contribute; a user, project or local source, or a hook in the flag source, refuses startup. The installed client reports agents as records with `name`, `description` and sometimes `model`; their names do not grant the absent Agent tool. Its boolean `hooks_applied` acknowledges initialization rather than listing hooks. If a client supplies a hook list or map there, it must be empty. These reads do not prove the effective tool inventory. MCP status exists, but connection and tool discovery can be deferred until the first turn, so Sotto does not invent an initialize inventory or require a pre-turn MCP report the client cannot yet provide.

The first-turn `system`/`init` frame reports `claude_code_version`, `tools`, `mcp_servers`, `permissionMode`, `model`, `slash_commands`, `skills` and `plugins`. Sotto requires exactly `AskUserQuestion` plus the supplied `mcp__sotto_threads__<name>` tools; exactly one connected `sotto_threads` server; the settings report's model; and `default` permission mode (the client's `manual` launch alias resolves to `default`). Customization catalogs must be empty. When present, `agents`, `terminal_slash_commands`, plugin errors and MCP errors are also checked. Before init, only `command_lifecycle` queued/started delivery metadata bound to the sent origin and native session may pass; it grants no tool access and does not satisfy the startup check. An absent init or any other turn frame preceding it fails closed. The check runs synchronously in the receive callback before handling that frame or a buffered successor. Transcript polling cannot replay unchecked turn work.

The remaining window is the first prompt's write until that process emits `system/init`, bounded by the adapter's turn deadline; there is no fixed wall-clock guarantee from Claude. If a mismatch is found then, that initial prompt has reached Claude, so the notice says that nothing else was sent. Sotto closes the process and revokes its server before handling subsequent turn work. The launch profile supplies only the native question tool, strict supplied MCP configuration, no setting sources, slash commands or Chrome, safe mode and restrictive parent settings. Safe mode ignores even the explicit `--mcp-config`, so Sotto attaches only its supplied HTTP server through the supported `mcp_set_servers` control after initialize and checks its added/removed/error lists. Built-in plugin disable settings supplement safe mode; a nonempty plugin inventory still refuses startup. It therefore offers no native filesystem, shell, web or agent operation during that window. The live check must verify that the installed client actually honors those flags, including project customization sentinels. Subsequent processes, including settings replacements and cold resumes, repeat both the pre-prompt reads and the init check. A newer client still has to provide these readable reports.

### Codex

The profile is pinned to the configuration controls accepted by app-server 0.162.0. Each command-center app-server's own initialize response supplies its version. CLI table overrides merge with the user's configuration. Before the session process, a short discovery process initializes and asks `config/read` for names, without creating a thread, asking MCP status or sending a prompt. Sotto then stops it and starts the session process with every inherited server except `sotto_threads` set to `enabled=false`. Inline TOML tables quote each complete name, including dots and quotes; this client does not parse quoted dotted CLI paths as TOML paths. Discovery also disables each inherited app and plugin and each explicit skill configuration entry, alongside the profile's feature gates. An inherited command or credential helper on the supplied server is refused during discovery. Before a turn, `config/read` (`includeLayers:false`, with the thread's working directory when available) supplies the effective nested configuration, and every page of `mcpServerStatus/list` supplies MCP server names and tool records. Sotto checks read-only sandbox, approval `never`, user review, the profile's disabled feature switches, disabled web search, empty notifications and only the supplied `sotto_threads` server enabled. Every inherited app/plugin/explicit skill entry must also be disabled; a newly added or still-enabled entry refuses startup. Its URL, headers, exact enabled tool names and exact per-tool approval settings must match. Its tools are exposed directly, omitted from deferred and Code Mode surfaces so a model needs no discovery/code tool to use them. Status must contain that server exactly once and exactly those tool names. Disabled inherited servers can remain in status: on 0.162.0 they report `runtimeStatus:null`, empty tools and empty resources/templates. Sotto accepts only that inactive shape or an explicit disabled status, with matching effective `enabled=false`; a running, unreadable or cached-tool entry refuses startup. A server added between discovery and the real launch is caught by this backstop. Missing or unreadable data, duplicate/repeated pagination or a mismatch stops and revokes before a prompt is sent. Configuration is checked before MCP status discovery may activate a server. The command-center process keeps its immutable launch configuration and never performs the runtime MCP reload ordinary threads use. Reports are rechecked before sends and steers and after settings changes; new launches discover again.

The `thread/start` and `thread/resume` replies must also confirm the requested model, read-only sandbox, approval `never` and user review. A restored conversation cannot carry wider permissions past the effective-configuration check. Codex does not report a native tool catalog. These reports prove configuration and MCP inventory, not absence of every native operation or that the OS sandbox enforces each write restriction. That proof belongs to the live check of the installed version and platform. No invented native-tool field or test-only attestation replaces it. The user's `CODEX_HOME` and authentication remain in use; Sotto never edits that home to obtain isolation.

### Grok Build

Grok admits only the exact version and build in an entry (the inspected client is 1.0.50, build `c58f321264ba`). Its bounded `--version` read supplies the build; each new ACP process's initialize response independently supplies `agentVersion`. Missing or different evidence refuses before session creation, load or prompting. A preliminary workspace settings check establishes only that an entry exists; the adapter performs the definitive version/build check before using a process. ACP reports neither effective tools nor harness, so the live check supplies all of that compatibility proof. A newer build cannot inherit it. The profile keeps its explicit discovery/invocation ToolConfig and isolated Sotto-owned `GROK_HOME`, with native authentication referenced through `GROK_AUTH_PATH` without reading or copying credentials. A command-center model/effort change uses the native model operation and confirms its selection; ordinary Grok thread behavior is unchanged.

### Administrator boundary and live proof

Machine-wide administrator settings are trusted as they are for ordinary threads: enterprise policies and system hooks are outside the user/project restriction. Sotto's parent policy does not claim to override an administrator. Inability to rule out administrator-installed hooks is no longer a reason to refuse an otherwise admitted combination. User and project customization, extra MCP discovery and native work capabilities remain restricted. This is a trust boundary, not proof that startup writes no provider-owned session/cache data.

`tests/integration/commandCenterProvidersLive.test.ts` requires both `SOTTO_COMMAND_CENTER_LIVE=1` and a provider selector, and skips in CI. It does not change the source list. Each provider gets six total turns: supplied tool; file edit and shell write; web fetch and subagent; extra project MCP; cold-resume tool; changed-effort/model tool. Fresh temporary project files include instruction, MCP, hook, skill and agent sentinels; harmless loopback servers record contacts. The suite checks bytes, marker files, extra-server/web contacts, native confirmations, user requests, admission/startup checks and required supplied calls, stopping at the first failure. The first failure is latched before disconnect and abort runs once, including synchronous subscriber notifications; cleanup errors cannot hide it or prevent the evidence write. Grok disconnect itself also guards synchronous subscriber reentry. During Grok session creation, only its temporary unconfirmed-settings status is deferred until the operation returns. Its native permission wrapper is not counted as an outside-profile confirmation only for the exact supplied Sotto tool, matching native session and one-time option; all other requests still fail the live check. A 120-second turn bound, 30-second operation bound and 18-minute suite bound prevent unbounded account use. Evidence in ignored `artifacts/command-center-live/` contains versions, platform, model and check verdicts only, with no prompt, output, credentials, token or external path. No user provider configuration or credentials are copied or modified. Project trust is not changed; the live result proves the observed run rather than every possible administrator or trust configuration. The October 9 Windows runs completed all six turns for Codex. Claude Code stopped at its nonempty built-in plugin inventory; Grok stopped at the extra-project-MCP native confirmation. Neither gets an entry. The verification note retains all recorded check verdicts and distinguishes submitted attempts from completed model turns.

This explicitly amends [ADR-0004](0004-authority-in-policy-records.md) and [ADR-0005](0005-codex-app-server-adapter.md) for bounded command-center start/send authority. An actual top-level user Send to the current master creates a main-owned **Command-center request**, rooted in that user's message. Main admits start, send now, queue, steer, targeted stop and settle through the existing coordinator lanes, outbox and delivery receipts. Workers start at no wider than the user's effective new-thread default; an explicit narrower choice is allowed only when comparable. Existing workers whose permissions exceed or cannot be compared with that ceiling are refused. Main enforces a computer-wide limit of four distinct automated targets by default (setting 1–8), including reserved, queued, uncertain and waiting targets, and four total prompts per target per request. Retries, wake-ups, compaction, restart and model changes renew neither budget. Lowering capacity stops nothing and holds new admission until usage falls.

The human-only answer rules of those ADRs and ADR-0065 stay in force. No command-center tool answers a question, approves a permission, changes policy or widens a worker's permissions. Native preallowance admits only a call to Sotto's scoped server; it grants no worker authority. Worker requests are answered on the worker's own request card. An unexpected permission outside the master's profile stops/revokes that profile, rather than inviting an approval. Main can enforce scope, identity, budgets and fences; it cannot prove that a generated brief faithfully interprets natural language. The original request reference and visible actions remain available to the user.

Direct user instructions or controls on a participating worker, including native and phone input, relinquish participation before dispatch. Main increments ownership generation and fences subsequent machine deliveries, retaining the user's drafts, queue and new turn. Opening, reading and answering an existing request card are not takeover. V1 offers the model no resume-ownership tool. User-only **Stop all** asks first, then stops only still-eligible threads the command center started; it excludes the master, user-started and taken-over threads and unrelated provider subagents. A targeted stop records its action under the user's active request and may address an existing ordinary thread. Closed/stopped requests cannot be revived by a tool or restored history.

Main wakes the master from observed participant and delivery changes, in bounded event batches, rather than model polling. [ADR-0061](0061-a-thread-can-babysit-its-pull-request.md)'s existing wake-up/queue path carries this distinct source of news without changing independent babysitting. Evidence carries source, observation time, identity, freshness and availability; a worker's claim is separate. Overview is a projection of all other threads, not a second attention store. Its precedence is Needs you, verified Landing, another open pull request, Quiet after twenty minutes of freshly observed active work without progress, Working, then Idle; display order is Needs you, Ready for review, Working, Landing, Quiet, Idle. Disconnection supplies stale/unavailable evidence, never an inferred failure or quiet turn. Landing is observed action/merge evidence and grants no permission.

`agents.json` keeps only versioned identities, requests, operation/retry/digest references, worker ownership generations, counters, reservations, takeover reasons/times, receipt links and read/wake positions. Tokens remain in memory. [ADR-0016](0016-sotto-owned-history-on-an-event-store.md)'s normal history-aware store holds messages and future cards; history off keeps command-center words and file contents only in memory, including queues, drafts and evidence payloads. No prompt, file content, bearer token, tool argument, protocol body or error prose enters control metadata, logs or backups. After restart unavailable text is reported unavailable; uncertain delivery is reconciled, never replayed.

Paired-host automation requires the optional `command-center-control` and `command-center-reads` features with closed machine-origin operations and owning-host enforcement. Ordinary privileged desktop commands are no fallback, and generic socket/phone clients cannot forge that origin or acquire remote-answer authority. Host protocol remains v1; unsupported hosts retain readable existing summaries and refuse automation. In v1 current and retired command-center conversations are hidden from phones, including old clients through host-side projection and targeted-command filtering; ordinary workers keep their existing phone journeys on their owning host. The desktop's aggregate roster is not a phone host feature.

Changing provider waits for no in-flight master turn, invocation or unresolved delivery, then creates a replacement native conversation with a new Sotto ID. The previous conversation becomes readable command-center history according to history settings, its tools are revoked, and the current reference changes atomically. A bounded visible handover is offered through the replacement's send path only after the user chooses to continue. Worker ownership and receipts survive; the handover revives no stopped or taken-over request. This preserves ADR-0002 rather than rebinding one conversation across providers.
