# Images are staged once and carried by handle

Accepted September 26, 2026. Issue #320, phase 3 of the performance tickets. The owner chose not to review this record before the code; the review stage checks the code against it. It amends [ADR-0025](0025-headless-host-and-client-identity.md) by adding a host feature, and finishes for drafts and the follow-up queue what `docs/perf/state-pipeline.md` did for submitted previews in history. It was written as ADR-0030 and renumbered when [ADR-0030](0030-screenshots-are-scaled-to-the-longest-edge-a-model-reads.md), the screenshot bound (#321), merged first.

## Context

An image the user attached traveled as a base64 data URL inside everything that mentioned its draft. With one 8 MiB screenshot in a thread's draft, on `origin/main` at `e093bd6c`:

- every debounced text save sent the image again, 11.2 MB from the window to main and 11.2 MB back in the answer;
- every shell, which main pushes to the main window and the widget as often as a thread streams, carried it: 11.2 MB per window per push, and `shell()` hashed it again to report the draft's save state;
- every write of `agents.json` held it, 11.2 MB, after cloning, stringifying and hashing it;
- a send with the image rewrote `attachment-previews.json`, one file of up to 100 MiB, in full.

The queue of follow-ups carried the same bytes in `followups.json` and the shell.

## Decision

**A staged image is named by its handle.** The window hands an image's bytes to main once, through a preload call, and gets back a handle: an ID for this attachment, the file name, the MIME type, the byte length and the SHA-256 digest of the content. Drafts, the coordinator's draft, queued follow-ups, commands, the outbox, the shell, the persisted state and every broadcast carry handles only. `CONTEXT.md` calls this a **staged image**.

**One attachment store per host, owned by main.** `src/main/agents/attachmentStore.ts` keeps each distinct content as one file, `attachments/<digest>.<png|jpg|gif|webp>`, in the host's data folder, with a small index, `attachments/index.json`, that lists digest, type, size and when it was staged. The index holds no names, no thread IDs and no text. Staging checks the type, the 10 MiB limit and the file's signature, writes the bytes to a temporary file and renames it into place, then writes the index, and only then answers with the handle, so a draft can never be saved pointing at content that was not yet on disk. The same bytes staged twice are stored once. A command that carries a handle the store does not hold, or whose type or size disagrees with it, is refused before anything else happens, and a send or steer is checked again once its outbox entry owns the content, just before the provider hears it. A draft save is the exception: it keeps the text, leaves such an image out and says so, so typing into a draft restored after its image went is never lost.

**What owns content keeps it.** Content is kept while a thread's draft, the coordinator's draft, a follow-up in the queue in any status, an outbox send or steer whose result is not known (it records the digests it carried), or a submitted preview names it. Nothing else counts: not the window's own copy, not a delivery record. Content nothing owns is removed once it has been unowned for an hour. The store is swept at start and with the preview upkeep every 30 seconds. At start every indexed content counts as unowned from that moment, so an image staged just before a crash, whose draft was never saved, is found through the index and removed an hour into the next run. A content file the index does not name, which a crash between writing it and writing the index leaves, is taken back into the index at start as unowned, so it goes by the same rule and a damaged index never strands a saved draft; a temporary file a crash left, and anything else in the folder, is removed at start. The hour is what lets a refused prompt go back to its composer, or be sent again from the window's copy, without staging again. Clearing, cancelling or refusing a prompt therefore releases its content on that rule, not at the press. Turning history off removes at once content that only previews owned, unless it was staged again after its latest preview was stored: that is the same screenshot attached to a draft the window has not saved yet, and it keeps its hour like any other.

**Previews keep their own rules.** `attachment-previews.json` becomes version 2: each entry is a thread, message and command with the handles its message carried, a few hundred bytes. The seven-day and 100 MiB limits still apply to entries, measured by the handles' sizes; a preview's content is removed only when nothing else owns it either. A version 1 file is converted at start by staging its bytes.

**History off keeps new content in memory.** While Keep local history is off, staging writes nothing: the bytes stay in memory, and so nothing new reaches disk. An inline image an older file held is the exception: its bytes are already on disk, inside that file, so converting it at start writes it to the store whatever the setting, and the draft or follow-up keeps it across restarts. After a restart a draft or follow-up whose content was only in memory comes back without that image. A follow-up that lost one is paused and says why instead of being sent without it; a draft that lost one comes back without that image's chip. Saying so in the composer would need a place on the draft to say it, which is a design question left open. Content already on disk when history is turned off stays until nothing owns it. Previews are already off in that mode.

**Bytes are read for three things only.** A composer restoring a chip it holds no copy of (after a restart, or a draft another window wrote), a submitted preview, and provider submission. The window keeps its own thumbnail for each chip, at most 256 pixels on the long side, keyed by digest for the life of the window: the 64 most recently used, and no more than 8 MiB of them between them. An image of at most 1 MiB that the canvas cannot draw is shown as it is instead, which is not bounded in pixels, so the cache is bounded in bytes too.

**Adapters build the provider's form at the protocol boundary.** An adapter's send and steer carry `PromptImage`s: the handle and a `read()` of its content from the store on the provider's host. Claude gets a base64 image block, as before. Codex gets a data URL `image` input, as before. Codex's `localImage`, a path on the provider's host, was considered and not taken: Codex loads a local image itself and scales it to fit its own limits before sending, which a data URL is not, so taking it would decide how screenshots are downscaled. ADR-0030 has since decided that in the composer, before staging, so what the store keeps is what is sent; the store's path makes switching to `localImage` a one-line change if that is ever wanted. Grok and Devin refuse an image before the provider hears anything, as before, because neither reports image input. `tests/integration/adapterContract.ts` sends a staged image through every adapter.

**The screenshot bound comes first.** The composer and browser feedback scale a screenshot past the screenshot bound down before they stage it (ADR-0030), so the staged bytes are the ones sent. The handle carries the sizes the composer attached and sent it at, `dimensions`, which the chip reads to say what it was **Resized from** and **to**; they describe the image and are never read as its content. The handle is built in four places and all four take them: `agentAttachmentHandleSchema` and `agentAttachmentStageRequestSchema` in `src/shared/agents.ts`, `hostAttachmentSchema` in `src/shared/hostProtocol.ts`, and `AttachmentStore.stage`. An inline image an earlier build saved with its sizes keeps them when it is staged at start.

**Remote hosts stage where the provider runs.** The window's staging call names the thread (or, for the coordinator's composer, the selected host), and the desktop router hands it to the host that runs it. Over the socket this is the host feature `attachment-staging`, with two requests: `stage-attachment` (the bytes as base64 in one frame, within the 16 MiB limit) and `attachment-content` (a staged image's bytes by digest, for a chip). A host that does not list the feature is older; the desktop sends it nothing and says which side to update, as it does for the other features. Protocol version stays 1: the envelope is unchanged, and a host and a client of different Sotto versions already meet the version sentence when thread and command shapes differ (the September 23 amendment of ADR-0025), which the draft's attachment shape now does.

**Old files are converted at start.** Inline images in `agents.json` (the coordinator's draft and thread drafts), `followups.json` and version 1 previews are staged and rewritten as handles when the coordinator starts. An inline image that is not the image it claims, which earlier versions saved without checking, is dropped from its draft or follow-up on the same terms: the follow-up is paused and says why, and the draft comes back without it. The three files go through one conversion, `inlineStager` in `attachmentStore.ts`. A failure to write the store leaves the file as it was and stops start, the way a failed migration of host identity does.

## Consequences

- With the same 8 MiB screenshot in a draft, a text-only draft save, a shell push to each window and a write of `agents.json` each carry a few kilobytes instead of 11.2 MB, and a send with the image writes a preview entry of a few hundred bytes instead of rewriting every stored image. The figures are in `docs/perf/2026-09-26-attachment-handles.md`.
- A prompt's digest (`followupDigest`) now covers each image's content digest rather than its base64. A prompt with images whose delivery was uncertain across the upgrade is reconciled by its draft ID, which every outbox entry has carried since per-thread drafts.
- Private image bytes now live as individual files in `attachments/` under the data folder of the machine that runs the thread, named by their content digest, instead of inside `agents.json`, `followups.json` and `attachment-previews.json`. The README says so under "Privacy and cost".
- A digest names content; it is not a secret. The staging and content requests are on the bridges of Sotto's own two windows, both of which have a composer that takes screenshots, and the content request answers only for content the host still keeps. Over the socket it is not narrowed further to content a draft on that host names: a paired client already reads every thread and draft on the host, and a chip restored between staging and the draft's save would lose its thumbnail. Staging over the socket takes the preview's one-at-a-time guard per client, so one client holds at most one 10 MiB image in flight.
- An image attached to two drafts, or attached and then submitted, is stored once.
- Going back to a build from before this record is not safe for a user with images in a draft or the queue. An older build's schemas read a handle as an unreadable draft or follow-up, and its store then sets the whole `agents.json` or `followups.json` aside as corrupt and starts from defaults: assignments, the outbox, delivery receipts, every draft and the queue go with it, and only the `.corrupt` copy is left. Sotto has no downgrade procedure (`docs/release/releasing.md` describes none), so this is recorded rather than guarded. Someone who must go back sends or clears drafts and follow-ups with images first.
- Content on disk is checked against its digest each time it is read. A file truncated, damaged or replaced since it was staged is treated as gone: the file and its index entry are removed, so the next start does not take it back, a send that names it is refused with the missing-image sentence rather than sent under the user's digest, and staging the same image again writes it afresh.
- A headless host refuses a missing image with its own sentence ("no longer kept on its host"), since the desktop that shows it is not the machine that lost it. An image the host refuses for what it is carries its sentence to the desktop instead of the host's general failure.

## Amendment, October 3, 2026: photos from the iPhone

The iPhone client attaches photos to a reply through the same two requests the desktop uses for a remote host, `stage-attachment` and `preview`, and needs nothing new from the host. What it decides for itself:

- **A photo is made ready on the phone.** The phone takes a photo from the system photo picker, which runs outside the app and hands over only the photos chosen, or from the camera, which asks for access the first time. It scales the photo to the screenshot bound (ADR-0030), upright, and draws it again as a new image, so no location, camera or other metadata leaves the phone. A PNG stays PNG while it fits in 10 MiB; anything else, HEIC included, goes as JPEG. A moving GIF that already fits, of at most 500 frames, keeps moving, as the desktop leaves GIFs alone: its frames are written again with their timing and nothing else. Any other moving image goes as its first frame. The phone sends the sizes it had and was sent at, so the desktop says what it was resized from. The bytes stay in memory on the phone until the reply is sent or the photo removed, and are never written to disk.
- **One large request at a time per computer.** The host refuses a second image request from a client while one is in flight (the preview guard above), so the phone queues staging and preview reads per computer, and a sent photo's thumbnail that scrolled away before its turn is never asked for. Photos are prepared one at a time across the app, so several large photos are never held decoded at once; staging runs apart from preparing, so a slow computer holds up only its own replies. A photo's original that hasn't arrived from the library within two minutes, such as one still downloading from iCloud, is left out and says so, and removing a photo ends its wait, so one photo never holds up the ones chosen after it.
- **A handle is staged again before the host lets it go.** The phone saves no draft on the host, so nothing owns its staged image there, and the host lets unowned content go after an hour. A photo staged 45 minutes ago or more, one staged over a connection that has since ended (the computer may have restarted, and with history off it kept the photo in memory only), one that never reached its computer, and one in a refused reply put back in the box are staged when the reply is sent. Staging the same bytes again costs the host nothing.
- **Only a model that says it reads images is sent photos.** The reply box's + button checks the thread's model in its computer's catalog (`supportsImages`), read as the host reads it (`catalogEntry`, so a 1M-context variant takes its base model's entry), and the host's `attachment-staging` feature. When either says no, the button stays, and its menu says why instead of offering Photo library and Camera.
- **Look.** Of three prototypes (`docs/prototypes/iphone-photo-attach-prototype.html`), the owner chose B: a + button opens a menu of Photo library and Camera, chosen photos wait inside the reply box above the words, and sent photos stand above their words in the thread, as Messages shows them, and open full screen.
