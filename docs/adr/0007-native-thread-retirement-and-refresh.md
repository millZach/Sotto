# Native thread retirement and targeted refresh

Accepted September 12, 2026 for ticket #24. Sotto now connects only to native Codex, Claude Code and Grok Build adapters; removing the intermediary host must neither lose saved work nor silently transfer authority. This supersedes the legacy provider default and first-discovery ID adoption in ADR-0002 and ADR-0005; their other identity, permission and recovery rules remain.

Before parsing current saved configuration, explicitly retire an old or omitted legacy provider. Preserve policy-redacted recovery evidence before writing disabled native state, retain draft text and images without the old target, and remove old assignments and uncertain actions from active dispatch. Keep historical thread bindings unchanged; new discoveries mint fresh Sotto identities. Retaining retired actions in the live outbox would permanently block provider switching, while relabelling them as native could send to an unrelated session. Recovery evidence is bounded by the existing history and expiry policy and never creates an automatic replay path.

Send validation and confirmation refresh only the target thread and return the complete cached provider view. Each native adapter preserves its dispatch-time takeover and permission guard; unrelated history reads must not hold the target's critical path. Full discovery remains a separate operation. Keep the coordinator's current command ordering until measured evidence justifies changing its shared draft and authority model.

The [pinned T3 source study](../research/2026-09-12-native-thread-source-study.md) informed this decision: separate summaries from thread detail, reconcile pending submissions by identity, and distinguish accepted intent from confirmed provider delivery. Sotto adapts those patterns to its existing outbox and native protocols, without importing another orchestration framework. Research citations and historical verification remain provenance; they do not describe a supported runtime provider.

## Amendment, September 26, 2026: a settings change is confirmed by the adapter's own snapshot (#318)

The decision above has send validation and confirmation refresh the target thread. For a thread settings change that read was not free. Reading a Claude thread opens it, so a thread the reaper had stopped started its CLI for the read before the change, and the change then restarted it. A Codex read is `thread/read` with the whole transcript, and a settings change made two. A Devin read after the change started the session the change had just stopped, although ADR-0022 resumes it on the thread's next action.

A settings change now reads nothing before it goes out. The coordinator checks it against the thread it holds, and each adapter checks the thread's status, pending requests and model itself before it acts, as it did already. An adapter that has the provider's confirmation returns the snapshot it emitted for the change as `AgentHostResult.snapshot`, carrying the thread's effective settings. Each host layer passes it up the way it passes a read: under Sotto's thread IDs, as the whole provider view, and as the workspace's view. The coordinator reconciles the outbox against it and reads the target thread only when no snapshot comes back. An uncertain result never carries one. Codex, Grok and Devin return it; Claude will with #317. Sends keep their confirmation read.

The outbox entry and its write before the change goes out stay: they are what makes an uncertain change reconcilable after a crash. When the provider confirms the change inside the same dispatch and nothing else in the coordinator's state changed, the write that would only remove the entry is not made. The next write carries the removal, and closing Sotto writes it. After a crash in between, the entry is on disk and the next connection reconciles it against the thread's settings like any other. If the thread's settings were changed outside Sotto in that window, the entry does not match and the thread refuses new actions with the existing unknown-result error, as an uncertain change already can. The measurements are in [the light-path note](../perf/2026-09-26-settings-light-path.md).
