# Work moves between a desktop's machines over its own SSH link

## Status

Accepted by Zach on October 14, 2026. It is built with #1033 (ticket E10). Zach decided on October 14 that workers can start on any machine connected to the desktop and that code moves directly over the SSH link rather than through GitHub (decision 6 of the Watcher engine ticket map, #1023). This record settles how, from a spike run the same day against forge. It is an Owl feature ([ADR-0072](0072-sotto-owl-is-a-windows-preview-release-track.md)).

Amended October 23, 2026, by [ADR-0105](0105-hosts-reach-each-other-over-host-links-the-desktop-sets-up.md) decision 8, which Zach accepted that day: decision 5 below is replaced, and decision 6 holds with the socket in place of SSH. See "Amendment: branches travel over the host socket" at the end. The Owl switch is `cross-machine-work`, this record's own entry.

## Context

The laptop and forge each keep their own clone of a project. A worker on forge commits to a branch the laptop cannot see, and the only way across today is to push to GitHub and pull on the other side. That puts work in progress on GitHub, which nobody asked for, and it needs a remote the user may not want touched.

The desktop already reaches each host it added over SSH ([ADR-0025](0025-headless-host-and-client-identity.md)), with the saved target, port and identity file, and the user's own `~/.ssh/config` deciding the rest. Git can carry a branch over exactly that.

## The spike, October 14, 2026

Run from the Windows laptop against forge (Omarchy, Linux 7.2.5), with throwaway repositories in `/tmp/sotto-e10-spike.*` on forge and under `%TEMP%` on the laptop, both removed afterwards. No real clone on either machine was touched. Every step below passed.

- **Which ssh.** Sotto's launcher runs Windows' own OpenSSH, `%SystemRoot%\System32\OpenSSH\ssh.exe` (9.5p2 on the laptop), not whatever comes first on PATH (`sshProcess.ts`). Git for Windows does not: with no `GIT_SSH_COMMAND` or `core.sshCommand`, `git` started from a Windows shell, whose PATH lists the System32 OpenSSH folder first, still ran its own bundled MSYS ssh (`C:\Program Files\Git\usr\bin\ssh.exe`, OpenSSH 10.2p1). The two told apart by their own error text for an unknown host. Setting `GIT_SSH_COMMAND` to the System32 executable made Git use it, and Git ran it through its bundled `sh -c`, so the path must be quoted if it ever holds a space.
- **The options.** `-o BatchMode=yes -o ConnectTimeout=15 -o ControlMaster=no -o ControlPath=none -o ControlPersist=no -o RemoteCommand=none -o RequestTTY=no -o ForwardAgent=no -o ForwardX11=no`, which are the launcher's own options except that a move asks nothing (`BatchMode=yes` rather than the launcher's askpass). The saved target `forge` carries no identity file, so `~/.ssh/config` supplied the host name, user and key, exactly as it does for the launcher. Git adds only `-o SendEnv=GIT_PROTOCOL`.
- **Forge to laptop.** `git fetch forge:<repo> refs/heads/work:refs/sotto/incoming/work` landed the branch in the laptop's repository in about 0.27 seconds.
- **Laptop to forge.** `git push forge:<repo> refs/heads/laptop-fix:refs/sotto/incoming/laptop-fix` landed as a new reference in about 0.26 seconds, while forge's checked-out branch, index and working tree stayed as they were.
- **A checked-out branch is safe.** A push into forge's checked-out `work` was refused by forge's Git ("branch is currently checked out") with `receive.denyCurrentBranch` at its default.
- **Nothing is forced.** A push that was not a fast-forward of an existing incoming ref was refused ("non-fast-forward"), and so was a fetch after forge rewrote `work`. Both refs stayed where they were. Both refusals are Git's, on the side that runs the command, and hold because Sotto never passes `--force` or a `+` refspec.
- **A new worktree from the moved branch.** `git worktree add -b laptop-fix <path> refs/sotto/incoming/laptop-fix` on forge, and the same on the laptop for a fetched branch, each in under 0.2 seconds, leaving the main checkout untouched.
- **Uncommitted work shows.** `git status --porcelain` listed a modified and an untracked file on the laptop and a modified file on forge, and nothing once they were put back.
- **Round trip.** A commit made in forge's new worktree came back to the laptop by fetch as a fast-forward of the branch the laptop had sent.
- **Git on forge.** `/usr/bin/git`, version 2.55.0. The laptop has Git for Windows 2.53.0.

## Decision

**1. Only committed branches move, as the commit Sotto checked.** Before a move, Sotto reads `git status --porcelain` in the sending working copy. Anything listed refuses the move in plain words, asking the user or the worker to commit first, and moves nothing. Sotto then resolves the branch to its commit and moves that commit by its hash (`<commit>:<ref>`), not the branch name, so work committed between the check and the transfer is never carried unchecked. Sotto never commits, stashes or discards on anyone's behalf.

**2. A moved branch always lands in a ref of its own on the receiving side.** Each move lands in `refs/sotto/incoming/<move>/<branch>` in the receiving repository, where `<move>` is the move's own identity: from forge to the laptop, the laptop fetches forge's branch; from the laptop to forge, the desktop pushes to that ref on forge. No checked-out branch, and no branch the user made, is written by a move.

**3. Nothing is forced.** No move passes `--force`, `--force-with-lease` or a `+` refspec. Because every move has its own incoming ref, a later move or a move back never meets an earlier move's ref, so a non-fast-forward cannot leave moves stuck. Sotto removes a move's incoming ref when the worktree made from it is cleaned up (ADR-0041), and never removes one a worktree still uses.

**4. The receiving worker starts in a new worktree.** It starts on a branch of the moved name, made from the move's incoming ref, in a worktree Sotto owns on that machine (ADR-0014, ADR-0041). A branch of that name that already exists there is never moved: when one exists, the new worktree's branch gets a distinct name Sotto shows (the way a new worktree's temporary `sotto/<token>` branch does, ADR-0014), and the user's branch stays as it was.

**5. Git uses the same ssh, target and identity as the launcher.** On Windows, `GIT_SSH_COMMAND` names Windows' own OpenSSH, because Git would otherwise use its bundled ssh, which the launcher deliberately avoids. Elsewhere it is `ssh` from PATH, as the launcher's is. The options are exactly the launcher's (`sshLauncher.ts`, `baseArguments()`), which keep `StrictHostKeyChecking=ask`, the keepalive (`ServerAliveInterval`, `ServerAliveCountMax`) and `IdentitiesOnly=yes` with the saved identity file and port, with one change: `BatchMode=yes`, so an unknown or changed host key refuses rather than being accepted. The spike's shorter option list above showed the transport works; the build reuses the launcher's list. Each move opens its own SSH session; it does not ride the launcher's port forward, which keeps multiplexing off by design, and a host on its **tailnet connection** is still reached for a move over SSH. A move asks nothing: when ssh would need an answer, such as a passphrase or an unknown host key, the move stops and says to connect the host again first. Whether a move should instead ask through the launcher's askpass is left to the build.

**6. No new host, nothing through GitHub.** A move contacts only the SSH host the user already added and runs only Git at each end. It needs no GitHub remote and never pushes to one. The README's privacy section says so.

**7. Watcher and continuing elsewhere use it.** `start_thread` gains a start from a thread's branch: Sotto moves the branch, then starts the worker. Results come back the same way, and #1030 (E7) brings them onto the parent's branch. Continuing a thread on another machine moves the branch first.

## Consequences

- Work in progress stays on the user's own machines. GitHub sees a branch only when the user or a thread pushes it there.
- `refs/sotto/incoming/*` holds one ref per move until the worktree made from it is cleaned up (decision 3). They hold commits Git would otherwise collect, so a move whose worktree is never made is also removed when its thread is.
- The receiving machine must already have a clone of the project; E9 refuses a machine without one in plain words and never clones.
- A key with a passphrase, or a host whose key changed, stops moves until the user connects the host again. That is the cost of asking nothing.
- A Mac host should behave as forge did but is unverified until one is connected.

## Proof, when built

Integration with two local repositories behind a file transport stand-in: uncommitted work refused, the checked commit moved even when the branch moves on during the transfer, a second move and a move back after a non-fast-forward both land, a checked-out branch untouched, a new worktree on the moved branch, an existing branch of the same name untouched, and the incoming ref removed with its worktree. Then a live run on forge: laptop to forge and back, Linux journeys on forge, Windows tests on the laptop.

## Amended October 23, 2026: where a new worker starts (#1032)

The Owl feature Work across machines (`cross-machine-work`, [ADR-0072](0072-sotto-owl-is-a-windows-preview-release-track.md)) is owned by this record. Its first part, #1032 with #1313's machine list and #1312's choice of system, decides where a new worker starts. Nothing moves a branch yet; that is #1033's.

1. **Where new workers start** is a setting (`newWorkerMachine`): **This computer**, the default, so nothing moves until the user chooses; a connected machine, by its saved host ID; or **Let Watcher choose**. Its control in Settings, Watcher comes with the prototype Zach is shown (variant B of October 14, the machine tiles); until then it stays on This computer.
2. **A start's own words decide for that start.** Watcher's `start_thread` may name a `machine` (a host ID from `list_machines`) or an `os` (`windows`, `macos`, `linux`), matched against **host facts**. A machine is kept to. A system goes to a connected machine of that system, the machine new workers start on first, then the project's, then This computer, and never falls back to another: with none connected, nothing starts and Sotto says so ("No Mac is connected. Connect a Mac, or run this on This computer. Nothing was started.").
3. **With neither named**, a project Watcher named on another machine starts there, as Watcher has always placed work, and one named on This computer goes to the machine new workers start on. Watcher names a project, and the project already says a machine; treating that as the request's own words keeps every start Watcher made before this the same. Zach confirmed this on October 23, 2026: the machine new workers start on applies only to This computer's projects; one with no copy of the project, or a host too old to say, refuses the start rather than falling back to This computer; and projects match by their `origin` remote only.
4. **A machine that is not connected, or no longer saved,** starts the worker on This computer instead, and the receipt's note says why (Zach, October 14: build the fallback, not the prototype's refusal). A machine named in the start's own words is refused when not connected.
5. **The same project on another machine** is the one whose `origin` remote names the same GitHub repository (`sameRepository`). A machine with none is refused in plain words ("Forge has no copy of Sotto. Add the project on forge first."), and Sotto never clones. A headless host reports its projects' origins through a new optional host-v1 feature, `project-origins`, only to a desktop and only where its own Owl answer turns the feature on; it carries the repository's host, owner and name, never a path or a URL. An older host cannot be matched, so a start there must name one of its own projects, and a start that would need matching says to update it. A working-copy or base-branch choice read on one machine is refused on another when the start names that machine or a system. A start that names neither stays on This computer when it reuses a worktree there or starts from a base branch read there, away from the default, and its receipt's note says why (Zach, October 25, 2026, after the review of #1514).
6. **The receipt records the machine** (`placement`: host ID, name, `awayFromDefault`, Sotto's note), in memory as a worker role's note is, and Watcher is told to say in its reply which machine and why whenever a start is away from where new workers start. Its instructions also tell it to read a project's own notes on where checks run.
7. **Working threads are counted on each machine**, and a Watcher start on another machine that leaves more than ten working there warns, as one on This computer does (#1183). A start whose thread that machine's list already holds counts by its own turn, the new start included, so a fast worker that finished before its answer came back, or a finished worker kept for its background work, is not working; one waiting for its first turn counts, since the machine lists a new thread before its first prompt goes, so a listed thread needs no other proof it was made; one the list does not hold yet counts only once the machine has created it, and a delivery that is merely unconfirmed, with no thread listed, does not count. Nothing is refused at any count. `workingThreadsByMachine` gives the window each machine's count for the room.
8. **A delegating thread** gets `list_machines` on `sotto_delegate`, the same list Watcher reads, and `delegate` takes `machine` or `os` for a new thread. A delegated thread starts only on This computer until delegation reaches other machines (#1316): a placement anywhere else is refused and recorded, and a setting that puts new workers on another machine is noted in the result, not followed. ADR-0081 decision 10 is amended to match.

Stable reads no setting for it, offers no machine or system, lists no `newWorkersStart` and asks no host for its projects' origins; a host on stable lists no `project-origins`. The setting itself is saved whatever the track, as every setting is, so turning the feature on restores it.

## Amendment: branches travel over the host socket (October 23, 2026)

Zach accepted [ADR-0105](0105-hosts-reach-each-other-over-host-links-the-desktop-sets-up.md) on October 23, and with it its decision 8. Each move opening its own SSH session meant a move started while nobody watched could wait on Tailscale SSH's `check` mode for a browser approval nobody gave (ADR-0105, Context). So:

- **Decision 5 is replaced.** A branch travels as a Git bundle over the host socket the desktop already keeps to each host it is connected to, in chunks of at most 1 MiB, with no new SSH session per move. The sender points `refs/sotto/outgoing/<move>` at the checked commit, bundles that ref against the receiver's tips that it also has, and removes the ref once the bundle is written. The receiver stages the bundle in its own data folder, checks its size, its SHA-256, `git bundle verify` and its one ref, imports the objects, checks that the ref names a commit, records the move with it and creates `refs/sotto/incoming/<move>/<branch>` once, with `git update-ref <ref> <commit> ""`. A cut-off transfer lands nothing and its staged file is removed. The socket request is `branch-move`, behind the optional host feature `branch-moves` (`docs/host-protocol.md`, "Branch moves").
- **Decision 6 holds, with the socket.** A move contacts no host the user did not add and runs only Git at each end; it needs no GitHub remote and pushes to none.
- **Decisions 1 to 4 are unchanged.** Uncommitted work is refused with a request to commit first; the commit Sotto checked is the one that moves; a move lands in a ref of its own; nothing is forced. Decision 3's "no `--force`" is not enough on its own outside `refs/heads` and `refs/tags`, where Git does not refuse a non-fast-forward fetch, so an incoming ref is created only when it does not exist, and a move ID that comes back with another commit is refused.
- **The cap.** One move carries at most 256 MiB (Zach, October 23). Sotto's last 40 pull request branches bundled to a median of 27 KB and at most 2.9 MB. A bigger bundle is refused in plain words on either side, and nothing moves.
- **What is built.** The operation is defined once on the host socket, with the desktop as its only caller (`src/main/agents/branchMoves.ts`); the Git half is shared by both sides (`src/main/agents/branchBundles.ts`), and a host's side is `src/host/branchMoves.ts`. A move ends in a receipt only. Starting the receiving worker from the moved branch (decision 4's worktree), Watcher's start from a thread's branch (decision 7) and the snapshot a check starts from come next; the sender takes a commit rather than a branch tip, which is where the snapshot's commit object goes. The worktree's removal of its incoming ref (decision 3) comes with that start.

## Amended October 27, 2026: Watcher's stop reaches a check waiting on a host (#1637)

Watcher's `stop_thread` on a check waiting in a paired host's own queue takes it out of that host's queue, starts nothing there, and reads stopped, as on This computer. Behind `cross-machine-work`.

1. **The stop travels as a stop.** The desktop sends Watcher's `stop_thread` in `watcher-control`, its target the waiting start's, rather than a field on the read as the user's Stop goes (`stoppedRequests`). A stop in `watcher-control` is an operation the host admits and answers, so the host decides, at the moment it acts, whether the check is still waiting: one still waiting has its start failed as stopped (`REQUEST_NOT_ACTIVE`) and the stop accepted in one change of the host's record; one whose turn has come is stopped as any thread is. The host's queue lets a check go before its thread is made, so the host never takes out as waiting a check whose thread exists or is being made. A stop that comes after its thread is made but before its first prompt has gone, which for a check includes the package install, cancels that prompt as a stop cancels any prompt still on its way. The check then never runs and reads stopped; once the prompt has gone, its start stands. A field on the read would have had the desktop record the check stopped before the host could say whether it had already started. Being an admitted operation, the stop also has its retry key and receipt (ADR-0058): an answer lost on the way is read back by its receipt, a retry with the same key answers with the one stop's receipt and stops nothing again, and a stop that never arrived is fenced and leaves the check waiting, which the model reads as an unconfirmed stop.
2. **The branch goes as before.** The desktop lets go of the branch it landed on the host for the check once the host's own copy of the start reads failed with no thread, as it already does after the user's Stop.
3. **No standing watch travels with it.** The host is sent a watch only once it has the thread, so the stop of a waiting check carries none.
4. **`watcher-check-stop`.** A host that keeps a check queue lists it, and only a desktop with Work across machines on uses it. Such a host's waiting checks are described as This computer's are ("stop_thread on its target, or the user's Stop, takes it out of the queue."). A desktop facing a host without it keeps the old words, that the user's Stop takes it out, and refuses `stop_thread` on its target as before, since the host has no thread there. A stable host keeps no queue and has nothing to stop.

## Amended October 27, 2026: one check worktree per repository on a machine (#1312, third part)

The research note's worktree reuse is built, behind `cross-machine-work`, for every check on a machine: delegated, Watcher's, and a host's own.

1. **One check worktree per repository per machine.** A check that gets a new worktree takes the machine's **check worktree** for its repository instead, a linked worktree under `check-worktrees/` in Sotto's data folder, named by the repository's common Git folder, on a detached HEAD. Each check moves it to its own commit, the check snapshot or the branch it starts from, and the incoming ref that commit arrived in goes once the folder has it checked out. The `node_modules` the checks before it installed stays, so a check costs no fresh `npm ci` and adds no 1.4 GB folder (ADR-0041). A check that works in the project folder or an existing worktree stays there. Sotto's own data folder rather than a repository's `.worktrees/`, which only this repository ignores: anywhere in the user's checkout it would show as untracked files there.
2. **`npm ci` first when `package-lock.json` changed.** The check worktree records the hash of the lockfile its `node_modules` was installed from in `node_modules` itself, so a `node_modules` that is removed, or emptied by an `npm ci` that then failed, installs again. When the commit's lockfile differs, `npm ci --ignore-scripts` runs there under the user's own Node, and the check's first message waits for it. No install script runs: Sotto runs the install before the check's thread exists, so no permission has been answered for any of that commit's code (ADR-0004), and a package that needs its script, such as a native build, is built by the check's thread with `npm rebuild` under its own approvals (Bug Bot on #1661, October 27). Then the model is told, in Zach's words (October 23), "Installing packages first, because package-lock.json changed since the last check on forge. The checks start when that finishes.", followed by "Install scripts do not run, so a package that needs one is ready only once the check's thread runs npm rebuild.", naming the machine as the queue's waiting words do. The words go only to the model and stay English. A project with no `package-lock.json` installs nothing.
3. **A failed install still starts the check** (`CHECK_STARTS_AFTER_FAILED_INSTALL`, Zach, October 27): its thread finds the packages missing when it runs and says so in its reply, and the model is told the install failed. The record is removed before the install changes anything and written only when it succeeds, so an install that stops partway is never trusted, and the next check installs again. `npm ci` is stopped after 30 minutes (`CHECK_INSTALL_TIMEOUT_MS`), and when Sotto closes, with its whole process tree, and nothing goes on until the tree is gone; closing waits for every setup to end before the store closes.
4. **Moving it never loses work** (`CHECK_WORKTREE_PREVIOUS_THREAD = 'follows'`, Zach, October 27). The thread of an earlier check lives on after its check. The check takes the folder's checkout reservation first, as a Git action does (ADR-0027's checkout guard), and holds it from before it reads the folder until its packages are ready, so no send or Git action starts there meanwhile. The folder then moves only when no other thread there holds work, active or pending, it holds no uncommitted changes or untracked files, its detached HEAD is the commit Sotto last put there, and Git can check the commit out without overwriting an ignored file (`--no-overwrite-ignore`); a branch checked out there keeps its own commits. Otherwise it stays as it is, and that check gets a worktree of its own, as checks did before, with its packages installed the same way. When it moves, the earlier check's thread follows its checkout, as a thread in a worktree does under ADR-0014; ADR-0014's "never switches one itself" holds for every other folder.
5. **How it shows.** The check's thread works in it as a reused folder, so its working copy shows that folder, detached at the check's commit, and no thread can reclaim it: ADR-0041's reclaim refuses a reused folder. **Previous worktree** and Search worktrees leave it out (Zach, October 27), since the next check moves it.
6. **When it goes.** Nothing removes it in this part; removing it is #1656. Projects are settled, not removed, and turning Work across machines off leaves it whole, as an Owl feature's records stay whole, so turning it back on finds its packages. It is one folder per repository on each machine.
7. **No host protocol change.** The `check` flag on `create-thread` is the host's own: only Watcher's and delegation's starts set it, the coordinator refuses it without their origin, and the remote command allow-list refuses it from any client.

## Amended October 27, 2026: Watcher's checks join the queue, and a host keeps its own (#1312, second part)

The October 26 amendment's queue now holds every check on a machine, behind `cross-machine-work`.

1. **One queue per machine, for every parent and for Watcher.** A Watcher `start_thread` with `testRun` is a check. On This computer it waits in the same queue as the checks threads delegate there, in the order asked. It takes its place as it is asked for, before it is placed and admitted, as a delegated check does, so a check asked later never overtakes it; it gives the place back when it is placed on another machine, refused, or a retry.
2. **A waiting receipt.** A Watcher check that waits answers at once, so the tool call does not last as long as the check ahead. Its result carries `check: { ahead, note }` and a `startedFrom` that "Starts on" its machine; `read_operation` gives the same words as the outcome's note, and a retry with the same key answers with the waiting receipt and the place as it is then. Its outcome stays `working`, with no new word. Its thread is made and sent its first prompt when its turn comes.
3. **Stop takes it out.** Watcher's own `stop_thread` on the waiting check's target (Zach, October 27), the user's Stop on Watcher, Stop all, or anything else that stops its request fails the waiting start as stopped, takes it out of the queue, starts nothing and lets go of the branch it would have started from. A check stopped while its snapshot is taken takes no place, and one whose snapshot finishes after Sotto closes lets go of its own branch. For a check waiting on a paired host, the desktop keeps the branch it landed there and lets it go when the start reads stopped or failed with no thread; `stop_thread` did not reach a check waiting on a host in this part; the amendment above (#1637) adds it.
4. **A host keeps its own queue,** shared by the checks its own threads delegate and the desktop Watcher's checks started there, named in the words its threads read as the relay's away sentence names it (#1316, Zach, October 27): by the name the desktop saved for it, which the desktop sends with `delegation-relay-name`, and by its own machine name until a desktop has sent one ("Waiting for forge's check to finish. 1 ahead."). The name is read each time the words are written, so a name sent later is used from then on. The desktop gives Watcher its own saved name for the host. The desktop marks a Watcher start as a check with a `check: true` flag on the start it sends in `watcher-control`, rather than a new host operation: the start already travels whole in that packet, its digest covers the flag, and the host's Watcher runs it through the same path as one of its own. A host lists `watcher-check-queue` only where its Owl answer turns on Work across machines. A stable desktop never sends the flag; a host whose answer is off refuses a start that carries it, and an older host's strict start schema refuses it as an unknown key. A host that does not list the feature is sent a plain start, which runs at once, as before this part.
5. **`test_run` for a host thread's `delegate`.** A thread on a headless host is offered `test_run`, gated by that host's own answer as its delegation is (#1310). It has no branch to start from there, so a check carries no snapshot, and `from_my_branch` is still refused.
6. **When a Watcher check leaves its place.** It holds while it is waiting, being started, working, or in background work not yet seen to end, which it holds until its thread has sat twenty minutes with no turn running (`CHECK_HOLDS_THROUGH_BACKGROUND`). A Watcher start has no proof of an unconfirmed first prompt arriving or never starting, as a delegated brief has, so an unconfirmed one holds only while its thread is seen working (`WATCHER_UNCONFIRMED_CHECK_HOLDS_WHILE_RUNNING`, Zach, October 27). A restart empties the queue: a start of the machine's still queued when Sotto starts again never made its thread, and its outcome reads unknown, with Keep local history on or off. The pass that releases checks runs on every publish and reads each check's operation at its last known place in the record, so its work does not grow with Watcher's history.

Not built in this part: one reused check worktree per project per machine, with `npm ci` first when `package-lock.json` changed (part 3, built in the amendment above), and the queue's place in Tools › Agents and the machine's panel (part 4).

## Amended October 26, 2026: one check at a time on a machine (#1312, first part)

Zach's answers of October 21 and 23 settle how checks are routed; the first part is built, behind `cross-machine-work`.

1. **A check queue per machine.** A machine runs one **check** at a time. The next waits in that machine's own queue, in the order asked, for every thread that asks. A check takes its place as it is asked for, before its snapshot is taken, so a slower snapshot never lets a later check overtake it. Only starts queue; a later brief to a check's thread does not (Zach, October 27). The queue lives in the memory of the Sotto running on the machine, so a restart empties it, and a check that waited is never started after one: its outcome reads unknown, as any brief that was waiting does (ADR-0081 decision 7).
2. **A waiting check is `working`.** There is no new outcome word. Nothing of it is started, so it counts as no working thread; its thread is made and sent its brief when its turn comes. The call's result carries `check: { ahead, note }`, the note saying "Waiting for This computer's check to finish. 1 ahead."
3. **Stop takes a waiting check out.** `cancel_delegation`, or Stop on the thread that asked for it, ends it as stopped, starts nothing, and lets go of the branch it would have started from. One stopped while it is being admitted takes no place at all. Closing Sotto lets go of every waiting check's branch, since none of them starts after a restart.
4. **The snapshot is taken when asked**, not when the check's turn comes, so edits made while it waits are not what it tests. The receipt says when, as the user's computer writes a time in the interface language (Zach, October 27): "Started on forge from feat/x with your uncommitted changes as they were at 2:02 PM (3 untracked files)." in US English, "14:02" in German. A headless host, which has no interface language, writes it its own default way. A check still waiting "Starts on" its machine.
5. **The reply is the contract.** `delegate`'s text asks the thread that starts a check to have the check's thread reply first with the verdict, the counts and the failing lines, inside the 32 KiB Sotto passes on; the full log stays in its history. Sotto passes the reply on as the thread's words and never reads pass or fail from it.
6. **A check holds its place through background work** its turn left running, until that work is seen to end or the outcome is released after twenty idle minutes (#1263; Zach, October 27, `CHECK_HOLDS_THROUGH_BACKGROUND`). It holds it too while its brief's delivery is unconfirmed, since the brief may yet have arrived, until it is seen to arrive or is proved never started.

Not built in this part: Watcher's checks joining the queue, on This computer and on a host, which needs a new host operation that a stable host refuses; one reused check worktree per project per machine, with `npm ci` first when `package-lock.json` changed; and the queue's place in Tools › Agents and the machine's panel (variant C of the October 23 prototype).

## Amended October 23, 2026: a worker started from a thread's branch (#1033)

The rest of #1033, step 8 of the research note's build order, is built on the transport above. Decisions 2 to 4 and 7 now run, and the snapshot a check starts from (ADR-0105 decision 8, which calls it a test run) with them. All of it is behind `cross-machine-work`: with it off, Watcher's `start_thread` and `delegate` offer none of it and refuse it as invalid, and a stable host neither lists nor takes `branch-move`.

1. **Watcher's `start_thread` takes `fromThread`**, a thread by host and thread ID, with a new-worktree working copy. Sotto places the start as #1032 does, then, after admission and just before the start runs, moves the thread's branch to the machine it goes to and starts the worker there in a new worktree made from the move's incoming ref. A start refused at admission moves nothing. The start a paired host is sent names only the move (`fromMove`), so the start it admits is the one the desktop digested; Watcher may not name a move itself.
2. **`delegate` takes `from_my_branch`.** A delegated thread starts on This computer for now (#1316), so its branch is copied into the project's incoming ref on this computer, before admission; a start admission refuses lets that ref go again.
3. **Every direction.** This computer to a host and a host to This computer are the moves above. A host thread's branch to a project on the same host is a `copy` the host makes itself, and from one host to another the desktop relays the bundle chunk by chunk over the two sockets it keeps (ADR-0105 decision 1), writing nothing of its own. On This computer the same copy runs in main.
4. **The worker's branch** has the moved name, or the next free `<name>-<n>` when a branch of that name is already there, as the source thread's own is when the worker starts beside it. The branch the user or the thread made is never moved (decision 4). Counting stops at 99, after which the worker takes a `sotto/<token>` branch.
5. **The incoming ref goes with the worktree** (decision 3): the worktree record keeps it (`incomingRef`), and removing the worktree, by the user or a cleanup rule, removes the ref. The worker's branch keeps the commits, so its folder can be put back on it.
6. **Uncommitted work refuses a plain start** with the move's own sentence, "This thread has uncommitted changes. Commit them first, then move the branch. Nothing was moved." A **check** (`testRun`, `test_run`), which only the call can say, carries it as a **check snapshot** instead (ADR-0105 decision 8). The snapshot's commit names Sotto as its author and is never signed, so a repository with no identity configured, or one that signs with a passphrase, cannot hold the start. The receipt lists the untracked files it carried.
7. **Receipts.** The start's `startedFrom` gives the machine, the branch, what a snapshot carried and Sotto's sentence: "Started on forge from feat/x." and "Started on forge from feat/x with your uncommitted changes (3 untracked files)." (Zach, October 23). In memory, as a start's placement is. A delegation Sotto refuses because its branch could not go is recorded as `BRANCH_UNAVAILABLE`, and its card says so.

What is not built here: queueing one test suite per machine and a reused test worktree (#1312), for which `testRun` is the seam; bringing results back (#1030); and a thread on a host delegating (#1310, #1316). A Watcher start that fails after its branch landed, before its worktree is made, lets the incoming ref go: when it is refused or stopped here, when the receiving machine refuses it or answers with a definite failure and no thread, and when reconciling finds that a start whose answer was lost failed with no thread. A delegation lets its ref go when admission refuses the start, when a racing call with the same retry key already made it, and when its new thread was not made. Otherwise the ref stays: while the outcome is uncertain, when the receiving machine may have made the thread, and in two cases where a lost answer is no longer followed. This computer remembers such starts only in memory, so a restart of this computer forgets them (Zach accepted this), and it remembers at most 1,000, so the oldest are dropped past that. A ref left this way waits until the repository's refs are tidied by hand, and the move record names it.
