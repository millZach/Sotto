# Mods change how Sotto looks and add parts of their own

Accepted by Zach on November 25, 2026. He asked for a way for users to customize everything in Sotto's window, as T3 Code and Claude Code allow. T3 Code keeps custom CSS with a theme and lets an agent write it. Claude Code has mods: code an agent writes that restyles the app and adds panes, bands, status lines and menu rows. A first take offered only text size, fonts, spacing and corners; Zach turned it down ("T3 Code lets you fully customize the UI, like everything in it"). The second prototype (`docs/prototypes/ui-customization/index.html` on the tag `prototype/ui-customization-mods`, beside the first take as `type-settings-v1.html`) showed three ways in. On the question card he chose B, a Mods page, with "Looks and new parts", "A thread, or by hand", and Owl.

A **mod** is a folder in Sotto's mods folder that changes how the main window looks, and later adds parts of its own to it. Mods are an Owl feature, `mods` in `src/shared/owlFeatures.ts` (ADR-0072).

## Decisions

1. **A mod is a folder of plain files.** Each mod is `mods/<id>/` in Sotto's data folder: `mod.json` names it (`name`, and an optional `description`), and `look.css` holds its look. The folder's name is its id: lowercase letters, digits and dashes. A folder without a readable `mod.json` is listed as a mod that could not be read, with the reason, and paints nothing. Sotto reads at most 64 mods, and at most 64 KB of CSS from each.
2. **Looks target named parts.** Every main surface carries a `data-part` name from `src/shared/modParts.ts` (`sidebar`, `sidebar-row`, `composer`, `message`, and so on). Those names are kept across Sotto's updates; class names are not, and a mod that uses them may break on any release. `modParts.test.ts` holds each name to an element in the renderer. A mod's CSS is painted after Sotto's own stylesheets, so it wins a tie; it can use `--tt-*` tokens to follow the theme.
3. **Nothing a mod paints reaches outside.** Main reads each `look.css` and refuses a look with an `@import`, an `image-set()`, a `src()` or a `url()` that is not a `data:` address or a `#fragment`, after decoding CSS escapes so `\75 rl(` counts as `url(`. T3 Code strips those; Sotto refuses the whole look and the Mods page says why, so what paints is exactly what was written and nothing is half applied. The main window's content security policy already refuses any outside font, picture or connection, so this is the second fence, not the only one. Mods paint only the main window: the floating widget, the popup and the iPhone are left alone. No new host is contacted.
4. **Made by a thread, or by hand.** Make a mod on Settings › Mods starts a thread in the **Mods** project, at the mods folder, with the user's words as its first message. Sotto keeps `AGENTS.md` and `CLAUDE.md` in that folder, written fresh each time a mod is made, saying how a mod is laid out and listing every part name, so any provider's agent learns the format from its working folder rather than from a rewritten prompt. Change it in a thread starts the same way with the mod named. A mod can also be written, copied in or shared by hand: Open mods folder shows the folder.
5. **Each mod has a switch.** Switched-off mods are listed by id in the `modsOff` setting, so a new mod is on as soon as it appears. Turn off every mod switches every listed mod off. **Turn off every mod** is also in the View menu, on Ctrl+Alt+Shift+M (Cmd+Option+Shift+M on a Mac), which answers even when a mod has hidden the controls. Remove moves a mod's folder to the bin, never deleting it outright.
6. **Live.** Main watches the mods folder while the feature is on and the window is open, and sends the list again when a file changes. The window replaces one stylesheet's text in place, so a change repaints without reloading or remounting anything.
7. **New parts come next, in a sandbox.** A mod will be able to add a pane, a band above the composer, a line in the strip and a menu row, drawn with Sotto's own components from a declarative tree. Its code will run in a worker with no network, no DOM and no `window.sotto`, given read-only facts Sotto chooses (a thread's title and state, its checks, the day's usage, the clock). That is the second part of this decision's plan, with its own pull request.
8. **A mod is never a grant** (ADR-0004). A mod cannot answer a permission or a question, cannot change what is sent to an agent, and cannot read keys or the words of a thread. The thread that makes a mod is an ordinary thread: it asks before it acts, as its permission mode says.
9. **Off, it is dormant.** Where the Owl answer is off, nothing reads or watches the mods folder, no CSS is painted, the Mods page and the menu item are absent, and the folder and `modsOff` are kept whole.

## Considered options

- **CSS in the theme (T3 Code's way, variant A).** Simple, and exported with the theme, but it can only restyle: it cannot add a pane or a band, which Zach chose to allow.
- **Customize in place (variant C).** Press a part, change it, or ask a thread about it. Kept as a later addition whose changes would save as one mod.
- **Mods as code in the window.** Running a mod's script in the renderer would give it `window.sotto`, and with it every command the window can send. The worker in decision 7 is the alternative.

## Consequences

The design captures paint with no mods. A part renamed in `modParts.ts` breaks mods that use it, so a rename needs a reason in its pull request and keeps the old name beside the new one for a release. `themeTokens.test.ts` does not reach a mod's CSS: a mod's colours are the user's choice.
