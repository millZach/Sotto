# 5. Codex App Server provider adapter

## Status

Accepted — 2026-09-10.

## Context

Ticket #20 implements section 10 and milestone M2 of the memory-first prototype spec v0.2. Threads belong to Sotto; the coordinator already reconciles uncertain commands by Sotto thread ID, message ID and request ID. Codex assigns its own thread ID, while `SottoThreadHost` reserves a separate provider session ID before dispatch. Changing the thread interface for one provider would spread a protocol detail into every adapter.

## Decision

**Use the native App Server protocol over stdio.** Codex CLI 0.154.0 provides thread creation, resume, streamed items, interruption and interactive requests directly. ACP would require an additional adapter for Codex; stream-json is the native route chosen for Claude, not the Codex thread service. A single child belongs to each connected `CodexAppServerHost`. JSON objects are framed by newline and validated with Zod. Native executable resolution and the filtered native environment are shared with `subscriptionCodex.ts`; no shell shim is launched. Endpoint and credential arguments are ignored by this provider. No prompt, protocol body, stderr text or secret is logged by the adapter.

**A project is a working directory.** Sotto records absolute project paths in `codex-projects.json` under Electron's user data folder and passes the selected path as `cwd`. Sotto's coordinator creates the directory before dispatch. The adapter does not discover Codex projects or attach unrelated provider sessions.

**Keep the existing thread interface and persist an adapter-owned alias.** `threads.json` retains the binding from Sotto thread ID to provider `codex` and the client-chosen provider session ID. `codex-threads.json` maps that client-chosen ID to `{ codexThreadId, projectId, cwd, title, modelId, createdAt, origins }`. Adapter snapshots and commands use only the client-chosen ID; the server-assigned Codex thread ID never crosses the adapter boundary. This is smaller than changing `SottoThreadHost`, `ThreadRegistry` or `AgentHost`, and keeps existing outbox reconciliation unchanged. The alias is saved before creation is reported, including a response received after the caller's timeout.

`origins` stores message/command IDs, a SHA-256 digest of each dispatched text, item/turn IDs when available, and a creation timestamp. It does not store prompt text. The origin is saved before dispatch; `clientUserMessageId`, returned `clientId`, and pending-dispatch digest matching preserve the coordinator's message ID through notifications and resume. A definitive rejection removes that pending origin. A timeout retains it for reconciliation. These metadata registries are local recovery data and are not a copy of the transcript.

**Coding threads keep tools and rollout persistence enabled.** Launch arguments are `codex app-server --stdio`, with `-c model_provider="openai"`, `-c approval_policy="on-request"`, `-c approvals_reviewer="user"`, and `-c sandbox_mode="workspace-write"`. Thread start/resume also specify the corresponding policy and reviewer; creation specifies `ephemeral: false`, `historyMode: 'legacy'` and `allowProviderModelFallback: false`. We do not apply the reasoning client's disabled-feature list, empty execution environments or `history.persistence="none"`. Models come from `model/list`, with a literal `gpt-5.4` fallback if discovery is unavailable. Native Codex owns authentication and its existing configuration.

**Route requests into the attention queue and require explicit decisions.** Command and file approvals expose Allow/Deny and respond with `decision: 'accept'` only from an answer command with `approved: true`. Decline, skip, interruption and disconnect never approve; interruption and disconnect send decline/empty-answer responses to pending requests. Additional permission profiles are visible but can only be declined in this version; approving them produces guidance to answer in Codex. We never synthesize a broad permission grant or a persistent session grant.

User-input questions retain the JSON-RPC ID while pending. Single answers become `{ answers: { questionId: { answers: [text] } } }`. Multiple questions display numbered text and options, and accept numbered answer lines or a JSON object keyed by question ID. MCP form elicitations support validated string fields and their offered options; explicit form answers use `action: 'accept'` and structured `content`. This is delivery of the user's answer, not a permission grant. URL, device-verification, unsupported structured fields and extension forms require an answer in Codex; disconnect sends `action: 'decline'`. `serverRequest/resolved` removes requests answered directly in the provider.

**Timeouts preserve uncertainty.** Every client request has a deadline (15 seconds by default); mutation timeouts return `{ accepted: false, uncertain: true }`. The response callback remains registered until its response or child exit so late creation aliases and message confirmations are still applied. The adapter does not retry mutations. A snapshot after uncertain prompt delivery reads the existing provider session with `thread/read`; a confirmed message carries the outbox message ID. A repeated pending creation or message dispatch is not sent again. Late `turn/start` responses cannot change a completed turn back to running. Response validation or pipe failure also retains uncertainty instead of asserting that the provider rejected a mutation.

**Resume known provider sessions on connect.** Load both registries, resume known aliases with `thread/resume`, and hydrate messages and status from its returned turns. Observations resume any known alias not yet live and ignore unknown IDs. The provider's reported runtime status is authoritative: resume restores conversation state, not processes killed with the previous App Server. Unexpected child exit publishes `connected: false` so AgentControl's existing reconnect path can recover. Stdout lines and the queued frame backlog are bounded to 1 MiB; stderr is counted and discarded with a 1 MiB lifetime cap. Disconnect ends stdin after denials and force-kills a child that does not exit; a shutdown barrier lets tests await process exit before removing temporary data.

**Detect takeover through the Codex session log.** `CodexSessionLogWatcher` searches `$CODEX_HOME/sessions/YYYY/MM/DD` for `rollout-*-<codexThreadId>.jsonl`, caches each path, and tails byte offsets on an unref'd interval. The default home is `process.env.CODEX_HOME` or `~/.codex`. Partial UTF-8 lines are retained; malformed or unrelated lines are ignored. Only `event_msg` user-authored entries count: `item_completed` with `item.type` equal to `UserMessage` or `user_message`, or `payload.type: 'user_message'`. `response_item` user messages may contain injected instructions and never cause takeover.

One matching dispatched-text digest consumes one own-message entry. Every other authored input becomes a user message with its rollout item ID (or a stable ordinal/text hash) and no command ID. AgentControl sees that fresh message outside `assignment.ownMessageIds` and changes the assignment to manual. Selecting or resuming a provider session without typing does not itself transfer authority. Polling avoids Windows `fs.watch` append reliability issues; snapshot and guarded send also poll before acting.

Protocol shapes were confirmed by running `codex app-server generate-json-schema --help`, then `codex app-server generate-json-schema --experimental --out <OS temporary directory>` against the installed 0.154.0 binary. The generated `ClientRequest.json`, `ClientNotification.json`, `ServerRequest.json`, `ServerNotification.json`, the v1 initialize schemas, v2 request/response/item schemas, and root approval/input/elicitation schemas are authoritative for this adapter. The protocol reference is <https://learn.chatgpt.com/docs/app-server>.

Exact names used:

- Client requests: `initialize`, `model/list`, `thread/start`, `thread/resume`, `thread/read`, `turn/start`, `turn/interrupt`; client notification: `initialized`.
- Server notifications: `thread/started`, `turn/started`, `turn/completed`, `item/started`, `item/completed`, `item/agentMessage/delta`, `error`, `serverRequest/resolved`. There is no generic `item/updated` notification in this generated schema.
- Server requests: `item/commandExecution/requestApproval`, `item/fileChange/requestApproval`, `item/permissions/requestApproval`, `item/tool/requestUserInput`, `mcpServer/elicitation/request`. The compatibility spelling `tool/requestUserInput` is also handled using the same answer shape, as in the existing reasoning client; it is not advertised by this binary's generated `ServerRequest.json`.

## Consequences

- The shared adapter integration contract exercises create, prompt, streaming, status, cancel, questions, permission decisions, skipping, uncertain delivery and restart. Every check runs against a real child process speaking the fake Codex protocol; the in-memory `FakeProviderHost` skips only transport uncertainty and durable restart because it has neither seam. AgentControl-level tests additionally cover the outbox, attention queue and manual takeover. These tests do not claim a live paid coding turn was run.
- Claude and Grok still need provider adapters, native request mappings, persistence, takeover handling and fixtures passing the same contract. The Threads page still needs provider selection, provider-specific presentation and access to underlying transcripts. Existing T3 labels remain for the integrator's UI work.
- Provider choice defaults to `t3` for existing saved configurations and is selected at connect time, after configuration restoration. Both adapters share the thread registry. The E2E host remains unwrapped. An omitted provider in a configuration patch cannot reset the selected provider.
- Foreign Codex thread discovery is intentionally absent. If the process dies before Sotto receives a `thread/start` response, an orphaned provider thread and an unresolved Sotto binding can remain; an alias cannot be reconstructed from an unknown server ID. Never repeat creation blindly to repair this window.
- Takeover depends on rollout persistence and the documented event shapes. Missing/locked logs delay detection. Digest matching cannot distinguish an identical externally typed prompt from one still-unmatched Sotto dispatch; each match suppresses only one entry. The watcher scans historical entries on restart and stable IDs prevent already-seen input from being fresh. No live session log content was printed or copied during implementation.
- Recovery metadata grows with dispatched message identities. Paginated history, history compaction, foreign discovery, richer MCP forms, and safely presenting/granting additional permission profiles are later work. This adapter requests legacy history so resume/read can hydrate turns without a pagination implementation.
