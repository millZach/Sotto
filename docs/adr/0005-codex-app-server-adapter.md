# 5. Codex App Server provider adapter

## Status

Accepted — 2026-09-10.

## Context

Ticket #20 implements section 10 and milestone M2 of the memory-first prototype spec v0.2. Threads belong to Sotto; the coordinator already reconciles uncertain commands by Sotto thread ID, message ID and request ID. Codex assigns its own thread ID, while `SottoThreadHost` reserves a separate provider session ID before dispatch. Changing the thread interface for one provider would spread a protocol detail into every adapter.

## Decision

**Use the native App Server protocol over stdio.** Codex CLI 0.154.0 provides thread creation, resume, streamed items, interruption and interactive requests directly. ACP would require an additional adapter for Codex; stream-json is the native route chosen for Claude, not the Codex thread service. A single child belongs to each connected `CodexAppServerHost`. JSON objects are framed by newline and validated with Zod. Native executable resolution and the filtered native environment are shared with `subscriptionCodex.ts`; no shell shim is launched. Endpoint and credential arguments are ignored by this provider. No prompt, protocol body, stderr text or secret is logged by the adapter.

**A project is a working directory.** Sotto records absolute project paths in `codex-projects.json` under Electron's user data folder and passes the selected path as `cwd`. Sotto's coordinator creates the directory before dispatch. The adapter does not discover Codex projects or attach unrelated provider sessions.

**Keep the existing thread interface and persist an adapter-owned alias.** `threads.json` retains the binding from Sotto thread ID to provider `codex` and the client-chosen provider session ID. `codex-threads.json` maps that client-chosen ID to `{ codexThreadId, projectId, cwd, title, modelId, createdAt, origins }`. Adapter snapshots and commands use only the client-chosen ID; the server-assigned Codex thread ID never crosses the adapter boundary. This is smaller than changing `SottoThreadHost`, `ThreadRegistry` or `AgentHost`, and keeps existing outbox reconciliation unchanged. The alias is saved before creation is reported, including a response received after the caller's timeout.

This adds an indirection to [ADR-0002](0002-sotto-owned-thread-identity.md): the thread registry holds the Sotto-chosen provider session ID, while the server-assigned Codex thread ID lives one hop further inside the adapter's `codex-threads.json`. A later feature that opens the underlying transcript asks the adapter rather than the registry. A rebind step on the thread interface was rejected because a late `thread/start` response would otherwise bind a second Sotto thread.

`origins` stores message/command IDs, a SHA-256 digest of each dispatched text, item/turn IDs when available, and a creation timestamp. It does not store prompt text. The origin is saved before dispatch; `clientUserMessageId`, returned `clientId`, and pending-dispatch digest matching preserve the coordinator's message ID through notifications and resume. A definitive rejection removes that pending origin. A timeout retains it for reconciliation. These metadata registries are local recovery data and are not a copy of the transcript.

**Coding threads keep tools and rollout persistence enabled.** Launch arguments are `codex app-server --stdio`, with `-c model_provider="openai"`, `-c approval_policy="on-request"`, `-c approvals_reviewer="user"`, and `-c sandbox_mode="workspace-write"`. One `threadPolicy` supplies the launch configuration and thread start/resume policy. Turn start uses only its approval policy and reviewer because its sandbox override is the distinct `sandboxPolicy` shape; creation specifies `ephemeral: false`, `historyMode: 'legacy'` and `allowProviderModelFallback: false`. We do not apply the reasoning client's disabled-feature list, empty execution environments or `history.persistence="none"`. Models come only from `model/list`. Discovery failure publishes no models and a plain snapshot error asking the user to check Codex and reconnect; creation rejects an unavailable model. Native Codex owns authentication and its existing configuration.

**Route requests into the attention queue and require explicit decisions.** Command and file approvals expose Allow/Deny and respond with `decision: 'accept'` only from an answer command with `approved: true`. Decline, skip, interruption and disconnect never approve; interruption and disconnect send decline/empty-answer responses to pending requests. Additional permission profiles are visible but can only be declined in this version; approving them produces guidance to answer in Codex. For `item/permissions/requestApproval`, the schema has no explicit decline form: an empty grant is the only refusal. The adapter sends `{ permissions: {}, scope: 'turn' }`. We never synthesize a broad permission grant or a persistent provider session grant.

User-input questions retain the JSON-RPC ID while pending. Before writing an answer, the adapter removes it from pending state and remembers the in-flight ID. Repeated answers are rejected, and interruption/disconnect cannot decline an answer already in flight, even after its write deadline. Reset clears in-flight IDs. Single answers become `{ answers: { questionId: { answers: [text] } } }`. Multiple questions display numbered text and options, and accept numbered answer lines or a JSON object keyed by question ID. MCP form elicitations support validated string fields and their offered options; explicit form answers use `action: 'accept'` and structured `content`. This is delivery of the user's answer, not a permission grant. URL elicitations expose Continue and Decline in Sotto. They remain questions, including app-tool confirmations: supervision on a managed thread may answer and accept them. This is the intended behaviour as of September 30, 2026, and is a specific exception to ADR-0004’s rule that supervision follow-ups approve nothing. The owner accepted that these confirmations may be accepted without the user seeing them first. Device-verification, unsupported structured fields and extension forms require an answer in Codex; disconnect sends `action: 'decline'`. `serverRequest/resolved` removes requests answered directly in the provider.

**Timeouts preserve uncertainty.** Every client request has a deadline (15 seconds by default); mutation timeouts return `{ accepted: false, uncertain: true }`. The response callback remains registered until its response or child exit so late creation aliases and message confirmations are still applied. The adapter does not retry mutations. A snapshot after uncertain prompt delivery reads the existing provider session with `thread/read`; a confirmed message carries the outbox message ID. A repeated pending creation or message dispatch is not sent again. Late `turn/start` responses cannot change a completed turn back to running. Response validation or pipe failure also retains uncertainty instead of asserting that the provider rejected a mutation.

**Resume a thread when it is opened, and read its turns once.** Amended for ticket #113. Load both registries at connect, but resume nothing there except the threads Sotto is already watching: the IDs a previous `observeThreads` named, plus personal chats, which have no other opening step and own their native request channel. Every `thread/resume` sends `excludeTurns: true`, so resuming carries the conversation and its status but no transcript, and costs the same for a long thread as a short one. Turns arrive from `thread/read` with `includeTurns: true` when a thread is opened and Sotto holds no history for it on this connection, and from the explicit reads that `refreshThread`, rewind and the guarded send path already make. A freshly created thread already holds its own empty history and is not read again. Observations open any known alias and ignore unknown IDs. A thread nobody opens costs nothing at connect, and connect no longer grows with the number or length of saved Codex threads.

The original decision resumed every known alias with its turns at connect, which shipped every turn of every thread on every start. A saved thread whose rollout is missing now reports that when it is opened rather than at connect, and input typed into an unopened thread stays buffered until Sotto opens it. The provider's reported runtime status is authoritative: resume restores conversation state, not processes killed with the previous App Server. Unexpected child exit publishes `connected: false` so AgentControl's existing reconnect path can recover. Stdout lines are bounded to 128 MiB and the queued frame backlog to 256 MiB, allowing legacy history to echo screenshots from multiple sends and steers; stderr is counted and discarded with a 1 MiB cap per one-second window (amended October 1, 2026, #532, across all four provider transports). Steady diagnostics do not exhaust a lifetime allowance. Disconnect ends stdin after denials and force-kills a child that does not exit; a shutdown barrier lets tests await process exit before removing temporary data.

**Detect takeover through the Codex session log.** `CodexSessionLogWatcher` searches `$CODEX_HOME/sessions/YYYY/MM/DD` for `rollout-*-<codexThreadId>.jsonl`, caches each path, and tails byte offsets on an unref'd interval. The default home is `process.env.CODEX_HOME` or `~/.codex`. Partial UTF-8 lines are retained; malformed or unrelated lines are ignored. Only `event_msg` user-authored entries count: `item_completed` with `item.type` equal to `UserMessage` or `user_message`, or `payload.type: 'user_message'`. `response_item` user messages may contain injected instructions and never cause takeover.

An authored receipt is suppressed only when its explicit client ID and text digest match a dispatched Sotto message. Legacy rows without a client ID stay unowned until complete turn history corroborates their identity; repeated text alone cannot hide native input. Foreign input becomes a user message with its rollout item ID (or a stable ordinal/text hash) and no command ID. This includes image-only input, whose text is empty. AgentControl sees fresh input outside `assignment.ownMessageIds` and changes the assignment to manual. Selecting or resuming a provider session without typing does not itself transfer authority. Polling avoids Windows `fs.watch` append reliability issues; snapshot and guarded send also call `pollSessionLogs()` before acting. The watcher and shared text extraction live in `codexSessionLog.ts`.

Rollout evidence from Codex 0.154.0 on this machine was inspected by entry types only: one user prompt produced exactly one `event_msg` with `payload.type: 'item_completed'` and `payload.item.type: 'UserMessage'`, no `event_msg` with `payload.type: 'user_message'`, and two `response_item` entries with `role: 'user'`. The latter remain ignored. No real rollout text was read or copied; alternate authored-entry spellings are covered by synthetic fixtures.

The adapter has not been run against a real `codex app-server` process. Every protocol claim rests on the generated JSON schema of Codex 0.154.0 plus the fake. The schemas generated by `codex app-server generate-json-schema --experimental --out <a temporary directory>` were rechecked locally, including `ServerRequest.json`, approval/input/elicitation responses, MCP form params and `TurnStartParams.json`. The generated `ClientRequest.json`, `ClientNotification.json`, `ServerRequest.json`, `ServerNotification.json`, the v1 initialize schemas, v2 request/response/item schemas, and root approval/input/elicitation schemas are authoritative for this adapter. The protocol reference is <https://learn.chatgpt.com/docs/app-server>.

The fake now validates replies to the server requests it raises using hand-written checks against the generated schema's required keys, decision/action values, answer maps and permission object/scope shapes. It records a malformed reply's method, ID and reason in `violations.jsonl`, then forwards resolution so tests do not hang. Fixture request inspection and cleanup throw with those reasons. The fake does not require generated files at test runtime.

Exact names used:

- Client requests: `initialize`, `model/list`, `thread/start`, `thread/resume`, `thread/read`, `turn/start`, `turn/interrupt`; client notification: `initialized`.
- Server notifications: `thread/started`, `turn/started`, `turn/completed`, `item/started`, `item/completed`, `item/agentMessage/delta`, `error`, `serverRequest/resolved`. There is no generic `item/updated` notification in this generated schema.
- Handled server requests: `item/commandExecution/requestApproval`, `item/fileChange/requestApproval`, `item/permissions/requestApproval`, `item/tool/requestUserInput`, `mcpServer/elicitation/request`. Other generated server requests (`account/chatgptAuthTokens/refresh`, `applyPatchApproval`, `attestation/generate`, `currentTime/read`, `execCommandApproval`, `item/tool/call`) receive an unsupported-request JSON-RPC error.

## Follow-up: clarification questions during work

September 23, 2026: enable `features.default_mode_request_user_input` on Sotto's thread start and resume configuration, preserving browser configuration and reasoning effort. The installed Codex CLI 0.156.1 exposes this feature but leaves it off by default. Its generated protocol includes `item/tool/requestUserInput` with `isBlocking`; Default mode can deliver a question without stopping the turn. The same question request and user-answer path already serve Sotto's question panel. Agent prose alone is not a structured request.

Sotto's developer instructions direct actionable clarification questions through `request_user_input`, including free-text questions and questions asked while independent work continues. This applies to project threads and personal conversations, including resumed ones. It does not change collaboration mode, approval policy, the user's global Codex configuration, or permission handling. Native questions still need an explicit user answer; a recommendation grants nothing. The feature is under development in the native client, so future compatibility changes require verification against that client's protocol.

For project threads, `developerInstructions` replaces the native configured value. Before starting or resuming, Sotto reads the effective `developer_instructions` with `config/read` scoped to the working directory and appends its question guidance. It retains only that field, without logging or persisting the config response. An unreadable or malformed response stops the operation before new work is sent and leaves creation retryable. Personal conversations retain their existing Sotto-owned instructions and untrusted memory context.

Evidence: the installed feature catalog and generated schemas, the [App Server reference](https://learn.chatgpt.com/docs/app-server), and OpenAI's `request_user_input_default_mode_forwards_non_blocking` protocol test. Scripted adapter tests establish Sotto's configuration and answer routing, not whether a live model always chooses the tool. See [verification](../verification/codex-questions-thread-agents.md).

## Follow-up: changing loaded thread settings

September 19, 2026: `thread/resume` is not a settings update for an already-loaded thread. Codex 0.155.1 can return the existing effort unchanged, and an unmaterialized thread has no saved rollout to resume. Change model, effort and permission settings with `thread/settings/update`. Its empty acknowledgement alone does not confirm effective settings; also require the matching `thread/settings/updated` notification, mapping `effort` and `sandboxPolicy` to the adapter's existing settings comparison. Both request and notification shapes were checked against the installed client's generated schemas. A live synthetic thread passed High → Ultra → High → Ultra with both approval-required and Auto permissions, without a model turn.

Register confirmation before dispatch and await it outside the serial frame callback. Retain unconfirmed intent across timeouts and reconnects; reconciliation only observes settings and never resends an update. A valid mismatch affects the thread, not the shared transport. An explicit replacement can resolve it, and a rejected replacement retains the previous intent. A native notification can only confirm the exact recorded choice; it cannot create permission authority.

## Follow-up: the newest-turn check before a send

September 26, 2026, ticket #324. A send used to read the whole transcript with `thread/read` and `includeTurns: true`, apply it and save it before `turn/start`, only so that input typed in another Codex process could not be answered by a stale reply. Against the fake app-server that read grew from about 30 ms at 50 turns to 2.7-5.3 s at 2,000, and most of it was Sotto applying the reply rather than Codex sending it (`docs/perf/2026-09-26-codex-send-read.md`).

Every read made immediately before a send now asks first for the newest turn alone: `thread/turns/list` with `limit: 1`, `sortDirection: 'desc'` and `itemsView: 'full'`. That covers the adapter's own read before `turn/start` and the personal-chat send's read before it resumes the chat's instructions. It also covers the coordinator's read before a manual send from the Threads page, a coordinator draft send, a supervision follow-up and a queued follow-up (the last added October 6, 2026, #764, when the checkpoint hook stopped reading the thread again). The coordinator asks for the check by passing `{ beforeSend: true }` to `AgentHost.refreshThread`. Every wrapping host hands it on. Since #765 the coordinator's read stands for the adapter's own, so a send makes the check once, and Claude and Grok honour the purpose too ("Amendment: one read before a send" below).

The check passes only when the newest turn is the one Sotto already holds, has ended, says it carries the full items, and reconciles onto exactly the messages Sotto already has. Then nothing was added to or taken from the transcript since Sotto last read or streamed it, and a whole read would change nothing the send checks. The send applies that one turn, saves, and goes on to the same `expectedLastUserMessageId`, status and request checks as before. The match is decided on copies of the turn's message identities and of the origins, with the same reconciliation applying the turn runs, and only a turn that matches is applied. A turn that does not match leaves the thread as it was for the whole read to find.

Anything else reads the whole transcript, as it always did. This is the full list, and the condition in `confirmNewestTurn` is the same list in code:

- a thread not yet read on this connection, or a paginated one;
- work or a request in flight, or delivery that is uncertain;
- a settings change, rewind or compaction not yet confirmed;
- session-log input not yet shown;
- a newest turn Sotto does not hold, one still running, or one Sotto rewound;
- a reply that does not say it carries the full items, or a message Sotto cannot match;
- a reply that arrived after the thread moved on;
- any refusal, or no reply in time. A reply that comes later is dropped, as a late whole read is.

A refusal that says Codex does not have the request, or does not know a value the request sends, stops Sotto asking on that connection: JSON-RPC's "method not found", or the invalid request naming an unknown variant that 0.157.1 sends for either. The check sends the same values every time, so such a Codex would refuse every send's check and each would cost a whole read on top. Any other refusal is asked again on the next send.

This is not a cache. Nothing is trusted because of when it was read, and the session log is still polled before the check and again before `turn/start`. Since #765 the coordinator's check stands for the adapter's, for the one send it was made for and only while the thread has not moved ("Amendment: one read before a send" below). The coordinator's reconciliation read after Codex accepts a send happens only when Codex's own echo has not already settled the send; since #765 it asks the workspace for what it holds before reading whole.

The evidence is the installed Codex CLI 0.157.1. Its generated schema has `thread/turns/list` without `--experimental`, newest first by default. Against a throwaway `CODEX_HOME` with a legacy thread and no model turn, the request works on a legacy thread; its newest turn has the same turn ID, item IDs and status as the last turn of `thread/read`, and both are stable across reads; and on a thread this app-server has resumed, both see a turn written to the session file from outside, which is what another Codex process does. The thread's `updatedAt` did not move when that turn was written, so it could not stand in for either request. Rewind, reconnect, opening a thread, a snapshot after uncertain delivery and a pending settings change still read the whole transcript.

## Consequences

- The shared adapter integration contract exercises create, prompt, streaming, status, cancel, questions, permission decisions, skipping, takeover with stale-reply rejection, uncertain delivery and restart. Every check runs against a real child process speaking the fake Codex protocol; the in-memory `FakeProviderHost` skips only transport uncertainty and durable restart because it has neither seam. AgentControl-level tests additionally cover the outbox, attention queue and manual takeover. These tests do not claim a live paid coding turn was run.
- Claude and Grok still need provider adapters, native request mappings, persistence, takeover handling and fixtures passing the same contract. The Threads page still needs provider selection, provider-specific presentation and access to underlying transcripts. Existing T3 labels remain for the integrator's UI work.
- Provider choice defaults to `t3` for existing saved configurations and is selected at connect time, after configuration restoration. Both adapters share the thread registry. The E2E host remains unwrapped. An omitted provider in a configuration patch cannot reset the selected provider. Changing the provider or its server is refused while assignments or outbox items exist; otherwise it disconnects the active provider and selects the new one on the next Connect. Only an endpoint change clears the T3 credential.
- Foreign Codex thread discovery is intentionally absent. If the process dies before Sotto receives a `thread/start` response, an orphaned provider thread and an unresolved Sotto binding can remain; an alias cannot be reconstructed from an unknown server ID. Never repeat creation blindly to repair this window.
- Takeover depends on rollout persistence and the documented event shapes. Missing/locked logs delay detection. Digest matching cannot distinguish an identical externally typed prompt from a pending Sotto dispatch or its consecutive duplicate entries. Suppression lasts until a different authored-text digest arrives. The watcher scans historical entries on restart and stable IDs prevent already-seen input from being fresh. No live session log content was printed or copied during implementation.
- A turn read is still whole: Codex 0.154's generated schema offers no turn range or page size for legacy history, so Sotto cannot ask for the last N turns of a long thread. Windowing that read waits for the paginated history mode below; until then the bound on one read is the adapter's 128 MiB frame cap. Background rollout polls still read 1 MiB at a time; a complete authored image row may span polls. Amended September 26, 2026: Codex 0.157.1 has `thread/turns/list`, which pages legacy history too, and a send now uses it for its newest turn alone (the follow-up above). Opening a thread and every other read are still whole.
- Recovery metadata grows with dispatched message identities. Paginated history, history compaction, foreign discovery, richer MCP forms, and safely presenting/granting additional permission profiles are later work. This adapter requests legacy history so resume/read can hydrate turns without a pagination implementation.

Codex 0.159 stores the client identity on `item.client_id` for completed user items. The watcher checks it as well as the envelope identity, suppressing an own receipt only when its digest agrees and the two identity fields do not conflict. ## Amendment: refresh changed MCP configuration before a turn (October 5, 2026)

Codex desktop can change its native computer-use pipe when it restarts, writing the new path in the global `config.toml`. An already loaded thread's app-server retains the earlier MCP configuration. Starting another turn on that process can then fail to reach the running desktop.

Before a new prompt is recorded or sent, Sotto compares the global config file's metadata with the metadata captured before that thread's app-server started. A change sends `config/mcpServer/reload` to that app-server and waits for its acknowledgement. This API has no params and returns an empty object in Codex 0.160.0's generated protocol. Sotto records the new metadata only after success. It reads no config body, logs no path or value, starts no watcher and changes no permission mode.

This check also precedes a steering prompt within an active turn. Codex 0.160.0 refreshes dirty MCP state before preparing subsequent tool calls; it need not end the turn first. Sotto keeps its existing steering validation after the awaited refresh, so a turn that ended or changed meanwhile cannot receive a stale steering prompt. A tool call already executing is not restarted or replayed.

Each thread's app-server owns its comparison and any pending refresh. Other threads keep their turns and request channels. A failed refresh leaves the prompt unsent and retryable, including a lost acknowledgement: uncertainty about a tool refresh is not uncertainty about prompt delivery. Sotto neither repeats a prompt nor retries a computer-use action. JSON-RPC method-not-found, or an invalid request naming this method as an unknown variant, disables automatic refresh for that process; older clients can still send ordinary prompts. A fresh app-server checks support again.

File metadata is a change signal, not a parser or a promise that every config edit changed MCP settings. An unrelated global config edit may cause one reload. Project config files are outside this check. See [the verification note](../verification/codex-computer-use-refresh.md) for the regression and live evidence.

The metadata probe is best effort. A missing file is a known state; another stat failure leaves the change signal unavailable and does not block runtime creation, a send or steering. The last successful metadata remains intact, so a later successful probe can still detect a change. This differs from a reload request that fails after a change was detected: that failure keeps the prompt unsent and retryable.

## Amendment: one read before a send (October 5, 2026, #765)

A send from the Threads page read its thread four or five times. The coordinator read it before the send, and so did the checkpoint hook. The adapter read it at the start of the send; Claude did that twice, building a whole snapshot each time and throwing it away. The adapter read it again just before the prompt went out. When the echo had not yet been published, the coordinator read it whole after the provider accepted. Grok also read every watched thread whenever the coordinator said which threads were on screen, which it does before every send, and the send waited behind that read. Every read through the workspace wrote `workspace.json` and published, whether or not it found anything.

**The read before a send stands for the adapter's first read.** The coordinator still reads the thread with `{ beforeSend: true }` immediately before it dispatches. The send is still written against what that read shows (`expectedLastUserMessageId`), so a turn another Codex process took back still lets the send go, as a whole read always did. The read now also names the message ID of the send it is for (`sendMessageId`). The adapter remembers that ID with how far the thread had moved (`readsBeforeSend.ts`):

- Codex, by its revision of the thread. Every notification that changes the thread's turns, items or requests moves it, and so does an entry in the session log. Settings and token-usage notifications do not.
- Claude, by the number of messages it holds for the thread.
- Grok, by how far it has read the thread's history.

Only the send with that message ID skips its first read, and only when the thread has not moved. The next command on the thread clears what was remembered, whatever the command is. So a send refused after the read leaves nothing for the next one. A queued follow-up is read the same way: since #764 the coordinator reads before dispatching one, naming its message, so it skips the adapter's read like any other send. A personal-chat send's own read before it resumes the chat's instructions names the send the same way. A Codex send therefore makes the newest-turn check once, in the coordinator's read, and again only when the thread moved after it.

**The recheck stays where the send can yield.** Between the read before the send and the prompt going out, the coordinator writes its outbox. The adapter saves the message's origin, starts or resumes the session and reads staged images. Someone can type into the session in that time. Claude and Grok still read what is new in the transcript or history once the origin is saved, just before the prompt goes out, the recheck (`CONTEXT.md`), and refuse a reply to an old last message there. Codex still polls its session log before `turn/start` and checks the same. On the success path Codex makes one read of the thread's history. Claude and Grok make two before the prompt, the read before the send and the recheck, and Grok reads its echo once after it.

What got weaker is the newest-turn check nearest `turn/start`. Since #764 that includes queued follow-ups, which the coordinator now reads for too. A turn another Codex process takes back is not seen if it happens after the coordinator's read and before `turn/start`. That was already true between the adapter's own check and `turn/start`. The window is now longer by everything between the coordinator's read and the adapter: the coordinator's outbox write, and in the desktop app the workspace's wait for the checkout, a reload of the skills catalog when skills are attached, the read of the thread's folder and branch, and the checkpoint hook. #762 measured Sotto's work before Codex hears a prompt at a median of 2.7 s and a p90 of 6.5 s, and this span is part of it, so the window can be seconds rather than milliseconds until #766 shortens it. #764 removed the checkpoint hook's read of the thread; its capture still runs in this window. Input typed in that window is still refused, by the session-log poll. This is accepted as the cost of one check per send; the issue asked for the check once "without weakening ADR-0005's follow-up", and this is the one way it does. It is the owner's to confirm.

A covered Codex send still waits for any read of the thread already in flight, as its own read would have queued behind it, so no read applies the thread across `turn/start`. When that read failed, or the thread moved while the send waited, the send reads for itself after all. So a thread Codex cannot read is refused with "Codex history could not be verified", as it was before.

**Claude and Grok honour the purpose.** Their read is split into bringing the thread up to date (`sync`: start the session when it has none, read what is new) and building the snapshot, which only `refreshThread` does. Codex's is split the same way. A Grok history read that found nothing new and moved no status publishes nothing. Grok reads a thread when it enters the watched set or has not been read on this connection, and leaves one that stays in the set to its poll.

**A read before a send that changed nothing writes and publishes nothing.** The provider switch publishes the read only when what the provider handed back differs from what it held. The workspace writes and publishes only when the read changed its state. Both compare structurally (`sameSnapshot.ts`). The frozen activity records an adapter hands back unchanged, and the message window the workspace keeps, make that a walk over small objects. Any other read writes and publishes as before.

**The read after an accepted send uses the echo already held.** A provider's echo of the sent message reaches the workspace as an event and can wait there for the end of its publish window. The coordinator now asks with `{ afterSend: true }`. The workspace answers that from what it holds without asking the provider, and the coordinator reads the thread whole only when the echo is not there. In a stack with no workspace, which tests compose, the Sotto thread host answers it from the adapter's snapshot instead. That read used to be the one that took Claude's transcript past a first send's echo. Claude records how far it has read its transcript only when a read reaches it, so a host stopped right after a first send had no record and read the transcript from its first byte when it started again, adding the prompt a second time. A Claude thread with no record now starts from what the history store holds, so the read from the first byte adds only what the store does not have.

The checkpoint hook's own read before a send was #764's, and #764 removed it. Devin's reads are #770's; `devin.ts` is unchanged, though a Devin read through the workspace benefits from the last two paragraphs like any other. [ADR-0007](0007-native-thread-retirement-and-refresh.md) points here, since its send validation and confirmation reads are the ones that changed. Measured in `docs/perf/2026-10-05-one-read-per-send.md`.

## Amendment: fewer writes before a send and between frames (October 6, 2026)

Issue #767. A send rewrote whole stores in series before the provider heard it, and Codex held every frame carrying a turn or a message behind a rewrite of `codex-threads.json`. What each guarantee needs is now written, and nothing else in front of the prompt. The coordinator's half, one write of `agents.json` per send, is [ADR-0056](0056-a-prompt-sent-at-once-is-saved-by-its-outbox-write.md).

- **An origin is still durable before the prompt is written.** Codex keeps writing its origin into `codex-threads.json` before `turn/start`, as above. Claude Code records a new origin as one synced line of `claude-origins.jsonl` beside `claude-threads.json` rather than rewriting every thread's record for it. Each time the adapter writes `claude-threads.json` whole it clears that journal, whose origins the write then holds, and it reads the journal back over the store when it connects and folds it in. The journal and the store are written in one order, so a clear never removes a line the store does not hold, and any journal is cleared on connect, so a line a crash cut short is always the last. Such a line belongs to a prompt that was never written, and is skipped. A clear that fails leaves a journal whose origins the store already holds, which is harmless, so the write it follows still counts as saved. An append whose sync fails after its line was written can leave an origin for a prompt the adapter then refuses to send; that is a record no echo ever matches, never a sent prompt without one.
- **Codex shows a frame's effect before it saves it.** A frame's message, turn or identity reaches the thread first; the save of `codex-threads.json` behind it is not waited for, and saves made while one is running share the next write. The responses to `turn/start` and `turn/steer` start their save in the frame queue too, and the send waits for it outside the queue, so the reply's frames behind the acknowledgement are not held; a failed save leaves that send uncertain, as a response that could not be applied does. What a crash between them can lose is identities the next read derives again: a reply's from its native item ID, a prompt's from its origin, which was saved before `turn/start`. A save that fails no longer stops the app-server; the next one carries the same state, and the next send's origin write, which a send does wait for, fails the send if the disk is still refusing.
- **The stores rewritten whole around a send and while a reply streams are written without indentation.** `claude-threads.json`, `codex-threads.json` (1.3 MB indented on the development machine, about 0.86 MB compact) and each provider's usage ledger are compact JSON, as `agents.json` is (ADR-0056). Every reader parses either form, so a file an older version wrote reads as before. A person reading one needs a JSON formatter.
- **The usage ledger is written at most once a second while a reply streams**, and at once when a turn ends or a compaction is recorded. It is serialized as the write starts rather than copied whole first.
