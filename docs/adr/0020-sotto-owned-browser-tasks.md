# Sotto owns browser tasks and their page access

Accepted for implementation September 21, 2026, following Zach's approval of the shared browser workflow and corner-preview variant A. Browser pages remain in the Tools pane; a task's corner preview shows the same page and opens it there without changing the user's conversation. Sotto owns page and browser-task identity across providers, using Sotto thread IDs and the thread's current working copy.

Agents receive a bounded browser tool interface. Supported providers receive a Sotto-owned authenticated loopback MCP endpoint bound to one thread. Native discovery is verified for Codex, Claude Code and Grok. The pinned Devin client ignores the supplied ACP MCP server, including during a bounded native turn, so Devin receives no browser tools or credentials. Codex uses per-thread MCP configuration because the installed native resume protocol cannot add dynamic tools to existing threads. The endpoint is local to this computer, rejects browser-origin requests, and exposes no renderer bridge, filesystem API, general debugger command, or permission-answer method. Provider adapters translate their own identifiers before calling it. No global provider configuration is changed and no new production dependency is added.

A page opened by the user is not automatically visible to an agent. The user may share observation of that page and revoke it. Opening a page through an agent, navigation, clicks and typing require an exact one-time answer from the user; agents and supervision cannot answer those requests. Approval is tied to the thread, task, page state and action and is invalidated when that context changes. A browser call waits up to five minutes for the user answer and returns the executed result to the same provider turn. Pause, revocation, closure and expiry unblock the wait without approval. This follows ADR-0004's one-time user answer; there is no stored automatic grant or inferred authority from the transcript. Pausing stops later browser actions, while dismissing a thumbnail only hides it.

Screenshots, selected-element context, bounded diagnostics and verification steps are transient task evidence held in memory. They are not operational logs. Browser responses go only to the provider of the requesting thread; page selection becomes a user-editable draft attachment and is not sent until the user submits it. Network diagnostics exclude headers, request bodies, response bodies and cookie values. Existing optional draft/history retention applies to material the user explicitly attaches and sends; provider-side retention is separate. Browser tasks and page grants do not survive an app restart.

ADR-0017 remains unchanged: Devin receives no injected browser endpoint. The installed ACP client did not discover the supplied server. Its main-config alternative migrates MCP configuration into separate native files, so it cannot establish isolated per-thread access without changing native configuration outside this scope. A future native protocol must pass discovery and actual call verification before adding Devin support. Imported native MCP servers, plugins, hooks and project configuration remain refused. A fixture test alone is not evidence of native CLI compatibility. See the implementation verification note for the actual checked providers and platforms.
On Windows, a detached or fully occluded native page has no capture surface. Real Electron experiments established that the same normal WebContentsView can render in a temporary, unfocusable, taskbar-hidden BaseWindow placed outside the display bounds when Chromium's CalculateNativeWinOcclusion feature is disabled before app readiness. Sotto uses this capture host only while a hidden page is being captured, returns the same view to Tools if it opens during the capture, and destroys the host afterwards. Captures have a bounded failure deadline. The Windows startup switch preserves existing disabled features. This disables Chromium's Windows occlusion optimization for the app; normal background throttling remains enabled outside captures. It is a rendering reliability tradeoff, not a second page, session, or browser process. Other platforms do not receive the Windows feature switch and require separate native verification.
