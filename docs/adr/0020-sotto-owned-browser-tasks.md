# Sotto owns browser tasks and their page access

Accepted for implementation September 21, 2026, following Zach's approval of the shared browser workflow and corner-preview variant A. Browser pages remain in the Tools pane; a task's corner preview shows the same page and opens it there without changing the user's conversation. Sotto owns page and browser-task identity across providers, using Sotto thread IDs and the thread's current working copy.

Agents receive a bounded browser tool interface. Supported providers receive a Sotto-owned authenticated loopback MCP endpoint bound to one thread. Native discovery is verified for Codex, Claude Code and Grok. The pinned Devin client ignores the supplied ACP MCP server, including during a bounded native turn, so Devin receives no browser tools or credentials. Codex uses per-thread MCP configuration because the installed native resume protocol cannot add dynamic tools to existing threads. The endpoint is local to this computer, rejects browser-origin requests, and exposes no renderer bridge, filesystem API, general debugger command, or permission-answer method. Provider adapters translate their own identifiers before calling it. No global provider configuration is changed and no new production dependency is added.

A page opened by the user is not automatically visible to an agent. The user may share observation of that page and revoke it. Opening a page through an agent, navigation, clicks and typing require an exact one-time answer from the user; agents and supervision cannot answer those requests. Approval is tied to the thread, task, page state and action and is invalidated when that context changes. A browser call waits up to five minutes for the user answer and returns the executed result to the same provider turn. Pause, revocation, closure and expiry unblock the wait without approval. This follows ADR-0004's one-time user answer; there is no stored automatic grant or inferred authority from the transcript. Pausing stops later browser actions, while dismissing a thumbnail only hides it.

Screenshots, selected-element context, bounded diagnostics and verification steps are transient task evidence held in memory. They are not operational logs. Browser responses go only to the provider of the requesting thread; page selection becomes a user-editable draft attachment and is not sent until the user submits it. Network diagnostics exclude headers, request bodies, response bodies and cookie values. Existing optional draft/history retention applies to material the user explicitly attaches and sends; provider-side retention is separate. Browser tasks and page grants do not survive an app restart.

ADR-0017 remains unchanged: Devin receives no injected browser endpoint. The installed ACP client did not discover the supplied server. Its main-config alternative migrates MCP configuration into separate native files, so it cannot establish isolated per-thread access without changing native configuration outside this scope. A future native protocol must pass discovery and actual call verification before adding Devin support. Imported native MCP servers, plugins, hooks and project configuration remain refused. A fixture test alone is not evidence of native CLI compatibility. See the implementation verification note for the actual checked providers and platforms.
On Windows, a detached or fully occluded native page has no capture surface. Real Electron experiments established that the same normal WebContentsView can render in a temporary, unfocusable, taskbar-hidden BaseWindow placed outside the display bounds when Chromium's CalculateNativeWinOcclusion feature is disabled before app readiness. Sotto uses this capture host only while a hidden page is being captured, returns the same view to Tools if it opens during the capture, and destroys the host afterwards. Captures have a bounded failure deadline. The Windows startup switch preserves existing disabled features. This disables Chromium's Windows occlusion optimization for the app; normal background throttling remains enabled outside captures. It is a rendering reliability tradeoff, not a second page, session, or browser process. Other platforms do not receive the Windows feature switch and require separate native verification.

Amended September 21, 2026. Sotto's own browser tools carry no native provider prompt on Claude Code. The native CLI treats a tool reached through `--mcp-config` as untrusted and asks before every call; Sotto rendered that request as the raw tool name and its JSON arguments, naming neither the browser nor Tools, so a thread left in the default permission mode saw an unreadable question and the agent was refused. That prompt was never this decision's gate. Authority stays where this ADR put it: opening a page, navigating, clicking and typing wait for the user's one-time answer in Tools, against the actual page and action, and admission to the endpoint remains separate from permission to operate a page. Claude Code is therefore launched with `--allowedTools` naming exactly the tools that thread's browser endpoint exposes, so reaching the endpoint no longer asks a second, less informative question. The flag names those tools and no others, the endpoint still binds one thread, and a revoked credential still closes it. That the flag admits nothing beyond them is read from what Sotto passes rather than observed: the native probe registers one synthetic tool, so the real names are covered by fixture alone. The other two clients reach the same place by their own mechanism, each scoped to this server and nothing else. Codex takes `default_tools_approval_mode = "auto"` on the `sotto_browser` entry Sotto already writes into that thread's own configuration; no global Codex configuration is touched. Grok is spawned with `--allow 'MCPTool(sotto_browser__*)'`, a rule on Sotto's own process rather than in Grok's configuration file. Neither is proven by a fixture, because a fixture replaces the client. Both were checked against the installed clients only far enough to show the launch and tool discovery still succeed; that the prompt is gone needs a model turn against a paid client and is recorded as unchecked. Grok carries the larger doubt: it runs in leader mode, where its `--allow` rules are reported upstream not to apply, so the rule may be accepted and ignored.

Amended September 22, 2026 (#232). Opening pages may now be answered for a whole thread. Zach picked this after answering the same open request again and again during one check: every new task asked once more, and the corner preview came back with it. A request to open a page, or to go to another page on one of the thread's pages, offers a second answer beside Allow once: **Allow this thread to open pages**. It opens this page and records a page-opening grant for that Sotto thread. While the grant lives, that thread's opens and navigations run without asking, and a page it opens is shared exactly as Open and share shares it: the same origin rule, and the same revocation when a navigation leaves that origin. Nothing else changes. Clicks and typing still wait for the exact one-time answer every time, the grant never makes a page the user opened observable, and it cannot be offered on any request but an open or a navigation. The grant is a record shaped like ADR-0004's policy records (action, resource, scope, effect, source, granted, expiry and revocation times) held in the browser service's memory, not in `memory.sqlite`, because this decision already has browser grants end with the app session. Only the user's answer in Tools creates one; the agent endpoint has no way to ask for or give it, and supervision, memory, repetition and a provider's own confirmation never do. It shows in Tools > Browser with a Stop control, and it ends at Stop, when Sotto no longer lists the thread, when the browser service shuts down with its window, and when the app quits. Settling a thread does not end it, because settling keeps the thread's work running. The same day the corner preview became the focused thread's (or the pinned Tools thread's) rather than the newest from any thread, and **Show browser previews** in Settings can turn previews off; browser work and Tools > Browser are unchanged by it. Because a preview may be off or showing another thread, a waiting request lights the dot on the Tools icon of the pane showing its thread, beside the working-agents meaning that dot already had, and its page tab in Tools > Browser. A request from a thread with no open pane has no mark outside Tools > Browser and can expire unseen; the thread list's waiting mark does not count browser requests.
