# Watcher coordinates threads with its provider's own tools

Accepted October 9, 2026. Zach chose this shape on October 9 after [the first Windows live checks](../verification/2026-10-09-command-center-live-windows.md) and [the Codex benchmark](../perf/2026-10-09-command-center-codex-benchmark.md). It replaces this ADR's isolated read-only design. The A2 room, phone scope and provider-change continuity chosen on October 8 remain, following [ADR-0068](0068-remove-voice-control-and-thread-management.md) and [the plan](../plans/2026-10-08-command-center.md).

Sotto has one current **Watcher** on this computer, identified by main's durable local host and Sotto thread IDs, special thread kind, project and creation operation. Titles, tool arguments, prompts, phones and host commands cannot select it. The stat-signature cache and failure isolation keep ordinary threads independent of a missing or corrupt Watcher record. Retired conversations remain readable history and refuse resume. Creation retains ADR-0002's immutable bindings and flush-before-dispatch rule.

## Provider tools and pinned permissions

Watcher is a native thread launched as an ordinary thread of its provider, on the user's account, with native tools, settings, instructions, skills, plugins, hooks and user-configured tool servers. It uses no second key or OpenRouter reasoning account. Its neutral Sotto-owned folder is separate from registered projects; it can read and search anything the provider can normally read. There is no Sotto project-file broker or promise of project containment or secret filtering. Paired hosts get workers, not another Watcher.

Its native permission mode is pinned to asking before changes. Main and each adapter refuse changes that widen that mode, in plain words; model and effort changes remain allowed. Native one-time approvals remain available; remembered session/always grants are refused because they widen future permission. Working-copy changes remain refused. Watcher's own edit, writing-command and network permission requests are ordinary request cards. They do not stop or revoke its scoped server, and the user alone answers them.

`watcherPrompt.ts` says: you are Sotto's Watcher; coordinate the user's threads through `sotto_threads`; start or brief threads rather than editing or running things yourself; read and search as needed; never answer a thread's question or permission; say what you sent and to which thread. This is guidance, not enforcement. A model can ignore it or a user can ask for native work. Enforcement comes from the pinned native permission mode, durable tool scope, and the absence of any answering or permission-changing Sotto tool.

These are native permission modes, not isolation from inherited customization or servers. Existing native allow/deny rules and server permissions still participate. Codex's read-only sandbox constrains native execution, not an inherited MCP server running outside that sandbox; Claude and Grok's asking modes are not OS read-only sandboxes. Native authentication and provider-owned session/cache writes continue. Keep local history governs Sotto's stores, not the provider's persistence. We do not claim an asking mode can undo the user's existing provider permissions or prevent an administrator's startup hook from running.

## Windows Codex launch probe (October 9, 2026)

The lead diagnosed the first live failure: the user's elevated Windows sandbox requires one-time setup that fails on this computer. With command-line overrides selecting unelevated and read-only, the lead observed a successful PowerShell file read; project and Temp writes denied with UnauthorizedAccessException and no changed files; and curl exiting 7 while the same outside request returned 200. These are the lead's reported checks, not a claim that every network path is isolated. PowerShell runs in Constrained Language mode. OpenAI describes [unelevated as a fallback with weaker network isolation](https://learn.chatgpt.com/docs/windows/windows-sandbox#configure-a-legacy-fallback).

Before the first model turn on each Windows Watcher app-server, Sotto runs two zero-model-turn `command/exec` calls through that same server with an explicit read-only policy. It creates an owned synthetic probe folder in the thread's project, checks a `Get-Content` read against its marker, then attempts `Set-Content` to a separate probe file. Successful reads, an explicit permission-denied write result, and an absent output file are all required. Set-Content works in Constrained Language mode; a forbidden .NET method would not prove filesystem enforcement. Because app-server converts an uncaught sandbox denial into an RPC error, the PowerShell probe catches only UnauthorizedAccessException with the OS E_ACCESSDENIED HRESULT and emits a fixed denial marker. The cmdlet category varies between creating a file and opening an existing one, so it is not the enforcement check. Any other result refuses launch. Sotto removes only its known probe files and folder.

A failed, malformed, timed-out or inconclusive probe ends that app-server before it can receive a turn, with a plain refusal saying the read-only sandbox is not working and nothing was sent. The check runs again on early start, cold resume, settings/model replacement and a replacement client process; resident reuse needs no repeated probe. The override and probe never read or change the user's saved provider configuration or credentials. Fakes cover both working enforcement and refusal, including a successful write and an unrelated command failure. macOS uses its existing native policy and remains outside this Windows proof.

## Sotto's scoped servers

Only main's current identity gets the frozen `sotto_threads` server and its exact contract tool names. Codex uses per-tool `approval_mode=approve` with a prompt default; Claude uses exact `mcp__sotto_threads__<name>` allowances; Grok's scoped admission compares exact offered server/tool names. Preallowance admits a call to Sotto's boundary, never authority over a worker. Ticket 3 supplies the real server; the live suite uses a stand-in with the same scoped attachment.

Attach `sotto_visual` and `sotto_pull_requests` as ordinary threads get them. Exclude Sotto's browser and host-setup servers from both offered servers and scoped admission. ADR-0029's automatic browser actions would exceed this shape. User-configured provider servers remain inherited.

## Proof and replacement of the old profile

Remove the admitted-combination list, version/platform gates, restricted flags and startup inventories, inherited-Codex-server discovery/disabling, Claude managed-policy and plugin/agent checks, Grok isolated home/ToolConfig, and permission-triggered shutdown. Remove the isolation live suite and benchmark harness; their dated notes and evidence remain historical records.

Fakes cover native tools/settings, exact scoped admission, all launch/resume/settings/replacement routes, ordinary request cards, permission-widening refusal and unchanged ordinary contracts. The opt-in `SOTTO_WATCHER_LIVE=1` suite selects one provider, never runs in CI, and uses at most four turns in a disposable project: scoped tool, native read/search, edit card interrupted without answering and unchanged sentinel, then scoped tool after cold resume. Windows additionally requires the same-app-server launch probe before any turn, and checks an unasked native write without a model turn. A successful unasked write stops the check; a sandbox setup failure leaves enforcement unproved. [The own-tools Windows note](../verification/2026-10-09-command-center-own-tools-windows.md) records actual results. macOS requires separate proof; a Windows result says nothing about it. No source admission list survives this decision.

This explicitly amends [ADR-0004](0004-authority-in-policy-records.md) and [ADR-0005](0005-codex-app-server-adapter.md) for bounded Watcher start/send authority. An actual top-level user Send to the current master creates a main-owned **Watcher request**, rooted in that user's message. Main admits start, send now, queue, steer, targeted stop and settle through the existing coordinator lanes, outbox and delivery receipts. Workers start at no wider than the user's effective new-thread default; an explicit narrower choice is allowed only when comparable. Existing workers whose permissions exceed or cannot be compared with that ceiling are refused. Main enforces a computer-wide limit of four distinct automated targets by default (setting 1–8), including reserved, queued, uncertain and waiting targets, and four total prompts per target per request. Retries, wake-ups, compaction, restart and model changes renew neither budget. Lowering capacity stops nothing and holds new admission until usage falls.

The human-only answer rules of those ADRs and ADR-0068 stay in force. No Watcher tool answers a question, approves a permission, changes policy or widens a worker's permissions. Native preallowance admits only a call to Sotto's scoped server; it grants no worker authority. Worker requests are answered on the worker's own request card. Watcher's own native question and permission requests use its normal request cards; only the user answers them. A request does not retire Watcher or revoke its tools. Main can enforce scope, identity, budgets and fences; it cannot prove that a generated brief faithfully interprets natural language. The original request reference and visible actions remain available to the user.

Direct user instructions or controls on a participating worker, including native and phone input, relinquish participation before dispatch. Main increments ownership generation and fences subsequent machine deliveries, retaining the user's drafts, queue and new turn. Opening, reading and answering an existing request card are not takeover. V1 offers the model no resume-ownership tool. User-only **Stop all** asks first, then stops only still-eligible threads Watcher started; it excludes the master, user-started and taken-over threads and unrelated provider subagents. A targeted stop records its action under the user's active request and may address an existing ordinary thread. Closed/stopped requests cannot be revived by a tool or restored history.

Main wakes the master from observed participant and delivery changes, in bounded event batches, rather than model polling. [ADR-0061](0061-a-thread-can-babysit-its-pull-request.md)'s existing wake-up/queue path carries this distinct source of news without changing independent babysitting. Evidence carries source, observation time, identity, freshness and availability; a worker's claim is separate. Overview is a projection of all other threads, not a second attention store. Its precedence is Needs you, verified Landing, another open pull request, Quiet after twenty minutes of freshly observed active work without progress, Working, then Idle; display order is Needs you, Ready for review, Working, Landing, Quiet, Idle. Disconnection supplies stale/unavailable evidence, never an inferred failure or quiet turn. Landing is observed action/merge evidence and grants no permission.

`agents.json` names its record `watcher`; current and earlier thread kinds are `watcher` and `watcher-history`, and the capacity setting is `watcherInFlightLimit`. These names are set before the first preview persists this branch’s records, so there is no migration from the working names. Stores predating this branch still receive an empty Watcher record and ordinary `project` thread kinds.

`agents.json` keeps only versioned identities, requests, operation/retry/digest references, worker ownership generations, counters, reservations, takeover reasons/times, receipt links and read/wake positions. Tokens remain in memory. [ADR-0016](0016-sotto-owned-history-on-an-event-store.md)'s normal history-aware store holds messages and future cards; history off keeps Watcher words and file contents only in memory, including queues, drafts and evidence payloads. No prompt, file content, bearer token, tool argument, protocol body or error prose enters control metadata, logs or backups. After restart unavailable text is reported unavailable; uncertain delivery is reconciled, never replayed.

Paired-host automation requires the optional `watcher-control` and `watcher-reads` features with closed machine-origin operations and owning-host enforcement. Ordinary privileged desktop commands are no fallback, and generic socket/phone clients cannot forge that origin or acquire remote-answer authority. Host protocol remains v1; unsupported hosts retain readable existing summaries and refuse automation. In v1 current and retired Watcher conversations are hidden from phones, including old clients through host-side projection and targeted-command filtering; ordinary workers keep their existing phone journeys on their owning host. The desktop's aggregate roster is not a phone host feature.

Changing provider waits for no in-flight master turn, invocation or unresolved delivery, then creates a replacement native conversation with a new Sotto ID. The previous conversation becomes readable Watcher history according to history settings, its tools are revoked, and the current reference changes atomically. A bounded visible handover is offered through the replacement's send path only after the user chooses to continue. Worker ownership and receipts survive; the handover revives no stopped or taken-over request. This preserves ADR-0002 rather than rebinding one conversation across providers.
