## Standing watching (October 13, 2026)

A standing watch records a user's durable assignment of any ordinary thread to Watcher. Watcher can also use `watch_thread` and `unwatch_thread` when instructed to watch threads. The watch stays the user's to give: `watch_thread` is refused unless the Watcher turn answers the user's own message, the root or a continuation of an active request the user started; a wake-up, a standing scope or Watcher's own initiative grants no watch. Sends under a watch the user gave need no further asking. Establishing a watch sends no prompt; it survives request closure and restart until Stop watching. Watcher gets observed finished, question, permission, failure, quiet, Git/PR/check news and manages the thread on its judgment, pinging the user only for a card that needs him. It still answers no card. Watching has no count cap; the in-flight cap remains on new starts.

A direct desktop, phone or native user instruction fences old automatic deliveries and pauses new Watcher sends to that thread until the user's turn ends. It does not remove its standing watch. A fresh bounded continuation request can be linked to the standing watch and the current Watcher turn; each target retains four prompts within that turn, retries do not reset that count and a stopped/closed request never becomes active again. Opening and answering remain distinct from takeover. Stop watching invalidates news and fences queued automation, preserving the user's own work.

A thread is watched when it is under a standing watch or takes part in an active request of the current Watcher (or of a paired master, on the host that owns the thread) that the user has not taken over and Watcher has not stopped. Main marks each projection row `watched` with that one answer (`isWatchedRow` in `src/shared/watcherRoom.ts`), and the room, the Threads page, the phone page and the phone shell's owl all read the mark rather than deciding for themselves. A thread watched only through a request, as on an older paired host, is taken over by a direct instruction and stops being watched.

Paired hosts require the additional optional host-v1 `watcher-standing-watch` feature. The owning host records assignments attributed to its authenticated SSH-recorded desktop/master, detects its local user turns and publishes the authoritative generation/pause state. Withdrawing an assignment retains a text-free fence so late synchronization cannot reinstall it. A retained latest master-creation frontier also fences retired conversations after empty synchronization. Older hosts refuse standing-watch automation. Paired phones negotiate optional `watcher-phone-manage` alongside `watcher-phone`; mutations are connection-guarded and exact retries return the original outcome with fresh state. Watching and returning to Ask for approval need pairing; choosing a mode that lets Watcher act without asking requires the phone's current Can answer policy at admission and the writer. Neither management feature grants card-answer authority. Stable desktops offer and start none of this and retain saved records whole.

## Historical Windows Codex launch probe (October 9, superseded October 13, 2026)

The lead diagnosed the first live failure: the user's elevated Windows sandbox requires one-time setup that fails on this computer. With command-line overrides selecting unelevated and read-only, the lead observed a successful PowerShell file read; project and Temp writes denied with UnauthorizedAccessException and no changed files; and curl exiting 7 while the same outside request returned 200. These are the lead's reported checks, not a claim that every network path is isolated. PowerShell runs in Constrained Language mode. OpenAI describes [unelevated as a fallback with weaker network isolation](https://learn.chatgpt.com/docs/windows/windows-sandbox#configure-a-legacy-fallback).

Before the first model turn on each Windows Watcher app-server, Sotto runs two zero-model-turn `command/exec` calls through that same server with an explicit read-only policy. It creates an owned synthetic probe folder in the thread's project, checks a `Get-Content` read against its marker, then attempts `Set-Content` to a separate probe file. Successful reads, an explicit permission-denied write result, and an absent output file are all required. Set-Content works in Constrained Language mode; a forbidden .NET method would not prove filesystem enforcement. Because app-server converts an uncaught sandbox denial into an RPC error, the PowerShell probe catches only UnauthorizedAccessException with the OS E_ACCESSDENIED HRESULT and emits a fixed denial marker. The cmdlet category varies between creating a file and opening an existing one, so it is not the enforcement check. Any other result refuses launch. Sotto removes only its known probe files and folder.

A failed, malformed, timed-out or inconclusive probe ends that app-server before it can receive a turn, with a plain refusal saying the read-only sandbox is not working and nothing was sent. The check runs again on early start, cold resume, settings/model replacement and a replacement client process; resident reuse needs no repeated probe. The override and probe never read or change the user's saved provider configuration or credentials. Fakes cover both working enforcement and refusal, including a successful write and an unrelated command failure. macOS uses its existing native policy and remains outside this Windows proof.

GitHub state, checks, current review decision and auto-merge are separate evidence facts for one URL and head, each retaining its own observation time and freshness. A reader updates only what it observed; carrying known checks through an unrequested read retains their original time. Explicit false values revoke approval/auto-merge facts, and a newer head clears earlier-head facts. Late older-head or older-field reads cannot restore superseded evidence.

Restart reconciliation uses the waiting queue's text-free evidence references while source observations are incomplete. An unobserved fact is unknown and cannot withdraw that waiting news; newly observed changes, explicit removals and ownership fences still invalidate it. Checkpoint initialization republishes the newest retained ready/unavailable capture for each thread once, through the gated observer, so saved captures repopulate evidence without polling or restoring prose.

The bounded source cache retains up to three hundred facts per target, enough for fifty linked PRs with independent facts. The existing evidence projection remains at one hundred entries, favoring recent actual changes. Clock-only refreshes update observation times without moving facts through that projection, so its limit cannot turn unchanged background reads into news.

Recovery compares actual source changes against the bounded cache, so projection omissions are not removals. First materialization remains unknown until the saved occurrence is reconciled; explicit new/removed PR associations and changed already-observed facts still supersede it. Before the newest checkpoint is published, retained captures are offered to the private restorer; only a capture referenced by the waiting occurrence seeds its comparison. This lets a newer saved capture supersede older waiting news without replaying unrelated historical captures.

Recovery and dispatch checks retain prompt charges from stopped/closed legacy scopes. Only an exact authored echo, accepted Send or possibly-written uncertainty opens another budget; saving a failed intent grants none. Owning-host withdrawal is checked inside admission and again at the writer. Own-change marks span same-turn steers under exact native/Sotto turn anchors, and transcript replay cannot move an already-observed file tool into a later steer.

## October 14, 2026: what wakes Watcher

On October 14, 2026 Zach watched four threads and found Watcher woken by almost every tool call in them. Most of the news said "Sotto observed changed evidence", because a worker's working copy and Git status change while it works, or "Sotto observed a new delivery receipt", for Watcher's own sends going through. He and the lead agreed that Watcher wakes only for what needs its attention. This amends ticket 4's event news (October 11); batching, the quiet rule, held news through restarts and babysitting's own wake-ups are unchanged.

- **Wakes Watcher:** a watched thread's turn finished or failed, a question or permission card appeared, the thread went quiet (twenty minutes, as before), a pull request's link, state, checks, review or auto-merge changed, the user took the thread over, and a receipt for one of Watcher's own sends that failed, was refused or may not have gone (failed, uncertain, or accepted with a refusal or uncertain thread creation).
- **Rides with a turn's end:** the thread's own facts, its working copy, Git status and checkpoints. A change to them never starts a wake-up. It joins a turn end not yet told, or keeps evidence news still waiting to go current. News already in Watcher's wake-up is never changed (October 15, round 6): if its evidence moved on before it went, the wake-up is withdrawn and that evidence is told again as it stands. Any other change waits for the thread's next turn end, which tells it only if the thread's own facts differ from what Watcher was last told. A change made while a thread rests is told with its next turn's end.
- **Never wakes Watcher:** an ordinary delivered or accepted receipt. Watcher made that send and reads its receipts with read_operation when it wants them. Such a receipt still waiting from an earlier build is withdrawn.

What Watcher was last told of a thread's own facts is kept in memory. After a restart, the first turn end may tell them again, inside the wake-up that turn end causes anyway.

## October 14, 2026: work settled

Turn-finished news fires once per turn and carries a background work count, but its identity is the turn and its status, so when the work a finished turn left running ended, Watcher heard nothing (#1024). T3 keeps a task open while a child waits on its own children; Sotto now says when that wait is over.

News gains one kind, **work-settled**: once per turn, when the work a finished or failed turn left running reaches zero. That work is the thread's provider-confirmed background work (Claude's background tasks), the working sub-agents in its roster (Codex's `subAgentActivity`) and its monitoring. Claude's background sub-agents appear in both of the first two, so the count takes the larger of those, plus monitoring; turn-finished and turn-failed news carry the same count, so a Codex turn whose sub-agents are still working no longer reads as done. A turn that finished with none gets no work-settled news. Like all Watcher news it carries identities and counts only, rides the same batch and wake-up path, and grants nothing. Quiet's rule is unchanged: it still reads background work and monitoring only.

Unknown is not zero. A restart cannot see how sub-agents that were running ended, so the roster holds them as unknown; while any are unknown, the turn stays unsettled and its news waits until the provider says how they ended. They count with the working ones in a finish's work count, so a turn that finishes while they are unknown reads as not done and is owed work-settled news like any busy finish. The news is due only while its turn is the thread's newest finished turn and its work is still zero and known. Work that starts again before delivery withdraws it, and the turn is owed it again, so it comes once, after the work truly reaches zero. A new turn replaces it.

It survives restart without repeating. A finish observed with work still running carries a second digest in its event ID, the work-settled scope (request, thread, generation and turn), so the saved or still-queued ID alone tells a restarted Watcher which turn is owed one; the work-settled ID itself is saved like any other and deduplicates the rest. Only a finish delivered as busy is owed one: a finish first observed with nothing running stays done, and work seen on that turn later brings no work-settled news. Paired hosts list an optional host-v1 feature, `watcher-work-settled`, offered under the same recorded desktop origin as `watcher-reads`: their thread projection carries background work, monitoring and the sub-agent summary. A host that does not list it reads as unknown, not as none running. Its finished turns carry no work count, and its threads get no work-settled news; Watcher learns a turn finished there and nothing about the work it left. No phone or host decoder reads news kinds.

`watcherPrompt.ts` tells Watcher that a turn finished with background work or monitoring still running is not done, and that work-settled news says when it is.

October 17, 2026 (#1150): a root Claude reply observed during a running Sotto turn records that turn's Sotto user-message anchor. No new permission follows from this evidence. The clock-crossing and gated-replay diagnostics demonstrate a weakness in time-based attribution; they do not establish the mechanism of the recorded Windows CI failure.

## October 15, 2026: a hidden wake-up never changes

Five rounds of review each found new edge cases in Watcher's hidden wake-up, and round 5 had five more: a thread's own facts inheriting a pull request's attention from a send in flight, an earlier build's queue saved as one blocked item, a failed save deleting news that came after a send, a withdrawal leaving a second hidden item, and a handover carrying wake-ups. All of them sat in one place. News folded into the wake-up while it was queued, stopped or being sent, and every retry, acknowledgement, withdrawal and load then had to work out which of its events a send had carried. So nothing folds into it any more. This supersedes the round-5 rules (one item consolidated on load, a record of attention, carried events and four tries kept with the item).

- **Made once, never changed.** Its news and the events it carries are fixed when it is made. News that comes while it exists waits with Watcher's own news, in memory, and becomes the next one once this one leaves. It shares no item with a resume note or pull request news, and it never pauses.
- **One at a time.** A hidden wake-up is made only when Watcher has none and the waiting news needs Watcher. A thread's own facts never make one; they ride along when one is made. News is checked again once its batch's turn comes, and if what is still true is only a thread's own facts, it waits. What Watcher was last told of a thread's own facts is what a made wake-up carried, never what was only observed.
- **It leaves whole, with one outcome.** Acknowledged: its news is told. Withdrawn, because some of it stopped being true before it went: what is still true waits again, and evidence that moved on is told again as it stands, a pull request's still needing Watcher. Surely not sent, or held by a Watcher turn that did not finish: its news waits again, and the next is made only with news that needs Watcher, or when Watcher next comes to rest. Unknown, with nothing left to reconcile it: never sent twice; its news is forgotten and observed afresh, as after a restart, quiet and pull request facts included. Three misses in a row and only news that needs Watcher makes another. A save that fails deletes nothing, since nothing else was ever in it.
- **News is told when the wake-up is made and untold again** for every outcome but acknowledged, in the saved record too, so a restart in between observes it afresh rather than losing it. The record is saved before the wake-up leaves the queue, on start as at any other time, so a crash between the two saves leaves the wake-up, which the next start drops and observes afresh. A wake-up settles once: when the pump and pruning both reach it, the later waits for the earlier rather than taking it out while the earlier's save is still on its way. The record is saved before every such removal, whatever memory says, since a settle whose save failed leaves the news untold in memory alone.
- **A restart starts Watcher's news afresh.** As the queue loads, every hidden wake-up goes, and a wake-up an earlier build saved with Watcher's news beside other news keeps only the other words. Their events are untold again, and what is still true is observed and told anew. A Watcher that restarts on its own, with Sotto running, still reads the news its queue holds, and counts that news's evidence as needing Watcher.
- **Handover.** A handover of an earlier Watcher conversation leaves out the wake-ups its pane leaves out, by the same provenance, and counts them nowhere.

`hiddenWakeUp.ts` names the outcomes and the step the queue takes; WatcherWakeUp keeps the rest. A randomized test drives both with the real queue through sends that land, fail or go unknown, news mid-send, late echoes, failed saves, withdrawals, restarts mid-send and queues earlier builds saved, and checks after every step that there is at most one hidden wake-up, that no send goes without new news that needs Watcher beyond the bounded tries, that a thread's own facts never wake Watcher alone, that every event is told once or forgotten and observed again, and that pumping with nothing new writes nothing.

## October 18, 2026: Watcher looks only at what it watches

Watcher's wake-up pass ran on every coordinator update and looked at every thread, watched or not, which with threads
streaming was about a fifth of main. Unwatched threads make no news; looking at them kept their facts and progress
current for Watcher's own reads. Zach's call: stop looking at them. A pass now looks only at watched threads and
Watcher's own, at once when a turn, a request card, background work, a connection or the record moves, and otherwise at
most every 250 ms. Each Watcher read looks at every thread first, so it reads them as they are. A thread that becomes
watched starts from its facts as they are, so what it had before is not told as news; after a restart, what changed is
still told. Quiet in `list_threads` therefore applies only to watched threads: an unwatched thread has no observed
history of its progress, so a silent one lists as Working. Watched threads' news, Quiet included, is unchanged.

## October 19, 2026: Watcher's replies to news in place

Hiding the news wake-up (October 15) left each news turn's work naming a message the conversation does not have. The

## October 19, 2026: a paired host holds Watcher to the desktop's default

## October 19, 2026: Watcher compacts its conversation and keeps its state (#1189)

Every Watcher call rereads its whole conversation. The session behind #1189 reached about 517,000 tokens, so each call cost about $0.10 just to read it back, against about $0.02 at the start. Zach chose the following the same day.

- **Compaction at 400,000 tokens.** Sotto compacts Watcher's conversation through the coordinator's ordinary `compact-thread` once its provider-reported context passes 400,000 tokens. Zach picked 400,000 over the 200,000 suggested, preferring fewer compactions. It waits for Watcher to rest: no turn running, no card, no compaction, no wake-up and nothing of the user's queued. It tries once per context reading, so a compaction that fails is tried again only after Watcher's next turn. Claude Code, Codex and Muse compact; Grok Build cannot, and its Watcher is never compacted. Compacting Watcher's own conversation answers nothing and grants nothing.
- **Watcher state survives it.** Watcher keeps the user's pending decisions, the standing rules the user gave and the issues it filed with a new tool, `keep_state`, one short line each, twenty to a list; each list it gives replaces the one kept. Sotto adds the watched threads and what each waits on, in its own words, from its records. A new tool, `read_state`, gives all of it back, with Watcher's context against the point. The state never depends on the provider's summary.
- **Watcher is told to read it.** After any compaction completes, the user's or Sotto's, each Watcher turn's note ends with a fixed line saying the conversation was compacted and to call `read_state` first, until Watcher does. The request note's Grok Build and Muse line strips the variant with it exactly, as before. The state is not pasted into the note, so the note stays fixed words.
- **Privacy.** The kept lists are the user's and Watcher's words. They are saved in `watcher-state.json` beside `agents.json` only while Keep local history is on; otherwise they live in memory and a saved file is emptied. The watched part is identities and Sotto's sentences.
- **The owl tile opens it.** This amends "Approved owl and words": in Watcher's room the Sotto Owl tile is now a control, named **Watcher's context and state**, with a thin bar under it filling toward the compaction point and a dot when close. It opens a panel with the context size against 400k, **Compact context**, and the state block: Watching, Waiting on you, Your rules, Issues filed. Zach picked this, variant C of three, and asked that the panel show no cost; the issue's running cost is left out. The prototype is outside the repository, at `zstack-scratch/watcher-cost-prototype/`.
