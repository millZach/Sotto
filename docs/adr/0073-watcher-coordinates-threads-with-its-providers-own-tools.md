Accepted October 9, 2026. Zach chose this shape on October 9 after [the first Windows live checks](../verification/2026-10-09-command-center-live-windows.md) and [the Codex benchmark](../perf/2026-10-09-command-center-codex-benchmark.md). It replaces this ADR's isolated read-only design. The A2 room, phone scope and provider-change continuity chosen on October 8 remain, following [ADR-0068](0068-remove-voice-control-and-thread-management.md) and [the plan](../plans/2026-10-08-command-center.md).

Sotto has one current **Watcher** on this computer, identified by main's durable local host and Sotto thread IDs, special thread kind, project and creation operation. Titles, tool arguments, prompts, phones and host commands cannot select it. The stat-signature cache and failure isolation keep ordinary threads independent of a missing or corrupt Watcher record. Retired conversations remain readable history and refuse resume. Creation retains ADR-0002's immutable bindings and flush-before-dispatch rule.

## Standing watching (October 13, 2026)

A standing watch records a user's durable assignment of any ordinary thread to Watcher. Watcher can also use `watch_thread` and `unwatch_thread` when instructed to watch threads. The watch stays the user's to give: `watch_thread` is refused unless the Watcher turn answers the user's own message, the root or a continuation of an active request the user started; a wake-up, a standing scope or Watcher's own initiative grants no watch. Sends under a watch the user gave need no further asking. Establishing a watch sends no prompt; it survives request closure and restart until Stop watching. Watcher gets observed finished, question, permission, failure, quiet, Git/PR/check news and manages the thread on its judgment, pinging the user only for a card that needs him. It still answers no card. Watching has no count cap; the in-flight cap remained on new starts until October 19, 2026, when it went (see that day's amendment below).

A direct desktop, phone or native user instruction fences old automatic deliveries and, until the user's turn ends, lets Watcher only steer that turn. It does not remove its standing watch or take the thread from Watcher (October 19, below). A fresh bounded continuation request can be linked to the standing watch and the current Watcher turn; each target retains four prompts within that turn, retries do not reset that count and a stopped/closed request never becomes active again (save a paired host's own closed copy, October 20, below). Opening and answering remain distinct from takeover. Stop watching invalidates news and fences queued automation, preserving the user's own work.

A thread is watched when it is under a standing watch or takes part in an active request of the current Watcher (or of a paired master, on the host that owns the thread) that the user has not taken over and Watcher has not stopped. Main marks each projection row `watched` with that one answer (`isWatchedRow` in `src/shared/watcherRoom.ts`), and the room, the Threads page, the phone page and the phone shell's owl all read the mark rather than deciding for themselves. A thread watched only through a request, as on an older paired host, is taken over by a direct instruction and stops being watched.

Paired hosts require the additional optional host-v1 `watcher-standing-watch` feature. The owning host records assignments attributed to its authenticated SSH-recorded desktop/master, detects its local user turns and publishes the authoritative generation/pause state. Withdrawing an assignment retains a text-free fence so late synchronization cannot reinstall it. A retained latest master-creation frontier also fences retired conversations after empty synchronization. Older hosts refuse standing-watch automation. Paired phones negotiate optional `watcher-phone-manage` alongside `watcher-phone`; mutations are connection-guarded and exact retries return the original outcome with fresh state. Watching and returning to Ask for approval need pairing; choosing a mode that lets Watcher act without asking requires the phone's current Can answer policy at admission and the writer. Neither management feature grants card-answer authority. Stable desktops offer and start none of this and retain saved records whole.

## Historical Windows Codex launch probe (October 9, superseded October 13, 2026)

The lead diagnosed the first live failure: the user's elevated Windows sandbox requires one-time setup that fails on this computer. With command-line overrides selecting unelevated and read-only, the lead observed a successful PowerShell file read; project and Temp writes denied with UnauthorizedAccessException and no changed files; and curl exiting 7 while the same outside request returned 200. These are the lead's reported checks, not a claim that every network path is isolated. PowerShell runs in Constrained Language mode. OpenAI describes [unelevated as a fallback with weaker network isolation](https://learn.chatgpt.com/docs/windows/windows-sandbox#configure-a-legacy-fallback).

Before the first model turn on each Windows Watcher app-server, Sotto runs two zero-model-turn `command/exec` calls through that same server with an explicit read-only policy. It creates an owned synthetic probe folder in the thread's project, checks a `Get-Content` read against its marker, then attempts `Set-Content` to a separate probe file. Successful reads, an explicit permission-denied write result, and an absent output file are all required. Set-Content works in Constrained Language mode; a forbidden .NET method would not prove filesystem enforcement. Because app-server converts an uncaught sandbox denial into an RPC error, the PowerShell probe catches only UnauthorizedAccessException with the OS E_ACCESSDENIED HRESULT and emits a fixed denial marker. The cmdlet category varies between creating a file and opening an existing one, so it is not the enforcement check. Any other result refuses launch. Sotto removes only its known probe files and folder.

A failed, malformed, timed-out or inconclusive probe ends that app-server before it can receive a turn, with a plain refusal saying the read-only sandbox is not working and nothing was sent. The check runs again on early start, cold resume, settings/model replacement and a replacement client process; resident reuse needs no repeated probe. The override and probe never read or change the user's saved provider configuration or credentials. Fakes cover both working enforcement and refusal, including a successful write and an unrelated command failure. macOS uses its existing native policy and remains outside this Windows proof.

## October 11, 2026: local tool and room boundary

Ticket 5 adds the optional host-v1 `watcher-control` and `watcher-reads` paths. A headless host offers them independently of its release track, while stable desktops use neither. Both listeners require the paired desktop's SSH-written client record; phone and general socket pairings cannot claim machine origin, even with Can answer. The local tool bearer remains local. Request attribution binds the authenticated desktop to the master's creation identity, root user-message reference and ceiling; operations retain the exact master-minted target, retry, digest and receipt identities. The owning host imports these into the established Watcher service rather than duplicating adapter enforcement. The master's default applies, held to Ask for approval where the host does not let that desktop answer (amended October 19, 2026, below). No policy is written and no request is answered.

The master persists and reserves capacity before sending. The host never creates master requests or extra global slots. A lost acknowledgement holds uncertainty until the owning receipt proves what happened; reconnection and host restart do not replay mutations. Host native or phone input fences ownership before the next machine writer. Scoped text-free projection pushes carry receipts, participation and sourced evidence, bounded at a thousand records of each kind, with separate exact operation reads. Thread reads use the owning store's positional cursor and epoch; no detail revision becomes a message position or event cursor. Older hosts keep ordinary summaries and refuse automation before the wire. No phone filter is introduced; Watcher's phone surface remains ticket 8 after its prototype.

The local service retains the model and effort in the creation intent, because recovering by a provider's first ready model could silently change the user's choice. Recovery resumes the saved intent under the same Sotto ID. A thread's immutable native binding remains unchanged.

Stop all uses a sixty-second, main-issued preview identity naming its exact eligible targets. An expired or changed preview refuses before stopping anything. Each target's ownership is rechecked at dispatch, so a later takeover can make a confirmed batch partial. The private room contract projects current identity/options, participation, takeover, capacity and text-free receipts without relying on desktop selection.

Forward reads use a position of -1 for a restart cursor before the first zero-based message. Card anchors and expected turn/last-user guards are separate identities. Local tools have no file broker and no remote-control fallback. With history off, machine queue items and Watcher drafts are omitted from disk while their control references remain.

Machine admission travels through the workspace, provider router and Sotto identity adapter as a private in-process guard, rechecked after native preparation and at the writer. It never becomes a field generic IPC or a socket client can supply. A machine interrupt cancels native work without sending a denial answer to a pending request. Targeted Stop increments participating generations and records `automationStopped`; it cancels only undispatched machine messages, retains uncertainty and prevents replenishment within those participations. A reserved creation whose target is unavailable returns its original receipt rather than dispatching again. Queued user continuations retain text-free draft/message references on their original request and share its budgets while it stays active; one delivered after that request stopped or closed starts its own (October 19, below).

Owl's history-off queue cleanup also covers corrupt and abandoned write copies. ## October 14, 2026: what wakes Watcher

On October 14, 2026 Zach watched four threads and found Watcher woken by almost every tool call in them. Most of the news said "Sotto observed changed evidence", because a worker's working copy and Git status change while it works, or "Sotto observed a new delivery receipt", for Watcher's own sends going through. He and the lead agreed that Watcher wakes only for what needs its attention. This amends ticket 4's event news (October 11); batching, the quiet rule, held news through restarts and babysitting's own wake-ups are unchanged.

- **Wakes Watcher:** a watched thread's turn finished or failed, a question or permission card appeared, the thread went quiet (twenty minutes, as before), a pull request's link, state, checks, review or auto-merge changed, the user took the thread over, and a receipt for one of Watcher's own sends that failed, was refused or may not have gone (failed, uncertain, or accepted with a refusal or uncertain thread creation).
- **Rides with a turn's end:** the thread's own facts, its working copy, Git status and checkpoints. A change to them never starts a wake-up. It joins a turn end not yet told, or keeps evidence news still waiting to go current. News already in Watcher's wake-up is never changed (October 15, round 6): if its evidence moved on before it went, the wake-up is withdrawn and that evidence is told again as it stands. Any other change waits for the thread's next turn end, which tells it only if the thread's own facts differ from what Watcher was last told. A change made while a thread rests is told with its next turn's end.
- **Never wakes Watcher:** an ordinary delivered or accepted receipt. Watcher made that send and reads its receipts with read_operation when it wants them. Such a receipt still waiting from an earlier build is withdrawn.

What Watcher was last told of a thread's own facts is kept in memory. After a restart, the first turn end may tell them again, inside the wake-up that turn end causes anyway.

## October 14, 2026: work settled

Turn-finished news fires once per turn and carries a background work count, but its identity is the turn and its status, so when the work a finished turn left running ended, Watcher heard nothing (#1024). T3 keeps a task open while a child waits on its own children; Sotto now says when that wait is over.

News gains one kind, **work-settled**: once per turn, when the work a finished or failed turn left running reaches zero. That work is the thread's provider-confirmed background work (Claude's background tasks), the working sub-agents in its roster (Codex's `subAgentActivity`) and its monitoring. Claude's background sub-agents appear in both of the first two, so the count takes the larger of those, plus monitoring; turn-finished and turn-failed news carry the same count, so a Codex turn whose sub-agents are still working no longer reads as done. A turn that finished with none gets no work-settled news. Like all Watcher news it carries identities and counts only, rides the same batch and wake-up path, and grants nothing. Quiet's rule is unchanged: it still reads background work and monitoring only.

Unknown is not zero. A restart cannot see how sub-agents that were running ended, so the roster holds them as unknown; while any are unknown, the turn stays unsettled and its news waits until the provider says how they ended. They count with the working ones in a finish's work count, so a turn that finishes while they are unknown reads as not done and is owed work-settled news like any busy finish. The news is due only while its turn is the thread's newest finished turn and its work is still zero and known. Work that starts again before delivery withdraws it, and the turn is owed it again, so it comes once, after the work truly reaches zero. A new turn replaces it.

It survives restart without repeating. A finish observed with work still running carries a second digest in its event ID, the work-settled scope (request, thread, generation and turn), so the saved or still-queued ID alone tells a restarted Watcher which turn is owed one; the work-settled ID itself is saved like any other and deduplicates the rest. Only a finish delivered as busy is owed one: a finish first observed with nothing running stays done, and work seen on that turn later brings no work-settled news. Paired hosts list an optional host-v1 feature, `watcher-work-settled`, offered under the same recorded desktop origin as `watcher-reads`: their thread projection carries background work, monitoring and the sub-agent summary. A host that does not list it reads as unknown, not as none running. Its finished turns carry no work count, and its threads get no work-settled news; Watcher learns a turn finished there and nothing about the work it left. No phone or host decoder reads news kinds.

`watcherPrompt.ts` tells Watcher that a turn finished with background work or monitoring still running is not done, and that work-settled news says when it is.

## October 14, 2026: outcomes

`read_operation` said that accepted meant delivered, not that the work succeeded, so after news Watcher paged through `read_thread` to find what a worker said, and with follow-ups it could not tell which answer was which brief's (#1025). Each start and send now has an **outcome** (CONTEXT.md): `working`, `background`, `answered`, `failed`, `stopped`, `paused` or `unknown`. This is the outcome ADR-0081's delegations reuse; they add `refused`, for a delegation main turned down as it was asked for, which Watcher's refusals, never recorded, do not have.

The brief's own message ties it to its turn. A start or send that began a turn is answered by that turn; a steer read into a running turn shares that turn's answer; a queued send gets its own. The anchors are the ones own-change marks use: Claude Code and Grok Build name a turn by the Sotto user message it began with, and Codex records that message as its turn's anchor. A turn Claude Code cut for Watcher's own steer goes on in the turn the steer runs as. For older replies without exact turn proof, a reply belongs to the newest turn begun above it that had started when it was written, because a steer Claude Code held past a turn's end is shown where it was sent, above the reply that turn still gave. The outcome keeps a text-free reference: the thread, the turn's Sotto anchor, the provider's own turn ID when the thread proves the two are the same turn, and the turn's final reply message.

October 17, 2026 (#1150): a root Claude reply observed during a running Sotto turn records that turn's Sotto user-message anchor. The first proved owner stays with the message through streamed completion, transcript replay, timestamp correction and text-free history seeding. The event store retains it with the message; a fresh provider read cannot erase or replace it. Watcher uses that exact owner before the older timestamp rule. A proved owner whose turn is outside the retained window is not reassigned to a different turn. Rewind and deletion discard the corresponding identities as before. No new permission follows from this evidence. The clock-crossing and gated-replay diagnostics demonstrate a weakness in time-based attribution; they do not establish the mechanism of the recorded Windows CI failure.

Before delivery the receipt decides: queued or dispatching is `working`, uncertain is `unknown`, and a failed delivery is `failed`, except that one the user's own turn took over is `paused` and one whose request was stopped first is `stopped`. After delivery the owning host's thread decides. A running turn is `working`. A finished newest turn is `background` while the work it left running, or sub-agents left unknown, remain, the same count work-settled news reads, and `answered` once that work ends. The count is the thread's, so a brief seen in `background` stays there while any work remains, even once another turn has begun. A turn cut for Watcher's steer is `working` until the steer's own turn shows. A failed turn is `failed`, and a turn cut before it answered is `paused` when the user's own message came next, `stopped` otherwise. `answered`, `failed`, `stopped`, `paused` and `unknown` never move again. A start or send that was in flight or still unanswered when Sotto stopped is `unknown` from the next start on, never `answered`: Sotto cannot prove how its turn ended.

`read_operation` returns the outcome, the reference, a sentence saying what the outcome means, and Sotto's evidence for that turn. Once answered it also returns the turn's reply, labelled as the worker's words (`from: worker`) and cut to 32 KiB, inside the existing 64 KiB read bound. With Keep local history off, a reply answered before a restart is not shown, and the read says so; Sotto holds it only in memory. Turn-finished, turn-failed and work-settled news name the operation the turn answers, by its ID. The control record, the room and the phone's receipt rows keep the outcome and reference only, never a reply's words. Reads and retries charge nothing; the four-prompt rule is unchanged, and the in-flight rule was until October 19, 2026 (below).

Each host observes the outcomes of its own threads. A paired host lists an optional host-v1 feature, `watcher-outcomes`, offered under the same SSH-recorded origin as `watcher-reads`. The desktop asks such a host for outcomes in its exact `read_operation`, and keeps what comes back as identities. The host sends outcomes nowhere else: projections, pushes and control packets carry none, so a desktop from before them reads the host as it did. A host that does not list the feature is not asked, and its accepted briefs read `unknown` with a sentence saying to update it, never a guessed outcome. A phone's receipt rows carry the outcome as an optional field that older phones ignore.

## October 15, 2026: work settled under the wake rule

Work-settled news (#1050) and the rule for what wakes Watcher were decided apart on October 14. Together:

## October 15, 2026: a turn end waits for its Git read

Sotto Bug Bot found that a finished turn's own Git read could miss its wake-up. ## October 15, 2026: a hidden wake-up never changes

Five rounds of review each found new edge cases in Watcher's hidden wake-up, and round 5 had five more: a thread's own facts inheriting a pull request's attention from a send in flight, an earlier build's queue saved as one blocked item, a failed save deleting news that came after a send, a withdrawal leaving a second hidden item, and a handover carrying wake-ups. All of them sat in one place. News folded into the wake-up while it was queued, stopped or being sent, and every retry, acknowledgement, withdrawal and load then had to work out which of its events a send had carried. So nothing folds into it any more. This supersedes the round-5 rules (one item consolidated on load, a record of attention, carried events and four tries kept with the item).

- **Made once, never changed.** Its news and the events it carries are fixed when it is made. News that comes while it exists waits with Watcher's own news, in memory, and becomes the next one once this one leaves. It shares no item with a resume note or pull request news, and it never pauses.
- **One at a time.** A hidden wake-up is made only when Watcher has none and the waiting news needs Watcher. A thread's own facts never make one; they ride along when one is made. News is checked again once its batch's turn comes, and if what is still true is only a thread's own facts, it waits. What Watcher was last told of a thread's own facts is what a made wake-up carried, never what was only observed.
- **It leaves whole, with one outcome.** Acknowledged: its news is told. Withdrawn, because some of it stopped being true before it went: what is still true waits again, and evidence that moved on is told again as it stands, a pull request's still needing Watcher. Surely not sent, or held by a Watcher turn that did not finish: its news waits again, and the next is made only with news that needs Watcher, or when Watcher next comes to rest. Unknown, with nothing left to reconcile it: never sent twice; its news is forgotten and observed afresh, as after a restart, quiet and pull request facts included. Three misses in a row and only news that needs Watcher makes another. A save that fails deletes nothing, since nothing else was ever in it.
- **News is told when the wake-up is made and untold again** for every outcome but acknowledged, in the saved record too, so a restart in between observes it afresh rather than losing it. The record is saved before the wake-up leaves the queue, on start as at any other time, so a crash between the two saves leaves the wake-up, which the next start drops and observes afresh. A wake-up settles once: when the pump and pruning both reach it, the later waits for the earlier rather than taking it out while the earlier's save is still on its way. The record is saved before every such removal, whatever memory says, since a settle whose save failed leaves the news untold in memory alone.
- **A restart starts Watcher's news afresh.** As the queue loads, every hidden wake-up goes, and a wake-up an earlier build saved with Watcher's news beside other news keeps only the other words. Their events are untold again, and what is still true is observed and told anew. A Watcher that restarts on its own, with Sotto running, still reads the news its queue holds, and counts that news's evidence as needing Watcher.
- **Handover.** A handover of an earlier Watcher conversation leaves out the wake-ups its pane leaves out, by the same provenance, and counts them nowhere.

`hiddenWakeUp.ts` names the outcomes and the step the queue takes; WatcherWakeUp keeps the rest. A randomized test drives both with the real queue through sends that land, fail or go unknown, news mid-send, late echoes, failed saves, withdrawals, restarts mid-send and queues earlier builds saved, and checks after every step that there is at most one hidden wake-up, that no send goes without new news that needs Watcher beyond the bounded tries, that a thread's own facts never wake Watcher alone, that every event is told once or forgotten and observed again, and that pumping with nothing new writes nothing.

## October 19, 2026: quieter news (#1190)

A Watcher session on October 19 cost about $28 over about 300 calls, and only about a third of some 110 wake-ups needed Watcher. Every wake-up rereads the whole conversation, so each costs more as it grows. This amends "what wakes Watcher" (October 14) and "work settled under the wake rule" (October 15). Zach chose the batch timing, and how delegated threads reach Watcher, the same day.

- **Ordinary news waits for more.** A question, a permission request, a failed turn, checks that newly fail, a takeover and a send that failed keep the two-second batch, capped at five seconds, and take whatever waits with them. Other news, turn ends, work settled, pull requests and quiet, goes twenty seconds after the last of it and never later than a minute after the first. A Git-backed turn end that comes just before the minute keeps its own five-second wait for its Git read; the rest goes at the minute.
- **A busy finish waits for its work.** A finish with background work still running needs Watcher only after twenty minutes. Until then it rides with that turn's work-settled news, a question or a failure, and a wake-up that holds both says the turn finished once; other ordinary news going does not take it along. If its thread begins another turn first, the finish is told then, since it happened, counted as new news, and is owed no work-settled news; its note says none will follow, as read_operation's note for a brief left in background does once the thread's newest turn is another, a steer read into the brief's turn not counting and a turn Claude Code starts by itself counting. A steer read into such a turn of the provider's own may still be placed on the brief's turn, as outcomes placed steers before this change. A wake-up that misses without it leaves it its retry, within the same bound on tries. Ripening counts as news that needs Watcher once, so a wake-up that missed before it cannot hold it back, and work that never settles still reaches Watcher.
- **Pull requests wake Watcher for what matters.** Checks failed or all passed on a commit, the checks the base branch requires passed on it, merged, closed, approved or asked for changes, a conflict with the base, and comments or reviews moving after Sotto first read them. A pending check, a check count, a new commit, auto-merge or a new link rides with the next news that needs Watcher. Conflicts come from the Pull request surface's and babysitting's reads, a review asking for changes from the Pull request surface's, and required checks and remarks from babysitting's, its remarks as their text-free fingerprint; any new review moves that fingerprint. They are kept in memory beside evidence, not added to its schema, which paired hosts share, and a read older than the one kept changes none of them. So a paired host's threads wake Watcher for checks, merging or closing and approval only: their conflicts, comments and required-only passes need an addition to host protocol version 1, left for a later change. A read that holds only some of a commit's checks can say one failed, never that all passed. Queued news of a pull request is checked again against what its pull requests say beside the evidence, so news of a conflict that has since cleared does not go. Evidence news of a pull request needs Watcher while its pull requests say something Watcher was not told in a wake-up it acknowledged: checks that fail and go back to running before the news goes say nothing new. A fact that ends and comes back, as checks that fail again on the same commit after running again, is news again. Required checks pass only on a read that holds all of a commit's checks, and only for the commit the pull request is on now. A pull request Sotto has not read, as after a restart, is unknown, so news restored from the queue still needs Watcher.
- **Told once.** A thread in several active requests is told under its standing watch, else the newest request, so one finish is one event. Turn ends, work settled, quiet and request cards have IDs without the request, so one told under one request is not told again under a newer one, after a restart too, since the saved IDs say so. One that stops being due before it goes, as when its request stops, was never told, and is told again under another request while it is still true. Work-settled news is owed per thread and turn, so a thread that moves to a standing watch keeps it. The first restart after this change may tell each watched thread's last finish once more, since the IDs saved before it named the request. A receipt that a tool's answer carried, a refusal included, is no news until it changes.
- **Delegated threads are their delegating thread's.** Watcher watches the thread that delegated. A thread it delegated to (ADR-0081), or one that thread delegated to in turn, makes no news while a thread above it is watched, even if it is watched itself, and news it made before then is withdrawn. Its question or permission request comes at once as news of the topmost watched thread above it, naming the delegated thread to open, while the delegated thread is connected, whether or not the watched thread is. That thread's `waitsOn` in `list_threads` lists its direct delegated threads' cards. The delegating thread's own model is not woken for it.
- **The reply rides with the news.** As a wake-up is sent, Sotto adds the first 500 characters of a finished turn's reply, labelled as the worker's words, and its own words for what a pull request says that Watcher has not been told. Both are read from the thread at that moment and go only into the note the send carries. The reply is the newest turn's own, by the rule outcomes use, or none. The queue and the control record keep identities only. The provider's own history keeps what it was sent, as it keeps `read_operation`'s replies; for a Grok Build Watcher the note is a line of its message, which Sotto's history keeps too while Keep local history is on, and which its conversation never shows. The detail gives way before any event when a note would exceed its 16 KiB.

## October 19, 2026: watching lasts until the user stops it

Watcher watched a thread Zach was also working in. He sent it a message himself, and from then on Watcher's sends to it were refused with "You took over this thread", while the thread still showed **Watched by Watcher** and offered no way to hand it back. The standing watch had survived, as decided on October 13, but the user's message also marked the thread's request participation `taken-over` for good, and every later send checked that mark. A second cause did the same with no user at all: a wake-up Sotto sent itself, delegation news, was read as the user's own native message because Watcher knew a thread's own messages only by its operations.

Zach decided the rule on October 19:

- **A standing watch lasts until the user stops it.** The user's own message, desktop, phone or native, no longer takes a watched thread from Watcher. It still fences what Watcher had prepared: the watch and every participation it keeps move to one new, higher generation, and queued Watcher messages are cancelled. While the user's own turn runs, Watcher can only steer that turn; a `now` or `queue` send is refused as `THREAD_BUSY` until it ends (Zach's pick: steer, over queueing behind it or waiting). `stop_thread` is refused the same way unless the Watcher turn answers the user's own message in that request, the user asking for the stop; under a standing watch's scope it never stops the user's turn. Afterwards Watcher sends under the watch, or under the user's request, as before. Only a thread watched for a request alone, as on an older paired host, becomes the user's again, and so does a participation Watcher had already stopped, which the user's command reviews so its held queue goes on. Records an older build marked `taken-over` on a thread that is still watched are given back when Watcher recovers and at the next send; a paired desktop takes the owning host's revival of its own thread, and the owning host gives a participation back the same way when the desktop's watch reaches it after the user sent there.
- **Once the user stops watching, Watcher cannot watch the thread again by itself.** The user's Stop watching (the room, a thread's page, the iPhone, Undo) records the thread and the newest message to Watcher at that moment (`userUnwatches`). `watch_thread` is then refused until the user hands the thread back: with **Watch**, at once, or in a message to Watcher sent after Stop watching, which the Watcher turn calling `watch_thread` must be answering. Sotto checks that the message is newer, not what it says. Watcher's own `unwatch_thread` blocks nothing (Zach's pick); it still fences automatic sends until a watch is given again, as before.
- **Sotto's own messages are never the user's.** A wake-up, babysitting's or delegation's news, known by the host's record of what it sent (`wakeUpMessageIds`, a message's `wakeUp`), and a brief delegation sent, known by its message ID, are neither a takeover nor a user's turn, like Watcher's own sends.
- **The label matches what Watcher can do.** A thread under a standing watch stays **Watched by Watcher**, because Watcher can act on it (Zach's pick: keep the label while the user's turn runs). Its reply box says Watcher can only steer the running turn, and Stop all leaves a thread alone while the user's own turn runs there. No UI moved; only those two lines' words changed, so no mock-up was made.

This supersedes, for standing watches, the October 13 sentences that a user instruction "pauses new Watcher sends" and that takeover marks participation, the Ticket 3 note that a changed native head is takeover, and October 17's local takeover scope: an earlier takeover no longer fences a request on a watched local thread, so its retained ordering (`localTakeovers`) now matters only for request-only watching and for when a queued instruction to Watcher starts a request of its own. The October 16 takeover line therefore follows only a thread watched for a request alone, or a participation Watcher had already stopped. Request identity, budgets, receipts and the paired-host protocol are unchanged; a paired host applies the same rule to the threads it owns.

## October 19, 2026: every user Send reaches Watcher under an active request (#1184)

On October 19 Zach pressed Stop on Watcher while a message to it waited in the queue. A retry keeps the request its first delivery made.

- **A steer into a turn that answers the user's own active request is part of that request.** Main records it as one of that request's messages before it is sent, so Watcher may watch, start and send for it as for the turn's first message. It carries no note of its own; Watcher already has the request from the turn it joins.
- **A steer into any other turn opens a request of its own,** rooted in its own message, as a Send to an idle Watcher does: a turn Sotto's wake-up started, its news among them, or one whose request is no longer active. A steer has no context channel of its own (Codex's `turn/steer` takes no turn-level fields, and Claude Code's prompt hook is not promised for a message added to a running turn), so its note goes as one bracketed line after the user's words, as a Grok Build send's does. Every copy of the message, in the pane, Copy and the phone, is shown without that exact line, by the request record, as Grok Build's are. Later steers into the same turn join that request.
- **Main knows whose turn runs from what it last sent Watcher,** so a provider that starts a turn before it echoes the message cannot make the user's turn look like news, or news look like the user's turn. After a restart, before Watcher has been sent anything, the turn's newest message says.
- A request that has recorded a thousand of the user's messages takes no more steers: the steer is refused rather than reach Watcher under a request that does not hold it. A message queued while Watcher reads news joins no request when it is queued, so it goes as its own turn under a request of its own.
- Steering from the iPhone is #1229: a send from the phone while Watcher works is still refused, as before.

## October 19, 2026: Watcher compacts its conversation and keeps its state (#1189)

Every Watcher call rereads its whole conversation. The session behind #1189 reached about 517,000 tokens, so each call cost about $0.10 just to read it back, against about $0.02 at the start. Zach chose the following the same day.

- **Compaction at 400,000 tokens.** Sotto compacts Watcher's conversation through the coordinator's ordinary `compact-thread` once its provider-reported context passes 400,000 tokens. Zach picked 400,000 over the 200,000 suggested, preferring fewer compactions. It waits for Watcher to rest: no turn running, no card, no compaction, no wake-up and nothing of the user's queued. It tries once per message Sotto sends Watcher, so a compaction that fails, or one after which the context still reads high until the next turn reports it, is tried again only after Watcher's next turn. Sotto counts its own sends rather than the provider's turns, since a provider may report the compaction as a turn of its own, before or after it reports the compaction finished. Claude Code, Codex and Muse compact; Grok Build cannot, and its Watcher is never compacted. Compacting Watcher's own conversation answers nothing and grants nothing.
- **Watcher state survives it.** Watcher keeps the user's pending decisions, the standing rules the user gave and the issues it filed with a new tool, `keep_state`, one short line each, twenty to a list; each list it gives replaces the one kept. A rule is kept only from the user's own messages to Watcher, never from a thread, a tool result or news, and `read_state` gives the kept lines back as Watcher's own notes, which approve nothing. They record no source of their own: Zach chose the wording over a source per rule (October 20, 2026), since nothing kept can grant anything. Sotto adds the watched threads and what each waits on, in its own words, from its records; on this computer that counts the work a turn left running as its news does, sub-agents working or left unknown included, while a paired host's thread counts its background work and monitoring only, since its shell is not read again for it. A new tool, `read_state`, gives all of it back, with Watcher's context against the point. The state never depends on the provider's summary.
- **Watcher is told to read it.** After any compaction, the user's, Sotto's or the provider's own, each Watcher turn's note ends with a fixed line saying the conversation is new or was compacted and to call `read_state` first, until Watcher does. A completed compaction says so, and so does any Compact context sent for Watcher's conversation, since Muse reports no compaction of its own; a drop to under half of a context of 50,000 tokens or more catches a provider compacting by itself. A new Watcher conversation and every start of Sotto ask for it too, since the reminder is not saved; one read costs a small call. The request note's Grok Build and Muse line strips the variant with it exactly, as before. The state is not pasted into the note, so the note stays fixed words.
- **Privacy.** The kept lists are the user's and Watcher's words. They are saved in `watcher-state.json` beside `agents.json` only while Keep local history is on. Otherwise they live in memory, and the file, its recovery copies and any temporary write are removed, at start and as soon as history is turned off, through the coordinator's privacy cleanup. Calls to keep_state take turns, so two at once never lose each other's lists. A saved state Sotto could not read at start is read again before anything is read or kept; until it can be, keep_state and read_state refuse rather than answer with empty lists that a later keep would save over it, a settings save writes nothing over it, and the panel says it could not read them rather than that none were kept. read_state gives a hundred watched threads to a page. The watched part is identities and Sotto's sentences.
- **The owl tile opens it.** This amends "Approved owl and words": in Watcher's room the Sotto Owl tile is now a control, named **Watcher's context and state**, with a thin bar under it filling toward the compaction point and a dot when close. It opens a panel with the context size against 400k, **Compact context**, and the state block: Watching, Waiting on you, Your rules, Issues filed. Zach picked this, variant C of three, and asked that the panel show no cost; the issue's running cost is left out. The prototype is outside the repository, at `zstack-scratch/watcher-cost-prototype/`.

## October 20, 2026: a request lasts its Watcher turn (#1254)

Asked to settle many threads in one message, Watcher settled the first and was refused every other with "This request is not active". A settle relinquishes its thread at once, so a request whose only participants were threads Watcher settled had none left participating after the first, and Sotto closed it while Watcher's turn still ran. Zach decided on October 20, 2026 that paired hosts are fixed in the same change.

- **On Watcher's computer.** A request is done only when every thread taking part has settled, nothing is queued to Watcher or to them, and no running Watcher turn answers it. The turn that answers it is the one its own message, a continuation or a steer began, as Watcher's tools already decide. A turn answering another request does not hold it, so a request does not outlast its turn.
- **On a paired host.** The owning host keeps its own copy of the request and closes it once the threads it holds have settled, because it cannot see the master's turn. A new operation the master admitted under its active request opens that closed copy again, in the same change that records the operation and after the host's own origin, authority and fence checks. A retry opens nothing, and settled and stopped participations stay as they are. This is the one way a closed request becomes active again.
- **Stop still ends it.** A Stop the master sends marks the owning host's copy stopped whether it was active or closed, so an operation the master sent before its Stop and that arrives after it is refused. A stopped request never becomes active again, on either computer.

## October 20, 2026: Watcher settles the watched threads that finish

Zach asked that any thread Watcher watches that finishes all its work be settled by Watcher, behind a toggle in Watcher's settings. Settling a watched thread was already Watcher's to do with `settle_thread`, but only when it thought to, and the thread stayed watched, so Watched filled with threads whose work was done.

Zach decided on October 20:

- **Settle finished threads**, a setting under Settings → Watcher (`watcherSettlesFinishedThreads`), on by default and part of Watcher's Owl feature. Main does it, not Watcher's model: no tool call, no prompt, no budget.
- **Done** means: the thread's last turn completed (a failed or stopped turn is not done), its status is idle, it has no request card, no background work, monitoring or working sub-agents, and no work unknown (a sub-agent a restart could not see end, or a paired host that does not report the counts, never counts as none), no thread it delegated to (ADR-0081) still working or asking, nothing queued or unsettled for it on this computer, no Watcher start or send to it still queued, dispatching or uncertain, the user's own turn is not running there, no active request has it taken over, and no pull request it has is open. A turn the user sent there counts like any other (Zach's pick, over leaving a thread the user wrote to alone).
- **Watcher hears first.** A thread is settled only once Watcher has been told all of its news that needs Watcher, its finished turn and a merged pull request included, and Watcher's own turn has ended with nothing queued for it. Watcher may act on the news, and settling before it had would cut off that work and leave the finish untold. `WatcherWakeUp.heardAllOf` answers this from the news it made, the news still waiting and the wake-ups not yet out of Watcher's queue.
- **Then Watcher stops watching it**, as Watcher's own `unwatch_thread` does, so the user's hand-back rule (October 19) does not apply (Zach's pick, over keeping it in Watched under Settled). This amends October 19's "a standing watch lasts until the user stops it": with Settle finished threads on, a standing watch also ends when its thread finishes and is settled.
- **Quiet.** No notice, no news, no line in Watcher's conversation (Zach's pick). This computer's thread is settled through the workspace's own write, checked again inside its lane, so a thread just given more work keeps its watch; it is neither the user's settle nor a takeover. A paired host's thread is let go first, asked again as it now stands, and then settled the way the user's Settle reaches that host from the desktop (`WatcherRemoteHosts.settle`), since that host reads the command as the user's and would otherwise record a takeover. One that changed in between, or that its host does not settle, is watched again. That last command carries no guard of its own, so work that reaches the host in the moment between the second look and the settle is settled with it; it keeps running, as settling never stops work. Stable event names only reach the log: `watcher-thread-auto-settled` and `watcher-thread-auto-settle-skipped`.
- **Work it delegated settles with it.** Since a thread's delegated threads settle with it (ADR-0081), each of them must be done the same way, its pull requests included.
- **Once per turn.** Each thread is tried once for each turn it finishes. A refused or failed settle is not retried until the thread finishes another turn, so a refusal never loops. The memory of what was tried is not saved, so a restart may try a thread once more.
- **Turning it on settles what already qualifies** (Zach's pick). Main looks at most once a second while updates come, and at once when Settings change.

Auto-settle merged threads, under Git, is unchanged and separate (Zach's pick: the two say nothing of each other). It settles any thread at rest, watched or not, once GitHub reports its branch's pull request merged, on the worktree cleanup's hourly sweep.

The toggle sits first in Settings → Watcher, under a **Watched threads** heading, above **Worker roles** under a heading of its own; the section now shows whenever Watcher is on, with worker roles still behind their own Owl answer. Zach picked this, variant A of three, on October 20, 2026; the prototype is the tag `prototype/watcher-settle-toggle`.

## October 21, 2026: Watcher's changing state is worked out, not kept (#1274)

After a compaction, the notes Watcher kept with `keep_state` still described threads that had finished and a check failure that had moved on, and missed a new issue and the exact merge queue, while the parts of `read_state` Sotto wrote from its records were right. Keeping notes current was a model habit, which cannot be relied on. Zach chose the following on October 21, 2026.

- **Sotto works out what changes.** `read_state` now gives, from live data at each read and never saved: each watched thread's open pull requests, as `list_threads`' slim rows summarise them; the **merge queue**, every open pull request of a watched thread that is not a draft and whose checks passed, oldest pass first by when Sotto first saw them pass (Zach's pick, over every open pull request ranked by checks, and over approved ones only); and the **pending settles**, the watched threads whose work is done but for an open pull request, or for Watcher hearing their news and resting, each with what holds it, while Settle finished threads is on (Zach's pick, over open pull requests only and over settle calls in flight). The pending settles come from the same check the settle itself makes, split so it can say what holds a thread; when Sotto settles a thread is unchanged. When a pass began is kept in memory only, like the rest of the evidence, so after a restart a pass counts from Sotto's first read of it. A pull request Sotto cannot say is not a draft, as one whose thread its host no longer lists, is left out of the queue. Both lists page with the watched threads, a hundred of each to a page, read once at the first page.
- **Kept notes are the user's words.** `keep_state` keeps the user's pending decisions and standing rules in the user's own words, and the issues Watcher filed (Zach kept that list, over dropping it). Watcher is told not to keep what `read_state` works out: what threads are doing or wait on, pull requests and checks, the merge queue or settles.
- **Stale notes are flagged.** `read_state` flags each kept line, in any of the three lists, that names a thread that is settled or that Watcher does not watch, by its title or Sotto thread ID, or a pull request that is merged or closed, by its link or number, with Sotto's reason. A one-word title shorter than eight characters, the "New thread" stand-in, or one a watched thread that is not settled also has, flags nothing, nor does a bare number that an open pull request also has; a link names its one pull request. A flag changes nothing kept: Watcher is told to fix or drop the line. Sotto cannot read an issue's state, so an issue is flagged only through a thread or pull request it names.
- **Only Watcher sees it** (Zach's pick). The owl tile's panel is unchanged; showing the merge queue or stale flags there can follow on its own.

Out of scope, possible follow-ups: a prompt before compaction to reconcile the notes against live state, and adding, removing or editing one kept line instead of replacing a whole list.

## October 21, 2026: held news goes, and says so once (#1263)

On the night of October 20, Watcher heard nothing for 7.5 hours while a thread it watched waited on a delegation that never came back (#1261). Two things made that cost hours instead of minutes, and a third buried what did come.

- **A wake-up to a thread no one was looking at could not be confirmed.** A thread outside the watched set carries no messages in a snapshot, and the queue never put the thread it was sending to in that set. So Watcher's hidden wake-up, sent while the user looked at another thread, reached Watcher but stayed unconfirmed in its queue, and while it was there every later piece of news waited behind it. It settled only when something else had Watcher observed, as `unknown`, and everything was then told again. The queue now puts a thread in the watched set from the moment it takes an item to send until that send settles (see **Watched set** in CONTEXT.md). This holds for a delegation's hidden news too.
- **A finish released after twenty minutes says so.** The twenty-minute release of a busy finish fired, but its line still said the turn was not done and work-settled news would follow, which reads as "keep waiting". When it goes by itself with its thread idle on that turn, the line now opens `Held N minutes, thread idle`, says no turn has run since and that Sotto has not seen the work end, and asks Watcher to read the thread. The start of the reply rides with it as before. No new timer: the release's existing wait is the only one, and it runs only while a finish is held.
- **The same facts are not told twice.** A wake-up whose send was `unknown` used to forget the pull request facts it carried, so a merged pull request was told again with every such wake-up, once a minute on Zach's machine. Those facts now count as told, since the send went out with them; only failed checks are told again, since a failure is never lost. The thread's own facts are still observed afresh and ride with its turn's end told again; only the pull request's are not made into news again. A receipt for a Watcher send turned away with `THREAD_TAKEN_OVER` is no news either: the user sent to that thread themselves, or their message changed its watch. `THREAD_BUSY` stays news, since an ordinary running turn refuses with it too.

Everything else an `unknown` send carried is still observed afresh, as the hidden wake-up's rules say.
