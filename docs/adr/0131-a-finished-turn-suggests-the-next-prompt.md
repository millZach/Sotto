# A finished turn suggests the next prompt

## Status

Accepted October 24, 2026, as an Owl feature (`next-prompt`). Drake picked variant 6, **Picker**, of `docs/prototypes/next-prompt-prototype.html` on October 24, 2026. A port of Drake's Claude Code mod `next-prompt`. Builds on [ADR-0026](0026-short-writing-runs-on-the-threads-own-provider.md) (short writing as a side call), [ADR-0072](0072-sotto-owl-is-a-windows-preview-release-track.md) (Owl features) and [ADR-0113](0113-the-composer-controls-are-text-buttons.md) (text buttons). **Number provisional until merge** (docs/agents/domain.md).

## Context

When an agent finishes, the user's next message is often predictable: "open the pull request", "run the tests again", "why not the theme roles?", or an answer to the question the reply ended on. Drake's mod for Claude Code asks a model, after every answered turn, for a one-line headline of the reply, the single most likely next prompt, four suggestions (continue, verify, challenge, wrap up) and, when the reply ended on a question, two or three answers. The prototype tried ten ways of showing that in a thread. Picker keeps the composer's height and the transcript as they are: the next prompt sits in the empty prompt as a ghost, and the rest opens on request, over the transcript, the way the skills list does.

## Decision

**1. One side call per finished turn, on the thread's own provider.** When a thread on this computer goes from working to idle with nothing waiting on the user, and its newest message is the agent's answer with words in it, Sotto asks the thread's own provider client on the side, exactly as it asks for a title (ADR-0026): the thread's account and model at its lowest effort, no tools, no session, never seen by the thread. No host is added and no key is needed; the call is billed to the thread's provider like the thread's own work. A turn the user stopped or that failed asks nothing, and neither do Watcher's own threads or a delegated thread, whose next message comes from the thread that delegated to it (ADR-0081). The material is the thread's last three exchanges, taken only from the messages the coordinator already holds in memory because a window shows the thread; a thread no window shows carries its summary alone, and its history is not read from the store at a turn's end for this, so it is asked nothing. The exchanges are oldest first, each half cut to 2,000 characters with a title's own excerpt: a prompt keeps its opening and a reply its ending, since what the user answers is how the reply ended. A provider with no side call (Devin) gets no suggestions. While local history is off nothing is sent, as for titles.

**2. The reply is untrusted JSON.** The instruction is the mod's, with the agent named for any provider. The outermost `{...}` is read as JSON and only well-formed fields are kept: a headline of up to 400 characters, a next prompt and texts of up to 200, labels of up to 32, at most four suggestions (each keeping its own intent, or taking its place's when it names none) and three answers. Anything unreadable leaves nothing. Failures log stable names only (`short-writing-failed next-prompt <reason>`, `next-prompt-failed unreadable`), never a prompt, a reply or a suggestion.

**3. Held in memory, guarded by generation.** Main holds each thread's newest suggestion in memory, tagged with the thread's newest user message when the turn ended, and nothing is saved. Main learns of starts and finishes from the pass the Finished unread mark already makes over each update's threads, so nothing new walks every thread on every update, and the side call runs after that update is published. A send, a steer or an answer to the thread once main has accepted it, the thread starting again, or a newer finish lets go of the suggestion, and a reply that lands after one of those is dropped; a send main refuses keeps it. A side call that a start or a newer finish supersedes is told to stop through its abort signal, so it costs no more than it already has, and nothing is logged for it. The window is told each change on its own channel, and a window that has just loaded reads what is held; nothing rides main's state broadcast. The window shows a suggestion only while the thread's newest user message is still the one it was made after.

**4. The next prompt is a ghost in the empty prompt.** While a suggestion stands, an empty Threads composer shows the next prompt in placeholder ink with a small **Tab** keycap, and Tab takes it into the prompt. When what the user typed is a case-insensitive prefix of it, the rest stays ghosted and Tab completes it; otherwise Tab moves focus as it always has. Escape in the prompt puts the ghost away for that turn, and Tab then moves focus as usual; the Next list still opens on request. Case is ignored in the prefix only where lowercasing keeps both lengths; otherwise only an exact prefix counts. The ghost is drawn after the text and is never part of the draft. A screen reader hears it in the prompt's description. While dictation writes, and while a list is open, the ghost steps aside.

**5. The Next list opens over the transcript.** Up in an empty prompt, or **Next** (a text button with a sparkle, after the option chips in the composer's footer), opens a list above the composer, built like the skills list so it never takes height from the composer. Its heading is the headline. Then come the answers, in the accent; the next prompt, keyed Tab; and the four suggestions, numbered 1 to 4, each with its intent's mark in ink. It opens closed and at its first row on every thread. Up and Down move, digits 1 to 4 pick while it is open, Tab takes the next prompt, and Escape closes it and returns focus to where it was opened from. Enter on a suggestion or the next prompt writes it into the prompt for the user to send: in place of an empty draft or one it begins with, otherwise on a line of its own after what is written. Enter on an answer sends it at once as the user's own message, through the composer's ordinary send, when the prompt is empty; with something written, it joins the prompt instead so nothing written is lost. Up in an empty prompt was unclaimed: the composer has no recall of the last message, and the pane's arrow keys belong to its tabs and grips, not the prompt.

**6. Hidden whenever it would not be the user's next move.** Nothing shows while a turn runs, while a request or question card is up, while a prompt is on its way or queued, in an archived or closed thread, in a continuation, in Watcher's composer, or once the user's send is accepted; a refused send brings it back with the draft.

**7. Suggestions answer nothing and grant nothing.** A suggestion is text Sotto offers; only the user's press puts it in the prompt, and only the user's send sends it. An answer chosen from the list is the user's own message, sent from the composer like any other: it is not an answer to a request card, and nothing here answers a permission or a question on the user's behalf ([ADR-0004](0004-authority-in-policy-records.md)). A provider's structured question (Claude Code's AskUserQuestion, Codex's request_user_input) stays with Sotto's question card and its own answers; the list's answers are only for a question the reply asked in prose.

**8. Owl gates it; a setting turns it off.** Main reads the `next-prompt` answer once at start: off, it builds nothing, asks no provider, registers no channel and gives the window no bridge. The window asks `useOwlFeature('next-prompt')`. **Suggest a next prompt after each turn** in Settings > Threads (`nextPromptSuggestions`, on by default) shows only while the Owl feature is on, and is read for every turn, so turning it off stops the next request without a restart.

## Consequences

- `CONTEXT.md` names the **next prompt** and the **Next list**. The design captures do not change: no fixture finishes a turn on this computer, and the design fixture host has no side call.
- Remote hosts are left out. A headless host builds no next prompts, since its threads' suggestions would need a host protocol message to reach this window; that is a later change if it is wanted.
- Each finished turn costs one short request on the thread's provider, counted against the same subscription limits as the thread's own work. The setting says so.
- Sending the feature to stable flips its entry's `sentToStable`.
