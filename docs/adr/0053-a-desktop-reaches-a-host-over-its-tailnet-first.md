# A desktop reaches a host over its tailnet first

## Context

A desktop reaches a remote host only through an SSH port forward (ADR-0025). Every connect is an `ssh` sign-in, and on a tailnet whose policy holds Tailscale SSH in `check` mode, every connect after the check period has lapsed waits for the owner to approve it in a browser. On October 5 forge, the owner's headless host, asked for an approval on every relaunch of Sotto, and a host Sotto started does not come back after its machine restarts until a desktop connects over SSH and starts it.

Since ADR-0050 a host with phone access on already has a second loopback listener that Tailscale Serve carries to the tailnet over HTTPS, with no administrative routes, sharing the host's one pairing store. The desktop is paired with that host already. Everything a connected desktop needs from the socket (threads, commands, provider sign-in, client updates) works over a paired session, and SSH is needed only for what the launch script does: start, stop, update and the host's administrative routes.

The options considered:

1. **Keep SSH for every connection.** Rejected: it is what makes each relaunch ask for approval, and the long-lived forward is the only reason a dropped SSH connection drops the host's threads.
2. **Tailnet only.** Rejected: the first pairing, the `remote-answer` grant, start, stop and update all need the SSH session, and a host whose Serve is off, or whose machine is not on the tailnet, would become unreachable.
3. **Tailnet first, SSH when it does not answer.** Chosen.
4. **Trust Tailscale Serve's identity headers.** Rejected: they name a tailnet user, not a paired client, and ADR-0004 lets nothing but a policy record grant authority.

## Decision

**Names.** The desktop's connection to a host through the host's tailnet address, authenticated by its pairing, is a **tailnet connection**. The path every host has today, an `ssh` sign-in whose port forward carries the socket, is the **SSH connection**; it stays, and carries the socket whenever the tailnet connection is not in use. The host's second loopback listener, which was the phone listener, is the **tailnet listener**: it now carries desktops as well as phones. The address the desktop uses, `https://<MagicDNS name>:<Serve port>`, is the host's **tailnet address**, learned from the host and never typed. An SSH connection opened for administrative presses while the host is on its tailnet connection is an **admin connection**. `CONTEXT.md` has an entry for each.

**What a saved host stores.** `remoteHostSchema` stays as it is: it is strict, and an older Sotto would reset `remote-hosts.json` to an empty list if it met a new key. The new state lives beside it in `remote-host-tailnet.json` in the user data folder, keyed by the saved host's ID: which connection the owner prefers (`tailnet` or `ssh`), the last tailnet address the host reported and when it was seen, and the last start at boot state a launch or a boot operation reported (ADR-0054). A host with no entry prefers SSH, so a host saved before this keeps connecting as it does until the owner chooses otherwise; Add host writes `tailnet` for a new host. The preference changes through a Hosts command, not a setting, and Forget deletes the entry. An older Sotto ignores the file and keeps connecting over SSH.

**How the address is found.** The host records its tailnet address and who started it in its listener descriptor, and reports both in the launch result and in the authenticated hello. The address carries the port Serve actually serves, so the desktop never assumes one. The desktop accepts only an `https:` address on a `*.ts.net` name. Matching the name against this computer's own `tailscale status` is evidence and nothing more. The host's identity is still its TLS certificate, the pairing token, and the session's host ID matching the saved host's.

**The order of a connect.**

1. If the owner prefers the tailnet, an address is known and this computer holds the host's pairing, the desktop opens the host service at the tailnet address: health within 5 seconds, then a session, then the socket. No `ssh` is spawned.
2. A tailnet connection that fails is classed, and the class decides what happens next. Unreachable (DNS, connect, TLS, a timeout, or 502 or 503 from Serve), a host whose ID is not the saved one, and a session refused because the host does not know this client as a desktop go to SSH. A refused pairing (401) goes to SSH, which pairs again over the forward exactly as today. A version mismatch stays final, as today.
3. Over SSH, the connect is today's launch, pairing and desktop grant, and the socket opens over the SSH connection's forward. If the launch reported a tailnet address and the owner prefers the tailnet, the desktop then tries the tailnet; when it answers, the socket moves there and the SSH connection closes, taking the administrative token with it. Otherwise the socket stays on the SSH connection, and the row says so.
4. While on the SSH connection with the tailnet preferred, the desktop tries the tailnet again every 5 minutes and moves across when it answers.
5. A drop, or a move from one connection to the other, marks the host's threads as reconnecting and swaps the connection in place, as a host update already does (ADR-0040). Threads, panes and the selection stay on the page. Forget, switching a host off, and a failure only the owner can fix take its threads away. A final failure (a changed host key, a version mismatch, a Tailscale approval that never came, and the others ADR-0025's typed codes mark final) stops the retries, the threads go, and the host's row says what to do, as ADR-0040 says of an update that cannot reconnect.
6. Retries keep the 3, 4, 8 and 16 second backoff. For a host that starts at boot whose last connection was a tailnet connection, the first 60 seconds of retries try the tailnet only, since the host restarts by itself and an SSH attempt would ask for an approval for nothing. After that each attempt tries the tailnet and then SSH.

**The desktop never pairs on the tailnet.** Its first pairing is always over SSH, at Add host, and the client refuses to redeem a code at any address that is not loopback. The pairing token is the same on both listeners, because the host has one pairing store.

**Admin connections.** A press that needs the launch script or the host's administrative routes uses the SSH connection when the host is on it, and opens nothing new; the token the launch handed back is already in memory for it. When the host is on its tailnet connection, the press opens an admin connection: the **Phones…** dialog for as long as it is open, **Stop host**, Forget's revoke, its stop of a host Sotto started and its removal of a boot unit, **Update** from the press to the restart, **Start at boot** and **Stop starting at boot** (ADR-0054), saving **Edit connection** (which is a test connect), and pairing again after a 401. An admin connection runs the launch script and has no socket on it. It begins with a connect, so a Tailscale approval shows inside the surface that asked for it, "Waiting for your approval in Tailscale" with **Open approval page**. It closes 60 seconds after its last use. The host's administrative token stays in memory for that one SSH connection, as ADR-0050 says. Provider sign-in and client updates go over the socket on either connection; host setup and provider jobs are agent threads that run `ssh` themselves, unchanged.

**Forget.** The host has no socket command that revokes a client, so Forget revokes this desktop's pairing with the launch script's `revoke-client`, over the SSH connection when the host is on it and over an admin connection otherwise, whichever connection carries the socket. The revoke comes before Forget stops the host or removes its boot unit, as today, since the revoke goes through the running host. When SSH cannot reach the host, Forget still removes the host from this desktop, and says plainly that the host still trusts this desktop until it is removed there, with the command to run on the host: `node host/index.js --data <data folder> --revoke-client <client ID>`, the client ID being the one Edit connection showed. Until then the token, its grant and any boot unit stay on the host.

**Authority.** The tailnet adds no grant. The `remote-answer` grant is still written only by the launch script over SSH (ADR-0025, September 29 amendment), and the tailnet listener reads the same policy store, so a desktop's grant, written over SSH, is honoured on its tailnet connection. A tailnet connection never asks for the grant: if hello says the desktop may not answer, the desktop waits and writes the grant at its next SSH or admin connection, and nothing opens SSH silently for it. Tailscale Serve's identity headers are ignored (ADR-0004). What this changes about a stolen token is under Consequences.

**Which clients are desktops.** The host records a client as a desktop only from the launch script, over SSH: at the step that confirms the desktop's paired client ID and writes its default grant, the script adds that ID to `desktop-clients.json` in the host's data folder. Every SSH connect does this, so a desktop paired before this file existed is recorded at its next SSH connect, which always comes before its first tailnet connection, since the tailnet address is learned from a launch. On the tailnet listener a client not in that file is treated as a phone, and an unreadable file counts nobody as a desktop. So a phone paired with the host's own `--pairing-code`, or before `phone-clients.json` existed (ADR-0050's fourth consequence), is a phone here, and a desktop the host does not know falls back to SSH, whose launch records it. `phone-clients.json` stays what the Phones dialog lists. This is a client kind, which ADR-0037 rejected because a client named itself and earlier pairings carried none; here the kind is written by the SSH account's own session, never by the client, and earlier pairings gain it at their next SSH connect. The desktop never redeems a code on the tailnet listener, so it never enters the phones list. The host refuses pairing on the tailnet listener while phone access is off, and while phone access is off and the listener is up for desktops, it refuses a session to every client that is not a desktop.

**The host side.** A new host-local setting, `tailnetConnections`, off by default, is set through a new administrative route over an SSH or admin connection. Serve runs while phone access or tailnet connections is on, so turning phones off no longer cuts desktops off. Adding a host, and choosing "Over your tailnet" in Edit connection, turn it on, and those presses are the owner's consent to that Serve setting on the host: each says so in one sentence before it is pressed. Saving "SSH only" in Edit connection turns it off over the admin connection the save opens, and the host turns it off itself when the last client in `desktop-clients.json` is revoked, so Forget's revoke leaves no Serve setting behind for desktops. The setting is the host's, so on a host two desktops share, "SSH only" on one moves the other to SSH too. The listener with the administrative routes is still never served to the tailnet.

**What the protocol gains.** Health on the tailnet listener lists every feature the listener offers. Hello lists the ones this client may use: a desktop gets provider sign-in and client updates, a phone today's list, and the handlers check the peer, not the listener. So on the tailnet listener a client uses a feature only when its hello lists it, which narrows `docs/host-protocol.md`'s rule that a client reads health first and uses what the host lists. Hello also reports `tailnetAddress` and `startedBy`, and to a desktop the host's phone access as the row words it (off, starting, on with how many phones are paired, or needs you), as it stood when the session opened. The launch result reports `tailnetAddress`, `startedBy` and the start at boot state. Every addition is an optional field, so `v` stays 1. Each listener gets its own observation key, the two share one command receipt map so a retried command survives a move between connections, and tailnet peers count as connected.

**What the owner sees (the delegated picks).**

- **Variant C with A's controls.** Add host's checklist gains a step after Paired, "Reach forge over your tailnet", and its connected card offers **Start forge's host at boot**, one consented press (ADR-0054). The row, Edit connection and the More menu are variant A's. A host saved before this is not announced: the owner moves it to the tailnet by choosing "Over your tailnet" in its Edit connection, and finds **Start at boot…** in its More menu. Variant C's one-time line above the list was dropped because nothing in Sotto announces itself unasked.
- **The row's meta line** begins with how the host is connected: `Tailnet · Connected · 2 providers · Phones on`; `SSH forge · Connected · Tailnet did not answer`, with "Sotto tries it again every 5 minutes." under it; `SSH forge · Connected` when the owner chose SSH; `Connecting over your tailnet…` and then `Connecting over SSH…` while connecting. Reconnecting, off and error lines are unchanged. On a tailnet connection the Phones words come from hello and the Phones dialog's reads; on the SSH connection they are read as ADR-0050 says. The More menu's Start at boot item follows the last start at boot state the desktop was given, and its modal reads the state again over its admin connection before it changes anything.
- **Edit connection** gains a radio group, **How Sotto connects**: "Over your tailnet, SSH when it can't" and "SSH only", above the SSH fields, which become a fieldset "SSH (for setup, updates and phones)". The tailnet choice says that Sotto turns on Tailscale Serve on the host for it, on the tailnet only.
- **The Phones dialog** shows the admin connection's approval at its top while that connection waits, and shows its switch, checks and phones as not yet read until it has read them.
- **The tailnet connection is the default for a new host.** Add host writes it; an existing host keeps SSH until the owner chooses the tailnet.

Each surface is checked at 1600×1000, 1280×800 and 820×560, in light and dark and with reduced motion. The radios move with the arrow keys, each dialog answers Escape, and focus goes back to the control that opened it.

**Privacy.** No new host is contacted. The tailnet address is the same machine, reached over the owner's own tailnet through a Tailscale Serve setting that Sotto owns on the host and turns on only with the owner's press, and Funnel is never used. Adding a host now turns that setting on by default, which changes ADR-0050's rule that Tailscale's CLI runs on a host only once phone access is turned on there. A desktop's pairing token, which carries its `remote-answer` grant, now works from any device on the owner's tailnet (Consequences). The README's "Privacy and cost" section says both when the connection ships, and its line that a desktop "connected through your SSH account" can answer changes to say the grant is written over SSH and honoured on the tailnet.

## Consequences

- A stolen desktop pairing token now works from any device on the owner's tailnet, not only through an SSH session, and it carries that desktop's `remote-answer` grant: whoever holds it can answer permission requests and set permissive thread modes on the host, where a stolen phone token can do that only once the owner has turned on its Can answer. The grant was justified by the authenticated SSH session (ADR-0025, September 29 amendment; ADR-0004's September 29 note); it is still written only there, but is no longer used only there. The token still ends only when it is revoked, as today: Forget revokes it over SSH, and when SSH cannot reach the host, Forget says so and the owner revokes it with the host's own `--revoke-client`.
- A relaunch, a reconnect and a dropped connection need no SSH and no Tailscale approval while the tailnet answers. A press that changes something on the host still asks, because it opens an admin connection.
- Adding a host turns on a Tailscale Serve setting on it, where before only turning on phone access did.
- The 32-peer cap and the pacing on the tailnet listener are shared by phones and desktops.
- On Linux, Serve needs the SSH account to be Tailscale's operator. Until it is, the desktop stays on SSH and the row says why, with `sudo tailscale set --operator=$USER` for the owner to run there. Sotto never runs it.
- Real TLS and MagicDNS cannot run in CI. The tests stand a loopback proxy in front of the host's tailnet listener, and only a check on a real host, recorded in `docs/verification/`, proves the certificate path.
- `docs/host-protocol.md` changes with the host side: the tailnet listener carries desktops, hello reports `tailnetAddress`, `startedBy` and a desktop's phone access, and features are per client.
