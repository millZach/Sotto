# An older host is updated from the Threads page

October 9, 2026 amendment: [ADR-0068](0068-remove-voice-control-and-thread-management.md) records the removal. The voice gate described below has been removed. Update remains an explicit user action, with the same host restart, busy-work and recovery rules.

## Status

Accepted September 29, 2026, for issue #475. The design is variant C, pill and panel, of `prototype/host-update` (commit 50b86b40), picked by the owner on September 29; the behaviour choices recorded on the issue with that pick stand. Builds on [ADR-0025](0025-headless-host-and-client-identity.md) (the headless host, the launch script, Stop host) and [ADR-0035](0035-an-agent-can-set-up-a-host-from-add-host.md) with its amendment recorded on #207 (the host downloads the archive from the releases page; this computer copies it over SSH when the host cannot reach GitHub). ## October 5 amendment: a host that starts at boot, and drops that keep the threads

[ADR-0054](0054-a-host-can-start-at-boot-on-linux.md), accepted October 5, 2026 under the owner's delegation, lets a Linux host start at boot from a systemd user unit. For such a host, `update-restart` points `current` at the new version and restarts the unit rather than stopping the host and starting a detached one, and a rollback points `current` back and restarts the unit again. The unit's script resolves `current` the way the launch script does, and an update rewrites the script when the new version needs a different Node. A host its unit started records `startedBy: "boot"` and counts as one Sotto started, so "A host Sotto did not start" below does not apply to it. Installing and removing the unit restart a host Sotto started (removing it from a host that is switched off only stops it), and both ask the busy-host question below first. When the host is on its tailnet connection, the update's operations run in an admin connection ([ADR-0053](0053-a-desktop-reaches-a-host-over-its-tailnet-first.md)).

ADR-0053, accepted the same day, takes the separate decision the third consequence below leaves open: a dropped connection, and a move between the tailnet and SSH, keep the host's threads as reconnecting, the way an update's restart does. "During the restart the threads stay" now describes every reconnect, and its rule that the threads go when only the user can fix why is the rule for all of them.

## Context

A host outlives updates to this computer. On September 29 the desktop was on 0.1.24 and forge's host on 0.1.22. Connecting used whatever host was already running, the launch script only ever started `<installation folder>/host/index.js`, and a version difference was noticed only when the protocol changed (`version_mismatch`). None of 0.1.23's and 0.1.24's host changes reached forge until it was updated by hand: the checksum checked, the old files backed up, the new ones unpacked over the flat folder, the old host sent SIGTERM (it saves its workspace and exits in about a second), and the desktop reconnected and started the new one by itself. This ADR is that, done by Sotto when the user asks.

## Decision

**Which hosts need an update.** A saved host that is connected, or whose SSH session is kept open for Stop host after a version mismatch, has said which Sotto it runs, in its health and its hello. It needs an update when that version is earlier than this computer's (`hostIsOlder`, by release number). A newer host is left alone, since stopping it would not help, and a host that says nothing, or something that is not a release number, is never offered one.

**Where it shows: a pill beside the window controls.** On the Threads page a small pill sits in the top strip just left of the window controls (at the top right on a Mac, whose window controls sit at the left): "Update for forge", "Updates for 2 hosts", "forge waits to update", "Updating forge · 2 of 4", "forge not updated", "forge updated". It comes before the thread panes in keyboard order and opts out of window dragging; the pane header under it stops short of it with a margin, because a drag region later in the page would otherwise cover it. When two panes stand side by side, or the window is narrower than 1100 pixels, the pill keeps only its mark, with its words as its accessible name and tooltip, so the last pane's title keeps its room. Pressing it opens a panel, "Hosts running an older Sotto", with a section for each host: its name, where it stands ("0.1.22 → 0.1.24", "Step 2 of 4", "Still 0.1.22"), what a press does, and its own buttons. Escape or a click outside closes it. Terminal mode does not show the pill; nothing about the update changes while it is hidden.

**Only the user starts one, one host at a time.** Nothing updates on its own. **Update forge** starts that host's update, and there is no Update all. **Not now** hides that host's update until Sotto next starts; the choice lives in memory, whatever reconnects in the meantime.

**A busy host asks first.** A host is busy while one of its threads has a turn running, is compacting its context, or has background work its turn started, since a restart stops all of them. Update then says "2 threads on forge are working. Updating restarts forge's host, which stops them." and "Only the work in progress on those turns is lost. Drafts and history stay.", with **Update when they finish**, **Stop 2 threads and update** and **Cancel**. Waiting reads "forge updates when its threads finish. 1 still working." with **Stop 1 thread and update now** and **Cancel update**, and starts the update the moment none of the host's threads is working. Stop sends each working thread the interrupt the composer's Stop sends, so a stopped turn reads Stopped in its transcript the way any stopped turn does. The prototype's "Stopped for forge's host update" is not written: the interrupt carries no reason, protocol version 1 is frozen, and the host being stopped is the older one, which could not carry a new field anyway. A line only this computer draws, from the IDs of the turns it stopped, was turned down too: it would be a new kind of transcript entry that no other client sees and that is gone after a restart, where the owner's choice was a line in the transcript itself. Whether the plain Stopped is enough is the owner's to decide. Escape on the question answers it as Cancel does.

**The steps.** The panel lists four, each with what it does now: **Download 0.1.24** ("From Sotto's releases on GitHub.", or "forge could not reach GitHub, so this computer is copying it over SSH."), **Check the download** ("Its checksum has to match the release's."), **Install beside 0.1.22** ("0.1.22 stays in place until 0.1.24 is running.") and **Restart forge's host** ("forge's threads are unavailable for a few seconds."). **Cancel update** is there during the first two and not after: unpacking and the restart are not stopped partway. Each step is an operation of the launch script over the host's own SSH connection, run under an update lock in the installation folder so two clients never update one host at once:

- `update-fetch`: the host downloads `Sotto-host-<version>-<platform>-<arch>.tar.gz` for its own platform and its `.sha256` sidecar from `https://github.com/millZach/Sotto-releases/releases/download/v<version>/`, with Node's own `fetch`, and checks one against the other. A download that does not match is deleted and nothing is installed.
- When the host cannot reach the page (no route, a failed download), this computer downloads the same two files in main and copies the archive over SSH, which the panel shows as the download, then checks it against the sidecar, which it shows as the check: the receive script runs as `node -e` through the same Node probe, so its stdin is free for the archive, and writes exactly the bytes it expects into the installation folder. A release with no archive for the host's platform, or a checksum that does not match, is not retried this way.
- `update-install`: the host checks the archive again against the checksum it is given, unpacks it with `tar` into its own version folder beside the running one, and refuses it unless its `package.json` names the version asked for, it has `host/index.js`, and the host's Node satisfies its runtime manifest.
- `update-restart`: the host points `current` at the new version, stops the running host the way Stop host does (SIGTERM, 15 seconds to save and exit, then a kill), and starts the new one as a launch does. When the new one does not start, `current` goes back to the old version and the old host is started again. The restart carries on if this computer's connection drops partway, so a host it stopped is always started again.

The checksum guards the transfer, not the publisher: the archive and its sidecar come from the same release over HTTPS, so trusting the update is trusting that release, as installing by hand from the releases page does.

**Install layout.** The installation folder holds versions side by side, each under `versions/<X.Y.Z>/`, and a `current` file naming the one to start, as the owner chose on the issue. `current` is a one-line file, not a symbolic link, so replacing it is one atomic rename on every system the tests run on, and the launch script never follows a link out of the folder; a value that is not a release number, or names a version that is not there, is ignored. A folder without `current`, the flat install every host had before this, starts its own `host/index.js` exactly as before, so nothing already installed changes until its first update. The Node check reads the runtime manifest of the version `current` names. After a successful restart the running version and the one before it are kept, and every other version folder is deleted; a flat install's files are never deleted by Sotto. #207's plan named `~/.sotto/runtime/versions/<version>/` for an installed runtime; when it lands it installs into this layout under the installation folder instead, so there is one place a host's versions live.

**During the restart the threads stay.** The host's threads keep their place on the Threads page, with their panes and the selection, and read Reconnecting rather than Disconnected; the composer keeps the draft and says "Its host is restarting after an update. Your draft stays here." Once this computer has connected to the new host, the new connection takes the old one's place in the router, and the same threads, under the same Sotto thread IDs, carry on. If it cannot connect again and only the user can fix why, the threads go and the host's row in Settings → Hosts says what to do, as for any failed connection. Disconnect, Stop host, Forget, Edit connection and the switch are refused, with a sentence, while an update is under way.

**Done and failed.** Done says "forge runs Sotto 0.1.24." with **Dismiss**, and goes by itself after 8 seconds, but not while the pointer is over it or a control in it has focus. A failure says what happened, what the host runs now and that nothing was lost ("forge still runs 0.1.22. Nothing was lost.", or "forge's threads are back. Nothing was lost." when the old version had to be started again), and what to do, with **Try again**, **Copy commands**, **Show commands** and **Not now**. The commands are the ones that update the host by hand, for its own folders: download, check, unpack into `versions/<X.Y.Z>`, write `current`, then Stop host and switch it on again. When the new version would not start, they are instead the commands that run it by hand to see what it says. Sotto never runs them.

**A host Sotto did not start.** Sotto never stops a host it did not start (ADR-0025), so it cannot restart one to update it. Its section says so ("Sotto did not start this host, so it cannot restart it. Update it on forge with these commands.") and offers the commands, whose last step is to stop that host and connect again, when Sotto starts the new version itself. There is no Update for it. A host that stops being Sotto's between the install and the restart is left running, with the new version installed beside it, and the failure says what to do.

**Outside the voice gate.** Update is a button the user presses. Nothing speaks, listens or manages a thread, so it sits outside `voiceCoordinatorEnabled` (ADR-0012).

**Privacy.** The host contacts the releases page, `github.com`, which serves the files from `release-assets.githubusercontent.com`, only when the user presses Update. When the host cannot, this computer downloads the same files from the same places and copies them over the SSH connection the user already set up. Nothing about the user, the host or its threads is sent. The README's "Privacy and cost" names both.

## Consequences

- The launch script has three more operations and a second, small script; `LAUNCH_SCRIPT_SOURCE` still travels on stdin and is never an argument. The receive script is an argument, since the archive needs stdin, and holds nothing secret.
- A stale listener descriptor whose process has gone now reads as no host at all, without a health request. A host an update has just stopped may not refuse a connection to its old port cleanly for a moment, and without this the new version's start was refused as `port-taken`.
- The router can swap a host's connection in place (`replace`) and mark a host's threads as reconnecting (`clientReconnecting`), which only a host update sets today. A dropped connection still takes a host's threads away until it reconnects; giving drops the same treatment is a separate decision.
- Stop N threads and update loses the work in progress on those turns; the panel says how many before the press.
- When #207 lets the desktop install a host on first connect, it reuses these operations and this layout, and the brief for an agent's host setup can say so.
