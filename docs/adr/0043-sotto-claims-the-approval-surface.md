# Sotto claims the approval surface

Accepted September 21, 2026. Claude Code threads stopped asking. Approvals never reached the user and questions never appeared; a thread would write its question into its reply and carry on working. Both came from one place. The adapter launched the CLI with `--permission-mode <mode> --permission-prompts host` and nothing else, and in Claude Code 2.1.278 `--permission-prompts host` only says prompts are not force-denied. The flag that makes a process the thing that answers them is `--permission-prompt-tool stdio`, which is what the native SDK passes whenever a `canUseTool` callback exists. Without it the CLI has no approval surface: it answers every prompt that needed a person with its own denial, and it drops `AskUserQuestion` from the session's tool list, so the model has no structured way to ask. A live probe of the adapter's exact launch, with and without the flag, is the whole of the evidence — one produced a `can_use_tool` control request and the question tool, the other produced neither, in both `default` and `auto` permission modes.

**Sotto names itself the approval surface at launch, in every runtime mode.** Including `full-access`. `bypassPermissions` prompts for very little, but what it does prompt for is still the user's to answer, and a mode that quietly answered for the user would contradict ADR-0004 at the transport instead of in the policy store. All four modes were checked against the installed client: each launches with the flag and each offers `AskUserQuestion`, so claiming the surface everywhere raises no false alarm anywhere. The two permission flags travel together from now on; the fake CLI in `tests/fixtures/fakeClaudeThread.mjs` refuses to start a coding thread without both, because the real client's way of objecting is to keep working.

**A refused surface is said out loud, not worked around.** The CLI reports no other sign of it, so the adapter reads the starting session's tool list: no `AskUserQuestion` means nothing can reach the user, and the provider carries a plain-words error saying so and naming the fix. Sotto considered failing the connection outright. That is the stricter reading of ADR-0004, but it turns a future rename of one tool into a provider nobody can open, and the thread is still worth reading and stopping even when it cannot ask. It also considered flipping the snapshot's `questions` and `permissions` capabilities to false, which hides the request cards and so hides the problem. Saying it once per connection, next to the threads it affects, is the version the user can act on.

**A request for the user that an adapter cannot read is the same failure, and is reported the same way — in all three adapters.** Claude Code included: `can_use_tool` is the CLI asking for the user, and one whose payload `claudePending` cannot read has to be denied, which Claude then reads as the user's own answer. That path used to deny in silence. Codex and Grok were probed and are healthy — Grok's `session/request_permission` and `_x.ai/ask_user_question` arrive and map correctly on 1.0.40, and every approval method Sotto listens for is present in the Codex 0.155.1 app-server. But both adapters answered an unrecognised request with a bare JSON-RPC `-32601` that nobody saw, and both providers read that refusal as the user declining. A renamed or reshaped approval would therefore have looked exactly like the Claude bug. `needsPerson` in `src/main/agents/nativeRequests.ts` recognises the shape of a request only a person can answer from its method name, deliberately not its payload, because the payload is the part that changes. On a known thread, such a request that the adapter could not map now surfaces an error as well as the refusal. Requests Sotto is never meant to answer, like `currentTime/read`, and requests about sessions that are not Sotto's, stay silent. So does a thread already holding more unanswered requests than Sotto will track, because denying a flood is a defence rather than a thing Sotto failed to read.

**The message never says which side is behind.** A renamed method means the client is ahead of Sotto; a dropped field means Sotto is ahead of the client; the frame does not say which. So the wording says what happened, that nothing else was lost, and to answer in the provider's own app meanwhile and check both for an update. An earlier draft said "update the client", which for a rename sends the user to make it worse.

**These messages are said again if something buries them.** One provider error field carries them, and an ordinary failed turn overwrites it. A first version latched, so a turn error could permanently bury the warning added to stop exactly this silence. The message is now re-asserted whenever it is not the error showing.

Codex's end-to-end approval path could not be exercised: the account's usage limit was reached, so the evidence there is the installed app-server's method names and the adapter's existing confirmation that `thread/start` returns the approval policy it was asked for.

## Amended 2026-11-06 (#657): the mode Claude Code reports is checked against the mode Sotto shows

Claiming the surface is not enough if the CLI runs in another permission mode than the one it was launched with. Something between Sotto and Claude Code can change it unseen: a wrapper script named `claude` earlier on PATH, which Sotto's client lookup finds first (ADR-0036), or Claude Code's managed settings. One such wrapper on a Linux desktop rewrote `--permission-mode auto` to `bypassPermissions`, so a thread showing Auto ran with every check bypassed. The mode the user picked is the policy (ADR-0004); the mode the CLI reports is evidence, and it has to agree.

**Each turn's `system`/`init` frame is compared with the mode this CLI should run.** That is the mode it was launched with, moved by every change Sotto made and Claude Code confirmed; while a change is still waiting on its answer, the mode it asked for is accepted too. Claude Code's modes are ranked by how much a session does without asking, strictest first: `plan` (runs nothing), `dontAsk` (turns down what is not already allowed and asks nobody), `default` (its other name is `manual`), `acceptEdits`, `auto` (Claude Code's own classifier allows commands too), `bypassPermissions`. `auto` sits above `acceptEdits` because it allows commands as well as edits, and below `bypassPermissions` because its classifier can still refuse. A mode Sotto cannot rank is one it cannot vouch for, so it counts as looser. A frame that names no mode says nothing either way.

**Looser stops the turn as soon as Claude Code reports it.** The init frame comes before the model's first reply, so the CLI is ended there at once: an interrupt, the end of its input, then a kill of its whole process tree (its process group off Windows, where it is started as a group's leader, and `taskkill /T` on Windows), so a CLI that a wrapper runs without `exec` ends too. That narrows the window but does not close it. The CLI keeps running after it writes the frame, so it can act before Sotto reads it, and whatever ran as it started, its startup hooks or a wrapper's own work, ran before the frame existed. A process a wrapper moved out of the tree, with `setsid` for one, is not reached by the kill at all. So the words say only what Sotto knows: Claude Code started in a looser mode than the thread shows, Sotto stopped it as soon as it reported its mode, before its first reply, so the model chose no tool for this message; anything Claude Code, its hooks or a wrapper did as it started may have run, so check the project; what may have caused it; and to fix that and send again. They never say nothing ran. If the tree cannot be seen gone, the words say Claude Code may still be running and to end its process, then check the project. The turn fails once the halt settles, whether or not it was confirmed, and does not wait for the CLI to close, since one that outlived its kill may never close; the next start still waits for that close, so a second CLI never runs beside it. A `/compact` stopped this way fails the same way, so the next send is not held behind it. Background work an earlier message started ends with the CLI, and the words name it and say to ask Claude to start it again, as ADR-0023's stops do. The thread keeps showing the mode the user chose. Sotto considered running the turn on and switching the mode back with a control request, but that trusts the same CLI that already ignored the launch flag, and anything it did before the switch would have run under a mode the user never chose.

**Stricter carries on, with one note.** A CLI that asks or refuses more than the user chose takes nothing from them, so the turn goes on and the thread gets one line saying Claude Code runs a stricter mode and may ask or refuse more. It is said once per CLI, not on every turn. Claude Code may also land there itself, as a session that enters `plan` does.

The check is in `src/main/agents/providers/claude/claudePermissionMode.ts` and `ClaudeStreamJsonHost.checkPermissionMode`; `tests/integration/claudePermissionModeDrift.test.ts` drives both directions through the fake CLI.
