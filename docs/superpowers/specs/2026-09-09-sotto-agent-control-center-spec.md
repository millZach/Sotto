## Problem Statement

Builders use several agent threads to work on projects, but they must continually return to each application to create projects, choose models, submit prompts, answer questions, and check progress. Ordinary dictation removes typing without managing that coordination. When several agents need attention together, the user must discover which thread needs what and ensure each answer goes to the right place.

Sotto currently provides local desktop dictation, a global shortcut, a floating widget, local history, and optional transcript formatting. The user wants to extend that experience into a voice control center for agents across harnesses and environments. They want to keep using the applications and provider accounts they already have, retain visible conversations and manual control, and delegate routine supervision without delegating decisions that require their judgment.

## Solution

Add a paid desktop agent-control mode alongside free local dictation. Saying "Hey Sotto" starts a spoken interaction. Sotto can create a project in an explicit location or configured projects directory, open a real thread in an existing application with the configured or requested model, collect a prompt, and submit it when the user says "send it."

T3 Code running locally is the first plugin. Its projects and conversations remain visible in T3. Sotto manages assigned threads, answers routine questions within the user's assignment, and asks agents to correct work they are responsible for fixing. Decisions requiring human attention and threads ready for another prompt enter a single queue. Sotto identifies one project and thread, lets the user respond, and then presents the next ready thread while other agents continue working.

Use a compact, expandable version of the existing floating widget for the transcript, active target, ready queue, and control state. Sotto speaks concise acknowledgments and questions. Directly sending a message in T3 transfers that thread to clearly indicated manual control; monitoring continues, and automatic replies resume only after an explicit request.

The Sotto subscription pays for voice controls, plugins, and supervision. Users bring supported provider subscriptions or API accounts. The first paid release does not bundle model usage. Support for other harnesses, remote environments, messaging escalation, and a public plugin SDK follows later.

## Implementation Decisions

- **Product boundary.** Sotto owns spoken interaction, assignments, supervision decisions, and the ready queue. Plugins connect those capabilities to existing applications. The host application owns agent execution and its native conversation state. T3 Code on the local machine is the first plugin; the architecture retains environment identity for future integrations.
- **Existing application structure.** Extend the existing Electron main/preload/renderer separation, typed and validated IPC contracts, production controller composition, and widget synchronization. Privileged app connections, credentials, and durable coordination belong behind the trusted native boundary. Keep renderer access narrow and validate both request shape and sender authority. Do not move native privileges into the renderer.
- **Terminology.** Keep dictation and its speech Model presets distinct from Agent models selected for T3 threads. An assignment is the user's delegated work on an identified thread. Managed means Sotto may send authorized automatic replies. Manual control means Sotto monitors that thread while the user controls replies. A pending question or permission request is a separate condition from whether a thread is managed.
- **Voice and dictation.** Local wake detection and local transcription are the initial approach. Agent control has an explicit listening state and spoken output. Preserve the established shortcut-driven dictation behavior. Cloud reasoning and spoken replies are allowed through configured connections after activation; background wake listening must not require uploading room audio. Prevent generated speech from triggering another command. Provide usable microphone and speech-stop controls and respect existing appearance and accessibility preferences.
- **Prompt composition.** A composed prompt stays attached to a specific environment, application, project, and thread. Long pauses do not submit it. "Send it" and a deliberate equivalent UI action submit the prompt. Keep composition visible and editable. Retain it across recoverable failures. Short action requests such as opening a named project do not require entering the long-prompt composition flow.
- **Project directories.** Support an explicit path or a configured default projects directory and create the project folder there. Validate the target, explain unavailable locations, and obtain a choice for existing-folder conflicts rather than overwriting work. Create the corresponding real project in T3. Resolve ambiguous names before issuing a mutation.
- **Agent model selection.** Use the configured default unless the user asks for another available provider or model. Discover provider readiness and model choices from the connected environment. Preserve that distinction when a shorthand name is ambiguous. Identify the resulting choice to the user and never silently substitute another provider or funding route.
- **Plugin boundary.** Use one coherent application-facing command/event contract for discovery, project and thread selection or creation, prompt submission, state observation, question and permission responses, and supported interruption. Include stable target identities, correlation identifiers, origin information where available, and explicit outcomes. Normalize provider-specific behavior inside the host/plugin boundary instead of exposing it throughout the queue and UI.
- **Capabilities.** Advertise discovery, creation, submission, progress, clarification, approvals, interruption, direct-user-message detection, and reconciliation as separate capabilities. Limited plugins are permitted when their restrictions are clear. Full supervision requires reliable status and response handling. The first T3 plugin must demonstrate the complete accepted journey, including manual control; it is not sufficient to expose a prompt-launching shortcut.
- **T3 integration gate.** Use T3's authenticated shared application state so that Sotto operates the projects and threads visible in T3. Source inspection found the necessary categories of internal commands and events, but no stable third-party API guarantee or tested Sotto connection. First prove authenticated connection, folder/project/thread creation, visible-thread access, available-model selection, prompt submission, questions, and message origin against an identified installed version. Record compatible versions and surface incompatibility. Do not silently substitute an invisible side session for the required existing-app experience.
- **Assigned-thread supervision.** Supervise threads explicitly assigned by the user. Carry the assignment, user instructions, established preferences, and already granted authorization forward. Handle routine directional questions and ask the agent to fix defects it is responsible for resolving within that assignment. Bring human decisions to the user. Do not create new assignments after completion, answer unassigned conversations, or override host permissions.
- **Human decision boundary.** Unclear requirements, new scope, publishing, external messages, and additional spending need user involvement unless already authorized. An unanswered or skipped request is still unanswered. Present the task and relevant request clearly enough for a decision. Agent-reported completion and actual evidence of completed checks must remain distinguishable.
- **Follow-up limits.** Start with a configurable limit of five automatic follow-ups per assignment and pause earlier when the same failure repeats without progress. At the limit, stop new automatic replies and ask before continuing. Preserve the thread, monitoring, and any work already running. Define and display the counter consistently across the supported kinds of automatic follow-up; reconnecting must not reset it as a side effect.
- **Ready queue.** Queue assigned threads that need human input or are ready for review or another prompt. Present one thread at a time, identifying its project and thread. Use arrival order by default with a stable tie-break for simultaneous events. The user may defer an item, advance, or select a named thread. The current composed response retains its target while other ready events arrive. After a reply is accepted, the receiving agent can work while the next queued item is presented.
- **Queue controls.** "Later" defers an item without answering it. "Next" presents the next ready item and preserves unresolved requests. A named selection changes the active target only after ambiguity is resolved. Queue focus alone grants no permission. Coalesce repeated notifications for the same outstanding request so that replayed or duplicate events do not produce duplicate spoken briefings.
- **Manual takeover.** A message sent directly by the user in an assigned T3 thread changes that thread to Manual control. Stop subsequent automatic replies there, retain monitoring, and leave existing agent work running. Other threads remain managed. Reading, selecting, or scrolling does not transfer control. Replies submitted through Sotto remain managed interactions. Resuming requires a voice command or Resume management button; leaving the T3 window is insufficient. Recheck control ownership before dispatching an automatic reply so that a takeover cannot race a queued send.
- **Required manual-control copy.** Show a prominent notice naming the thread: "You're replying directly in T3. Sotto is still watching this thread, but won't send replies. Say 'resume managing Workshop' or select Resume management to hand it back." Replace Workshop with the actual target. Announce the transition once: "You're controlling Workshop. I'll keep watching. Say 'resume managing Workshop' when you want me to take over again." Keep the visible Manual control state until management explicitly resumes.
- **Recovery and persistence.** Persist the information needed to recover assignments, control ownership, pending requests, queue targets, configuration, and follow-up limits. Reconcile with the host on reconnect before issuing commands. A lost acknowledgment must not cause an automatic duplicate folder, project, thread, or prompt. Preserve correlation and distinguish attempted, accepted, failed, and unresolved actions. Respect local history and privacy settings; define bounded retention for any additional assignment context instead of silently broadening dictation history collection.
- **Reasoning and speech connections.** Keep provider connections replaceable so that Sotto's supervisor and spoken replies can use an eligible supported route without coupling them to T3's coding provider. One provider may fill several roles. Implement and validate an initial supported combination as part of the voice proof. Prefer supported existing subscription access where available, and offer explicitly configured API access. Do not treat access to a native app as permission to reuse its credentials with arbitrary endpoints.
- **Credentials and membership.** Keep host-owned authentication with the host when the supported connection allows it. Introduce OS-backed storage for credentials Sotto must hold and migrate the existing optional formatting credential through a controlled path. Keep Sotto membership separate from provider credentials and usage accounts. The paid entitlement grants Sotto features; it does not promise included agent usage.
- **Paid account implementation.** Provide Sotto sign-in, hosted checkout, server-validated billing changes, and cached desktop entitlement state. Show connection roles, known billing sources, entitlement state, and recovery actions. Validate renewal and cancellation. Free dictation remains account-free and works when membership services are unavailable. Ending a Sotto entitlement must not abruptly cancel independent work already running inside T3. Select the billing service, price, and entitlement validity policy after the private beta establishes operating and support costs.
- **Platform and distribution.** Preserve the existing Windows x64 and Apple silicon macOS support. Begin the live integration proof in the available Windows environment, then verify the supported Mac experience. Respect the accepted macOS distribution ADR: arm64, ad-hoc signing, DMG distribution, existing microphone/Automation/Accessibility handling, and no implied migration to notarization, Intel builds, or a macOS updater as part of this feature. Preserve current Windows update behavior.
- **Delivery order.** First prove T3 compatibility and the wake/speech loop. Then complete the single-thread journey, add supervision and multiple-thread queue behavior, verify recovery and manual control, and introduce production paid access after the private beta. Validate a second harness before publishing a plugin SDK. These are implementation gates within the work, not evidence that the feature already exists.

## Testing Decisions

- **Primary seam, confirmed by the owner.** Extend the existing Electron end-to-end harness as the main application-level entry point. Exercise the real main process, preload/IPC boundary, renderer, widget, and production orchestration. Supply controlled speech input, host events, reasoning results, speech-output responses, and membership outcomes at external adapter boundaries through the existing test composition approach. Keep one coherent harness rather than adding test-only access to every new internal module.
- **What makes a good test.** Assert externally visible behavior and effects: the displayed/spoken target, prompt contents and destination, accepted host commands, preserved pending questions, visible control ownership, user-facing failures, and recovery results. Avoid assertions about private queue representations, helper calls, component wiring, or a model's hidden reasoning. A successful fake-provider run is not evidence of real provider compatibility or audio quality.
- **Modules covered through the primary seam.** Cover voice-session coordination, prompt composition, project/thread routing, assignments, supervision limits, the ready queue, manual ownership, connection state, and widget presentation together through user actions and external events. Extend existing IPC/security integration tests only where new privileged contracts add distinct validation or sender-authority requirements. Avoid creating separate seams solely to test implementation details.
- **Existing prior art.** Reuse the repository's Electron onboarding-to-dictation/paste/history journeys, registered-hotkey scenarios, deterministic production-controller factories, trusted native test bridge, widget synchronization coverage, renderer-loss recovery cases, and design-capture workflow. The current harness uses owned temporary profiles and is excluded from packaged builds; retain those properties. Existing clipboard-before-paste, history-disabled, hotkey-conflict, microphone-denial, silence, paste-failure, theme reload, and recovery behavior form the regression baseline.
- **Voice composition scenarios.** Exercise wake activation, visible listening state, speech acknowledgement, transcription corrections, a long pause without submission, explicit send, a deliberate cancel or mute action, denied microphone access, and unavailable speech service. Verify that ordinary dictation still follows its established path and that background listening does not emit cloud requests carrying room audio.
- **Project and model scenarios.** Create a folder and corresponding T3 project using the default directory and an explicit location. Cover existing-folder conflicts, invalid locations, ambiguous names, existing-project selection, configured agent-model defaults, an explicit override, unavailable models, unavailable provider access, and preservation of the request without silent substitutions.
- **Three-thread queue scenario.** Assign three threads and emit overlapping completion and human-input events. Verify one spoken briefing at a time, correct project/thread identification, preserved input while another event arrives, submission to the intended thread, and advancement while the prior agent works. Exercise later, next, and named selection. Replay a readiness event and confirm that it does not create a duplicate queue item or briefing. Skipping a permission request must produce no approval.
- **Supervision scenarios.** Supply an agent-responsibility failure and verify an in-scope automatic follow-up; supply a human decision and verify that Sotto waits. Exercise prior authorization, an unassigned thread, an agent-reported completion with insufficient evidence, a completed assignment with no new scope, the fifth follow-up boundary, and repeated failure without progress. Confirm that a paused supervisor leaves the host's already running work intact.
- **Manual takeover scenarios.** Send a direct user message through the host boundary and verify Manual control, the one-time spoken notice, continued monitoring, and no subsequent automatic reply for that thread. Confirm that another assigned thread remains managed, reading/selecting does not transfer ownership, and Sotto-origin submissions do not trigger takeover. Exercise voice and button resumption. Race a direct user submission against a planned automatic follow-up and verify ownership is checked before sending.
- **Recovery scenarios.** Disconnect before an acknowledgment, reconnect with the host's authoritative result, and verify no duplicate project, thread, or prompt. Exercise missing and repeated events, unknown outcomes, renderer loss, application restart, preserved manual control, retained pending requests, and preserved follow-up counters. Assert an honest unresolved state when reconciliation cannot establish the outcome.
- **Accounts and entitlement scenarios.** Use controlled membership and provider responses to cover supported subscription access, API access, role/billing-source display, missing credentials, expired access, allowance exhaustion, renewal, cancellation, and a membership-service outage. Verify no silent account/funding switch, no abrupt host-task cancellation, and continued free dictation. Exercise the credential migration without exposing credential contents in visible state or diagnostics.
- **Focused live compatibility checks.** Run a small test with an actual compatible T3 installation and real project/thread state to verify authenticated connection, filesystem/project creation, available model selection, visible conversation access, question response, direct-user-message origin, and reconnect behavior. Keep this separate from deterministic regression tests so network access, account availability, and provider charges are explicit. Documentation inspection alone cannot satisfy it.
- **Real voice and visual inspection.** Test an actual microphone and speakers, representative pauses and interruptions, background sound, and Sotto speaking its own name. Measure wake accuracy, false activations, conversational latency, and speech intelligibility; use the private beta to set defensible release thresholds. Inspect the expanded widget, queue, pending questions, Manual control, resume action, error states, themes, text scaling, and reduced motion in the real desktop experience.
- **Release evidence.** Confirm the tested native T3 version and connection method, the selected reasoning/speech routes, and actual Windows and Apple silicon macOS coverage. Run the project's applicable lint, type, automated, design, and packaging checks when implementation reaches those stages. This specification work does not itself claim those tests have run.

## Out of Scope

- Hermes Agent, Grokbot, Telegram, SMS, or other phone escalation in the first release.
- Connections to remote T3 environments or other machines in the first release.
- Implementing every named harness, arbitrary desktop computer control, or replacing the host application's agent runtime.
- A second full conversation workspace that duplicates T3's main interface.
- A public plugin SDK or marketplace before a second integration has validated the common interface.
- Bundled model credits, unlimited agent-usage promises, or a fixed subscription price chosen before usage and support costs are understood.
- Unsupported reuse of consumer subscriptions, undocumented credential repurposing, or silent fallback to a different provider or billing account.
- Supervising unassigned threads, inventing new assignments after completion, or treating deferred questions as approvals.
- Intel macOS builds, signing/notarization changes, a new macOS updater, or unrelated distribution changes.

## Further Notes

- This spec synthesizes the completed product discussion. The owner explicitly required wake activation, spoken replies, existing-app threads, sequential handling of ready threads, and a clearly stated manual-takeover rule. T3 is the first implementation of the broader control-center direction.
- The application currently has local dictation and a tested Electron integration structure; it does not yet implement this control center, a T3 plugin, conversational speech output, or Sotto membership billing. No live T3 or voice integration tests were run while writing this spec.
- T3 source inspection found shared desktop/web/mobile state, project/thread creation, submission, questions, permission responses, and a provider/model catalog. These are internal interfaces. Compatibility, visible-thread access, filesystem effects, origin detection, and reconnection must be proven against the installed target before the integration is considered complete. [T3 Code source and documentation](https://github.com/pingdotgg/t3code)
- Provider support must be checked per connection role and authentication route. Codex documents ChatGPT sign-in for app-server clients; inspected Realtime voice documentation describes metered API usage. Native subscription access does not automatically establish eligibility for every third-party endpoint. [Codex app-server authentication](https://learn.chatgpt.com/docs/app-server#authentication-modes), [Realtime billing](https://developers.openai.com/api/docs/guides/realtime-costs)
- Claude's documented third-party login requirements and its subscription-usage billing guidance address different questions and should both be checked before offering a commercial connection. xAI documents Voice API authentication and pricing, while particular third-party subscription eligibility remains to be established. [Claude SDK requirements](https://code.claude.com/docs/en/agent-sdk/overview), [Claude plan billing guidance](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan), [xAI Voice API](https://docs.x.ai/developers/model-capabilities/audio/voice), [Grok subscription FAQ](https://docs.x.ai/grok/faq)
- Exact speech/reasoning implementations, numeric voice-release thresholds, subscription price, billing provider, and entitlement validity are decisions for the validation and commercial stages. They are deliberately visible here rather than silently treated as settled product requirements. The implementation agent should resolve technical choices within the agreed behavior, record verified limitations, and avoid substituting a different user experience for a failed integration path.
