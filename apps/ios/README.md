# Sotto for iPhone

Native iOS 17+ client for Sotto on your computers, over a private Tailscale connection. It pairs with every computer running the Sotto desktop app, and with any host without a screen, and shows their threads and desktop terminals together. Each computer is found by its machine name on the tailnet and paired with a code it shows.

Three tabs: **Threads**, the home page, puts questions and permissions first, working threads next, then recent threads. The page scrolls as one, with its heading, computer selector and search field, and questions and permissions with a few choices are answered on their cards. Each card and row names its computer, and the Threads badge counts waiting requests across computers. A recent thread that finished while neither device showed it has a dot in the margin, a bold title and **Just finished** until it is opened here or on the desktop, and the badge counts it too (ADR-0046). **Computers** offers Add computer, then each computer with whether it can be reached, whether this iPhone may answer there, its client ID, Rename and Remove. **Settings** offers the theme, Dark, Light or System appearance, five text sizes, message density, local notifications and new-thread defaults, saved on this iPhone across launches. Those preferences do not change any computer's settings.

A thread shows its messages with the agent's steps between them in time order, each run of steps folded into one line that opens in place, under a title, computer and Git chips that scroll away, takes replies, with photos from the library or the camera, and stops a working turn; a waiting question or permission opens as a sheet. A question with a few choices, or a permission, can also be answered on its card in Threads. Pairing does not grant permission authority. On current hosts, changing Can answer updates the connected iPhone immediately; older hosts require reconnecting. Shell input, file management, speech and push are outside this client. Android is a separate proposed client. The look is Glow ([ADR-0051](../../docs/adr/0051-the-iphone-takes-the-glow-look.md), the [Glow plan](../../docs/plans/iphone-glow-look.md)); the approved Focus design and its revisions are recorded in [ADR-0039](../../docs/adr/0039-the-iphone-opens-on-focus-threads.md), the [Focus plan](../../docs/plans/ios-focus.md), and the [new-thread plan](../../docs/plans/iphone-new-threads.md).

**New thread (+)** at the top of Threads opens a guided flow: choose a connected computer, choose its project, then choose a model, effort and permissions. **Browse another folder** opens that computer's folders, including Windows drives through **All folders**; **Home**, **Up**, **Filter folders** and a full path help find a project. The filter matches names in the directory shown, without searching the whole disk; **Done** closes its keyboard. **Use this folder** selects an existing folder, and **Open thread on Laptop** adds it as a project when needed and opens the thread there. Only folders are listed; files and their contents are not read. Folder browsing needs the computer's `host-folders` feature. Send the first message in the new thread to start work on that computer; work continues there while the phone is suspended.

Creation uses the project folder, or a new worktree when **Working copy** says so. The defaults from Settings, where that computer offers them, and otherwise its saved new-thread model and effort are used where available; an unavailable saved model stays unselected until you choose another. Permissions start on an asking mode and are sent explicitly, so a permissive desktop default is never silently inherited. Modes that allow actions without asking need this iPhone's **Can answer** policy on that computer. The host rechecks it before acting. A lost creation acknowledgement leaves an ID-only marker on Threads, blocks another creation on that computer, and is never resent. **Check again** reads the receipt and, for a thread, its phone-minted Sotto ID. After a computer restart, an unknown project-registration receipt stays unconfirmed until the user checks the computer and dismisses it; no folder path, prompt or command body is persisted in that marker.

This directory is independent of the Electron/npm package. SwiftUI, Foundation and Security are system frameworks; SottoCore has no external dependencies. The wire models mirror `src/shared/hostProtocol.ts` version 1. Each paired computer is its own Keychain item under its host ID, listed in order by a small index item; its connection, session and state are its own, so a computer that can't be reached holds up none of the others. Everything that names a thread carries the host ID with the thread ID, because two computers can hold the same thread ID. The single pairing an earlier build saved becomes the first computer on launch. No signing team is embedded. TestFlight delivery is described below.

Unsettled threads stay visible; **Settled** expands threads put aside on desktop, including settled projects. Searching reveals matching settled threads. A finished turn stays visible until its thread is settled. Confirmed background agents keep a thread Working after its turn ends. A background command alone reads Waiting; running compaction reads Compacting context. Both stay under **Working now** until the computer confirms they have finished. Reachable questions, permissions and ongoing work stay above Settled even when their thread or project is settled. Unreachable computers retain their last shared threads with an explicit connection state rather than claiming live work. A thread that cannot load offers **Try again** without disconnecting its online computer.

The client reads snapshots, skips unused event history and accepts incremental thread updates. An observation supplies its initial messages once. Decoding runs outside the UI actor; missing delta bases trigger a single full read. Connection recovery never resends commands.

Terminal mode rows from a current desktop join the same **Needs you**, **Working** and **Recent** sections, with a terminal glyph and their computer. **Search threads and terminals** searches both. Opening a terminal shows its state and clears **Just finished** on both devices; only a foreground detail counts as viewed. Closed terminals leave the phone list. Older computers keep showing threads only, because the client uses the advertised `terminals` feature and opts in through hello.

A supported Claude terminal permission uses the Glow **Permission** card with at most eight live screen lines, **No**, **Yes** and **More choices**. Without Can answer it says **This iPhone can't answer on <computer> yet.** and offers **Review permission**. A missing or changed preview offers review again or directs you to the computer. Each answer goes through the exact run's blocking hook, never as keystrokes; the computer rechecks Can answer and confirms only hook acknowledgement. More choices directs you to review on the computer, where persistent native choices stay. Codex, Grok and screen-only requests offer no phone answer controls. Unconfirmed answers retain only opaque IDs for **Check again**; it reads a receipt and never sends the answer again. Preview lines are never persisted or logged.

## Build and test

Use a Mac with Xcode 15 or newer (iOS 17 SDK or newer) and its command-line tools selected. Uploading to App Store Connect needs Xcode 26 or newer, which is what CI uses. From the repository root:

```sh
swift test --package-path apps/ios
sh apps/ios/Scripts/verify.sh
```

On macOS, the package also tests the actual AppModel against scripted storage and transport: a failed thread read must keep its computer online, and an observed detail must not be downloaded twice. Core tests cover incremental updates, stale revisions and desktop settlement rules. The optional list budget runs with `SOTTO_PERF_ASSERT=1 swift test --package-path apps/ios --filter ThreadPerformanceTests`.

The second command also compiles an unsigned simulator app. This is independent of root npm tests. It must run before calling the native client verified. The shared Xcode scheme is `Sotto`; the package tests cover protocol rejection, host/session identity, the accepted ports and the order they are tried, native permission IDs, stale requests, structured questions, ambiguous delivery, merging and filtering threads across computers, thread identity across computers, and moving the single saved pairing over. They do not substitute for a live app journey.

To run the built app on a booted simulator:

```sh
xcrun simctl install booted apps/ios/.build-native/Build/Products/Debug-iphonesimulator/Sotto.app
xcrun simctl launch booted com.millzach.sotto.ios
```

Choose an installed iPhone simulator using Xcode or `xcrun simctl list devices available` first. The app deliberately accepts only certificate-validated `https://*.ts.net` origins on port 443, 8443 or 10000; it has no localhost/cleartext production bypass. Live connection verification therefore requires a reachable private host route. The approved Focus prototype is retained on `prototype/ios-threads-redesign` at `0d3e5835`, under `apps/ios/prototypes/threads-redesign/`; its README gives the preview command. A browser preview is not the iOS app.

## Sign and install on an iPhone

With a Mac, open `apps/ios/Sotto.xcodeproj`, choose the Sotto target, set your own development team in Signing & Capabilities, and confirm that `com.millzach.sotto.ios` is available for that team (change the identifier if needed). Connect the iPhone, enable Developer Mode when Xcode requests it, select it as the run destination and build. Do not commit team-specific provisioning material or account credentials.

Install/sign in to Tailscale on the iPhone and grant the intended tailnet access, with MagicDNS on for the tailnet. On a computer running the desktop app, phone access in Settings › Phones runs Tailscale Serve on HTTPS port 8443, or 10000 when another app already uses 8443, leaving 443 to other apps. For a host without a screen that a desktop reaches over SSH, turn on Let phones reach it with Phones on its row in that desktop's Settings › Hosts, which runs Tailscale Serve on the host's machine on 8443, or 10000 the same way (ADR-0050). A host run by hand can still be served on its own private HTTPS origin, usually port 443. On the iPhone, tap Add computer (the first launch starts there) and type the machine's name (`forge`): the app resolves it through the system resolver, which Tailscale answers with MagicDNS, takes the full `forge.<tailnet>.ts.net` name from the canonical or reverse-lookup answer, and reads `/v1/health` on port 8443, then 10000, then 443, before asking for a code. The full `.ts.net` address can be typed instead, and an address typed with its port is used only on that port. Then enter the fresh code the computer shows (Settings › Phones › Pair a phone), the host's Phones dialog shows on the desktop, or the host's pairing command prints; the pairing is refused if a different host answers than the one found, and a computer already paired is refused until it is removed. A computer saved on 8443 or 10000 that no longer answers there is looked for on the other of the two, since phone access can come back on it after a restart; only the host it paired with is used there, and the address the app keeps stays as it was. The computer's name comes from its health (`name`, which the desktop sends); an older host sends none and is named by its tailnet machine name, and either can be renamed on the iPhone. Allowing this client's answers is a separate explicit policy on each computer: turn on Can answer for the iPhone in that computer's Settings › Phones, in a host's Phones dialog on the desktop, or use a host's documented `--allow-answers` operation with this client ID. No credential or pairing secret belongs in a URL or log.

## TestFlight from GitHub Actions

No Mac is needed to put the app on an iPhone. `.github/workflows/ios-testflight.yml` archives, signs and uploads it to TestFlight on a macOS runner whenever a tag named `ios-testflight-*` is pushed (ADR-0032):

```sh
git tag ios-testflight-$(date +%Y%m%d-%H%M) && git push origin --tags
```

About half an hour later the build appears in the TestFlight app on the phones of the internal testing group. The build number is the workflow's run number; the marketing version is `MARKETING_VERSION` in the Xcode project.

One-time setup, all in a browser plus `gh`. `bash apps/ios/Scripts/testflight-setup.sh` walks through steps 1 to 4, opening each page and storing the secrets without showing them:

1. In the Apple Developer account, under Certificates, Identifiers & Profiles, register the App ID `com.millzach.sotto.ios` (explicit, no capabilities), and note the Team ID under Membership.
2. In App Store Connect, create the app under Apps with that bundle ID. The App Store name must be unique across the store; the name on the home screen stays Sotto.
3. In App Store Connect under Users and Access, Integrations, App Store Connect API, generate a team key with the **Admin** role (cloud-managed signing needs it). Download the `.p8` once and note its Key ID and the Issuer ID.
4. Store them as secrets of the `testflight` environment: `APP_STORE_CONNECT_KEY` (the `.p8` file's text), `APP_STORE_CONNECT_KEY_ID`, `APP_STORE_CONNECT_ISSUER_ID` and `APPLE_TEAM_ID`.
5. After the first upload, add yourself to an internal testing group under TestFlight in App Store Connect, and install the TestFlight app on the iPhone.

No certificate or profile is stored anywhere: Xcode's automatic signing uses Apple's cloud-managed certificates, authorised by the key. Revoke the key in App Store Connect if the repository's secrets are ever in doubt. The app declares standard encryption only (`ITSAppUsesNonExemptEncryption` is false), because it uses the platform's TLS and Keychain and no cryptography of its own; review that if the implementation changes. External testing and the App Store need Apple's review and are not set up.

On a Mac, the same archive can be made locally: open the project, set your team under Signing & Capabilities, and use Product > Archive, or run `apps/ios/Scripts/testflight.sh` with the environment it documents.

## Lifecycle and privacy

The host does the work while iOS suspends the app. Health and session requests each allow thirty seconds. Reconnect and Remove check ready health against the saved host first. Foreground activation gets a fresh signed session, shell and selected-thread snapshot; socket frames never replay commands. Lost acknowledgements retain an ID-only Keychain marker. A reply, answer or stop reads as sending while its command is on its way, and while the computer's receipt says it is still carrying it out; the receipt is read every two seconds for about ten minutes at most, and only a command the computer can't account for is marked unconfirmed. Every fresh shell settles reply markers from delivery evidence and clears answer markers for requests that are no longer waiting, without resending. Stop remains available for a working turn while its reply is unconfirmed. A receipt that vanished after host restart stays unconfirmed; the user can check the thread and explicitly dismiss the marker without resending it. A completed transport receipt alone does not establish prompt delivery: provider delivery evidence must agree. Only that answer command's completed receipt with no error and explicit successful-outcome evidence says "Answer sent." If a request disappears without that receipt, the app says "That request is no longer waiting." A desktop answer, stopped turn or provider cancellation cannot confirm the phone's answer. Older hosts omit the outcome evidence, so their waiting answers remain unconfirmed and a vanished request settles neutrally. An unrelated computer error does not decide its delivery, and settling a marker preserves feedback about other actions.

The per-device host token uses `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`, with synchronization disabled. Provider keys never enter this client. HTTP and socket credentials are headers/body fields, never URL parameters, and redirects are refused. URLSession is ephemeral with no cookies or disk response cache. Transcript and unsent draft text remain in memory; backgrounding preserves drafts, termination loses them. The app obscures content while inactive. No transcript, token or protocol-body logging is implemented. Looking up a machine name is a DNS query from the iPhone: with Tailscale connected MagicDNS answers it inside the tailnet; with Tailscale off, the query for that one name goes to the iPhone's usual DNS server. Only an answer that points into Tailscale's own address ranges is used, so another network cannot hand the phone a different host.

If secure storage is locked at launch, unlock the iPhone and return to Sotto. It reads saved computers again when active. A damaged saved-computers index is preserved. Sotto rebuilds the list from readable per-computer Keychain items and saves the recovered order separately when that index is readable. If both indexes are damaged, they are kept and the list is recovered again on each launch. Recovery is announced only when no recovered index existed at launch. Sotto reports how many saved computers need pairing again, once for each unreadable item, without naming their host IDs. Damaged unconfirmed-action markers are kept at launch and a message asks you to check your threads before sending again. Nothing is resent.

Remove this computer applies the reconnect host check, revokes this pairing when confirmed, then clears its Keychain item, its delivery markers and its drafts. A computer that can't be reached, or that doesn't confirm the revocation, is removed from the iPhone anyway, and the app says so and how to remove the iPhone there: in Settings › Phones, in a host's Phones dialog on the desktop, or with a host's `--revoke-client` command and this client ID. The token the computer keeps is a hash nobody holds. The Keychain item goes first, so an interrupted removal never leaves an index entry the app would try to connect to. Keychain reinstall behavior is not a substitute for revocation on the computer. The app asks for camera access only when you first take a photo for a reply, and for no microphone or location access. It asks to show alerts only when you first turn one on in Settings; an alert carries the thread's title and a plain line saying what happened and where, and iOS keeps it in its notification centre until you clear it. It doesn't ask for photo library access: the system's own picker hands it only the photos you choose. A photo is scaled, drawn again without its location or camera details, and kept in memory until it is sent or removed; nothing is written to the iPhone's disk.

## Verification required before delivery

- Native package tests and simulator compile; inspect both themes at small/large text sizes, VoiceOver, reduced motion, portrait and landscape, and the software keyboard.
- On the real iPhone and desktop, read the same thread on the host, reply and receive streaming updates, interrupt, answer structured questions and each supported permission form explicitly.
- Revoke authority while a request is visible; another client answers first; disconnect after send but before acknowledgement; restart host; switch networks; lock/unlock; terminate/relaunch. No automatic resend or stale request answer.
- Find by name with Tailscale connected (MagicDNS short-name lookup has not been observed on a device yet), with Tailscale off, with a name that is not a Sotto host, and by full address. Find a desktop on 8443, a desktop on 10000 while another app holds 8443, and a host run by hand on 443.
- Pair two computers, one desktop and one host; see both on Threads, narrow with the computer selector, search, and answer, reply and stop on each. Take one offline: its connection state and retained rows remain visible without hiding the others. Rename one, remove one while reachable and one while not. Upgrade over a build that held a single pairing and check it becomes the first computer.
- Check the question-first, Working now and Recent groups with a foreground turn, confirmed background work, compaction, a settled question and a settled working thread. Check collapsed Settled and matching settled search results. Review a request in its thread and confirm the Threads badge updates. Let a thread finish while it is open on neither device: its row reads Just finished and the badge counts it; open it on the phone and check the desktop's mark clears, then the other way round.
- Change the theme, appearance, text size and density in Settings, terminate and relaunch, and confirm every choice remains. Check the system's accessibility text sizes as well as the app's text size steps.
- Turn on a notification, allow it when iOS asks, and confirm an alert arrives for a thread that needs you on another screen, and not for the thread on screen.
- Expired/invalid pairing, Keychain locked/unavailable, wrong host identity, offline host, revoked token, and revocation followed by local deletion failure.
- Verify host work continues while the app is suspended. Record device/iOS/app versions and native captures. HTML, static source checks and simulator builds cannot establish this result.

## Bundled assets

Colours are not in the asset catalog. `Sotto/ThemePalettes.swift` is generated from the desktop's six palettes in `src/shared/themes/palettes.ts`; `tests/unit/shared/iosPalettes.test.ts` fails when the two drift and says how to regenerate it. The catalog holds only the app icon.

Figtree is distributed under the included `Sotto/Resources/Figtree-OFL.txt` (SIL OFL 1.1). `Figtree.ttf`, `Figtree-SemiBold.ttf` and `Figtree-Bold.ttf` are regular (400), semibold (600) and bold (700) instances of the upstream variable font at [Google Fonts revision a60a77e](https://github.com/google/fonts/tree/a60a77e14f28abd4ef243a1b5dfc48df0cec5205/ofl/figtree), instanced with fontTools as a development operation; fontTools is not an app dependency. Static faces, because iOS does not synthesize weights for a custom font. The app icon renders this repository's `build/icon.svg` on Sotto's canvas; `node scripts/generate-brand-assets.mjs` writes it with the desktop's icons. Native named colors are the default Sotto palette's light and dark roles in `src/shared/themes/palettes.ts`, converted from OKLCH to sRGB (every text pair at 4.5:1 or better); no theme/provider text is interpreted as a native color.

Current evidence and limitations: [client implementation plan](../../docs/plans/ios-client.md) and [Focus implementation plan](../../docs/plans/ios-focus.md). Native compilation, signing and device execution must be reported separately from source completion.


The shared scheme's Test action uses the process launcher without LLDB, so automated UI verification does not depend on debugger attachment. The Run action still attaches LLDB. To debug a test interactively, enable its debugger in the scheme editor for that session.

While active, the app checks socket liveness every 25 seconds. A computer that loses its connection is tried again for about a minute, with waits from 1 to 30 seconds, then gives up; one that has not been online since the app opened is tried once. A computer that gave up reads Can’t reach it and waits for Try again or Reconnect: returning to the app and pull to refresh leave it alone. The open thread stays on screen while it is read again. Backgrounding cancels retries; returning opens fresh sessions and reconciles pending actions without replaying them.
