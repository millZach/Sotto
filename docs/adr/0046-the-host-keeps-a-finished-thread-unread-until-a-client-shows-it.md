# The host keeps a finished thread unread until a client shows it

Accepted October 3, 2026, for issue #703. The desktop's sidebar says **Just finished** on a thread that finished while you were elsewhere. That mark lived only in the renderer (`src/renderer/src/agents/finishedThreads.ts`), whose header gave the reason: it is about what you have seen, not about the thread, so it stays out of the state main publishes, and a restart forgets it. The iPhone now needs the same mark, and the owner decided that seen means opened on either device. Only the host knows what every client shows, so this reverses that reasoning. It is recorded here because it was decided, not followed.

## Decision

**The host's coordinator owns the mark.** `FinishedUnread` (`src/main/agents/finishedUnread.ts`) keeps the rules the renderer had. A thread is busy while its turn runs or background work the turn started runs on. A thread that was busy and becomes idle while no client shows it earns the mark. A thread shown when it finishes never earns it, and leaving it afterwards does not mark it after the fact. A disconnect, of the thread's provider or of the whole host, ends the work without finishing it: it earns nothing, and the thread stops counting as working, so coming back idle earns nothing either. A turn that fails, or that stops to ask the user something, earns nothing, and a marked thread that works again, fails or asks loses its mark until it next finishes out of sight.

**What a client shows is what it observes.** Every client already tells the host which threads it is looking at with `observe-threads`, unreceipted, and `LocalHostService` and the socket server merge every client's set into one. The desktop window observes the threads in its panes and the Tools panel's pinned thread, which is the set the sidebar's own record used. A paired iPhone observes the thread it has open (its `observe`, sent when a thread is selected). A desktop showing a remote host's thread sends that host its panes the same way, so the remote host clears its own mark. No new command was needed, so nothing new goes on the remote allow-list. Neither the coordinator's active thread nor a selection on its own counts as showing.

**The desktop window shows its threads only while it has the focus.** This is the owner's decision (October 3, 2026). A thread that finishes in one of the window's panes while another app is in front, or while the window is minimised or hidden to the tray, earns the mark, so the phone shows it. When the window gains the focus again, the threads in its panes and its pinned Tools thread count as shown, which clears their marks, as coming on screen does. Main reads the focus from Electron's window focus and blur events and tells `LocalHostService`, which leaves the window's observed threads out of what it shows while the window is unfocused. The renderer has no part in it, and the window's `observe-threads` is unchanged: its threads' history keeps streaming whether or not it has the focus. The floating widget shows no thread, so the widget taking the focus is the window losing it. A phone shows what it has open whatever the window does, and a remote host still counts a desktop's panes as shown, focused or not.

**It is published as an optional field and saved with the coordinator's state.** A marked thread carries `finishedUnread: true` in the shell and the whole state; an unmarked one carries nothing. The field is add-only on protocol v1 (ADR-0025): an older client ignores it and an older host never sends it. The coordinator saves the marked thread IDs, and nothing else about the thread, in `agents.json`, oldest first and at most 200. A thread missing from a snapshot keeps its mark, because at start a provider may list its threads after the first snapshot. What was working is not saved, so a turn that ends across a restart earns nothing.

**Clients read it and do not keep their own.** The desktop sidebar says **Just finished** from the published field, with the look it had. The iPhone marks the row in Recent, and in Settled when that shows, with an accent dot in the margin, a bold title and a **Just finished** line, and counts it on the Threads tab (prototype variant A, branch `prototype/ios-unread-finished`). The Threads tab shows one number, waiting requests plus unread finished threads in Recent. That is the owner's decision too: it takes the place of the prototype's separate Needs you tab, which no longer exists (ADR-0039). The phone treats the thread it has open as read at once, which is the only copy it keeps, and the host's next shell agrees.

## Consequences

- Seen is per host, not per person or device: any client that shows the thread clears it for every client, including a paired phone or desktop that predates the field and cannot show the mark itself.
- The desktop is stricter than the renderer's record was: that counted a pane as shown whether or not the window had the focus. Now a thread that finishes while you are in another app reads **Just finished** when you come back to it in the sidebar, unless it is in a pane, which coming back to the window reads.
- A remote host knows nothing of the desktop window's focus, so a remote host's thread that finishes in a pane stays unmarked while the window is unfocused.
- On the iPhone one badge counts what wants you: a thread with two waiting requests counts two, and an unread finished thread counts one. A settled one is marked where it shows but not counted, since the Settled shelf may be closed. A computer the phone cannot reach marks and counts nothing until it is back.
- The desktop renderer no longer keeps a record of its own; `finishedThreads.ts` is gone. An updated desktop connected to a remote host that predates this shows no **Just finished** for that host's threads until the host is updated, where the old renderer record marked every thread it was sent.
- A mark for a thread that is later forgotten stays in `agents.json` until newer marks push it past the limit. It names nothing but the thread ID, and no client shows a thread that is gone.
