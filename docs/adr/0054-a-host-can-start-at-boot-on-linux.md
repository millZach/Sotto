# A host can start at boot on Linux

October 9, 2026 amendment: [ADR-0068](0068-remove-voice-control-and-thread-management.md) records the removal. The voice gate described below has been removed. Start at boot remains an explicit user action under the same consent, systemd and recovery rules.

## Context

A host Sotto started outlives the desktop (ADR-0025, September 22 amendment) but not its machine. After forge restarts, its threads are out of reach, from phones and from a tailnet connection alike, until a desktop connects over SSH and the launch script starts the host again. On a tailnet whose Tailscale SSH policy is in `check` mode, that connect waits for the owner's approval in a browser. So a reboot undoes most of what ADR-0053 buys.

Linux machines with a systemd user manager can start a user's own process at boot without root, through a user unit and the account's linger setting. Without linger, the account's user manager, and every unit it runs, starts at the account's first sign-in and stops when its last sign-in session ends; a forward-only `ssh -N -L` opens no sign-in session. A host started by the launch script today is detached and survives sign-out, so a unit without linger would keep the host up for less time than today, not more. The host's release is Linux-only (ADR-0025).

## Decision

**Start at boot** is a host's systemd user unit, installed by Sotto, that starts the host when its machine starts. `CONTEXT.md` has the term. Avoid "service", which is the host service, and "daemon".

**Where it applies.** Linux with a systemd user manager. macOS hosts are out: a LaunchAgent starts only at sign-in, and a LaunchDaemon needs root. Windows hosts are out: the launch script is POSIX only. Linux without a user manager (WSL without systemd, a container) is out. In each case the launch script's `boot-status` says `unsupported` with one plain sentence saying why, and the desktop offers nothing.

**Linger comes first.** Start at boot needs the account to linger, and nothing on the host changes until it does. The unit is installed only once linger is on, and **Start at boot** refuses to enable it while linger is off. If linger is later turned off, the next launch turns start at boot off (below), so a unit never runs a host that would stop at sign-out.

**The launch script's operations.** Three new operations, each one `ssh` command like the others:

- `boot-status` reports whether boot start is supported, installed and active, whether the account lingers, and whether the unit's pinned Node has drifted from the one the host archive wants. A launch reports it too.
- `boot-install` reads the account's linger setting first (`loginctl show-user -p Linger`). If it is off, it runs `loginctl enable-linger` for the account, without sudo, since linger is the account's own setting and the owner consented to it with the press. If polkit refuses, it stops there: nothing is written and the running host is untouched, and the result carries `sudo loginctl enable-linger <user>`, which the modal shows with a copy button and the advice to run it on the host and press Start at boot again. Sotto never runs sudo, as with the Serve operator (ADR-0050). Once the account lingers, it writes `~/.config/systemd/user/sotto-host.service` and a small `boot-start.sh` in the installation folder, reloads the user manager and enables the unit. It then hands over a running host: one Sotto started is stopped the way Stop host stops it (SIGTERM, 15 seconds to save and exit) and started again by the unit, so it restarts once; one Sotto did not start is left running and the unit takes over at the next boot. The modal says which before the press.
- `boot-remove` disables and stops the unit, removes both files, and, only when the host is switched on, starts the host the way a launch does, so it keeps running. That is a restart, and the modal says so before the press. It never starts or restarts a host that is switched off: after Stop host, or for any host this desktop has switched off, the host stays stopped. Forget runs it without the last step (below). The amendment below lists what it runs, in order.

**A busy host asks first.** Installing the unit over a host Sotto started, and removing it, each restart the host once, which stops its turns in progress. Both use ADR-0040's busy-host question: when one of the host's threads is working, the modal says how many and offers to wait until they finish, to stop them now, or to cancel, as Update does.

**The unit.** It runs `boot-start.sh` with `SOTTO_HOST_STARTED_BY=boot`, restarts the host on failure after 5 seconds, gives it 25 seconds to stop, and is wanted by the user's default target. `boot-start.sh` resolves `current` the way the launch script does (ADR-0040) and runs the host with an absolute Node path, the data folder and the port, and no key file, as a launch does. The Node path is pinned when the unit is written, and an update rewrites the script when the probe finds a different Node or the new version needs a different range. Provider clients under systemd's short `PATH` are found by the login-shell fallback the host already has.

**Ownership.** `startedBy: "boot"` is a new value in the host's listener descriptor. A host started by the launch script or by its boot unit counts as started by Sotto, so Stop host, Forget's stop and Update still apply.

**Lifecycle with the unit installed.**

- A launch reads the unit and the account's linger before it spawns anything, so a launch and the unit never race for the host lock. With linger on and the unit enabled, it never spawns a detached host: if `sotto-host` is active it uses that host. Otherwise it first looks for a running host the way a launch does today and uses one with the expected host ID, since `boot-install` leaves a host Sotto did not start running beside an enabled unit. Only when no host is running does it clear the unit's failed state (`systemctl --user reset-failed sotto-host`), ask the user manager to start the unit and wait for the host; a start the user manager refuses, or a unit that lands failed while the launch waits, is reported at once rather than waited out. A host refused because another live host holds the lock exits with a code of its own, which the unit lists in `RestartPreventExitStatus=`, so a unit that loses the lock to another host stops instead of retrying every 5 seconds for as long as that host runs. The lock's other refusals, such as a moment's contention while a stale lock is cleared, keep the ordinary failure code, so `Restart=on-failure` still retries them. The unit also sets a start limit that a start every 5 seconds can reach, 5 starts in 120 seconds, so a refusal only a hand can fix (an unreadable or unremovable lock, a folder it cannot write) or any other crash loop, such as a drifted Node, stops the unit instead of retrying for good; `boot-status` then reports it not active, and the next launch takes the path above. The start limit also refuses a start by hand while it holds, which is why every start and restart Sotto asks for clears the failed state first. The amendment below settles when a wait counts a unit as given up, and the second look before it says so.
- With linger off and the unit enabled, the launch's own sign-in may already have started the unit through `default.target`. The launch disables the unit, stops the unit's host if one is running, and then spawns a detached host as today. It reports start at boot as off, with `sudo loginctl enable-linger <user>` for the owner to run before pressing Start at boot again. The unit's files stay, disabled.
- **Stop host** stops the unit. Its confirmation says "forge's host stops now and starts again when forge restarts or when you switch it on."
- **Forget** revokes this desktop first (ADR-0053, "Forget"), then removes the unit and its script wherever it is installed, and stops the host only if Sotto started it, so a forgotten host does not come back at the next boot. Its confirmation says so. A host that is already stopped cannot revoke, so Forget removes its unit and says the pairing was not revoked, as ADR-0053 says. When SSH cannot reach the host, the unit stays, and Forget says so with the rest.
- **Update**'s restart writes `current`, clears the unit's failed state and restarts the unit, then waits for the new host. A rollback points `current` back, clears the failed state and restarts the unit again. A restart the user manager refuses, or a unit that lands failed during the wait, is reported at once. The amendment below settles when its wait counts a unit as given up, and what a rollback stops first.
- The host puts Serve back at start from its own `phoneAccess` and `tailnetConnections` settings (ADR-0053), and the Serve setting survives a reboot in tailscaled too. A user unit cannot be ordered after `tailscaled`, so for the first 5 minutes after a start the host's phone access retry, every 30 seconds, also covers Tailscale missing and Serve failing.

**What the owner sees (the delegated picks).** Add host's connected card offers **Start forge's host at boot**, one consented press. The row's More menu has **Start at boot…**, or **Stop starting at boot…** once it is installed, and each opens a modal that says what changes on the host (linger for the account, a unit in the account's systemd folder, a script in the installation folder), that a host Sotto started restarts once and its turns stop, and the linger command for the owner to run there if the host asks for an administrator. Each runs over the SSH connection, or opens an admin connection when the host is on its tailnet connection (ADR-0053), so a Tailscale approval shows in the modal.

**Outside the voice gate.** Start at boot is a press in Settings. Nothing speaks, listens or manages a thread, so it sits outside `voiceCoordinatorEnabled` (ADR-0012), like Update.

**Privacy.** Nothing new is contacted. The unit and its script stay on the host, and the commands Sotto runs there (`systemctl --user`, `loginctl`) talk only to that machine's own system.

## Amendment, October 5, 2026: what the build settled

The pull request that built the launch script's side (`feat/host-boot-start`) settled three points carried from the review of the decision, and a few the decision left open. They are picks made under the same delegation.

- **When a wait stops waiting.** A launch's wait and Update's wait both treat a unit as given up when it is failed, when its host exited with 75, or when it is waiting to restart with a failed last run after more than one restart (`NRestarts > 1`). One restart is waited through, so the retry a moment's lock contention causes still starts the host.
- **A second look before giving up.** Before a unit that gave up is reported, the launch looks for a running host and then at the lock's holder, as its first look does, and waits for and uses a host that took the lock in between.
- **What boot-remove runs.** `systemctl --user disable --now sotto-host`, then both files are removed, then `daemon-reload`, then `reset-failed sotto-host`. It starts no unit.
- **Only this installation's unit.** The unit is this installation's when its `ExecStart=` names this installation's `boot-start.sh`. A launch, Stop host, Update and `boot-remove` start, stop, change or remove only that unit, and `boot-install` refuses, changing nothing, when another installation's unit holds the name `sotto-host`. The path is written double-quoted with `%` and `$` doubled, so systemd reads any folder name literally.
- **What the script pins.** `boot-start.sh` pins the Node the launch script runs under, which is the one the probe chose for the archive, the installation and data folders, the port and, when the SSH account's environment sets `SOTTO_HOST_KEY_FILE`, that key file's path, since a user unit does not read the account's shell profile. The path is pinned, never the key. Every unit start Sotto asks for, a launch's as well as Update's, first rewrites the script when any of these differs from the launch's own. `boot-status` reports `nodeDrift` until then. When the data folder or port differ, as after Edit connection changed them, the unit's host serves a folder this launch would never find, so the launch stops the unit before the rewrite and starts it again.
- **A rollback starts afresh.** Update's rollback, and an install's undo, stop whatever the unit runs before they start the host again, since that is the host that did not come up: a new version the unit keeps active but that never answers would otherwise be waited on a second time while `current` names the old one.
- **Ownership without the mark.** A host this installation's unit runs counts as started by Sotto even when its descriptor does not say `boot`, as a host release from before the mark records only `launch-script`, so Stop host and Update still apply to it.
- **Linger before the user manager.** On a machine that runs systemd, an account with no sign-in session and no linger has no user manager to answer `systemctl --user`, as over an SSH server that opens no session. `boot-status` then reports start at boot as supported, with linger off and its command, and `boot-install` turns linger on first, which starts the user manager, and waits up to 10 seconds for it before it writes anything. `no-user-manager` is for a machine that does not run systemd, or an account that lingers and still has none.
- **An install that does not finish.** When the user manager will not reload or enable the unit, the install is undone (`disable --now`, both files removed, `daemon-reload`, `reset-failed`) and the result is `boot-install-failed`; the host is untouched. Installing again over this installation's own unit is the exception: the unit that was already there stays, since undoing it would stop the host it runs, so start at boot stays as it was. When the host Sotto started will not stop, the install is undone the same way and the result is `boot-stop-failed`; the host keeps running. When the unit does not bring the host back after `boot-install` stopped it, the install is undone and the host is started the way a launch starts it, and the result is `boot-start-failed`, with `restarted` saying whether that start worked and `cause` the unit's own failure code. Otherwise, in each case start at boot is off, with nothing installed.
- **One change at a time.** `boot-install` and `boot-remove` run under the installation folder's update lock, so an update and a change to start at boot never restart the host together, and both carry on when the desktop's connection drops partway, as Update's restart does.
- **Where the unit goes.** `$XDG_CONFIG_HOME/systemd/user/`, or `~/.config/systemd/user/` when that is not set, which is where the user manager reads it. A session that did not set `XDG_RUNTIME_DIR` gets `/run/user/<uid>`, so `systemctl --user` finds the user manager over a plain SSH session.
- **The desktop's side.** A failing unit (`boot-start-refused`, `boot-unit-failed`) is a failure only the owner can fix, so the reconnect backoff stops, and the row offers `journalctl --user -u sotto-host -n 50 --no-pager` to run on the host. Start at boot and Stop starting at boot run as presses (ADR-0053), over the SSH connection the host is on or an admin connection, and an admin connection's launch reports start at boot too. Forget removes the unit, after the revoke and before the stop, only when the connection or the press reported one installed, and not when the host refused the revoke, since that host is left running. A host Forget finds stopped has no press to run it in: Forget's admin connection asks its launch to take this installation's unit away (`removeBoot`) when it finds no host, under the update lock, before it reports `host-not-running`, and it still starts nothing. Any other admin connection to a stopped host leaves the unit alone. A failing unit's message says nothing was lost and that the unit may still be trying, since the launch cleared its failed state and asked it to start.
- **What is left for later.** Editing a saved host's installation folder leaves the old folder's unit behind: it is no longer this installation's, so Sotto neither starts nor removes it, and `boot-install` refuses beside it with `boot-unit-taken` until the owner removes it on the host. Two saved hosts that share one installation folder with different data folders would each move the unit to their own folder at every launch; Settings > Hosts does not stop that yet.
- **The phone access retry.** For 5 minutes after a host starts, its phone access looks again every 30 seconds at a Tailscale that is missing and at a Serve setting that failed, as well as at one that is not running.

## Amendment, October 6, 2026: what the Settings side settled

The pull request that built the surface in Settings > Hosts (`feat/host-boot-start-ui`) settled these, under the same delegation.

- **Where a change runs.** Main runs Start at boot and Stop starting at boot, keyed by saved host and kept in memory, the way it runs an update (ADR-0040): the modal and the card only show where it stands. Closing the modal while the change waits for its threads, or while it runs, leaves it going, and the row reads "Starts at boot when its threads finish" or "Starting at boot…" until it ends. A change that then fails stays on the host's row, with what happened, the command to run where there is one, and **Dismiss**, and opening the modal again opens on it; one that ended well is put away. Closing the modal on the question cancels, and closing it on a result puts the result away. A wait carries on through a dropped connection and its reconnect, and ends, with nothing changed, only when the host is switched off or forgotten. The question goes ahead by itself once no thread is working, since the owner has already pressed, and a Cancel that comes while **Stop N threads now** is still stopping them wins. "Connected again" is said only once the host is; until then the result says Sotto is connecting to it, with Tailscale's approval when it waits for one. While a change runs, the host's connection commands (Stop host, Forget, Edit connection, the switch) and Update wait for it, and a change waits for an update in the same way.
- **The busy-host question's words.** "1 thread on forge is working. Starting at boot restarts forge's host, which stops it." Its answers are **Wait until they finish**, **Stop 1 thread now** and **Cancel**, shorter than Update's because "Stop 1 thread and stop starting at boot" does not fit the narrowest window; each button's accessible name says the rest. It is asked only when the change restarts the host: installing over a host Sotto started that the unit does not run yet, or removing a unit that runs the host.
- **Where the offer is.** On Add host's connected card when the host is added with Add it, and in the More menu above a line (with Forget below another, as the prototype draws it), for a connected host whose launch said it can start at boot. A host an agent set up (ADR-0035) gets it from the More menu. A host whose launch did not say, such as one running a Sotto from before this, gets nothing.
- **What Forget says about the unit.** When Forget could not take the unit away (the host refused the revoke and was left running, the removal failed, the host stopped answering partway through, or the launch that found it stopped could not remove it), its notice says the host still starts at boot and gives one line that removes the unit on the host. Like `boot-remove`, the line acts only on this installation's unit, the one whose `ExecStart=` runs the installation folder's `boot-start.sh`: `systemctl --user disable --now sotto-host`, the unit file and `boot-start.sh` removed, `daemon-reload` and `reset-failed`. It finds that unit by the `ExecStart=` line the launch script writes, with the folder resolved and quoted the same way, and when there is none it says so, changes nothing and names `systemctl --user cat sotto-host` for a look at the unit. The one folder it cannot match is a home folder whose own path holds `%`, `$`, `\` or `"`; there too it changes nothing. When the revoke went through and only the unit was left, the notice says that alone. Sotto never runs the line. The notice that said only that a revoke did not happen (ADR-0053) is now the **Forget notice**, since it covers both. A launch on Forget's admin connection that finds no host running says whether this installation's unit is still there (`bootLeft` beside `host-not-running`). Forget's confirmation for a host that is not connected says it removes start at boot too, if the host starts at boot, since the row cannot know.
- **The update panel.** For a host that starts at boot, it says the host restarts through its systemd unit and still starts at boot after.
- **What is left for later.** Stop starting at boot is offered only for a connected host, since only a connection says how start at boot stands, and a host that is switched off keeps its unit until it is switched on, which starts it, or forgotten. Offering it for a host that is not connected, and a Forget notice for the unit of a host SSH could not reach and this computer never saw connected, wait for the last known start at boot state that the tailnet store keeps per saved host (item 4 of the plan). The modals show start at boot as the host's connection last read it rather than reading it again when they open; the launch script reads linger and the unit again before it changes anything, so what can be out of date is the consent's words and whether the busy-host question is asked, not what changes.

## Consequences

- A host started at boot keeps its threads reachable from phones and tailnet connections across a restart of its machine, with no desktop and no SSH.
- Installing the unit, and removing it, each restart a host Sotto started once; removing it from a host that is switched off, which only Forget does for now, stops it and leaves it stopped. Its turns in progress stop, as Stop host's do, after the busy-host question.
- A host whose account cannot linger without an administrator gets nothing until the owner runs the command; Sotto does not install a unit that would stop the host at sign-out.
- When linger is turned off on the host while the unit is enabled, the next launch's `disable --now` stops the unit's host without the busy-host question, so its turns in progress stop, unlike a drop, which keeps them (ADR-0053). It happens once for each time linger goes off, and the launch's result then reports start at boot as off, with the linger command.
- The pinned Node path drifts when a version manager upgrades Node. `boot-status` reports the drift and an update rewrites the script.
- Tests use fake `systemctl` and `loginctl` executables on the path. Only a check on a real Linux host, recorded in `docs/verification/`, proves the unit, linger and a reboot.
- A macOS or Windows host, and a Linux host without the unit, keep today's behaviour: it starts again only when a desktop connects.
