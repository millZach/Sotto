# T3 Code monitoring popup

Studied on 2026-09-20 for Sotto's selected creature animation, variant C. This is a source inspection, not a live T3 or provider test. The public repository was checked in the browser and `origin/main` fetched into the existing reference clone. All T3 links below pin commit [`adcd90858c3bfece59095465d2f49860ba3dcea9`](https://github.com/pingdotgg/t3code/commit/adcd90858c3bfece59095465d2f49860ba3dcea9), the fetched main revision (commit date 2026-09-20).

## Finding

T3's composer banner uses task lifecycle state, not a ten-second timer. It appears when foreground work has settled and recognized background tasks remain alive. Its title is **Monitoring** only when those tasks are all classified as monitors. This is narrower than showing it for every command, but broader than proving the agent is actively inspecting a process: T3 also classifies surviving background shells as monitors. [Composer condition and title](https://github.com/pingdotgg/t3code/blob/adcd90858c3bfece59095465d2f49860ba3dcea9/apps/web/src/components/ChatView.tsx#L6225-L6296), [task categories](https://github.com/pingdotgg/t3code/blob/adcd90858c3bfece59095465d2f49860ba3dcea9/packages/contracts/src/providerRuntime.ts#L537-L550).

## Exact eligibility

The registry maintains live agent and monitor task IDs per thread. It returns `working` if any agents remain, otherwise `monitoring` if any monitors remain, otherwise `null`. Monitor task types are exactly `monitor`, `monitor_mcp`, `local_bash`, and `shell`. `plan` and `dream` are inert. Unknown or missing task types count as agents, not monitors. A subagent's internal monitor/shell tasks are excluded; nested agents still count as working. [Registry](https://github.com/pingdotgg/t3code/blob/adcd90858c3bfece59095465d2f49860ba3dcea9/apps/server/src/orchestration/ThreadBackgroundLiveness.ts#L105-L168), [classification constants](https://github.com/pingdotgg/t3code/blob/adcd90858c3bfece59095465d2f49860ba3dcea9/packages/contracts/src/providerRuntime.ts#L537-L550).

The composer exposes that state only with `!isWorking && activeThread`. `isWorking` includes a running phase, busy send, connecting, checkpoint revert, compaction, or bootstrap worktree setup. While those are active, this background banner is absent. Once they clear, a live monitor can appear immediately; live agents instead produce an agent-count or background-work banner. [Foreground predicate](https://github.com/pingdotgg/t3code/blob/adcd90858c3bfece59095465d2f49860ba3dcea9/apps/web/src/components/ChatView.tsx#L3249-L3260), [banner](https://github.com/pingdotgg/t3code/blob/adcd90858c3bfece59095465d2f49860ba3dcea9/apps/web/src/components/ChatView.tsx#L6225-L6296).

There is no age, elapsed-time check, repeated-poll threshold, or delayed reveal in those predicates. Consequently, a task that ends during the foreground turn never needs this banner; a monitor that survives the turn for only a brief interval can still show it. The latter is an inference from the predicates, not a live observation. T3's code comments assume that short pacing sleeps end inside the turn and a surviving shell is usually a watch loop. That assumption does not establish active inspection. [Registry rationale](https://github.com/pingdotgg/t3code/blob/adcd90858c3bfece59095465d2f49860ba3dcea9/apps/server/src/orchestration/ThreadBackgroundLiveness.ts#L30-L34), [immediate banner predicate](https://github.com/pingdotgg/t3code/blob/adcd90858c3bfece59095465d2f49860ba3dcea9/apps/web/src/components/ChatView.tsx#L6230-L6231).

## Provider event path

- Claude `task_started` becomes `task.started`, retaining the native task ID, task type, and owning subagent. `task_progress`, `task_updated`, and `task_notification` become progress, update, and completion events. Task identity is retained for later transitions. [Start mapping](https://github.com/pingdotgg/t3code/blob/adcd90858c3bfece59095465d2f49860ba3dcea9/apps/server/src/provider/Layers/ClaudeAdapter.ts#L3707-L3780), [later transitions](https://github.com/pingdotgg/t3code/blob/adcd90858c3bfece59095465d2f49860ba3dcea9/apps/server/src/provider/Layers/ClaudeAdapter.ts#L3782-L3870).
- Orchestration feeds only `task.started`, `task.progress`, `task.updated`, and `task.completed` into this liveness registry. It clears the registry on `session.exited`. Ordinary command item events do not qualify. [Ingestion switch](https://github.com/pingdotgg/t3code/blob/adcd90858c3bfece59095465d2f49860ba3dcea9/apps/server/src/orchestration/Layers/ProviderRuntimeIngestion.ts#L2472-L2507).
- Codex `item/commandExecution/terminalInteraction` becomes `item.updated`, with the original payload carried as data. This mapping does not distinguish blank-stdin polls from typed stdin and does not create a monitor task. Codex child-agent events do become task events, but as agent work. Thus this Monitoring banner should not be described as triggered by `write_stdin`, terminal interaction, or `unifiedExecInteraction`. [Terminal event mapping](https://github.com/pingdotgg/t3code/blob/adcd90858c3bfece59095465d2f49860ba3dcea9/apps/server/src/provider/Layers/CodexAdapter.ts#L1743-L1757), [child-agent mapping](https://github.com/pingdotgg/t3code/blob/adcd90858c3bfece59095465d2f49860ba3dcea9/apps/server/src/provider/Layers/CodexAdapter.ts#L1040-L1101).

A source search across current `apps/web/src` and `packages/client-runtime/src` found no separate terminal-interaction/command-wait popup. This is a bounded search finding, not a claim that every historical T3 release has identical behavior.

## Ending and stale events

A completion event, idle status, or terminal status (`completed`, `failed`, `stopped`, `cancelled`, `interrupted`) removes the task, even when its final event omits its original type. A status-free progress/metadata event cannot restart an already-ended task. Classification is recalculated per transition. The registry is in memory and starts empty after server restart; session exit clears the thread. There is no stale-task timeout in this registry. [Removal and update rules](https://github.com/pingdotgg/t3code/blob/adcd90858c3bfece59095465d2f49860ba3dcea9/apps/server/src/orchestration/ThreadBackgroundLiveness.ts#L36-L168), [session exit](https://github.com/pingdotgg/t3code/blob/adcd90858c3bfece59095465d2f49860ba3dcea9/apps/server/src/orchestration/Layers/ProviderRuntimeIngestion.ts#L2502-L2504).

The banner disappears when background liveness clears or foreground work resumes. Its Stop control requests interruption; the pending stop label remains until liveness clears rather than assuming request acceptance means completion. [Banner stop lifecycle](https://github.com/pingdotgg/t3code/blob/adcd90858c3bfece59095465d2f49860ba3dcea9/apps/web/src/components/ChatView.tsx#L6230-L6265). Existing source tests cover agent precedence, monitor completion, missing task types on completion, idle tasks, nested ownership, reclassification, and session clearing; these tests were read, not executed. [Tests](https://github.com/pingdotgg/t3code/blob/adcd90858c3bfece59095465d2f49860ba3dcea9/apps/server/src/orchestration/ThreadBackgroundLiveness.test.ts#L4-L228).

## Recommendation for Sotto

Drop the arbitrary ten-second buffer only together with a positive lifecycle signal for a recognized watch task. Ordinary commands, generic busy/running state, and merely launching a background server should not be enough. This recommendation is a Sotto design inference, not a claim about T3 behavior.

T3 supplies a useful lifecycle pattern, but copying it exactly would show the creature only after foreground work settles and would count unattended surviving shells. That does not fully match Zach's request for a creature while the agent is monitoring. Provider-specific proof of watch activity remains necessary for that stricter behavior. Short confirmed watches can still appear without a timing rule; lifecycle classification removes ordinary short commands but cannot guarantee that every brief watch stays hidden.

No production integration or prototype behavior was changed by this study.

Follow-up decision: Zach agreed to remove the arbitrary buffer and require confirmed active monitoring. The separate creature prototype was subsequently updated to demonstrate this; production integration remains pending. The study above records the source behavior, not a production verification.
